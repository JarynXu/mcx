# 离网 MCPTT：一直不活动，整通呼叫怎么结束？

**离网 MCPTT 服务须在一段不活动之后结束整通呼叫。** 服务还须给 MCPTT 管理员提供预先设置不活动定时器的机制。一个说何时结束呼叫，一个说谁能预设定时器。听见发话停止不等于呼叫已结束；有一份定时器配置也不证明本次已到期。（TS 22.179 V20.0.0，Release 20 Stage 1，R-7.4-001/-002，印刷页 65）

先确认这次 MCPTT 是[离网运行](off-network-direct-path.md)。有网络覆盖也能选用离网直通；只看覆盖状态，不能决定该用哪条要求。

## 结束的是一次发话，还是整通呼叫？

| 已知的事件 | 对照的要求 |
| --- | --- |
| 离网发话者表示不再发话，或接收者收到发话结束提示。 | §7.3.4：对象是[离网发话结束](off-network-transmit-stop-and-time-limit.md)，不是整通呼叫。（页 64） |
| 离网一次发话申请对应的发话时长达到上限。 | §7.3.5：对象是[单次发话时限和话权](off-network-transmit-stop-and-time-limit.md)，不是 §7.4 的呼叫不活动时长。（页 64–65） |
| 离网服务中的整通呼叫经历了一段不活动。 | §7.4：结束这通呼叫。-001 不把某一位结束发话、释放话权或收到提示写成直接拆话的条件。（页 65） |

[在网发话结束和单次发话时限](floor-permission-end-and-transmit-limit.md)另有 §6.2.3.4/.5。不要把在网终止发话许可的角色和提示当成 §7.4 的拆话条件。

## 定时器能按 Hang Time 计算吗？

**仅凭 §7.4，不能算出这个定时器何时开始或何时到期。** 该节没定义哪些事件算活动、何时起停或复位，也没给时长默认值、计时点的报文或各终端如何确认呼叫已结束。只看到最后一个 RTP 包、一段录音无声或一条发话结束提示，都不足以按这节计算。

§3.1 把 **Hang Time** 定义为同一呼叫中连续两次传输之间的可配置静默上限；§4.3 的组呼概述说，前一次传输结束时开始计时。若下一次传输在这段不活动期间内开始，计时器停止并复位，等这次传输结束再启动。在网 R-6.2.4-003 明写 **Hang Time 到期后**结束呼叫；在网 R-6.4.9-002 给管理员预设带话权通话无流量时段的机制。§7.4 没用这个名字，也没把概述的计时起停带入离网要求。术语相近不能替代本次离网活动或到期的证据。（页 10、16、41、43、65）

在网呼叫达到**呼叫总时限**时也有单独的释放要求（R-6.2.4-006，页 41）。[在网 ad hoc 组呼的挂起时长字段](../identity/ad-hoc-broadcast-hang-time.md)是 Stage 3 配置。两者都不为 §7.4 定义离网定时器。

## §7.4 有四个 Void，前两条还有效吗？

**有效。** 本版 TS 22.179 的 R-7.4-001/-002 是上面的两条现行要求；-003 至 -006 为 Void。资料性附录 A1 把这四条依次指向 **TS 22.280 的 R-7.4-001 至 -004**。右栏的 -001/-002 虽与本页这两条现行编号写法相同，却属于另一份规范。本页只核迁移入口，没核 TS 22.280 的目标正文。（引言、§7.4、附录 A1，页 8、65、69、81）
