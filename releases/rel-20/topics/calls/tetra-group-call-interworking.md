# MCPTT 与 TETRA 组呼互通：验哪些能力，谁能发起抢占？

**普通组呼、应急互通、端到端加密组呼分开验。查抢占时，先看发起者的授权。**加密组呼条款对 MCPTT 用户列了两个条件：支持 TETRA 语音编解码，也支持端到端加密。

依据：3GPP TS 22.179 V20.0.0，Release 20，Stage 1，第 6 章在网。以下七条在 §6.18.3.3、印刷页 59。

## 接通多台，不等于能接多套 TETRA 系统

MCPTT 服务须支持与符合 **ETSI TETRA 标准**的非 3GPP PTT 系统互通（-001）。这是支持要求，不指定部署时默认开启。互通还须覆盖**多套独立管理的 TETRA 系统**（-002）；-002 括号所指的是交换和管理基础设施（Switching and management Infrastructures，下文简称 SwMI）。接通同一套系统下的多台移动台，只能说明这些设备接通；并不能证明能接多套独立管理的系统。本条不要求每通呼叫都跨多套，也没指定管理方或网络拓扑。

## 普通组呼、应急互通和加密组呼分开验

| 场景 | 本条要求 |
| --- | --- |
| **普通组呼（-003）** | 须支持 MCPTT 用户与 **TETRA 移动台和控制台**之间的 MCPTT 组呼。普通组呼已通，不是后两项的证据。 |
| **应急（-004）** | 须支持 **MCPTT 应急组呼**与 **TETRA 应急呼叫**的互通。原文没有把 TETRA 端写成某一种应急组呼，也没有规定应急状态、优先级或告警如何映射。 |
| **端到端加密组呼（-005）** | 须支持 MCPTT 用户与 TETRA 移动台和控制台之间的端到端加密 MCPTT 组呼；用于此类组呼的 **MCPTT 用户须同时支持 TETRA 语音编解码和端到端加密**。只有一项不能认作满足本条所列条件。各段链路分别加密也不证明这次呼叫端到端加密。 |

-005 不要求每通组呼都加密。它写的是这类互通场景，不能把两个条件套到普通组呼的 -003，也不能拿来改写[一般 MCPTT 终端的编解码支持要求](mcptt-voice-quality-mos-lqo.md)。条文未指定密钥分发、转码或网关处理。

## 谁能发起抢占

- **-006：获授权用户。**互通须给获授权用户提供发起混合 PTT 组呼抢占的手段。原文没指明该用户的端型，不能改成“只限 MCPTT 用户”，也不能从本条列出更多端型。
- **-007：获授权的 TETRA 移动台或控制台。**互通另须给这两种端型提供发起这类组呼抢占的手段。这里是移动台**或**控制台；不要求同一通呼叫同时有两种端型。

这里写的是**发起混合 PTT 组呼抢占**，不是实际已抢占、撤掉谁的话权或接收方播放哪路。这两条没指定由谁授予权限、怎样授权。别套用 [P25 组呼的 MCPTT 管理员授权机制](p25-group-call-interworking.md)；要查 [TETRA 带话权私呼的抢占](interworking-private-call-override.md)，也要换到私呼条款。重组、用户标识和其他 TETRA 条款不在本页范围。
