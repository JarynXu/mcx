# MCPTT 在网私呼：振铃、用户接听和 UE 确认各说明什么？

**手动开始，等被叫用户接受建呼请求，呼叫才继续。自动开始，不等被叫用户操作；被叫 UE 仍须确认收到建呼请求，音频传输要等这项确认。** 两种要求都适用于在网有话权控制和无话权控制的私呼。不同的是谁要做什么，以及它卡在哪一步。

依据：3GPP TS 22.179 V20.0.0，Release 20，Stage 1。术语见 §3.1，印刷页 10；两种私呼的概述和要求见 §5.6.1/.3、§6.7.1/.4，印刷页 25–26、45–46。

| 已知场景 | 查什么 | 有话权 / 无话权 |
| --- | --- | --- |
| 手动开始的私呼 | 看被叫**用户**是否接受本次建呼请求。响铃、收到请求或拒绝都不等于接受。 | R-5.6.3-007 / R-6.7.4-006 |
| 自动开始的私呼 | 看被叫 **UE** 是否确认收到本次自动建呼请求。确认收件是音频继续的前提，不等于用户按下接听，也不证明语音已经送达。 | R-5.6.3-013 / R-6.7.4-012 |
| 在手动开始模式下请求自动应答 | 服务须提供机制，让获授权的 MCPTT 用户请求被邀 UE 自动应答。有权限、提出请求、UE 实际应答是三件事。条文没有把提出请求定为自动应答已经发生。 | R-5.6.3-011 / R-6.7.4-010 |

## 主叫知道“对方收到”不等于通话已建立

有话权私呼的 R-5.6.3-012 要求服务提供一种通知：**获授权的主叫用户**可获知被叫 **MCPTT 用户**收到了私呼请求。它没有限定手动或自动开始。不能只凭这项通知认定被叫用户已接受，或被叫 UE 已发出本次自动建呼所需的收件确认。无话权 §6.7.4 的 R-6.7.4-011 是 **Void**；不能把有话权这项通知搬过去当要求，也不能据此断言不允许通知。资料性附录 A1（印刷页 77）把这条指向 **TS 22.280 的 R-6.7.5-003**。同页下方私呼终止节的另一条箭头，左端也写 R-6.7.5-003，那是 TS 22.179 本地私呼终止条目的编号，不是这个查找目标。这里只核映射，未核 TS 22.280 对应版本的目标正文。

两类私呼的 UE 都须支持手动和自动开始（R-5.6.3-010 / R-6.7.4-009）；支持不说明一次呼叫实际用了哪个模式。§5.6.1 说，自动开始时，如果被叫可用且能接受该来电，就会立即加入并处理主叫音频。这段概述没有取消收件确认的要求。

**先查同一通呼叫的模式和证据，再判所处步骤。** 这些要求不指定 SIP ACK、200 OK、话权许可或终端界面应当怎样对应。若查的是发起端计时在哪个事件停止，读[接入 KPI](mcptt-access-clock.md)；若主叫指定多个候选用户，读[首应答规则](private-call-first-to-answer.md)。 若被叫拒接或忽略，或参与者要结束已建私呼，读[带话权私呼的三个动作](private-call-user-termination.md)。
