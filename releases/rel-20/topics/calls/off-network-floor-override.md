# 离网 MCPTT 话权抢占：原发话者一定被撤权吗？

**不一定，先看离网组呼生效的配置。** 组只准抢占者发话时，服务须撤销被抢占者的发话许可。组允许双方发话时，服务须按配置提供机制，让获授权的接收参与者能收听抢占和被抢占的发话。发话许可与接收者听到哪路是两件事。（TS 22.179 V20.0.0，Release 20 Stage 1，§7.3.3，印刷页 64）

## 谁有条件抢占正在进行的发话？

- **终端先预配。** MCPTT 管理员和／或获授权用户须给终端配置运行离网话权抢占所需的信息。管理员另外通过服务设置用于抢占的优先级层级，决定哪些参与者、参与者类型和紧急传输类型的抢占请求可获准。层级至少四级，不是至少四人同时发话。（R-7.3.3-001 至 -003）
- **比较相对优先级。** 请求针对正在进行的发话，且抢占方参与者或呼叫类型的优先级严格高于当前发话方参与者或呼叫类型的优先级时，服务须提供抢占机制。相等不满足这个条件；该条没有决定并列怎么裁，也没有规定参与者优先级和呼叫类型冲突时谁先。配置了机制或提交较高优先级的请求，不等于本次抢占已经发生。（-004）
- **通知被抢占的一方。** 获授权的参与者实际抢占后，服务须提供通知被抢占参与者的手段。只有申请、只知道申请者获授权，或看到服务具备通知手段，都不能说本次通知已送达。（-005）

## 发送侧能发什么，接收侧要呈现什么？

| 实际场景 | 查哪项要求 |
| --- | --- |
| 获授权的参与者抢占了离网组呼中的发话。 | 服务须提供机制供 MCPTT 管理员配置接收参与者收到哪种组传输：抢占方、被抢占方或两者。配置不证明本次传输送达或播放。（-006 前半） |
| **离网组呼中，发送侧话权控制失效，已经发生未获授权的抢占。** | -006 前半所说的离网组传输接收机制，在接收参与者侧也须决定向用户呈现哪路传输。这只是接收呈现的要求，不是授权或恢复发送话权；一次未获授权的尝试、只有控制故障，或只观察到两路音频，都不能单独认定命中这一分支。（-006 后半） |
| 组配置只允许抢占方发话。 | 服务须撤掉被抢占发话者的发话许可。撤权不证明接收端已停播，也不等于整通呼叫已结束。（-007） |
| 组配置允许抢占方与被抢占方都发话。 | 服务须按配置提供机制，让获授权的接收参与者能收听两方发话。不能扩大到所有听众，也不能仅凭并发许可推断本次收到两路或要求混音。该条没给连续抢占时的传输路数上限。（-008） |

## 一对一私呼，能照搬组呼配置吗？

**不能拿组呼这几条证明私呼也有同样的配置。** §7.1 概述同时提到离网组呼与一对一私呼；[离网话权申请](off-network-floor-request-outcomes.md)的 R-7.3.2-005/-006 明列带话权私呼的申请结果。这不能证明本次允许抢占。§7.3.3 的 -001 至 -005 没把叙述限定为组呼；-006 的组传输配置及 -007/-008 的双路分支却写明了组对象。相比之下，**在网** R-6.2.3.3.1-004 单独写出带话权私呼的单双方发话配置。不能用那条填补离网私呼的规则，也不从这里宣称离网私呼禁止抢占。（页 36、62、64）

在网[组内插话](group-audio-cut-in.md)和[多发话者组](group-multi-talker-control.md)有各自的触发条件。不要把“最新请求拿唯一话权”或“超过同时发话人数才抢占”套到离网 §7.3.3。若问何时收掉整通离网呼叫，查[离网呼叫不活动终止](off-network-inactivity-call-termination.md)。这些是业务要求，不指定话权报文、混音方式、分布式仲裁算法或设备实测结论。
