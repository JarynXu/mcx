# MCPTT 发起紧迫险情组呼时，终端须能发位置更新吗？

**须提供发送能力。** TS 22.179 V20.0.0 的 R-5.12-011 要求：每当 MCPTT 用户发起紧迫险情组呼（Imminent Peril Call），MCPTT 服务须提供一种办法，让 MCPTT 终端能发位置更新。第 5 章的要求在网、离网共用。这里说的是**发起组呼时须有发送手段**，不是已经建呼才适用，也不是终端每次都已自动采集、发送或送达。（§3.1、第 5 章、§5.12，印刷页 10、22、31）

§3.1 所说的位置是 MCPTT 终端当前的物理位置，含坐标、估计精度和时间戳。这是术语定义，不是 R-5.12-011 指定的报文字段。该要求没有指定接收方、传输方式或是否重新测量，也不能据这条判断用户、管理员或应用能否读取他人位置。

## 三种位置证据，不是同一操作

| 场景 | 查哪条 |
| --- | --- |
| MCPTT 用户发起紧迫险情组呼，查终端能否发位置更新。 | **业务要求 §5.12。** 发起是 R-5.12-011 写明的场景。§5.7.1 另说组呼获准会开启该组的进行中险情状态。只看到组状态、有人迟入或某次呼叫成功，不能替代对发起事件和更新的核对。 |
| 查紧急告警里的位置。 | **概述 §5.7.1。** 紧急告警由终端向 MCPTT 服务发出，其中包括该用户终端当前可获得的最新位置。概述没有要求告警前重新测量。紧迫险情组呼不是这个告警；概述写明没有 MCPTT Imminent Peril Alert。（印刷页 28） |
| 查离网通话里，迟入者能否获得发话者的位置。 | **离网能力描述 §7.1。** 离网 MCPTT 终端能够把发话者的位置等信息送给通话中的其他所有用户，包括迟入这通进行中通话的离网终端。发话者是其终端正在发送的用户。该段没写迟入者须先查询位置，也不证明某位迟入者实际收到了位置。（印刷页 63） |

[离网不是只指没有网络覆盖](off-network-direct-path.md)：§7.1 也描述在有覆盖时选用 ProSe 直通的情形。用户要能直通通信，须在 ProSe 直通通信范围内；在范围内不等于已经收到位置。该节所列 MCPTT 管理员和获授权用户是为离网使用预配终端的角色，不是查阅别人位置的权限名单。不能把离网发话者位置的接收范围或直通方式套到 R-5.12-011。（印刷页 61–63）

## 在网位置条款标 Void，去哪里查？

- **R-5.12-011 仍是本版的业务要求。** §5.12 的其余 14 个编号标为 Void。资料性附录 A1 的 `R-5.12-010 → TS 22.280 R-5.11-011` 是另一条的映射，不是本条的迁移位置。（印刷页 31、69、72）
- **在网 §6.12 的七个位置编号均为 Void。** A1 将它们指向 TS 22.280 的同号条目。同页 §6.11 的三个多终端编号也为 Void，不能用它们判断哪台终端应发送位置。离网 §7.9 的 R-7.9-001 同样为 Void，A1 指向 TS 22.280 R-7.8-001。本页只核到这些入口，没用目标正文补出位置查询、授权或上报流程。Void 不是禁止位置功能。（引言、第 6、7 章、§6.11、§6.12、§7.9、附录 A1，印刷页 8、33、50、61、66、69、79、82）

这是 Release 20 **Stage 1** 的业务要求。[位置用户配置的 XCAP 取档](../identity/location-user-config-xcap.md)是 **Stage 3** 的另一件事。取到配置不证明发起组呼时已上报；本页也不规定 LMS 注册、配置下发、位置查询、传输报文或适用的系统应用权限。
