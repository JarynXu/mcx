# MCPTT 在网私呼：回叫请求是谁发的，终端收到什么？

**A 是原主叫，B 是原被叫。**回叫请求让 A 请 B 方便时尽快给 A 打个呼叫。服务须提供发出这种请求的机制，不是收到请求就自动拨号。条文没把它限于未接、失败或手动开始，也没设 B 必须回叫的时限。（R-6.7.6-001）

依据：3GPP TS 22.179 V20.0.0，Release 20，Stage 1，§6.7.6，印刷页 47。第 6 章是在网要求。§6.7.0 涵盖带话权和无话权私呼，无话权只支持在网；§6.7.6 没有另限无话权，也不能套到离网带话权私呼。（印刷页 33、44–45）

## 紧急度由谁设，谁该收到什么？

| 条件 | MCPTT 服务须提供 |
| --- | --- |
| 原主叫给回叫请求指定紧急度（R-6.7.6-002） | 可给任何回叫请求指定低、普通或紧急（low、normal、urgent）的机制。条文未规定每次必设或没设时默认哪档 |
| MCPTT UE 收到回叫请求（R-6.7.6-003） | 给**收到请求的这台 UE**提供原主叫指定的回叫紧急度指示 |
| MCPTT UE 收到回叫请求（R-6.7.6-005） | 给**收到请求的这台 UE**提供指示：哪位 MCPTT 用户呼叫过、何时呼叫 |

“何时呼叫”不等于回叫请求发送或到达的时间。服务需要给接收 UE 哪些信息，与该 UE 实际收到了什么、用户有没有看到，是两回事。只凭主叫发送过，不能认定被叫的任一 UE 已收到；原文也没指定要显示在哪、不规定显示形式或时间戳编码。

**回叫紧急度是请求的标记。**不能用 urgent 推定回叫按更高接入优先级建呼、触发应用层抢占、授予话权或把呼叫变成紧急私呼。查[在网接入与应用层优先级](on-network-call-access-priority-and-preemption.md)或[带话权紧急私呼](emergency-private-call-state.md)，用对应条件判断。（§6.8.1、§6.8.6.2、§6.8.7.2，印刷页 47–49）

## 取消的是回叫请求，不是已经建立的私呼

R-6.7.6-004 要求服务给 **MCPTT 用户**提供取消回叫请求的机制。句子没指定只能由原主叫或原被叫来取消，也不足以认定任一用户可以取消任一请求。没写取消需要的状态、通知或已经发生的处置。若 B 已经在呼叫 A，取消请求不能当作结束这通私呼。取消还没建立的普通私呼请求、拒接和挂断已有呼叫各查它们自己的条件，见[私呼开始与收件确认](private-call-commencement-evidence.md)及[私呼的拒接、忽略和结束](private-call-user-termination.md)。

**同编号先看规范。**TS 22.179 本版 §6.7.6 的 001–005 是在网回叫请求条款。资料性附录 A1 给本节列的是 NA；前一节 §6.7.5 的两个 Void 编号映射到 **TS 22.280** 的 R-6.7.6-001 和 -002。这里只核编号分流，不用别规范的同号替换本节，也未核映射目标正文。（印刷页 47、69、77）
