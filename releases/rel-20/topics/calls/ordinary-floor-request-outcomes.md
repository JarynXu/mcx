# MCPTT 普通在网话权：谁该收到申请结果或开始发话提示？

**申请结果提示给发话一侧；开始发话提示给接收参与者。**同一组呼里，申请者看到“可以发话”，不等于别人已收到开始提示或已经听到音频。

依据：3GPP TS 22.179 V20.0.0，Release 20 Stage 1，§6.2.3.2（印刷页 35–36）。本页查在网的一般申请规则，组呼按普通模式举例；已配置插话或多发话者控制的组另看其专用条款。

## 先看申请的是哪种呼叫

获授权的参与者须能向组或单个参与者申请发话。**同一呼叫**里出现同时申请，话权控制须确定由谁发话；只看到申请，不能认定谁拿到了话权。本节没有指定同时间请求的赢家或裁决算法。（R-6.2.3.2-001/-003，页 35）

| 观察到什么 | 该提示谁、提示什么 |
| --- | --- |
| 已归属普通组的成员向自己选中的同一组申请发话，且实际获准或未获准。 | 给**提出请求的该成员**结果。获准则提示可发话；未获准则提示其申请被拒绝还是排队。只选中组、未核归属，不能据此套用这两条。没有许可也不能直接当作拒绝。（-004/-005，页 35–36） |
| 在带话权的私呼中提出发话申请。 | 给**获准发话的用户**提示可向目标 MCPTT 用户发话；给未获准的用户提示被拒绝还是排队。不把组成员归属或选中组加到私呼条件，也不把给发话侧的提示当作被叫已经接受呼叫。（-007/-008，页 36） |

这几条只要求提示获准、拒绝还是排队，并未再要求给出拒绝原因、队列位置或位置查询。**不是禁止提供这些信息。**已配置多发话者控制的组排除 §6.2.3.2；拒绝原因、排队位置和已排队成员按需查询位置另按 §6.2.3.7.1/.3（页 39–40）。

## 别把建呼提醒与开始发话提示混用

- **普通组呼建呼时，没有其他组员已归属此组。**服务须提醒正尝试发话的组员，例如用声音、视觉或两者提示。没收到别人的建呼确认，不等于没有其他已归属成员；这个提醒也不是拒绝话权的结果。（-002，页 35）
- **发话参与者开始发话。**服务须向接收参与者给出开始提示。给发话一侧的许可、给接收侧的开始提示、接收侧实际听到音频，须分别核对。（-009，页 36）

## 排队要查的是谁、哪笔申请

普通话权队列的深度须可配置；组队列另须提供管理员配置定时器的机制。这是两个配置要求，条文没给默认值。（-006/-012，页 36）

参与者须能从队列移除**自己的申请**。服务还须具备在该申请被接受、被拒绝或定时器到期时将它移出队列的机制。这三个是各自的条件，不需要等三者都发生。移出队列本身不能说明是哪种原因，更不能证明已发话或整个呼叫结束。（-010/-011，页 36）

[已配置组内插话](group-audio-cut-in.md)不支持话权排队，却仍有获准和开始发话的专用提示要求。不要把该组的“最新请求”规则套给普通组。若现场没有确认组的生效模式，先依据配置核对，不从队列提示反推模式。（§6.2.3.6.1/.2/.3，页 37–38；[多发话者组](group-multi-talker-control.md)另查）

**排障时分开留证。**先核本次在网呼叫、组模式与成员归属，再把同一笔申请的结果和相应一侧提示对上。要查[发话结束或单次发话到期](floor-permission-end-and-transmit-limit.md)，不要用本页的开始提示代替。本页不规定 SIP 或话权报文、队列排序和提示的交付机制，不从一侧日志推断其他人已收到或应用已播放；不外推到离网或无话权私呼。
