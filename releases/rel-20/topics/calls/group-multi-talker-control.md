# MCPTT 在网多发话者组：什么时候抢占，降低人数上限要撤谁？

TS 22.179 V20.0.0，Release 20，Stage 1。以下规则适用于已配置多发话者控制的在网组，包括启用这一模式的 ad hoc 组。组须支持配置该模式，但不是每个组默认开启。§6.2.3.7.1 排除 §6.2.3.1、.2、.3 和 .6 的话权规则，保留 §6.2.3 的其他要求。若核实待判断的在网组呼适用[普通话权抢占](on-network-group-floor-override.md)，查该页。只知多发话者模式未启用或配置未知，不能确定走普通抢占。已配置多发话者控制时，也不搬用[组内插话](group-audio-cut-in.md)的“最新请求获唯一话权、不排队”。（§6.2.3.7.1、§6.2.3.7.2，印刷页 39）

**先看人数超限的原因：是申请发话的人多了，还是通话中把上限调低了？**

| 发生什么 | 按哪条判断 |
| --- | --- |
| 请求发话的用户数超过该组允许同时发话的人数。 | 服务须采用本模式的抢占机制。上限为 2、申请者有 3 名时触发。申请者恰有 2 名并不满足这条的超限条件，也不能推出两人必定获准。发话人按参与者与呼叫类型的相对优先级决定；相对优先级不足的请求须拒绝，不能因为有排队功能就把这一分支改为排队。参与者或呼叫类型的优先级相对当前发话人或其呼叫类型更高时，服务须提供抢占活动发话的机制；优先级较高不等于已经抢占。（§6.2.3.7.4.1，R-6.2.3.7.4.1-001、-004 至 -006；印刷页 40） |
| 授权用户在组呼中调低并发发话上限。例如从 3 调到 2，此时仍有 3 人获准发话。 | 撤回发话许可，直到不超过新上限。调低上限这条规则的注把撤谁留给实现，不要求按普通或本模式的抢占优先级撤最低者，也不能从调低上限推断有新的抢占请求。（§6.2.3.7.2，R-6.2.3.7.2-008 及注；印刷页 39） |

管理员能配置组的并发发话上限，并能为抢占活动发话设置优先级层级。**至少四级**说的是抢占优先级层级，不是默认或最少四人同时发话。获授权的 MCPTT 用户可以在组呼中改变并发上限，也可以改变发话者的优先级层级；不用同时改两项。（§6.2.3.7.2，R-6.2.3.7.2-005 至 -007；§6.2.3.7.4.1，R-6.2.3.7.4.1-002/-003；印刷页 39–40）

## 建呼时没有其他归属组员，提醒谁？

**提醒正在尝试发话的本组组员。**已配置多发话者控制的在网组建呼时，如果没有其他组员归属（affiliated）该组，服务须向这位组员给出提醒。声音、视觉或两者一起都是例子。这条不另要求尝试者本人已归属、已选中该组或已拿到话权。（R-6.2.3.7.3-002，页 39）

例如，B 已归属该组，只是没有发话、没有听到音频，或者没回[建呼确认](group-call-setup-acknowledgement.md)。这些情况都不能把 B 算作未归属。这里数的是**同组其他归属成员**，不是申请发话的人数或正在发话的人数。不能用这个提醒认定并发上限已满、发话被拒或排队、发生了抢占，或终端实际收到、播放了音频。

[在网普通组](ordinary-floor-request-outcomes.md)和[插话组](group-audio-cut-in.md)也有各自的建呼提醒；先核实生效模式，不靠提醒的文字辨认。那两页给接收参与者的开始发话提示也不是本条给发话尝试者的提醒。（§6.2.3.2-002/-009、§6.2.3.6.3-002/-004、§6.2.3.7.1，页 35–36、38–39）

## 发话申请的结果给谁？

获授权的参与者可以请求发话。若同一呼叫内同时有发话请求，服务须确定哪些参与者发话，本节没有给出优先级并列时的裁决算法。选中该组、已关联（affiliated）的组员提出请求后，按**实际结果**提示：

- 已获准：提示该申请者可以发话。
- 已拒绝：给该申请者拒绝原因。
- 已排队：给该申请者在队列中的位置；已在队列的关联成员，还应能按需查询位置。注把排队机制留给实现，不规定排队顺序，也没有规定每次位置变化都主动通知。

（§6.2.3.7.3，R-6.2.3.7.3-001、-003、-004/-004a/-004b、-005 及注；印刷页 39–40）

确认抢占时另看结果：授权参与者实际抢占了活动发话，服务须提供通知被抢占者的方式；对被抢占的发话人，服务须撤回发话许可。可通知不等于已经送达，撤回发话许可也不证明整个组呼结束或实际音频已经停止。（§6.2.3.7.4.1，R-6.2.3.7.4.1-007/-008；印刷页 40）

验收时分别核对该组生效的模式与上限、同一呼叫的请求和实际许可。服务须支持多人同时发话并让每个参与者可接收其他发话者的音频；该能力不是这一次实收、混音方式、SIP/话权报文或离网行为的证明。迟入的计时另查[在网组呼迟入](late-call-entry-kpi.md)，不由本节推出。（§6.2.3.7.2，R-6.2.3.7.2-002 至 -004；印刷页 39）
