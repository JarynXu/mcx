# MCPTT 带话权紧急私呼：一定发告警吗？取消优先级时退出紧急状态吗？

TS 22.179 V20.0.0，Release 20，Stage 1。主规则在第 5 章，在网和离网共用；不展开离网直通流程。这里区分一通私呼的紧急优先级、用户本人的紧急状态和一整个组的紧急状态。

**用户发起带话权的紧急私呼，发起人须进入紧急状态；Emergency Alert（紧急告警）则可能触发，不是必发。** 规范要求服务支持获授权用户发起这种私呼。支持发起或看到一次普通私呼，不等于发生了这一次紧急私呼发起。没有看到告警，不能据此否定发起人已进入紧急状态。（§5.7.2.3.1，R-5.7.2.3.1-001 至 -003；印刷页 30）

离网时，-001 的注说明，使用该功能依赖**被叫 MCPTT 用户**位于 ProSe 通信范围内。只知道主叫的位置或状态不能替代这个前提；被叫在范围内也不证明私呼已建立或告警已送达。

## 取消私呼优先级和取消本人状态是两件事

| 标准说的动作 | 可以判断什么 |
| --- | --- |
| 授权 MCPTT 用户取消一通带话权紧急私呼的优先级。 | 服务须支持取消**这通私呼**的紧急优先级。是否由原发起人操作，要看这个用户是否具备授权；条款并未把操作人限定为发起人。 |
| 达到 MCPTT 管理员设定的条件。 | 服务还须支持按此取消这通私呼的紧急优先级。超时是例子，不是默认计时器；这条不用再等一位授权用户手动取消。 |
| MCPTT 用户取消自己的紧急状态。 | 服务须支持用户取消**本人**的 Emergency State。概述把用户的状态描述为持续至本人取消。 |

依据：§5.7.2.3.2，R-5.7.2.3.2-001 至 -003（印刷页 30）；§5.7.1 概述（印刷页 28）。**私呼优先级已取消，不足以判断用户已退出紧急状态。** 反过来也一样。不要据此判断告警是否已撤、私呼已挂断或媒体是否继续。

## 组的紧急状态另看组呼

Emergency Alert 是 UE 向服务发出的通知。**In-progress Emergency** 是服务已接受、尚未由授权用户取消的组紧急状态。§5.7.1 把启动这个组状态的事件写成开始紧急组呼。它也描述了先有组呼、后有对应告警而转为紧急组呼的情况。若告警包含组 ID，紧急组呼用同一 ID。用户或调度员也可能不经告警发起紧急组呼。单看一条告警或一通私呼，不能证明某个组已进入或退出紧急状态。概述说，对仍处于该组状态的组，组成员随后发起的组呼按紧急组呼对待；组状态取消时移除组的紧急优先级。（§3.1、§5.7.1，印刷页 10–11、28）

在网时，§6.8.7.2 的 R-6.8.7.2-003 要求具备把进行中的带话权私呼转为紧急私呼的能力。这不是证明某次转换已经发生，也不单独说明该次转换是否触发告警、改变用户状态或启动组状态。（印刷页 49）

本版 §5.7.2.1.2 的组呼取消、§5.7.2.4.1/.2 的紧急告警与取消编号标为 Void。资料性附录 A1 给出 TS 22.280 的对应编号，例如 R-5.7.2.1.2-001 → R-5.6.2.2.2-001、R-5.7.2.4.2-001 → R-5.6.2.4.2-001。这里只保留查找入口，未核目标正文；Void 不是禁止实现，也未让 §5.7.2.3 的私呼要求失效。不从这些业务条件补出 SIP、操作鉴权细节或状态同步规则。（印刷页 29–30、69、71–72；引言印刷页 8）
