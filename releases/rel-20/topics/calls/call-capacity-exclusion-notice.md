# MCPTT 在网通话：因容量不足被排除，谁必须收到通知？

**MCPTT 用户因容量不足、无法参加而被排除在呼叫之外，服务须确保被排除的用户收到通知，并说明是容量不足。**给发起者提示、服务器记下原因或只看到通知已发，都不能代替这些用户收到通知。（R-6.2.1-015）

依据：3GPP TS 22.179 V20.0.0，Release 20，Stage 1。第 6 章是在网要求。-015 在 §6.2.1「MCPTT 组呼的开始方式」节，印刷页 35；本句写的是「MCPTT 呼叫」，没在句内另写组呼、只限第一次建呼、无需确认或已归属。按这句查实际的容量排除，不把节标题或句内未细分的呼叫类型当成所有私呼、迟入或离网也按同一流程的依据。（印刷页 33–35）

## 别把「发起者知道缺人」当成「被排除者收到通知」

| 已知发生什么 | 查谁获得什么 |
| --- | --- |
| **一名或多名用户实际因容量不足被排除（-015）** | 服务须确保**这些被排除的 MCPTT 用户**收到通知，知道这次没能参加是因为容量不足。只知道某成员没参加、服务满载或他的话权没获准，均不足以证明这项排除。 |
| **无需建呼确认的组呼，服务已知有已归属组员不能参加（-014）** | 服务须向**请求者**提示呼叫在未包含全部已归属成员的情况下继续，并按管理员策略提供缺席名单。条文未要求这些成员不能参加的原因是容量不足。[组呼建呼确认](group-call-setup-acknowledgement.md)有这条及确认超时的区别。 |
| **参与者已在进行中的呼叫中，因容量不足无法继续参加而被抢占移出（R-6.2.4-002）** | 服务须确保**被移出的用户**收到通知，说明因容量不足被移出。仅见呼叫已有 active 状态，不证明受影响的用户此前已经参加或被抢占。读[在网呼叫终止](on-network-call-termination.md)判断移出及给发话者的另一路提示。（印刷页 40） |

例如，无需确认的组呼中，服务已知已归属的 B 不能参加，并确认 B 因容量不足被排除。按 -014 核服务应向请求者提供的提示和名单，按 -015 核服务是否确保 B 收到容量原因。前一项提示不能证明后一项已做到。-015 没规定发送几条消息、终端怎么显示或用什么确认报文；这条也不决定整通呼叫是继续还是结束。
