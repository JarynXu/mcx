# 非 3GPP 互通私呼：有话权控制，就一定能抢占当前发言吗？

**有话权控制，不等于支持私呼抢占。**查 P25 互通时，先确认这是带话权控制的私呼，再看对端系统有无私呼抢占能力。无此能力、且参与者尝试抢占时，要求通知**尝试者**无法完成；有此能力时，这一分支要求提供抢占机制，条件是其优先级**严格高于**当前发言者，且要抢占的是正在进行的 MCPTT 发送。这不是抢占已经发生的证据。

依据：3GPP TS 22.179 V20.0.0（Release 20，Stage 1），第 6 章的在网业务。以下比较 §6.18.3.2 至 §6.18.3.4 各自列出的要求。

## P25：能力不同，验收点不同

§6.18.3.2 适用符合 TIA-102 的 P25 系统（`R-6.18.3.2-001`）。本小节本来就要求在 MCPTT 用户与 P25 用户台或控制台之间互通带话权控制的 PTT 私呼（`R-6.18.3.2-014`），另用两条要求处理抢占：

| 实际情况 | 本版的要求 |
| --- | --- |
| **对端不支持私呼抢占，而且参与者已尝试抢占** | 通知该尝试者不能完成抢占。条款举 P25 Phase 1 为例，不要求在没人尝试时就主动发通知，也不规定用哪条报文或状态码。（`R-6.18.3.2-020`，p.59） |
| **对端支持私呼抢占** | MCPTT 服务须提供抢占正在进行的 MCPTT 发送的机制，前提是尝试者的优先级比当前发言者更高。条款举 P25 Phase 2 为例；优先级持平或较低不满足这条条件，不能从本条推出具体的拒绝方式。（`R-6.18.3.2-021`，p.59） |

P25 的[组呼互通与抢占授权](p25-group-call-interworking.md)另查。Phase 1/2 是原文例举，分支用的是**对端是否支持私呼抢占**。不知道对端能力，不能直接判作不支持，也不能因已建私呼便判作支持。

### 开始方式和端到端加密单独验

- **开始方式。**互通须有机制，协调 MCPTT 用户和 P25 用户台或控制台之间的**带话权私呼**开始方式（`R-6.18.3.2-015`）。本条没有把“两边模式已经不一致”写成提供机制的条件。出现不一致时，条文也没指定哪一边服从另一边、哪种模式优先，或用哪条信令协调。原生 MCPTT 的[手动接受和自动确认](private-call-commencement-evidence.md)不是 P25 的跨系统协调流程。
- **端到端加密。**互通须支持这两侧之间的**端到端加密、带话权** PTT 私呼（`R-6.18.3.2-016`）。普通带话权私呼接通，不能替端到端加密的场景验收。即使每段链路各自加密，也不能仅据此认定是两端之间的端到端加密。本条没要求每通都加密，也没指定密钥分发或处理方法。

-014、-015、-016 都在印刷页 58。它们分别验基本互通、协调能力和端到端加密支持；哪一项通过，都不替代其他项或上面的抢占条件。

核[编解码协调或被抢占者音频](p25-interworking-codecs-and-losing-audio.md)另读 -017 至 -019；这三项没写只限带话权私呼。

## TETRA 和传统 LMR：不要把旁边分支的条件搬过来

- **TETRA（ETSI TETRA 标准）。**`R-6.18.3.3-011` 列出 MCPTT 用户与 TETRA 移动台或控制台之间的 PTT 私呼，没有在该条写“带话权控制”。`R-6.18.3.3-014` 才用这一前提：对端支持私呼抢占，且尝试者优先级严格高于当前发言者，MCPTT 服务须提供抢占活动 MCPTT 发送的机制。这一小节没有另列 020 那样的“不支持时通知”。这不等于设备不通知，也不能只从这里判定另一小节下的通用措辞是否跨分节适用。（§6.18.3.3，p.59–60） 查 [TETRA 组呼和混合组呼抢占的发起](tetra-group-call-interworking.md)，不要套这一私呼分支。 若查 [TETRA 私呼端到端加密与编解码协调](tetra-private-call-encryption-and-codec-reconciliation.md)，另读 -012/-013。
- **传统 LMR（符合 TIA-603-D）。**`R-6.18.3.4-008` 明列 MCPTT 用户与传统系统的用户台或控制台之间的带话权控制私呼。该节另列的 `R-6.18.3.4-004` 至 `R-6.18.3.4-007` 讲的是有两侧参与者的混合 **PTT 组呼**：有给获授权的 MCPTT 用户发起抢占的机制，也有给获授权的 TIA-603 用户台或控制台发起抢占的机制；MCPTT 服务还须给管理员提供授权机制，分别为 MCPTT 用户和 TIA-603 用户台或控制台授权。组呼的两侧授权和抢占机制都不能移给私呼。§6.18.3.4 没有另列私呼抢占或相应失败通知要求，不能据此宣称设备禁止或不支持。（§6.18.3.4，p.60） [TIA-603-D 的 PTT 组呼、编解码和被抢占者音频](legacy-lmr-tia603d-voice-interworking.md)另查。

此处说明业务要求，不证明某个互通系统已启用哪种能力、已实现某个网关方案、已发送拒绝信令或已抢占成功。
