# MCPTT 在网组呼插话：谁拿话权，被打断的人要重新申请吗？

TS 22.179 V20.0.0，Release 20，Stage 1。这里的插话（audio cut-in）是指定在网组的组内话权规则。

**已配置插话的组，话权给选中该组、提出最新发话请求的组员。当前发话人若因此被打断，他原来的请求就结束，不排队，也不会等对方说完后自动继续。要再发话，得重新申请。**（§6.2.3.6.2，R-6.2.3.6.2-002/-004/-005，注 3；印刷页 38）

| 场景 | 按这组要求怎样判断 |
| --- | --- |
| 系统提供插话配置；不知道该组有没有启用。 | R-6.2.3.6.2-001 要求组可配置插话，不能当作它已经启用。获授权的参与者须能在已配置插话的组里申请发话；可以申请不等于已拿到话权。（§6.2.3.6.2/.3，R-6.2.3.6.2-001、R-6.2.3.6.3-001；印刷页 38） |
| A 正在说，B 选中该组并作出可辨先后的最新发话请求。 | 话权给 B。已配置插话的组同一时刻只允许一人发话；该模式不支持任何话权排队及相关功能。A 因请求被打断时，他的请求结束；不是结束整个组呼。（§6.2.3.6.2，R-6.2.3.6.2-002 至 -005；印刷页 38） |
| 两个发话请求同时收到。 | 注 2 把同时接收的请求交给厂商实现处理，没有指定谁拿话权。单人发话、不排队的要求仍在。两个终端显示相同的按键时间，不等于话权侧同时收到请求。（§6.2.3.6.2，R-6.2.3.6.2-002 后注 2、-003/-004；印刷页 38） |
| 某已加入该组（affiliated）的成员在自己选中的插话组发起请求，实际获准。 | 须向该申请者给出允许发话的提示。只看到申请，不能当作已经获准；获准提示也不说明其他成员已听到音频。（§6.2.3.6.3，R-6.2.3.6.3-003；印刷页 38） |

单人发话不等于打开了插话。普通抢占按参与者的相对话权优先级及呼叫类型优先级判断；组可配置成只留抢占者，或让抢占者和被抢占者都发话。不把普通抢占的更高优先级门槛加到插话的最新请求规则上。已配置多发话者控制的组走 §6.2.3.7；其概述将 §6.2.3.6 的插话规则排除在该模式之外。（§6.2.3.3.1/.2、§6.2.3.7.1，印刷页 36、39）

这是同一组内的话权，不是[另一呼叫打断环境监听](ambient-listening-interruption.md)，也不是[非 3GPP 互通私呼抢占](interworking-private-call-override.md)。

做一次验收时，把该组生效配置、实际同组请求、谁获准与原请求是否结束对到同一次事件。§6.2.3.6.1 的概述称最新请求立即获得话权，但没有给出毫秒门槛。本页不定义 SIP/话权报文、UI 样式、请求的精确排序时钟或音频交付，也不套用到离网组；离网时查[话权抢占条件和撤权](off-network-floor-override.md)。
