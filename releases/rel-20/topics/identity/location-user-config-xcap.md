# 位置用户配置：MC 服务客户端从哪个 XCAP 地址取档？

先查**生效的 MC 业务用户档**指向哪份位置用户配置。TS 24.484 V20.1.0 §7.4.1.1 允许位置档专用于一个业务或由多个业务共用；同一 MC UE 同一时点只生效并使用一份。共用时，各业务的生效用户档须指向**同一份位置档**。这一步不是 LMS 下发位置上报规则。

## 找引用，核对业务 ID 和文件号

MCPTT、MCVideo、MCData 的用户档均可在 `Common → anyExt → LocationUserProfileURI` 放一个可选的 `anyURI`，其值指向 §7.4.1.2 所定义的位置用户配置 XCAP 地址。§7.4.1.1 说明生效档与位置配置的引用关系，不把这三个结构条款的可选元素变成必填，也没有规定缺项时自动另找一份。（§8.3.2.1/.7、§9.3.2.1/.7、§10.3.2.1/.7）

§7.4.1.2 标题写的是 LMC 访问，正文给的是 **MC 服务客户端**访问该文档所用的 XCAP URI：

```text
CMSXCAPROOTURI/org.3gpp.mcs.location-user-config/users/sip:<MCSERVICEID>/location-user-config-<INDEX>.xml
```

XCAP 用户目录按已认证的 **MC 业务 ID** 定位。§7.4.1.2 要求用与该业务 ID 对应的文件名存入用户树下；§7.4.2.8 把文件名写成固定前缀加索引再加 `.xml`，如 `location-user-config-3.xml`。同一 ID 可以有几个索引不同的文件，生效档指向其中一份。不要把最大索引当成最新版本，也不要拿 MCPTT 用户档的 `user-profile-index` 替代这里的索引。

§7.4.2.8 用的是“`<index>` attribute”这一措辞。§7.4.2.3 的位置文档根类型没有单列名为 `index` 的属性，只有具名的 `domain` 和属性通配。这不能用来给位置文档添必填 `index`，或判定该属性一概不允许。

## 共用文档，不等于任意身份都能取

§7.4.1.2 写明专用或共用时使用同一 XCAP URI，同时给出的格式仍含业务 ID 和索引。共用首先核对各生效用户档是否指向同一文档，再核对授权：策略须能按 MC 用户认证时提供的任一业务 ID 取回共用文档；§7.4.2.11 另要求允许所有可使用该文档的 MC 业务 ID 访问。原文没有给出把目录里的 ID 换成任意 ID 的规则，也不能用“同一”断定两个独立文档的完整 URI 必相同。服务器内部的存储、复制或别名不由此确定。

§7.4.2.1 的结构文字要求至少一个 `mc-service-id`，列出文档对哪些业务 ID 有效；§7.4.2.3 的选择组及其中的 `mc-service-id` 却允许出现零次。不能用 Schema 的零次替代结构要求，也不能仅凭 XML 里列了 ID 判访问已获授权。

## 两个 URI 与文档变更

- `LocationUserProfileURI` 指向**这份位置用户配置文件**。在 §4.2.1 的在线引导路径中，终端用 MCS UE 初始配置 MO 里的 CMS URI，为每项已启用的业务获取对应的位置用户配置。条文没把启用动作规定为取档触发。
- 文件内可另有 `default-location-config-URI`，指向 **LMC 的默认位置配置**。§7.4.2.7 把其 URI 的定义指到 TS 24.283 §7.1.3.4；这里只核到引用，没有核对该规范正文。
- §7.4.2.12 要求支持按 §6.3.13.3 订阅**这份 XCAP 文档的变化**。其后一句把 XCAP URI 的出处写成 §7.4.1.1，而显式 URI 公式在 §7.4.1.2；查地址用后者，不把两个原文引用位置写成相同。

本页只核 Release 20 Stage 3 的 TS 24.484 V20.1.0。§7.4.1.1 把 LMS 和 LMC 怎样使用该文档指到 TS 24.283。这里的取档、变更订阅能力不证明某次订阅或应用已发生，也不规定 LMS 注册、位置上报触发或配置下发时点。不能拿另一 Release 的 LMS 消息补这段流程。
