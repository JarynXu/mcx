# CMS 返回 SIP 失败：没有 Response-Source，就不是 CMS 拒绝的吗？

**不能这样判断。**配置管理服务器（CMS）在对收到的 SIP 请求自行发出失败响应时，可以按运营商策略加 `Response-Source` 头。按这一条加头时，`role` 参数的值写 `cms`。有无这个头，不决定是否应拒绝该请求。

依据：3GPP TS 24.484 V20.1.0，Release 20，Stage 3，§6.2.4.2。条文适用于 CMS 对**任一已收到 SIP 请求**自行发出的失败响应，没有限定为 SUBSCRIBE 或 403。§6.2.1 的总述提到 HTTP，§6.2.4.2 写的是具体的 SIP 失败情形。

## 抓包时，头字段和拒绝原因分开查

| 看到什么 | 能判断什么 |
| --- | --- |
| 已确认 CMS 自己对收到的 SIP 请求发出失败响应。 | 可以按运营商策略插入该头，不是必须加。若按本条加，`role` 写 `cms`，并按所引 TS 24.229 §5.7.1.0 处理。 |
| 只看到某条 SIP 失败响应有 `Response-Source`，其中 `role` 为 `cms`。 | 报文带了 CMS 的角色标记；只凭它不能核实该响应确由 CMS 生成或定位服务器实例，也不能断定哪条授权检查导致失败。 |
| 看到 SIP 失败，但抓包里没有该头。 | 不能排除 CMS，也不能倒推运营商策略。不看到头不是看到 CMS 没有发出失败。 |

把失败响应对应到**同一 SIP 请求**，再查 CMS 处理记录。仅看到某节点转发失败，不能证实它自己发起失败。§6.2.4.2 没有给成功的 SIP 响应、HTTP 响应或转发处理规定，也没有定义收到这个头的客户端下一步要做什么。TS 24.229 §5.7.1.0 在这里是指针，不据此补写完整头语法、中间节点行为或来源校验。

## 403 的要求来自实际命中的业务分支

- [CMC 初始代理订阅](cmc-subscription-notify-fetch.md)命中接收和鉴权条件，清单只有一项且认证身份无权订阅其变更：CMS 须回 SIP 403 并停止后续步骤（§6.3.13.3.2.2 d）。
- [业务服务器续订](mcs-server-service-config.md)命中收包条件，CMS 按这次入站 PAI（`P-Asserted-Identity`）的 URI 判断权限。若清单只有一项文档或元素且这个身份无权订阅其变更，CMS 须回 SIP 403 并停止后续步骤（§6.3.13.3.2.4 b）。

上面是两条例子，不是说所有失败都回 403，也不推断清单部分获准时的处理。即使必须回 403，要不要加角色头仍按 §6.2.4.2 另判。

**HTTP 取文另查身份。**CMS 按 §6.2.4.1 所引程序确定这次 HTTP 请求的发送方，并以此作为已认证身份做授权判断。SIP 的角色头不替代 HTTP 发送方身份，也不证明已取回配置。
