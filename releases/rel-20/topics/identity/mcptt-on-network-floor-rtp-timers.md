# MCPTT 在网话权的 RTP 计时：包间隔、撤权后转发与双话权

**先分清量的是包与包之间、撤权后的服务器转发，还是发话本身。**这四个字段在 MCPTT 业务配置的 `<on-network>/<fc-timers-counters>` 里。它们的名字近似，计时对象不同。

依据：3GPP TS 24.484 V20.1.0（Release 20，Stage 3）§8.4.2.1/.3/.6/.7。

| 配置字段 | §8.4.2.7 的在网含义 |
| --- | --- |
| `T1-end-of-rtp-media` | RTP 媒体包之间允许的最大间隔（项 12）。 |
| `T3-stop-talking-grace` | 撤销发送 RTP 媒体的许可后，话权控制服务器继续转发 RTP 媒体包的时间上限（项 13）。不是客户端还能发话的许可，也不要求服务器每次都转发到上限。 |
| `T11-end-of-RTP-dual` | 双话权操作中，打断发话的参与者的 RTP 媒体包之间允许的最大间隔（项 16）。 |
| `T12-stop-talking-dual` | 在网**组呼**的双话权操作中，打断发话的参与者的发话时限（项 17）。 |

### 先找到谁的哪段时间

有 RTP 包连续到来，包间隔没超限，发话本身仍可能达到另一个时长上限。不要把 T1 当成同一在网配置中由 `<transmit-time>/<time-limit>` 表示的组呼或私呼发话时限（§8.4.2.7 在网项 7）。[TS 22.179 V20.0.0 的 Stage 1 单次发话上限](../calls/floor-permission-end-and-transmit-limit.md)也不能用来给这个 Stage 3 的 T1 填计时动作。

T3 以**已撤销 RTP 发送许可**为条件。只知道发话者申请未获准，不等于撤掉已有许可。它也不是邻项 15 的 T8：T8 计的是 `Floor Revoke` 消息在收到 `Floor Release` 前的重发间隔，不是转发媒体的时限。

T11 和 T12 都看打断发话的参与者，不是被打断的参与者。T11 所在的在网分支写的是双话权，没有 T12 项中另写的“在网组呼”限定；不把组呼限定搬给 T11，也不据此认定 T11 适用于所有私呼。两项都不说明某次已经启用了双话权或授予了话权。

### 配置类型和时长校验

§8.4.2.1 在网项 7 及 §8.4.2.3 在已选在网分支的 `fc-timers-countersType` 内列出这四个字段；它们都是必需的 `xs:duration`，各声明未给默认值。这个必需条件不移到只含离网块的业务档。

§8.4.2.6 的 25 项具名时长清单中，T1、T3、T11、T12 分别是项 10、11、14、15。若要判格式不符还是秒值无效，查[具名时长的两个校验分支](ad-hoc-broadcast-hang-time.md#缺项和校验怎么判)。名字同为计时器，不能把该清单套给未列字段，也不要把包间隔或撤权后转发上限当作[私呼挂起或整通时长](mcptt-private-call-service-timers.md)。

这些条文说明配置项量什么。没有给出完整的运行状态机、计时器启动或复位的报文，也不证明某次真的撤权、转发媒体或停止发话。
