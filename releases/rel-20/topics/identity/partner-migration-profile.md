# 迁入伙伴 MC 系统：接入时用哪份用户配置档，接入后又订阅哪份？

终端先用**主系统提供的用户配置档**找到伙伴系统的身份管理服务器（IdMS），并办理迁移业务授权。随后，终端在伙伴系统办理常规业务授权，再向伙伴侧订阅配置。**后来订阅的用户配置档与先前选来接入伙伴的配置档不同**。这两份档案不能互相充当接入前提或迁移成功的凭据。

适用范围：3GPP TS 24.484 V20.1.0，Release 20，Stage 3，MCS 终端在线配置中的伙伴迁移。只问标准如何规定，不需要先提供抓包；若判断某台终端走到哪一步，则要看那一步自己的证据。

## 先选伙伴，再从主系统的配置档中选一份

主系统至少给终端一份包含伙伴信息的用户配置档。每个伙伴条目给出伙伴系统标识及这个伙伴的 **MCS UE 初始配置文档**。需要迁移时（例如注册 PLMN 改变），终端分两次选择。PLMN 是终端实际注册的移动网；看到某个伙伴的域名可达，不能代替条目匹配。

1. **选伙伴系统。**主系统给出的某份配置档里要有该伙伴的条目，且**同一条目**列有当前注册 PLMN。仅当该 PLMN 码关联了 S-NSSAI **且**终端通过 5GS 注册时，这个 S-NSSAI 还必须在终端的 Allowed NSSAI（允许切片列表）内。任一前提不成立，就忽略切片这一项，PLMN 条件照常检查。默认自动选择；无用户输入或从手动切回自动时，若有多个合格伙伴，由实现择一。切到手动时，只列出全部合格伙伴的标识，由用户选定；列表顺序由实现决定。（§4.2.2.1.2.1；§4.2.2.1.2.2.1–.3）
2. **选主系统提供的用户配置档。**对**已选伙伴**逐份检查：候选档里属于这个伙伴的条目必须含当前 PLMN，且满足与上一步相同的条件式切片检查。多份档案都合格时，选择算法由实现决定。比如一份档里甲伙伴列有当前 PLMN，乙伙伴没有；选中乙后，不能借甲的条目让这份档合格。这些条款没有规定无匹配时改选第一项或回退主系统。（§4.2.2.1.2.3）

## 从哪儿取地址、用哪个令牌、办哪次授权？

| 环节 | 终端使用什么 | 这一步能说明什么 |
| --- | --- | --- |
| 伙伴用户认证 | 从**选中配置档 → 已选伙伴条目 → 伙伴 UE 初始配置**取 IdMS 的 HTTPS URI，带主系统 IdMS 取得的安全令牌联系伙伴 IdMS，按 TS 24.482 认证。 | 成功后取得在伙伴系统使用的访问令牌。知道 URI 或只看见一次联系，不是已经拿到伙伴令牌。 |
| 迁移业务授权 | 使用**伙伴访问令牌和先前选中的主系统用户配置档**。 | 两者是本次授权使用的资料；此条没说整份配置档一定出现在某个报文里。 |
| 伙伴系统常规 MCS 业务授权 | **完成迁移业务授权后**，可用伙伴用户认证所得的访问令牌，也可另外联系伙伴 IdMS 取得新访问令牌。 | 不强制再取一个令牌。迁移授权完成也不等于常规授权已完成。 |

以上均见 §4.2.2.1.2.1。主系统自身的在线配置（§4.2.2.1.1）也有 IdMS 地址，但它从主侧终端初始配置取址；这不是查伙伴 IdMS 的位置。此处介绍 TS 24.484 使用哪些输入，不展开其他规范的认证或各业务授权报文。

## 配置订阅、收到变化和业务生效，是三件事

- **订阅配置。**常规授权之后，§4.2.2.1.2.1 把订阅所用的访问令牌描述为在**伙伴用户认证或伙伴 MCS 业务授权**时取得。终端针对每项已启用的 MCS 业务，经配置管理服务器（CMS）的订阅代理订阅 **UE 配置、用户配置档、业务配置**。这里的 UE 配置也不是用来取伙伴 IdMS 地址的那份 UE **初始**配置。图 4.2.2.1.2-1 的业务配置标签写有“离网”；同条正文写的是各项已启用业务的业务配置，没有把订阅限定为离网。（§4.2.2.1.2.1，含注 1）
- **辨认订阅请求。**配置管理客户端（CMC）的初始 SIP SUBSCRIBE 发往配置好的 **CMS 订阅代理公共业务标识（PSI）**。不要用伙伴 IdMS 的 HTTPS URI，也不要套用直接订阅的地址（以 XCAP 根为基 URI、带 `auid` 参数的 SIP URI）。在代理分支，资源列表正文（`application/resource-lists+xml`）为每个要订阅的文档或元素列一个含相对路径的条目。（§6.3.13.2.2，初始请求 a、b）
- **核对令牌字段。**另一个正文（`application/vnd.3gpp.mcptt-info+xml`）的 `mcptt-access-token` 字段取自 TS 24.482 的认证过程（§6.3.13.2.2，初始请求 c）。这是字段取值的说明；上面 §4.2.2.1.2.1 写的是整个订阅流程可用的令牌来源。两处没有说常规业务授权一定会签发新令牌，也不能据此认定这两个来源对应的值必然相同。这里不展开完整报文。
- **检查本地副本。**若文档比终端本地保存的版本更新，终端接收与本次订阅对应、含 **XCAP Diff** 的 SIP NOTIFY，CMC 更新本地副本。核对某一份配置时，区分“发出订阅”“收到与该订阅和该文档匹配的变化通知”“副本已更新”。只有不相干的 NOTIFY，不能说明目标文档变了；即使副本已经更新，也不能据此断言业务已采用新配置。变更通知还可能在伙伴系统业务使用期间到达，并非只在初次接入时出现。（§4.2.2.1.2.1，含注 2；§6.3.13.2.2）
- **组文档另查。**组文档的订阅按 TS 24.481；终端按通知给出的 HTTPS URI 取组文档，取回过程也归 TS 24.481。不能把它当作上述多文档代理中的第四份普通配置，或把“拿到 URI”当成“已取回组文档”。（§4.2.2.1.2.1）

## MCPTT 配置档里的 XML 为什么看起来有两种写法？

§8.3.2.1 项 10(g)(xii)(A)–(B) 描述 MCPTT 配置档的伙伴条目：`PartnerMCPTTSystemId` 下面有 `uri-entry`；`AccessInformationForPartnerMCPTTSystem` 包住初始配置。§8.3.2.3 的 XML Schema 却把 `PartnerMCPTTSystemId` 直接声明为 `xs:anyURI`，并在同一 `MigratablePartnerMCPTTSystemInfoEntryType` 里直接引用 `mcpttiup:mcptt-UE-initial-configuration`。§8.3.2.7 说明了含义：标识指出可迁入的伙伴，条目内含 §7.2 的初始配置。可以据此理解取址所需资料，不能因此断定两种 XML 在网上等价，或替实现选择一种编码。这处差异只对照本版 MCPTT 的结构说明和 schema。
