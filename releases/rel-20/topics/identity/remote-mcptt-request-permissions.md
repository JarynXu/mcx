# MCPTT 用户配置档：远程环境监听、远程私呼和远程组呼分别查哪个请求权限？

**查与请求类型对应的字段。**远程环境监听、远程发起私呼、远程发起组呼是三项许可。配置档中有一项 `true`，不能替另外两项授权，也不能证明服务器已采用这份配置或某次呼叫已获准。

依据：3GPP TS 24.484 V20.1.0（Release 20，Stage 3）§8.3.2.1、§8.3.2.3 和 §8.3.2.7。只说明 MCPTT **请求用户**的用户配置档，不拿被请求一方的配置档替代。业务层区别另见 [Stage 1 的远程发起呼叫与环境监听](../calls/remotely-initiated-mcptt-call.md)。

| 要请求的业务 | 对应元素及表号 | 值的含义 |
| --- | --- | --- |
| 远程发起环境监听 | `allow-request-remote-initiated-ambient-listening`，表 8.3.2.7-40 | `true` 表示该 MCPTT 用户获准提出此请求；`false` 表示未获此请求许可。该表只说明用户权限，没有像下面两表那样指明参与功能服务器。 |
| 远程发起私呼 | `allow-request-remote-init-private-call`，表 8.3.2.7-43 | `true` / `false` 告知为该请求用户执行参与功能（PF）的 MCPTT 服务器，该用户获准 / 未获准发起这类私呼请求。 |
| 远程发起组呼 | `allow-request-remote-init-group-call`，表 8.3.2.7-44 | 同样是给该请求用户的 PF；`true` / `false` 分别表示有 / 没有这类组呼的请求许可。不是私呼权限或某个组的已接纳证明。 |

## 没写，不等于写了 false

先找请求用户的配置规则。§8.3.2.1 第 11(b)(xxxviii) 项在 `rule` 的 `actions` 下列出 `anyExt`，上述三个子元素分别是 C、F、G，按可包含的元素写。§8.3.2.3 分别把它们声明为 `xs:boolean`，没有给这三项声明 `default` 或 `fixed` 值。没有 `anyExt`，或有容器但缺目标字段，都不是字段明确写了 `false`。这几处原文没有给出缺项时的业务默认：不能自行补上 `true` 或 `false`，也不能用私呼项的值填补组呼项。

例如，私呼项写 `true`、组呼项写 `false`、环境监听项未出现：这份规则里有私呼请求许可，明确没有组呼请求许可，环境监听只能记为**缺项**。不能按“远程发起”三个字合并这三项结果。

## 查得到配置，不等于某次请求已通过

问“档案声明什么”，看匹配用户和请求类型的字段。问“现场已生效吗”，要确认服务实际采用的配置；即使对应权限是 `true`，也不能由此断定某次请求已放行、已建通、获高优先级或已获话权。

三项在本条分别指向 TS 24.483 的 §5.2.48R、§5.2.48W1、§5.2.48W2；各表把请求流程交给 TS 24.379。本页不复述那些过程，也不从配置值推定报文、失败码或设备行为。
