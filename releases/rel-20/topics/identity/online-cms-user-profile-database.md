# 在线 CMS 处理用户档：一次修改为什么可能既读库又写库？

**读库用于下发用户档或支持终端修改；写库对应终端已创建或更新用户档。**这是两种用途，不是同一步。仅看到读库，不能判定档案已经更新或存入。

依据：3GPP TS 24.484 V20.1.0（Release 20，Stage 3）§4.4。这里只讲用于**在线配置**的配置管理服务器（CMS）。原文所说的用户库是 MC service user database。

## 管理员交来文档：先分清两个管理对象

- CMS 接收管理员的 **MCS UE 初始配置文档**，需要转换为适合配置 **MCS UE 初始配置管理对象（MO）**的格式。这个动作不以存在默认用户档引用为前提。
- **初始配置 MO** 中有 `default-user-profile` 元素，且它标识一份 MCS 用户配置文档时，CMS 还要把管理员提供的那一份文档转换成适合配置 **MCS 用户档 MO** 的格式。规则看引用实际指向哪份，不能据本条推断“只有一份用户档”时会自动选它。没见到引用，不能由这条推出需要转换某个默认档，也不能据此否定下表中的终端用户档取用。

这是格式转换，不是证明哪份档已下发。[初始配置引用的写入校验](default-profile-reference-xcap.md)与[主系统终端的下载条件](primary-ue-online-configuration.md)分开看。

## 终端用户档：哪项需要用户库？

| 要处理的事 | §4.4 中 CMS 的动作 |
| --- | --- |
| 向 UE 下载用户档，或支持 UE 更新用户档 | **从用户库取** MCS 用户档。 |
| 用户配置文档已由 UE 创建或更新 | **存入用户库**，作为 MCS 用户档。仅看到修改请求不证明文档已经更新或写库成功。 |
| UE 已订阅该用户配置文档，CMS 要获知这份档的变更 | 用所引流程**获知用户库中该档的变更**。实际看到 CMS 获知库中变化，不证明终端收到这份档对应的 SIP NOTIFY。终端订阅了另一份档，也不能充当这份档的订阅条件。 |
| UE 请求删除 MCS 用户档 | 用所引流程**从用户库删除**该 MCS 用户档。看到请求不能证明删除成功，也不说明默认引用会随之改选。 |

上面四项使用 TS 29.283 所定义的流程。这里不补写该规范的报文、读写次数、缓存或事务顺序，也不把它扩成对所有 CMS 文档的存储规则。CMS 获知库侧变更，与[终端 CMC 收到对应通知和取回文档](cmc-subscription-notify-fetch.md)是两条观察线。只看到终端侧通知，反过来也不能代替这次库侧通知记录。

§4.4 的注说本规范不覆盖 CMS、GMS 的离线配置职责，不从在线规则推断离线行为。
