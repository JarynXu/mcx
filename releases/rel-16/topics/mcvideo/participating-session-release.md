# 在网 MCVideo 开始释放会话时，参与功能该停发什么，什么时候才处理媒体资源？

“开始释放”和“会话已释放”是应用与信令平面给 **MCVideo 参与功能**的两种不同指示。前者要求停发，后者才按会话类型处理资源。这里看的是参与功能这一侧：客户端中有**传输参与者**，控制功能中有**传输控制服务器**。传输参与者是协议角色，不表示这个客户端此刻正在发送视频。以下适用于在网传输控制，按需会话已经建立，或预建会话正在使用。[TS 24.581 V16.9.0，Release 16，Stage 3，§6.1，印刷页 33](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=34)；[§6.4.1，印刷页 101](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=102)。

**收到“开始释放”：不用等第二个指示，参与功能就必须停发两类东西。**

| 参与功能不再发送什么 | 停止向谁发送 |
| --- | --- |
| 传输控制消息 | 传输参与者、传输控制服务器 |
| RTP 媒体包（承载视频的包） | MCVideo 客户端、控制 MCVideo 功能 |

两行都是对参与功能**发送**行为的要求。假设客户端稍后又收到一个视频包，单凭到达时间，不能判断参与功能是在指示前还是指示后发出的。要判断它有没有违反停发要求，应比对同一会话中参与功能收到指示和发出该包的记录。反过来，某段时间没有包，也不是参与功能已收到第二个指示的证明。[§6.4.4 第一段第 1、2 项，印刷页 102](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=103)。

**收到“会话已释放”：先认清是哪一类会话。** 若是**按需会话**，参与功能必须释放与**这项会话**相关的媒体资源。仅有这条指示，能说明该做什么，不证明实际清理已经执行，更不能把同一服务器上别场呼叫的资源一并记为已释放。若是**预建会话**，这一版 §6.4.4 第二段第 1 项明确要求按 **§9.3.2** 处理；按需会话的资源释放规则写在另一项，不能移过来。[§6.4.4 第二段第 1、2 项，印刷页 102](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=103)。

把预建分支指向的原页翻开，[§9.3.2 表 9.3.2-1，印刷页 181](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=182)列的是 MBMS（多媒体广播组播业务）子信道的控制消息。例如，表里有解除组与承载映射的消息，但列出一种消息不等于要求每次释放都发送它，也不说明预建资源该全部拆除还是全部保留。没有另外的依据时，保留本版回指，具体清理结果记为未知。

若手里的记录是某个客户端或服务器**请求结束呼叫**，查[一对一私呼的结束请求与应答](private-call-release.md)或[服务器释放整场在网组呼](server-group-call-release.md)。这些记录不能替代参与功能收到“会话已释放”的指示。要分辨修改媒体与释放**整项预建会话**，查[通用预建立会话的修改与释放](../bearers/common-preestablished-media-change-release.md)；它也不能替这版 §6.4.4 改写回指。
