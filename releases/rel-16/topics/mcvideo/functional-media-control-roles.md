# MCVideo 功能职责：会话、传输接收控制与媒体分发

## 适用范围

- 固定 TS23.281 V16.4.0（2021-01），Rel16 Stage 2；仅解释在网功能职责，不是完整协议或部署实现。
- 各声明按对应功能和业务证据分别适用；不要求所有功能已启用、所有角色或成功事件同时出现。

共同依据：TS23.281 V16.4.0 §1、6.2.1，印刷页11、16。

## 应用服务与传输控制是不同功能职责

条件：识别在网 MCVideo 的应用服务、控制服务器与 UE 参与者；不要求先取得媒体许可才能解释这些职责。

MCVideo client 是应用事务的用户代理，MCVideo server 提供集中服务支持。Transmission control server 可按上行条件调度请求，并可在请求获准时按下行条件通知参与者；竞争时可提供排队。Transmission control participant 处理发送请求以及到来的视频流邀请和通知。在网控制服务器位于 MCVideo server，参与者位于 UE。传输控制定义同时涉及谁可发送以及后续下行视频传输。

强度：功能定义和职责描述，不把支持能力表述成某次业务已成功。

- 这些是功能实体描述，§6.2.1 明确不等于物理实体；不能由名称数出服务器台数。
- 组呼、私呼和功能别名的控制角色相互独立；不能照搬其他业务的角色划分或把别名许可当媒体许可。
- 这里不从功能支持推导 SIP 准入、RTCP 编码、客户端状态或排队确认算法。

依据：3gpp-ts-23.281-v16.4.0 §3.1 transmission control,6.2.1–6.2.2.3.2,6.2.2.3.6–7，印刷页12,16,17,18。

## 建立会话、控制许可与媒体交换分属不同接口

条件：在网业务使用相应参考点时，分别判断会话信令、传输/接收控制或媒体交换；不把它们合成必须同时成功的共同条件。

MCVideo-1 用于建立服务会话的应用信令，MCVideo-4 承载单播传输控制信令，MCVideo-7 在媒体分发功能与 UE 媒体混合功能之间交换单播媒体。服务器将发送许可单播给获准发视频的参与端；媒体传输通知告诉接收侧另一用户的媒体可用。接收请求和接收响应又分别表达接收意图与该请求能否接收的结果。

强度：功能定义和职责描述，不把支持能力表述成某次业务已成功。

- 这些Stage2职责/信息流含义不能互代：会话建立不直接证明接收结果，发送者获准不证明接收者已经收到并呈现。
- 本页不规定全部控制步骤的顺序、应答码、消息字段或完成证据，也不把Stage2信息流直接映射为Stage3报文。
- §7.7.1.2.1 说明部分控制信息流可捎带呼叫控制；功能分工不表示每类职责必须使用独立物理连接。具体承载和实现仍需其各自规范。

依据：3gpp-ts-23.281-v16.4.0 §6.3.1,6.3.4,6.3.5,7.7.1.1–7.7.1.2.1,7.7.1.2.3;7.7.1.2.5–7 descriptive text，印刷页18,19,123,124,125。

### 甲请乙开传：谁获准，谁得知结果？

本例是同一 MC 系统内的在网传输控制（[§7.7.1 与 §7.7.1.1，在网范围，印刷页 123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=124)；[§7.7.1.3，同一系统，印刷页 129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=130)）：会话和传输控制都已建立，当前无人传视频。若甲自己申请发送，服务器在图示的获准分支把许可给甲，再由甲向服务器发视频。若甲有权请乙开始发送，请求者和发送者就不是同一人。下面说的是**在已有会话中启动乙的上行**，不是重新建立一场让乙把画面传给甲的私呼。图中只画两台终端，不限定会话人数。[§7.7.1.3.1，前提及步骤 1–6，印刷页 129–130](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=131)；[§7.7.1.3.7，前提 1–3，印刷页 142](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=143)。

甲端向传输控制服务器单播 **Remote transmit media request**。请求表列了两个必填的 MCVideo ID：一个标识远程发起者甲，一个标识被要求发送的乙。媒体标识是可选项，只在媒体复用时才可能出现。服务器核查的是**甲有无权启动乙的发送**；即使甲具备资格，服务器仍须按传输控制准则决定准许、拒绝或排队。正文以组策略为例，图中还检查同时传输数上限。图示走准许分支；不能从一份请求判定乙已获准，也不能从“可以排队”判定这笔请求已入队。[§7.7.1.2.17，请求表，印刷页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=128)；[图 7.7.1.3.7-1、步骤 1–2，印刷页 142](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=143)。

| 记录 | 这笔记录能说明什么 |
| --- | --- |
| 服务器 → 乙：**Transmit media granted** | 服务器接受甲的请求时，将许可给乙的参与端，表示乙可以发送；仅有这条许可，不能确认乙实际发过视频。 |
| 服务器 → 甲：**Remote transmit media response** | 告诉请求人甲结果。成功表示服务器报告乙已开始发送；若服务器拒绝请求，甲收到的是说明失败原因的响应，乙不会因这次被拒的请求取得许可。这不是给甲的发送许可，也不是服务器向甲下发视频。 |
| 乙 → 服务器：**视频媒体** | 图示成功路径的最后一步，乙在已有会话中开始上行。要独立核实乙确已发流，查乙端发出的对应媒体；要确认服务器收妥，还需服务器侧接收证据。即使上行已核实，也不能据此填报甲端已收到、已呈现或甲本人已看过。 |

许可信息流单播给获准的参与端；远程响应单播给请求人。远程开传的响应表（表 7.7.1.2.18-1）只列一个可选媒体标识，也只有媒体复用时才可能出现。**“成功或失败原因”是流程说明的响应含义**，表中没有列出必填的结果字段或原因码；不能据此指定线上编码，也不能因表里没列原因码就把失败写成无原因。[§7.7.1.2.3，发送许可，印刷页 124](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=125)；[§7.7.1.2.18，响应表，印刷页 127–128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=129)；[§7.7.1.3.7，步骤 3–5，印刷页 142](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=143)。

## 分发与混合不能混为许可或任意解密能力

条件：分别判断网络媒体分发或 UE 媒体混合的职责；涉及网络侧混合时另判断媒体是否端到端加密。

媒体分发功能利用服务器提供的信息接收上行、按需要复制并下发媒体，还支持保存媒体流为内容文件以及网络侧混合。UE 的 media mixer 支持发送和接收一个或多个流，并按媒体策略组合多个流，也支持保存流为内容文件。网络侧混合若发生，与 UE media mixer 独立；媒体端到端加密时不能在媒体分发功能内进行该混合。

强度：功能定义和职责描述，不把支持能力表述成某次业务已成功。

- 功能支持不等于每次通话都必须录制，也不授予用户无条件录制或访问权限。
- 本页不提供编解码、混合算法、解密方案或已呈现的证明，不用网络分发职责填补接收客户端实现缺口。
- 部署场景在 §6B 转引通用架构；本页不从图或功能位置推出未核物理拓扑。

依据：3gpp-ts-23.281-v16.4.0 §6.2.1,6.2.2.3.3–4 including NOTE1–2,6B，印刷页16,17,18,20。

## 使用边界

- 本页只用在网会话内远程启动一路发送的例子区分角色，不推导其他远程控制、离网、MBMS、跨系统或紧急流程；通用架构和安全转引仍是独立依赖。
- 功能定义不能证明某个Stage3程序已实现，也不能填补其模式选择、错误处理或计时器缺口。
