# 在网 MCVideo 手动私呼：主叫收到响铃，能确认对方接听了吗？

不能。甲呼叫乙时，服务器可以告诉甲“呼叫正在建立”；稍后发给甲的响铃消息表示乙端正在提醒乙。只有乙在界面上操作接受，乙端才走接受分支。甲从服务器后续的私呼响应得知乙已接受，以及接受的媒体参数。响铃、用户接听和建立媒体面是三个不同的步骤。〔§7.2.2.3.2.2 步骤 5–10、步骤 5 后的注，印刷页 70–71〕

**这条流程何时适用？** 甲、乙在同一 MC 系统，两个客户端都由主 MC 服务提供者服务，都已注册；两名用户均已通过身份认证并获准使用 MCVideo。甲选择手动开始，或者没有指定开始模式；两种情形都要求乙端设置为手动开始。甲端可有已激活、供本次使用的功能别名；MCVideo 服务器也可能已向系统内的别名控制服务器订阅激活或停用通知。这两项不是手动呼叫的必备条件。〔§7.2.2.3.2.2 引言和前提 1–5，印刷页 69〕

**甲发出了什么，服务器又查什么？** 甲端按乙的 MC 服务 ID 发起私呼，请求中的 SDP 提议列出一种或多种媒体类型。若甲要求手动开始，甲端可在请求中指明该模式。服务器另行核对双方参加这次私呼的权限，检查乙端的开始模式以及甲是否有权发起手动私呼；若提供了功能别名，还要核实甲能用它且它已为甲激活。服务器发给乙端的请求包含甲的 MC 服务 ID，有可用的甲方别名时一并携带。它提出原请求中的全部或部分媒体类型。若乙已用多台终端注册且已指定接收私呼的终端，请求只送到指定端。〔§7.2.2.3.2.2 步骤 1–4，印刷页 70〕

甲端还可以在私呼请求里一并**请求发送媒体**。这样，呼叫开始时甲会获得发送许可，不必在建立媒体面时再单发一次初始媒体发送请求。不一并请求也能发起私呼，此时乙可以先请求发送媒体，但不等于乙已经获准发送。两种选择都没有替乙接听，也不表示视频已开始传输。〔§7.2.2.3.2.1，印刷页 69；§7.2.2.3.2.2 步骤 7–10，印刷页 71〕

**从提醒到接听，分别看哪条消息？**

- **建立进度（步骤 5）**：服务器可向甲端发进度指示。它不是必发；若发，时机是步骤 3 的检查之后、步骤 6b 的响铃之前，不必紧跟服务器向乙端发请求的步骤 4。
- **响铃（步骤 6a、6b）**：乙受到提醒，乙端向服务器发送响铃；服务器再向甲端发送响铃，表示乙端正在被提醒。它不能证明乙做了接听动作。
- **接受（步骤 7–9）**：乙通过用户界面操作接受后，乙端向服务器发私呼响应。服务器向甲端发私呼响应，告知乙已接受，并给出接受的媒体参数。成功流程的下一步（步骤 10）才是建立媒体面和传输控制；收到响铃或知道媒体参数，都不能单独证明实际视频已传输。
- **未接受（步骤 8 的另一分支）**：若乙没有接受来电，乙端向服务器发呼叫失败响应，不在这条响应里添加失败原因。该条不能用来推断甲一定收到什么失败消息，或所有拒绝都不带原因；也不能沿着失败分支得出已建立媒体面的结论。
