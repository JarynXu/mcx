# 离网 MCVideo 组呼已在进行：后来者等通告，还是先发通告？

两种做法都能加入同一场组呼。区别在于后来者 X 怎样取得**正在进行的通信所用的参数**：被动加入时，X 等已有参与者周期通告；主动加入时，X 先发自己的通告，已有参与者再用一条通告告诉它现用参数。后一条仍是**组通信通告**，不是 X 用来告知全组“我已参加”的**组通信应答**。

**先确认是否适用。** 这里是 Rel-16 的离网组通信，客户端之间直接通信。其他客户端已在同一场组呼中；它们与后来进入通信范围的 X 都是同一个 MCVideo 组的成员，而且每一端都已预配该组的 ProSe 直通通信信息及其到 ProSe 二层组标识的映射。仅知道组号、发现附近有人，不能代替这些前提。见 §7.1.3.1（印刷第 53 页）及 §§7.1.3.4.2、7.1.3.5.2 各自的前提 1–3（第 58、59 页）。

| X 怎样加入 | 谁先发、发什么 | X 依据什么设置媒体面 |
|---|---|---|
| 被动 | X 进入范围后先等待。一个已有参与者发出周期性的组通信通告。 | X 收到该通告，按其中的参数设置媒体面，加入正在进行的组通信。X 不必先发加入请求。 |
| 主动 | X 向组发出试图发起新通信的组通信通告，带有新的通信参数（例如通信标识）。一个已有参与者收到后，再发一条组通信通告，给出现有通信的参数。 | X 收到已有参与者的通告，按**现有通信**的参数设置媒体面并加入。仅见 X 的第一条通告，不能说另一个组呼已建立，也不能说 X 已经加入原组呼。 |

被动路径见 §§7.1.3.4.1–2（第 58–59 页，步骤 1–5）；主动路径见 §§7.1.3.5.1–2（第 59–60 页，步骤 1–5）。主动路径总述说 X 请求所需参数，具体步骤给这条消息的名称是组通信通告，并未另设一条“加入请求”消息。

**没有 X 的应答，能算加入失败吗？** 不能。两种加入程序的步骤 4 都说：若 X 收到的通告带有确认模式指示，X **可以**向组发应答，让成员知道它参加了；即使带了指示，也不要求它一定发送。步骤 5 是原组通信有 X 参加并继续进行。不见应答不能单独判定加入成功或失败；即使已确认 X 加入，也不能据此断言某一段视频已从 X 发送、被它收到或呈现给用户。这里说的是加入既有组呼，不是首次建呼的应答规则。

**读字段表时，先看消息名。** 通告中发通告者的 MCVideo ID、目标 MCVideo 组 ID、媒体编解码信息、媒体组播端口、传输控制端口和通告周期均为必填；确认模式指示是可选项。若 X 发组通信应答，应答表列为必填的是发送应答者的 MCVideo ID 和相应的 MCVideo 组 ID。表内“必填”约束的是一条已发消息，不能据此要求 X 必须发应答；也不要把应答当成已有参与者向主动加入者提供参数的通告。两表均在第 54 页，见表 7.1.3.2.1-1、7.1.3.2.2-1。

**相邻问题。** 若是恢复覆盖后由服务器邀请、或由客户端请求重入，查[在网预安排组呼的迟入与重入](prearranged-late-entry-rejoin.md)。若只想知道附近终端能提供什么视频能力，查[离网能力发现](offnetwork-capability-discovery.md)；能力通告不是此处现有组呼的参数通告。
