# MCVideo 环境查看：收到 INFO 的 200，预建立会话还在吗？

**这份 200 回的是 INFO，不能单独证明预建立会话保留。** 要判断这一点，另查终端的媒体面记录：它是否明确说这场业务呼叫结束、对应的预建立会话保留。

这里只看 **Rel-16 在网、已经进行的 MCVideo 环境查看呼叫**，目标终端用与该参与功能对应的预建立会话。控制功能简称 CF，参与功能简称 PF。本场业务呼叫和终端与 PF 之间的预建立对话是两个对象。[TS 24.281 V16.12.0，Stage 3，§15.3.2.3，印刷页 348](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=349)。

## CF 的 BYE 到了 PF，终端收到的为什么可能是 INFO？

| 看哪一端的记录 | 这一段能判断什么 |
| --- | --- |
| **PF 实际收到 CF 发给本场的 BYE**，会话标识指向在这个 PF 有对应预建立会话的目标用户，且 BYE 带指定的 MCVideo 信息 MIME | PF 须复制该 MIME 正文，在目标终端已有的预建立对话内发 SIP INFO。本条给终端的请求是 INFO，不是转发原 BYE。只见 CF 发出、对不上目标会话、或没有指定正文，都不能认定触发了这个发 INFO 的动作。 |
| **目标终端实际收到 INFO**，其指定 MIME 正文里有 `release-reason` | 终端须针对这份 INFO 生成并发送 200，并按 §15.2.2.5 处理。在上一行的 CF BYE 实收和目标预建立会话对应条件成立后，PF 的正文条件只要求指定 MIME，不要求带释放原因。不能用 PF 发出的记录替代终端实收。 |
| **PF 实际收到匹配自己所发 INFO 的 2xx** | 本版指向未定义的 X3，编者注说后续以后定义。终端发出 200、或者 PF 收到别的事务的 2xx，都不是这项实收；匹配 INFO 的 2xx 也不是 CF 那份 BYE 的 200。 |

指定的 MCVideo 信息 MIME 是 `application/vnd.3gpp.mcvideo-info+xml`。BYE 缺少它时，本节没有给出替代动作。依据：[§15.3.2.3，PF 两个实际入口，印刷页 348](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=349)；[§15.2.2.4，终端实收 INFO，印刷页 343](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=344)。

## 什么证据才说明这场结束、预建立会话保留？

看终端是否另有**实际收到的媒体面指示**，同时指明本场环境查看呼叫释放、对应的预建立会话保留。满足这项条件才按 §15.2.2.5 判断，终端须清掉本场缓存的环境查看角色和类型。仅见 INFO、INFO 的应答或视频停流，都不够。保留不等于下一通一定可以复用；原文仍有编者注，预建立情形的呼叫建立和释放需要在 TS 24.581 定义。本节不补写媒体命令。[§15.2.2.5，开头、编者注与第 3 项，印刷页 343](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=344)。

## 如果是终端用户主动结束，还是同一个流程吗？

不是。终端要核对**本场实际收到**的环境查看释放能力指示：从服务器来的本场 INVITE，或与自己发出的本场 INVITE／REFER 匹配的 200。确认未收到这个 `Feature-Caps` 指示，须跳过其余步骤；如果日志截断，只能说还不知道有没有收到。[§15.2.2.3 第 1–2 项，印刷页 342](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=343)。

收到该指示，才走 §6.2.5.2 的对话外初始 REFER。请求地址指向服务 MCVideo 服务器上标识预建立会话的公共业务身份；`Refer-To` 指向要结束的**业务呼叫**，其中的 BYE 是方法参数，不是这份请求的类型。`Target-Dialog` 标识**预建立对话**。终端实际收到匹配这份 REFER 的 2xx 后须与媒体面交互，不能用这份响应证明另一腿结束。发起侧 PF 收到这种 REFER 时，§15.3.1.3 的正文指向未定义的 X1。它在环境查看章内，标题却写 private call；不能用这个标题把相邻普通私呼条款当成 X1。[§6.2.5.2，印刷页 46](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=47)；[续文，印刷页 47](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=48)；[§15.3.1.3，印刷页 345](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=346)。

## 记录如果属于另一类释放

- **实际是按需环境查看：** §15.3.2.2 明写 PF 收到 CF BYE 要查 §10.2.4.2.2.1；不是上面的预建立 INFO 分支。[印刷页 348](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=349)。
- **实际是参与功能收到应用与信令平面给它的释放指示：** 查[参与功能的媒体面释放](participating-session-release.md)。这不同于当前终端收到 INFO 或媒体面保留指示，不能用来补 X1 或 X3。
- **实际请求是修改或释放整项预建立会话：** 查[通用 Stage 2 预建立会话修改与释放](../bearers/common-preestablished-media-change-release.md)。
- **实际是普通在网预安排组呼已按需建立，CF 实收其中一人的业务 BYE：** 查[该组呼的单腿和整场释放判断](prearranged-group-sip-bye-policy.md)。不是这里的环境查看。
