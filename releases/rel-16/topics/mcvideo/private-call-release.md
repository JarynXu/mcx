# 一对一 MCVideo 私呼：谁发起结束，服务器向谁请求、向谁应答？

乙的终端收到服务器发来的结束请求，只能确定服务器向乙发送了请求，不能据此认定是服务器主动挂断。甲要求结束通话时，乙也会收到这样的请求。以下是 Release 16 的在网控制面流程：甲、乙均已注册 MCVideo 服务，正在进行一对一私呼。原呼叫采用手动还是自动开始模式，并不决定由谁发起释放。

**甲主动结束。** 甲的客户端向服务器发出结束请求，指定要结束与乙的私呼；服务器再向乙的客户端发出相应请求。乙端通知乙通话结束，并向服务器应答。服务器收到乙端的应答后，才针对甲端原来的请求向甲端生成并发送应答。乙端应答的是服务器，甲端收到的也不是由乙端直接发出的应答。[TS 23.281 V16.4.0 §7.2.2.3.3.1，图 7.2.2.3.3.1-1、步骤 1–6，印刷页 71–72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=72)

**服务器主动结束。** 服务器判定满足终止条件后，分别向甲、乙的客户端发结束请求。两端各自通知本端用户，再各自向服务器应答。这时甲也是请求的接收方，不是等待原请求结果的发起方。该节列举了管理员配置的最长私呼时长已到，以及因没有收发而超时等情形；它没有给出统一时长，短暂没有画面也不证明已触发终止。图中两端请求使用同一步号，不表示两端同时收到或按特定先后应答。[§7.2.2.3.3.2，前提、图 7.2.2.3.3.2-1、步骤 1–4，印刷页 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=73)

**两种流程清理的资源相同。** 两端释放本次私呼使用的全部媒体面资源。只有原呼叫建立时带有传输控制，才释放相应的传输控制资源。若记录只到一条结束应答，可以认出相应的信令步骤，不能据此认定两端均已完成清理，或据以还原用户最后看到的画面。这是 Stage 2 的业务流程，不给出具体 SIP 方法和状态码。[§7.2.2.3.3.1 步骤 7，印刷页 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=73)；[§7.2.2.3.3.2 步骤 5，印刷页 73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=74)。

[一对一视频推送](one-to-one-video-push.md)另有正常结束条件：推送的视频传输完成后，用上述私呼释放程序。推送条款没有指定必须由哪一方先发结束请求；反过来，看见私呼释放也不能证明此前发生了推送或视频已经传完。[§7.4.2.3.2 注 2、§7.4.2.3.3，印刷页 94](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=95)。如果原呼叫尚未建立，查[普通私呼的应答与取消](private-client-answer-evidence.md)；若是一人离开仍有其他参与者的组呼，查[组呼成员退出](group-call-leave.md)。
