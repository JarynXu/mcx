# 同一 MC 系统内的在网 MCVideo 受限聊天组：加入或恢复覆盖后，怎样判断媒体面是否已接通？

乙、丙还在同一场受限聊天组呼里，甲的终端没有画面。先查甲失去画面前有没有参加**这场呼叫**，再查甲与服务器之间的媒体面。若整场呼叫当时都没有进行，则查下文的建呼示例。这三个起点不能凭同一张黑屏截图区分。这里限于同一 MC 系统内的在网 MCVideo。

## 别人已经在通话，甲第一次加入这场呼叫

乙、丙已经加入，三端都已注册，三人都通过认证并获准使用 MCVideo。甲本来就是组成员，现在表示要参加正在进行的这场呼叫。甲的客户端向服务器发组加入请求，给出目标组 ID、甲的 MCVideo ID 和甲端的媒体参数；甲若同时申请发送，请求中带隐式发送请求指示。服务器核实甲能否归属该组，尚未归属才为甲生成隐式归属。功能别名可不带；若带了，服务器还要查该别名是否允许使用、是否已经为甲激活。这里的“加入”不是新授予组成员资格。[§7.1.2.3.1.2.5 前提及步骤 1–2，印 38](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=39)。

服务器用加入响应告诉甲已接受请求。**接下来**，甲端与服务器用媒体面控制信令建立两者之间的媒体面。若日志停在服务器已接受甲的请求，继续查这段建链，不要把成功响应或乙、丙之间已有视频当作甲端也已接通。[§7.1.2.3.1.2.5 步骤 3–4，印 38](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=39)。

## 甲原来就在通话，失去无线覆盖后返回

这次要对上两段记录：失去覆盖时甲和乙、丙已在通话，返回时**原来那场**还在进行。甲端或服务器发现甲已恢复覆盖；本节不规定怎样发现。随后甲端与服务器用媒体面控制信令**重建这两者之间的媒体面**，不是重建整场组呼。视甲失去覆盖的时长，这一步可以包含甲发起的重新入组信令；本节没有规定多长时间必须重入。即使查明甲没有再发加入请求，也不能单据此判恢复失败。若只是现有日志没显示这条请求，更不能说它一定没发。要验的是甲这条媒体面有没有重建，不是无线信号是否已回来。即使查到重建成功，若还要确认甲已经看见乙的视频，仍须另核甲端接收和呈现乙这路视频的记录。[§7.1.2.3.1.2.6 前提 1–2、步骤 1–2 和注 1–2，印 39](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=40)。

若甲在这次失去覆盖前已经主动离开、没有重新参呼，或乙丙已在同一个组另开一场，都不能按原参与端返回原场处理。但甲若早先退出后**已经重新参呼**，本次掉线时仍在场，回来时原场也还在，就符合这个返回流程。只知道组名和重新上线的时间，则先补掉线当时的参呼记录和呼叫延续记录。无线中断本身不证明甲退出了呼叫或解除了组归属。

**甲收到“当前发送者是乙”，能认定什么？** 在这两种迟入流程里，服务器可以告诉甲当前谁在发送，也可以给甲发送许可、拒绝或队列位置信息。它们说明的事不同：发送者通知不是给甲的发送许可，排队也不是已获准。乙、丙可能收到甲加入或返回的提示，也可能没有。要认定甲已经看到乙的视频，仍要查甲端对这路媒体的接收和呈现记录；甲的加入响应、建链或上述通知都不能替代。[§7.1.2.3.1.2.5 步骤 5–7，印 38–39](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=39)；[§7.1.2.3.1.2.6 步骤 3–5，印 40](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=41)。

## 加入成功就表示媒体面已接通吗？

不一定。甲成功加入时，**若已有媒体传输正在进行**，甲的客户端接入这次传输的媒体面。**若组呼当前未在进行**，甲只为该呼叫预置了媒体参数。规范对后一种情形给出两个条件：组内参与端都没有收发媒体，且传输控制交互之间的超时已经届满。只知道此刻无人发送，还不足以选这个分支。接入媒体面也不是甲已看见乙的视频；要填“已显示”，还要核甲端接收和呈现乙这路视频的记录。要填“甲能发视频”，另查甲的发送许可。〔[TS 23.281 V16.4.0 §7.1.2.3.1.2.1，印刷页 35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=36)〕

**谁能加入，谁会被邀请？** 在同一 MC 系统的受限聊天组呼中，想参与的成员各自发起加入，不用等服务器点名；建立这场呼叫本身不会向任何其他组成员发出邀请。即使只邀请乙一人，也不是这次建呼触发的。加入请求表示甲想参与，开始接收组内媒体传输的通知；它不改变甲的组成员资格。服务器核实甲是获授权的组成员，并按归属程序检查甲是否获准归属该组。甲若尚未归属，请求应触发服务器为甲生成隐式归属。隐式归属不是把一个非成员变成成员，也不是准许甲发视频。〔[§7.1.2.3.1.2.1，印刷页 34–35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=35)；[§7.1.2.3.1.2.2 步骤 1b，页 36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=37)〕

**成功响应确认了什么？** 规范的建呼示例从一组已经有人加入、眼下却没有组呼在进行的情况开始：乙、丙先前已经加入，三端均已注册，三位用户均已通过认证并获准使用 MCVideo 服务。甲的客户端向服务器提交目标组 ID、甲的 MCVideo ID 和客户端媒体参数；若甲同时申请发送媒体，请求中就带隐式发送请求指示。功能别名可选；若带了别名，服务器检查它是否允许使用、是否已为甲激活。示例中服务器接受甲加入，并在响应中返回**服务器选定**的组呼媒体参数。即便请求里附了发送意图，这份加入响应本身也不证明甲获得发送许可、已传视频，或乙丙已经看到画面。〔[§7.1.2.3.1.2.2 前提 1–3，页 35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=36)；[步骤 1、1a–1c，页 36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=37)〕

**甲接下来要发视频怎么办？** 已加入的甲要向其他已加入者发视频，仍须走正常的传输控制程序。示例步骤 2 写的是：甲向服务器请求发送媒体时，服务器在本次呼叫的媒体面尚未建立的情况下建立它；已有媒体面就不必重建。呼叫期间，甲、乙、丙各端的传输控制参与者继续使用传输控制。相邻两次聊天组呼之间，服务器可视资源情况拆除或保留媒体面，因此“要发视频”不等于“必然重建媒体面”。〔[§7.1.2.3.1.2.1，页 35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=36)；[§7.1.2.3.1.2.2 步骤 2–3，页 36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=37)〕

这里解释 Release 16 的 Stage 2 业务流程，不给出 SIP 字段或超时数值。如果问题是恢复覆盖后如何重入一场**预安排**视频组呼，见[预安排组呼的迟入与重入](prearranged-late-entry-rejoin.md)；若查的是 **MCPTT 语音** chat 的初始信令，见[按需 MCPTT chat 组呼](../calls/chat-establish-join.md)。
