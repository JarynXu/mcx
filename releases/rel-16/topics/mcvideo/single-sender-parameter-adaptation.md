# 在网 MCVideo 组呼丢包后，接收端想要的分辨率就是实际使用值吗？

不是。甲正在组里发视频，乙因丢包请求改用 720p。这条记录只说明**乙希望改用 720p**。要判断这场组呼是否已改用它，还要看服务器如何处理请求，以及组呼最后应用的是哪组参数。

这里讨论 3GPP TS 23.281 V16.4.0（Release 16，Stage 2）的两个在网组呼示例。两者都限于**只有一名发送用户**的组呼，广播组呼是一个例子。为简便，条款只展示一名接收用户，并没有把接收者人数限制为一人。本版未规定允许多个用户发送视频的组通信如何适配参数；不能把同一套程序给每个发送者套用一次。[§7.17.3.1 开头、注及前提，印刷页 164](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=165)；[§7.17.3.2 开头及前提，印刷页 165](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=166)。

**如果是发送端甲先提出修改：**甲的客户端检测到网络状况改变，例如丢包或时延，向服务器请求调整参数，例如编码格式、分辨率或帧率。服务器检查的是**甲这名发送用户是否有权更新参数**；获准后，服务器才把更新请求发给接收端乙。乙的用户获通知，乙的客户端接受并向服务器应答，服务器再把结果回给甲。示例到下一步才写组呼应用新参数。所以，只有甲的请求、服务器的授权结果或发给乙的通知，都不足以证明画面已经换了分辨率。[§7.17.3.1 步骤 1–7，印刷页 165](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=166)。

**如果是接收端乙先提出修改：**乙的客户端发现网络变化，把期望的参数报给服务器。其他接收端也可能提出不同的期望。服务器检查权限，并依据收到的通知决定是否更新；如何作出这个决定由实现选择。这就是接收者**触发**、服务器**发起更新**的区别：没有规定照抄乙的值，也没有规定取多数或最低分辨率。[§7.17.3.2 开头，印刷页 165](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=166)；[步骤 1–2 及注 1，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=167)。

在接收端触发的成功示例里，获准后服务器向**正在发送视频的甲**发更新请求；随后，例中的收、发两个客户端都接受请求，分别向服务器应答，组呼才应用新参数。甲乙的应答和组呼实际采用哪组参数是不同的记录。若手里只有乙请求 720p 的记录，即使又看到甲收到服务器的更新请求，仍不能写成“组呼已改用 720p”。[§7.17.3.2 步骤 3、5–6，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=167)。

若手里只有一份[终端能力清单](onnetwork-capability-sharing.md)，它回答的是设备**支持什么**，不能代替本场组呼的参数更新记录。[广播组呼建立](onnetwork-broadcast-group-call.md)则回答什么时候能开始发视频，不是已在通话中的参数何时改变。
