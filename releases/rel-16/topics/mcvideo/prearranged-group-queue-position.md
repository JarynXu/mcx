# 普通预安排视频组呼：排队成员怎样查队位、等授予

普通在网预安排 MCVideo 组呼，使用传输控制且已协商排队；控制功能直接服务该参与者。从成员发出显式传输请求、在 U: pending request to transmit 等待答复开始。此时可直接收到拒绝；只有收到 Queue Position Info 后才适用本页的已排队分支。
客户端和服务器逐参与者接口按各自当前状态及实际事件处理。已协商排队不表示本次请求一定入队。

TS 24.581 V16.9.0 §6.2.1、§6.3.5.4.1、§14.2.2;14.3.2（印刷页 33, 71, 224, 225）

## 谁回答队位查询，谁有权显示结果？

适用事件：客户端已处于待发送请求或已排队状态。服务器回复查询这一事件另要求：面向该参与者的接口处于 U: not permitted and Transmit Taken，并已收到其 Queue Position Request。

客户端还在等待 Transmission Request 的答复时，收到 Queue Position Info 就通知用户请求已排队，可同时给出队位和优先级，随后进入 U: queued transmission。此时无需先发队位查询。进入队列后，只有收到客户端要求查询的指示，参与者才按本分支发送 Queue Position Request、启动 T102，并把 C102 置 1；仍然排队。

另一成员已获发送许可时，服务器面向查询者的接口在上述状态收到这条请求，回送 Queue Position Info，在 Queue Info 字段给出队位和传输优先级，并保持原状态。服务器可以把 subtype 首位置 1，要求确认；客户端在待请求或排队状态收到该位置消息时，首位为 1 就须回 Transmission control Ack（过程指定 Message Type=5、Source=0）。服务器是否以及如何处理缺少的 Ack 是实现选择。

客户端已经排队时，收到位置消息会停止仍在运行的 T102，保持排队。如果消息表明请求已排队，或客户端已发过队位查询，可以向用户提供可用的队位和优先级。服务器须填写字段，不等于客户端必须显示它。位置值 255 表示已排队，但服务器不知道或按策略不公布具体位置；254 表示未排队。§6.2.4.9.2 对收到这条消息的排队客户端仍规定保持状态，没有按 254 另外写退队步骤。

在网的查询和回报均走单播。请求报头的 SSRC 标识查询者，回报报头的 SSRC 标识服务器。§11.1.1 把第一次收到 Queue Position Info 列为 T100 正常停止事件；这与队列中的 T102 不是同一计时器。

依据：TS 24.581 V16.9.0 §6.2.4.4.5、§6.2.4.9.1–3（印刷页 38, 42）；TS 24.581 V16.9.0 §6.3.5.4.1、§6.3.5.4.7（印刷页 71, 77）；TS 24.581 V16.9.0 §9.2.3.5、§9.2.11–12、§11.1.1 table 11.1.1-1 T100/T102（印刷页 149, 165, 166, 167, 201）

## T102 到期：再问一次，还是结束请求？

适用事件：客户端处于 U: queued transmission；本次队位查询的 T102 到期。

尚未达到 C102 上限时，客户端重发 Queue Position Request，重新启动 T102，C102 加 1，继续排队。达到上限时不再发送队位查询。§6.2.4.9.8 的步骤是通知 MCVideo 客户端排队超时、向服务器发送 Transmission End Request、启动 T101、将 C101 加 1，随后进入 U: pending end of transmission。这是本地查询超时，不是收到服务器的拒绝。

同版图 6.2.4.1-1 却把 T102 到限的箭头从已排队画到无发送许可。判断时须说明采用的是正文还是状态图，不能把两个终点说成一致。T102 时长取服务配置，C102 的默认上限为 3。

不是所有退出都将 C101 加 1：用户主动撤回排队请求时，§6.2.4.9.4 规定发送 End Request、启动 T101、将 C101 初始化为 1，再进入待结束。

依据：TS 24.581 V16.9.0 §6.2.4.1 figure 6.2.4.1-1、§6.2.4.9.4、§6.2.4.9.7–8（印刷页 35, 42, 43）；TS 24.581 V16.9.0 §11.1.1 table 11.1.1-1 T102、§11.2.1 table 11.2.1-1 C102（印刷页 201, 211）

## 什么才改变发送许可？

适用事件：待请求客户端直接收到 Rejected；或客户端因位置报告而排队之后收到 Granted、Rejected 或 Cancel Request Notify。服务器转发 Grant 则要求其逐成员接口处于 U: not permitted and Transmit Taken，并收到仲裁逻辑的 Grant。这些是替代事件。

服务器接口收到仲裁的 Grant 才按此分支转发给关联参与者，并进入 U: permitted。已排队的客户端实际收到 Transmission Granted 后，按请求位回 Ack，保存获准参与者的 SSRC 并在本次许可释放前用于 RTP；尚未通知过用户时发出获准通知，停止 T102，进入有发送许可状态。§6.2.4.5.1 的注记说明：曾排队者开始发送媒体前会请求用户确认；用户确认后才开始发媒体，否则释放许可。有编码视频到达或已有缓存，是 §6.2.4.5.2 要求客户端开始转发的另一个条件。

Transmission Rejected 则是待发送请求状态的拒绝：按请求位回 Ack、通知用户，可显示 Reject Cause，停止 T100 并进入无发送许可状态。已排队状态没有收到 Rejected 的专门程序，按 §6.2.4.1 丢弃这种无对应程序的消息并保持状态。若实际收到的是 Transmission Cancel Request Notify，§6.2.4.9.6 要求按请求位回 Ack、直接转入无发送许可；这和查询超时走正文所述的待结束分支不同。

第 1 个 subtype 位置 1 时客户端回 Ack；过程指定 Granted、Rejected、Cancel Request Notify 对应的 Message Type 分别为 0、1、10，Source 都是 0。所列数值用于识别过程，不是完整的 Ack 编码规则。

依据：TS 24.581 V16.9.0 §6.3.5.4.9（印刷页 77）；TS 24.581 V16.9.0 §6.2.4.1 (unhandled message)、§6.2.4.4.1–2、§6.2.4.5.1 NOTE;6.2.4.5.2、§6.2.4.9.6;6.2.4.9.9（印刷页 35, 37, 39, 43）
