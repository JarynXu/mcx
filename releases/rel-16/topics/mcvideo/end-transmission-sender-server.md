# 在网 MCVideo：结束甲正在发送的一路视频，谁向谁确认？

看结束响应的方向。**服务器答复甲**，是告诉甲：甲请求结束的那路视频，服务器已经终止了。**甲答复服务器**，则是确认收到服务器的结束请求；服务器在发请求之前就已终止甲的传输。两种响应都不是乙的回执。

这里比较同一 MC 系统内的两个在网示例。甲、乙的客户端和 MCVideo 服务器之间已建立会话，两端与传输控制服务器之间已建立传输控制。甲、乙都已获准发送，而且**各自正在发送**，以下要结束的是甲的那一路。示例只列两台终端是为了简化描述，不是人数限制。[3GPP TS 23.281 V16.4.0，Release 16，Stage 2；§7.7.1，印刷页 123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=124)；[§7.7.1.3，印刷页 129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=130)；[§§7.7.1.3.6.1–2 的引言和前提 1–3，印刷页 139–140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=140)。

### 甲自己要求停发

甲端向传输控制服务器请求结束自己的发送。服务器终止甲的这路传输，再向甲端发结束响应，说明已经办结。服务器另向乙端发结束通知，指明是**发送用户**结束了甲的这路视频；乙端收到该通知，应告知乙用户。终止传输的动作由服务器执行，通知里说明的发起人却是甲，两者并不矛盾。[§7.7.1.3.6.1，步骤 1–5，印刷页 140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=141)

### 服务器因终止事件结束甲的发送

传输控制服务器**先终止甲的这路传输**，再向甲端发结束请求，说明为什么结束。甲端回给服务器的结束响应是对这个请求的确认，不是准许服务器现在才停发。服务器另向乙端发结束通知，指明这次是**服务器**终止了甲的传输；乙端收到后，应告知乙用户。条款列举的事件包括为另一项优先媒体传输而撤销当前传输、没有接收参与者等，并未给出完整的终止策略；具体原因要看发给甲的请求，不能从响应名称猜。[§7.7.1.3.6.2，步骤 1–5，印刷页 141](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=142)

在记录中，两条流程的结束响应都叫 **Transmit media end response**。只有名称、没有收发方向，分不出是谁发起；只看到服务器发给乙的通知，也不能当作乙端确已收到或乙用户确已获知的记录。两条流程都没有要求乙因此也停发自己的视频，更不能用甲停发证明[整场组呼已经释放](server-group-call-release.md)。

若记录只写“服务器不再把甲的这路视频发给乙”，先查[乙结束接收选定的视频流](end-reception-selected-stream.md)：只有这次停收使继续传输条件不再满足，服务器才会**因此**另行发起结束甲发送的程序；停收本身不是结束甲发送的结果。尚在等发送许可的人要撤回的是[排队的请求](queued-request-cancellation.md)，不是本页已经开始的传输。其他用户远程要求某个发送者停发，也不属于以上两例。
