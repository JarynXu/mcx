# 在网 MCVideo 结束一路视频：谁要求停发，谁收到答复？

同样是传输控制服务器向甲答复“已结束”，停下来的可能是甲自己的视频，也可能是乙的视频。**先对上请求人和发送者，再看完整的消息名称与方向。** 若是服务器主动停掉甲的视频，方向反过来：甲向服务器确认收到了结束请求。

以下三例限于同一 MC 系统：客户端与 MCVideo 服务器已建立在网会话，参与端与传输控制服务器已建立传输控制。图中只列两台终端是为了简化描述，不是人数限制。[TS 23.281 V16.4.0，Rel-16，Stage 2，§7.7.1，印刷页 123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=124)；[§7.7.1.3，印刷页 129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=130)。

### 甲要求停掉乙的视频

乙已获发送许可，且正在传这路视频；**不要求甲也在发送**。甲有权远程结束乙的这路传输。甲向传输控制服务器发 **Remote transmit media end request**，按流程步骤写明乙和甲各自的 MCVideo ID：乙是要停的发送者，甲是请求人。服务器仍要核查甲是否有权结束乙的这路传输，获准才终止。发出请求或写对两个身份，都不能证明已经办结。本条未给出核权失败的具体响应码，也未规定这两个身份在线上怎样编码。[§7.7.1.3.6.3，前提 1–4、步骤 1–2，印刷页 141](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=142)。

服务器终止乙的传输后，**必须向正在接收乙这路视频的参与端发结束通知**。例如丙在收乙、丁只在收别人的视频，丙是该通知的对象；不能只因丁在同一会话就把丁也列入。服务器另向请求人甲回 **Remote transmit media end response**。核对这条响应确实对应甲要求停乙这一路的请求，才能据此签认“服务器已停乙的发送”；另一笔停发的答复不能填到这张工单上。甲若也在收乙的视频，甲既是响应的对象，也是通知的对象，两者用途仍不同。甲的成功响应不是乙端的确认，也不是丙端收到通知的凭据。要确认丙已收，查丙端对应的通知接收记录；本例没有以乙回执作为终止条件。[§7.7.1.3.6.3，步骤 2–3，印刷页 141](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=142)；[步骤 4，印刷页 142](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=143)。

### 甲自己停发，或服务器主动停掉甲的视频

以下两例中，甲、乙均已获发送许可，且各自正在发送，目标是甲的那一路。两例的响应都叫 **Transmit media end response**，不带上面的 **Remote**；在这两例之间，可以用响应方向区分谁发起。[§7.7.1.3.6.1，前提 1–3，印刷页 139](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=140)；[§7.7.1.3.6.2，前提 1–3，印刷页 140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=141)。

- **甲自己要求停发：服务器答复甲。** 甲端请求结束自己的发送，服务器终止后再向甲答复“已结束”。服务器另向乙端发通知，说明是发送用户结束了甲的这路传输；乙端收到后应告知乙用户。[§7.7.1.3.6.1，步骤 1–5，印刷页 140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=141)。
- **服务器因终止事件停发：甲答复服务器。** 服务器先终止甲的传输，再向甲发说明原因的结束请求。甲的答复是确认收到请求，不是准许服务器现在才执行。服务器另向乙端发通知，说明是服务器终止了甲的发送；乙端收到后应告知乙用户。为另一项优先传输撤销当前传输、没有接收参与者，都是终止事件的例子，不是完整清单；实际原因看发给甲的请求。[§7.7.1.3.6.2，步骤 1–5，印刷页 141](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=142)。

这两例中，服务器向乙发出通知不能证明乙端已经收到，也不能证明乙用户已获知。结束甲的一路视频，不等于乙自己的发送也结束了。要确认[整场组呼释放](server-group-call-release.md)，应查该场呼叫的释放记录。若只有[某个接收端停收选定的一路](end-reception-selected-stream.md)，不能据此判发送者已停发；只有此次停收使继续传输条件不再满足，服务器才会因此另行发起结束发送。若用户还在排队、尚未开始发送，要查的是[撤回排队请求](queued-request-cancellation.md)。
