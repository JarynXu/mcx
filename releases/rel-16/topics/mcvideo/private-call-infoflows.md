# 在网 MCVideo 私呼：请求能证明获准发视频吗？响应能证明被叫点了接听吗？

甲呼叫乙。甲端发出的请求里有两项名称很像：一项回答“这通私呼用不用传输控制”，另一项回答“甲有没有借建呼请求一并申请发视频”。即使两项都有，且值分别表示“使用”和“申请”，这条请求也只记录了选择和申请，没有记录授予发送权。另一端是否接受这通呼叫，是响应要回答的另一件事。

3GPP TS 23.281 V16.4.0（Rel-16，Stage 2）把一次普通在网私呼的建呼信息分成四张表。**先看是请求还是响应，再看这一跳从谁发给谁。** 下表中甲一直是主叫、乙一直是被叫；M 表示该表必备，O 表示该表可选。这里读的是业务信息，不是 SIP 报文模板。[§7.2.2 与 §7.2.2.2，印刷页 63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=64)。

| 请求：哪端提出什么 | 必备（M） | 可选（O） |
|---|---|---|
| 甲端 → 服务器，表 7.2.2.2.1-1 | 甲的 MCVideo ID、乙的 MCVideo ID、是否使用传输控制、SDP offer（提议的媒体参数）。 | 甲的功能别名、所请求的开始模式、隐式发送申请；另列一对一推送指示、一对一拉取指示、本次呼叫请求的应用优先级。 |
| 服务器 → 乙端，表 7.2.2.2.2-1 | 同样是甲和乙的 MCVideo ID、是否使用传输控制、SDP offer。 | 甲的功能别名、所请求的开始模式、隐式发送申请。该表未列上行表的推送、拉取和请求优先级三行。 |

两张请求表中的 *Transmit media request indication* 都必须说明**是否**使用传输控制；字段必备，不等于它的值必须是“使用”。*Implicit transmit media request* 才表示用户还申请发送视频。没有该可选项，只能说这条请求不带这项申请，不能判定本次呼叫不用传输控制、用户被拒或以后无法申请。请求里选了开始模式或写了优先级，也只说明所请求的模式或级别。[两张请求表及各行说明，印刷页 64](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=65)。

| 响应：哪端回给谁 | 必备（M） | 可选（O） |
|---|---|---|
| 乙端 → 服务器，表 7.2.2.2.3-1 | **甲**的 MCVideo ID、SDP answer（所选的媒体参数）。 | 乙的 MCVideo ID、开始模式。模式行的英文名称仍含“requested”，但在这张响应表中，它说明将使用的模式。 |
| 服务器 → 甲端，表 7.2.2.2.4-1 | 仍是甲的 MCVideo ID、SDP answer。 | 乙的 MCVideo ID、接受确认。确认指示用户是否已明确接受本次呼叫；要读实际值。 |

**为什么乙发回的响应里，必备 ID 却是甲的？** 表里按呼叫角色列 ID，不按这条信息的发送者列。一次完整的乙端响应如果只有主叫 ID 和 SDP answer，并不因为没有被叫 ID 或模式而违反该表的必备项要求。若只拿到一段日志，连这段里的 ID 指谁都没标注，就不要把它认作乙的 ID，也不要据摘录判定原响应漏项。乙端已发出响应，也不代表服务器给甲端的响应已经送达。[两张响应表，印刷页 65](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=66)。

**验收记录怎么写？** 假设服务器给甲端的响应里出现了接受确认。仅知道“字段存在”不能写“乙已接受”；若值明确表示肯定，可以写“服务器向甲端报告乙已明确接受本次呼叫”，不能再写“乙在屏幕上点了接听”。这项信息不记录交互方式。若完整响应没有该项，就记“此响应未给出接受确认”，不记为乙拒接；SDP answer 能证明此处列出了所选媒体参数，不能证明已发送视频或乙看到画面。[表 7.2.2.2.4-1 的接受确认和 SDP answer 行，印刷页 65](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=66)。

某个信息项只列在一张表中，不表示它在整个系统中被禁止，也不表示服务器必须原样复制、删改或转送它。要查被叫端如何[自动接听](onnetwork-automatic-private-call.md)，或[手动接听时响铃与接受如何区分](onnetwork-manual-private-call.md)，须查相应建呼过程。要核对带传输控制、直接 ID 的普通按需私呼里具体的 SIP 请求、应答和取消，查[Stage 3 客户端建呼证据](private-client-answer-evidence.md)。本页四表不含离网或紧急私呼；本版在 §7.2.2.2.6 起另列紧急请求，不能拿普通请求表代替。[§7.2.2.2.6 标题，印刷页 65](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=66)。
