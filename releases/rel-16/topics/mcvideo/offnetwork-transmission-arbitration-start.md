# 离网 MCVideo 开始发视频：单仲裁与自仲裁怎样判断能否发送？

只看到一端发出 **Transmission Arbitration Taken**，分不出组用的是单仲裁还是自仲裁。两种方式都可能发这条宣告。先查组配置，再看发起端是否就在等现任仲裁端的答复，以及哪一端检查了发送数上限。这个问题从**离网 MCVideo 组通信已经建立**开始，不是首次建立组呼。

## 组配置与终端看见的情况

组配置分别给出**仲裁方式**和**同时发送数上限 N9**。单仲裁由一台组内终端为可达范围内的成员处理发送请求；自仲裁由各端根据自己看到的拓扑作判断。配置表要求把仲裁方式配置给 MCVideo 终端和组管理服务器，不要求配置给 MCVideo 业务服务器；N9 则要求配置给三者。这说明参数需要配置给谁，不决定具体组设的是哪个方式或什么数值，也不表示业务服务器参加离网仲裁。[TS 23.281 V16.4.0（Rel-16，Stage 2）§7.7.2.1，印刷页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=144)；[附录 A.1，列标含义，印刷页 169](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=170)；[表 A.4-3 前两项，印刷页 181](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=182)。

## 想开始发送时，谁检查上限？

| 场景 | 规范示例 |
| --- | --- |
| **单仲裁：甲请求后没检测到响应** | 甲想发视频，已判断未到配置上限，先向组发请求探测现任。甲没检测到响应，便向组发 Taken，开始担任仲裁端，随后向组发视频；可以提示用户。除了组内尚未选出仲裁端，也可能是现任仍在、但甲已离开它的范围。没听到响应不能区分这两种情况。 |
| **单仲裁：甲已经发现现任** | 这两个例子还要求至少一端正在发视频。甲向组发请求并等候，由现任仲裁端检查上限。未到上限，现任向组发 Granted，指明获准者是甲；甲收到授权后可以发视频。已到上限，现任向组发 Rejected，指明被拒的是甲，可以附上满额原因。两例都可以提示用户。发往组与点名哪位申请者是两回事。 |
| **自仲裁：甲自己看发送数** | 甲检查配置上限并告知用户。本例不把“先发探测、等不到现任答复”列为前提。若已到上限，用户可以推迟、请求替换一路发送，或决定继续并接受可能的干扰。图中继续发送的路径是甲向组发 Taken，再发视频；不能把这两步套到用户决定推迟时。 |

见 [§7.7.2.3，印刷页 145–146](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=146) 的前提、图 7.7.2.3-1 和步骤 1–4；[§7.7.2.4–.5，印刷页 147–149](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=148) 的前提和授予、拒绝步骤；[§7.7.2.3A，印刷页 146–147](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=147) 的前提、图 7.7.2.3a-1、步骤 1–3 和注。

**现任拒绝后，甲就没再发吗？** 单仲裁的拒绝例在步骤 4 后允许用户决定继续发送，并指向 §7.7.2.3。现任说已到上限，是现任侧的判断；§7.7.2.3 自己仍列出甲已判断未到上限的前提。原文没有说怎样在本例协调两端的判断，也没有说拒绝会自动转成许可或甲一定又发出了视频。[§7.7.2.5，步骤 4 后一段，印刷页 149](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=150)；[§7.7.2.3，前提 2，印刷页 146](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=147)。

**自仲裁满额，能照搬现任让位的办法吗？** §7.7.2.1 只给一般关系：从甲看容量已满且另一发送端优先级较低，甲可以直接向那一端请求替换；那一端可拒绝，也可接受并让位。§7.7.2.3A 提到替换时指向 §7.7.2.8，但 §7.7.2.8 明说它只用于单仲裁，编辑注把自仲裁的替换细节留待研究。不能拿单仲裁的撤权、授予和接任步骤补这一段。[§7.7.2.1，印刷页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=144)；[§7.7.2.3A 步骤 1，印刷页 147](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=148)；[§7.7.2.8 开头和编辑注，印刷页 151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=152)。

## 单看 Taken，能确认什么？

一端实际收到 Taken，可确认这一端收到了**有人宣告自己承担传输仲裁**的信息。表里的必填 MCVideo ID 指承担仲裁责任的用户。仅有这条控制消息，不能确认取得仲裁前发生了什么、其他成员也收到它、全组只有一名仲裁端，或有人已经收到并看到了视频。发送视频在上述继续发送的示例里是另一步。[§7.7.2.2.6 及表 7.7.2.2.6-1，印刷页 145](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=146)；[§7.7.2.3 步骤 3–4、§7.7.2.3A 步骤 2–3，印刷页 146–147](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=147)。

若组中[两端同时请求发送](offnetwork-simultaneous-transmission-requests.md)，且采用自仲裁或当前无人担任单仲裁端，另查它们怎样比较优先级。若已发现现任单仲裁端且发送数满额，查[它怎样为获准的替换申请让位](offnetwork-sender-override.md)。要查普通离网组 **single** 的终接或晚加入端收到实际消息后的状态，读 [Stage 3 参与端程序](offnetwork-single-participant.md)。这里的 Stage 2 示例不规定线编码、等待时长或实际组内媒体交付。
