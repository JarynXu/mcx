# MCVideo 排队中的视频发送请求：谁能撤，谁收到通知？

乙已获发送许可，正在传视频；甲和丙的发送请求还排在传输控制服务器上。**可以撤的是排队的请求。** 移除丙的请求不会因此撤销乙的许可，也不意味着甲马上能发视频。本页说的是同一 MC 系统内的在网 MCVideo 传输控制。

## 本人撤回和替别人撤回，有什么不同？

甲可以请求撤回自己的发送请求。如果甲有权替别人撤回，还可以一次请求移除一名或多名排队者的请求。甲向传输控制服务器发取消请求，带上发起者甲的 MCVideo ID；若代撤，按步骤 2 的建议，还应列出各目标参与者的 MCVideo ID。写上丙的 ID 只说明甲想撤谁的请求。服务器必须核查甲有没有相应权限，获准才移除；不能把甲发出请求的记录当作已经办结。

同一次代撤可能涉及三种不同的消息：

| 谁收到 | 服务器告诉对方什么 |
| --- | --- |
| 发起人甲 | 取消完成后，回给甲的是这次取消的完成响应。甲撤回自己的请求时也是如此。 |
| 被代撤的丙 | 服务器通知丙：丙的排队请求已被取消。若实际移除了多人的请求，通知相应的被移除者。 |
| 仍在排队的参与者 | 服务器可以告知新的队位；此项可选。没收到新队位，不能据此断定代撤失败。 |

等正在进行的传输结束、并发数允许时，服务器才按更新后的队列处理发送请求；代撤完成本身不指定下一个获准者。[TS 23.281 V16.4.0，Release 16，Stage 2，§7.7.1.3.5.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=138)，印刷页 137–138，前提及步骤 1–5。核对原文时要留意：步骤 4 把发送请求回指到步骤 3，但编号正文中是步骤 2 由甲发请求、步骤 3 由服务器查权限并移除，步骤 4 才通知被代撤者。

## 服务器自己移除请求时，重复申请一定替换旧申请吗？

服务器可以依策略从队列移除请求，定时器到期是一个例子。另一种情形是：同时传输数已到上限，丙已经排队，又提交一次发送请求。步骤 1 给出两个结果：

- 服务器接受新请求，把它放进队列，移除丙的旧请求。
- 服务器拒绝新请求，把丙的旧请求留在队列。

这里的“接受”是接受**入队**，不是授予发送许可。不能仅凭丙又申请了一次，就断定旧项必被替换、新项沿用原队位、排到队尾或立即获准。若服务器实际移除了请求，它通知请求被移除的参与者；可以另向其他仍在排队的人告知新队位。拒新留旧时，不能把拒绝新请求说成取消了旧请求。

依据：[同版 §7.7.1.3.5.2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=139)，印刷页 138–139，前提及步骤 1–3。这些步骤不规定新项的具体名次或策略定时器的时长。

如果只想知道成员如何[查询队位、等待授予](prearranged-group-queue-position.md)，或想知道[组会话换控制方时怎样转交排队请求](role-switch-transmission-queue.md)，可分别查对应的 Stage 3 主题；队位查询和转交都不是这里的代撤。
