# MCVideo 预安排组呼：一个 BYE 的 200，等于整场结束吗？

**不等于。** 控制功能（CF）实际收到一名参与者这条会话的 BYE，先与媒体面交互以释放该段资源，给这份 BYE 回 200，再判断要不要结束整场。继续通话时，CF 的会议状态 NOTIFY 只发给**仍在场且已订阅**的客户端。

这里查 3GPP TS 24.281 V16.12.0（Rel-16，Stage 3）中**已通过按需信令建立的普通在网预安排 MCVideo 组呼**。SIP BYE、对这份 BYE 的 200、初始 INVITE 的 200、媒体面的 Transmission Release 是不同事件。下文的发起侧参与功能是 O-PF，终接侧是 T-PF；按各处实际收到的请求和响应判断，不从逻辑收件角色推导物理下一跳。[§9.2.1.2.3.1，印刷页 169](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=170)；[§9.2.1.4.3，印刷页 186](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=187)。

## CF 收到参与者 BYE：回 200 与整场决策分开

1. **本段：** CF 须和媒体面交互，处理面向该离开客户端的 SIP 会话所关联的媒体资源，生成并向该客户端方向发送 BYE 200。条款没有说媒体清理已同步完成，也没要求先等其他人回执。
2. **整场：** CF 接着查释放策略。当前是组呼，取 §6.3.8.1；通用收 BYE 条款也提到的 §6.3.8.2 是私呼策略，不再给本场叠一层私呼条件。

[§9.2.1.4.3 → §6.3.3.2.4 第 1–3 项，印刷页 186、91](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=92)。判断本场是否需要释放，按组策略下列五项，有一项成立即可：

| 匹配到的事件或状态 | 核对哪份证据 |
| --- | --- |
| 预安排组呼的 T4（不活动计时器）到期 | **CF 实际收到媒体面的到期指示**；光看见画面停了不够。 |
| 本场只剩一人或无人 | 看这场会话中的参与人数；不要求离开者是发起人。 |
| 预安排组呼的发起人离场 | 此项还须**本地策略要求这样做**；本地策略不要求且其余条件均未命中，不能因发起人离场而释放。 |
| 在场的已归属组员不足适用的最低人数 | 与本场只剩一人是两项检查；不拿全组名册人数或首次建呼的启动阈值代替这项。 |
| 组呼计时器 TNG3 到期 | 这是另一个计时器的实际到期，不是 T4 的媒体面报告。 |

[§6.3.8.1 第 1–5 项，印刷页 106–107](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=107)。本段不规定具体最低人数、计数采样时点或配置实现。

**策略要求释放整场：** CF 按 §6.3.3.1.4 向本场所有参与者发送释放用的 SIP BYE，不扩大到没参加的人。若入站 BYE 带有 MCVideo 信息 MIME（`application/vnd.3gpp.mcvideo-info+xml`），才按第 4 项把这一 MIME 复制到出站 BYE；不从本条推断其他 MIME 都要复制。**CF 实际收到其某份外发 BYE 的匹配 200**，按本条处理该参与者对应 SIP 会话的媒体资源；不能据这一端的响应填其他端已回或所有资源已清。[§6.3.3.2.4 第 4 项及末段，印刷页 91](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=92)；[§6.3.3.1.4，印刷页 78](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=79)。

**策略不要求释放整场：** CF 须向本场尚余且订阅了 conference 事件包的客户端发 SIP NOTIFY；未订阅者和已经离开的参与者不在这个分支的接收集合内。**零名符合条件的订阅者，仍要给离场一侧的 BYE 回 200。** 发出 NOTIFY 也不证明订阅者实际收到，更不证明画面或客户端状态。[§6.3.3.2.4 第 2、5 项，印刷页 91](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=92)；[§9.2.3.4.2，印刷页 229–230](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=231)。

TNG3 还有两个不同的事件：计时器自身到期时，管理条款另明确调用通用 BYE 程序；走通用 BYE 程序且**最后一个客户端已移除、TNG3 尚未到期**时，才按该项停止 TNG3。只见某个 BYE 200，不足以认定这两个事件中的任何一个。[§6.3.3.5.1，印刷页 94–95](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=95)；[§6.3.3.1.4，印刷页 78](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=79)。

## 终端和 T-PF：哪一份 BYE 或 200 才触发本段动作？

- **终端主动离开当前场次。** 用户请求离开已经按需建立的会话时，终端先和媒体面交互，BYE 的 Request-URI 用**待离开的 MCVideo 会话身份**，不是组身份或首次建呼的业务身份；向服务器方向发送。终端实际收到这份 BYE 的 200，再按依赖规范和媒体面交互。这里不补 IMS 路由集、ACK 或 NAT 处理。[§9.2.1.2.3.1，印刷页 169](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=170)；[§6.2.4.1，印刷页 46](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=47)。
- **T-PF 从 CF 实收 BYE。** 组呼小节 §9.2.1.3.4.1 的标题印有“private call on-demand”，但该处父节是组呼，正文明确把来自 CF 的 BYE 指向 §6.3.2.2.8.1。T-PF 处理与 CF 侧会话关联的媒体资源，生成并向终端发 BYE，复制入站 P-Asserted-Identity 和存在的指定 MCVideo 信息 MIME。T-PF 真正收到终端对这份 BYE 的 200 时，才按该段对原 CF 请求回 200，并处理与终端侧会话关联的媒体资源。不是两侧共用一条收件记录。[§9.2.1.3.4.1，印刷页 174](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=175)；[§6.3.2.2.8.1，印刷页 74–75](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=75)。
- **客户端实收组呼释放 BYE。** 客户端和媒体面交互，然后向服务器发 200；网侧发出 BYE 和终端实收不能互换，这个 200 也不能替其他客户端证明释放。[§9.2.1.2.3.3，印刷页 170](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=171)；[§6.2.6，印刷页 47](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=48)。

## 两处回指不一致，不能拿它们填全链路

- **O-PF 收客户端 BYE。** 组呼入口 §9.2.1.3.3.1 字面回指 §6.3.2.1.6，后者是优先呼叫条件。旁边 §6.3.2.1.5 才是通用收 BYE 后发 BYE，且通用条文末段的角色又印作“terminating MCVideo function”。将两处并列保留；不据此认定本版这条组呼 O-PF 链已经闭合，也不把优先呼叫处理当成 BYE 转发。[§9.2.1.3.3.1，印刷页 174](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=175)；[§6.3.2.1.5–6，印刷页 66](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=67)。
- **CF 主动发起整场释放或移出一人。** §9.2.1.4.4.2 和 §9.2.1.4.4.3 的标题与触发讲 BYE，字面都指向 §6.3.3.1.5；那一节是紧急组呼 re-INVITE。不能拿它构造 BYE，也不偷偷改成 §6.3.3.1.4。这个回指差异不影响上文 **CF 实收 BYE** 时第 4 项明文回指的通用 BYE 路径。主动移出另一条明文是：**已成功移出客户端后，可向会议状态订阅者发移出通知**。这里是 MAY，不是入站 BYE 后整场继续分支的 SHALL。移出例子也不能单凭一条 BYE 定性为已经解除归属。[§9.2.1.4.4.2–3，印刷页 186–187](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=187)；[§6.3.3.1.4–5，印刷页 78](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=79)。

若要看同一 MC 系统内、已定义组仍在通话时的[一人离开业务流程（Stage 2）](group-call-leave.md)，在那一层区分本人离场和解除归属。若同一 MC 系统内的预安排或聊天组呼已满足至少一项适用终止条件，问[整场释放的业务流程（Stage 2）](server-group-call-release.md)，不能用它补本页的 SIP 回指。若是普通在网按需预安排组呼中[新初始 INVITE 重入或服务器主动迟入](prearranged-group-sip-rejoin.md)，不要把那个 200 当成 BYE 应答。手里若是[在网 MCVideo 组非控制方 NCF 的媒体控制 Release／Ack](noncontrolling-participant-rtp-release.md)，也要先核对其 P 状态或服务器接口实收；它不是本页的关呼信令。
