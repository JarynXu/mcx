# MCVideo 非控制方：无发送许可时 RTP 怎么走，Release 要上送吗？

**P 无发送许可，不等于不能向该端下发 RTP。** 分发器来的 RTP 按下行处理；关联终端来的 RTP 触发本地 Transmission Revoked，原因为 #3。接着若 P 收到该端的 Transmission Release，先看自己是否在等这个参与端的 Release，再看消息是否要求确认。只看到一个 Ack，分不出它走的是哪一支。

本页查 3GPP TS 24.581 V16.9.0（Rel-16，Stage 3）中**在网 MCVideo 组的非控制功能（NCF）**。NCF 中的 **P** 是面向参与端的传输参与者接口：每场会话的每个客户端有一个状态机实例。NCF 还另有面向控制方（CF）的传输控制服务器接口。两处要各自有收件或指示，不能把 P 的事件当成服务器接口已经收到。这里的 Transmission Ack 是媒体传输控制确认，不是 SIP ACK。[§6.5.1，印刷页 102](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=103)；[§6.5.5.1，印刷页 110–111](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=112)；[§6.5.5.3.1，印刷页 112](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=113)。

## P 没有发送许可：先认清 RTP 从哪边来

同一 P 处于 `P: has no permission`，实际收到网络媒体接口的收件指示：

| 收件指示说 RTP 来自 | P 须做什么 |
| --- | --- |
| 媒体分发器 | 要求网络媒体接口把所收 RTP 发向本关联终端。P 仍无发送许可。 |
| 本关联终端 | 向该端的传输参与者发 **Transmission Revoked，Reject Cause #3**（无发送媒体权限），记下期待该参与者的 Transmission Release。P 仍无发送许可。此 Revoked 不经 NCF 的传输控制服务器接口。 |

[§6.5.5.3.9 两段，印刷页 113](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=114)；[§6.5.4.13 注，印刷页 110](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=111)。下行指令不是接收侧获准、终端收包或显示画面的证据。上行分支没有给这批包的转发或丢弃指令；§6.5.5.1 的默认丢弃只适用于没有规定处理程序的事件，不能代替本分支。§9.2.10.1 的通用描述说 Revoked 发向有许可者，但 §6.5.5.3.9 明确也用于这次无许可上行，§9.2.10.2 的原因 #3 与后者对应。仅看见 Revoked，不能填“原本获准”或“由这一个 P 发出”。[§9.2.10.1–2，印刷页 164–165](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=165)。

**服务器接口另看自己的收件指示。** 若分发器报告收到了 CF 发来的 RTP，服务器接口须请求分发器转给本会话中由 NCF 管理、且所用 SSRC 与来包不同的客户端。若媒体分发功能报告已从某个网络媒体接口收到 RTP，服务器接口须请求分发器把这批 RTP 转向 CF。第二项不是 P 本地发 #3 的后续步骤；仅见 P 的本地事件，不能断言违规 RTP 已到分发器、已转向 CF 或已被丢弃。[§6.5.4.12 及注，印刷页 109](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=110)；[§6.5.4.13，印刷页 110](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=111)。

## P 无许可且收到 Release：先查期待记录，再查 Ack 要求

以下都以**同一 P 仍无发送许可，且实际收到关联参与端的 Transmission Release** 为前提。期待的是这个参与端在这场会话的 Release，不用别的终端或另一场会话的记录。每一行处理后，P 都仍无发送许可。[§6.5.5.3.10，印刷页 113–114](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=114)；[§9.2.2.1，表 9.2.2.1-1 与确认说明，印刷页 145–146](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=146)。

| P 在等这个参与端的 Release？ | 这份 Release 要求 Ack？ | P 须做什么 |
| --- | --- | --- |
| 是 | 是 | 向关联参与端回 Transmission Ack，清除期待记录。本分支没有上送 Release 的步骤。 |
| 是 | 否 | 清除期待记录；本项不要求发 Ack，也没有上送 Release 的步骤。 |
| 否 | 否 | 把 Release 转给 NCF 的传输控制服务器接口；不进入要求 Ack 的本地策略分支。 |
| 否 | 是 | 按本地策略，在 P 回 Ack、让外发 Release 不再请求 Ack，或等待传输控制服务器的 Ack，两种做法中取其一。两种做法都须把 Release 转给 NCF 的传输控制服务器接口；收到 Ack 不是转交的额外前提。 |

本地回 Ack 既可能出现在期待分支，也可能出现在没有期待的策略分支。单独一条 Ack 不能判断 Release 是否上送。只见 P 发 #3，未见同一 P 收 Release，也不能断言已清除期待记录。本页所列两条程序没有为等 Release 规定超时或断开动作。[§6.5.5.3.9–10，印刷页 113–114](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=114)。

**服务器接口实收 Release**，才是它按本条向 CF 转发的触发；只有它的被动队列里有该参与端的申请，才移除对应项。看见 P 已转交，不能直接填 CF 已收到或 CF 的主动队列已改变。若 P 当时仍处于有或无发送许可状态，且实际收到服务器接口转来的 Transmission Ack，则交给关联端，P 保持当时的状态。选择等待不证明 Ack 已来。[§6.5.4.3，印刷页 105–106](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=106)；[§6.5.5.5.1，印刷页 115](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=116)；[§6.5.5.5.2，印刷页 116](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=117)。

## P 已有发送许可：收到上游 Revoked 不等于 P 当场转态

**实际收到来自 NCF 服务器接口的 Transmission Revoked** 时，有许可的 P 须把它交给关联参与端。该消息若要求 Ack，P 须记下期待对这个 Revoked 的 Ack。§6.5.5.4.7 写的是 **P 仍为 `P: has permission`**，不是说终端实收了该消息或可以继续发送。这里等的是对 Revoked 的 Ack，与前面本地 #3 分支等该端的 Release 是两件事。[§6.5.5.4.7，印刷页 115](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=116)。

有许可的 P 实收服务器接口转来的 **Transmission Idle** 或 **Transmission Arbitration Taken**，则须转给关联端并进入无发送许可状态。两处状态条款都仅在消息要求确认时记录期待 Ack。表 9.2.2.1-2 的 Transmission Idle 列为不请求 Ack，不从状态条款的条件句推造另一种 Idle。[表 9.2.2.1-2 及确认说明，印刷页 146](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=147)。图 6.5.5.1-1 把 Taken 同时标在有许可自环和转向无许可的边上；这里按 §6.5.5.4.6 的收件条件和三项动作判断，不从重复标记补一个自环条件。[图 6.5.5.1-1，印刷页 111](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=112)；[§6.5.5.4.5–6，印刷页 115](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=116)。

再对照有许可时的两种本地事件：收到关联端上行 RTP 的指示，P 须要求媒体接口把这些包转向分发器；收到关联端的 Transmission Release，P 须把 Release 交给服务器接口。两种事件各按自己的条件判断，P 均留在有许可。不要把无许可分支的期待记录和 Ack 策略套到这里。[§6.5.5.4.2–3，印刷页 114](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=115)。

Transmission Release 可以结束传输，也可以撤回排队的传输请求；消息名本身不是 SIP 挂断或应用与信令面释放指示。[§9.2.7，印刷页 161](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=162)；[§6.5.3，印刷页 104–105](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=105)。要判断这场组呼的终端是否获准接收、是否实收或显示，需查该场对应的接收端证据；不能用普通按需一对一私呼的接收程序补组呼。若另问普通在网预安排组呼的控制方怎样处理某接收者对一路视频的申请，且不涉及 MBMS、接收覆盖或抢占，可查[控制侧逐流接收许可](prearranged-group-reception-server.md)。该页讲控制方，不证明这台终端已收到或呈现。若只剩原因值 5 或 7，查[相同数字在不同消息中的含义](message-scoped-causes.md)；若控制方 U/G 在处理满容量的抢占，查[控制侧撤销与等待](onnetwork-preemption-revoke.md)，不套用 NCF P 的本地程序。
