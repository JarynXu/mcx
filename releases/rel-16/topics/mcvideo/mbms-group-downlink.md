# MCVideo 组呼下行：组播子信道如何映射，哪些成员仍走单播

同一场在网 MCVideo 组呼可以同时使用组播和单播。参与侧 MCVideo 功能为使用组播的业务组分配 MBMS 子信道，再按目标成员是否监听该子信道分发视频。

依据：[3GPP TS 24.581 V16.9.0，Release 16，Stage 3](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf)，§4.1.2、§10.1。

## 一条承载如何区分多个业务组

参与侧 MCVideo 功能先激活 MBMS 承载，并向服务区内的客户端通告其标识 TMGI。一条承载可以供多个组共用。承载通告让终端能够监听这条承载；具体哪组使用哪些子信道，由后续的 `Map Group To Bearer` 消息给出。

组会话已经存在，但本次传输尚未启用 MBMS 子信道。此时，参与侧收到传输请求或媒体传输通知后，若决定使用 MBMS 且承载容量足够，就在通用子信道上首次发送 Map。Map 把 MCVideo 组 ID 与 TMGI、子信道参数关联起来，其中包括组播目的地址和相应端口。容量不足时，参与侧可以把已有会话移到单播以腾出容量，也可以用 MBMS 送信令、用单播送媒体。

本次传输已经使用 MBMS 子信道时，参与侧若收到发给该子信道监听者的媒体传输通知，就经该子信道转发这条通知。收到通知本身不会触发 Map 重发；T301 到期时，参与侧才按重发流程在通用子信道上再发 Map，让晚到的终端也能取得映射。

依据：§4.1.2.1–2（印刷页 22），§9.3.4 表 9.3.4-1（页 184–185），§10.2.2.1–2（页 193–194），§10.2.3.3、§10.2.3.8（页 195、196）。

## 同一场组呼如何分发给不同成员

假设甲和乙都是这段视频的目标组员：甲正在监听对应子信道，乙不能接收。参与侧为甲处理 RTP 视频包时，先查该包是否已经在这条子信道上发过；发过就丢弃这个待转发副本，没发过才让媒体分发功能组播。给乙的媒体仍走单播。对于其服务的已归属成员，参与侧根据已知或能推知的接收情况，把媒体和媒体面控制消息分别经相应的单播承载送给不接收或无法接收该子信道的成员。

依据：§4.1.2.3（印刷页 22–23），§10.2.3.5（页 195）。

## 客户端如何处理映射和收到的包

客户端在通用子信道收到 Map 后，保存组 ID 与 TMGI、相应子信道之间的关联。如果承载通告已声明音视频采用前向纠错（FEC），客户端此时为该子信道建立解码器。

收到的包若能匹配到正在进行的组内传输，客户端就按包的类型处理：控制消息交给传输参与者，未受 FEC 保护的 RTP 包直接交给媒体混合功能，受 FEC 保护的 RTP 包及相应的修复包交给解码器。解码后的 RTP 包再交给媒体混合功能。

没有对应的活动传输映射时，客户端忽略收到的控制消息或 RTP 包。收到 `Unmap Group To Bearer` 时，则按消息中的组 ID 移除已有的对应映射。

依据：§10.3.1–4（印刷页 197–198），§10.4.3（页 198–199）。
