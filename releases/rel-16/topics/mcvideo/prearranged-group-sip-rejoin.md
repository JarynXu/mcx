# MCVideo 预安排组呼重入：INVITE 和 200 各用哪个会话身份？

**目标是回到原来那场组呼，终端发的是新的初始 INVITE。** Request-URI 填待重入的 MCVideo 会话身份 URI。若控制侧实际获知成员刚归属该组或恢复覆盖，另有服务器发起迟入邀请的程序。两条路径看谁先发请求，不是一个流程的前后两步。

这里查的是 Rel-16 **在网、普通按需预安排 MCVideo 组呼**的 Stage 3 信令。不含紧急、迫近危险、广播、聊天组、离网或已建 SIP 对话中的 re-INVITE。文中 CF 是控制功能，O-PF 是发起侧参与功能，NCF 是组的非控制功能。

## 终端主动重入：前后两段 Request-URI

用户要求回到一场正在进行的会话，或恢复覆盖已经触发重入时，客户端按初始 INVITE 程序发请求。**Request-URI 填该场 MCVideo 会话身份的 URI**。不能用组 ID 或普通首次建呼使用的参与功能公共业务身份代替；MCVideo 会话身份、正文里的组身份、SIP 对话是三样东西。本条不规定终端如何获知已经恢复覆盖，也不从恢复覆盖推断终端已发请求。[TS 24.281 V16.12.0 §9.2.1.2.4.1，印刷页 170](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=171)。这条回指首次程序的第 9 项，实际第 9 项是 Session-Expires，第 10 项才是 Request-URI。按本条直接写明的 URI 读，不把这处回指当成定时器改法。[§9.2.1.2.1.1 第 9–10 项，印刷页 162](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=163)。

O-PF 收到这类请求且 MIME 的 `session-type` 是 `prearranged`，按预安排组呼的发起侧程序处理。走到生成下一段 INVITE 时，**出站 Request-URI 用入站 Request-URI 所给会话身份映射得到的 URI**，不按普通第 10 项填组关联的 CF 公共业务身份。标准没有在这一节规定映射怎么实现，也没说两段 URI 必须相同。判断失败先找响应节点：用户的同时组呼数已超限时，沿用的 O-PF 基本程序要求回 486，Warning 文本码 103；这并不是下面 CF 的本场人数上限。[§9.2.1.3.1.1 第 5、9–10 项，印刷页 171](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=172)；[§9.2.1.3.5.1，印刷页 175](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=176)。

## CF 收到重入请求：先看在哪一项停止

以下按 CF 对本场会话身份收到重入 INVITE 后的程序读。若一项已拒绝，不能假定后面的检查已经通过。

| CF 检查 | 这一项的结果 |
| --- | --- |
| 资源不足而不能处理，或有拥堵风险 | 可回 500，也可带 Retry-After；未采用此拒绝，继续检查。 |
| 入站 Request-URI 对应的组呼不在 | 回 404。这里找的是本场组呼，不是检查组文档。 |
| SDP 的媒体参数不可接受，或没有提供 MCVideo 编解码 | 回 488。 |
| Accept-Contact 缺少 `g.3gpp.mcvideo`，或缺少值为 `urn:urn-7:3gpp-service.ims.icsi.mcvideo` 的 `g.3gpp.icsi-ref` | 回 403，不继续。这一项没指定 Warning 文本码。 |
| 已确定主叫 MCVideo ID，但该用户不满足加入本场预安排组会话的授权规则 | 回 403，Warning 文本码 121。 |
| 到归属检查时，用户未归属该会话所关联的 MCVideo 组 | 回 403，Warning 文本码 120。 |
| 本场已到参加人数上限 | 若按本地策略该用户优先于已有参与者，CF 可以按移人程序移出一人并跳过 486 分支。未走这项且仍落在人数上限分支时，回 486，Warning 文本码 122。 |

依据：[§9.2.1.4.5.1 第 1–10 项，印刷页 187](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=188)。121、120、122 是 Warning 文本前缀，不是 SIP 响应码，也不是 Warning 头的 399 数值本身。[§4.4.1–2，印刷页 26](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=27)。

加入授权按组文档规则判，**授权与已归属是两项检查**。通过第 6 项后，CF 按第 7 项的回指缓存从 Contact 收到且自身支持的 SIP 特征，再核对第 8 项的归属。第 8 项把归属判定回指 §6.3.3.5；该节讲的是组呼定时器 TNG3。保留“未归属 → 403／120”的直接规定，不把定时器当成归属算法。[§6.3.5.3，印刷页 104–105](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=105)；[§6.3.3.2.2，印刷页 89](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=90)；[§6.3.3.5，印刷页 94–95](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=95)。

归属检查之后、人数检查之前，CF 须核对入站请求有没有 Resource-Priority。对带这个头的请求，可以按回指的程序给予优先处理。它不替代满员时的本地策略判断。**看见较高优先级或 Resource-Priority，不足以确定移了谁、是否已经移出、或者重入是否成功。** [§9.2.1.4.5.1 第 9–10 项及注 2，印刷页 187](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=188)。

## 到达成功分支：Contact 和通知各自说明什么？

CF 生成 200 OK，附入站 offer 的 SDP answer；Contact 里的 SIP URI 标识该会话在 CF 的会话身份。按第 13 项与媒体面交互；注 3 说明相应媒体面处理完成才执行下一步发送 200。**即使没有客户端订阅会议状态事件包，CF 走到成功分支也须发 200。**

随后才看会议通知：CF 为已订阅的客户端生成加入通知。第 16 项写“向各客户端”发送 SIP NOTIFY；第 15 项生成对象和会议通知专节的发送对象均明确是订阅者，不能据第 16 项单句扩大到未订阅成员。看到 200 不能证明有订阅者、通知已发出或已被收到。200 和 SIP NOTIFY 也都不证明画面已到达或本端已有发送许可。[§6.3.3.2.3.2 第 5 项，印刷页 90](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=91)；[§9.2.1.4.5.1 第 11–16 项及注 3，印刷页 188](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=189)；[§9.2.3.4.2，印刷页 230](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=231)。

组的 **NCF** 收到这类重入请求，Request-URI 带正在进行的会话身份时，它**面向该客户端**按上述终接程序充当控制功能。它的 200 Contact 填 **NCF 自己生成的会话身份**，不能把上游 CF 的 Contact 当成本条要求。角色只限这一侧，不能据此判断整个组呼已经换控制方，也不能推断后续 ACK/BYE 路由。通知回指本版正文没有列出的 §9.2.3.5.2；§9.2.3.4.2 实际列在 CF 下，不能用它无声补齐 NCF 的专用通知程序。[§9.2.1.5.3.1，印刷页 197](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=198)；[§9.2.3.4.2，印刷页 229](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=230)；[§9.2.3.4.4 后转 §9.2.4，印刷页 231](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=232)。

## 服务器主动邀请迟入：看谁收到通知

CF 或 NCF **实际获知**某客户端刚归属组或恢复覆盖时，须按各自的发起程序邀请该客户端加入正在进行的组呼。CF 回指 §9.2.1.4.1，面向客户端邀请的第一跳 Request-URI 是相关 T-PF（终接侧参与功能）的公共业务身份；NCF 回指自己的 §9.2.1.5.1。从覆盖恢复本身不能得知谁获知事件、哪条 INVITE 已发或两条路径撞在一起时如何取舍。本节也不说明如何取得恢复覆盖的通知。[§9.2.1.4.1.1 第 2 项，印刷页 176](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=177)；[§9.2.1.4.6，印刷页 188](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=189)；[§9.2.1.5.1，印刷页 193](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=194)；[§9.2.1.5.3.2，印刷页 197](https://www.etsi.org/deliver/etsi_ts/124200_124299/124281/16.12.00_60/ts_124281v161200p.pdf#page=198)。

要看两条业务流程、功能别名或媒体传输信息通知，读[预安排组呼迟入与重入（Stage 2）](prearranged-late-entry-rejoin.md)。若处理的是普通组呼首次建立，读[客户端首次请求和应答](prearranged-group-client-establishment.md)。若问题涉及客户端获准发送或实际 RTP，读[预安排组呼的传输控制](prearranged-group-transmission-server.md)，并核对该页的状态和适用条件。
