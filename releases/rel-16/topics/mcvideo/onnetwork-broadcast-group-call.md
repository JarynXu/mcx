# 在网 MCVideo 广播组呼：何时能发视频，何时结束，优先于哪些组呼？

**发起方不必等接收者应答才开始传媒体。** 在这场广播组呼中，只有发起用户可以发送媒体；发起用户传输完成后，释放的是整场广播组呼。这里说的是 Release 16 的在网 MCVideo，而不是离网广播的不活动释放。[3GPP TS 23.281 V16.4.0，Stage 2，§7.1.2.4.1，印刷页 41](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=42)；[§7.1.2.4.2 开头、步骤 2–3 及注 1，印刷页 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=43)。

**两类广播怎样建立？** 客户端甲、乙都是本次所用广播组的成员。无论用的是用户广播组（user-broadcast group）还是组广播组（group-broadcast group），都走同一广播程序。甲的用户发起组呼建立，沿用预安排组呼的建立信令（§7.1.2.3.1.1），并带上广播组呼指示；随后由甲开始传媒体。接收者的应答不是开始传媒体的条件，这不等于整个建立过程没有协议响应。反过来，只看到甲在发视频，也不足以认定这是广播。[§7.1.2.4.2 前提 1、步骤 1–2，印刷页 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=43)。

**优先范围怎么判？** 两类广播的建立方式相同，但注 2 比较的对象不同：

- **用户广播组**：看另一场组呼有哪些用户参与。广播优先于涉及该用户层级内用户的组呼。
- **组广播组**：看另一场组呼在哪个组上进行。广播优先于其下属组上的组呼。

如果只知道另一场呼叫也在进行，不知道它是否属于上述范围，就不能用这条注为两场呼叫排序。注中给出的是限定范围内的优先关系，没有说另一场呼叫必定被强制拆除。[§7.1.2.4.2 注 2，印刷页 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=43)。

**怎样判断整场结束？** 步骤 3 看的是发起用户的媒体传输是否完成，不是乙是否静默、有没有看到最后一帧。光凭甲的画面短暂停住，不能断定其传输已完成；光凭甲开始发送，也不能证明乙已收到或观看。[§7.1.2.4.1，印刷页 41；§7.1.2.4.2 步骤 2–3，印刷页 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=42)。

离网广播是否因一段时间内没有往来传输而释放，见[离网广播的不活动条件](offnetwork-broadcast-inactivity.md)。一般在网组呼中若只是一个人离开，个人资源与整场组呼要分开判断，见[组呼成员退出](group-call-leave.md)。[结构化条件与声明](onnetwork-broadcast-group-call.json)。
