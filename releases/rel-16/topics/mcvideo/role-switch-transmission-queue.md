# MCVideo 组会话换控制方：已排队的传输请求怎么办？

看原控制方手里还排着哪些请求，先分清它是在**准备合并**，还是已收到**完成切换**的请求。准备时要交代的是当前发送者；完成切换时要逐一转交的才是仍在排队的请求。反过来，原来只跟踪请求的一方接任控制，则把自己跟踪到的请求移入主动队列。

## 让出控制：什么时候才转交排队请求？

应用与信令面要求准备与另一个组会话合并时，原传输控制服务器须释放本次呼叫的一般传输控制状态机实例。只有处于 G: transmit taken（已有发送者）时，服务器才按本项把当前发送者的信息交给应用与信令面。条款的注说明，后者用这份信息通过 SIP MESSAGE 提出传输请求；这不是把排队成员的请求逐条转发。

对原控制功能所管组内、且已参与这场会话的每个 MCVideo 客户端，服务器须生成一个 0 至 4294967295 范围内的随机临时标识，保存标识与该传输参与者接口的对应关系，记录 mc_queueing 与 mc_priority 已协商的能力和该客户端是否请求隐私，并启动该参与者接口的状态机。释放旧的一般传输控制实例、启动这些接口，都不等于已完成切换。

依据：[TS 24.581 V16.9.0，Release 16，Stage 3](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=104)，§6.5.2.3.1、§6.5.2.3.2（印刷页 103–104）。

要进入第二步，应用与信令面须先收到确认：传输控制服务器与面向它的接口之间的 SIP 会话已经建立。旧服务器收到应用与信令面要求完成切换的请求后，才开始充当这个接口。如果旧主动队列存在，接口须为其中每一项向传输控制服务器发一条 Transmission Request，然后把整个旧主动队列移为被动队列。没有主动队列就没有这两项队列操作，但仍须开始充当接口，并执行 §6.5.4 的接口规程。

**发出的请求怎样保留来源？** 每条请求都须带上参与者原来给出的全部字段。临时标识用准备阶段保存的那一个：

- 原请求已有 `Track Info`：把临时标识追加在已有 `Transmission Participant Reference` 项的末尾，不替换旧引用。
- 原请求没有 `Track Info`：增添这个字段。`Queueing Capability` 填协商所得的 `mc_queueing` 值；`Participant Type` 按可用的 `participant-type` 值填写，没有就填 `unknown`；第一条 `Transmission Participant Reference` 填该参与者的临时标识。

依据：[§6.5.2.3.3 第 1–4 项](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=105)（印刷页 104）。本条要求接口发出请求，不以新控制方已经收妥或批准作为本地移动队列的条件。

## 接任控制：被动队列里的请求去哪儿？

非控制功能转为控制功能时，服务器新建一个一般传输控制状态机实例，并为这场呼叫中的每个 MCVideo 客户端各增加一个面向参与者的基本传输控制实例。被动队列中已有的每个传输请求都移入主动队列。被动队列原先用来跟踪本非控制功能所管参与者发出的请求，并非全组的权威队位表。迁移的是待处理请求；两种切换都不能单凭迁移动作认定队位不变、请求已获准或视频已经发出。

依据：[§6.3.2.3 及其注](https://www.etsi.org/deliver/etsi_ts/124500_124599/124581/16.09.00_60/ts_124581v160900p.pdf#page=54)（印刷页 53）。本条不是让出控制的第二步，也没有要求在接任控制时照搬前述逐条转发步骤。

如果问题是成员怎样查询队位、收到授予后何时能发送，请看[普通预安排组呼的队位与授予](prearranged-group-queue-position.md)。
