# 离网 MCVideo 拉视频给自己：甲收到“已接受”，什么时候才算甲端出了画面？

甲想看乙端的视频。甲端把拉取请求直接发给乙端，请求里指定**甲端自己收视频**。乙端自动接受并发回应答。**甲端收到这份应答后，通知甲“拉取已接受”**（步骤 3）。乙端发了应答，不能证明甲端已经收到；甲端收到，也不能单凭收件记录验收它已经通知甲。这时还不能验收画面：两端还要建立媒体面，乙端才向甲端传视频，由甲端呈现给甲。规范把“呈现给甲”写在步骤 5，没有把“甲本人看过”列为该步骤的结果。[3GPP TS 23.281 V16.4.0，Rel-16，Stage 2，§7.3.3.3.2 步骤 1–5，印刷页 89](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=90)。

## 两台设备同组，够不够？

不够。这个例子从**甲已向乙发起拉取**开始。两端须属于同一 ProSe（邻近服务）发现组，而且都支持 ProSe 一对一直通；甲端还须已通过 ProSe 发现程序，在附近发现**与乙用户关联的乙端**。组成员名单能核对同组，设备能力能核对直通支持，哪一项都不能代替本次发现结果。记录里若只有“发现一台附近设备”，还要核对发现的是不是乙端。[§7.3.3.1，印刷页 87](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=88)；[§7.3.3.3.1–2 开头及前提 1–3，印刷页 88](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=89)。

这是两客户端的离网直通，不经过 MCVideo 服务器。它复用离网私呼的请求和应答：甲的请求带 SDP offer（媒体参数提议），乙的接受应答带 SDP answer（所接受的媒体参数）。通用请求表把视频拉取指示列为可选，因为这张表也供别的私呼使用；本程序的步骤 1 则明确要求请求表达拉取，并指明甲端是视频预期接收方。只有“甲向乙发过私呼请求”，没有请求用途和接收方的材料，不能据此把这通通信认成拉给自己，也不能按请求方向认定甲是视频源。[§7.3.3.2，印刷页 88](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=89)；[表 7.2.3.2.1-1、7.2.3.2.2-1 及各自注 2，印刷页 76](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=77)；[§7.3.3.3.2 步骤 1、2b，印刷页 89](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=90)。

## 乙端通知乙什么，甲端又通知甲什么？

乙端通知乙的是“甲来拉视频”（步骤 2a）。发给甲端的接受应答由**乙的客户端自动作出**（步骤 2b）。乙端可以自主运行，也可以由人控制；两种情况走同一程序。通知乙和自动应答可以任意先后。即使乙端先发应答、后通知乙，也不缺一个“请乙先点同意”的步骤。只有应答日志时，也不能声称已经通知了乙，或乙本人同意了。[§7.3.3.3.2 适用对象，印刷页 88](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=89)；[步骤 2a、2b 及注 1，印刷页 89](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=90)。

甲端收到本次接受应答后，按步骤 3 通知甲拉取已获接受。**通知是流程中的一步**；要认定某次通知确实发生，须有甲端通知用户的证据。验收时，把记录对到同一次拉取，按能证明的最远一步写：

| 现有记录 | 可以验收到哪里 |
|---|---|
| 乙端已发送接受应答；没有甲端记录 | 乙端已接受并发出应答。不能代甲签收，更不能登记甲端已通知用户。 |
| 甲端只记录收到接受应答 | 能签甲端已收，不能签它已提示甲。查甲端同次会话的用户通知记录；若证实没有通知，则步骤 3 未完成。 |
| 甲端已收到接受应答并提示用户 | 甲端已通知甲本次拉取获接受。要验收步骤 4，还需这两端建立媒体面的结果。 |
| 两端媒体面已建，但未见视频接收 | 步骤 4 完成。要验收视频已到达，查乙发往甲的这路媒体及甲端接收记录。 |
| 甲端已收到乙的视频，显示端没有记录 | 能验收到达。要验收步骤 5 的呈现，还需甲端将这路画面呈现给甲的证据，例如同次会话的首帧显示记录。即便呈现属实，也不能替甲本人确认看过。 |

这些是取证例子，不是规范指定的日志名或报文格式。[§7.3.3.3.2 步骤 2b–5，印刷页 89](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=90)。

若一端建立通信失败，该端**宜**向相应客户端发送带失败原因的私有通信失败响应。收到失败响应可能在媒体会话建立之前，也可能在之后；若会话已经建立，则终止会话，并通知本端用户失败及原因（如有）。若收到时尚未建会，没有已建会话可终止；这条注没有单独规定建会前是否通知用户。收到失败响应本身不能证明此前建过会话或甲端此前出过画面。[§7.3.3.3.2 注 2–3，印刷页 89](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=90)。

如果实际是在普通[离网自动私呼](offnetwork-automatic-private-call.md)中给被叫传自己的画面，不要照搬本例的媒体方向，也不要反过来把普通私呼的指定端检查加进本例。若乙打算把收到的视频另推给丙，查[离网转推](offnetwork-local-video-push.md)；若甲经服务器向乙拉取，查[在网一对一拉取](one-to-one-video-pull.md)。
