# 一对一视频推送：谁能发画面，多台终端中哪台接呼？

甲要把自己终端的画面推给乙。这是一种在网 MCVideo 私呼，但在**本次推送**中，只有主叫甲能向被叫乙发送视频。乙的客户端可以应答呼叫，这不赋予乙反向发送视频的权利。甲端经授权的用户可以手动发起，也可以在甲端设置触发条件，让客户端自动发起。如果是丙从别处要求甲向乙发视频，则有另一层远程推送请求：甲接受丙的远程请求后，仍可复用这里的一对一建呼流程。只看到甲、乙建呼，不能据此断定此前有丙参与。[TS 23.281 V16.4.0 §§7.4.2.3.1–2，印刷页 93](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=94)；[§7.4.2.5.2 步骤 1、4，页 96](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=97)

**先选人，再按条件选终端。** 甲的客户端向 MCVideo 服务器发送私呼请求，其中有乙的 MCVideo ID、列出一种或多种媒体类型的 SDP 提议，以及表明甲要向乙发视频的推送指示。服务器分别核查甲能否发起、乙能否接收这种推送私呼。甲可以不带功能别名；若带了，服务器还要检查该别名可供甲使用且已为甲激活。

通过授权检查后，服务器向乙端转送请求。媒体类型沿用甲提议的全部或其中一部分；请求携带自动开始模式指示，依据是甲请求的开始模式或乙端设置。若乙用多台终端注册了 MCVideo 服务，**并且**已指定其中一台接收私呼，这次的入呼请求就只发给指定的那台。只知道乙注册了两台、不知道是否指定时，这一条不能判定两台都收到，也不能判定只发到哪一台。乙的客户端会通知乙有视频推送来呼；若请求中带有甲的功能别名，也会显示它。[§7.4.2.3.2 图 7.4.2.3.2-1，页 93；步骤 1–5，页 94](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=95)

**进展、接通和传完是三件事。** 服务器可以向甲端报告建呼进展；注 1 明确，这个标成步骤 3 的提示也可以出现在服务器已转送请求（步骤 4）和乙端返回应答（步骤 6）之间。提示既非必需，也不是最终应答。图中的成功路径上，乙端接受并向服务器应答，服务器再向甲端报告建呼成功；两端建立媒体面和传输控制，可以进行媒体通信。这不证明乙的终端已经呈现画面，更不证明乙本人已经看过。

**视频传输完成时，释放本次私呼。** 判断释放的依据是传输完成，不是乙收到来呼提示，也不是甲收到建呼成功应答。推送的释放沿用 §7.2.2.3.3 的私呼释放程序；本条并未指定每次都由甲或乙首先挂断，也没有规定以“已观看”作为释放条件。[§7.4.2.3.2 步骤 3、6–8 及注 1–2；§7.4.2.3.3，页 94](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=95)

这是 Release 16 的 Stage 2 流程，不是逐条 SIP 报文规则。要判断普通按需私呼的 SIP 应答该怎么看，见[普通私呼的客户端应答](private-client-answer-evidence.md)；若关注的是普通按需呼叫的准入与转送，见[普通私呼的服务器准入与路由](private-server-admission-routing.md)；要区分建呼、媒体许可与实际媒体交换，见[会话、传输控制与媒体分发的职责](functional-media-control-roles.md)。本页不处理视频拉取、向服务器推送、群推或离网通信。
