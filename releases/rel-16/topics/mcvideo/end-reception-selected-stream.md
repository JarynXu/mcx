# 在网 MCVideo：乙停收甲的一路视频，甲也要停发吗？

不一定。乙停收，直接改变的是**服务器是否继续把这一路视频发给乙**。甲是否也要停发，得另看乙停收是否使这路视频的继续传输条件不再满足。

下面两种流程都在同一 MC 系统内：MCVideo 会话已建立，参与端与传输控制服务器之间已建立传输控制，甲已获准发送媒体。假设乙正在看甲的一路视频。规范为简化描述只画出两台终端，不表示只有乙能接收。[3GPP TS 23.281 V16.4.0（Release 16，Stage 2），§§7.7.1.3.2A、7.7.1.3.2B 各自的引言和前提，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=133)

### 谁先要求停收？

- **乙自己决定不看了。** 乙端把接收结束请求发给传输控制服务器，在请求中指明要停收的流。服务器向乙答复，并根据收到的请求停止向乙下发所选流。请求不是发给甲的，服务器也不需要等乙再回一次响应才停下行。[§7.7.1.3.2A 步骤 1–4，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=133)
- **服务器决定乙不再接收。** 传输控制服务器根据事件或配置作出决定，向乙端发出指明该流的接收结束请求。乙用户得到通知，由乙端向服务器答复；服务器停止向乙下发所选流。用户得到通知，不等于由用户提出申请，也不能把乙端的响应当作用户手动同意。[§7.7.1.3.2B 步骤 1–5，印刷页 133](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=134)

两种流程用的消息都叫 **Media Reception End Request / Response**。若只看到响应名称，不能判断谁先提出停收。若只看到一份响应，即使知道方向，也不能把它当作下行实际停止的媒体记录。

### 什么时候才轮到甲停发？

两条流程都单独检查同一件事：**如果乙结束接收使该路视频的继续传输条件不再满足，传输控制服务器就另行发起媒体发送结束程序**（§7.7.1.3.6.2）。例如，若丙还在接收甲的同一路视频，且继续传输条件仍满足，服务器应停止给乙发这一路，却不因乙停收而启动这个分支。只知道还有丙，不能反过来断定继续传输条件一定满足。若已知条件因乙停收而失效，能据此判定服务器应发起后续程序；要断言甲的发送已经结束，还需该程序的执行记录。[用户发起：§7.7.1.3.2A 步骤 4–5，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=133)；[服务器发起：§7.7.1.3.2B 步骤 5–6，印刷页 133](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=134)。

在记录里要对准接收者和流：乙停收甲的一路，不能由此认定乙的其他视频都停了、其他接收者都停了，或整场呼叫已经释放。若查[整场组呼的释放](server-group-call-release.md)，要看针对那场呼叫的释放程序；若查[普通私呼客户端等待结束响应的状态](reception-client-permission-and-end.md)或[接收许可被覆盖时的通知](reception-override-downlink.md)，则是另外的问题。
