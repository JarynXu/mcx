# 离网 MCVideo 私呼：收到释放应答，整通私呼就结束了吗？

**不能这样判定。释放应答确认对方客户端收到了请求；只有两个方向的媒体面都已释放，这通私呼才结束。** 媒体面承载一个方向的视频。两端共同释放甲到乙的媒体面，仍只是释放了一个方向；如果乙到甲的媒体面还在，私呼就没有结束。[TS 23.281 V16.4.0（Rel-16，Stage 2），§7.2.3.6.2 步骤 2a、3，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=84)

### 谁能发起，收到请求后做什么？

这套流程适用于两端正在进行的离网私呼，不论当初是手动还是自动建立。在通信期间，原来发起私呼的人和接到私呼的人都可以随时请求释放：可以只释放一个方向，也可以结束整通私呼。条款示例里的 A 是**这次发起释放的人**，未必是当初发起私呼的人。[§§7.2.3.6.1–2 总述及前提，印刷页 82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=83)

例如，甲原先呼叫乙，现在乙要释放。乙的客户端直接向甲的客户端发请求（步骤 1）。甲端接到后向乙端回复收件应答（2a），并把释放请求告知本端用户甲（2b）。**这两件事不分先后**：乙收到应答时，不能据此判断甲已经获知请求；通知的也不是请甲批准挂断。[§7.2.3.6.2 步骤 1、2a、2b 及注，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=84)

接下来才是步骤 3：两端按请求释放相应的媒体面。若请求结束整通通信，步骤 3 涉及两个方向；若只请求释放一个方向，就要看另一方向是否也已释放。例如，另一方向先前已经释放，这次实际释放剩下的一向，同样会结束私呼。不论请求选了哪种范围，单有应答都不足以证明步骤 3 已经完成。[§7.2.3.6.2 程序说明，印刷页 82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=83)；[同节步骤 3，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=84)

### 请求和应答里的两个用户 ID 指谁？

两表都必列两个 MCVideo 用户 ID：**原来请求通信的人**和**当时请求与之通信的人**。在上例中，两表对应的被标识者依次都是甲、乙，即使这次是乙先发释放请求。按两表的注 1、2，若是甲发起视频推送，甲是视频源，乙收视频；若是甲发起视频拉取，甲想收视频，乙才是视频源。不能单凭谁发起释放就给两个 ID 交换角色。[表 7.2.3.2.3-1、7.2.3.2.4-1 及各表注 1、2，印刷页 77](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=78)

**释放原因**只在请求表中列为可选项，应答表没有这一项。两表也都没有单列“一个方向／整通”的字段；请求有这两种范围，依据是 §7.2.3.6.2 的程序说明。不能把缺少原因解读成默认释放整通，也不能从这些 Stage 2 表推定范围在线路上用哪个字段、哪个取值表示。

若要判断[离网手动私呼是否已经建立](offnetwork-manual-private-call.md)，应区分振铃、接受和媒体建立。若记录中出现服务器中转，应查[在网一对一 MCVideo 私呼释放](private-call-release.md)，不要套用这里的端到端应答顺序。
