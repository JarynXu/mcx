# 在网 MCVideo：服务器给甲发送许可，怎么判断被抢占的乙是排队还是终止？

**看服务器发给乙端的撤销原因，不看甲的优先级，也不看甲端的授予通知。** 同一个 MC 系统里，甲、乙的客户端与 MCVideo 服务器已经建立会话，参与端与传输控制服务器也已建立传输控制。这个抢占示例还有两个前提：乙已获准发送，但此刻只是**可能**正在发视频；达到上限的是这场会话的**媒体发送数**，不是乙的接收流数。只画甲、乙是为了简化，不限两台终端。[3GPP TS 23.281 V16.4.0，Release 16，Stage 2；§7.7.1，印刷页 123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=124)、[§7.7.1.3，印刷页 129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=130)、[§7.7.1.3.3，引言及前提 1–4，印刷页 135](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=136)。

甲想发视频，甲端给传输控制服务器的发送请求带有发送优先级，必要时还带其他信息。**请求不是裁决。** 在这个例子里，服务器决定接受甲的请求，并选择排队或终止乙的这路发送。仅有甲的请求，即使写了高优先级，也不能证明服务器已经接受，更不能替服务器选定乙的去向。[§7.7.1.3.3，步骤 1–3，印刷页 136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=137)

### 给乙的是撤销，给甲的是授予

服务器向**乙端**发撤销消息（Transmission revoked），说明乙的发送被排队还是终止；向**甲端**发发送授予（Transmit media granted）。随后，乙的传输控制参与端获知撤销及其处置，甲端用户得到授予通知。若只有服务器发出两条消息的记录，不能把两端也记作已经获知。即使确知甲用户已获通知，甲端开始向传输控制服务器发送视频仍是下一步；看见甲已开始上行，也不是其他终端已收到或显示画面的证据。[§7.7.1.3.3，步骤 4a/4b、5a/5b、6，印刷页 136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=137)

### 怎么读乙的撤销消息？

在网撤销信息流由传输控制服务器发给参与端。以下是这条**信息流**的字段，不是只有上述满容量示例才适用的报文检查表。[§7.7.1.2.10，引言，印刷页 125](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=126)；[表 7.7.1.2.10-1，含注 1、注 2，印刷页 126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=127)。

| 字段 | 怎样判读 |
| --- | --- |
| 撤销原因 | 必选（M）。原因区分本例的两种处置：乙的发送排队，或乙的这路发送终止。终止不等于整场会话释放。 |
| 队列位置 | 可选（O），但注 1 规定：因排队而撤销时要带上位置。若乙的发送排到第三，第三是这次撤销给出的队位，不是新的许可，更不是保证稍后恢复。 |
| 媒体标识 | 可选（O）。字段描述把它限定为仅在媒体复用时出现，用于标识通信，例如区分复用的媒体流；注 2 又规定因终止而撤销时要带上媒体标识。**已知使用复用且原因为终止**，两处文字都适用。若已知没有复用、原因却是终止，不能择一删去另一处限制，再据此判定缺标识一定合规或一定违规。只有媒体标识而没有原因摘录，也不能反推一定是终止。 |
| 是否要求确认 | 可选（O）。它说明是否要求参与端确认，不是参与端已经回复的证据。 |

**下一步查什么？** 若要问已经排队的发送者现在排第几，查[查询当前队位](current-queue-position.md)。若要追普通在网预安排组的显式抢占，特别是满容量时的撤销等待、旧媒体与实际 End 事件，查[该组呼的 Stage 3 状态机](onnetwork-preemption-revoke.md)，不要用它替这张 Stage 2 表裁决缺字段。若是同一系统内的在网接收端已满，且另有新流待送该端，查[谁选让位的接收流](reception-override-modes.md)。若在普通在网预安排组里接收端已获准，服务器收到上行视频却不能转发给该端，查[接收侧的下发与通知](reception-override-downlink.md)。这两种接收侧记录都不等于乙的发送被撤销。
