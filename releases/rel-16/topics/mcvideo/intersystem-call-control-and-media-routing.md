# 跨系统 MCVideo：谁控制这通呼叫，视频该到哪个系统？

**呼叫控制、视频去向和实际收件，要分别查。** 组呼的视频须路由到定义该组的 MCVideo 系统。私呼视频按 MCVideo 专规的两种路由选项之一处理。通用呼叫控制另查 TS 23.280：在 §5.2.10.1 所述互连范围，两个 MC 系统分别为两侧用户提供业务，且分属不同信任域。这时若有组归属系统的伙伴侧用户实际参加这通组呼，组归属系统提供控制；若两名用户由不同系统服务且这通私呼实际使用互连，主叫当前的服务系统提供私呼控制。[TS 23.281 V16.4.0 §5.1，印刷页 13](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=14)；[TS 23.280 V16.7.0 §5.2.10.1 开头，印刷页 23](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=24)；[§5.2.10.1 续、§5.2.10.4–5，印刷页 24](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=25)。

这里查的是 Rel-16 **Stage 2**。例如，G 由甲定义，组员林的主系统是丙，林当前在乙接受业务。甲是 **G 的组归属系统**；乙、丙分别是**林的服务系统、主系统**。在本例，甲、乙分属不同信任域，分别给两侧用户提供业务。此时还要核实乙是相对于 G 归属系统的伙伴，且林实际参加这通组呼，才按 §5.2.10.5 判甲负责控制。乙是林迁入的伙伴、缓存了 G 配置，或林已归属 G，都不能代替组伙伴关系和实际参呼。若在上述互连范围内，林从乙经互连给由不同 MC 系统服务的周打私呼，则按 §5.2.10.4 由乙负责私呼控制。信任域关系未知，或已知两系统在同一信任域时，不能用这两款通用互连规则判本次控制方；不影响按 TS 23.281 §5.1 判断已识别组呼或私呼的视频路由要求。要查[通用互连里的控制归属、用户授权和连通性](../identity/interconnection-authorization.md)，按当前提供业务的系统取证，不用用户主系统名称猜。[TS 23.281 §3.1，印刷页 12](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=13)；[TS 23.280 §5.2.10.1，印刷页 23–24](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=24)；[§5.2.10.4–.5，印刷页 24](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=25)。

## 视频去向按组呼、私呼分开

| 要判断哪条规则 | TS 23.281 §5.1 写的媒体去向 |
| --- | --- |
| **组呼** | 视频流须路由**到**该组的归属 MCVideo 系统。不能从这句话判定只有该系统处理媒体、已实际收到视频，或所有终端都已接收。 |
| **私呼，选项 1** | 两人属同一组织，经主 MCVideo 系统；两人属不同组织，经两人各自的主 MCVideo 系统。条文按**组织**分支，不按两人是否由同一系统服务分支。未规定跨两个主系统的先后顺序。 |
| **私呼，选项 2** | 视频可以在主 MCVideo 系统的控制下本地路由，经过一个能把媒体复制给各用户主 MCVideo 系统的实体。仅凭条文没有选定是哪个用户的主系统控制，也没有证明每份流实际复制、对端收到，或规定怎么去重。 |

私呼须按两种选项中的一种路由。不是先走选项 1、再走选项 2，也不把私呼的本地分支借给组呼。看到本地节点，只能从这一节点的实际记录判断其已做的动作，不能由节点名称选定路由方案。[TS 23.281 §5.1，两种私呼选项及组呼末段，印刷页 13](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=14)。

**组归属系统和组宿主不是同一个概念。** 前者是定义这个组的系统；后者是给这个组集中提供 MCVideo 业务支持的服务器。支持同一组用户的客户端须为这一组使用同一个 MCVideo 服务器；客户端支持涉及多个组的用户时，可以和多个 MCVideo 服务器有关系。功能实体不能按图数成物理设备，这段不要求每台客户端直接连某台宿主，也不抹掉通用互连中的参与服务器。[TS 23.281 §3.1，印刷页 12；§6.2.1、§6.2.2.3.2，印刷页 16–17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=18)。

## 看到网关，先认清两端和所传的东西

| 两端 | 参考点与作用 |
| --- | --- |
| MCVideo 服务器 ↔ 另一 MCVideo 服务器，或 MCVideo 服务器 ↔ MC 网关 | **MCVideo-3**：用于 MCVideo 应用信令。 |
| 一个 MCVideo 系统的 MC 网关 ↔ 另一个互联系统的 MC 网关 | **MCVideo-10**：建立 MCVideo 会话的应用信令须使用 **SIP-3** 传送和路由。话权控制信令（原文 *floor control*）和媒体也经 MCVideo-10 参考点传送；不能因此认定媒体由 SIP-3 承载。 |

SIP-3 在通用架构中是 **SIP 核心网到 SIP 核心网**的参考点，用于会话管理和媒体协商等信令；媒体协商是信令，不是视频本身。MCVideo-10 对建会信令须用 SIP-3 的表述是明确要求；通用规范的编辑注仍把不同信任域服务器使用 SIP-3 时**是否需要改动**留待研究。两句都保留，不拿编辑注取消这一要求，也不据此补出改动、固定 SIP 方法或线路。[TS 23.281 §6.3.3，印刷页 19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=20)；[§6.3.8，印刷页 20](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=21)；[TS 23.280 §7.5.3.4，印刷页 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=43)。

MC 网关为不同信任域的伙伴 MCVideo 系统提供互连和拓扑隐藏，它代理伙伴侧一个或多个 MCVideo 服务器，无需把主 MCVideo 系统的服务器暴露到其信任域之外；另负责转送呼叫控制、话权控制及媒体。网关可由 MCVideo 服务器承担这个角色。原文把它**能否充当 TS 33.180 所定义的信令代理**留待研究，不等于把本节列出的代理、转送职责也留待研究。即使已启用拓扑隐藏，只看到某处网关有记录，也不能倒推出本次走了哪条物理路径、下一跳是否收到或组宿主作了哪项决定。[TS 23.281 §6.2.2.3.8，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=19)。

## 哪些问题要去别处查？

- **查准入或复制两件事。** 若要判断本次准入，读[伙伴组呼准入](../groups/partner-group-call-admission.md)，再匹配双侧拓扑隐藏示例或伙伴应用本地组配置的前提。TS 23.280 §10.14.2.2 第 2–3 步和第 4 步后的注 3 写发起侧的**服务系统**，第 5、12–13 步写发起侧的**主系统**；两者不同的部署不能按图补齐每一跳。若发起端由组主系统服务、参加示例的客户端均已归属，呼叫、传输控制和媒体路径均已建立，发送者已获传输许可，且同一伙伴业务服务器为多个接收者服务并负责复制，再按[伙伴组媒体复制示例](../media/partner-group-media-replication.md)判断那一条跨服务器流。该图的单流数不覆盖反向发送、多台伙伴服务器或所有部署。[TS 23.280 §10.14.2.2，印刷页 206–207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=207)；[§10.14.3.1–3、§10.14.4.1–2，印刷页 207–210](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=210)。
- **查归属、迟入或一人离开。** MCVideo 的归属与解除归属复用 TS 23.280 §10.8。实际归属使用户具备收发该组媒体的资格，不代替某场会话的参加或发送许可；实际解除归属后不能再收发该组媒体。TS 23.281 §7.1.2.1 提到单个或多个 MCVideo 服务器，不把 §7.1.2.3 的**同一 MC 系统**流程改成跨系统流程。已知符合原场次和范围后，再查[服务器邀请迟入和终端主动重入](prearranged-late-entry-rejoin.md)，或[解除归属导致离场与本人离场](group-call-leave.md)。不要从伙伴组的归属响应、恢复覆盖或一个 BYE 猜出完整的跨域加入或释放链。[TS 23.281 §5.2，印刷页 14；§7.9，印刷页 155–156](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=157)；[§7.1.2.1、§7.1.2.3，印刷页 20、29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=30)。
- **查具体角色或收件。** 普通在网按需预安排组呼中，若查主动重入发出的新初始 INVITE、其对应应答或控制侧实际触发的迟入邀请，读[重入 INVITE](prearranged-group-sip-rejoin.md)，不把它套到既有对话内的 re-INVITE。若已确认该场普通在网预安排组呼**已按需信令建立**，再按实际 BYE、匹配应答或释放策略读[BYE 和整场释放](prearranged-group-sip-bye-policy.md)。仅早期对话中的 BYE 或对应 200 不能证明该场已建立。若查的是在网组的非控制功能实收到的 RTP、Transmission Release 或 Ack，按[该端的媒体面状态](noncontrolling-participant-rtp-release.md)查。NCF 面向一个端的会话身份不是整场控制迁移；一处发出或给出本段响应，不替另一端证明收到、用户看见或整场已释放。
