# 在网 MCVideo 整场组呼由谁释放？没有回执时怎么判断？

**聊天组呼里，没看到乙的释放回执，不能断定乙还在通话，也不能仅凭沉默认定乙已完成释放。** 要看的是哪一场呼叫、谁在参与，以及各端是否释放了这场呼叫的资源。预安排组呼和聊天组呼都是由 MCVideo 服务器发起整场释放，但两种流程对回执的要求不同。

### 谁决定结束，通知谁？

同一 MC 系统内，一场组呼正在进行，至少一个适用于这场呼叫的终止条件已经满足时，服务器发起整场释放。预安排组呼举例：最后一名或倒数第二名参与者离开、发起人离开，或在场的已归属成员不足最低人数。聊天组呼举例：聊天时限届满、最后一名参与者离开，或发起人离开。这些是各自条款的例子，不是所有组呼统一启用的条件；单看某人退出，还不能断定整场结束。[预安排 §7.1.2.3.1.1.3，印刷页 31](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=32)；[聊天 §7.1.2.3.1.2.3，印刷页 36，含注 1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=37)。

服务器先识别这场呼叫的参与者，再生成释放请求并发给每个参与端，参与用户获知组呼将释放。比如组内甲、乙正在通话，丙也已归属但没参加这场呼叫：请求的对象是甲、乙，不因丙在组内而包括丙。预安排流程经 SIP 核心网发请求；聊天流程也可用信令面的 SIP 信令发送请求。[预安排步骤 1–5，印刷页 32](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=33)；[聊天步骤 1–4 及注 2，印刷页 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=38)。

### 看到或没看到乙的响应，分别能说明什么？

- **预安排组呼：**乙的客户端收到组呼释放请求后，向服务器发送组呼释放响应，确认收到请求。流程随后写的是各参与端释放与这场呼叫关联的传输控制和媒体面资源。只有乙的响应，还不能证明所有参与端都已释放资源。[§7.1.2.3.1.1.3 步骤 6–7，印刷页 32](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=33)。
- **聊天组呼：**乙的客户端收到释放请求后，可以向服务器发释放响应，也可以不发。注 3 明确请求经单播承载发送时可以回；它没有说单播必须回，也没有规定组播时禁止回。响应虽可选，各参与端仍要释放这场呼叫的传输控制和媒体面资源。成功释放聊天组呼不改变任何客户端对该组的归属；原已归属的乙仍已归属，但不再参加这场已结束的呼叫。预安排释放条款没有给出同样的归属结论。[§7.1.2.3.1.2.3 步骤 5–6 及注 3，印刷页 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=38)。

这里比较的是 3GPP TS 23.281 V16.4.0（Release 16，Stage 2）中的整场释放。若只有[一人离开仍在进行的组呼](group-call-leave.md)，先看离开程序；若只有两端通信且业务本来就是[私呼](private-call-release.md)，不要按组呼的响应规则判读。
