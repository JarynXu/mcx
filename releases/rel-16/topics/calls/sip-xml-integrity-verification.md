# MCPTT 的 XML 签名校验：SIP 403 和 Warning 文本 139 能定位哪一步？

看到 `<Signature>`，**不能把 XML 完整性校验记成通过**。消息中哪份正文受保护、接收端有没有完成校验，是两个问题。收到 SIP `403 (Forbidden)`，Warning 文本以 `139` 开头，也不能直接认定 `SignatureValue` 校验失败：引用校验失败会产生相同的响应。这里查的是 Rel-16 MCPTT 客户端或服务器接收 SIP 中 XML 正文时的规则。[TS 24.379 V16.14.0 §§6.6.3.4.1–2，印刷页 147](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=148)

## 先核对签名指向哪份正文

§6.6.3.4.1 用 XML MIME 正文中是否有 `<Signature>` 来表述保护判定。看抓包时，还要区分**签名段与被签正文**：§6.6.3.1 的 `application/vnd.3gpp.mcptt-signed+xml` 是单独的 MIME 正文，可以带多个签名。图里每个签名通过引用与对应的被签正文 `Content-ID` 关联。只搜业务 XML 没看到签名，不能断定它没有受保护；在别的段看到签名，也不能断定它保护了这份正文。匹配到签名后，还要查这份正文的实际校验结果。[§6.6.3.4.1，印刷页 147](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=148)；[§6.6.3.1，印刷页 143](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=144)；[图 6.6.3.1-1，印刷页 144](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=145)

## 查接收端停在哪一步

| 接收端实际记录 | 能下的结论 |
| --- | --- |
| 必需的 `Signature` 子元素缺失，收发双方也未通过其他方式掌握这些信息 | 第 1 步判完整性保护过程失败并退出。本步骤没有写发送 `403/139`，也不能据此断言线路上一定没有响应。 |
| `Reference` 校验失败 | 第 3 步发送 `403`，Warning 文本为 `139 integrity protection check failed`，随后停止本校验流程。没有进入签名值校验。 |
| 引用校验通过，接收端通过收到的 `XPK-ID` 取得 `XPK`，但 `SignatureValue` 校验失败 | 第 5 步发送相同的 `403` 和 Warning 文本，随后停止本校验流程。 |
| 引用校验和签名值校验都通过，过程走到第 6 步 | 返回这份 XML 的完整性校验成功。不能据此认定已解密、业务已授权或呼叫已建立。 |

[§6.6.3.4.2 步骤 1–6，印刷页 147](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=148)

应答里的 `403` 是 SIP 状态码，`139` 是 Warning **文本**里的编号。对 MCPTT 服务器在 SIP INVITE 响应中携带这类 Warning 的情况，§4.4.1 给出的 Warning 码是 `399`。只看到 `403/139`，记录「对端报告 XML 完整性校验失败」即可。要区分引用失败与签名值失败，查同一消息、同一正文的接收端校验步骤；不要拿这个响应猜密钥或正文哪里出了问题。[§4.4.1，印刷页 33](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=34)；[表 4.4.2-2，印刷页 37](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=38)

接收端先判定并验证已施加的完整性保护，再检查 XML 元素是否需要解密；完整性校验失败时，不继续 §6.6.1.4 的后续步骤。判为「未施加完整性保护」也不等于「校验通过」，不是本节之外的放行或拒绝决定。[§6.6.1.4，印刷页 139](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=140)；[§6.6.3.4.1，印刷页 147](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=148)

若问题出在消息只解析到 SDP 或找不到第二段正文，先查 [SIP 多正文封装及 SDP 顺序](sip-mime-body-order.md)。若在对照协商归属，另查 [请求回执、用户确认和归属状态](../groups/negotiated-affiliation-client.md)，完整性校验通过不能替代这些证据。

如果签名检查之后遇到的是 XML 元素或 URI 属性的保密保护，或要核对服务器复制值时如何重新保护，读[XML 保密标志、解密失败和转发取证](sip-xml-confidentiality-copy.md)。
