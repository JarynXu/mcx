# MCPTT 组呼怎样把首选语音编码写进 SDP？为什么离网加入时不改公告？

要区分三件事：发起在网组呼时构造 SIP INVITE 的 SDP offer，离网探测超时后新建组呼，以及收到离网组呼公告后加入。前两种都可能把配置中的语音编码名填入 `a=rtpmap`，但读取的配置项不同。第三种使用正在进行的呼叫的 SDP，不重做这次选择。

## 在网和离网新建分别读哪个配置项？

| 正在构造的 SDP | 看哪个配置项 | 何时把名称写进语音段的 `a=rtpmap` |
| --- | --- | --- |
| 客户端向组身份发起在网呼叫的 offer | 组管理客户端取得的组文档中，`preferred-voice-encodings` 下 `encoding` 的 `name` 属性 | 组文档含上述元素和属性，且 MCPTT 客户端支持该编码名时，把该 `name` 值写入 encoding name 字段。〔§6.2.1 第 2b 项，印 57〕 |
| 离网客户端新建组呼的 SDP | 配在组管理客户端的组文档中的 `/<x>/<x>/Common/PreferredVoiceCodec` 叶节点 | 叶节点含 RTP 载荷格式名且 MCPTT 客户端支持首选编码名时，把叶节点的值写入 encoding name 字段。原文的支持条件仍称“name 属性”，实际取值步骤明示取叶节点；不要据此再要求在网 XML 元素。〔§10.2.1.1.2 第 2c 项，印 319–320〕 |

两个条件都没有规定：首选项未配置或客户端不支持时，必须选哪一种替代编码，或必须只有一种编码。首选不出现，不能证明 offer 不含 MCPTT 语音编码，也不能把一次 488 归因于没有配置首选。若在网呼叫返回 488，要核对收到的完整媒体描述和相应服务器的检查，见[预安排组呼的服务器准入](prearranged-server-admission-routing.md)。在网发起的业务字段和 SDP 入口见[预安排组呼客户端发起](prearranged-client-establishment.md)。〔§§6.2.1、10.2.1.1.2〕

## 离网终端查到已有公告时，为什么不套用自己的首选？

在 **S2 等待组呼公告**时，若 **TFG1 先到期**，客户端生成并保存新呼叫的 SDP，将其放进自己发送的 `GROUP CALL ANNOUNCEMENT` 的 SDP IE，按存下的 SDP 建立媒体会话。这时查发起端的离网 `PreferredVoiceCodec` 和它是否支持该编码。〔§10.2.2.4.3.1 第 2、7d、8–9 项，印 324〕

若在 S2 收到**组 ID 匹配的** `GROUP CALL ANNOUNCEMENT`，客户端保存**该消息的 SDP IE**，按保存的 SDP 建立媒体会话。不能因本地配置指向另一首选，就在这个加入分支用本地偏好替换公告 SDP。此版离网组呼的媒体流在呼叫中不可修改，整场呼叫使用同一 SDP。排查时先确认终端是新建还是加入，再比对同一呼叫的公告内容与终端实际采用的媒体配置；看到公告或 `rtpmap` 不能证明有人已收到语音。〔§10.2.2.4.3.2 第 3、8 项，印 324–325；§10.2.2.1，印 320〕

本页不判定接收方不支持公告中编码时实现怎样报错。探测、已有呼叫与后续状态见[普通离网组呼客户端程序](offnetwork-group-client.md)。
