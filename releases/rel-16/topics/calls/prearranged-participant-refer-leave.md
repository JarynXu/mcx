# 预安排组呼离会：终端发 BYE 还是 REFER，哪一腿先回 200？

同一名组员离会，先看他用什么方式参呼。按需会话中，终端发 BYE，参与功能（PF）另向控制功能（CF）发 BYE。向终端转送 200，要等发往 CF 的那份 BYE 得到 200。若用的是预建立会话，终端发 REFER；PF 先应答 REFER，再向 CF 发业务 BYE。两者都不是“一名成员离会就结束整场”。以下限普通、在网、单系统、已经建立的预安排组呼。[TS 24.379 V16.14.0，§10.1.1.2.3，印 229](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=230)；[§10.1.1.3.3，印 239](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=240)；[§6.3.2.1.6–7，印 87–88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)。

## 重入后按需离会：PF 发给 CF 的 BYE 用哪个会话标识？

假设甲通过按需信令重入，后来要求离会。终端先与媒体面交互，生成一份 BYE，把**要离开的业务会话标识**填进 Request-URI，向 MCPTT 服务器发送。甲实际收到对这份 BYE 的 200 后，终端还要与媒体面交互。重入只是这个例子的来由，不是离会的前提。[§10.1.1.2.3.1，印 229](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=230)；[§6.2.4.1，印 60](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=61)。

**PF 收到甲的 BYE 后，生成新的 BYE，不是把原报文原样转发。** PF 先与媒体面交互。新请求的 Request-URI 取**收到的 BYE 中的 MCPTT 会话标识**，P-Asserted-Identity 从入站 BYE 复制；若入站带有 `application/vnd.3gpp.mcptt-info+xml` 正文，这份正文也要复制。PF 随后向 CF 发送新 BYE。不带这份正文不等于没有会话目标。[§10.1.1.3.3.1，印 239](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=240)；[§6.3.2.1.6 第 1–6 项，印 87](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)。

例如，PF 当初给甲的会话标识是 S，从 CF 收到并与 S 对应的标识是 T。处理甲的[重入 INVITE](rejoin-late-entry.md) 时，§10.1.1.3.5.1 明写出站 Request-URI 用映射所得的标识。处理甲的**离会 BYE** 时，§6.3.2.1.6 第 3 项写的是来件中的会话标识；若本次 BYE 带的是 S，就不能仅凭旧映射表里有 T，认定本条要求把目标改为 T。这个规定回答的是业务请求该取哪个标识，不是说 S 和 T 必须相等，也不是取消 §4.5 的映射职责。MCPTT 的 PF 是这里的处理角色；普通 SIP 代理怎样按对话路由 ACK 或 BYE、Record-Route 的域名能否解析以及应选哪个公网映射，不由这条 BYE 程序决定。[§4.5，印 38–39](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=39)；[§10.1.1.3.5.1，印 239](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=240)；[§6.3.2.1.6，印 87](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)。

**两份 200 要分别配对。** 先查是否收到了对发往 CF 的这份 BYE 的 200。收到后须向甲转送 200，并与媒体面交互以释放同 CF 的这条 SIP 会话关联的媒体资源。条款没有规定转送与这次媒体交互谁先。应答甲，是对甲的 BYE 而不是对先前重入的 INVITE。条款开头将收发请求者称为“参与功能”，结尾的响应段却称其为“终接 MCPTT 功能”；这里按该段明确的入向 200、出向 200 和资源对象核对，不据称谓另添一跳。要确认甲收到了应答、或媒体资源已实际释放，还需甲的接收记录、相应资源的处理结果。[§6.3.2.1.6 末段，印 87](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)及[续，印 88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=89)。

## 预建立会话离会：为什么 REFER 的 200 早于控制侧 BYE？

PF 先回 REFER、再发业务 BYE，说的是 PF 的发送顺序，不保证各端收到报文的顺序。

终端先与媒体面交互，再在对话外发初始 REFER。Request-URI 是服务端标识**预建立会话**的 PSI（公共业务身份），Target-Dialog 也标识这项预建立会话。Refer-To 中才放**要离开的业务会话标识**，并把这一 URI 的 method 参数设为 BYE；请求方法仍是 REFER。终端要带 Refer-Sub: false 和 Supported: norefersub；实际收到这条 REFER 的 2xx 后再与媒体面交互。[§6.2.4.2，印刷页 60](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=61)

按需建立的组呼离会使用终端发出的业务 BYE，Request-URI 指业务会话。若终端实际要拆**整项预建立 SIP 会话**，它在预建立会话自己的对话内发 BYE，Request-URI 是预建立会话的 URI。不能只看是否出现 BYE 字样，就把三种操作填成同一种。[§6.2.4.1–2，印刷页 60](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=61)；[§8.4.1.1，印刷页 165](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=166)

## 两个 200 分别回答什么？

1. **PF 回终端的 REFER。** PF 从 P-Asserted-Identity 中的公共用户身份查 MCPTT ID 绑定。找不到时回 403，Warning 文本编号 141，并停止。没有被这项检查挡住，PF 须先生成并发送 REFER 的 200。正常来件带上述两项头时，PF 不建这次 REFER 的隐含订阅；200 带 Supported: norefersub，请求有 Refer-Sub: false 时也带同样的值。不必等这次 REFER 引起的订阅 NOTIFY；另行订阅的会议事件不受这句话排除。
2. **PF 发给 CF 的业务 BYE。** PF 把收到的 Refer-To 里的业务会话标识用作新 BYE 的 Request-URI，复制原 REFER 的 P-Asserted-Identity，发往 CF。PF 实际收到这条 BYE 的 200 后，须与媒体面交互释放它与 CF 之间这条 SIP 会话关联的媒体资源。排障要分别找 PF 的发包、对端对本次 BYE 的答复和 PF 的媒体处理；第一份 200 不能代替后两项。[§6.3.2.1.7，印刷页 88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=89)

## 发起人退出后，其他人为什么还能说？

CF 收到业务 BYE 后，先与媒体面交互释放离会这条 SIP 会话关联的资源，并发该 BYE 的 200，然后才检查整场释放策略。发起人走了会不会结束整场，要看**本地策略是否要求这样处理预安排组呼**。以下是其他独立触发条件：CF 从媒体面收到本场 T4 不活动计时器到期指示；只剩一名或没有参与者；在场的已归属组成员不足所需下限；本场 TNG3 到期。只看到发起人离开，不能替这几项作判断。[§6.3.3.2.4 第 1–5 项，印刷页 121](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=122)；[§6.3.8.1，印刷页 136](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=137)

需要结束整场时，CF 按释放程序向本场所有参与方发送 BYE；不需结束时，CF 向仍在本场且订阅了会议事件的客户端发 NOTIFY。要认定整场结束，要查 CF 的决定和各条业务腿的处置，不拿一名离会者收到的 200 或一条会议通知代替。要查某台终端是否收到请求、完成释放，再看它这一腿及媒体处理的记录。[§6.3.3.1.5，印刷页 106–107](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=107)；[§6.3.3.2.4，印刷页 121](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=122)；[§10.1.1.4.3、§10.1.1.4.4.2，印刷页 251](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=252)

## 控制功能发起释放：参与功能要等终端的 BYE 200 吗？

先确认**控制功能（CF）要移出谁**，再看**终接参与功能（PF）为这个参与者使用哪种会话**。CF 移出单个客户端（例如该用户解除组归属，或要接纳更高优先级的用户）时，按移除这一参与者的程序发送 BYE。成功移出后，CF 可以通知订阅了会议事件的客户端；没有这条 NOTIFY，不等于没移出。若 CF 判定须结束整场，则向本场所有参与者发 BYE，不以会议事件订阅为发送条件。无论哪种范围，CF 在发 BYE 前须与媒体面交互；实际收到**这条 BYE** 的 200 后，再按这条 SIP 会话释放关联的媒体资源。单腿 200 不是整组结束的记录。[§10.1.1.4.4.2–.3，印刷页 251–252](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=252)；[§6.3.3.1.5，印刷页 106–107](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=107)。

| PF 收到 CF 的业务 BYE 时，这一成员用什么会话？ | 下行处理与 200 的来源 |
| --- | --- |
| **按需会话** | PF 先与媒体面交互，释放 CF 这段 SIP 会话关联的资源；另发 BYE 给终端，复制入向的 P-Asserted-Identity，有 mcptt-info 正文时也复制。终端实收下行 BYE 后先与媒体面交互，再回自己的 200。PF 实收**对下行 BYE 的 200**后，回 CF 原 BYE 的 200，再与媒体面交互释放本端与终端这段 SIP 会话关联的资源。 |
| **预建立会话，且这次业务的 MCPTT 会话标识指向与该 PF 有预建立会话的用户** | PF 先与媒体面交互，断开面向 CF 的媒体资源；PF 自己回 CF 的 200，再与媒体面交互，断开终端侧与 CF 侧媒体资源的连接，保留面向终端的预建立会话。此分支不列向终端发下行 SIP BYE，也不把终端的 SIP 200 或媒体面确认列为回复 CF 的前提。 |

按需的组呼入口在 §10.1.1.3.4.1。该小节标题写着 “private call on-demand”，但它位于预安排组呼的终接 PF 释放条款下，正文直接引用 §6.3.2.2.8.1。表格按这个调用点读，不把私呼的释放策略移入。预建立按 §10.1.1.3.4.2 和 §6.3.2.2.8.2，不能只凭“这个用户有旧对话”选择本行；还要对上本次 BYE 的业务会话与该 PF 的用户关联。[§10.1.1.3.4.1–.2，印刷页 239](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=240)；[§6.3.2.2.8.1–.2，印刷页 102](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=103)；[§10.1.1.2.3.3，印刷页 229](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=230)；[§6.2.6，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=62)。

排障时给每条 200 配对请求和收发端。预建立分支里，CF 已收到 200 而下行旧对话仍在，符合这两条记录各自的作用：一条应答业务 BYE，一条供后续业务复用。它们不证明终端已收到媒体面释放指示、媒体已停或 PF 在回复之后的媒体处理已执行。要判断那些结果，另查本次通话的实际媒体事件；这一节不规定失败或超时如何收尾。

实际收的是预建立对话内的 BYE，读[拆正在使用的预建立会话](preestablished-session-in-use-release.md)。实际是聊天组，读[聊天组一人离开与整场结束](chat-participant-or-session-release.md)。若手头只有会议事件的 NOTIFY，读[会议参与者通知](conference-participant-status.md)。
