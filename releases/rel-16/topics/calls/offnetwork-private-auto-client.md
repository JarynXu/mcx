# 离网普通私呼自动应答：被叫发了 ACCEPT，双方就都在通话了吗？

被叫发出 `PRIVATE CALL ACCEPT` 后，即使已经按 SDP 建好本地媒体会话，基本呼叫控制仍处于 **P5（待定）**。要判断主叫与被叫是否各自到了 **P4（已参加通话）**，须分别看两端收到了什么。自动应答省去等被叫用户按键的环节，不省去这个确认过程。

以下只讲 Rel-16 普通离网 MCPTT 一对一私呼的自动启动模式。P 状态属于各端的基本呼叫控制；进入 P4 不证明用户已开口、听到声音或已经获得一次新的话权授予。[固定原文：3GPP TS 24.379 V16.14.0](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf)，下列页码均为印刷页。

## 主叫等不到回答，什么时候放弃？

主叫在 P0（起止）或 P1（忽略相同呼叫标识）收到用户发起指示，且 `PrivateCall/Authorised=true`。用户请求自动模式且 `AutoCommence=true` 才保存自动模式；否则，`ManualCommence=true` 时选手动。主叫为本次呼叫保存标识、双方身份和 SDP offer；发出带这些信息、呼叫类型和模式的 `PRIVATE CALL SETUP REQUEST` 后，将请求计数 CFP1 置 1，启动重传计时器 TFP1。原在 P1 时还须停止 TFP7，再进入 P2（等呼叫响应）。

- **TFP1 到期、CFP1 低于上限：**CFP1 加 1，用保存的呼叫标识、身份、模式、类型和 offer 重发请求，重新启动 TFP1，仍在 P2。计数从首次发送算起，不是从首次重发算起。
- **TFP1 到期、CFP1 等于上限：**已保存自动模式的主叫启动 TFP7，释放呼叫类型控制状态机，进入 P1，忽略相同呼叫标识。这里不再转去等 TFP9，也不能推断被叫已经收到或拒接。手动模式在同一达限事件上才启动 TFP9 并留在 P2。

依据：§11.2.2.4.2.1–2、.2.4–5，页 423–425。

## 被叫能回 ACCEPT，还是必须拒绝？

被叫在 P0 或 P1，收到带新呼叫标识（不同于本机保存值）的自动模式请求。若 offer 声明的媒体可建立，被叫保存本次标识和双方身份，建立呼叫类型控制状态机，再检查 offer：

- **不含 `a=key-mgmt` 属性**，须按无该属性的分支处理；**含值为 `mikey`、携带 MIKEY-SAKKE I_MESSAGE 的该属性**，则须先验证签名。验证成功后，提取并解密 PCK、取出 PCK-ID，再走接受分支。条文没有把其他属性值视同“没有此属性”。
- 两条成功路径都须生成并保存 SDP answer，向主叫回 `PRIVATE CALL ACCEPT`（本次标识、双方身份、answer），按 answer 建本地媒体会话，置 CFP4=1、启动 TFP4。原在 P1 时停止 TFP7，进入 P5。这里不以发 RINGING、等待用户操作为前置步骤。

两种失败不能合并。若媒体原本就不能建立，被叫记录标识和双方身份，回 `PRIVATE CALL REJECT`，原因通常为 `MEDIA FAILURE`，启动 TFP7；原在 P0 的转 P1，原在 P1 的仍在 P1。若媒体可建立、但上述签名验证失败，被叫回 REJECT，原因通常为 `E2E SECURITY CONTEXT FAILURE`，释放刚建立的呼叫类型控制状态机，保持原来的 P0 或 P1；此分支没有规定启动 TFP7。两种拒绝都只有在**请求限制失败通知且 `FailRestrict=true`** 时才把对应的具体原因改为 `FAILED`。仅凭收到 `FAILED`，不能在这两个分支间判因。

依据：§11.2.2.4.3.1，页 426；§11.2.2.4.3.2，页 427–428。

## 哪一端已经进入 P4？

| 在哪一端看到什么 | 该端须做什么 | 这条记录证明不了什么 |
|---|---|---|
| 主叫在 P2 收到响应本次请求、呼叫标识相同的 ACCEPT | 保存 answer，发 `PRIVATE CALL ACCEPT ACK`；停止仍在运行的 TFP1、TFP9，按 answer 建媒体，启动主叫侧话权控制和最大时长计时器 TFP5，进入 P4。 | 主叫发出 ACK，不证明被叫已收到。仅见其他呼叫标识的 ACCEPT，不能套用这个转换。 |
| 被叫已发 ACCEPT、建媒体且在 P5；随后收到 ACCEPT ACK，**或收到来自主叫的 RTP 媒体** | 停止 TFP4，启动终接侧话权控制和 TFP5，进入 P4。两个触发条件满足一个即可。 | 被叫发送 ACCEPT 不等于主叫已收到；只见本地媒体会话创建也不足以判定 P4。收到 ACK 本身不是收到或播放音频的证据。 |

因此同一时刻，主叫已进 P4、被叫仍在 P5，并不矛盾。这里的 ACK 只确认收到 ACCEPT；下层是否播放出来，要看另外的观测。依据：§11.2.2.4.2.8，页 425–426；§11.2.2.4.3.2、.3.4，页 427–429；§15.1.11.1，页 482。

## 被叫等不到 ACK，也没有主叫媒体

被叫等的是确认，计的是 **CFP4/TFP4**，不是主叫请求所用的 CFP1/TFP1。在 P5，TFP4 到期的重传条款要求用保存的标识、身份和 answer 再发 ACCEPT，CFP4 加 1，重新启动 TFP4，仍在 P5。另有专门的达限失败条款：TFP4 到期且 CFP4 **等于**上限，启动 TFP7、释放呼叫类型控制状态机、进 P1。重传条款自身没有写“低于上限”这个守卫；不能据此指定两条同时匹配时的实现调度顺序。失败条款也未列发送 RELEASE、终止本地媒体会话或已获对端确认。

依据：§11.2.2.4.3.3–5，页 428–429；表 B.3.2-1 的 TFP4 行，页 537；表 C.2.2-1 的 CFP4 行，页 542。
