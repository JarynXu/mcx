# MCPTT 组动态通知：参与功能回了 200，甲从 MBMS 收到了什么？

只看到 200，还不知道甲收到了什么。**回 200 的是终接参与功能，不是甲的客户端。** 要确认甲收到 G 组“组呼进行中”，得在甲端看到一条 Group Dynamic Data Notify，里面的组 SIP URI 是 G，且 `Group call ongoing` 的值是 1。参与功能回给上游的 200、它在 MBMS 承载上发出通知、甲端实际收到通知，是三处不同的证据。[3GPP TS 24.380 V16.9.0，Release 16，Stage 3，§10A.1，印刷页 211–212](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)；[§8.5.3.4，印刷页 190](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=191)；[§8.5.4，MCPTT Group ID，印刷页 192](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=193)。

## 同一个组，甲与乙可以走不同的承载

甲和乙都订阅了 G 组动态数据。参与功能须在使用 MBMS 承载前激活并通告该承载。至于向谁经 MBMS 发通知、向谁继续用单播，参与功能根据监听状态报告按用户决定。假设甲在监听 MBMS 子信道，参与功能选乙继续走单播。甲的监听报告只能作为选路依据，不是甲对某条通知的收件证明；要查乙有没有收到，要看乙的单播链路。这里不以“这个组呼已用单播建立”为前提。[§10A.1，第 1、2 段，印刷页 211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)。

甲这一支从**终接参与功能收到请求**算起：发来 SIP NOTIFY 的是控制 MCPTT 功能，通知关联一项组动态数据订阅，目的用户甲正在监听 MBMS 子信道。三项条件不能少。终接参与功能须按以下次序处理：

1. 对收到的 **SIP NOTIFY** 回 200 (OK)。不是对 SUBSCRIBE 的答复。步骤 1 的动词是 *respond to*，末尾却把 SIP 200 (OK) 写作 *request*；按这一步的动作判为对来向请求的应答，不另设一次 SIP 请求。
2. 把该 NOTIFY 中的信息映射到 §8.5.3 的信息元素。规范在此给出映射目标，没有列一张逐字段的 SIP 转换表。
3. 在 MBMS 承载上发送 **Group Dynamic Data Notify**。下游消息不是原样转发的 SIP NOTIFY。按甲的监听状态选择 MBMS，也不说明下游消息只向甲寻址。只看到第 1 步，不能把后两步记为已执行；看到第 3 步，也不能替甲签收。[§10A.1，步骤 1–3，印刷页 211–212](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)。

## 在甲端读这条通知

先认消息，再对组。MBMS 通知协议名是 `MCNC`；Group Dynamic Data Notify 的子类型是 `00000`，由参与功能发往 MCPTT 客户端。用其中 **MCPTT Group ID 的 SIP URI** 找到 G 组。SSRC 是参与功能的标识；即使 H 组的消息来自同一参与功能，也不能拿它当 G 组的报告。[§8.5.1–2，表 8.5.2-1，印刷页 188](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=189)；[§8.5.4，表 8.5.4-1 及字段说明，印刷页 192](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=193)。

| 甲在 G 组通知里读到的字段 | 如何解读 |
| --- | --- |
| `Status`，字段 ID 0 | 值 **0 = emergency（紧急）**，**1 = in-peril（遇险）**，其他值保留。它报告组的紧急状态，不回答有没有组呼。 |
| `Status changing MCPTT User Identity`，字段 ID 1 | 指上次改变该组状态的用户，值是此人的 MCPTT ID（URI）。它不标识这条通知的收件人，也不说明谁在讲话或是谁发起组呼。 |
| `Group call ongoing`，字段 ID 2 | 值 **0 = 该组没有进行中的组呼**，**1 = 有进行中的组呼**，其他值保留。它不表示甲个人已加入，也不说明通话媒体是否经 MBMS 传输。 |

例如，甲端日志只列出 G 的 `Status=0`：能填的是“G 组报告紧急”，不能填“G 没有组呼”。反过来，只列出 G 的 `Group call ongoing=0`，能填的是“G 报告没有进行中的组呼”，不能填“紧急状态解除”。没取得可读值的字段，和读到明确的 0，是两回事；没有更改者身份就不能指认某个人。[§8.5.3.1，表 8.5.3.1-1，印刷页 188–189](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=189)；[§8.5.3.2–3，印刷页 189–190](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=190)；[§8.5.3.4，印刷页 190](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=191)。

§8.5.4 在引言写参与功能在会话开始时发送此消息。§8.5.3.4 同时明确定义了“没有进行中的组呼”的值 0。前一句不能把收到的 0 改判成 1；后一句也不能反推每次组呼结束，参与功能都必须发送包含 0 的通知。[§8.5.4 引言，印刷页 191](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=192)；[§8.5.3.4 值定义，印刷页 190](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=191)。

**甲端实际收到的是一份关于 G 的报告。** §10A.1 的三个步骤止于参与功能发送；§8.5.2–§8.5.4 给出下游消息的方向和字段。这些条款没有给出这条消息逐客户端确认收件的步骤，也没有规定收到后如何维护缓存。若日志截断、字段没显示、值保留或根本没有甲的接收记录，不能据此断言甲端写入了默认值、沿用了旧值或清除了旧状态。若要断定甲的应用已经改了本地记录，还要看甲端的应用记录。[§10A.1，印刷页 211–212](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)；[§8.5.2–§8.5.4，印刷页 188–192](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=189)。

若要查**已归属客户端如何据组状态决定是否晚入或重入单播建立的组呼**，见[单播 MCPTT 组呼的 MBMS 状态通知（Stage 2）](mcptt-mbms-group-status.md)。要查控制功能为什么发 SIP NOTIFY，见[组动态数据的 SIP 订阅与通知](../groups/group-dynamic-data.md)。若问题在承载一侧，可分别查[客户端获知该监听哪条承载](../bearers/mbms-bearer-announcement.md)和[监听报告与特定控制消息回执的区别](../bearers/mbms-application-control-signalling.md)。[结构化条件与声明](mbms-group-dynamic-notify.json)。
