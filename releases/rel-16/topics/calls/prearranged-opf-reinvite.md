# 普通预安排组呼已建立：O-PF 收到 re-INVITE，用哪份 SDP、回哪笔应答？

发起侧参与功能（O-PF）收到它所服务终端发来的**会话内 re-INVITE**，才用这节查更新。组里已有一通呼叫，不等于新发来的初始 INVITE 就是更新。终端已有预建立 SIP 对话，也不等于它正更新这通组呼。判断这笔通信时，先对上终端、O-PF 的实际收件和所指的现有组会话；查规范可以按条件读，不必先有抓包。

这里选同一 MC 系统、直接组身份、普通在网预安排组呼，按 [TS 24.379 V16.14.0 §10.1.1.3.1.3，印刷页 236–237（PDF 237–238）](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=237) 的 Stage 3 规则。原文开头说兼顾按需与预建立；接收入句仍写明请求所识别的是按需预安排组会话。保留这两句：**看这一笔从所服务终端哪条对话到达，并核对它与所指组会话的关联**，不是见到一条预建立对话就套用。终端收到网络侧更新、T-PF 收到初始邀请、重入、聊天组、私呼和优先级变更各另判。

## O-PF 的本地检查和出向请求

缺资源而无法处理，或有拥塞风险时，O-PF **可以**回本地 500；可带 `Retry-After`。若这样拒绝，不继续余项。到了媒体检查，来向 SDP 的媒体参数须可接受，并实际提供 MCPTT 语音编解码；任一不满足，回 488。没看全来件，不能断定它确实未提供编解码。预建立来件中语音与话权控制描述应与旧协商相同是注 2 的预期；这不是新拒绝规则，不能据此把任意差异写成 488，也不是终接侧初始邀请的空闲会话筛选。[§10.1.1.3.1.3 第 1–2 项及两处注，印刷页 236–237](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=238)

| 本次 re-INVITE 从哪里收到 | 发往控制侧的 SDP offer 以什么为依据 |
| --- | --- |
| 按需对话 | 本次来向 offer。按 §6.3.2.1.1.1 构造相应语音与来向有的媒体控制描述，不能把旧协商内容当成这次来件。 |
| 与该组会话对应、适用本条的预建立对话 | 此预建立会话已协商的 SDP。按 §6.3.2.1.1.2 处理语音和适用的控制参数；不是照抄当前来向 offer。 |

O-PF 按 §6.3.2.1.9 生成出向 re-INVITE。来向有含受邀 MCPTT 用户 ID 的资源列表、有 MCPTT 信息 MIME，或有 MCPTT 位置 MIME，分别按该通则复制相应的来向正文。组程序还要求将该条所称发起用户的 MCPTT ID 写入 `mcptt-calling-user-id`。来向含 `Resource-Priority` 才带它的原值，由控制功能（CF）判断有效性；复制不等于准许优先级。这里不把私呼的重新查绑定、初始 INVITE 的位置构造条件或另一腿的内容挪过来。[§10.1.1.3.1.3 第 3–8 项，印刷页 237](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=238)；[offer 辅助条款，印刷页 83–84](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=84)；[§6.3.2.1.9，印刷页 92](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=93)

## 对上 O-PF 实际收到的应答，再查回终端的那一腿

只有 O-PF 实际收到、且匹配自己这笔出向 re-INVITE 的应答，才进入下面两个分支。另一腿、早先的应答或 CF 一侧已发的记录，都不能代替。

- **收到对应出向 re-INVITE 的 2xx：** O-PF 另造给终端的 200。§10.1.1.3.1.3 在此只回指 §6.3.2.1.2.1（按需 SDP answer 辅助条款）。它没有为预建立另列一种 answer 规则。别从聊天组的明确分支补成“预建立 answer 也用此前协商的 SDP”，也别把上节两种 offer 依据当成 answer 依据。起句写 2xx，接下来的 `Warning`、`P-Asserted-Identity`（PAI）取自**实际收到的 200**；§6.3.2.1.5.2 的 MCPTT 信息正文复制也要求该 200 确实带这正文。不能从别的 2xx 补造这些 200 字段。O-PF **先向终端发 200，再与媒体面交互**。
- **收到对应出向更新的 403：** O-PF 另造给终端的 403。来件含 MCPTT 信息 MIME 才复制该体，带来件的 `Warning`。**先向终端发 403，再与媒体面交互**。只有一个 403 状态码，不能补出正文里的指示，也不能把这个处理泛化给其他失败码。

印刷页 237 的成功和 403 段都回指第 7 项，但第 7 项写的是 `Resource-Priority`，第 8 项写发送。第 4 项和 403 段字面又称 `SIP INVITE`。核对该段实际发出的更新和收到的对应答复；不要把这些标签补成另一次初始 INVITE。CF 一侧已发、O-PF 实收、O-PF 自己向终端发、终端实收与媒体动作完成是不同记录。一个成功响应不保证后几项。[两段响应步骤，印刷页 237](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=238)；[§6.3.2.1.2.1，印刷页 84](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=85)；[§6.3.2.1.5.2，印刷页 87](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)

若同一 MC 系统内，普通在网按需预安排组呼按直接组身份发初始 INVITE 新建或加入活动组呼，且组由 GMS 管理、非临时、未重组，也不是组成组或预配置重组，查[普通预安排组呼的准入和新建、加入](prearranged-server-admission-routing.md)。初始 INVITE 的 Request-URI 若指待重入的业务会话身份，不走这个按组入口。

确认是聊天组的实际对话内更新，查[聊天组更新的 offer、answer 和 403](chat-preestablished-refer-outcome.md)；普通在网直接 ID、单被叫且带话权控制的已建按需私呼，查[私呼 O-PF/T-PF 的绑定和响应顺序](private-server-admission-routing.md)。在同系统的普通在网按需直接预安排组，无隐式话权请求、临时或重组、广播、优先级情形及 NCF 时，终端将待重入的业务会话身份放入初始 INVITE 的 Request-URI，查[主动重入](rejoin-late-entry.md)。同一范围内，若 CF 实收新归属或返回覆盖的通知、且该组呼仍在进行，看同页的 CF 晚入邀请。不能只见 CF 发邀请就认定这项触发。

在同系统的普通在网预安排组，未请求隐式话权，终端用对话外 REFER 指向已有预建立会话、另标出待重入的业务会话身份时，查[普通预建立重入](preestablished-group-rejoin.md)；这不是更新正在用的旧对话。若原请求是通过已有预建立会话发起紧急或迫近危险组呼、等待控制侧的业务应答或实际 INFO，查[优先级确认](prearranged-preestablished-priority-confirmation.md)。
