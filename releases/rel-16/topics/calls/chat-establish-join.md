# 按需 MCPTT 聊天组：怎样新建或加入会话？控制功能为什么有时先发 UPDATE，再接受 INVITE？

Release 16、Stage 3，在网按需 MCPTT 聊天组语音呼叫。客户端以未重组的 MCPTT 组 ID 请求发起或加入，不使用临时组身份（TGI）或预建立会话。

普通组呼中，甲、乙各发自己的初始 INVITE，不代表建立了两场会话。控制功能按该组的聊天会话身份是否存在决定新建还是加入。请求或组状态涉及紧急、迫近危险时，还要查控制功能怎样核对 Resource-Priority。查 200 时先分清抓包位置：客户端将 INVITE 发给发起侧参与功能（O-PF）；O-PF 另生成 INVITE 发往控制功能（CF）。CF 所在一侧的 200 还要区分它回答的是 PRACK、UPDATE，还是 O-PF 发来的 INVITE。

## 普通组呼：按组身份建立或加入

本段限普通组呼：本次请求不是紧急或迫近危险请求，组也不处于这两种状态。

### 初始 INVITE 发给谁，要加入哪个组又写在哪里？

两种操作都由客户端发出初始 SIP INVITE：Request-URI 填服务该用户的参与 MCPTT 功能的公共服务身份；消息体的 session-type 填 chat，mcptt-request-uri 填目标组身份，mcptt-client-id 填发起客户端 ID。主叫用户的 MCPTT ID 不由客户端填入该消息体，由发起侧参与功能补入。这条加入程序不要求客户端先取得既有会话 ID。

信令还须携带 SDP offer；需要隐式请求话权时按 §6.4 指示。发出 INVITE 或收到成功响应本身均不能证明获得话权。

依据：§10.1.2.2.1.1（客户端初始请求步骤 9、13a–c、注 2、14–16，印刷页 265、266）。

### O-PF 回 404/141 或 403/108：主叫身份没查到，还是没有发起权限？

这两种拒绝都在发起侧参与功能（O-PF）处理客户端的初始 chat INVITE 时判断，不是控制功能（CF）查组文档的结果。以下限同一 MC 系统内的普通在网按需聊天组，使用未重组的 MCPTT 组身份，不是临时组；请求和组状态均非紧急、非迫近危险。[§10.1.2.3.1.1，入口与第 2、2a、3 项，印刷页 276](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=277)。

- **404/141：查身份绑定。** O-PF 用来向 INVITE 的 `P-Asserted-Identity` 中的公共用户身份查主叫的 MCPTT 业务用户身份（MCPTT ID）。查这条绑定用的是用户身份，不是组 ID，也不是客户端 ID。找不到这两个身份的绑定，或现有绑定有效期已过，第 2a 项要求回 **404**，Warning 引号内是 `141 user unknown to the participating function`，且不得继续其余步骤。单看 141 分不出缺绑定还是绑定过期，也不能据此认定用户、系统或目标组不存在。本段没有规定已确认缺少 PAI 时要回什么；如果只有 404 状态，既没有对应 Warning，也没有能定位这条腿的处理记录，就不能断定是 141。
- **403/108：查发起权限。** O-PF 已确定主叫的 MCPTT ID，但本地策略判定该用户无权发起聊天组呼时，第 3 项要求回 **403**，Warning 引号内是 `108 user not authorised to make chat group calls`。它没有第 2a 项那句明确禁止继续其余步骤的文字；这并不等于第 3 项另给了拒绝后继续处理的许可。本项说明的是 O-PF 的本地授权，不是 CF 判定该用户未归属、也不是本场是否存在。[§10.1.2.3.1.1，第 2、2a、3 项，印刷页 276](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=277)。

404 和 403 是 **SIP 状态**，141 和 108 是 **Warning 引号内的文本码**，不是 SIP 状态，也不是 Warning 外层的 399。比如只见一个 403，不能判为本地无权发起：下文的 **CF 403/120** 在另一条腿上。CF 通过组文档初检后，发现该用户未归属且不具隐式归属资格，才按第 5 项拒绝。[§4.4.1–2，Warning 外层码及文本格式，印刷页 33–34](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=34)；[表 4.4.2-2，108、141 项，印刷页 36–37](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=37)；[§10.1.2.4.1.1，第 5 项，印刷页 287](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=288)。

这两个本地检查列在 O-PF 另生成并发送 CF 侧 INVITE 的步骤之前。抓包时先把响应配到该侧的 INVITE，再看完整 Warning 和实际处理记录。O-PF 收到它发出的 INVITE 的 4xx、5xx 或 6xx 时，也须生成客户端侧响应，并带上收到的 Warning。所以，**只凭终端看到响应来自 O-PF，不能判定拒绝由 O-PF 作出**。找不到发往 CF 的包，也不等于没发过。[§10.1.2.3.1.1，出向第 9、10、16 项，印刷页 277–278](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=278)；[§10.1.2.3.1.1，收到失败响应后的第 1–3 项，印刷页 279](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=280)。

### CF 查组文档：取不到、组停用、不在名单和未归属怎样区分？

以下限同一 MC 系统内的普通在网按需聊天组，使用未重组的 MCPTT 组身份，不是临时组；请求和组状态均非紧急、非迫近危险。**先确认控制功能（CF）实际收到这次发起侧参与功能（O-PF）发来的 INVITE，而且走到第 4 项。** CF 在这条来向请求的正文中，从 `mcptt-request-uri` 读组身份，从 `mcptt-calling-user-id` 读主叫的 MCPTT ID。[§10.1.2.4.1.1，入口和第 4 项，印刷页 286–287](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=287)。

**先看这次取没取到该组的文档。** CF 尚未订阅这组的文档时，须订阅该文档的 `xcap-diff`。如果**这项订阅**收到 404，CF 对原来向 INVITE 回 **404/113**（`group document does not exist`）；若 CF 收到与这项订阅匹配的其他实际 4xx、5xx 或 6xx，CF 对原 INVITE 发带 **Warning 文本码 114**（`unable to retrieve group document`）的最终响应，并停止其余步骤。114 这一项没有为 INVITE 的最终响应指定一个统一的 SIP 状态码。把组身份、订阅请求和应答对在本次事务上。查不到缓存、只看到已发订阅，或没抓到响应，都不能判成 113 或 114。两种结果说明这次取文档的情况；114 的说明文字不能证明文档实际存在，也不能据此判它之后的状态。[§6.3.5.2，第 1–3 项，印刷页 131](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=132)；[表 4.4.2-2，113–114 项，印刷页 36](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=37)。

**有文档才查禁用和成员名单。** 收到 GMS 携目标组文档的通知，或已有该组文档缓存，CF 才能按文档分类，走未重组、非临时组的检查。已有缓存与已订阅是两个条件，不能互换。CF 先查禁用，再查成员名单；命中禁用就停止，不走名单拒绝。[§6.3.5.2，第 1、4–5 项，印刷页 131–132](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=132)。

| 在这次处理使用的组文档中 | CF 对本次 INVITE 的处理 |
| --- | --- |
| 存在 `on-network-disabled` 元素 | **403/115**（`group is disabled`），不继续其余步骤。正文看的是 `on-network-disabled` **存在**。Warning 表的解释写的是 `disabled` 为 `true`；不能用它替代这项检查。 |
| `list-service` 下的 `list` 没有匹配主叫 MCPTT ID 的条目 | **403/116**（`user is not part of the MCPTT group`），不继续其余步骤。这里查的是组成员名单，不是归属状态。 |

[§6.3.5.2，第 5(a)、(b) 项，印刷页 131–132](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=132)；[表 4.4.2-2，115、116 项，印刷页 36](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=37)。

**在名单不等于已归属。** 组文档初检通过后，CF 查目标组记录，在其中核主叫的用户记录及这次发起客户端的 `mcptt-client-id`，再检查用户记录是否到期。三项找齐且用户记录未到期才判该用户在本次发起端已归属；不能用另一台客户端的记录代替。比如甲在成员名单上，但这次发起客户端不在用户记录里：CF 判本端未归属，再核隐式归属资格。**只有本次发起客户端未归属且主叫不具隐式归属资格，才在第 5(b) 项回 403/120，并停止其余步骤。** 有资格不触发这个拒绝，也不等于已经归属或已获准入会。后续建会、加入和实际归属见下一节。[§10.1.2.4.1.1，第 4–5 项，印刷页 287](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=288)；[§6.3.6，第 1–5 项及注，印刷页 135–136](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=136)；[§9.2.2.3.6，第 1–2 项，印刷页 191](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=192)。

113、114、115、116、120 都在 Warning 引号内，不是 SIP 状态，也不是外层 399。查到其中一个码时，先把失败与 **CF 这一腿对应的 INVITE** 配对；若还要核对终端一侧，应查 O-PF 收到匹配失败后带过去的 Warning。终端看到 O-PF 是发送方，不等于这一项检查发生在 O-PF；只见状态或缺另一腿的记录，不代填原因。[§4.4.1–2，Warning 格式，印刷页 33–34](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=34)；[§10.1.2.3.1.1，收到出向 INVITE 失败后的第 1–3 项，印刷页 279](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=280)。

### 普通聊天组的 488：按哪一侧的 SDP offer 查媒体参数和编解码？

以下限同一 MC 系统内的普通在网按需 MCPTT 聊天组，使用未重组的组身份，不是临时组；请求和组状态均非紧急、非迫近危险。**先看哪个功能检查哪份 SDP。** 客户端发给发起侧参与功能（O-PF）的 INVITE 带 offer A；若请求处理到对外发送步骤，O-PF 会另生成一份发往控制功能（CF）的 INVITE，带基于 A 生成的 offer B。控制功能核对的是自己收到的 B。[§10.1.2.3.1.1，出向第 9、10、12、16 项，印刷页 277–278](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=278)。

| 观察点 | 各自的媒体检查 |
| --- | --- |
| **O-PF 收到 A** | 到第 4 项时，检查媒体参数是否可接受、是否提供 MCPTT 语音编解码。两项都满足才继续本条后续步骤；任一项不满足，就对收到的 INVITE 回 488。 |
| **CF 收到 B** | 到第 9 项才做本侧检查：媒体参数须可接受，也须提供 MCPTT 语音编解码。任一项不满足，就对它收到的 INVITE 回 488，并跳过其余步骤。 |

O-PF 条文写的是“否则继续”，CF 条文明确写了拒绝后跳过其余步骤。O-PF 通过本侧媒体检查，不等于后续步骤都通过，也不替 CF 接受 B。两个拒绝段都没有给这一分支指定 Warning 头或专用文本，也没有说不能有 Warning。[§10.1.2.3.1.1，第 4 项，印刷页 276](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=277)；[§10.1.2.4.1.1，第 9 项，印刷页 288](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=289)。

**B 以 A 为基础，不等于整份 SDP 照搬。** 需要换媒体流的 IP 地址和端口时，O-PF 用自己的地址和端口；若有媒体面控制通道，按条文换写该通道的地址和端口。注 2 给出省略条件：相关功能在**同一台 MCPTT 服务器**，且 O-PF 没有该流或通道的专用 IP 地址或专用端口，省去相应替换。同一 MC 系统不等于在同一台服务器上。不要从两份 SDP 值相同推断它们是同一次事务，也不要从值不同就认定地址改写导致了拒绝。[§6.3.2.1.1.1，按需 offer 的组成项 1–2 及注 2，印刷页 83](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=84)。

**定位拒绝看对应响应；定位原因还得看检查记录。** 若 O-PF 实际收到对它发出的 INVITE 的匹配 4xx、5xx 或 6xx，须生成客户端侧响应，带上实际收到的 Warning 字段，再送给客户端。这条规则不能证明两侧 SIP 状态数字必然一样。抓到 CF 腿对应 INVITE 的 488，能确认这条腿出现了拒绝；要确认是不是第 9 项、是参数不可接受还是没提供语音编解码，还要核对 CF 这次收到的 offer 和实际处理记录。仅看到终端这侧的 488 或 Warning 外层码 399，不能定位到 O-PF 或 CF 的媒体检查，也不能猜出具体 codec。没抓到第二腿的请求或应答，不证明 CF 没收到或 O-PF 没发。[§10.1.2.3.1.1，收到出向 INVITE 的失败响应后第 1–3 项，印刷页 279](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=280)；[§4.4.1，印刷页 33](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=34)。

### 谁判断要不要建会？

控制功能先取组文档并进行初检。对这里的未重组组 ID，若发起用户尚未归属该组，步骤 5 要求检查其隐式归属资格；不具资格就拒绝（SIP 403，Warning 引号内的 MCPTT 文本码为 120）并停止。媒体参数不可接受或未提供 MCPTT 语音编解码也须拒绝（488）。通过前序处理，到达步骤 10 时，若该组的 chat 会话身份尚不存在，控制功能须建会并为它分配一个 MCPTT 会话身份。会话已在进行时，获准的用户加入原会话，不因自己的初始 INVITE 再分配一个组会话身份。

TNG3 是可选的组呼计时器处理，不是判断是否建会的标志。资格检查不改变归属状态。走到步骤 12 时，只有步骤 5 判为有资格、且本条此前尚未调用 §9.2.2.3.7，控制功能才须执行该规程；处理对象是主叫用户对请求所指组的归属。若此前已调用，步骤 12 不要求再调用。这个条件不说明具体在哪一步先行调用，更不代表每次加入都会改变归属。

要查 CF 在普通聊天组何时按组文档启动 TNG3、何时停止，以及怎样确认是本场到期导致的释放，见[聊天组的 TNG3 与释放](chat-participant-or-session-release.md)。

已重组组或 TGI 在组文档初检时另有分支，本页不为这些分支排列建会、归属或授权的顺序，也不规定并发建会的实现。

这里有三层数字：403 或 486 是 SIP 响应状态码；Warning 头的外层警告码（warn-code）是 399；引号内警告文本开头的三位数才是 MCPTT 文本码（mcptt-warn-code）。120 和 122 都不填在外层警告码的位置。

依据：§10.1.2.4.1.1（入口定义 1–2、控制功能步骤 4–5，印刷页 286、287）；§10.1.2.4.1.1（步骤 9–10、12，印刷页 288）；§6.3.5.2（步骤 4b、5，印刷页 131–132）；§9.2.2.3.7（起首和步骤 1–2，印刷页 192）；§4.4.1、§4.4.2 表 4.4.2-1、表 4.4.2-2 的 120、122 项（印刷页 33、34、36）。

### 正在进行的组已满，较高优先级是否保证入会？

进行中的会话已达到在网参与人数上限（on-network-max-participant-count）时，若本地策略判断新用户的优先级高于至少一名既有参与者，控制功能可以按所引的参与者移出规程移出一人，跳过容量拒绝这一步，再继续后续处理。是否移出并非强制，也没有规定必须挑优先级最低的人。不采用该例外时，该满员分支须向发起网络返回 486（Busy Here），Warning 引号内的 MCPTT 文本码 122 表示人数过多。尚未达到上限则不触发这一容量拒绝；仍须满足其余入会条件。

步骤 11 的注 2 只举出可能的策略输入，如用户优先级、参与者类型及其他组文档信息；未规定统一的排序、候补或抢占算法。移出结束的是该客户端参与这场会话。解除组归属和给高优先级用户腾位置都可能导致移出；只看到移出，不能判定用户已解除组归属，也不能判定组成员名单有变。

SIP 486 和 MCPTT 文本码 122 说明这次请求因人数上限未获准，不报告用户此前是否已归属，也不能单凭该响应断定是否曾执行过隐式归属。

依据：§10.1.2.4.1.1（步骤 11a–b、注 2，印刷页 288）；§10.1.1.4.4.3（定义移出及所列原因，印刷页 251）；§4.4.1、§4.4.2 表 4.4.2-1、表 4.4.2-2 的 122 项（印刷页 33、34、36）。

### 同样是 486 Busy Here，怎么区分哪项限制触发？

**先看 Warning 引号里的文本码，再核对是哪一侧的 INVITE。** 以下限同一 MC 系统内的普通在网按需聊天组，使用未重组的 MCPTT 组身份，不是临时组；本次请求和组状态都不是紧急或迫近危险。客户端把初始 INVITE 交给发起侧参与功能（O-PF）。走到发往控制功能（CF）的步骤时，O-PF 另生成一个 INVITE。两个请求的应答要分别配对。[§10.1.2.3.1.1，第 9、10、16 项，印刷页 277–278](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=278)。

| Warning 引号内的文本 | 谁拒绝哪一腿，查什么 |
| --- | --- |
| `103 maximum simultaneous MCPTT group calls reached` | **O-PF 回客户端。** 第 5 项检查该用户的同时 MCPTT 组呼数是否超过用户配置的 `MaxSimultaneousCallsN6`。正文条件是“已超过”，不能从提示里的 `reached` 推出计数恰等于上限就应拒绝。 |
| `102 too many simultaneous affiliations` | **O-PF 回客户端。** 先按收到的 `mcptt-client-id` 和目标组判断。用户在**本次发起客户端**未归属目标组时，O-PF 才执行隐式归属；实际执行且因该用户已有 N2 个同时归属而失败，第 7 项才回 486 并停止。另一客户端的归属状态不能代替这一项；只知未归属、已达到 N2，或不知道本次隐式归属为何失败，都不足以判为这一支。 |
| `122 too many participants` | **CF 回 O-PF 发起的那一腿。** 本场已在进行且达到在网参会人数上限，没有采用上一节的可选移人分支，才按第 11(b) 项回 486。它限制的是**这场会话**的参与者数，不是用户的组呼数或归属组数。 |

N6 和 N2 都是在 O-PF 处理客户端请求时检查，不是 CF 在数这场有多少人。N2 的定义由第 7 项后的注 4 回指；本页不规定它的数值或归属算法。[§10.1.2.3.1.1，第 5–7 项及注 4，印刷页 276–277](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=277)；[§9.2.2.2.11，第 1–3 项，印刷页 183](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=184)；[§10.1.2.4.1.1，第 11(a)、(b) 项，印刷页 288](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=289)。

**不要把三个数字放错字段。** 486 是 SIP 响应状态；`Busy Here` 是状态行里的提示。399 是这里适用的 SIP `Warning` 外层警告码。102、103、122 是 `Warning` **引号内开头**的 MCPTT 文本码。只见 486、`Busy Here` 或 399，分不出这三种原因。[§4.4.1–2，表 4.4.2-1 和 4.4.2-2，印刷页 33–36](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=34)。

例如，O-PF 发往 CF 的那条 INVITE 收到 **486、Warning 文本码 122**，终端侧与本次加入配对的 INVITE 也收到 **486、122**。两侧都对上，就能把原因定位到 CF 的人数限制。O-PF 收到对它发出的 INVITE 的 4xx、5xx 或 6xx 时，须生成应答，把实际收到的 Warning 头字段纳入应答，再发给客户端。**终端看到包是 O-PF 发来的，不等于拒绝是 O-PF 作出的。** 这条规定不是在说两侧的整包相同，也没说丢失的 Warning 可以补造。若只拿到状态行，且没有对应 Warning 或能说明处理分支的记录，就不要判为 N6、N2 或本场满员；没抓到 O-PF 发往 CF 的 INVITE，也不能证明它没发。[§10.1.2.3.1.1，收到出向 INVITE 失败响应的第 1–3 项，印刷页 279](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=280)。

### 普通组呼的 200(INVITE) 与会议通知分别能证明什么？

控制功能在对其入向 INVITE 的 200 中用 Contact 给出 MCPTT 会话身份和 isfocus 等标记，与媒体面交互后发送该响应。发起侧参与功能收到 2xx 后，另生成 200 发给客户端。客户端收到自己这侧的 2xx 后须与用户面交互，但可自行决定是否订阅会议事件。若加入的是已有会话且已有参与者订阅，控制功能须向所有已订阅的参与者发送 NOTIFY。

首次建会或无人订阅时，本次入会均不触发这项通知。给新人腾出席位与对其初始 INVITE 回 200，只说明容量与入会信令的处理；都不是话权授予。这个 200 也不能分辨会话是不是刚建的、其他成员是否已加入或听到语音。

依据：§10.1.2.4.1.1（步骤 15、19、23–25，印刷页 290）；§10.1.2.3.1.1（收到 2xx 后的步骤 2–3、8，印刷页 278–279）；§10.1.2.2.1.1（收到 2xx 后的步骤 1、3，印刷页 266）。

### 恢复覆盖后主动加入：怎样知道是不是原来那场？

甲失去覆盖前参加了 G 组的聊天会话。恢复覆盖后，**如果甲主动请求加入 G**，客户端走上面的普通按需入口：发新的初始 INVITE，Request-URI 填服务甲的参与功能（PF）的公共服务身份，正文 `session-type=chat`，`mcptt-request-uri` 写 G 的组 ID。旧会话身份不是这条 INVITE 的目标。触发是**用户请求加入**，不是网络恢复本身。仅看到恢复覆盖，不能断定客户端会自动重发或控制功能（CF）会发邀请。§10.1.2.2.1.6 的入向 INVITE 是紧急、迫近危险呼叫中已归属但还未加入的客户端入口，不能套给这里的普通聊天组。[§10.1.2.2.1.1，开头及步骤 9、13，印刷页 265–266](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=266)；[§10.1.2.2.1.6，开头，印刷页 272](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=273)。

若通过前序检查，CF 到步骤 10 发现 G **当前没有聊天会话身份**，须新建并分配会话身份。若 G 当前有进行中的会话，且甲的请求获准，则加入那一场。即使甲之前参加过 G，也不能只凭这次 2xx 说回了原场：如果原场已在失覆盖期间结束，甲可能进了同组另一场，也可能由这次请求新建。[§10.1.2.4.1.1，步骤 9–10，印刷页 288](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=289)。

**要认原场，就对会话身份。** 先把当前的成功响应配到各自那侧的 INVITE。CF 在自己的 200 的 Contact 中给出控制侧会话身份，PF 收到成功响应后发给甲的另一个 200 使用映射的身份。比较失覆盖前后控制侧的会话身份；若只有甲侧的身份，先核对 PF 的映射，别拿甲侧的 Contact 和 CF 侧的 Contact 裸值直接对比。只看到甲的这次 2xx，可以判断这次加入请求成功，不能判断同一场、话权已授予或 RTP 已恢复。[§10.1.2.4.1.1，步骤 15、19、24，印刷页 290](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=291)；[§10.1.2.3.1.1，收到 2xx 后的步骤 2、6、8，印刷页 278–279](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=279)；[§4.5，印刷页 38–39](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=39)。

## 紧急或迫近危险：控制功能如何纠正优先级

### 初始 INVITE 缺少 Resource-Priority，控制功能就要发 UPDATE 吗？

紧急指示 emergency-ind 为 true，或组已处于紧急状态时，控制功能核对自己收到的 INVITE 是否带紧急档。若组不处于紧急状态，而迫近危险指示 imminentperil-ind 为 true 或组已处于迫近危险状态，则核对迫近危险档。两处分支分别是 13a 和 14a。只有头缺失或与应有档不符，这两个分支才调用同一个纠错程序（§6.3.3.1.8）生成 UPDATE。调用它的分支负责把 UPDATE 发向这份入向 INVITE 的发起方，并在收到该 UPDATE 的 200 后继续。头值正确就不走这项纠错。

普通请求遇到普通组，缺头本身不会触发纠错。已带高档头的 INVITE 还可能在更早的检查被拒绝：带紧急档、无紧急指示且组紧急状态为 false，按 8a 回 403 并停止；带迫近危险档、无迫近危险指示且组迫近危险状态为 false，按 8b 也回 403 并停止。这两种请求都不会收到用来降档的 UPDATE。

依据：§10.1.2.4.1.1，步骤 3、6–8（印刷页 287–288），13a、注 3（288），14a、注 4（289）。

### UPDATE 里的优先级跟随请求的指示，还是跟随组状态？

控制功能看填写 UPDATE 时组的进行中状态：紧急为 true 取紧急档；紧急为 false、迫近危险为 true 取迫近危险档；两者都为 false 取普通档。按 §6.3.3.1.19，从 MCPTT 服务配置的 OnNetwork 下对应的 emergency-resource-priority、imminent-peril-resource-priority 或 normal-resource-priority 同时读取 resource-priority-namespace 和 resource-priority-priority。

13a/14a 核对来包所需的档，与辅助程序按组当前状态填 UPDATE，是两个判断。新声明紧急并不自动使 UPDATE 取紧急档：若填头时两个状态均为 false，辅助程序写普通档。主流程把原为 false 的组状态置为 true 的动作分别在后面的 13c(i)、14c(i)。

依据：§6.3.3.1.8，收到 PRACK 后的步骤 4–5（印刷页 109）；§6.3.3.1.19（118–119）；§10.1.2.4.1.1，13a、13c(i)、14a、14c(i)（288–290）。

### 控制功能侧的 183、UPDATE 与三个 200，怎样和两侧的 INVITE 配对？

客户端发给 O-PF 的 INVITE 带 offer A。O-PF 另生成一份 INVITE 发往 CF，其中的 offer B 以 A 为基础，须替换媒体流地址时，O-PF 写入自己的 IP 地址和端口。CF 纠错时先向客户端方向发可靠 183（Require: 100rel），里面的 SDP answer 回答 B。收到针对该 183 的 PRACK 后，CF 回 200(PRACK)，再向其入向 INVITE 的发起方发带 Resource-Priority 的 UPDATE；UPDATE 携带新 offer C，编制依据仍是 B，不是 183 中的 answer。即使 A 和 B 中的字段碰巧相同，也要按 CF 收到的那份 INVITE 配对。

在 CF 一侧，200(PRACK) 只回应 PRACK。CF 必须收到对自己所发 UPDATE 的 200 才继续处理；最终发出的 200(INVITE) 才接受 O-PF 发来的 INVITE，其 Contact 含会话身份和 isfocus。未走纠错时，步骤 16 要求 CF 的 200(INVITE) 带 SDP answer；走了纠错，183 已回答 B，步骤 16 不再要求这个 200 重给 answer，也不禁止其中出现任何 SDP。

在客户端一侧，不能套用 CF 的步骤 16。O-PF 收到其发往 CF 的 INVITE 的 2xx 后，要另生成一个 200，按参与功能的规程加入 SDP answer，再发给客户端。CF 发出的 200 没有重复 answer，并不表示客户端收到的 200 也可省略它。

依据：§10.1.2.3.1.1，发向 CF 的 INVITE 步骤 9–10、12（印刷页 277），收到该 INVITE 的 2xx 后步骤 2–3、8（278–279）；§6.3.2.1.1.1、§6.3.2.1.2.1（83–84）；§6.3.3.1.8，183 步骤 1–4 及收到 PRACK 后的步骤 1–5（印刷页 109）；§10.1.2.4.1.1，13a(ii–iii)、14a(ii–iii)（288、289）及 15–16、19、23–24（290）。

普通在网按需预安排组呼的客户端如何发起、如何应答，见[预安排组呼的按需建立](prearranged-client-establishment.md)。已知普通在网预安排组呼的目标会话身份，客户端本次按需主动重入、不使用预建立会话，也不请求隐式话权，可按[重入与晚入](rejoin-late-entry.md)核对重入流程。若这份重入 INVITE 还请求隐式话权，该页仍可核对客户端的 Request-URI 是否指向已知会话身份，但不能用来验证话权请求的处理或授予。实际使用预建立会话时走 REFER，不走这里的按需重入。新会话建立时，怎样识别隐式话权请求、主叫何时可获提前发送 RTP 的许可，见[隐式话权请求与早期媒体](../media/implicit-floor-early-media.md)。

若已经加入使用未重组的 MCPTT 组身份的普通按需聊天会话，且不是临时组，要查客户端主动退出或控制功能发 BYE 时参与功能的两侧处理，见[聊天组 BYE 与单人或整场释放](chat-participant-or-session-release.md)。
