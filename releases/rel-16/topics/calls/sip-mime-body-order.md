# MCPTT 的 SIP 消息有多个正文时，为什么 SDP 要放第一？

发送 MCPTT 的 SIP 请求或响应时，先数这条消息实际携带的 MIME 正文，再核对每段的类型。§6.5 要求 MCPTT 客户端和服务器都支持 SIP 请求、响应中的多个 MIME 正文。它规定封装与顺序，不规定每种业务必须带哪些正文。〔TS 24.379 V16.14.0，Stage 3，§6.5，印 137–138〕

## 一个正文和多个正文，外层 Content-Type 不同

- **只有一个正文：** SIP 层的 `Content-Type` 直接写该正文的 MIME 类型，后面放正文内容。例如只有 SDP answer，就写 `application/sdp`，不是用单段的 `multipart/mixed` 包一层。
- **有多个正文：** SIP 层的 `Content-Type` 写 `multipart/mixed`，带选定的 `boundary` 参数。每段前写边界分隔符，每段带自己的 `Content-Type` 和内容；最后写结束分隔符。外层类型和任一段自己的类型不是同一个字段。

只见外层 `multipart/mixed`，不等于已经看到所有段。核对实际字节里的分隔符、分段类型和结束分隔符，别用日志里显示的段数代替完整消息。〔§6.5，印 138〕

## 多个正文里含 SDP offer 或 answer，就让 application/sdp 排第一

这个要求同时适用于请求和响应，例如同带业务 XML 的 INVITE offer 或 200 answer。**多个 MCPTT 应用正文之间没有规定先后。** 若某程序用 REFER 里的 `cid` 指向某一正文，仍要核对引用是否指中那个正文；不能改用第几段推断业务对象。若消息未携带 SDP，§6.5 不要求为排序而补一个。〔§6.5 正文及注，印 138；业务引用见[预建立私呼发起](private-preestablished-origination.md)〕

## 旧 SIP 核心只处理首段时，交换两段业务正文没有用

§6.5 的注解释了为什么让 SDP 在前：底层 SIP 核心若有不能理解多个 MIME 正文的功能实体，它会忽略首段以外的段。因此，只在 SDP 后交换两个 MCPTT 应用正文，不会让这样的实体处理其中一段。这不等于每个 SIP 核心都会忽略后续段，也不说明某台设备会删掉后续段再转发。〔§6.5 注，印 138〕

发送侧有完整消息，接收侧日志只显示 SDP，先分清**那一段实际收到了什么**和**日志展示了解析出的哪一段**。对照同一请求或响应在各跳的完整记录，查 multipart 封装是否保留，以及对应 MCPTT 功能是否收到了所需应用正文。未核对接收原文和本段响应，不能从一条 SDP 日志断定发送端漏写或业务已经失败。若普通私呼处理记录认定缺少资源列表，另查[相应服务器收到的 INVITE 与 403/145](private-server-admission-routing.md)。这属于业务程序，不是 §6.5 对正文排序给出的失败码。
