# 迫近危险组通信由谁发起？组优先级何时改变，迟入成员得到谁的身份？

这是 3GPP TS 22.280 V16.8.0（Release 16，Stage 1）的[在网和离网共用要求，印刷页 12](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=13)。下文短号均指 §5.6.2.3.1：[R-5.6.2.3.1-001 至 -006，印刷页 19](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=20)；[R-5.6.2.3.1-007 至 -009，印刷页 20](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=21)。

## 发起和选组

业务须支持**获授权且已归属该 MCX 业务组的成员**发起迫近危险组通信（-001）。业务还须让管理员配置该用户用**自己所选的业务组**还是**专用迫近危险组**（-009）。配置的是业务组，不是发起时使用哪些业务应用；配置也不代替归属或授权。若已有一场组通信正在进行，业务须能把它改为迫近危险组通信（-003）。本条未指定谁可执行升级。

## 优先于什么，能抢占什么

- **其他组传输（-002）：** 迫近危险组通信须优先于同一 MCX 业务中的其他组传输。
- **其他类型的通信（-004）：** 迫近危险组通信的**内容和信令**都须有高于同一 MCX 业务中其他类型通信的抢占优先级。

两项都排除系统通信、业务紧急组通信、业务紧急私通信和其他迫近危险组通信。条文没有给这些例外排先后，也没有规定承载参数，不能据此判断另一个业务或某个承载已被抢占。本节编者注将紧急通信与迫近危险通信的交互列为待研究（FFS），不是另一项要求。[R-5.6.2.3.1-008 后的编者注，印刷页 20](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=21)。

## 组优先级、转态通知和身份信息

组的**迫近危险进行中（In-progress Imminent Peril）状态**发起时，业务须给该组附加迫近危险优先级（-007）。该组状态取消时，业务须移除与组关联的迫近危险优先级（-008）。一场通信结束，不足以证明该组状态已取消。这里没有规定开始维持组状态的时点；取消权限和处理另属 §5.6.2.3.2。

一场组通信**转为迫近危险进行中**时，须通知已归属组成员（-005）。这场通信**继续处于迫近危险状态**时，业务须向现有及迟入的已归属组成员提供两项信息（-006）：**状态发起者的 MCX 业务用户 ID**，以及**这是迫近危险组通信的指示**。例如，甲建立普通组通信，乙后来发起迫近危险状态。只要状态仍在，此时迟入且已归属的丙应得到乙的 ID。要找的是状态发起者，不是按建呼人或当前发送者取 ID。
