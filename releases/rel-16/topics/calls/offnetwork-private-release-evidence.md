# 进行中的离网私呼收到 RELEASE：Q 清理、P 等待和媒体终止怎样区分？

在一通已经建立的离网 MCPTT 一对一私呼里，**清除本机呼叫类型不必等 RELEASE ACK**。基本呼叫控制 **P** 和呼叫类型控制 **Q** 并行。一个终端可能因用户释放请求已按 Q 分支清理类型，却仍按 P 分支等待释放确认。这不表示另一台终端也已清理。以下只讲固定 TS 24.379 V16.14.0 的实际释放，不是紧急优先级取消或升级没有应答。[§11.2.3.1、§11.2.3.3.1–3，印刷页 436–437](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=437)

## 实际释放时，哪些计时器和状态属于 Q？

在 **Q1（进行中的普通私呼）** 或 **Q2（进行中的紧急私呼）**，本机收到用户要求释放本次呼叫的指示，**或**本机实收这通呼叫的 `PRIVATE CALL RELEASE`，就按呼叫类型控制的释放程序处理。无需再用 RELEASE ACK 作 Q 入口。两种状态都要清除保存的当前呼叫类型及 ProSe 包优先级，进入 Q0。

| 触发前本机的 Q 状态 | 该条另要求停止 |
| --- | --- |
| Q1 | **仍在运行的 TFP6**，即紧急私呼取消的重传计时器。 |
| Q2 | **仍在运行的 TFP1**，即私呼请求重传计时器；**TFP8**，即隐式降级计时器。原文没有为 TFP8 再加“若正在运行”的条件。 |

因此，若甲本机确有用户释放指示，甲不必先看到乙的响应才适用 Q 清理。若乙真实收到本通呼叫的 RELEASE，也按**乙当时的 Q 状态**查需停的计时器，不用甲的状态代替。Q0 只描述本地类型状态，不证明已按基本呼叫程序结束媒体、已拆除整通呼叫或已经新建呼叫。两套状态机在同一事件上的执行顺序未规定，要确认实际动作是否完成须查本端状态和计时器记录。[§11.2.3.4.7，印刷页 443](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=444)

## 本地媒体何时终止？ACK 与无响应各说明什么？

看同一通呼叫在**同一端**的基本状态和实收事件，不把一个端的发包代替另一端实收。[§11.2.2.4.5.1，印刷页 433](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=434)；[§11.2.2.4.5.3–.5，印刷页 434–435](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=435)

| 本机基本呼叫状态和事件 | 本机按该 P 分支处理 |
| --- | --- |
| P4 中用户要求释放 | 发送带已存呼叫标识和双方 ID 的 RELEASE，停止 TFP5，置 CFP3=1、启动 TFP3，进入 **P3 等释放回应**。这一步没有规定终止媒体。 |
| P4 中实收本次呼叫的 RELEASE | 用已存呼叫标识和双方 ID 回 RELEASE ACK，**发送后**终止本地私呼媒体会话，停止 TFP5、启动 TFP7，释放呼叫类型控制状态机，进入 **P1**。 |
| P3 中实收对应 RELEASE 的 ACK | 停止仍在运行的 TFP3，终止本地媒体会话，启动 TFP7，释放呼叫类型控制状态机，进入 P1。 |
| P3 中 TFP3 到期且 CFP3 **等于**上限 | 终止本地媒体会话，启动 TFP7，释放呼叫类型控制状态机，进入 P1。本分支不以收到 RELEASE ACK 为前提，也不据此判断对端有无发出确认。 |

P1 的 TFP7 到期才清除已存 Call identifier，进入 P0。仍有旧标识不表示本机仍在通话。旧手动私呼页另有重传条文及其与达限守卫的区别；这里不补它们的执行优先级，也不从 P1 推定某个重复报文一定有 ACK。[§11.2.2.4.5.7，印刷页 435](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=436)

**RELEASE ACK 的定义是回复 RELEASE，表示发送方终止呼叫。** 它与只确认收到 ACCEPT 的 ACCEPT ACK 不同。核对本端实际收到的是本次 RELEASE 的 ACK，再用本机记录查 P3 后的媒体动作。也不能把 ACK 的发送时刻当作乙媒体确实已停的时刻：P4 收到 RELEASE 的程序先发 ACK，随后才要求终止媒体。无 ACK 达限同样不证明对端收到、拒绝或终止。要核实两端实际状态或媒体结果，各查两端的处理与媒体记录。[§15.1.10.1、§15.1.11.1，印刷页 482](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=483)；[§11.2.2.4.5.4–.5，印刷页 434–435](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=435)

需要核对普通手动初建取消和重传细节，见[普通离网私呼手动应答](offnetwork-private-manual-client.md)；仍在初建等 ACCEPT 的，见[普通离网私呼自动应答](offnetwork-private-auto-client.md)。如果只有紧急升级的 SETUP REQUEST、匹配 REJECT 或 TFP1/CFP1 达限，见[离网私呼紧急升级](offnetwork-private-emergency-upgrade.md)，不能当作实际 RELEASE 来处理。
