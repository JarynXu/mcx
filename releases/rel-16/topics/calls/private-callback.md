# MCPTT 私呼回电：对方确认了“请回电”，通话建立了吗？

没有。假设甲请乙回电，乙的客户端会登记请求、通知乙，并发回业务答复。甲端凭匹配的答复进入“已确认”，意思是**甲还在等乙来电**。乙是否已决定拨号、甲是否接听、双方是否听见声音，都不能从这条答复得出。

本页只讲 Release 16 在网 MCPTT 普通私呼回电的两个客户端。下文一直称甲为**请求方**、乙为**目标方**；乙实际回拨时，乙才是这通私呼的主叫。依据 [3GPP TS 24.379 V16.14.0（Stage 3），§§11.1.5.1–11.1.5.2.3，印刷页 390–393](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=391)。

## 甲发请求，乙登记什么？

甲端先查用户配置：请求回电查 `allow-request-private-call-call-back`，取消回电另查 `allow-cancel-private-call-call-back`。本次操作对应的许可缺失或为 false，就告知甲并退出，不发送这次请求。能请求不等于能取消。

允许请求时，甲端在 SIP MESSAGE 里指定乙的 MCPTT ID，带上紧急程度（低、普通或高）和请求时间；本地按乙的 ID 记下 I2（等业务确认）。乙端收到请求，按甲的 MCPTT ID 保存目标端状态、紧急程度和请求时间，通知乙，再用另一条 SIP MESSAGE 返回回电业务答复。紧急程度是这个请求的属性，不是乙已拨号或已经接听的证据。（§§11.1.5.1、11.1.5.2.1–2，印刷页 390–393。）

这一版的目标端状态代码有冲突，不能默改：§11.1.5.2.2 步骤 1(b) 在乙登记时印作 `PCCB-I2: private-call-pending`；同节取消分支、§11.1.5.2.3 履约分支和[表 G.13-2](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=595)的状态行写作 `PCCB-R2: private-call-pending`。二者都在指乙端的回电待办，本页不裁定应如何改字或编码。甲端自己的 I2 是等确认（confirm-pending），不能因代码相像就混作一端的状态。

## 甲收到哪一种答复才算确认？取消又看什么？

- **确认：**原 SIP MESSAGE 事务的成功响应，不是乙的回电业务答复。甲须收到乙端另发的回电答复 MESSAGE：其中的 `mcptt-calling-user-id` 匹配本地为乙保存的条目，且该条目正在 I2，才转为 I3（已确认）。若答复来自另一个用户或甲不在这个状态，不能按这条规则推进。
- **取消：**在表 G.13-1 所示的已确认路径上，取消许可通过后，甲端发取消 MESSAGE，记 I4（等取消确认）；不是一按取消两端记录就同时消失。乙端收到取消请求时，若甲的条目匹配且处在取消分支写明的 R2，置 R1 并删除甲的条目。乙端用 MESSAGE 回取消业务答复；甲端收到与乙 ID 匹配的取消答复且仍在 I4，才按这一成功分支置 I1，删除乙的条目。这里取消的是回电待办，不是挂断已建立的私呼。
- **失败：**另有一条明确的退出路径：甲发出的请求或取消 MESSAGE 收到 SIP 4xx、5xx 或 6xx 时，甲端把对应乙的条目置 I1、删除并退出。这证明甲端按失败分支清理，不证明乙已取消，更不是乙已履约。

见 §11.1.5.2.1–2（印刷页 391–393）；资料性附录 G.13 的表 G.13-1、G.13-2 均在印刷页 594。表中 I3 仍保留乙的 ID 和甲端状态。

## 乙真的拨回来，双方何时清掉待办？

只有乙用户想回拨时，乙端才从待办中取甲的 MCPTT ID，以**手动应答模式**向甲发起私呼。有话权控制的建呼走 §11.1.1.2.1.1 或 §11.1.1.2.2.1，无话权控制走 §11.1.2.2。发起建呼与甲应答仍是两个事件。

按 §11.1.5.2.3（印刷页 393）的履约分支，**甲发送**针对这次私呼建立请求的 SIP 200 (OK)，且对应乙的条目仍在 I3，甲端才转 I1 并删除条目。**乙收到**本次建呼 INVITE 或 REFER 的 SIP 2xx，且对应甲的条目在该段写明的 R2，乙端才转 R1 并删除条目。资料性表 G.13-2 用收到 200 举例描述归零；程序正文列的是 2xx。不要把回电请求 MESSAGE 的成功响应当作建呼响应，也不能把一端记录消失当成另一端已清理或媒体已通的证明。
