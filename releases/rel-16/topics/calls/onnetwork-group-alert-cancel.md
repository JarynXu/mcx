# 在网 MCVideo、MCData 组紧急告警：谁取消谁的告警，谁回了执？

乙替甲取消先前发给组 G 的紧急告警，丙的客户端向业务服务器发回取消响应。这里有三个人：**乙是取消人，甲是原告警人，丙是这份回执的发送者。** 按取消响应表填写的用户 ID 是乙，不是甲或丙。要核实丙端是否已回应，得把响应的实际发送端和这一次取消对上；要核实乙有没有代撤权限，也得另查授权。[TS 23.280 V16.7.0，表 10.1.2.17-1、10.1.2.18-1，印刷页 66](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=67)；[§10.10.1.2.2 注 2，页 179](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=180)。

**先分清本人取消和代撤。** Release 16 的这套 Stage 2 在网程序用于 MCVideo、MCData；是否也适用于 MCPTT，本版列为待研究。图 10.10.1.2.2-1 画的是甲取消**自己的告警**：甲的客户端 1 此前已成功发起告警，现在仍处于紧急状态，并已归属指定紧急组。图中客户端 1、2、3 的用户属于组管理服务器（GMS）定义的同一业务组。只看到一次发起请求，不足以确认发起成功；只在组员名单上，也不等于客户端已归属。图中用一个业务服务器代表用户归属业务服务器和组托管业务服务器，不限定部署拓扑。注 2 另允许获授权的用户取消发起人的告警、组的进行中紧急状态，或两者一起取消；它没有把本人流程改画成一套代撤时序。[§10.10.1.1，印刷页 176](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=177)；[§10.10.1.2.2 开头、前提 1–3、图及注 1，页 178](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=179)。

**取消请求里的两行 MC service ID 各填谁？** 表 10.1.2.17-1 用于客户端发给服务器、服务器发给客户端两个方向。服务器把请求转向丙，并不会把表中任何一行改成“收件人丙”。

| 请求中的信息 | 乙请求取消甲的告警时怎样读 |
| --- | --- |
| 第一行 MC service ID（M，必填） | 写取消人乙。 |
| 第二行 MC service ID（O，带表注） | 写原告警人甲。请求取消另一用户的告警时，这一行**必须有**。若在完整请求中没有这一行，所指就是取消人乙自己的告警，不能靠工单备注把它解释成甲的告警。未采到完整请求则无法判断这一行是否缺失。 |
| MC service group ID（M） | 写与这次告警关联的组 G。本人流程的步骤 2 指向原来发过告警的那个组。 |
| Group's in-progress emergency state cancel request（O） | 要求同时取消 G 的进行中紧急状态。这是附加请求，不是组状态已清除的结果。 |

第二行出现甲的 ID，只能判请求指向甲的告警，不能证明乙有权代撤、服务器已接受或甲的终端已复位。[§10.1.2.17 方向说明，页 65](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=66)；[表及表注，页 66](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=67)。

**取消告警后，组还可以处在紧急状态吗？** 可以。服务器对“取消甲的告警”和“取消整个 G 的进行中紧急状态”可分别接受或拒绝。例如两项都请求了，服务器接受前一项、拒绝后一项，两项结果并不矛盾。不能凭一份告警取消确认给 G 记作已解除；若要判 G 的实际状态，要看针对 G 的决定和状态记录。[§10.10.1.2.2 步骤 1、注 2，页 179](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=180)。

**本人取消时，哪一端在确认什么？** 甲在步骤 1、2 发起取消，请业务服务器通知原组。步骤 3，业务服务器根据 GMS 的资料解析组号，确定成员及其归属状态。接下来要分三处看记录：

- 步骤 4 是**服务器 → 甲的客户端 1**，确认甲的取消请求；图示本人流程在这一步由客户端 1 复位自己的紧急状态。服务器发出确认不等于已经观察到甲端复位。也不能套用这一步，说乙代撤时乙的终端必然复位，或由一份代撤响应认定甲已复位。
- 步骤 5、6 是服务器向**已归属成员的客户端**发取消请求，再由各接收端通知本机用户。成员名单不是发送记录，发送记录不是收件凭证。接收端通知用户也不等于人已读。
- 步骤 7 是**各接收端 → 服务器**，确认收到取消。单播取消时，收到的客户端发送回执；组播取消时，客户端若未配置为发送回执，就不发，配置为发送时才回。不论单播还是组播，没采到丙的回执都不能证明丙没收到取消。组播还要先看丙是否配置为发回执。只见丙发回执，不等于服务器已经收到。服务器收到并能对应到丙端和本次取消，只能确认丙这一端，不能代其他成员签收。

步骤 4 和 7 共用表 10.1.2.18-1：必填的 MC service ID 都指**取消人**，必填的 MC service group ID 都指**告警关联组**。在图示本人取消中两项是甲、G；在乙代撤的取消响应中是乙、G。表中没有单列原告警人或回执发送人的字段。只看取消响应中的这两项，不能认出被代撤者或指认哪位组员回了执：乙替同组另一位用户撤警，响应里的乙、G 也不变。它们同样不能说明全组都已收到或两项取消各获什么决定。[§10.1.2.18，页 66](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=67)；[图 10.10.1.2.2-1，页 178](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=179)；[步骤 1–7，页 179](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=180)。

若问的是同一 MC 系统在网单播**发起** MCVideo 或 MCData 组告警时，下发谁的位置、组员如何确认收到告警，查[组告警的发起与位置](onnetwork-group-alert-location.md)。若同一 MC 系统内的在网 MCVideo 或 MCData 终端刚离开预设区，要判断谁决定是否启动取消，查[在网区域告警](emergency-alert-area-entry-exit.md)。若是离网 MCVideo 或 MCData，接收端跟踪他人的组告警，后续周期通告迟迟不来，查[离网组告警的超时与明确取消](offnetwork-group-emergency-alert.md)。
