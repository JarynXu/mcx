# MCPTT 组呼：组的控制方一定是某个组员的主系统吗？

不一定。TS 24.379 V16.14.0 的图 5.3.2-6 给了一个三系统例子：**伙伴 1 拥有组并承担控制功能，但没有任何组员以伙伴 1 为主系统。** 发起客户端 X 和发起侧参与功能在图示主系统；终接侧参与功能和客户端 Y 在伙伴 2。组归谁所有、组员以哪个系统为主系统，是两件事。〔Release 16，Stage 3，[§5.3.2 图 5.3.2-6 及前一段，印刷页 54](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=55)〕

## 先认角色，再看角色在哪个系统

参与功能（PF）服务用户，图中按其服务发起端或终接端标为 O-PF 或 T-PF；控制功能（CF）承担本场组呼的控制角色；图中非控制功能（NCF）代表临时组的一个组成组。功能框不代表独立服务器。同一 MCPTT 服务器可以在同一组呼中同时承担 PF 与 CF，或同时承担 PF 与 NCF。同一个系统也可把功能放在多台服务器上。同一台 MCPTT 服务器承担的功能之间传递请求，不经过底层 IMS SIP 核心。同属一个系统不足以套用这条说明。〔[§5.3.1 的角色说明，印刷页 51–52](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=52)；[§5.3.2 开头注，印刷页 52](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=53)〕

图 -6 说的是组员的主系统，不是组员是否已归属到该组、当前由谁服务或是否参会。伙伴 1 没有以它为主系统的组员，不等于组为空，也不能把所有组员都算到伙伴 2。图 -5 的非受信任互助仍有互助关系；仅见 NCF 代邀也不能反推不受信任，同系统的图 -2 就允许代邀。受信任时可以提供身份，并不要求每次转交，也不说明身份字段、别名披露规则或 CF 已经收到名单。

## 要确认具体呼叫，查哪个规则？

这些图给的是功能关系，原文允许其他模型。不能由图数物理节点或网关，也不能确认这场呼叫的 SIP 路由、注册结果、准入或媒体到达。

- 要判断组呼控制方应由哪个系统提供，读 Stage 2 的[互连下的控制方与用户业务授权](../identity/interconnection-authorization.md)，按组主系统和伙伴服务成员的条件判断；要核对某台服务器能否控制一个临时组，读[跨系统临时重组的控制资格](../groups/partner-system-regroup.md)。这里的图不替代两项规则。
- 要判断伙伴是否放行一通来话，读[伙伴组呼的逐通准入](../groups/partner-group-call-admission.md)；若实际是预安排组成组 INVITE 返回带名单的 403，读 [CF 和 NCF 各自的报文条件](trusted-regroup-refused-uri-list.md)。不能拿图 -5 的互助关系代替报文或许可。
- 若问题是已确认合设的 O-PF 与 CF 为何不在 IMS 抓包里单独出现，读[按需预安排组呼的合设与 SDP](prearranged-server-admission-routing.md)；若手上只有失败响应里的角色标签，读 [Response-Source 能指出什么](failure-response-source.md)。角色标签不是主机标识，PF 标签也分不出发起侧和终接侧。
