# MCPTT 私呼回电：谁转发成功响应，谁生成 200？

甲请乙回电。甲的客户端收到了 SIP 200 (OK)，应当先问：**这是对哪条消息的响应？** 如果是对回电请求 MESSAGE 的响应，200 说明这条消息的事务得到成功响应，不是乙客户端另发的回电业务答复，更不是乙已经拨回来、甲已接听的证据。取消回电也一样：取消 MESSAGE 的 200 不是取消业务答复。

下面只看 Release 16 在网 MCPTT 的私呼回电服务器程序。对甲发出的这条请求，发起侧参与功能服务甲，控制功能把请求送往乙所在的终接侧参与功能，终接侧参与功能再送向乙。三者是**功能角色**，不是三台物理服务器的部署要求。依据 [3GPP TS 24.379 V16.14.0，Stage 3，§§11.1.5.3–4，印刷页 393–396](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=394)。

## 同样是拒绝回电，原因可能在哪一侧？

**发起侧先认甲，再查甲这次要做什么。** 它用请求中断言的公共用户标识查发方的 MCPTT ID。无绑定或绑定已过期，须拒绝并停止：SIP 404，Warning 文本以 141 开头。如果绑定有效，请求回电查用户配置的 `allow-request-private-call-call-back`；取消则查 `allow-cancel-private-call-call-back`。本次所需的许可缺失或为 false，须回 403 并停止：请求用 Warning 文本 151，取消用 152。一次申请获准不能当作以后可以取消。这里的 141、151、152 是 Warning 文本中的编号，不是 SIP 状态码。[§11.1.5.3.1 步骤 2、2a、3–4，印刷页 394](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=395)。

**控制功能检查业务标记和收件人。** 回电请求、取消请求和回电业务答复，都可以是控制功能收到的 MESSAGE 请求。如果 Accept-Contact 中没有带规定 MCPTT 服务标识值的 `g.3gpp.icsi-ref` 标签，须回 403 并停止。另一项检查是资源列表：没有资源列表消息体，或该消息体含多个条目，须回 403，Warning 文本为 145（不能确定被叫），并停止。不能只凭一个 403 就说甲没有取消许可；也不要把“已有列表体但零条目”悄悄算成步骤 3 明列的情形。继续处理时，控制功能把列表中的目标 MCPTT ID 交给终接侧，请求发往服务该目标的终接侧参与功能。如何查得该功能的地址，本版不规定。[§11.1.5.4 开头、步骤 2–4、8–9 及注，印刷页 395–396](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=396)。

**终接侧要认的是乙。** 它按收到的目标 MCPTT ID 查与公共用户标识的绑定。没有这项绑定，须回 404；这一步没指定发起侧的 Warning 文本 141，也没把发起侧的“过期”分支另列为条件。单凭一个 404，不能断定查不到的是甲还是乙。[§11.1.5.3.2 步骤 2–4，印刷页 395](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=396)。

三种角色各自在资源不足以处理请求或有拥塞风险时，**可以**回 500；选用 500 时也**可以**附 Retry-After。不是一遇资源紧张就必须回 500，更不能从 500 推出必有重试时间。[两项参与功能程序及控制功能程序各自的步骤 1，印刷页 393、395](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=394)。

## 成功怎样回到甲？出错又怎样回去？

从乙这一端往回看，每一行处理的都是**对本角色发出的 MESSAGE 的响应**：

| 收到响应的角色 | 收到 2xx 时 | 收到 4xx、5xx 或 6xx 时 |
| --- | --- | --- |
| 终接侧参与功能 | 把收到的 2xx 转给控制功能；此处未要求自行生成 200 | 把错误响应转给控制功能 |
| 控制功能 | 生成 200，发回发起侧参与功能 | 把错误响应转给发起侧参与功能 |
| 发起侧参与功能 | 生成 200，发回客户端甲 | 把错误响应转给客户端甲 |

因此，哪怕甲看到的是 200，也不能倒推出乙侧最初返回的一定是 200。反过来，从终接侧返回的 4xx、5xx、6xx 在这三段按错误转回，不因到达控制功能就改成成功。乙若要确认回电请求，须用另一条 MESSAGE 传递业务答复；若要真的回拨，还须另行建立私呼。客户端怎样区分这几件事，见[回电的业务确认、取消和实际回拨](private-callback.md)。[§11.1.5.3.1 末两段、§11.1.5.3.2 末两段、§11.1.5.4 开头及末两段，印刷页 394–396](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=395)。

**本版有两处文字不能直接当作操作顺序。** 发起侧成功响应段写“步骤 13”发出了 MESSAGE；步骤 13 实际是在加 Accept-Contact，列出发送的是步骤 15。终接侧步骤 5 写出站 INVITE；相邻步骤 4 和 6 分别写生成、发送 MESSAGE。这里保留两处差异，不据此插入一次新呼叫，也不替规范指定勘误或报文实现。[§§11.1.5.3.1–2，印刷页 394–395](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=395)。
