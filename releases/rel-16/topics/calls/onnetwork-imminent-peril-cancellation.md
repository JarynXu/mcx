# 取消在网迫近危险组呼状态：403 的 false 为什么不算取消成功？

在网 MCPTT 预安排组呼正在进行，用户想取消 **迫近危险（imminent peril）** 状态，不是挂断组呼，也不是取消紧急告警。本文限按需会话和该组没有进行中的紧急状态。先对上**原来那笔取消 re-INVITE**，再区分发起端、控制功能（CF）和其他成员收到的消息。

## 发起端先查权限，回包看状态码和正文

客户端按发起用户配置档中 `allow-cancel-imminent-peril` 的 true 或 false 判断已列的授权情形。未授权时，客户端应提示并必须跳过余项。调用取消辅助程序时，用户授权已经核对，且该客户端的迫近危险呼叫状态为 MIGC 3，或它记录的组状态为 MIG 2。客户端发起会话内 SIP re-INVITE，业务正文的 `imminentperil-ind=false`，`session-type=prearranged`，`mcptt-request-uri` 指向组；将客户端记录的组状态置为 **MIG 3**（等待取消结果）。这里对照业务指示和状态，不是完整报文示例。

核对发起端实收的同一笔 re-INVITE 的最终响应：

| 实际响应 | 发起客户端按 §10.1.1.2.1.5 做什么 |
| --- | --- |
| 2xx | 与用户面交互，把组状态设为 MIG 1（无迫近危险），把迫近危险呼叫状态设为 MIGC 1（可发起）。 |
| 4xx、5xx 或 6xx，且满足其一：`imminentperil-ind=true`、未带该元素 | 把本地组状态设为 MIG 2（进行中）。 |
| 4xx、5xx 或 6xx，且正文明确为 `imminentperil-ind=false` | 该节没有给出这组响应的客户端状态迁移。不能套用上两行、填成 MIG 1 或 MIG 2，也不能断言终端以后都停在等待状态。 |

这不是把正文的 false 当成响应成功位。要确定某台终端实际怎么处理第三行，查该终端对本事务的状态记录；不要由客户端显示反推 CF 处理结果。[TS 24.379 V16.14.0，Rel-16 Stage 3，§§6.2.8.1.10–.11，印刷页 67](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=68)；[§10.1.1.2.1.5，印刷页 225–226](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=226)。

## CF 的 403 与实际取消是两条分支

CF 在 §10.1.1.4.7 处理**标识按需预安排组会话**的 re-INVITE；带迫近危险元素时先调用优先请求校验。该入站请求中若有 `imminentperil-ind`，§6.3.3.1.17 要求不同时带 `emergency-ind` 或 `alert-ind`，不合法组合另回 403、Warning 文本编号 150。这与取消权限的拒绝是两项检查。到了第 9 项，存在迫近危险指示且组的进行中紧急状态为 false，才转到 §10.1.1.4.8，并跳过 §10.1.1.4.7 的余项。

在 §10.1.1.4.8 **编号的取消分支**，对收到的 `imminentperil-ind=false`，CF 依发起用户的配置档独立核对 `allow-cancel-imminent-peril`：true 授权；false 或该项缺失不授权。未授权时，CF 回 **403**，在该响应的 MCPTT 正文中写 `imminentperil-ind=false`，然后停止该分支。这个 **403 + false 是拒绝**，不是组状态已改为 false，也不会替发起端补出表中未写的状态迁移。

固定版的文字不能混读：§10.1.1.4.8 开头只写收到 true，编号第 2、3 项却明确处理 false；第 2 项引用的权限辅助条款 §6.3.3.1.13.6 在句中把请求称为 emergency cancellation，标题、入参和判定指向 imminent peril cancellation。这里按 §10.1.1.4.7 第 9 项的入口和编号取消分支读取，不把开头一句改写成通用挑选规则，也不把两类业务合并。[§6.3.3.1.13.6，印刷页 114](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=115)；[§6.3.3.1.17，印刷页 117–118](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=118)；[§10.1.1.4.7 第 2、9 项，印刷页 253、255](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=254)；[§10.1.1.4.8 开头及第 2 项，印刷页 256–257](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=257)。

## 组原本有迫近危险状态，成功取消后按在场与否分发

CF 判定这笔取消获准、且组的进行中迫近危险状态确实为 true 时，将它设为 false，记录该用户不再有未结的迫近危险组呼。**组状态的变化不能从某个成员收到的 false 单独反推**，应查 CF 对本事务的状态变更记录。

- 对**其他正在参加本场呼叫**的成员，CF 按 §6.3.3.1.15 发 re-INVITE。该构造在组的迫近危险确为 false 时使用普通组呼的 Resource-Priority 值，业务正文写 `emergency-ind=false` 和 `imminentperil-ind=false`。CF 实收对应成员腿的 **200** 后与媒体面交互。成员端自己实际收到含迫近危险 false 的 re-INVITE 时，有另一个客户端状态入口，按 §10.1.1.2.1.6 第 4 项设 MIG 1、MIGC 1。入站 CF 的校验不能当作这些发往成员的 re-INVITE 的校验。
- 对**已归属但没参加本场**的成员，CF 发 SIP MESSAGE，正文 `imminentperil-ind=false`。不要拿这份通知当作把对方加进呼叫，也不要用发起端收到的 2xx 代替成员腿的应答或终端实际收音。

§10.1.1.4.8 注 2 提到紧急状态和紧急告警；本处第 3 项的更新和分发按其迫近危险守卫和所引用的构造动作核对。这里不宣布紧急告警已经取消或整场会话已释放。[§10.1.1.4.8 第 3–8 项，印刷页 257–258](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=258)；[§6.3.3.1.15，印刷页 116–117](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=117)；[§10.1.1.2.1.6 第 4 项，印刷页 227–228](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=228)。

若取消对象是[紧急组呼或紧急告警](emergency-group-server.md)，或仍在[新建聊天组呼的优先级纠正](chat-establish-join.md)，查相应入口。处理[离网组呼的紧急降级](offnetwork-group-emergency-downgrade.md)时，不套用本页的 SIP 事务。
