# MCPTT 会话 GRUU 能带组 ID 吗？只看得到 URI，不能判断 XML 是否加密

**运营方要求保护敏感应用数据时，MCPTT 会话身份不得包含被列为敏感的身份信息，包括 MCPTT 用户 ID 和 MCPTT 组 ID。** 例如，把真实组 ID 拼入建呼响应的 `Contact` 会话 URI，再加密消息正文，仍不符合会话身份的要求。这里限制的是承载会话身份的 URI，不是要求把所有 SIP URI 加密或禁止可读域名。[TS 24.379 V16.14.0，§4.5，印 38](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=39)；[§4.8，印 45–46](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=46)。

## 不把组 ID 写进 URI，怎么核对重入的是同一场会话？

会话身份仍是 MCPTT 服务器分配的 **GRUU** 形式的 SIP URI。在各自参与的会话建立时，控制功能（CF）和非控制功能（NCF）分别为本功能分配并托管唯一的会话身份。参与功能（PF）从它们发来的请求或响应的 `Contact` 收到会话身份后，会分配由 PF 托管的身份，写入向客户端发送的请求或响应的 `Contact`。§4.5 明确 PF 为发给客户端与从 **CF** 收到的对应身份维护映射。[§4.5，印 38](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=39)及[印 39](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=40)。

普通按需预安排组呼的重入，客户端把原会话身份放进新 INVITE 的 `Request-URI`；发起侧 PF 向 CF 发送的 INVITE 则使用映射后的身份。比如终端侧采到 `Contact` 给出的 S，CF 侧采到另一值 T，S 与 T 不同不足以判为两场呼叫。要把两段记录对起来，查 PF 这笔会话的映射，不靠从 URI 字符串里猜组号，也不因看到历史 `Contact` 就断言映射仍然有效。完整重入流程见[普通按需预安排组呼重入](rejoin-late-entry.md)；这里不据此生成 ACK、BYE 或配置代理路由。[§10.1.1.2.4.1，印 229](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=230)；[§10.1.1.3.5.1，印 239](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=240)。

## URI 不含敏感身份，是否就证明业务正文受保护？

不证明。**会话 URI 的内容**和**SIP 消息 XML 中敏感字段的机密性**要分开验。前者看会话身份实际包含什么；后者要看这项流程适用的配置、正文中有哪些敏感元素或属性，以及这些字段实际怎样发送。§4.8 的清单还包括位置、紧急／告警／迫近危险指示、含 MCPTT ID 的访问令牌、客户端 ID 和功能别名。§6.6.2.1 说，XML 机密性配置打开时，不能只从 §4.8 所述敏感元素和属性里挑几项保护。即使正文有签名，也不能用签名说明内容已经加密。相反，在 SIP 层能读到一枚不含敏感身份的会话 URI，也不能据此断定正文没有加密。[§4.8，印 45–46](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=46)；[§6.6.1.1–.2，印 138](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=139)；[§6.6.2.1，印 139](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=140)。

这里以第 9–12 章一般流程里的会话信令为例，不拿它替代第 7 章的注册与业务授权保护，也不展开预建立会话 REFER 的专门机密性规则。要判[收到的 SIP XML 签名是否验证通过](sip-xml-integrity-verification.md)，查该独立流程；要辨别[非控制功能在本地重入成功时写入谁的 Contact](noncontrolling-prearranged-rejoin.md)，查 NCF 的接收程序。
