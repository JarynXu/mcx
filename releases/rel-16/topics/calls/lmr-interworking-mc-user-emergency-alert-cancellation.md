# MC 用户撤销互通紧急告警：本机、IWF 和组内客户端分别确认什么？

发起端收到服务器确认后清除自己的紧急状态。它收到的不是 IWF 回执，也不是组内客户端的回执。TS 23.283 V16.8.0 §10.6.5.2 允许服务器先回复发起端，也允许先向 IWF 发撤警请求。[图 10.6.5.2-1、步骤 1–8 与注 2–3，印刷页 140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=141)

### 这条流程从哪里开始？

MC 业务客户端 1 先前已成功发起告警，且仍处于紧急状态。IWF 已掌握该组是互通组的信息（组可由 LMR 或 MC 系统定义），并配置好两侧组和用户身份的映射。示例中的客户端 2 已归属该组；MC 业务服务器可能已为 LMR 用户执行显式或隐式归属，但这不是必经步骤。两系统间经 IWF 的信令由 IWF 做身份转换和协议转换。[§10.6.5.2 前提与注 1，印刷页 139](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=140)

客户端 1 的用户发起撤警，请服务器对先前发过告警请求的同一 MC 业务组发送撤警请求。服务器解析组 ID，判断成员的归属状态，并检查是否要通知 IWF。本例有归属该组且以 IWF 为归属端的成员，IWF 必须参与。撤警请求可以附带取消该组进行中紧急状态的指示；能请求，不等于组状态已经取消。[图 10.6.5.2-1、步骤 1–8 与注 2–3，印刷页 140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=141)

### 三类确认各对应哪条请求？

| 步骤 | 谁发给谁 | 可以核对什么 |
| --- | --- | --- |
| 3 | MC 业务服务器 → 发起的客户端 1 | 服务器确认客户端 1 的撤警请求。流程中客户端 1 随后清除自己的紧急状态。一条确认消息不能证明本机已清除状态，或其他接收方已经收到撤警。 |
| 4–5 | MC 业务服务器 → IWF；IWF → MC 业务服务器 | IWF 代表该组的 LMR 用户归属时，服务器向 IWF 发一条撤警请求。若 MCPTT 服务器收到该组 LMR 用户的逐人归属，则为每位已归属的 LMR 用户向 IWF 各发一条。IWF 向服务器回复，以确认 IWF 撤警请求。 |
| 6–8 | MC 业务服务器 → 已归属该 MC 组的成员客户端；这些客户端 → MC 业务服务器 | 客户端通知各自用户，撤销的是客户端 1 发起的告警。接收客户端向服务器回执；在组播呼叫场景不发送这些客户端回执。这个例外不适用于步骤 5 的 IWF 回执。 |

注 3 只明确步骤 3 和 4 可任一先后。不能凭发起端确认、IWF 回执或某一客户端回执，判断其他接收方的状态、LMR 无线侧处理、组状态或整场组呼释放。LMR 用户通过 IWF 发起的反向撤警见 §10.6.5.1；先前的告警发起过程见 §§10.6.4.1–.2，都不是本节的撤警流程。[图 10.6.5.2-1、步骤 1–8 与注 2–3，印刷页 140](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=141)

若要核对 MCPTT 定义组的两种归属，见[MCPTT 定义组中的 IWF 代表归属和逐人归属](../groups/mc-hosted-lmr-affiliation.md)；若要判断整场互通组呼如何释放，见[整场互通组呼释放](lmr-interworking-group-release.md)。
