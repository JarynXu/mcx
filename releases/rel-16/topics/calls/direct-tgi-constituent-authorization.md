# INVITE 正文直接写 TGI，谁查组成组文档、谁做授权？

Rel-16、Stage 3。这里看的是一笔给 MCPTT 组控制功能（CF）的 INVITE：正文 `mcptt-request-uri` 已是临时组标识 TGI，且 CF 取得与它对应的临时组文档。先按正在处理的这个 INVITE 和 TGI 对齐。原组 ID 找到重组映射、非宿主因此回 302，是[另一个入口](regrouped-group-invite-redirect.md)。

## 有组成组提示和没有提示，先查不同的文档

**有 `associated-group-id`。** CF 核对这个字段所指组成组是否归本机负责（homed）。若归本机，且尚未订阅这一组成组的文档，为它订阅 `xcap-diff`。这里订阅的是组成组，不是再订阅顶层 TGI。若提示所指组成组不归本机，§6.3.5.2(8a) 没有确定一个自动动作：不能因此切到无提示分支订所有组成组，也不能从这项本身推出已经向非控制功能（NCF）发送 OPTIONS。原组入口 (6h) 另有守卫，不套到这里。

**没有 `associated-group-id`。** CF 根据临时组文档中的各项 `constituent-MCPTT-group-ID` 分清每个组成组归 CF 还是 NCF。只为归 CF 且尚未订阅的各组成组订阅文档。此分支的注 6 写明遇订阅错误便停止继续订阅其他组成组，没有规定先查哪个。两种分支中，若实际收到这次匹配文档订阅的 404，则在原 INVITE 回 404/Warning 文本 113 并停止；若实际收到其他 4xx、5xx 或 6xx，则回带 Warning 文本 114 的最终响应并停止。未见文档不是已收到失败响应，114 也不是 SIP 状态码。

**(8c) 另有“本机负责的组成组文档全部已取到”的守卫。** 查本机对应 TGI 的组成组列表、哪些组归本机，以及逐组取得对应文档的证据。发出订阅、订阅成功或拿到其中一份文档，不足以判定全部已取到。文档齐备后，用原 INVITE 正文的 `mcptt-calling-user-id` 核成员资格：任一已取到的本机组成组文档列该用户，退出这一条组文档程序；全不列，则判定需要由 NCF 授权，再退出这一条。不能据此判用户已获准或被拒、要发哪笔最终应答、通话已建立。原文没有裁定提示分支只取一份时如何补齐“全部”、本机无任何组成组时如何执行，或把 CF 的本地缓存视为“全部已取到”的实现规则。

依据：[TS 24.379 V16.14.0 §6.3.5.2(8)，印 133–134](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=134)。只有一条订阅日志时，可先查[组文档是否可用](../groups/mcptt-server-group-document-cache.md)。

## 预安排终止侧实际走到 NCF 授权时，看另一笔 OPTIONS

在预安排组呼的 CF 终止流程里，组文档程序判定需要 NCF 授权，才调用 §6.3.3.1.13.7，并停止继续原终止流程的后续步骤。这个承接点不由某个组成组查询、订阅 200 或成员名单空缺自行触发，也不套用于未调用该程序的其他呼叫。

- **CF 发送 OPTIONS。** 原 INVITE 有组成组提示，则用所提示组成组关联的 NCF 公共业务身份（PSI）；无提示，则对每个不归 CF 的组成组发往其关联 NCF。OPTIONS 的 SIP Request-URI 是该 NCF PSI，正文 `mcptt-request-uri` 是这笔要查的组成组 ID，而非顶层 TGI；正文主叫 ID 沿用原 INVITE。标准在此不规定如何找到该 NCF 的地址。
- **NCF 实际收到 OPTIONS。** §10.1.1.5.4 先看 `P-Asserted-Identity` 标明的发送服务器是否获准提出请求；这不是在查主叫资格。合格才按 OPTIONS 的正文组 ID 查该组成组文档。实收取得的文档或 NCF 本机已有对应缓存是这一步的依据。聊天组按加入规则、预安排组按发起规则判断主叫资格；通过时 NCF 在 OPTIONS 这笔事务上回 200，带 Warning 文本 147、组类型 `session-type` 和 NCF 的 `P-Asserted-Identity`。
- **CF 实收第一份带 147 的 OPTIONS 200。** CF 按实际应答的 `P-Asserted-Identity` 填给原 INVITE 的 302 Contact，按实际应答正文取 `mcptt-request-uri` 和 `session-type`；若已发多笔 OPTIONS，清掉缓存应答并忽略余项。这里不是非宿主从原组文档得 TGI 后回的那种 302。**NCF 正常 200 的构造条文没有列出 CF 要复制的 `mcptt-request-uri`。** 查实际收到的字段；若缺，以上条文不能支持拿 TGI 或组成组 ID 补值，也未规定该缺字段时的继续方式。只见 200/147、发出 302，均不证明下一条呼叫腿或用户入会。

依据：[§10.1.1.4.2(5c)(i)，印 244](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=245)；[§6.3.3.1.13.7，印 114–116](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=115)；[§10.1.1.5.4，印 263](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=264)。

## 多笔 OPTIONS 拒绝：最后收到 403，原 INVITE 为什么回 404？

先对齐同一个原 INVITE 和 CF 发出的多笔组成组授权 OPTIONS。下面的处理按 **CF 实收的应答** 和 **当时是否还预期收到其他 OPTIONS 应答** 区分。抓包里这是最后一条可见应答，不等于 CF 不再期待其他应答。

| CF 实收的应答 | 仍预期其他应答 | 不再预期其他应答时，原 INVITE 怎样回 |
| --- | --- | --- |
| `404` 且 Warning 文本码为 `113` | 缓存这笔 OPTIONS 404。 | 回 `404`，带**本笔** 404 的 Warning。 |
| `403` 且 Warning 文本码为 `106` 或 `109` | 这里的最终响应分支不适用。 | 有缓存 404：回 `404`，带**缓存那笔** 404 的 Warning；没有：回 `403`，带**本笔** 403 的 Warning。 |
| 不属于前列或前述成功分支的其他实收应答 | 这里的最终响应分支不适用。 | 有缓存 404：回 `404`，带**缓存那笔** 404 的 Warning；没有：回 `403`。条文没有要求复制这笔应答的 Warning。 |

例如，甲腿先回 `404/113`，CF 还等乙腿，先缓存甲腿。后来乙腿回 `403/109`，且 CF 已不再期待其他应答：原 INVITE 应回 `404`，Warning 取甲腿，不取乙腿的 `109`。反过来，若没有缓存，且最后实收的是 `403/109`，原 INVITE 回 `403`，Warning 取乙腿。**不是把最后一腿的状态码原样复制。**

§10.1.1.5.4 所列 NCF 否决主叫加入或发起条件时回 `403/119`，不是表中的 `106` 或 `109`。在上述多笔且不再预期其他应答的条件下，它属于「其他实收应答」。无缓存时，CF 按该分支回 `403`，不要把转抄 `119` 当成条文要求。

第一份合格 `200/147` 仍按上面的成功分支回 `302`，多笔时清掉缓存并忽略余项。不能把一次取文档失败或一笔 OPTIONS 的 `404/113` 当成所有组成组已检查的证据；也不把表用于单笔 OPTIONS、全超时或未观察到响应的情况。本条未规定超时如何改变「预期」状态、多笔 404 的缓存取舍或地址发现。

依据：[§6.3.3.1.13.7 的多笔应答分支及注 3，印刷页 116](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=117)；[§10.1.1.5.4，印刷页 263](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=264)。
