# 发起离网紧急组呼：什么时候新建，什么时候接入已有呼叫？

终端发出 `GROUP CALL PROBE` 时还在找这一组有没有进行中的呼叫。若在等待期间收到同组公告，基本呼叫控制可以接入公告里的呼叫；若本机仍在等公告、TFG1 实际到期，才走本机新建分支。紧急类型有一套并行的状态：已存类型是紧急，不等于已经进入 T1。以下限 3GPP TS 24.379 V16.14.0（Release 16，Stage 3）的离网 MCPTT 组呼建立，不是把一通已参加的普通组呼升级。[§10.2.2.4.2.1、§10.2.2.4.3.1–2，印刷页 323–325](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=324)；[§10.2.3.1，印刷页 332](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=333)。

## 按下发起键时，什么条件才把类型预设为紧急？

本机基本呼叫控制在 S1，用户指示发起该组的组呼。终端保存组 ID、创建类型控制状态机，发出带该组 ID 的 `GROUP CALL PROBE`，启动探测重传 TFG3 和等公告的 TFG1，进入 S2。PROBE 报文有消息类型和 MCPTT 组 ID，**没有 Call type 字段**。从 PROBE 本身看不出本机准备普通还是紧急，也不能证明本机已参加通话。[§10.2.2.4.2.1，印刷页 323](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=324)；[表 15.1.2.1-1，印刷页 478](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=479)。

类型控制在 T0 收到用户发起探测的指示时，按**该组**的已存紧急告警状态分两条：

| 本机保存的该组紧急状态 | 什么时候预设为紧急组呼 |
| --- | --- |
| true | 组配置 `/<x>/<x>/Common/AllowedEmergencyCall` 为 true。此分支没有再列用户配置的 `EmergencyCall/Enabled`，也不要求这次发起指示另选紧急类型。|
| false | 用户这次确实发起紧急呼叫，且用户配置档 `/<x>/<x>/Common/MCPTTGroupCall/EmergencyCall/Enabled` 和组配置 `AllowedEmergencyCall` 都为 true。|

命中时终端保存 `EMERGENCY GROUP CALL` 和对应的 ProSe 每包优先级。类型程序还记录当前 UTC 和本机 MCPTT 用户 ID 作为上次变更时刻和变更用户，仍留在 T0。未满足任一紧急选择条件，不能据此断定会拒绝、按普通类型继续或不发 PROBE。基本呼叫的探测入口与类型选择分别规定。[§10.2.3.4.2，印刷页 334–335](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=335)。

这里的紧急状态来自按组维护的告警状态机。符合条件的发警程序会保存该组紧急状态、发送独立的 `GROUP EMERGENCY ALERT`；这条程序本身不建呼。即使此前发过告警，选型也要查本端发起探测时的该组已存状态，不能把历史发送记录当作当时仍为 true。不能把看到 ALERT 当成用户已发起组呼探测、看到 PROBE 当成已发告警，或把告警权限当成建呼许可。[§12.2.2.2、§12.2.3.1，印刷页 457–458](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=458)；[§15.1.16.1 及表 15.1.16.1-1，印刷页 484–485](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=485)。

## 本机仍在 S2、TFG1 到期：如何认出是自己新建的？

本机实际走到 TFG1 到期分支时，停止仍在运行的 TFG3，生成新的呼叫标识与 SDP，选刷新间隔，记录**自己的 MCPTT 用户 ID 为原发起者、当前 UTC 为呼叫开始时刻**。终端发送 `GROUP CALL ANNOUNCEMENT`，其中有这些呼叫字段、组 ID，以及从类型状态取出的当前类型和上次类型变更的时刻、用户。若本机存的是紧急类型，此时公告才把紧急类型传出去。**呼叫开始时刻和类型变更时刻是两个字段**，不能拿新建时刻覆盖探测阶段保存的变更时刻。[§10.2.2.4.3.1，印刷页 324](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=325)。

发送后，基本呼叫程序按本地 SDP 建立媒体会话，以发起话权参与者的角色启动话权控制，启动 TFG6 和 TFG2，进入 S3。并行的类型程序在**本端仍是 T0、实际因 TFG1 到期发出公告、已存类型为紧急**时，按 §10.2.3.4.1.1 启动 TFG13，进入 T1。公式使用的是上次类型变更时刻，不是呼叫开始时刻；发起端此处不以收到对方公告为前提。核实本机发起，应查这次到期、实际发送、新呼叫标识与本机的状态记录。后续已有呼叫的公告也会沿用原发起者字段；公告里有自己的 ID，不单独证明本机走了这次新建分支[§10.2.2.4.4.1 第 1(e) 项，印刷页 327](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=328)。仅有 PROBE 或等待结束，不能证明组内没有别的呼叫，也不能证明其他终端已收到公告、已获话权或听到语音。[§10.2.2.4.3.1，印刷页 324](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=325)；[§10.2.3.4.6(b)、(1)，印刷页 337](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=338)；[§10.2.3.4.1.1，印刷页 334](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=335)。

## 等待时收到同组公告：怎样接入公告里的已有呼叫？

已在 S3 的终端实收同组 PROBE，且已存的探测应答标志为 false，才把 TFG2 改成探测后的短等待并将标志置 true。该端在 S3 等到 TFG2 到期，按既有呼叫记录生成公告；标志仍为 true 则加 `Probe response`，发出后清除此标志，恢复周期计时。应答终端不必是原发起者。该信息元素表示公告是对探测的应答，没有标记是哪一个探测端或哪一次探测，不能用来证明某端收到。[§10.2.2.4.2.3，印刷页 323](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=324)；[§10.2.2.4.1.1.2，印刷页 322](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=323)；[§10.2.2.4.4.1，印刷页 327–328](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=328)；[§15.2.16，印刷页 494](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=495)。

对还在等待的探测端，要分别看两次判断：

- **基本呼叫控制在 S2，实收同组公告。** 入口没有要求 `Probe response` 信息元素。终端停止 TFG3、TFG1，采用公告的呼叫标识、原发起者、开始时刻、SDP 和刷新间隔，不生成自己的新呼叫。终端按所存 SDP 建媒体，以终接话权参与者的角色启动话权控制，启动 TFG6、TFG2，进入 S3。[§10.2.2.4.3.2，印刷页 324–325](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=325)。
- **类型控制在 T0，实收作为探测应答的紧急公告。** 终端设紧急类型和对应优先级，复制公告中的上次变更时刻、变更用户，启动 TFG13，进入 T1。这个紧急接收分支没有再列发起者的两项配置检查。仅知公告同组，不能判定它就是探测的应答。若本端已预选紧急、实际收到的是普通类型，便不满足第 3 项所列“来件与本地都普通”的条件；这并不改写 S2 的同组入口，也不据此规定两套状态机怎样协调。[§10.2.3.4.3 第 1、3 项，印刷页 335–336](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=336)。

## 本端在 S1 收到紧急公告：要按接受吗，要发 ACCEPT 吗？

未参加呼叫的终端在 S1，且没有其他状态机已存相同的组 ID，实际收到紧急公告。这是 S1 的收呼入口，不是本端在 S2 等自己探测应答的入口。§10.2.2.4.3.3 未要求来件带或不带 `Probe response`；该标志也不能证明是本端发起了相应的探测。终端保存公告的组 ID、呼叫标识、原发起者、开始时刻、SDP 和刷新间隔，创建类型控制。**本机配置是否要用户确认**决定是否等待；**公告是否带 `Confirm mode indication`** 才决定基本呼叫分支是否发送 `GROUP CALL ACCEPT`。二者不是同一个确认。[§10.2.2.4.3.3–5，印刷页 325–327](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=326)。

| 接收端配置 | 基本呼叫控制 | 类型控制 |
| --- | --- | --- |
| 要用户确认 | 实收公告后启动 TFG4；有 Confirm IE 等在 S5，无该 IE 等在 S4。用户实际接受后，按所存 SDP 建立媒体会话，以终接话权参与者的角色启动话权控制；S5 发送 ACCEPT，S4 没有发送步骤。随后停 TFG4，启动 TFG6、TFG2，进入 S3。 | 实收公告后保存紧急类型、优先级、公告的变更时刻和用户，仍在 T0。用户实际接受且本地已存类型为紧急时，启动 TFG13，进入 T1。 |
| 不要用户确认 | 实收公告后按所存 SDP 建立媒体会话，以终接话权参与者的角色启动话权控制；只在公告带 Confirm IE 时发送 ACCEPT。随后启动 TFG6、TFG2，进入 S3。 | 实收公告后保存公告的变更时刻和用户、设置紧急类型与优先级，启动 TFG13，进入 T1。 |

收到公告或只看已存类型，还不能证明本机已参加；查本机是否完成相应分支并进入 S3/T1。没有看到 ACCEPT 不能反推用户没接受；发出 ACCEPT 也不能证明别端已收到或已经传送语音。这里不从两套程序推导未规定的执行顺序。[§10.2.2.4.3.3–5，印刷页 325–327](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=326)；[§10.2.3.4.4–6，印刷页 336–337](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=337)。

[普通离网组呼的客户端状态](offnetwork-group-client.md)可用来对照基本状态；紧急分支看本文。已经参加通话、只是改变类型时，分别查[普通转紧急](offnetwork-group-emergency-upgrade.md)或[紧急恢复普通](offnetwork-group-emergency-downgrade.md)。
