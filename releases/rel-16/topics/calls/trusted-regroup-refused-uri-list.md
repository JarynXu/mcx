# 伙伴组 INVITE：预安排组的 403 名单，组成聊天组的初始邀请与并接

先分清组成组类型。预安排组返回 403 时，下面先讲临时组控制功能（CF）能否按伙伴用户名单另发邀请。若 CF 邀请的是**组成聊天组**，分流条件是收件前本地有没有聊天组呼：[尚未开会](#chat-ncf-initial-invite)查准入及初始应答；[已经在通话](#chat-ncf-ongoing-invite)查本组是否选择并接，以及 200 与 ACK 之间还没有完成的角色切换。

## 重组组呼收到 403，CF 何时按伙伴名单发邀请？

控制 MCPTT 功能（CF）向伙伴系统的非控制 MCPTT 功能（NCF）发组 INVITE。在采用查询方法重组时，返回的 403 可能携带供 CF 邀请伙伴用户的名单。不能只看 403 或 `isfocus already assigned` 判定通话结束或可以改发用户邀请。以下两段处理有各自条件。〔TS 24.379 V16.14.0，Stage 3，§§10.1.1.4.1.2、10.1.1.5.2.2，印 241–242、259–260〕

## CF 收到 403：先核齐条件，再按人数上限发邀请

对于发给伙伴组 NCF 的这份 INVITE，§10.1.1.4.1.2 要同时满足：**本地策略允许**；同一 403 的 Warning 文本含 MCPTT 业务编号 **128**；有 **`P-Refused-URI-List` 头**，也有 **`application/resource-lists+xml` 正文**。这里的 128 是 Warning 文本中的业务编号，不是 SIP 状态码。名单中的 MCPTT ID 指向伙伴系统内要邀请的用户。缺头、缺正文、缺 128，或者不符合本地策略，均不能走本节的这条名单分支。只有日志未显示某字段时，先核对完整响应，不能直接判它缺失。〔§10.1.1.4.1.2，403 段及注 1，印 242；§4.4.2 表 4.4.2-2，128 项，印 37〕

满足上述条件后，CF 检查组文档的 `on-network-max-participant-count`。组成员数超过上限时，只从该正文名单中邀请上限所列人数；具体选谁看运营方策略。未超过时，仍按本节用名单中的 MCPTT ID 发邀请。这一条没有规定跨多份名单的去重或排序算法。拿到了名单、发出了用户邀请、被邀用户加入，是三个不同的结果。〔§10.1.1.4.1.2，403 段的后续第 1–2 项及注 2，印 242〕

## NCF 返回 403：有名单与有 128 不能互相替代

下表只限**本组没有正在进行的预安排组呼**，NCF 收到给本组的邀请并到达以下分支。〔§§10.1.1.5.2.1、10.1.1.5.2.2，印 259–260〕

| NCF 查到的条件 | 本节要求它返回什么 |
| --- | --- |
| 根据 P-Asserted-Identity 所标识的主系统，没有互助关系 | 403，Warning 文本编号 128；停止后续步骤。 |
| 有受信任的互助关系、支持所引用的查询程序，且成功取得组成员 | 403，按该条用**已归属成员**填 `P-Refused-URI-List`；发回 CF 并停止后续步骤。 |
| 已进入上述受信任的查询分支，但取成员没有成功 | 403，带 128；发回 CF 并停止后续步骤。 |

NCF **成功**条目明确要求名单头，没有同时写“加 128”；CF **接收**条目却明确检查 128、名单头和资源列表正文。§4.8 也提到 Trusted Mode 的组员通过带名单头的 403 正文返回。不能把这些文字拼成“只要 NCF 查到名单，就一定满足 CF 条件”，也不能推成“成功响应禁止带 128”。若实际完整响应只有 403 + 128 而没有名单，不能借 128 判定名单查询成功；若有名单而完整响应无 128，也不能走该 CF 直接邀请分支。规范没有在这里给出补齐发送端和接收端条件差异的算法。〔§4.8，印 46；§10.1.1.5.2.2 第 4–5 项，印 259–260；§10.1.1.4.1.2，印 242〕

若**预安排**组成组已在通话，另查[已有预安排组呼并接与拆分](prearranged-group-join-split.md)。若收到的是**直接以 TGI 为目标**的请求，查[直接 TGI 的组文档和授权](direct-tgi-constituent-authorization.md)。这两种场景不由这里的 403 名单分支代替。

来源：[3GPP TS 24.379 V16.14.0，Release 16，Stage 3（ETSI），CF 接收 §10.1.1.4.1.2，印 241–242](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=242)；[NCF 生成 §10.1.1.5.2.2，印 259–260](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=260)。

若取到的是临时组会话启动中、NCF 发给 CF 的另一笔 INVITE 的最终响应，读[转出 INVITE 收到非 2xx 时本地临时预安排组呼如何继续](regrouped-local-session-fallback.md)。先核对发请求和回包的方向。

## 组成聊天组还没开会：同一条服务器腿为什么回 403、488 或 200？

临时组控制功能（CF）第一次邀请组成聊天组 A。先查 A 收件前有没有正在进行的聊天组呼，再确认这是 **CF 发给 A 的非控制功能（NCF）** 的请求。终接侧直接按 PSI 路由，SIP Request-URI 是服务该组的 PSI，**请求** Contact 带 `isfocus`。只有属于这类请求且本地聊天组呼未在进行，才按下面的 §10.1.2.5.1.2 处理。已有聊天组可以选择[并接并切换角色](#chat-ncf-ongoing-invite)；若是成员先要求入会，见[A 向 CF 新发 INVITE 时的用户鉴权和两条腿的应答](regrouped-local-session-fallback.md#chat-outgoing)。[§6.3.1.1，印 78](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=79)；[§§10.1.2.5.1.1–.3，印 297–298](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=298)。

| A 的 NCF 查什么 | 这笔 INVITE 的处理 |
| --- | --- |
| 缺少资源而不能处理，或存在拥塞风险 | 可拒绝并回 500，不是必须拒绝。第 1 项把可加 `Retry-After` 的主体写作 CF，不能改读为 NCF 必须带此头。 |
| 收到的 SDP offer 的媒体参数是否可接受、是否提供 MCPTT 语音编码 | 任一条件不满足，回 488。查这笔入站 offer，不查某个手机后来选了什么编码。 |
| `Accept-Contact` 是否列出了 `g.3gpp.mcptt`，以及取值为 `urn:urn-7:3gpp-service.ims.icsi.mcptt` 的 `g.3gpp.icsi-ref` | 任一项缺失，回 403 并停止。该项未要求 Warning 文本 128。 |
| 伙伴系统与主系统之间是否有互助关系；主系统由**该请求**的 `P-Asserted-Identity` 识别 | 没有互助关系，回 403，Warning 文本为 `128 isfocus already assigned`，并停止。128 是文本里的业务编号，不是 SIP 状态码；这句话不是要求再找一个缺失的 `isfocus`。 |

遇到 403，先把响应对回所属的 INVITE。只见状态码，分不开标签缺失和伙伴关系；这节也没让 CF 凭 128 就从名单逐个邀请。上面的预安排组名单规则有另一组接收条件。**这条腿拒绝的是组级邀请，不是组员分别作了拒绝应答。** [§10.1.2.5.1.2 第 1–4 项，印 297](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=298)。

通过前面检查后，NCF 要查入站 INVITE 有没有 `Resource-Priority`；是否给予优先处理是可选的。接下来的先后顺序是：

1. **生成 200，给本次 offer 写 SDP answer。** 应答的 `P-Asserted-Identity` 是 NCF 的 PSI；`mcptt-called-party-id` 写组成组 A 的身份，`floor-state` 写话权状态。响应 Contact 列 MCPTT 和 MCPTT ICSI 两种业务标签。§6.3.4.2.2.2 没把这份服务器间 200 的 Contact URI 指定为 A 给其客户端使用的本地会话身份。已接受的媒体流用 NCF 的 IP 和端口；入站 offer 有且接受的媒体控制通道也用 NCF 的 IP 和端口，并带规定的 `fmtp` 属性。[§6.3.4.2.1，印 128](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=129)；[§6.3.4.2.2.2，印 129](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=130)。
2. **与媒体面交互，等这次处理完成，再把 200 发给 CF。** 第 8 项引用 TS 24.380 §6.3.5；注 2 把处理完成放在第 9 项发送之前。两条本地记录之间有延迟，不足以断定延迟原因；可用同一事务的生成、媒体完成和实际发送记录核对。服务器发出的 200 不是 CF 的收件记录，也不是手机的入会应答、话权授予或语音接收记录。[§10.1.2.5.1.2 第 5–9 项及注 2，印 297–298](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=298)。

要查**临时组会话身份**，看 CF 发来的这笔 INVITE 的 Contact：NCF 反向订阅会议事件时以这里取得的临时会话身份为目标。要查**本地客户端的会话身份**，看 NCF 后来在非控制连接模式下接受组成组客户端加入时，发给该客户端的另一笔 200。不要把这两个身份填回眼前的服务器间 200。[组成组客户端加入及两侧会议订阅](temporary-group-conference-notify.md)；[§10.1.2.5.1.5，印 299](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=300)；[§10.1.3.5.3，印 306](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=307)。

## 组成聊天组已在通话：发 200 前要完成什么，收到 ACK 后做什么？

邀请方向没有变：临时组的 CF 邀请组成组 A 的 NCF，请求 Contact 带 `isfocus`。不同的是，A 正在主持本地聊天组呼。§10.1.2.5.1.1 允许 A 从控制模式切到非控制模式，并未要求每次都切，也没有为“不选择切换”指定响应码。以下是 A 选择按 §10.1.2.5.1.3 并接时的程序，不是成员发起的[另一笔 INVITE](regrouped-local-session-fallback.md#chat-outgoing)。[TS 24.379 V16.14.0，§§10.1.2.5.1.1、.3，印 297–298](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=298)。

**先核这份入站邀请。** SDP 媒体参数不可接受，或 offer 没有 MCPTT 语音编码，回 488。`Accept-Contact` 缺 `g.3gpp.mcptt`，或缺值为 `urn:urn-7:3gpp-service.ims.icsi.mcptt` 的 `g.3gpp.icsi-ref`，回 403；与入站 `P-Asserted-Identity` 所标识的主系统没有互助关系，回 403，Warning 文本为 `128 isfocus already assigned`。后两种拒绝均停止处理。第 4 项的缓存有 Contact 中收到相应内容且支持特定功能标签的条件，不是让 A 把整份 INVITE 无条件存下来。第 5 项要求检查 `Resource-Priority`，是否优先处理由 A 决定。本节没有列出未开会分支第 1 项的可选 500。[§10.1.2.5.1.3 第 1–5 项，印 298](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=299)。

| 同一条服务器腿 | 组成组 A 此时做什么 |
| --- | --- |
| **200 尚未发出** | 第 6 项先生成 200，第 7 项附本次 offer 的 SDP answer。第 8 项再指示媒体面初始化向非控制模式的切换，等这次处理完成。媒体面报告话权状态；若话权已被占用，会提供当前讲话者信息。第 9 项要求在收到讲话者信息时缓存。到第 10 项才把 200 发给 CF。 |
| **A 实际收到对应的 ACK** | 若缓存了当前讲话者信息，按 §6.3.4.1.3 生成 INFO 并发给 CF。无论是否有讲话者缓存，A 都要指示媒体面完成向非控制模式的切换。若本地聊天会话内至少有一个客户端已订阅会议事件，A 还须向 CF [反向订阅会议事件](temporary-group-conference-notify.md)。 |

缓存讲话者与已有会议订阅是两个独立条件。例：A 有讲话者缓存，但本组没人订阅会议事件。收到 ACK 后，A 要发 INFO，也要指示完成切换；这条 ACK 不触发反向 SUBSCRIBE。反过来，只有已有订阅、没有讲话者缓存时，该订阅仍要发起，不因没有 INFO 而跳过。[§10.1.2.5.1.3 第 6–10 项、注 2 及 ACK 后第 1–3 项，印 298–299](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=299)。

这里要保留两个原文回指。TS 24.379 §10.1.2.5.1.3 第 8 项在“初始化”处指向 TS 24.380 §6.5.2.3，ACK 后第 2 项在“完成切换”处写的是 TS 24.380 §6.3.5.3。在本库采用的版本中，[TS 24.380 V16.9.0 §6.3.5.3，印 75](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=76) 讲的是话权控制服务器面向参与者的 `U: not permitted and Floor Idle` 状态，不是并接第二步。媒体面怎样准备、何时开始按非控制模式工作，分别见 [§6.5.2.3.2、.3，印 104–105](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=105)。这是两份规范的条款对照，不据此改写 TS 24.379 的编号。

抓到 200，能定位的是这笔组邀请的成功响应，不是最终切换已经执行；收到 ACK 后发出的完成指令也不是媒体面执行记录。原话权队列如何处理，见[媒体面的并接与交接](../media/merge-floor-queue.md)。讲话者 INFO 通知的是原组状态，不证明临时组已授予其话权、终端已经加入或收到 RTP。
