# MCPTT 私呼查哪个人的 KMS URI？对端专用值和初始配置怎样取舍？

**谁在准备本次私呼密钥，就在谁的配置里按密钥接收者的 MCPTT ID 查 KMS URI。** 甲普通私呼乙，甲查乙；甲发起首接呼叫，乙准备应答，乙查甲。先看本端用户档中与对端匹配的专用项。找不到对端 ID，或该项的专用 URI 为空，才按本条用本端初始配置。不是向对端读它的用户档，也不是按 SIP Contact 的域名选 KMS。

KMS 是管理安全域并为终端提供密钥材料的服务器。PCK 是保护本次私呼的密钥。以下依据 TS 24.379 V16.14.0，Release 16，Stage 3。只讲终端需要确定某个已识别 MCPTT ID 所关联的 KMS URI 时怎样取值。两端的 URI 不同，不能单独证明属于不同安全域。[§6.2.8.3.9，印 76](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=77)。

## 甲、乙各在什么情况下查对方？

| 进入的密钥准备步骤 | 谁在自己的配置里查谁 |
| --- | --- |
| **在网普通一对一按需私呼**，甲发起，且需要建立端到端安全上下文 | **甲查乙**，使用受邀用户乙的 MCPTT ID 及其 KMS URI 为乙准备本次 PCK。[§11.1.1.2.1.1 第 11 项，印 353](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=354)、[续，印 354](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=355)。 |
| **在网按需首接**，乙收到甲的首接 INVITE，且需要建立端到端安全上下文 | **乙查甲**，使用这份 INVITE 的发起用户甲的 MCPTT ID 及其 KMS URI。乙准备了密钥，不等于乙已应答或获选。[§11.1.1.2.1.2 第 5 项及注 4，印 357](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=358)。 |
| **离网普通私呼初建**，甲按程序发起，且需要建立端到端安全上下文 | **甲查乙**，使用受邀用户的 MCPTT ID，按下表的离网配置路径取 KMS URI。本项不是离网首接流程。[§11.2.2.4.2.1 第 1–6 项，印 423](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=424)。 |

用来查询的 MCPTT 用户 ID 属于**这份密钥的接收者**；密钥消息里的 IDRi 属于**消息发起者**。两者不能互换，也不改用 IMS 公共用户身份、客户端实例 ID 或功能别名。[§11.1.1.2.1.1 第 11 项，印 354](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=355)；[§11.1.1.2.1.2 第 5 项，印 357](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=358)。密钥消息在本次 SDP 的哪一边、何时验签，见[普通私呼和首接的 PCK](private-fta-pck-authentication.md)。

## 专用值和初始配置，哪个优先？

| 本终端的工作方式 | 先按对端 MCPTT ID 找用户档 | 对端 ID 未命中，或匹配项的专用 URI 确认为空 |
| --- | --- | --- |
| **在网** | 在 MCPTT 用户档的 `Common / PrivateCallList` 内，找 `PrivateCallURI` 的 `entry` 匹配对端 ID；使用所命中列表条目的 `anyExt / PrivateCallKMSURI / entry` 中的非空值。 | 取本终端初始配置文档的 `on-network / App-Server-Info / kms`。 |
| **离网** | 在用户档管理对象（MO）的 `/<x>/<x>/Common/PrivateCall/UserList/<x>/Entry/MCPTTID` 查对端 ID；读取同一 `Entry` 的 `PrivateCallKMSURI` 叶节点，用其中的非空值。 | 取本终端初始配置管理对象的 `/<x>/OnNetwork/AppServerInfo/KMS`。离网条款也明确回指这里的 `OnNetwork`，不是自行换成 `OffNetwork`。 |

例如，甲查到乙的在网私呼条目，专用值是 A，甲的终端初始配置是 B，这次取 **A**。若甲在完整用户档里找不到乙，或乙那条的专用值确为空，才取 **B**。日志只记录部分字段、导出里没这一列，不能判定为空。该段也没有单列“命中对端但整个专用节点缺失”、URI 格式不合法或连接失败时的处理；不能据此推定试连失败就换 KMS。[§6.2.8.3.9 在网与离网两段，印 76](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=77)。

**查到对端 URI，不等于这次要直接访问对端的 KMS。** 这个 URI 用来识别对端安全域的密钥材料。§4.7.1 描述的是封装密钥的一端事先从自己的归属 KMS 下载各域的材料：普通私呼是甲从甲侧取，首接应答是乙从乙侧取。本次查到的 URI 也不证明材料已经备好、对端已经收到密钥或验签通过。[§4.7.1，普通私呼，印 43](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=44)；[首接段续，印 44](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=45)。即使有呼叫 200，也要核对本次使用的密钥消息和端上处理；要认定实际语音已保护，还须相应的媒体面证据。这条不规定离网时连 KMS 的方法，也不定义密钥服务请求或加密实现。若手头拿的是[组成员配置里的逐业务 KMSUri](../groups/member-kms-uri.md)，那是另一份配置和另一条判定，不是这里的私呼用户档。
