# 紧急组通信怎样发起？组的紧急状态和优先级何时改变？

这是 [3GPP TS 22.280 V16.8.0（Release 16，Stage 1）第 5 章](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=13)的在网、离网共用要求。下文的短号均指 §5.6.2.2.1：[R-5.6.2.2.1-001 至 -009，印刷页 18](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=19)；[R-5.6.2.2.1-010 至 -014，印刷页 19](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=20)。

## 谁能发起，在哪个组？

获授权的组成员可在**当前所选组**或**指定用于紧急组通信的组**发起，业务须支持这两种目标（-001）。业务还须让管理员能够配置某位用户采用所选组还是专用紧急组（-013）。这是选组，不能用“配了哪些 MCX 应用”替代。若一场组通信已经在进行中，业务须能把它**改为紧急组通信**（-005）；不是只能另建一场。

发起紧急组通信**须使该用户进入个人紧急状态**（-003），但**可能触发**而非必然触发该用户的紧急告警（-002）。因此，没看到告警不能单凭这一点排除紧急组通信，也不能用告警是否送达来判断组状态。正文把发起者的个人状态与下文该组的紧急条件分开。

## 优先级比较的是哪类通信？

| 比较 | 同一 MCX 业务内的要求 |
| --- | --- |
| 其他组传输（-004） | 紧急组通信须有最高优先级。 |
| 其他类型的通信（-006） | 紧急组通信的**内容和信令**都须有抢占优先级。 |

两条都排除系统通信、紧急私通信与其他紧急组通信。不能用这两条给例外项排高低，或判断另一项 MC 业务是否也会被抢占。-004 的紧急私通信原文作 `MCX Service Emergency Private Communications`，-006 作 `MCX Emergency Private Communications`。本节的编者注把紧急通信与迫近危险通信的交互留作进一步研究（FFS）；上述优先级不补全这种交互。

## 组的紧急条件从何时维持？

[§3.1（印刷页 10）](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=11)称业务已接受而尚未取消的紧急条件为 **In-progress Emergency**。就这项组条件的维持区间，-012 把起点写成**首次紧急组通信被请求之时**，终点是**组紧急条件取消**。这不把任意请求算作已接受，也没有把起点改成收到第一帧媒体。一场通信停了，不能只因通信结束就判断这个组的紧急条件已取消。

组进入紧急条件时，业务须为该组附加紧急优先级（-008）；该条件取消时须移除与组关联的紧急优先级（-009）。该组通信转为进行中的紧急时，须通知**已归属的组成员**（-010）。这里通知的是状态转变。取消由谁发起、用什么手续，以及个人紧急状态是否同时改变，不能由优先级移除这条推出。

## 已在场或迟入的人应得到谁的身份？

- **紧急组通信发起者（-007）。** 业务须向已归属组成员提供该发起者的 MCX 业务用户 ID，并指明这是紧急组通信。
- **业务掌握的发起成员（-011）。** 业务须知道哪些已归属成员发起了一场或多场紧急组通信，直至组紧急条件取消。这不是保存全体参与者名单，也不要求在通知里列出所有发起者。
- **组紧急状态发起者（-014）。** 组通信仍维持该状态时，业务须把状态发起者的 MCX 业务用户 ID 和紧急组通信标志提供给现有的及迟入的已归属组成员。当前发送者可能已经换人，不能用正在发送的人的身份替代状态发起者。

例如，甲首次发起，乙后来正在发送，丙此时加入仍处于组紧急状态的通信。丙这条要查的是**组紧急状态发起者**及紧急组通信标志。若问题改成丙怎样迟入、应得到当前发送者的哪些信息，组紧急状态的条款没有替代普通迟入规则。
