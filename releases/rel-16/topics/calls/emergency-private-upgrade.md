# 普通私呼升为紧急：CF 已记状态，收到 200 / 149 又确认了什么？

甲、乙正在打一通普通按需私呼。甲要求把**这通**私呼升为紧急，并同时申请发告警。满足缓存条件时，控制功能（CF）须先记下这对用户的紧急状态；这不是乙已经应答。若本次升级走到成功应答、只有告警没有获准，CF 给甲方向的升级应答仍是 200，Warning 文本编号 149 要另查本次应答的 ACK 和同对话 INFO。下面只看 Rel-16、在网、同系统、双方都用按需会话的一对一私呼，不套用新建私呼、预建立承载的 REFER、紧急降级或群呼程序。

## 先把升级请求与原建呼分开

甲通过已有通话发 **re-INVITE**，按紧急私呼程序填 MCPTT 信息正文和 Resource-Priority，并在 SDP offer 中使用已建立的媒体参数。看本次升级的请求和应答，不拿原初始 INVITE 的 200 作升级凭据。以下在 CF **实际收到** `emergency-ind=true` 的 re-INVITE 时判断；终端本地按键或上游日志不证明 CF 收到了该值。[TS 24.379 V16.14.0 §11.1.1.2.1.5，印 361–362](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=362)。

先区分两种失败。CF 先核 SDP，必须至少有一路媒体的参数和至少一种编解码或媒体格式可接受；否则回 488 并停止。随后检验指示组合：当 `emergency-ind=true`，必须**有** `alert-ind`，且**没有** `imminentperil-ind`。缺 `alert-ind` 不是写了 `false`；即使 `imminentperil-ind` 明写 `false`，也仍然带了这个元素。不合组合时回 403、Warning 文本编号 150；这是正文校验失败，不是已准许升级后单独拒绝告警。组合合法还要过紧急私呼权限检查。CF 判定升级请求未经授权时，须回 403，正文的 `emergency-ind` 和 `alert-ind` 都置 `false`，并停止。优先级头本身不能代替授权。[§6.3.3.1.14，印 116](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=117)。[§11.1.1.4.3 第 1–4 项，印 383–384](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=384)；[§6.3.3.1.17，印 117–118](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=118)。

## CF 已记状态，为什么不能算乙已接受？

若已通过相应检查，来件有 `emergency-ind=true`，而甲此前没有与乙的进行中紧急私呼状态，CF **先**缓存这对用户的状态。只有来件明确请求告警且告警也获准，才在这一步再记甲向乙发告警的信息。**然后** CF 为入站 re-INVITE 的 resource-lists 所列收件人另发 re-INVITE。若缺这份列表，不能据此说 CF 应从历史会话或 Request-URI 补出名单：终端升级条款没有单列构造这份列表的步骤。即使已经看到 CF 的缓存写入，也不能代替乙方向应答，更不能证明乙已收到告警。这里不从某侧失败或暂缺应答推定缓存已回滚。[§11.1.1.4.3 第 5–6 项，印 384](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=385)；[§11.1.1.4.5，印 386](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=387)。

## 哪份 200 触发 149？之后查谁的 ACK 和 INFO？

1. **乙方向 → CF。** 查 CF 实收的、与它发往乙方向的 re-INVITE 匹配的 200。发送程序要求 CF 缓存这个响应的 Contact；当 CF 尚未向甲的方向发送本次应答时，接收程序要求生成对来向 re-INVITE 的另一份 200，给来向 offer 作 SDP answer，使用已有会话的当前媒体参数。 两段没规定缓存 Contact 与发送面向甲的 200 谁先。[§11.1.1.4.3 应答段，印 384](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=385)；[§11.1.1.4.5 末段，印 386](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=387)。
2. **CF → 甲方向。** 若来向升级请求明确写 `alert-ind=true`，且告警未获准，CF 给甲方向生成的这份 200 要带 Warning 文本 `149 SIP INFO request pending`。CF 与媒体面交互并发送应答。149 不是 SIP 失败状态，也不是乙方向回复的告警回执。 发起侧参与功能（O-PF）实收这次匹配的 200，须把收到的 Warning 带进自己给甲生成的 200。查甲有没有收到 149，要比对 O-PF 的入、出两份应答。[§11.1.1.3.1.3 应答第 1–6 项，印 376](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=377)。甲实际收到这次升级的 2xx 时先与用户面交互；若客户端私呼状态为 `MEPC 2` 或 `MEPC 3`，按 §6.2.8.3.4 把紧急优先级置为 `MEPP 2`（若尚未是），私呼置为 `MEPC 3`。本地告警仍在 `MPEA 2` 时，有 149 就不能靠这份 2xx 把告警改成已发起；若这一条件下 2xx 不带 149，才按该项置 `MPEA 3`。客户端状态不是被叫实际收警的凭据。[§11.1.1.4.3，印 384](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=385)；[§11.1.1.2.1.5，印 362](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=363)；[§6.2.8.3.4，印 73](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=74)。
3. **与 CF 发出的这份 200 相匹配的 ACK。** CF 实收这份 ACK，且它发出的 200 确实带 149，才按此分支向发起客户端方向在该优先请求的对话里发 INFO。查 `Info-Package: g.3gpp.mcptt-info` 及匹配 MIME 正文中的 `emergency-ind=true`、`alert-ind=false`。这里不是等乙侧的 200 或乙侧的 ACK 来代替，也不套用撤警失败的 INFO。[§11.1.1.4.3 末段，印 384](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=385)；[§6.3.3.1.18，印 118](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=119)。

**CF 发了 INFO，不等于甲已经处理。** 私呼 INFO 辅助程序明确规定，客户端在相应对话实收、满足 INFO 包和正文条件，且告警仍在 `MPEA 2` 时，读到 `alert-ind=false` 则回到 `MPEA 1`。但升级条款末段写的是 Request-URI 标识进行中的“组会话”，却回指私呼辅助程序。保留这个文字差异：先对上实际包和终端进入的程序，再核对告警状态，不把任意 INFO 认作本次结果，也不从服务器发包推定终端一定执行。[§6.2.8.3.7，印 75](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=76)；[§11.1.1.2.1.5 末段，印 362](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=363)。

实际是从无通话开始拨出的，查[紧急私呼初建与告警](emergency-private-call-alert.md)；实际在取消紧急状态，查[私呼降级和撤警](emergency-private-downgrade.md)。两者的响应不能代替本次升级。
