# LMR 与 MC 业务互通：谁发紧急告警，谁回响应？

两种方向都由 **MC 业务服务器**核查发起者对指定组的告警权限。LMR 用户发起时，IWF 把请求送给指定的 MC 业务服务器。MC 业务用户发起时，客户端先请求服务器；本流程中有已归属、由 IWF 服务的组员，服务器须走 IWF 投递。服务器对发起方的确认不等于收警客户端的回执。MC 业务用户发起时，IWF 回给服务器的是另一段响应。[3GPP TS 23.283 V16.8.0，Release 16，Stage 2，§10.6.4.1，印刷页 135–136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=136)；[§10.6.4.2，印刷页 136–138](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=137)。

两图的共同前提是：MC 业务组已在组管理服务器（GMS）定义，图中的 MC 业务客户端 1、2 已归属；IWF 已接入 MC 业务系统并获准互通，已知该组是互通组，且已配置两系统的组与用户身份映射。互通组可由 LMR 或 MC 系统定义。跨系统的信令经 IWF 时由 IWF 做身份转换和协议转换。

## LMR 用户发起

此图从 LMR 用户在 LMR 侧发起告警开始。IWF 可以已显式办理该组归属，也可以尚未办理。**IWF → 指定的 MC 业务服务器**发告警请求；IWF 拿不到该 LMR 用户的位置时，这条 IWF 请求必须标明位置不可用。规范没有说明 IWF 怎样识别 LMR 侧的紧急情况。

服务器核查**代表该 LMR 用户的 MC 业务用户 ID**能否对指定组发起紧急告警，并确定组员的归属状态。图中服务器先回 IWF，确认 IWF 的请求；再向已归属组员的 MC 业务客户端投递。收警客户端另向服务器回执。

步骤 8 只适用于 **MC 系统定义的互通组**：该 LMR 用户尚未归属时，服务器把其个人 MC 业务 ID 隐式归属到紧急组。若 IWF 配置为通过一次归属代表其所有组员，则服务器改归属 IWF ID。此步骤可在步骤 3 后执行，最晚紧接步骤 7（收警客户端回执）执行。[图 10.6.4.1-1 和步骤 1，印刷页 135](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=136)；[步骤 2–8 及注，印刷页 136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=137)。

## MC 业务用户发起

用户 1 发起，客户端 1 向 MC 业务服务器发请求。服务器解析组 ID，确定组员的归属，并检查是否要通知 IWF。图示组内有已归属、由 IWF 服务的成员，**在这个场景下须通知 IWF**。服务器还核查发起用户的 MC 业务用户 ID 对指定组是否有告警权限。服务器回客户端 1 确认发起请求，这不是 IWF 或收警客户端回的响应。

服务器随后向 IWF 投递。拿不到客户端 1 的位置时，**IWF 请求**必须标明位置不可用。IWF 已代表该组的 LMR 用户办理归属时，只发一条给 IWF；IWF 为 LMR 用户逐人办理归属时，经 IWF 向每名已归属的 LMR 组员各发一条。IWF 向服务器回响应，确认 IWF 收到的请求。这个响应不能证明无线侧的每名用户已收到或看到告警。

向 IWF 投递（步骤 5）和向 MC 业务客户端投递（步骤 7）可以任一顺序进行。若发起客户端 1 尚未归属到紧急组，服务器在步骤 10 为它隐式办理归属，可在步骤 3 后执行。条款没有给出隐式归属的有效期。[图 10.6.4.2-1 和步骤 1–9，印刷页 137](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=138)；[步骤 10 及注 3–5，印刷页 138](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=139)。

## MC 业务客户端收到什么

两条过程都由服务器向已归属组员的 MC 业务客户端发送告警。请求必须携带位置、MC 业务 ID、MC 业务组 ID 和发起用户的任务关键组织名称。按组配置，组 ID 指用户选中的组或专用紧急组。用户收到提示后，收警客户端向服务器回告警响应。原文将“位置不可用”的指示写在两种方向各自的 IWF 请求中，没有将它写成 MC 业务客户端投递的兜底规则。[§10.6.4.1 步骤 2、5–7，印刷页 136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=137)；[§10.6.4.2 步骤 5、7–9，印刷页 137](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=138)。

只发告警、没有另行请求发起紧急呼叫，不会把组置于持续紧急状态。发告警也不会让组内其他终端进入紧急状态。若组已处于持续紧急状态，向该组发起的业务组呼按紧急呼叫建立。不能从告警回执倒推该状态或呼叫已建立。两图没有描述告警权限不通过时的响应，也不规定撤警、紧急呼叫建立或具体报文。[§10.6.4.1 注 3、5–6，印刷页 136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=137)；[§10.6.4.2 注 2，印刷页 137](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=138)；[注 4–5，印刷页 138](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=139)。

要查代表归属与逐人归属怎样办理，读 [MCPTT 系统定义组的归属](../groups/mc-hosted-lmr-affiliation.md)。同一 MC 系统内的在网 MCVideo、MCData 发起确认与成员回执，另见[在网组告警的位置和回执](onnetwork-group-alert-location.md)。跨业务的收警对象要求见[紧急告警的通知范围](common-emergency-alert-distribution.md)（Stage 1）。
