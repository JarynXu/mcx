# MCPTT 终端进出预设紧急告警区：200 响应确认了什么？

参与 MCPTT 功能给甲的客户端发了预设紧急告警区的进区通知，随后收到了对这条通知的 SIP 200 (OK)。按照协议，参与功能此时必须记下“甲的客户端已收到进区通知”。不能写成“甲已看到提示”，更不能写成“全组已收到甲的紧急告警”。收区域通知的是甲的客户端；向外发起紧急告警，是另一项程序。

**响应须与那条预设紧急告警区通知对应。** 按 3GPP TS 24.379 V16.14.0，参与 MCPTT 功能判定目标客户端进入或离开预设紧急告警区后，向该客户端发区域通知。通知中的 `emergency-alert-area-ind` 表示方向：`true` 是进入，`false` 是离开。这不是甲当前的紧急状态。客户端收到这类通知，须生成 200 并发往 MCPTT 服务器。参与功能收到对这条预设紧急告警区通知的 200 时，必须按原通知的方向分别记录“客户端已收到进区通知”或“客户端已收到离区通知”。只有出站通知或一条未关联的 200，都不足以作这项判断。[§6.3.2.4.1，引言、步骤 8–9 和末段，印刷页 103–104](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=104)；[§12.1.1.5，步骤 2–3，印刷页 449](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=450)。

**收到预设紧急告警区的进区通知，看甲原来是否处于紧急状态。** 指示为 `true` 时，客户端可以显示进区提示，不要求一定显示。若甲原不在紧急状态，客户端须启动 §12.1.1.1 的紧急告警发起程序；这不以显示提示或甲点击确认为前提。若甲已经处于紧急状态，本进区条款没有要求再次发起。启动程序也不等于发起已经成功或组员已收到告警。[§12.1.1.5，步骤 1a(i)–(ii)，印刷页 449](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=450)。

**收到预设紧急告警区的离区通知，看的是方向，不是解除警情。** 指示为 `false` 时，客户端可以显示离区提示。若甲的本机紧急状态已经置位，离区本身不会将它清除；条文的注说明，是否仍处于危险中由甲判断，需要时甲可以手动清除。离区通知、可选的屏幕提示，以及对这条通知的 200，都不能证明甲已清除本机状态或组员已收到取消告警。[§12.1.1.5，步骤 1b(i)、随后的注和步骤 2–3，印刷页 449](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=450)。

**两份规范回答不同问题。** 上述两条是 Release 16 的 MCPTT 专项协议（Stage 3）。同一 Release 的公共架构 [TS 23.280 V16.7.0 §10.10.1.1，印刷页 176](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=177) 将其在网紧急告警发起、取消程序列给 MCVideo 和 MCData；这些公共程序是否也适用于 MCPTT，该版编辑注明确留待研究。专项条文可以回答甲的客户端怎样处理通知，不能据此把公共流程的适用性改成“已确定”；反过来，公共规范的待研究项也不否定这两条专项协议。

若要查公共 Stage 2 的进出区示例，见[在网紧急告警：进区与离区](emergency-alert-area-entry-exit.md)。若要查用户本人主动发起的独立组告警及其回执，见[独立组紧急告警客户端](standalone-group-alert-client.md)；那里的告警请求响应不是这里的区域通知响应。
