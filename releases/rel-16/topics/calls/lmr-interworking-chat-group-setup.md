# MCPTT–LMR 聊天组呼：加入时谁核什么，什么时候建媒体面？

加入获接受，表示本条请求被接受，响应还带所选媒体参数。**该端请求发话且媒体面尚未建立时，MCPTT 服务器才建立媒体面。** 哪一侧请求发话、谁选参数，要看加入方向和组定义在哪一侧。

这里是 MCPTT 用户加入 LMR 定义的聊天组，或 LMR 用户加入 MCPTT 定义的聊天组。IWF 已配置两系统的组和用户身份映射；跨系统且经 IWF 的信令由 IWF 转换身份和协议。 以下是 3GPP TS 23.283 V16.8.0（Release 16，Stage 2）所列的两条流程。LMR 系统不原生支持聊天组时，IWF 仍可能把其呼叫适配到 MCPTT 聊天组模型；规范未说明如何适配。基础流程回指 TS 23.379 §10.6.2.3.1.2。[§10.3.5.1，印刷页 61](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=62)。

## MCPTT 用户加入 LMR 定义组：先看是否带位置

MCPTT 服务器与 IWF 事先从配置或组创建得知互通组。客户端向 MCPTT 服务器发组加入请求。若请求发话，请求带隐式话权请求指示，并按需带加入方位置。[§10.3.5.2 前提与注，印刷页 61](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=62)；[图 10.3.5.2-1 和步骤 1，印刷页 62](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=63)。

服务器检查是否有位置。**有位置时**，服务器核对请求用户在通话中发言时是否可以分享位置的隐私策略，以决定能否把位置提供给其他 MCPTT 用户和 IWF。服务器据此把请求带位置或不带位置转给 IWF。这是位置转发的门槛，不是组归属核权。IWF 选出媒体参数，把接受结果和参数放在 IWF 组加入响应中回服务器；服务器再转给发起客户端。[§10.3.5.2 步骤 2–5，印刷页 62](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=63)。

## LMR 用户加入 MCPTT 定义组：核对归属权，再看是否已归属

IWF 已从配置获知该组，图中的两个 MCPTT 用户此前已归属该组。LMR 用户发起加入时，由 IWF 向 MCPTT 服务器发 IWF 组加入请求。条款先说加入请求可含发言方位置；接着说，若请求发话，则带隐式话权请求指示和所需的加入方位置。不要替这两句加上“只有请求带了隐式话权指示，才可带位置”的限制。[§10.3.5.3 开头与前提 1，印刷页 62](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=63)；[其余前提、图 10.3.5.3-1 及步骤 1，印刷页 63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=64)。

服务器核对这个 MCPTT ID 是否获准归属该组。成功流程中，尚未归属的 ID 才补隐式归属，已归属不再生成。**这一方向由 MCPTT 服务器选媒体参数**，并在给 IWF 的组加入响应中返回接受结果和所选参数。本节未说明 MCPTT ID 的选法、核权失败响应或该方向的位置隐私规则。[§10.3.5.3 步骤 2–3，印刷页 63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=64)。

## 哪一侧的发话请求触发媒体建立

- **MCPTT 用户加入 LMR 定义组：** MCPTT 客户端请求发话且媒体面尚未建立，由 MCPTT 服务器建立。[§10.3.5.2 步骤 6–7，印刷页 62](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=63)。
- **LMR 用户加入 MCPTT 定义组：** IWF 请求发话且媒体面尚未建立，由 MCPTT 服务器建立。[§10.3.5.3 步骤 4–5，印刷页 63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=64)。

没看到发话请求，不能据此断定原先没有媒体面。两节也没有规定必须另发一条独立的发话请求消息。呼叫期间，MCPTT 客户端和 IWF 对应的话权参与者继续使用话权控制；至少一名用户仍归属时，后续本组呼叫继续使用话权控制方式的媒体面信令。条款没有给出媒体资源一直保留的保证。带隐式话权请求指示也不能证明话权已经授予。

若用户此前正在同一 LMR 宿主聊天组呼，掉线后返回，查[恢复覆盖时重建媒体](lmr-chat-return-to-coverage.md)。[预安排组呼的组员分发](lmr-interworking-prearranged-group-setup.md)和[MCPTT 定义组的显式归属机制](../groups/mc-hosted-lmr-affiliation.md)有各自的适用条件。若要读[普通在网按需聊天组的客户端报文](chat-establish-join.md)，查 Stage 3 主题，不把它当作 IWF 报文定义。这里不收录 §10.3.5.8/.9 已有组呼的晚入，也不处理整场释放。
