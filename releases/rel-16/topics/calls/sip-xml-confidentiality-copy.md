# MCPTT SIP XML 保密保护：怎样区分元素和 URI 属性，转发时能照抄密文吗？

这里核对 TS 24.379 V16.14.0 第 9 至 12 章业务 SIP 请求里，§4.8 所列敏感 XML 数据的保密保护。例如，MCPTT ID 可以在普通业务元素里，也可以在私呼 INVITE 的资源列表 URI 属性里。**不是所有 SIP URI 都是这里的加密对象。** 不拿 Contact、Request-URI 或会话 GRUU 去套 XML 属性的规则。本页不展开第 7 章的注册和业务授权，也不展开预建立 REFER 的内嵌正文特例。

## 先辨部位和保护标志，再查解密结果

| 要检查的值 | §6.6.2.4.1 用什么判定是否受保密保护 |
| --- | --- |
| XML 元素内容 | 元素包含 `EncryptedData`。这只识别保护形态；是否成功还要查解密过程。 |
| XML 属性中的 URI | URI 使用 MCPTT 保密保护专用域名。仅有 `sip:` 前缀或几段看似密文的文本，不能代替这一判定；域名相符也不证明密钥正确或已解密。 |

发送方 §6.6.2.3.4 把受保护属性值包在 SIP URI 内，带 IV 和密钥标识；固定版写 `;key-id=`，接收方 §6.6.2.4.3 对同一字段的描述却写 `;=key-id`。发送侧关于保护域名的引文编号写 TS 23.203，接收侧用 TS 23.003。本页保留两处原样差异，不据此指定部署域名或给出接收兼容规则。

**403 的 Warning 文本编号 140 对应 XML 元素解密程序。** 已进入 §6.6.2.4.2 的元素解密时，若所需的 `EncryptedData` 或其子元素缺失，或解密失败，按该条回 403 并带 140。§6.6.2.4.3 另列怎样恢复 XML URI 属性的值，这条没有列上述失败回包。不能拿 140 认定是 URI 属性解密失败，也不能反过来认定任何实现都不会在其他适用分支回 140。若抓包只显示有 `EncryptedData`，先找接收端的实际处理结果，别把形态登记成成功。

接收端按 §6.6.1.4 先识别和校验已施加的完整性保护；失败就不继续该条的后续程序。之后才检查看元素是否受保密保护并调用解密。该条的总述回引的是元素解密 §6.6.2.4.2，不能仅由总述补出属性解密的错误码；服务器复制程序则为属性单列了 §6.6.2.4.3 的调用。完整性检查失败的 [Warning 文本 139](sip-xml-integrity-verification.md) 不是这里的 140。

依据：[TS 24.379 V16.14.0，Rel-16 Stage 3，§4.8，印刷页 45–46](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=46)；[§6.6.1.1、.4，印刷页 138–139](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=139)；[§§6.6.2.3.4、6.6.2.4.1–.3，印刷页 141–142](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=142)。

## 服务器复制同一业务值，不等于转发同一密文

若收到的 SIP 请求含业务 XML 元素或属性，且该值需要**不作修改地复制**到发出的 SIP 请求，§6.6.1.2 指向 §6.6.2.5。复制程序先按入站值的实际形态识别；对加密值，须解密成功。该程序在选择出站写法时才检查出站保密配置，不用入站配置替代是否加密的实际判定：

1. 对没有 `EncryptedData` 的元素，按第 1 项复制到出站的同一 XML 正文。这个动作不能代替对其中受保护 URI 属性的处理。
2. 对已判为加密的元素或 URI 属性，先用**入站方向**的密钥按各自程序解密。只有成功，才继续处理该值。
3. 若**出站方向**启用了保密保护，用该方向的密钥重新保护同一内容，写入出站的同一 XML 正文。若该方向的保密保护未启用，按该条写入解密后的值。这里描述既有出站配置怎样生效，不建议为便于转发而关闭保护。

| 业务信令的发送方向 | 该段的密钥种类 | 出站保密配置 |
| --- | --- | --- |
| 客户端 → 服务器，或服务器 → 客户端 | CSK／CSK-ID | 分别按 §6.6.2.3.1 或 .3.2 检查 `confidentiality-protection`；true 或缺项启用，false 禁用。 |
| 服务器 → 服务器，同域或跨域 | SPK／SPK-ID | 按 §6.6.2.3.2 检查 `protection-between-mcptt-servers` 下的 `allow-signalling-protection`；true 或缺项启用，false 禁用。 |

例如，入站来自客户端、出站发给另一台服务器，先看是否按 CSK 成功解密，再看服务器间出站配置。若出站启用，按 SPK 重新保护。不要把入站信令已保护当作出站一定已保护，也不要用密文是否逐字相同判断业务值是否保持不变。没有已核实的方向、配置和处理记录，就不能签认转发符合本条。

依据：[§6.6.1.2，印刷页 138](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=139)；[§§6.6.2.2、6.6.2.3.1–.2，印刷页 139–140](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=140)；[§6.6.2.5，印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=143)。

若报文只有一个正文被读到，先查[多正文封装及 SDP 顺序](sip-mime-body-order.md)。若看到的是 [SIP 会话 GRUU](session-gruu-sensitive-identity.md) 而不是 XML 属性，别把该会话 URI 当成密文。
