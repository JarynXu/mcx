# 拆除正在使用的 MCPTT 预建立会话：已发 CANCEL，为什么还要发 BYE？

甲的客户端要求拆掉与参与 MCPTT 功能（PF）的预建立会话。恰好有一通呼叫正在用它建立，PF 为此发了 CANCEL。**如果远端对原来的业务 INVITE 回了 200，且 PF 收到了这个 200，PF 仍须向控制 MCPTT 功能发业务 BYE。** CANCEL 撤销的是尚在建立的请求；远端对 INVITE 的 200 说明它已经接受了这次邀请。发出 CANCEL 不能把已经接受的呼叫当作没有建立。[3GPP TS 24.379 V16.14.0，Release 16，Stage 3，§8.4.2.1 第 1(b) 项，印刷页 166](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=167)；[§6.3.2.1.6，印刷页 87–88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)。

先认准甲想结束什么。甲要拆**整项预建立会话**，客户端在这项会话的 SIP 对话内向 PF 发 BYE，Request-URI 是预建立会话的 URI。如果甲只想**退出其中的一通预安排组呼**，客户端发的是对话外的初始 REFER。Refer-To 指向要退出的业务会话，其中的方法参数是 BYE；请求本身仍然是 REFER。[§8.4.1.1 第 1–3 项，印刷页 165](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=166)；[§10.1.1.2.3.2，印刷页 229](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=230)；[§6.2.4.2，印刷页 60](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=61)。

## 客户端发起拆除：PF 收到 BYE 时，这通业务呼叫在哪里？

| PF 检查到的情况 | PF 应怎样处理 |
| --- | --- |
| 呼叫已建立 | 按 §6.3.2.1.6 将甲从该业务会话移出：与媒体面交互，生成业务 BYE，发往控制 MCPTT 功能。移出的是甲，并非要求其他组员也挂断。 |
| 呼叫还在建立 | 发 CANCEL 取消正在建立的呼叫。若收到远端对原业务 INVITE 的 200，则按 §6.3.2.1.6 释放该业务会话。只有 CANCEL 的发送记录，不能判断远端最终怎样答复。 |
| 没有业务会话在用 | 与媒体面交互，断开面向甲的媒体资源，向甲原来的预建立 BYE 回 200。不需要虚设一条业务 BYE 再等远端应答。 |

这三行取决于业务的使用情况，不是三项连续动作。[§8.4.2.1 第 1(a)–(c) 项，印刷页 166](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=167)。§6.3.2.1.6 说明业务 BYE 发往控制功能，使用 MCPTT 业务会话标识；§8.4.1.1 给客户端原 BYE 指定的却是预建立会话 URI。条款没有给出两者的换算规则，不能直接把后者抄成前者。[§6.3.2.1.6 第 1–6 项及应答段，印刷页 87–88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)；[§8.4.1.1 第 2、3 项，印刷页 165](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=166)。

**沿着开头那通呼叫看三个 200。** 它们状态码相同，回答的问题不同：

1. **远端 → PF，答业务 INVITE**：触发业务释放。这个 200 既不是 CANCEL 的应答，也不是说业务已经释放。PF 此时应发业务 BYE。
2. **远端 → PF，答业务 BYE**：PF 收到它后，须先与媒体面交互，释放面向远端的资源；再与媒体面交互，释放面向甲的资源；随后才向甲的客户端回 200。
3. **PF → 甲，答甲最初的预建立 BYE**：甲的客户端收到这份应答后，还须按 TS 24.380 与媒体面交互。看到了第 2 个 200，不等于看到了第 3 个；看到了 PF 发出第 3 个，也不能据此断定甲已收到并完成媒体处理。[§8.4.2.1 第 1(b) 项及末段第 1–3 项，印刷页 166](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=167)；[§8.4.1.1 第 4 项，印刷页 165](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=166)。

§6.3.2.1.6 的末段把收到业务 BYE 的 200 后回客户端并与媒体面交互的一方称为“终接 MCPTT 功能”（terminating MCPTT function）。上面第 2 步按客户端发起拆除所用的 §8.4.2.1 末段判读，该段写的是参与 MCPTT 功能。称谓不同，不足以判定是同一实体还是另一个实体，也不表示应向客户端再回一份 200。[§6.3.2.1.6 末段，印刷页 87–88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)。

## 换成 PF 发起拆除：两个方向的 BYE

PF 须先释放**所有使用这项预建立会话的呼叫中的相关参与者**。它与媒体面交互，以业务会话标识为 Request-URI，向**控制 MCPTT 功能**发业务 BYE；对业务 BYE 回 200 后，第 1(f) 项写的是收到该应答时由**终接 MCPTT 功能**与媒体面交互；发出业务 BYE 的主体则是发起拆除的 PF。原文这处称谓不足以判定两者是同一实体还是不同实体。如果没有呼叫在用，就没有这一步要释放的参与者。这里没有要求终止同组其他人的通话。[§8.4.2.2 第 1(a)–(f) 项，印刷页 166](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=167)。

接着 PF 以**预建立会话 URI** 为 Request-URI，在**预建立对话内**向**甲的客户端**发另一条 BYE。收到甲对这条 BYE 的 200 后，PF 须与媒体面交互。若有多通呼叫在用，前一段说的是各有关业务，不是整次拆除固定只会出现两条 BYE。[§8.4.2.2 第 2–5 项，印刷页 167](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=168)。

甲收到 PF 的预建立 BYE，也要检查还有没有呼叫在用。有已建立的业务会话，甲须按 TS 24.380 逐会话退出；无业务会话使用时，甲断开面向 PF 的媒体资源，并对收到的 BYE 回 200。**客户端这一段没有规定“建立中就发 CANCEL”**，不能把 PF 收到客户端 BYE 时的规则倒过来套用。上述条款指向 TS 24.229 的 SIP 程序和 TS 24.380 的媒体程序，本页不推导未列出的超时或响应，也不凭一条记录判断双方已清理完毕。[§8.4.1.2 第 1、2 项，印刷页 165–166](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=166)；[§8.4.2.1 第 1(b) 项，印刷页 166](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=167)。

若要查最初怎样建立这项会话，或没有业务使用时怎样修改、释放，见[预建立会话的生命周期](preestablished-session-lifecycle.md)。若只想挂断某通普通私呼，见[私呼释放与预建立会话的区别](private-client-release.md)。若关心各种 MC 业务共用的 Stage 2 流程，以及改为非活动和释放有何不同，见[修改媒体与释放整项会话](../bearers/common-preestablished-media-change-release.md)。[结构化条件与声明](preestablished-session-in-use-release.json)。

若客户端没有发预建立对话内的 BYE，而是用 REFER 退出一通已经建立的预安排组呼，见[预安排组呼离会的 REFER 200 与控制侧 BYE](prearranged-participant-refer-leave.md)。它解释应答为何先于业务 BYE，不能照本页把预建立会话整体拆掉。
