# 在网 MCPTT 普通私呼：挂断一次通话，会拆掉预建立会话吗？

不会因为这次挂断就自动拆掉。预建立会话是客户端与服务它的参与 MCPTT 功能（PF）之间预先建好的会话；一次私呼可以使用它，但两者不是同一个释放对象。下面区分三件事：用户要求挂断，客户端实际收到私呼的 BYE，以及终接侧 PF 收到控制 MCPTT 功能（CF）的 BYE。依据是 3GPP TS 24.379 V16.14.0（Release 16，Stage 3）；不涉及服务器主动发起的私呼释放或离网私呼。

## 用户挂断按需私呼：看当时是否仍在建立

- **仍在建立：**客户端按 TS 24.229 发送 SIP CANCEL，到此跳过本释放程序余下步骤，不再按本分支与媒体面交互或补发 BYE。
- **已经建立：**客户端先按 TS 24.380 与媒体面交互，再按 TS 24.229 生成 SIP BYE，把 Request-URI 设为**待释放的 MCPTT 业务会话身份**，向 MCPTT 服务器发送。不是发给被叫用户的个人身份。

这里描述的是挂断方发什么；如果要判断接听方在 INVITE 最终应答前收到 CANCEL 后怎样应答，见[普通私呼的客户端应答](private-client-answer-evidence.md)。依据：[§11.1.3.1.1.1，印刷页 388](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=389)；[§6.2.5.1，印刷页 60–61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=61)。

## 主叫 BYE 已获 200，被叫也已挂断吗？

不能凭这个 200 判断。以主叫挂断为例：这是一通**已经建立的普通按需私呼**，同系统内的两个用户以 MCPTT ID 直接呼叫，通话有话权控制，不用预建立会话。把主叫称为**挂断方**，被叫称为**接收方**。下面的“发起”和“终接”指这次释放请求的方向；每个 200 都要与它应答的那一份 BYE 配对。

1. **挂断方终端 → 本侧参与功能（PF）→ 控制功能（CF）。** 终端按上一节发送 BYE。本侧 PF 实际收到它，先与媒体面交互，再生成一份发给 CF 的 BYE。新请求的 Request-URI 取来件中的 MCPTT 业务会话身份；PF 复制来件的 P-Asserted-Identity，来件含有 application/vnd.3gpp.mcptt-info+xml 正文时也复制该正文。收到**发往 CF 的这份 BYE** 的 200 后，§6.3.2.1.6 末段规定向客户端转送 200，并与媒体面交互以释放与 CF 的 SIP 会话所关联的媒体资源。该节起首写参与功能，末段原文称 *terminating MCPTT function*；这一称谓不把该响应变成接收方终端的 200。[§11.1.3.2.1.1，印刷页 389](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=390)；[§6.3.2.1.6，印刷页 87–88](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=88)。
2. **CF 先答复挂断方，再决定是否释放其余参与者。** CF 收到 BYE，先就面向该客户端 SIP 会话的媒体资源与媒体面交互，生成并向挂断方方向发送这笔请求的 200，**然后**才检查私呼释放策略。在本例中，若会话只剩一名或没有参与者，CF 必须释放私呼；不要求先等 T4 到期或等到通话超时。还有对端需要移出时，CF 按发送 BYE 的程序与媒体面交互，生成并向该对端发送**另一份** BYE。如果入向 BYE 含有上述 MCPTT 信息正文，须复制到出向 BYE。CF 实际收到出向 BYE 的 200 后，还要就相应参与者 SIP 会话的媒体资源与媒体面交互。这里不套用组呼的 TNG3 或向全组发送 BYE 的规则。[§11.1.3.3.1，印刷页 389](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=390)；[§6.3.3.2.4，印刷页 121](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=122)；[§6.3.8.2，印刷页 136](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=137)；[§6.3.3.1.5，印刷页 106–107](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=107)。
3. **CF → 接收方 PF → 接收方终端。** 接收方 PF 实际收到 CF 的 BYE，先与媒体面交互以释放 **CF 一侧** SIP 会话关联的媒体资源，再生成发给本端用户的新 BYE。PF 复制 P-Asserted-Identity；若来件含上述 MCPTT 信息正文，也须复制。终端**实际收到**这份 BYE，才按 §6.2.6 与媒体面交互并向服务器回 200。PF 收到**对自己发给终端的 BYE** 的 200 后，须先向 CF 回 200，应答原先从 CF 收到的 BYE，再就**终端一侧** SIP 会话的媒体资源与媒体面交互。[§11.1.3.2.2.1，印刷页 389](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=390)；[§6.3.2.2.8.1，印刷页 102](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=103)；[§6.2.6，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=62)。

判断“被叫已挂断”，先问要证明什么。要证明被叫终端处理过释放请求，核对它收到的 BYE、对应的 200 及其本地媒体交互记录。若还要判断媒体资源已回收，须看相应资源的释放结果。主叫腿的 200 不等待这些事件；一处没有抓到远端的 BYE，也不能反推远端没有收到。

## 私呼使用预建立会话：BYE 写在 REFER 里

用户只要求结束这次私呼时，客户端先按 TS 24.380 与媒体面交互，再生成一个**在 SIP 对话之外发起的初始 REFER**，按 TS 24.229 发送。读报文时分清三个位置：

| 位置 | 指向什么 |
| --- | --- |
| Request-URI | 标识该预建立会话的公共服务身份，位于服务此用户的 MCPTT 服务器上。 |
| Refer-To | 待释放的 **MCPTT 业务会话身份**，在这个 URI 内设置参数 `method=BYE`。 |
| Target-Dialog | 标识已存在的**预建立会话**。引用了该对话，不等于 REFER 在该对话内发送。 |

REFER 还必须带 `Refer-Sub: false` 和 `Supported: norefersub`。客户端实际收到**这个 REFER 的 2xx** 后，再按 TS 24.380 与媒体面交互。这个响应不是对预建对话内 BYE 的应答，也不证明对端已经收到 BYE。若要判断客户端何时主动拆除**空闲的预建立会话本身**，见[预建立会话的生命周期](preestablished-session-lifecycle.md)中的 §8.4。

依据：[§11.1.3.1.2.1，印刷页 389](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=390)；[§6.2.5.2，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=62)。

## 谁收到了 BYE？

**客户端实际收到私呼的 SIP BYE：**无论本地是按需私呼，还是使用预建立会话，客户端都按 TS 24.380 与媒体面交互，然后按 TS 24.229 向 MCPTT 服务器回复 SIP 200 (OK)，应答**刚收到的 BYE**。这里的入口是客户端收到了该请求，不能仅凭另一端挂断就认定这个事件已经发生。[§11.1.3.1.1.2、§11.1.3.1.2.2，印刷页 388–389](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=389)；[§6.2.6，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=62)。

**终接侧 PF 收到 CF 的 SIP BYE：**如果业务会话 ID 指向的用户与该 PF 有预建立会话，PF 先通过媒体面断开面向 CF 的媒体资源，向 CF 回 200 (OK)，再通过媒体面把面向客户端的资源与面向 CF 的资源断开。PF **必须保留面向该客户端的预建立会话**。这里的 200 是 PF 发给 CF 的，并非客户端对 BYE 的应答；本分支也没有要求 PF 把这个 BYE 转发给客户端。[§11.1.3.2.2.2，印刷页 389](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=390)。

这些条款区分信令和媒体面的交接点，不给出所有资源释放完毕的确认，也不保证预建立会话今后不会因其他原因被释放。

若要追到媒体面，见[Disconnect 的确认、重试到限与本地状态](../media/preestablished-release-outcome.md)。

若现场是已经建立的在网按需环境监听，不走本页普通私呼的挂断判断；查[环境监听的停止权限、BYE 与定时器](ambient-call-release-evidence.md)。
