# 临时组呼的 conference 事件退订：最后一个订阅结束后，哪条链路才停？

临时 MCPTT 组呼还在进行，甲向控制功能（CF）退订会议事件包，收到 `200 OK`，乙仍在订阅。这个 `200` 只回答甲的退订请求，CF 不能据此把给各非控制功能（NCF）的订阅一并撤掉。等这场通话在 CF 侧没有剩余订阅，无论最后一笔是主动退订还是订阅计时器到期，CF 都须终止它在本临时组会话中所有 NCF 上的 conference 事件订阅。[TS 24.379 V16.14.0，§10.1.3.4.4，印 305](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=306)

## NCF 上只剩 CF 建立的反向订阅，是否还要保留 NCF → CF？

**不用。** 在 NCF 侧，统计剩余订阅时不计由 CF 建立的订阅。若最后一个本地订阅主动结束或到期，即使 NCF 仍保有 **CF → NCF** 的订阅，也须终止 **NCF → CF** 的订阅，也就是终止自己在 CF 上建立的订阅。NCF 收到主动退订的 `SUBSCRIBE` 时须回 `200 OK`；计时器到期是独立分支，不是收到另一笔退订请求。[§10.1.3.5.4，印 307](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=308)

NCF 不因这一步代 CF 撤掉 **CF → NCF**。若 CF 还有别的订阅者，这个方向不满足 CF 的清理条件；若 **NCF → CF** 恰是 CF 侧的最后一笔，CF 处理其终止后才按自己的条件清理各 NCF 上的订阅。两端的“最后一个”按各自的订阅记录判，不是数这一对服务器还连着几条链路。[§10.1.3.4.4，印 305](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=306)；[§10.1.3.5.4（含注），印 307](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=308)

## 抓到退订的 200，怎样确认哪边真的停了？

先对上临时会话、发起订阅的一端和收订阅的一端。**CF → NCF** 指 CF 发起、在 NCF 上建立的订阅；**NCF → CF** 则相反，两边建立时各用新的 SIP 对话。再看对应一端还有哪些有效订阅，以及相应会话的订阅对话有没有终止记录。只看到给某一笔退订的 `200`，缺另外几个订阅对话的记录，不能给所有方向验收。若验收的是通话结束，这些步骤终止的是事件订阅，不是让参与者退组，也不证明组呼已释放。[§10.1.3.4.3–.4，印 304–305](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=305)；[§10.1.3.5.3–.4，印 306–307](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=307)

如果还没弄清调度端是在拉一次快照，还是订阅后续变化，从[会议事件包的查询、订阅与参与者状态](conference-participant-status.md)查起。若工单其实在验收聊天组通话中的单人退出或全会话释放，查[聊天组的离开与结束](chat-participant-or-session-release.md)。
