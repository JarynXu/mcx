# MCPTT 新会话的隐式话权请求：主叫何时可以提前发 RTP？

服务器要分两次判断：这份信令是否在请求话权，收到受邀侧反馈后是否提前允许主叫发媒体。请求、排队和发送许可是三项不同的结果。

适用于 3GPP TS 24.380 V16.9.0（Rel-16，Stage 3）中，控制 MCPTT 功能侧在新 SIP 会话建立带话权控制的组会话或私会话时的初始化。组聊建立和重入只在明确注明的识别规则中讨论。

主体是话权控制服务器；受邀侧参与 MCPTT 功能提供指示，受邀客户端接受邀请或媒体，邀请方客户端（主叫）获得许可后发送 RTP。涉及缓存时，保存收到的包的是 MCPTT 服务器。

## 收到初始 INVITE 或 REFER，算不算请求话权？

适用：初始 SIP INVITE 或 SIP REFER 用于建立 MCPTT chat 组呼，或用于重入正在进行的 MCPTT 呼叫。

在这两种用途下，除非请求中明确表示要请求话权，话权控制服务器不把该请求按隐式话权请求处理。区分“初始”与“初次通话”：重入也可能有初始请求。明确表示的是请求意图，不是授予。

不要把这条服务器入口规则反用为客户端构造许可。对重入进行中组呼的 INVITE，§6.2.1 从话权参与者侧明确不视为隐式请求。对 SDP offer，§14.3.5 的服务器一般接受规则另排除了加入 chat 组呼或进行中的预安排呼叫。不能只凭 mc_implicit_request 就断定这些加入、重入都可以按普通初建流程取得话权。

依据：§6.3.2.1（印刷页 51、52）；§6.3.2.2（印刷页 52）；§6.2.1（印刷页 35）；§14.3.5（印刷页 240）。

## 协商了排队，初始化请求一定要入队吗？

对于已识别的隐式话权请求，如果支持且已按第 14 章协商 mc_queueing，服务器可以把请求排队，并非必须入队。组呼还要看组配置：音频切入（audio cut-in）组不允许排队。仅有排队能力不能替代协商，实际入队也不是发言许可。

同一条款末段另谈显式 Floor Request 消息：支持并协商排队、另一参与者持有话权且其优先级等于或高于请求者时，适用显式请求的入队规则；音频切入组仍不得排队。不能据此把初始化的隐式请求改写成相同条件下必排。

依据：§6.3.2.2（印刷页 52）。

## 被邀侧首次给出未确认指示，主叫就能发 RTP 吗？

因隐式请求给予主叫发送媒体的许可，既适用于确认指示，也适用于未确认指示。话权控制服务器收到受邀侧参与功能的第一个未确认指示时，若 MCPTT 服务器支持且允许缓存媒体，可以向主叫给出提前发送 RTP 的指示。只观察到被邀侧的未确认指示，还不知道服务器是否向主叫给了早期许可。服务器若给出了早期发送指示，主叫的话权参与者此时即获发送许可；MCPTT 服务器缓存从该客户端收到的 RTP 包，至少持续到首个受邀客户端接受邀请，或 RTP 包缓存超过其上限。

早期许可只说明主叫可以发送；不证明某个被邀用户已经接受邀请、已经收到或听到语音。这里列出缓存的最低持续条件；没有指定缓存大小、溢出后怎样处置，或何时向哪些客户端转发。

依据：§6.3.2.2（印刷页 52）。

## 不支持缓存，和支持但不允许缓存，有区别吗？

这里以服务器已识别出主叫的隐式话权请求为前提；在这两种缓存条件下，均不给主叫早期 RTP 发送指示。首个受邀 MCPTT 客户端接受媒体时，才授予主叫的话权参与者发送许可。受邀侧给出的首个未确认指示不能取代接受媒体。注意这里判断的是“接受媒体”；前一分支的缓存条款写的是“接受邀请”。

不能倒推：即使有缓存能力且允许使用，服务器仍可不发早期指示。只看见没有早期指示，不足以诊断服务器没有缓存能力；本条款也没有为“可以缓存但未给早期指示”的分支单独指定授予时刻。

依据：§6.3.2.2（印刷页 52）。
