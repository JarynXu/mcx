# 普通在网话权：客户端请求、排队确认与释放

- 固定 TS24.380 V16.9.0，在网且采用话权控制的普通客户端；限非ambient、非broadcast、非dual/multi-talker、非抢占业务，不展开紧急/迫近危险/system call、audio cut-in或预建立承载建立。
- 客户端当前状态与收到的用户指示、控制消息、媒体、计时器或信令层事件共同决定动作；各claim事件是替代入口，失败、撤回及释放不以已经获准发送为前提。
- 必要的呼叫控制边界仅以TS24.379 V16.14.0实际入口作比较；不复制另一Release规则，不宣称完整媒体、安全或外部RFC实现。

## 通话建立、隐式请求和获准是三件事

- 条件：应用层发起或完成普通在网通话、重入既有通话，或协商媒体控制通道；各入口分别适用。

媒体控制通道通过 SDP 协商，以 UDP/IP 上的 RTCP APP 承载。m=application 的端口是控制通道 RTCP 端口，不与其他 m-line 的 RTCP 端口混用。支持排队时在 offer 带 mc_queueing；answer 仍受不得增加 offer 未有参数的通用规则约束。初始 INVITE 可接受在200中获知授权时，客户端带 mc_granted；它不代替 Floor Granted 的基本操作。服务器仅在 offer 有此参数且决定以200授予隐式请求时，在 answer 带 mc_granted；临时组会话不得用此方式指示获准。mc_implicit_request 表达隐式请求意图，不表达已经获准。客户端按协商创建话权状态机：主叫在200之前收到控制消息先保存；建立的呼叫使用隐式请求时启动 T101、置 C101=1、进入 pending Request，再按该状态处理保存的消息。非隐式请求的 chat 建立及重入分别进入 has no permission；被叫建立也进入 has no permission。因此普通 SIP 200、能够收听或已经入呼都不是发言许可。

规范强度：控制通道构造、客户端状态及条件保存为 SHALL；服务器选择通过200给出授权为 MAY，临时组禁用该指示为 SHALL NOT；未被明确要求的隐式请求选用为 implementation option。
- 边界：仅在已采用话权控制的通话中应用本页；无话权私呼/FTA、预建立会话控制、临时组和特殊优先业务不在本页展开。
- 边界：TS24.379 §6.4 指向24.380 clause12，固定24.380的clause12是SDP语法，协商程序在clause14；保留引用层次，不将其改为另一版条款。24.380 §14.3.5 对加入chat或进行中预安排呼叫另列例外，§6.2.1又明确重入不算隐式请求；不以普通初始INVITE规则覆盖这些入口。
- 边界：§6.2.4.2.2 未在该段给出所有非chat、非隐式主叫组合的统一初态，本页不补默认分支。安全要求仍按§6.1调用clause13，不因话权状态满足而省略安全处理。

依据：3gpp-ts-24.380-v16.9.0 §4.3.1–4.3.3.1 / 6.1–6.2.4.2.3，印刷页 31,32,34,35,36,37；3gpp-ts-24.380-v16.9.0 §14.1–14.4 (14.2.6/14.3.7 comparison only)，印刷页 237,238,239,240；3gpp-ts-24.379-v16.14.0 §6.4 initial INVITE and other (re-)INVITE classification; REFER comparison only，印刷页 136,137。

## 语音能收，话权控制报文走哪个地址和端口？

先读**承载话权的媒体控制段**。在协商建立这个通道的 SDP offer 中，找 `m=application <端口> udp MCPTT`。这行写的端口就是供控制通道的 RTCP APP 使用的端口；别把它当作语音 RTP 端口，也别在它的基础上再加一找控制 RTCP。[3GPP TS 24.380 V16.9.0，Rel-16，§4.3.2、表 4.3.3.1-1 及注 1，印刷页 31–32](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=32)。

**核对端口冲突，要拿它和其他媒体段的 RTCP 端口比。** 假设这份 SDP 的语音 `m=` 行写 41000，另有证据确认语音 RTCP 用 41001。话权控制段若也写 41001，就违反该款要求的 RTCP 端口分离。若写 41000，不能因为它与语音 RTP 一样就按该款判为 RTCP 端口冲突；也不能凭这点断言这个 RTP/RTCP 端口组合可用。要把控制端口同这份 SDP 其他媒体段对应的 RTCP 端口都核对一遍，不用音频行上那个 RTP 数字代替它们。[§4.3.3.1 表后正文及注 1，印刷页 32](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=33)。

**控制通道如果用另一个 IP，连接地址跟控制段走。** 此时控制 `m=` 段需要关联自己的 `c=` 行；只有归属音频媒体段的 `c=` 行，不能声明另一个控制 IP。该注没有要求控制和其他媒体同 IP 时也一定为控制段单列 `c=`。查报文是否走对地址时，记清本端、对端和哪个媒体段，不用已经收到了语音来补上没抓到的控制通道证据。[§4.3.3.1 注 2，印刷页 32](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=33)。

**控制媒体行和 `fmtp` 是两项检查。** 协商建立媒体控制通道的 offer 必须带这条 `m=` 行；按一般规则可以附 `fmtp`。具体能力仍有各自条件，例如客户端支持话权请求排队时，offer 必须带 `mc_queueing`。没看到 `fmtp` 不等于没声明控制媒体段。找这个通道的初次 offer 也不必局限在初始会话的第一份 SDP；只看到一份 offer，不能确认对端已接受、实际收到了 RTCP APP 或允许本端发言。[§§14.1、14.2.1–2，印刷页 237–238](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=238)。

## 请求尚未授权，拒绝和重试耗尽均可返回无权限

- 条件：处于 has no permission 收到用户申请发送指示；或处于 pending Request 收到响应、媒体或 T101 到期。事件分别适用，不以请求获准为前提。

用户请求时发送 Floor Request，启动 T101、置 C101=1，进入 pending Request。请求的 Location 字段须存在；位置不可用或配置不准上报时类型为0，否则按允许的实际位置编码。若使用不同于普通值的优先级，值不能超过协商上限。pending Request 收到 Floor Granted 或 SIP 200 中明确的 floor granted indication 时，按消息要求回 Ack（Message Type=1、Source=0），尚未通知时通知获准，停止运行中的 T103 和 T101，进入 has permission。收到 Deny 时按要求回 Ack（3、0），提示拒绝，可显示原因，停止 T101，进入无权限。T101 未到 C101 上限时重发请求、重启计时并将计数加1；达到上限时提示请求超时并进入无权限。收到他人 RTP 须请求播放但不因此获得发送权；收到 Floor Taken 在本页普通非抢占范围回到无权限，不能把它当作本用户的 Granted。

规范强度：发送、状态转移、条件Ack、拒绝和超时通知为 SHALL；显示拒绝原因是 MAY；接收媒体时启动可选T103为 SHOULD；请求重传总时长小于6秒为 SHOULD。
- 边界：C101 默认上限3，不是额外再重传3次；T101 的实际时值由配置决定，本页不编造统一毫秒数。
- 边界：计时器表把 Floor Taken、Queue Position Info、他人 RTP 等列为 T101 正常停止事件；§6.2.4.4.7 接收RTP步骤仍写保持 pending Request，§6.2.4.4.11另写条件停止T100而非T101。保留表与事件正文各自措辞，不把停表等同于获准或静默改成统一状态算法。
- 边界：§14.3.3 的非默认优先级上限取请求值、组用户优先级、服务层级数量的最低值，并对 on-network-recvonly 另作处理；本页不实现配置获取或借默认值解除接收限制。

依据：3gpp-ts-24.380-v16.9.0 §6.2.4.3.1–6.2.4.3.6 / 6.2.4.4.1–6.2.4.4.7 / 6.2.4.4.11，印刷页 37,38,39,40,41,42；3gpp-ts-24.380-v16.9.0 §8.2.2.1 / 8.2.3.21 / 8.2.4，印刷页 147,148,159,160,161,162；3gpp-ts-24.380-v16.9.0 §11.1.1 table11.1.1-1;11.2.1 table11.2.1-1 / 14.2.3;14.3.3，印刷页 212,213,222,223,238,239。

## 排队获准后还要用户确认，查询超时与确认超时不同

- 条件：pending Request 收到 Queue Position Info；或已在 queued 收到控制消息、队列查询指示、用户确认/撤回、T104/T132 到期。

首次收到 Queue Position Info 时按要求 Ack（9、0），通知已排队，可显示位置/优先级，进入 queued。queued 中收到 Granted 按要求 Ack（1、0），提示获准，停止运行中的 T104，在本页非dual范围停止相应运行中的 T103，启动 T132，但仍留 queued。只有用户表示要发送且 T132 正在运行，才停止 T132 并进入 has permission。T132 到期则发送 Release，可提示不再可用，直接进入 has no permission。查询位置时发 Queue Position Request、启动 T104、置 C104=1；未达上限重发并递增，达到上限提示队列超时、发 Release并进入 pending Release。queued 中收到更新的位置消息停止运行中的 T104并留 queued；收到 Deny 或 Idle 则按要求 Ack，停止运行中的 T104并进入无权限。用户主动撤回 queued 请求则发 Release，启动 T100、置 C100=1，停止运行中的 T104及T132，进入 pending Release。

规范强度：所列发送、条件Ack、计时/计数、通知及状态动作为 SHALL；排队能力支持、位置/原因/失效提示以及Release请求Ack为 MAY；queued接收媒体时重启T103为 SHOULD。
- 边界：排队是可选能力，audio cut-in组不进入queued；本页不强迫所有呼叫支持排队。T132默认2秒但可配置，C104默认上限3。
- 边界：§6.2.4.9.11 的T104耗尽分支没有逐项重列T100启动/C100初始化；表11.1.1-1又将发Release列为T100启动原因。须同时保留这两层，不能假装事件正文完整复用了用户撤回的全部步骤。
- 边界：T132超时进入无权限，不改成pending Release；T104耗尽进入pending Release，不改成无权限。Deny/Idle步骤未列统一清除所有计时器，不从别的事件补上。

依据：3gpp-ts-24.380-v16.9.0 §5.2.2 / 6.2.4.1 NOTE2 (audio cut-in comparison) / 6.2.4.4.9 / 6.2.4.9.1–6.2.4.9.13，印刷页 33,36,41,48,49,50,51；3gpp-ts-24.380-v16.9.0 §8.2.2.1 / 11.1.1 table11.1.1-1 / 11.2.1 table11.2.1-1 / 14.2.2;14.3.2，印刷页 148,212,213,222,223,238,239。

## 终端提示“话权空闲”，一定收到了 Floor Idle 吗？

不一定。在普通在网单话权组呼里，终端的可选 T103 用来观察本端接收的媒体是否结束。处于**无发送许可**时，实收 Floor Taken，宜为该消息对应的参与者启动可选 T103；实收 RTP，宜启动或重启 T103。不必先听见语音才可能启表。已启用的 T103 到期时，终端**可以**提示空闲，但仍无发送许可。这条计时分支不需要收到 Floor Idle，也不要求提示或发送 Ack。实收 Floor Idle 则有自己的入口：按收到的请求位判 Ack；若 T103 正在运行，则须停止。若这条 Idle 属于普通持有者主动放权且满足该页条件，可从[持有者释放的收发路径](on-network-holder-release.md)核对。[§6.2.4.3.2，印刷页 37–38](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=38)。[TS 24.380 V16.9.0 §6.2.4.3.3–.4，印刷页 38](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=39)；[§6.2.4.3.6，页 39](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=40)。

**正在等待 Floor Request 应答**时，T103 也能运行。此时它到期，正文写的是不执行动作；不能照搬无许可状态的空闲提示。终端仍按请求应答或 T101 等各自的事件处理，不能用 T103 到期判断请求已超时、获准或被拒。[§6.2.4.4.1，印刷页 39](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=40)。

**已经排队**时，实收 Floor Taken 也宜启动可选 T103，但仍留在队列状态。若实收的是队位通知（Floor Queue Position Info），则停正在运行的 T104，仍保持排队；这不是 Taken 的启表，也不是授予。若实收的是 Floor Idle，则停正在运行的 T104，转为无发送许可。计时表把收到 Floor Idle 列为 T103 的正常停止原因，排队的这个收件条款却只明确写停 T104，未另列 T103。看现场日志时，不拿表替这一条补成所有状态都停 T103，也不由正文没写判它实际一定还在运行。转成无许可说的是本端状态，不说明服务器实际清了哪条请求。[§6.2.4.9.3，页 48](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=49)；[§6.2.4.9.7，页 49–50](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=50)；[§6.2.4.9.8，页 50](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=51)。

[表 11.1.1-1，印刷页 213](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=214)建议 T103 的配置时值与服务器 T1 相等，不表示它们是同一只计时器、在同一时刻启动或到期。只有终端提示或本地媒体安静，不足以断定服务器看到 RTP 断流、全组话权空闲，或 SIP 通话已释放。

## 有权限才启动语音转发，撤销授权要求停发并丢弃缓存

- 条件：处于 has permission 收到编码语音/已有缓存、用户释放意图或 Floor Revoke；或者 pending Request 收到用户撤回意图。这些是替代事件。

has permission 中得到编码语音或已有缓冲语音时，要求客户端开始向服务器转发并保持有权限；已排队用户须先完成前述确认。用户即使尚未发出媒体也能释放：发 Release，启动 T100、置 C100=1，进入 pending Release。pending Request 中用户撤回同样发 Release、启动T100/C100，并停止T101后进入pending Release。has permission 收到 Revoke 时须告知用户、要求丢弃剩余缓冲RTP并停止向服务器转发；可说明原因。在非dual的 G=0 分支发带 G=0 的 Release，启动T100/C100，进入pending Release。Release是否请求Ack可选，收到/未收到该Ack的处理是实现选项，不等于已有统一的Ack后完成规则。

规范强度：转发请求、撤回/撤销处理、停止并丢弃缓存及状态转移为 SHALL；撤销原因提示及Release请求Ack为 MAY。
- 边界：向服务器转发的动作不证明远端已经收到、播放或所有成员均在听。
- 边界：主动Release段未逐字重复Revoke段的丢弃缓存步骤；本页不把两个入口写成相同的缓冲清理算法。
- 边界：T100实际时值由配置决定；C100默认上限3，Release重传总时长须小于6秒（表11.1.1-1 NOTE1中的shall）。

依据：3gpp-ts-24.380-v16.9.0 §6.2.4.4.8 / 6.2.4.5.1–6.2.4.5.5 / 8.2.2.1，印刷页 41,42,43,148；3gpp-ts-24.380-v16.9.0 §11.1.1 table11.1.1-1;11.2.1 table11.2.1-1，印刷页 212,213,222,223。

## 撤回后的晚到 Granted 不重新授予发送权

- 条件：当前处于 pending Release，收到 Idle、Taken、RTP、Revoke、Granted 或 T100 到期；不是仍在等待请求授权。

T100 未达 C100 上限时重发 Release，可请求Ack，重启T100并递增C100，保持pending Release；达到上限进入has no permission。收到普通非broadcast的Idle时按要求Ack（5、0），可通知空闲，停止T100，进入无权限。收到Taken按要求Ack（2、0），可提示，宜为新讲话者启动可选T103；仅本用户不在 List of Granted Users 时停止T100，随后进入无权限。收到RTP时要求播放，宜启动可选T103，停止T100，进入无权限。收到Revoke可提示但保持pending Release；晚到Granted按要求Ack（1、0）后仍保持pending Release，不能按pending Request的规则重新开麦。

规范强度：重发、计时/计数、条件Ack、媒体播放请求和状态变化为 SHALL；提示及Release请求Ack为 MAY；可选T103启动为 SHOULD。
- 边界：本段仅判客户端当前状态，不证明服务器已清除全部排队/授权记录。
- 边界：Taken的T100停止有名单守卫，不因随后转无权限便抹掉该条件；不补不存在的通用FloorAck终态入口。

依据：3gpp-ts-24.380-v16.9.0 §6.2.4.6.1–6.2.4.6.8 / 8.2.2.1，印刷页 45,46,47,148；3gpp-ts-24.380-v16.9.0 §11.1.1 table11.1.1-1;11.2.1 table11.2.1-1，印刷页 212,213,222,223。

## 一次话权释放不等于结束通话

- 条件：以下为替代事件入口：在非 Start-stop 且非 Releasing 状态收到应用/信令层的通话释放 step1；在 Releasing 状态收到应用/信令层的通话释放 step2；或任一状态收到未定义处理的控制消息/RTP。

通话释放是独立的两阶段接口：step1停止发送话权控制消息并要求停止RTP，进入Releasing；应用/信令层确定通话已释放后触发step2，释放包括运行中计时器在内的相关资源，回Start-stop并终止本实例。用户面可发起step1，step2始终由应用/信令层发起。某状态没有对应接收程序时，丢弃该控制消息或RTP并保持状态；不能把某条Granted规则应用到所有状态。普通无权限、pending Request或queued期间仍可接收/播放媒体，这与发送权限不同。

规范强度：通话释放接口动作、资源清理及未定义接收的丢弃为 SHALL；接收媒体相关可选T103动作按各事件为 SHOULD，不改成发言授权。
- 边界：本页解释话权状态与媒体动作证据，不展开SIP释放事务、完整服务器仲裁、安全密钥/加解密、RTP编码与送达保证。
- 边界：可选T103表示接收媒体结束，表中建议等于T1且由配置确定；不能把T103到期一概解释为通话释放或发送获准。
