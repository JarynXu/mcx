# 并行使用不同 MC 业务：哪些应独立，终端资源冲突时怎么办？

**不同 MC 业务应独立运行，包括各自已有的话权控制。** 终端的同一个不可共享资源真被争用时，再看终端资源规则。比如边用 MCPTT 发话边收 MCVideo，与两项业务都要用同一个不可共享的扬声器，不是同一种情况。

本页依据 [3GPP TS 22.280 V16.8.0，Release 16，Stage 1，§§8.2–8.3，印刷页 58–59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=59)。Stage 1 写业务应具备什么能力，不给出消息、系统流程或产品实现。本页只比不同、应独立运行的业务，不回答同一业务可同时开多少会话。

## 哪些并行行为不能因业务相互影响而受限？

业务独立与话权独立是两个要求。每项 MC 业务各自运行；多项业务同时使用时，已有的话权控制也各自独立。原文均保留“另有明确规定”的例外。不能仅因一项业务拿到话权，就把另一项业务也判成可以发话；也不能由此要求每项业务都有话权控制。

| 不同业务的并行方式 | 对用户能力的要求 |
| --- | --- |
| 一发一收 | 能在一项业务发送，同时在另一项接收，不因业务相互影响受限（R-8.2.2-003）。 |
| 两边发送 | 能在不同业务近乎同时发送，不因业务相互影响受限（R-8.2.2-004）。 |
| 两边接收 | 能在不同业务近乎同时接收，不因业务相互影响受限；争用**同一个不可共享资源**时例外，例如同一个不能共享的显示器或同一个不能同时使用的音频部件（R-8.2.2-005）。 |

条文没有规定多短的时间差才算“近乎同时”。只有两边接收这一项明写了同一个不可共享资源的例外，不能将这句移到另两项上。也不能反过来推断任何终端都有无限容量。§8.2.1 把产品能承受的业务总量和同一业务内实例上限留给供应方说明；网络侧可能避免业务本身造成的冲突，但这里不规定其动作。[§8.2.1、§8.2.2 R-8.2.2-001 至 -005，印刷页 58](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=59)。

## 争用终端资源，谁决定用哪项业务？

普通 MCPTT 和 MCVideo 都要同一个不能共享的扬声器时，**MC 业务必须提供让用户设定资源使用优先次序的机制**。最近选择的业务优先、MCPTT 语音优先只是原文举例，不是统一默认。如果争用的一边是标记为 **Emergency** 或 **Imminent Peril** 的通信，另一边两种标记都没有，有标记的通信必须优先使用该终端资源。这条不排序两种标记之间的优先级，也不要求结束另一项业务的会话。[§8.3 R-8.3-003，印刷页 58](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=59)；[R-8.3-004，印刷页 59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60)。

**一项业务被拒用该终端资源时，两项要求都适用。** 要提醒用户资源已被拒用，也要让用户在资源受限期间选择优先使用该资源的 MC 业务。它不是设定永久默认，不能从这项能力推断用户可以覆盖上述有标记通信的优先要求。条款没给提示样式、处理时限或被拒后的会话动作。[§8.3 R-8.3-005、-006，印刷页 59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60)。

能区分多路声音是对终端的建议（**should**）；允许终端提供各路相对音量和空间呈现控制（**may**）。不把这两项都当成必须提供的功能，也不拿音量控制代替拒用提醒。[§8.3 R-8.3-001、-002，印刷页 58](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=59)。

## 如果忙的是网络，不是扬声器呢？

在**同一网络**使用不同 MC 业务时，无线资源须能在各业务各自阈值和／或合计阈值以内有效利用。无线资源分配可随需求变化，也可预先安排。另一个要求是：按 3GPP 网络运营方与任务关键组织之间的协议，网络须能把分给各业务或全部 MC 业务合计的无线资源保持在阈值**以下**，使这部分 MCX 资源使用不影响非 MCX 业务。这里说的是网络可实现的分配约束，不给阈值数值、调度算法，或任何负载下的实测性能保证。要查执行优先级决定时怎样一起管理不同 MC 业务的数据流，以及调度动作改变流优先级后应通知什么，见[§8.5 的业务间优先级](../bearers/cross-service-priority.md)。那里没有把传输容量不足列为附加条件。[§8.2.1、§8.2.2 R-8.2.2-006、-007，印刷页 58](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=59)。

若瓶颈是同一项业务的收流数上限，查 [Stage 2：MCVideo 同一业务怎样选停一路](../mcvideo/reception-override-modes.md)。若问 [MCData 功能角色](../mcdata/service-capability-and-functional-roles.md)或[并行组呼是否需要增加承载](../bearers/unicast-bearer-priority-sharing.md)，分别看对应的 Stage 2 主题。这些页不替代本页的跨业务要求；单个组使用多项 MC 业务的 §8.4 也不在本页范围。
