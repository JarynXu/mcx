# 本来要发起的组呼已经在打，隐式话权请求怎么处理？

先确认这个客户端此次的 SIP 会话已经建立。控制侧接口正在处理 Start-stop 下的入态，并且**已识别这次尝试是在发起既有组呼，且携带隐式话权请求**。本页只看普通在网单话权 MCPTT 组呼中控制侧面向此客户端的接口 U。首次新建、无隐式请求重入、单独受邀、正在通话中发显式 Floor Request，都有自己的入口。单独看到 SDP 里的 mc_implicit_request 或 SIP 200，不能确认本次符合这条，也不能确认客户端已有话权。[TS 24.380 V16.9.0，Release 16，Stage 3，§6.3.5.2.2 入口与第 3 项，印刷页 71–74](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=72)。

## 先看谁已有发送许可，再看请求端有没有协商排队

| 控制侧所知的条件 | 这次接口要做什么 |
| --- | --- |
| 没有任何客户端获准发媒体 | 把隐式请求按收到 Floor Request 的规程交给话权仲裁处理，并按入态条文设这个接口为 U: permitted。这里的“按收到处理”不表示线路上有一份显式 Floor Request。也保留仲裁条款自己的适用和拒绝条件，不能只见 U 的状态就认定仲裁成功、终端收到授予或开始发 RTP。 |
| 别人已获准，请求端**协商了**排队 | 优先级取该端协商可请求的最高值；若该值为抢占优先级，改用高（high）优先级。将这名请求端插入活动队列，紧接最后一个同优先级排队请求。须给这名请求者发 Floor Queue Position Info，含队位和话权优先级；此接口进入无发送许可的 Floor Taken。 |
| 别人已获准，请求端**未协商**排队 | 须给请求端发 Floor Taken，并进入无发送许可的 Floor Taken 状态。普通非广播下可带 Permission to Request=1；允许继续请求，不是允许发送语音。 |

**听不到声音，不能当作无人获准；知道客户端支持排队，也不能当作已协商。** 通过这一入口加入正在进行的呼叫时，初始隐式请求不抢占当前发送者。若要请求抢占，注 5 写的是另发带抢占优先级的显式 Floor Request，不保证该显式请求一定抢占成功。[§6.3.5.2.2 第 3(a)–(c) 项及注 4、5，印刷页 73–74](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=74)；[§6.3.4.3.3，印刷页 57](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=58)；[§6.3.5.5.2，印刷页 85](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=86)。

## 队位变了，要通知所有排队端吗？

不是。第 3(b)(iv) 项只说**宜**给符合条件的其他排队端更新：它还在活动队列里，已协商排队，曾请求队位状态，且比上次给它的队位通知发生了位置变化；本次加入的请求端不在这批更新里，它有上一节单独的必发通知。更新若发送，仍须带队位和话权优先级。没看到某个终端的更新，不足以判它没在队列或这次排队没有处理。[§6.3.5.2.2 第 3(b)(iii)–(v) 项，印刷页 73](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=74)。

排查时分别对照控制侧认到的请求、它处理的队列或授予、以及终端实际收到的结果。队位通知或 Floor Taken 到达终端，都不能用作这名终端已获发送许可的凭据。若是[无隐式请求的重入](../calls/rejoin-late-entry.md)、[从新建会话的隐式请求判断提前媒体许可](implicit-floor-early-media.md)，或[普通空闲组呼实收显式 Floor Request](on-network-idle-floor-server.md)，各回自己的入口。
