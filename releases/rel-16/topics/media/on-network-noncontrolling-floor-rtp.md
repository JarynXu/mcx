# 在网 MCPTT：非控制功能怎样处理无许可终端收发的 RTP？原因 #3 后的 Release 给谁？

无许可限制的是**这个终端发言**。在普通单话权组呼中，终端没有话权，仍可接收别人的语音。若非控制功能内面向这个终端的参与者接口（P）处于 `P: has no permission`，并收到网络媒体接口的指示，得知 RTP 来自这个终端自己，P 就向该终端发 Floor Revoke，原因 #3（无权发送媒体突发），并记下等它发 Floor Release。这个动作不要求整组停止通话。

这里有两个不同的接口。非控制功能内的**参与者接口 P** 在一次会话中为每个终端各维护一个状态机；`P: has no permission` 说明它关联的那一端没有发送许可。**服务器接口**在同一个非控制功能内，面向控制 MCPTT 功能（CF）。P 的状态不等于终端自己的状态，也不等于控制方直接面向终端的接口状态。依据 3GPP TS 24.380 V16.9.0（Release 16，Stage 3）：[§6.5.1，印刷页 103](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=104)、[§6.5.5.1，印刷页 113](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=114)、[§6.5.5.3.1，印刷页 114](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=115)。

## 看到 RTP，先看谁报告、包从哪里来

设甲的 P 处于无许可状态。网络媒体接口报告它收到了 RTP，P 要按报告中的来源处理：

| 网络媒体接口报告的来源 | 甲的 P 必须做什么 |
| --- | --- |
| 来自媒体分发器 | 指示网络媒体接口把这些包发往甲，保持无许可。指示下发不是甲已收包或播放的回执，也没有授予甲发送权。 |
| 来自甲自己的终端 | 给甲的话权参与者发 Floor Revoke（Reject Cause = #3），记录期待甲的 Floor Release，保持无许可。该项没有写要丢弃或转发这批包、停止分发或启动 T8；也没有把先前收到 Release 或“带载荷”（with payload）另列为条件。 |

[§6.5.5.3.9，印刷页 115](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=116) 明写了这两种收包事件，不能套用 §6.5.5.1 对**当前状态没有规定处理程序**的包所列的默认丢弃动作。

服务器接口看到的是另一种报告。**下行**，媒体分发器报告收到 CF 的 RTP 时，若未存双话权获准者的 SSRC（同步源标识），服务器接口须请求分发器转给本会话中由本非控制功能管理、且自身 SSRC 与来包不同的各终端。收件范围不是全体组员，转发请求也不是这些终端的到包记录。[§6.5.4.12 第 1 项，印刷页 111](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=112)。

**上行**，服务器接口若实际收到媒体分发功能的指示，得知它已从某个网络媒体接口收到 RTP，就须请求分发器将所收包转向 CF。条款的注说，无许可终端的 Revoke 由 P 本地发，不需要服务器接口参与；注没有说这批包是否到了分发器。[§6.5.4.13 及注，印刷页 112](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=113)。追甲发来的某个包，先区分四处证据：甲这一侧的网络媒体接口向 P 报告收包；分发功能向服务器接口报告收包；非控制功能朝 CF 实际发包；CF 实际收包。发了本地 Revoke 只能解释纠正动作，既不证明包已经上行，也不证明包被丢了。某处没抓到包，仍不能替另一处下结论。

## 甲随后发 Floor Release：本地确认，还是往上转？

要看**甲的 P 收到甲的 Release 时，是否已记下期待这条 Release**。旁边另一个终端的记录不算。这两个分支处理后，甲的 P 都留在无许可状态。[§6.5.5.3.10，印刷页 115–116](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=116)。

- **有期待记录**：若收到的 Release 的 subtype 首位是 1（要求确认），P 须给甲回 Floor Ack；首位是 0 则不要求这一步。两者都须清除期待记录。该分支没有把 Release 转给服务器接口的步骤。
- **没有期待记录**：P 须把 Release 转给本地服务器接口。首位是 0 时，不触发确认选择；首位是 1 时，本地策略有两种选择：P 给甲回 Ack，并把外发 Release 的首位改成 0；或者等待话权控制服务器的 Ack。“等待”决定谁来确认，不是收到 Ack 才准把 Release 转出去。

只有服务器接口**实际收到** P 转来的 Release，才按 [§6.5.4.3，印刷页 106](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=107) 向 CF 转发：原消息有 Track Info 就在引用尾部追加临时标识，没有则补该字段；其本地被动队列若确有该端的请求，才移除那一项。这个接口的动作不证明 CF 已收到，也不证明 CF 的活动队列已变。如果确实要查的是一个排队者撤回请求，读[撤回排队时被动队列与活动队列各由谁改](on-network-preemption-revoke.md)。

只见 P 发 Revoke，不证明甲已收到或回复。若 P 仍在无许可状态，又收到网络媒体接口关于甲发来 RTP 的指示，仍按 §6.5.5.3.9 处理。这是再次收到指示，不是定时重发，也没有要求一个 RTP 包对应一次 Revoke。若能把 P 回的 Ack 对应到甲的 Release，它确认 P 收到这份 Release；两个分支都可能本地回 Ack，不能只凭它判定当时有期待记录、Release 已转给 CF 或下游已停收。§6.5.5.3.9–10 没有为等不到 Release 的 P 指定超时、重发次数或自动断开动作。

## 同是原因 #3，什么时候会停转并启动 T8？

**控制方直接关联终端**时，看它面向此端的接口 U。两种入口都要求网络媒体接口实际报告收到了该端**带载荷**的 RTP。若 U 处于 *not permitted and Floor Idle*，还须是它在上一个 *permitted* 状态收到了该端的 Floor Release；若 U 处于 *not permitted and Floor Taken*，对应条款没有这个前置 Release 条件。符合各自条件时，U 须要求网络媒体接口不把这些包交给分发器，向该端发原因 #3 的 Revoke，进入 *not permitted but sends media* 并启动 T8。[§6.3.5.3.8 及注，印刷页 77](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=78)、[§6.3.5.4.6 及注，印刷页 83](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=84)、[§6.3.5.7.2，印刷页 89](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=90)。这两个入口的注都把非控制功能所管终端的无许可 RTP 留给非控制功能处理，不能把 U 的停转指令、状态或 T8 移到 P 上。

如果实际是原持有者主动松开 PTT，读[持有者放权与控制方的停转请求](on-network-holder-release.md)。若要判断**终端自己**收到 Revoke 后是否启动 T100，先核实该端当时确在 *has permission* 且实际收到 Revoke，再看[普通在网话权客户端](on-network-floor-client.md)及[§6.2.4.5.4，印刷页 43](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=44)。P 发出的 #3 不能代替这个终端收件条件，T100 也不是 P 等 Release 的计时器。

## 什么才是呼叫释放的停媒体指令？

甲的 P 尚处于无许可状态，若它**收到应用与信令面发来的呼叫释放第 1 步请求**，它须停止向甲发话权控制消息、忽略来自甲的话权控制消息，并要求网络媒体接口既停止向甲发 RTP，也停止将甲的 RTP 转给分发器。P 通知服务器接口甲已开始断开，进入 `P: Releasing`。甲离开会话就可能触发这个入口，不等于其他人也离开。[§6.5.5.5.1、§6.5.5.5.3，印刷页 118](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=119)。

若收到应用与信令面呼叫释放第 1 步请求的是**服务器接口**，该接口须忽略来自话权控制服务器和各 P 的话权控制消息，请求分发器停止向客户端的网络媒体接口分发 RTP。[§6.5.4.14，印刷页 112](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=113)。这和甲本地回应 Floor Release 是两个入口。要判断停的是甲这一端还是会话侧的分发，应找相应接口收到的释放请求和它发出的停转指令；要断言某个终端实际停收，还需要该终端的证据。

若实际是参与功能处在 MBMS 活动态，查[话权转发、Floor Ack 与 RTP 重复的不同条件](mbms-floor-ack-and-rtp-duplicates.md)。
