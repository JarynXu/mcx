# 在网 MCPTT：非控制侧怎样把 Floor Granted 送回申请话权的终端？

甲和乙通过同一个非控制 MCPTT 功能参加组呼。甲按下 PTT。回来的 Floor Granted 应该给谁？**非控制侧的服务器接口收到控制方的 Granted 后，用 Track Info 的末尾引用，在本地找到与它关联的参与者接口。** 不用猜谁刚按过 PTT，也不必先从队首选人：控制方决定是否授予，非控制侧负责把答复送给相应终端。被动队列保存符合排队能力条件的出站请求记录。单凭一条记录，连非控制侧是否实际发包都不能确定，更不能断言控制方已收件、甲排第几或是否获准。

下文限普通在网单话权组呼，不讨论广播组呼、环境监听或 audio cut-in；当前不涉及合组、角色切换、抢占、双话权或多人同时发言。**P** 是非控制功能面向一个终端的话权参与者接口，每个会话里的每个终端各有一个 P。**服务器接口**在同一非控制功能内，面向控制 MCPTT 功能（CF）。甲的 P、甲的终端和 CF 各自按收到的事件行动。[TS 24.380 V16.9.0 §6.5.1，印刷页 103](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=104)、[§6.5.5.1、图 6.5.5.1-1，印刷页 113](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=114)。

## 甲的 Floor Request 怎么留下回程引用？

新 SIP 会话建立组会话时，服务器接口收到应用与信令面的组会话启动指示，为各个参加会话且由本功能管理的终端生成随机临时标识，把标识与该端的 P 对应起来，并保存协商的能力。这里用到的 Floor Participant Reference 是 32 位值，只有生成它的非控制侧服务器接口知道它指向哪个参与者。它不是用来标识 RTP 源的 SSRC，也不是 MCPTT 用户 ID；不能当作跨会话的全局身份。这些条款没有给出引用碰撞或查不到对应关系时的恢复办法。[§6.5.2.2，印刷页 103–104](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=104)、[§8.2.3.13、表 8.2.3.13-1 及注 2，印刷页 154–155](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=155)。

甲的 P 原在 `P: has no permission`。它**收到甲发的 Floor Request**，就把请求交给本地服务器接口，自己仍无许可。这是话权控制消息，不需要媒体分发器先报告收到了 RTP。[§6.5.5.3.4，印刷页 114](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=115)。

服务器接口**收到 P 交来的请求**才向 CF 转发。它保留参与者带来的字段：若已有 Track Info，把甲的本地临时标识追加到引用末尾；若没有，就新建 Track Info，以协商的 `mc_queueing` 填 Queueing Capability，以可得的 participant-type 填 Participant Type（取不到填 `unknown`），把甲的标识放在第一个引用。只有外发 Track Info 的 Queueing Capability **为 1**，这一步才要求把**外发的 Floor Request** 存进本地被动队列。原请求已有 Track Info 时，判断的是保留下来的 Queueing Capability，不再用本地协商值替换它。能力为 1 表示甲支持排队，不表示 CF 已收包或已把甲列入活动队列。[§6.5.4.2，印刷页 106](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=107)。

## CF 回了授予、拒绝或队位通知，哪些地方会变？

看服务器接口**实际从 CF 收到的那条消息**。它用 Track Info 的末尾引用找甲的 P；它在本地怎么处理队列，与稍后甲是否收到消息是两件事。

| 收到的消息 | 服务器接口发给谁、改什么 | 本地被动队列 |
| --- | --- | --- |
| Floor Granted（授予） | 给末尾引用指向的甲的 P。若只有一个引用，从外发 Granted 删掉整个 Track Info；若有多个，只删末尾引用，保留前面的。这个普通分支中，若未存双话权获准者的 SSRC，服务器接口还给其余 P 发 Floor Taken；发往乙的 P 的 Taken 通知有人获准，不是给乙的 Granted，也不证明乙收到了通知。 | 若队内确有来自甲的 Floor Request，移除该请求。 |
| Floor Deny（拒绝） | 按末尾引用找 P，转发 Deny。多引用时去掉最后一个；单引用的措辞见下。 | 若有来自甲的请求，移除该请求。 |
| Floor Queue Position Info（队位通知） | 按末尾引用找 P，转发队位通知。多引用时去掉最后一个；单引用的措辞见下。 | 本条没有移除请求的步骤。队位通知也不授予话权。 |

例如，假设本地标识为 17，已收到的 Granted 带引用 `[9, 17]`：用 17 找甲，交给甲的 P 时还带 `[9]`；若是 `[17]`，交给 P 时不带 Track Info。9 和 17 仅用于说明顺序，均不表示队位。17 能定位甲的 P，不能单凭它判定 Granted 对应甲的哪一次请求或重发。[§6.5.4.6 第 1、2a、3 项，印刷页 107–108](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=108)。

**Deny 和队位通知有一处原文用词不能照 Granted 类推。** 两个条款第 2a 项都把“单引用时删除整个 Track Info”的对象写作外发 **Floor Granted**；第 3 项却分别要求转发 **Floor Deny** 和 **Floor Queue Position Info**。目标 P、要转的消息种类以及多引用去尾都有明文；仅凭这两处单引用文字，不能断言外发 Deny 或队位通知一定删除整个字段。[§6.5.4.7，印刷页 108](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=109)、[§6.5.4.11，印刷页 111](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=112)。若想知道的是 CF 在什么条件下会授予，要看[控制侧已处于 Idle 时怎样处理请求](on-network-idle-floor-server.md)；若甲是在撤回排队，见[撤回后两侧怎样各自移队](on-network-preemption-revoke.md)。

## 甲的 P 需要等 Ack 才有许可吗？

**不需要。** 在无许可状态，甲的 P 收到本地服务器接口给它的 Granted、Deny 或队位通知，都要把相应消息发给甲。若所收消息的 subtype 首位为 1，P 还须记下期待对**这种消息**的 Floor Ack。处理 Granted 时，P 进入 `P: has permission`，没有“先收到 Ack”这一条件。处理 Deny 或队位通知时，P 仍是 `P: has no permission`。这是 P 的状态转换，不是终端收件的证明，也不规定几条日志的出现顺序。[§6.5.5.3.5，印刷页 114](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=115)、[§6.5.5.3.6–7，印刷页 115](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=116)。

甲的 P 收到甲的 Ack，要看其 Message Type。只有已记下期待对该类型的确认，P 才按这一条把 Ack 上交服务器接口，并清掉**这个类型**的期待；P 保持当时的状态。对队位通知的 Ack 不能拿来确认 Granted。若期待的 Ack 没到，采取什么动作由实现决定。服务器接口若实际收到 P 上交的 Ack，须保留参与者带来的字段，已有 Track Info 就把本地临时标识加在末尾，没有就新建字段，把该标识放在第一个引用，再把 Ack 发往 CF。CF 是否收到要在 CF 一端核实。[§6.5.5.5.1–2 及注，印刷页 118](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=119)、[§6.5.4.5，印刷页 107](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=108)。

**终端确认收到 Granted，不等于排队用户已决定发言。** 看甲终端是否实际收到相应消息，以及收件前的状态：它在 pending Request 收到 Granted 会进入有许可；若先收到队位通知，则进入 queued。在 queued 收到 Granted，终端启动 T132，仍在 queued；T132 运行时再收到用户要发言的指示，才进入有许可。终端侧的这些条件不移到 P 上。排查时用同一会话、同一端的收件记录核实送达，再查终端的状态和用户动作，不用服务器的发包记录替代。详见[普通在网话权客户端](on-network-floor-client.md)及[§6.2.4.4.2，印刷页 39–40](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=40)、[§6.2.4.4.9，印刷页 41](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=42)、[§6.2.4.9.4，印刷页 48–49](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=49)、[§6.2.4.9.12，印刷页 51](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=52)。

## 已获准，怎样判断甲的 RTP 到了哪里？

1. **甲这一端。** 先核实甲的 P 在收包指示到来时仍有许可，例如查这个会话中甲的 P 的状态记录，或核对它收到 Granted 后经历的状态转换。如果网络媒体接口报告收到了来自甲终端的 RTP，P 须指示媒体接口把这些包转向媒体分发器，P 仍有许可。这一步指向分发器，不是 CF。若甲的 P 当时无许可，读[无许可终端收发 RTP 的两个方向](on-network-noncontrolling-floor-rtp.md)，不能套用获准后的动作。[§6.5.5.4.2，印刷页 116](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=117)。
2. **从分发器朝 CF。** 服务器接口有自己的触发条件：媒体分发功能向它报告已从某个网络媒体接口收到 RTP，它才按此条请求网络媒体分发器把所收包转向 CF。P 的指令不能证明分发器收到了这些包；服务器接口的转发请求也不是出口发包记录。[§6.5.4.13，印刷页 112](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=113)。
3. **实际送达。** 要说“甲的这批 RTP 已转出”，查非控制侧朝 CF 的实际出口；要说“CF 已收”，查 CF 的对应入口。要证明对端终端收到了或播放了语音，还要该端的收包或播放证据，CF 收包也不能代证。

判断 P 当前状态，不能只看先前的一条 Granted 或最近的一条 Release。有许可的 P 收到甲的 Floor Release，要向服务器接口转交，但这一步仍有许可；若它收到服务器接口的 Floor Idle，或本页非多人发言情形的 Floor Taken，则按相应入口把消息发给甲并转入无许可。[§6.5.5.4.3、.5、.6，印刷页 117](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=118)。

若收到控制侧的 [Floor Idle，查单发与群发的 Track Info、ACK 和被动队列](noncontrolling-floor-idle-delivery.md)，不要把 Granted 的动作套给 Idle。
