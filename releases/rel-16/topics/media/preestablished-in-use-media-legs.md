# MCPTT 预建立会话：PF 转了语音，终端为什么还可能丢弃？

看两边各自的状态。比如，这次组呼没用 MBMS，参与功能（PF）在用这条预建立会话，实收控制功能（CF）的 RTP，须转给终端。另一份可靠记录表明同一 RTP 确实到了终端，但终端侧还未进入在用。它要丢弃这份 RTP。PF 应转发与终端应丢弃并不矛盾。PF 发出不证明下游收到，必须另有终端收件证据。

这里查普通在网单话权组呼。先把报文和这次组呼拟用或正在使用的那条已建立的预建立会话对应起来，不预设接收端已经在用。PF 和终端分别记自己这条预建立会话的在用状态。它不是终端的基本话权状态，也不是控制功能（CF）的仲裁状态。别用另一条预建立会话、一次 SIP 200 或一条 Accepted 替代它。[TS 24.380 V16.9.0，Release 16，Stage 3，§9.1、§9.2.2.1 印刷页 193–194](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=194)；[§9.3.2.1 印刷页 197](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=198)。

## PF 在用并收到包：先看从谁来、往谁去

PF 在自己这条会话的 `G: Pre-established session in use` 下实收话权消息或 RTP，分别按 §9.3.2.4.2、§9.3.2.4.3 的入口处理，**仍留在本侧在用状态**。两处都回指 §6.4.1；它是参与功能程序入口，不是每类包的具体转发条目。适用一项转发规程，不表示已经执行或下游已收到。[§§9.3.2.4.1–.3，印刷页 200](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=201)；[§§6.4.1–.3，印刷页 101–103](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=102)。

**上行语音看 PF 来包。** PF 实际收到本场的客户端 RTP，须立即转给控制功能（CF）。这条上行规则没有列 MBMS 条件，也没有列“先收 Connect 的 Accepted”。若当时 PF 已在用且确实收到本场的 RTP，只因 T55 还在跑，不能用这些条款认定必须先等确认才能转发。也不能反推终端在确认前就能发 RTP，或 CF 后来已收到。[§6.4.3 第 1 项，印刷页 102](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=103)。

下行 RTP 不走上行条目。若这场通话没用 MBMS，实际收到的 RTP 可能来自 CF 或非控制功能（NCF）；不要把同一个来向条件套给下行话权消息。普通话权转发、无 MBMS 的下行与实际使用 MBMS 时的下行分流，见[PF 的话权与语音转发](mbms-pf-floor-routing.md)，按该场通话的实际承载查，不以设备支持 MBMS 代填。[§6.4.2 第 1、2 项、§6.4.3 第 2 项，印刷页 101–102](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=102)。

## 终端收到包：会话在用，不等于人有话权

终端在 `U: Pre-established session in use`，实际收到普通话权控制消息（不是 Connect 或 Disconnect）或 RTP，须按自己的 §6.2.4 基本话权状态处理，**预建立会话仍在用**。要判断某个 Floor Granted 是否满足终端的授予入口，或某包 RTP 是否触发本机播放请求，去查[普通在网终端话权](on-network-floor-client.md)。PF 发出、终端实收、本地请求播放、用户听到，是不同证据。[§§9.2.2.4.3–.4，印刷页 196](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=197)。

相反，**本侧仍是“已建但未在用”且实收 RTP**，该状态下没有处理 RTP 的条目。终端和 PF 各按自身状态机的通则丢弃这份 RTP、保持原状态。这一句只对 RTP 作判断，不把通则推广成“已建未用就丢掉任何话权消息”；终端未在用的总则还明确说可以收到话权控制消息。也不能只从没有语音推定任一方已丢包。[§9.2.2.1 图后通则、§§9.2.2.3.1–.6，印刷页 194–195](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=195)；[§9.3.2.1 图后通则、§§9.3.2.3.1–.5，印刷页 197–200](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=198)。

若要查两边分别何时进入在用，或同名确认来自哪一步，读[Connect 的应答与重试](preestablished-connect-outcome.md)；消息究竟是 MCPC 还是普通话权控制，读[RTCP APP 的 Name 与 subtype](rtcp-app-name-subtype.md)；若另查使用预建立会话的普通在网私呼怎样释放，读[预建立私呼的释放与确认](preestablished-release-outcome.md)。这不是本场组呼的释放规程。不是本页这场组呼、或本次实际上采用按需会话，不套预建立会话的状态条件。
