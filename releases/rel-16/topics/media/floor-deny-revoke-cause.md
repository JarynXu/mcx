# Floor Deny 和 Floor Revoke 的原因码：同一个值为什么不一样？

在网 MCPTT 抓包里，**Floor Deny 的原因 3 表示「只有请求者一名参与者」；Floor Revoke 的原因 3 表示「终端无发送媒体的权限」**。两种消息都用 `Reject Cause`，却各用自己的原因码表。日志若只记「原因 3」就不足以判断：先找收到的那一包，确认消息类型，再读数值。

范围：Release 16、Stage 3，TS 24.380 V16.9.0。以下用在网通话的话权控制举例；不把这些值当成 SIP 状态、SIP Warning、预建立会话的 MCPC 应答原因或其他版本的代码。

## 先读消息类型，再读字段

- **识别 RTCP APP 的消息。** `PT=204` 表示 APP，`Name=MCPT` 才用话权消息表。Floor Deny 的 subtype 为 `00011` 或 `10011`（十进制 3 或 19）；首位 1 的后者要求确认。Floor Revoke 的 subtype 固定为 `00110`（十进制 6）；不能给它套 Deny 的首位变化规则。若日志没记 Name 或 subtype，回到原始包或能分辨消息类型的接收记录。[§8.1.2，印刷页 145–146](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=146)；[表 8.2.2.1-1，页 148](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=149)。
- **拆开字段 ID、字段长度和原因值。** 字段 ID 2 标识 `Reject Cause`；后面的原因值占 16 位。字段长度计入原因值和可选说明文字，不计填充。因此，在其他格式正确的前提下，**长度 2 表示有原因值、没有说明文字**，不表示截断，也不表示原因值是 2。不能把填充当作文字。[表 8.2.3.1-2，页 149](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=150)；[§8.2.3.4，页 150](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=151)。

## 根据消息查表，不要只看数字或说明文字

| 数值 | 若是 Floor Deny：为什么不授予请求 | 若是 Floor Revoke：为什么要求停发 |
| --- | --- | --- |
| 2 | 话权控制服务器内部错误。 | 本次发言太久。例如控制侧 T2（Stop talking）到期。 |
| 3 | 请求者是该 MCPTT 会话中唯一的参与者。 | 该客户端没有发送媒体的权限。 |
| 4 | 发送权限已被撤销，话权控制服务器的 T9（Retry-after）尚未到期，不能批准这次请求。 | 该客户端的发送权限正在被抢占。 |

这三个 Floor Revoke 原因在本版均不带附加信息。Deny 专条虽枚举了原因值和文字两个组成项，同一段也说明原因值后可以带文字。按共用字段规则，长度 2 时无文字，仍按 Deny 表读数值；不能因没显示说明就改读 Revoke 表。表中的含义是发包方在报文中给出的原因，不是对对端状态的独立测量。[§8.2.6.1，页 164](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=165)；[§8.2.6.2，页 165](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=166)；[§8.2.10.2，页 170–171](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=171)。

## 要定原因，就把回应与发送侧事件配在一起

- **Deny 3 还是 Revoke 3？** Deny 3 对应的是**拒绝话权请求**；要复核只有一名参与者的原因，查该会话中控制侧收到的 Floor Request 以及当时的参与者记录。与之不同，若控制侧面向该终端的接口处于无权发送且话权已占用状态，收到这个终端带负载的 RTP，指定程序要求不转发这批 RTP、向该终端发 Revoke 3，再转入「无权但仍发媒体」状态。此时要查该终端的 RTP 和权限记录，不数在线人数。这个 Revoke 分支只是例子，不能从原因 3 倒推出唯一的发送状态。[§6.3.4.3.3 第 1–2 项，页 57](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=58)；[§6.3.5.4.6，页 83](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=84)。
- **两包都报 4，是不是同一个动作？** Revoke 4 是发给被抢占者的撤权原因。例如，控制侧处理满足条件的抢占话权请求，并按本地策略选了撤销当前发言者，才在该分支填写 Revoke 4。它不证明旧终端已经停发，也不证明新请求者已经获准。Deny 4 则是对请求的拒绝，说明撤权后的 T9 此时尚未到期；不指定此前是用哪一个 Revoke 原因撤权，也不能凭原因码算出还要等多久。看到一前一后两个 4，要分别对上通话、终端、撤权记录和再次请求，不能只凭数字判是同一次抢占。这里的 T9 既不是 T2，也不是 SIP 的 `Retry-After` 头；原因码表并没有给 T9 时值、启动条件表或重试成功保证。[§6.3.4.4.7 第 1–2 项，页 61–62](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=62)；[§6.3.4.4.4，页 60](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=61)；[§8.2.6.2 的 4，页 165](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=166)。

若还没认出是哪一类 APP 包，见[Name 和 subtype 怎样联读](rtcp-app-name-subtype.md)。要查控制侧是否处在接收请求的空闲态，见[在网话权空闲态](on-network-idle-floor-server.md)；要查抢占与撤权发出后如何继续，见[在网抢占和撤权](on-network-preemption-revoke.md)。
