# MCPTT 在网多人讲话：收到某人释放话权的通知，自己就失去话权吗？

不一定。**先分清是谁放权，再看自己的终端收到通知前处于什么状态。** 例如甲、乙都有话权，乙的终端收到通知，说甲已经释放话权。乙须获知组里有人放权，但乙自己仍有话权。这既不是撤销乙的话权，也不是把甲的话权授给另一位正在排队的人。[§6.2.4.5.9，印刷页 45](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=46)；[§6.2.4.9.14，页 51](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=52)。

**谁发消息，谁结束讲话？** 在 Release 16 的在网 MCPTT 中，话权控制服务器向话权参与端发送 `Floor Release Multi Talker`，表示指定用户已结束本次媒体传输并释放话权。消息中的 User ID 是**放权者的 MCPTT ID**，不是收件人名单；§8.2.14 把在网 SSRC 写成话权控制服务器的 SSRC。主动放权的仲裁规程 §6.3.4.4.6 第 5(a)(i) 项却写成放权参与者的 SSRC。表 8.2.14-1 只列一个 SSRC 栏，也列了 Track Info。不能据此补出第二个 SSRC 栏、裁定线上取哪一值，或只凭 SSRC 判断放权人。这种通知只用于在网模式，单播和 MBMS 承载均可使用。仅凭它不能判定全组话权空闲，也不能判定哪位听众实际收齐或播放了语音。[3GPP TS 24.380 V16.9.0，Stage 3，§8.2.14 开头及 SSRC、User ID 字段说明，页 174](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=175)；[§6.3.4.4.6 第 5(a) 项，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=62)。

**接收端要做什么？** 下列五种状态有同一项要求：终端**必须通知本地用户**，多人讲话组中有一位参与者已释放话权。即使表里的状态不变，通知也不能省略。状态变化看的是接收端自己，不是服务器记录的全组状态。

| 收到前的本端状态 | 仅处理这条通知后的本端状态 | 固定原文 |
| --- | --- | --- |
| 没有话权（U: has no permission） | 仍然没有话权。 | [§6.2.4.3.7，页 39](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=40) |
| 等待请求结果（U: pending Request） | 继续等请求结果；这不是对请求的授予或拒绝。 | [§6.2.4.4.10，页 41](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=42) |
| 已有话权（U: has permission） | 仍有话权。 | [§6.2.4.5.9，页 45](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=46) |
| 已排队（U: queued） | 仍在队列中；这不是获准发言，也没有给出新的队位。 | [§6.2.4.9.14，页 51](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=52) |
| 等待释放结果（U: pending Release） | 若通知是因**本端自己放权**而发，转为没有话权；否则继续等待释放结果。 | [§6.2.4.6.9，页 47](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=48) |

例如乙已发起释放并正在等结果。若收到的是甲放权的通知，乙仍须通知用户，继续等自己的释放结果；若这条通知正是因乙本次放权而发，乙也须通知用户，但应转为没有话权。若记录只保留了消息名称，没有说明是哪次放权所致，就不能判断乙走了哪一支。[§6.2.4.6.9，页 47](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=48)。

## 服务器已收到一名获准者主动放权，还要停其他人的语音吗？

先看控制侧的一般话权仲裁 G。这里是**已建立的普通在网多话者组呼**：G 已在 `G: Floor Taken`，且实际收到名单中一名获准者甲发来的 `Floor Release`。这不是尚未获准的队列请求撤回，也不是撤权或超时。G 须要求媒体分发器停止转发**来自甲**的 RTP，并停掉甲仍在运行的 T2 和 T20。单见这个请求，不证明分发器已经停转。这几步也不要求停止其他获准者的语音；不能据此保证他们的语音已经连续送达。[§6.3.4.4.6 第 1–3 项，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=62)。

多话者分支要求 G 发 `Floor Release Multi Talker`，并从当前获准发言名单移除甲。**移除后名单仍有乙，G 留在 `G: Floor Taken`；名单已空，才进入 `G: Floor Idle` 的规程。** 判断看获准名单，不看这一刻还有几个 RTP 流。不能凭发过放权通知判定全组空闲、整个呼叫结束或下一位已经获准。[§6.3.4.4.6 第 5 项，印刷页 61](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=62)。

## 非控制侧把通知发给谁？

非控制 MCPTT 功能（NCF）的**话权控制服务器接口**实际收到控制功能发来的 `Floor Release Multi Talker` 后，用来向 Track Info 的**最后一个 Participant Reference** 找出目标话权参与者接口 P。只有一个引用时，发往该 P 的消息移除整个 Track Info；有多个时，只移除末位引用，再发给识别出的 P。User ID 指向放权者，末位引用指向这一跳的收件接口。两者可以不同，不能按放权者 ID 替代末位引用，也不能把本款的定向转交当成向全部本地终端广播。没有可用引用时，本款没给默认收件人或回退规则。[§6.5.4.17，印刷页 112](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=113)。

目标 P 每个会话按该客户端单独维护。P **实际收到**服务器接口转来的通知时，原在 `P: has no permission` 或 `P: has permission` 的两支都须发给关联参与者，并保持各自原状态。P 发出不等于终端收到；若终端另有实收，再回到上面的终端状态表。控制侧发出、NCF 服务器接口实收、P 实收和终端实收是四个判断，不用其中一次替其他步骤作证。本段不讨论参与功能的 MBMS 分发。[§6.5.5.1，印刷页 113](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=114)；[§6.5.5.3.12，页 116](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=117)；[§6.5.5.4.9，页 118](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=119)。

若组呼不支持多话者，按[普通在网持有者主动放权](on-network-holder-release.md)的适用条件核对。若事件是新参与者申请发言，则查[多话者容量与抢占](on-network-multi-talker-capacity.md)，不把容量分支套到本次放权。

另一个问题是服务器为何发起撤权，见[在网显式抢占与撤销](on-network-preemption-revoke.md)；若要查新增发言人时服务器选择保留原许可的条件，见[在网双话权入口](on-network-dual-floor-entry.md)。两者都不是收到本通知后要依次执行的步骤。
