# MCPTT 媒体控制收到未知 subtype 或字段，该忽略哪一部分？

先分清接收方不认识的是**整条控制消息的 subtype**，还是**已知消息里的某个字段**。TS 24.380 V16.9.0 对这两类情况规定了不同的忽略范围。预建立会话控制的接收章节对 MCPTT 客户端和参与 MCPTT 功能重申了同样的规则。〔§§8.1.4、8.3.3.9，印 147、179–180〕

| 接收时已确认的情况 | 规范要求忽略什么 |
| --- | --- |
| subtype 未知 | 忽略整条 RTCP APP 消息。 |
| subtype 已知，消息里有本版未规定的字段 | 忽略该字段，例如其他版本增加的项。不能单凭这一项忽略整条消息。 |
| subtype 已知，一个可选字段语法不正确 | 忽略该可选字段。这条不能套在必需字段上。 |

前提是能辨认这条消息及相关字段。若必需字段缺失、必需字段不合法，或无法确定分段边界，这几条没有给出通用的恢复或接收规则。忽略某个字段也不代表其余内容已经符合该消息的条件，更不代表已应答或已改变话权、会话状态。先用[Name 和 subtype 确认消息族](rtcp-app-name-subtype.md)，再查该消息自己的程序。日志没有打印 subtype 或字段，不等于接收端不认识它。〔§§8.1.4、8.3.3.9〕

## 一份 IP 报文有多条控制消息，只忽略其中一条是什么意思？

§8.1.1 把每条媒体控制消息描述为一个 RTCP APP 包，不按复合 RTCP 包发送；同一个 IP 报文却可以承载多条媒体控制消息。假如能够分别识别出两条消息，并确认其中一条**预建立会话控制消息**的 subtype 未知，忽略的对象是那一条 APP 消息，不是其中某个字段。不能仅因这条 subtype 未知，就把 §8.1.4 的“整条消息”当成丢弃整个 IP 报文的要求。另一条也不能因此自动算作处理成功。〔§8.1.1，印 145；§8.1.4，印 147；§8.3.3.9，印 179–180〕

排障记录分开写：IP 报文是否到达、其中各条 APP 消息是否可识别、接收方忽略了消息还是字段、是否出现相应的业务响应。只有适用的程序与实际记录能说明这一次 [预建立会话 Connect](preestablished-connect-outcome.md) 或 [终端话权响应](on-network-floor-client.md) 到了哪一步。
