# 离网 MCPTT 组呼：收到授给乙的消息，接收端何时应请求播放乙的语音？

丙已加入一通普通离网 MCPTT 组呼，没按 PTT，也没排队。此刻丙正在收甲的语音，本机的话权状态是 `O: has no permission`（无发送权），保存的当前仲裁者是甲。**丙收到甲发来的 Floor Granted，消息授给乙而不是丙。丙应请求客户端停播，把乙记作候选，当前仍是甲。** 单看这条授予消息，不能确认丙已收到乙的 RTP 语音包，也不能确认丙已听见乙。

若没有其他事件介入，下一份 RTP 来自乙，丙应请求播放乙，把乙记为当前；若下一份来自甲，则请求播放甲。两条分支都清候选，也都不给丙发送许可。若丙刚加入、仍在 `O: silence`（静默）、没有保存当前甲，同一条授给乙的消息也会让丙记下候选乙，但这一步**不要求停播**。

“不能发语音”不足以判断丙处在哪个话权状态：处于 `O: silence` 的丙也不能发。要查丙应如何处理一条消息，先查收包当时本机会话中的话权状态名。SSRC 是同步源标识；下文以甲、乙代指各自的 SSRC。**当前**指丙记录的当前话权仲裁者，**候选**指可能接任的人。两项都不是扬声器的播放记录。核对次序看控制消息和 RTP 在**丙端**的到达顺序，不用发送时间重排。[3GPP TS 24.380 V16.9.0，Release 16，Stage 3，§7.2.3.1，印 121](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=122)

## 刚加入时，先收到的是消息还是语音？

普通组呼以终接成员身份启动话权时，丙创建本地话权实例，启动 T230（静默失活计时），进入 `O: silence`。此时没有发起话权请求，也没有在接收 RTP。下列是**三个可替代的入口**，不是须按顺序收齐的三条记录。[§7.2.1，印 120](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=121)；[§7.2.3.2.3，印 123](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=124)

| 丙在静默中收到什么 | 丙应记谁？此步要求播放吗？ |
| --- | --- |
| 甲的 RTP，未保存当前 SSRC | 取该包的 SSRC 记甲为当前，请求客户端开始播放所收 RTP。若原已保存当前且包源匹配，也应请求开始播放，无须重新指定当前。 |
| Floor Granted，其中 User ID 不是丙，授给乙 | 把被授者乙的 SSRC 记为候选；这一步不把乙设为当前，也不要求播放。静默中的这一条没有要求发送者先匹配已存当前。 |
| Floor Taken，其中被授方的 SSRC 为甲 | 取消息中 **SSRC of granted floor participant** 字段，记甲为当前，不是候选。这里只收到了话权消息，还没有可据此要求播放的语音包。 |

三条分支都停 T230，进 `O: has no permission`（本机无权发媒体）。对于 RTP，启动或重启 T203；对于上述两种控制消息，启动 T203。T203 名为“RTP 媒体结束”计时器，它开始运行不证明已经收到第一个包。在没有已存当前而收到首个 RTP、收到上述 Granted 或 Taken 的三个入口，均可提示用户话权已被占用；缺少提示不能推翻这些记录。[§§7.2.3.3.1、.3、.4，印 125–126](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=126)；[§§7.2.3.3.6、7.2.3.4.1，印 126](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=127)

## 正在收甲：一条授予记录，两种接续结果

此时丙的话权状态是 `O: has no permission`，已记甲为当前。读 Floor Granted 要分开看：**谁发的**，用来匹配丙所记当前甲；**授给谁**，消息中的 User ID 必须不是丙自己的 MCPTT ID，候选要取被授者的 SSRC，不能抄发送者甲的 SSRC。两项条件均满足，丙须请求停播、重启 T203，记乙为候选，保留当前甲，仍无发送权。普通组呼的占用提示可选。如果工单只写“授给乙”，要补查消息到达时丙的话权状态和已存当前 SSRC，再核对发送者 SSRC、User ID 是否指向别人以及被授者 SSRC。缺了这些，不能签这一步的停播请求。[§7.2.3.4.5，印 127–128](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=128)

| 丙处于 `O: has no permission` 时收到的 RTP | 丙须对该包做什么？处理后记谁？ |
| --- | --- |
| 当前甲、候选乙；乙的包先到 | 请求播放乙的包，把乙改为当前，清候选。 |
| 同样是当前甲、候选乙；甲的包先到 | 请求播放甲的包，甲仍是当前，**清候选乙**。不能拿此前那条 Granted 继续给后来乙的包作候选匹配。 |
| 没有已存当前，即使已有候选乙；收到丁的包 | 先走“无当前”分支，不要求丁匹配候选。请求播放丁的包，记丁为当前，清除已有候选。 |

这三个分支都重启 T203，丙保持 `O: has no permission`。把第三行的本地状态换成 `O: silence`，其余观测不变：无已存当前、快照仍显示候选乙，收到丁的 RTP。此时应按静默分支记丁为当前、停 T230、启动或重启 T203，请求开始播放丁的包，再转入 `O: has no permission`。静默分支没有要求这一步清候选，不能照搬第三行。两种初态虽都不能发媒体，处理却不相同。[§7.2.3.3.3，印 125](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=126)

要判断“丙应请求播放乙”，需有符合对应分支的乙的 RTP；要记“客户端已执行播放”，还需播放器侧证据。“用户确实听见”又不是仅凭抓包或播放请求能确认的事实。[§7.2.3.4.6，印 128](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=129)

## 什么情况下请求停播？回到静默算退组吗？

仍从丙的 `O: has no permission` 状态、当前甲、候选乙开始，比较两份独立记录：

- **丙收到 Floor Release。** 消息里的 SSRC 匹配当前甲**或**候选乙，就须请求停播，停止 T203，启动 T230，**清当前和候选**，转入静默。匹配乙不要求乙已经发来 RTP；若只见别的 SSRC 发来 Release，不能套用此分支。
- **没有匹配的 Release，丙的 T203 到期。** 丙也须请求停播、启动 T230、转入静默；条款只要求**清当前**，没有规定在这一步清候选。不能据此把“已清候选”写进记录，也不能反推候选以后一定保留。这两个回静默的分支都可以提示用户话权空闲，并非必须提示。[§§7.2.3.4.3–4，印 127](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=128)

**只有 T230 到期日志，能签“本地话权实例已终止”吗？不能。** T203 到期后的规定结果是回静默，不是终止实例。丙在 `O: silence` 中等到 T230 到期时，须向呼叫控制报告这次到期，终止本地话权参与实例，并回到 `Start-stop`。到期日志证明的是触发事件；到这里为止，上述三项都只能记为**应执行**，不能记为已执行。

核现场结果，要对上丙的同一实例和这一次到期。另有“实例终止完成”记录，可确认本地终止动作已完成；另有状态转入 `Start-stop` 的记录，可确认已进入该后态。终止完成记录不是状态迁移记录，后态记录也不单独证明终止动作已执行；两者都不是给呼叫控制的通知凭据。即使本地话权实例确实已终止，规范也只说这**可能**导致呼叫会话终止，不能据此认定整通呼叫或全组已结束。[§7.2.3.3.7，印 126](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=127)；[§7.2.2，印 121](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=122)

本页只查已经入呼、未请求话权的普通离网组呼接收端。若在查本机如何探测、接受或退出组呼，见[普通离网组呼的加入与退出](../calls/offnetwork-group-client.md)；本机已经按键、排队或刚把话权交给别人，见[离网话权参与者的请求、排队与交接](../calls/offnetwork-floor-participant.md)。

另看两份在网服务器工单。都是普通 MCPTT 单话权呼叫，服务器不支持多发言人控制，也都已经授予甲话权。若要查**服务器授予后收不到甲的 RTP，或甲这次发言达到时限**，见[在网服务器的 T1/T2 媒体超时](on-network-floor-media-timeouts.md)。若甲的 RTP 仍在到达，记录写的是另一人请求抢占、服务器因此选择撤销甲的话权并启动 T3，就应按**抢占与撤销**查，不能凭同一台服务器启动了 T3 判作媒体超时。只有 T3 记录而不知何事触发撤销，也分不出原因。这两种工单都不适用离网接收端的 T203/T230。
