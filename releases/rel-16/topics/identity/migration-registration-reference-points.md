# 迁移注册时看到 Cx：这是 AAA-1 查库，还是 AAA-2？

先核对两端的**功能角色**和这笔操作的用途。SIP 核心向 SIP 数据库取信令面资料，以及迁移时为 SIP 注册与 Diameter 代理交互，都用 Cx。只看 Cx，不能把这两笔记成同一个参考点；只看哪一方的网络，也不能代替端点信息。[TS 23.280 V16.7.0，Release 16，Stage 2，§§7.5.3.8–.9，印刷页 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=44)。

| 这笔操作已核实的两端和用途 | 参考点 |
| --- | --- |
| SIP 核心与 SIP 数据库。核心从库中取得信令面资料。 | **AAA-1**，使用 Cx。规范列了一个跨网例子：注册器和 SIP 库在 MC 业务提供方网络，查找注册器的功能在 PLMN 运营方网络。跨网本身不会把它变成 AAA-2。 |
| SIP 核心（或 IMS）与 Diameter 代理。该交互用于用户迁移期间的 SIP 注册，为迁移向业务层提供认证和安全支持。 | **AAA-2**，须使用 Cx。终端的信令用户代理与核心之间另有 SIP-1，不能把它记成核心到代理的这段。参见 [§7.5.3.2，印刷页 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=43)。 |

如果记录只写“Cx”，看不到是与数据库还是代理交互，也不知道在办什么，就先把参考点记为未确定。即使已确认是 AAA-1，跨网也不决定库的访问权限；仍要按谁服务此用户、对所提供的数据是否同属信任域核对。这里判的是两段逻辑参考点，不给出 Diameter 命令、AVP、报文顺序或实际认证结果。[§§7.5.3.8–.9，印刷页 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=44)；[§7.4.3.2.1，印刷页 36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=37)。

## 没在核心外看到 Diameter 代理，验收就失败吗？

不能仅据此判失败。用在 AAA-2 上的 Diameter 代理**可以位于 SIP 核心或 IMS 内部**；代理实例数量由部署决定。标准没有要求另装一台外置代理，也没有规定合设后必然抓不到这段信令。要核实这次注册实际走了哪项功能，查核心的实际部署和这笔操作的记录；仅在某个外部观察点没看到对等连接，不能证明没有代理、没有注册或注册失败。[§7.4.3.1.4 正文及注，印刷页 36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=37)。

## 已注册，能不能登记为已获伙伴业务许可？

不能用它代替该业务的迁移授权结果。AAA-2 说明迁移注册用到的接口及其认证和安全用途；识别出接口不等于取得某次认证成功的证据。即使另有证据确认用户已成功注册并取得申请业务授权所需的凭据，伙伴业务服务器仍要检查能否接纳来自该用户主系统的迁入；主系统业务服务器另查这名用户能否使用所选配置档迁到该伙伴。若在客户端验收，核对伙伴业务服务器发来**与本次请求对应的迁移业务授权响应及其结果**。仅看到响应名称、发送记录，或主系统写下迁移记录，都不能代替客户端实际收到成功结果。[表 10.6.3.2.2-1 与 §10.6.3.3 前提，印刷页 116](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=117)；[步骤 1–2、6–8 及 11，印刷页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=118)。
