# 用户配置档：在主系统下载哪些，迁到伙伴系统又取哪一份？

在主系统，需要下载时，配置管理服务器返回**请求中的 MC 业务 ID 关联的全部用户配置档**。迁到伙伴系统时，终端向**伙伴系统**要档，主系统按**目标伙伴系统的标识**找出适用于这次迁移的档。前者按用户的业务 ID 确定下载范围，后者还要区分用户迁往哪里。[3GPP TS 23.280 V16.7.0，Release 16，Stage 2，§§10.1.4.3.1–2，印刷页 72–74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=73)

## 在主系统：有几份关联档，要送几份？

用户已在身份管理服务器完成认证，终端能安全访问配置管理服务器。终端的配置管理客户端向配置管理服务器请求取档，请求必带该用户的 MC 业务 ID。服务器取得相应配置信息，再向客户端答复。通用响应表把配置档数据列为必填，描述为与请求 ID 关联的一份或多份档；主系统流程第 3 步进一步说明：**需要下载时，响应包含该 ID 的所有关联档**。若该 ID 关联三份档且本次需要下载，就是三份。不能仅凭一次重连或响应的名称便认定每次都发生了全量下载，也不要由此推定不需要下载时有一个不带数据的响应。[表 10.1.4.2.1-1、10.1.4.2.2-1，印刷页 69](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=70)；[§10.1.4.3.1，前提及步骤 1–3，页 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=73)

**清单只列了两份档，算漏下载吗？** 用户档配置可以分多次交换。配置管理服务器可以向终端提供一份清单，列出部分或全部已启用的档，供用户选一份。清单可以只带足以区分候选档的资料。假如同一业务 ID 关联的甲、乙、丙三份档都已启用，清单只列甲和乙，不能据此判定丙漏下载。若确认收到的是上面第 3 步的取档响应，而且本次确需下载，响应仍须包含该 ID 的所有关联档。§10.1.4.1 没有指定清单用什么报文，也没有规定取档必须先发清单。[§10.1.4.1，印刷页 68 末段及 69 页续文](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=69)；[§10.1.4.3.1，步骤 3，印刷页 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=73)

**用户选了一份，哪份档在用？** 在主系统，已认证用户的配置包含多份用户档时，完成业务授权后，MC 业务客户端和业务服务器把配置好的预选档设为活动档。仅凭清单或用户作出的选择，不能确认预选已改、业务已获授权或当前活动档已切换。核对预选变更或在服切换，见[预选与当前配置切换](user-profile-switch.md)。[§10.1.1.1，图 10.1.1.1-1 后第 2 段第 3 句，印刷页 59](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=60)

## 迁到伙伴系统：谁取档，谁改档？

这条流程有三个前提：① 用户获准迁往目标伙伴系统，两边都已配置相关授权；② 用户已在伙伴系统完成 MC 业务用户认证，并取得读取配置、请求业务授权所需的凭据；③ 终端已有地址信息，让配置管理客户端能够访问伙伴的配置管理服务器。**能请求业务授权不等于已经获得该业务授权**：取迁移档在向伙伴业务服务器请求业务授权之前。[§10.1.4.3.2 的前提，印刷页 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=73)；[§10.1.4.1，页 69](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=70)

终端先向**伙伴配置管理服务器**要迁移档。伙伴服务器再向主系统的配置管理服务器请求；主系统按目标伙伴系统的标识，从**主系统的 MC 业务用户数据库**取出相应的档，交给伙伴服务器。因此，同一用户迁往不同伙伴时，可以用不同的档，并非一定不同。伙伴系统按本地配置信息修改收到的档，把修改后的档存入**伙伴系统自己的 MC 业务用户数据库**。此时证明的是伙伴侧已经保存，不是终端已收到。[§10.1.4.1，印刷页 68](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=69)；[§10.1.4.3.2，步骤 1–5，页 73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=74)

## 修改后必须回传主系统吗？验证失败还能交给终端吗？

主系统在交档时**可以**要求验证修改后的配置档（步骤 4）。**如果主系统提出了要求，伙伴服务器可以把修改档发回主系统**供验证（步骤 6）；提出要求也不能证明伙伴已经回传。步骤 7、8 描述主系统验证修改档、向伙伴返回验证结果；不能倒过来据此认定每次迁移都必须回传并验证。步骤 9 才是伙伴配置管理服务器把档交给终端配置管理客户端。条款明确说明：**如果验证失败，不执行步骤 9**。没有看到验证结果，也不能据此断定流程已失败或终端已经收到档。[§10.1.4.3.2，步骤 4–8，印刷页 73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=74)；[步骤 9 及其注，页 74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=75)

## 同一次迁移取档，哪一段是跨系统，哪一段是读写用户库？

甲是用户林的主系统，乙是目标伙伴。**林获准由甲迁往乙，甲、乙是分属不同安全域的 MC 系统。** 乙的配置管理服务器（CMS）向甲的 CMS 要林的迁移档，甲的 CMS 把选出的档给乙的 CMS。两端均为 CMS，为获准在这两个系统间迁移的用户共享配置。对这样的**非订阅、非通知**信令，应用面参考点是 **CSC-17**，用 **HTTP-1、HTTP-2、HTTP-3** 传送和路由。这是按端点、用户和操作给步骤 2、4 的系统间交换归类，不是把步骤编号换成 HTTP 跳序。林的客户端向乙 CMS 要档、乙 CMS 向客户端交档，都不是 CSC-17。若两个 MC 系统处在同一安全域，该条就不适用；若只是查不到林的迁移许可，则应把适用性留作待核，而不是认定林被拒。[§7.5.2.17，印 41](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=42)；[§10.1.4.3.2 前提及步骤 1–5，印 72–73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=73)；[步骤 9 及注，印 74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=75)。

**查用户库，要分主侧读和伙伴侧写。** CSC-13 的一端是 CMS，另一端是指定的 MC 业务用户数据库。它供 CMS 往该库存用户配置档数据，或从该库取得用户配置档，用于后续配置 MC 业务终端。步骤 3 明写甲的 CMS 按乙的系统标识，从甲的用户库取出林的迁移档；这对角色和用途符合 CSC-13 的读取情形。步骤 5 写的是**乙系统**按本地配置修改档，再存入乙的用户库。乙库已存修改档可以有独立证据；要把这次写入也认作 CMS 与用户库之间的 CSC-13 操作，还得核对写入方在这笔事务中的角色。仅凭步骤 5，不能点名某台 CMS 已经写入。§7.5.2.13 也没有给这一数据库操作指定 HTTP 或 SIP 方法。[§7.5.2.13，印 40](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=41)；[§10.1.4.3.2 步骤 3–5，印 73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=74)。

例如，乙库留有修改档，甲随后验证失败：前者可以是真，乙仍不执行向终端交档的步骤 9。即使甲确认验证通过，也要另核乙给林的客户端交档、客户端实际收档的记录。一份客户端本地档或一条未标对象的双网关 SIP-3 记录，都不能替主系统的用户库证明本次读取。[§10.1.4.3.2 步骤 3–8，印 73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=74)；[步骤 9 及注，印 74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=75)。

若终端已收到档，仍要分清问的是什么：要判断**下次授权预选哪一份，或某客户端当前已改用哪一份**，查[预选与当前配置切换](user-profile-switch.md)，不能用取档结果代替选择结果。若已有档，问题是**收到变更通知后怎样取得新值，或如何把修改写回**，查[配置档数据更新](user-profile-data-update.md)。[§§10.1.4.4–7，印刷页 74–77](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=75)

若已确认另查的是**为允许系统间迁移而跨系统共享用户配置的订阅或通知**，要区分配置管理服务器与 MC 网关、以及异系统异安全域的两个 MC 网关，见[配置订阅与通知的参考点](../groups/partner-group-configuration.md)。只有一条没有对象或用途的 SIP-3 记录，不足以断定是这类业务。
