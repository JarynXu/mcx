# 功能别名现在由谁使用：业务服务器或 LMS 收到什么才知道名单？

位置管理服务器（LMS）订了“北站值班”。负责控制这个别名的 MC 业务服务器答复“成功”，LMS 还不能据此把甲写成当前值班人，也不能把名单清空。**订阅响应给的是这次请求的成败；名单在控制服务器另发的通知请求里。** 普通 MC 业务服务器也可作订阅方。名单列的是激活这个别名的用户的 **MC 业务 ID**，不是所有获准使用该别名的人，也不是通知的收件人。这是 3GPP TS 23.280 V16.7.0（Release 16，Stage 2）的在网程序。[§10.13.1，印 192](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=193)；[§10.13.10.1–2，印 203](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=204)。

## 六条消息，哪条有名单？

用 F 表示被订阅的一个功能别名。“控制方”是控制 F 的 MC 业务服务器；“订方”是希望获知 F 使用者的业务服务器或 LMS。下表列出各信息流表中的全部信息项，**列出的项都是必备项（M）**，不是对线上编码或其他协议字段的规定。

| 已认出的消息 | 从谁到谁 | 本条信息流要求什么 |
| --- | --- | --- |
| 订阅请求 | 订方 → 控制方 | F、订阅类型：一次通知或持续通知。完整请求少了类型，不能补作某种默认订阅。 |
| 订阅响应 | 控制方 → 订方 | F、订阅请求的成败。不含使用者名单这一项。 |
| 通知请求 | 控制方 → 订方 | F、已激活 F 的用户的 MC 业务 ID 清单。清单可以为空。 |
| 通知响应 | 订方 → 控制方 | F。表中不列成败、名单或保存结果。 |
| 退订请求 | 订方 → 控制方 | F。请求停止向这个订方通知 F 的使用者。 |
| 退订响应 | 控制方 → 订方 | F、退订请求的成败。不是任何一个用户停用 F 的结果。 |

[表 10.13.2.11-1、12-1，印 195](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=196)；[表 10.13.2.13-1 至 16-1，含清单表注及各节引言，印 196](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=197)。

**同一方向、相同字段，可能是不同操作。** 限于上面六种信息流，并且所列字段完整：“控制方 → LMS，F、成功”既符合订阅响应，也符合退订响应；“LMS → 控制方，只有 F”既符合通知响应，也符合退订请求。先查操作类型；类型没留下，还可以找能与本条配对的另一条消息，不论它在前还是在后。例如，随后有一份**已识别为退订响应、且确实对应本条**的答复，那么 LMS 发出的仅 F 就是退订请求。只因两条记录相邻，不能这样配对。若字段本已截断，不应把以上两个候选当作全部可能。已认作通知响应时，它只证明订方作了回应；要给名单写库签字，还得有写入结果。

## 控制方发给订方的名单通知请求：清单是空的，还是没显示？

订阅程序的前提是控制方持有 F 的已激活用户名单，条文未要求至少一人在用。订方指定一次或持续通知，控制方回订阅成败。这里没另列控制方对订方执行用户查询授权的步骤，不表示订阅一律免授权。条文也没说成功后立即发第一份名单，或一次通知的订阅在哪个时点自动拆除。[§10.13.10.2，前提，印 203](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=204)；[图 10.13.10.2-1、步骤 1–2，印 204](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=205)。

图示的**变更通知**有两个前提：订方已订 F；控制方所持 F 的名单因激活、停用或接管而改变。仅有接管提议，不等于名单已变。满足前提时，控制方向订方发名单，订方向控制方回复。不用先证明现场发生过变更，才可按信息流表核对一份已认明类型的通知；反过来，只有服务器出站记录，不能说订方已收到。[§10.13.10.3，前提、图 10.13.10.3-1 与步骤 1–2，印 204](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=205)。

例如，乙原来独自使用 F。LMS 后来确实收到一份针对 F 的名单通知，清单项存在但没有条目：**这份通知报告的是无人激活 F**，不是 F 已不存在。对已经认明类型、内容完整的名单通知请求，清单和 F 缺任何一项都不满足表的要求；若值班摘要只显示 F、其余字段已隐去，就连原通知是否有清单也不知道。后二者都不是清空原记录的依据。若通知列了乙、丙，能认定收到的是这两人的业务 ID，不因此获得他们的位置；要证实数据库已经更新，还得看对应的写入结果。[表 10.13.2.13-1 与表注、表 10.13.2.14-1，印 196](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=197)。

**退订不会撤掉谁的值班身份。** 退订程序同样列出控制方持有 F 名单的前提。LMS 的目标是自己不再接收 F 的名单通知，控制方答复这次退订是成功还是失败。请求已发还不是成功；失败也不告诉 LMS 眼下谁在用 F。成功不等于乙停用 F，更不能替另一台订阅服务器退订。原文表 10.13.2.16-1 的引言和 §10.13.10.4 步骤 2 写的是 subscribe response（订阅响应）；同处的表题、图及操作目的都指退订响应，不是退订后另发一次订阅。[§10.13.10.4 前提，印 204](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=205)；[图 10.13.10.4-1、步骤 1–2，印 205](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=206)；[表 10.13.2.16-1，印 196](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=197)。

## 工单问的是另一件事时

- 用户在业务客户端只查一眼谁在使用 F，读[按别名或用户查询当前使用情况](active-functional-alias-lookup.md)。那是客户端查询，有自己的授权检查和空结果；和服务器订“一次通知”不是一个操作。
- 已认出是拥有该别名的 **MCPTT** 服务器收到 **SIP SUBSCRIBE**，要解释 200、423 或 NOTIFY 中的用户，读[MCPTT 功能别名解析订阅](alias-owner-resolution-subscription.md)。不能用公共信息流表推算 SIP 状态码。
- 终端的别名管理客户端收到新配置的引用，读[功能别名配置通知与取档](functional-alias-configuration.md)。同系统的业务服务器因排班等自身条件触发，要判断还能否给新人激活别名，读[服务器自动激活](functional-alias-automatic-activation.md)，不必先证实激活成功。获授权用户在激活程序中获悉别名仍由他人使用、可提出接管，要查其是否申请及服务器如何裁决，读[用户申请接管](functional-alias-takeover.md)。若在同一 MC 系统按别名请求同一业务内多名已激活者的位置，读[按活动别名取位置](../location/active-alias-trigger.md)并核对该流程前提。
