# 收到功能别名配置通知，终端就有新配置了吗？

没有这层保证。**通知告诉终端哪份配置信息可取；取档响应才带配置数据。** 即使终端已回复通知，也不能据此断定它取过数据，更不能断定已在本地保存。这里讨论 Release 16 中功能别名管理客户端与服务器之间的 Stage 2 流程。[3GPP TS 23.280 V16.7.0，§§10.1.7.1–2，印刷页 84–86](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=85)

## CMS 发了配置通知，它就是这个别名的控制方吗？

不能只凭这条通知判断。取档、订阅和配置通知由功能别名管理客户端与服务器办理。在本版功能模型中，**配置管理客户端**提供功能别名管理客户端职能，**配置管理服务器（CMS）**提供功能别名管理服务器职能。取别名配置时，终端的日志若把客户端记为“配置管理客户端”，这与角色分工并不矛盾。[§§7.4.2.2.1–2 末段，印刷页 32](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=33)

要查某个别名的启用、停用或接管，找承担该别名控制职责的 **MC 业务服务器**。只知道 CMS 发了这项别名的配置通知，不足以认定它承担控制职责。这些是功能角色，不规定它们部署在同一台还是不同的机器上，也不指定这笔交易实际用了哪个 URI。[§7.4.2.3.2 末段，印刷页 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=34)；[§7.4.1，印刷页 31](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=32)

## 何时可以取档，谁来取？

一种情形是：业务授权后，**配置管理客户端**已收到功能别名清单，而**功能别名管理客户端**需要取得相应配置。另一种情形是别名管理服务器已通知有新配置可取。收到清单不等于收到配置，收到通知也不要求立即下载。取档程序的前提是：别名管理服务器已收到并保存配置；终端已注册业务，且别名管理客户端需要下载适用于当前用户的配置。[§10.1.7.1，取档时机与前提，印刷页 84](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=85)

取档时，别名管理客户端向别名管理服务器发送请求，必须给出**别名 URI** 和**配置信息引用**：前者标识哪个别名，后者指向该别名的配置资料。可以再列出所需的业务，在 MCPTT、MCVideo、MCData 中指定一项或多项。不列时，请求的是**为这个别名定义的全部业务**。例如，若该别名只定义了 MCPTT 和 MCData，不列业务就请求这两种的配置，并不增加 MCVideo，也不扩大授权。服务器的取档响应必带别名 URI 和配置数据；下一步是**客户端**保存收到的配置。只看到服务器返回数据，不能证实客户端已保存。[表 10.1.2.9-1（含注）、10.1.2.10-1，印刷页 63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=64)；[§10.1.7.1，步骤 1–3，印刷页 85](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=86)

## 订阅成功和通知成功，各能说明什么？

客户端要持续接收**获授权别名**的配置更新，可以向别名管理服务器订阅。前提是服务器已有一些别名配置。订阅请求必带别名 URI；所需业务可选，省略时仍限该别名定义的全部业务。和取档请求不同，订阅请求表没有列配置信息引用。服务器向客户端返回别名 URI 和订阅结果（成功或失败）；成功说明订阅请求成功，不等于交付了一份配置。[§10.1.7.2，订阅前提与步骤 1–2，印刷页 85](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=86)；[表 10.1.2.11-1（含注）、10.1.2.12-1，印刷页 64](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=65)

服务器通知客户端时，有两件事已经成立：**客户端已订阅，该服务器已收到并保存新配置**。条款没有规定这两件事彼此谁先谁后。通知请求由服务器发给客户端，必带别名 URI 和指向已存资料的引用。客户端向服务器回复别名 URI 和通知结果（成功或失败）。这个结果针对通知，不能充当取档回执。接到通知后，客户端**可以**另走取档程序；要确认新配置已在终端保存，应再看取档响应里的配置数据，以及客户端的保存结果。[§10.1.7.2，通知前提、步骤 1–2 及后续取档说明，印刷页 85–86](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=86)；[表 10.1.2.13-1、10.1.2.14-1，印刷页 64](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=65)

配置流程本身不证明某个别名正在使用或已被停用。要查“现在谁在用”，看[活动别名查询](active-functional-alias-lookup.md)；要查“用户没申请，别名为何停用”，看[所有者自动停用](owner-alias-auto-deactivation.md)。若要判断 MCPTT 客户端如何申请启停或接收别名状态，查[MCPTT 别名客户端协议](mcptt-functional-alias-client.md)，不要把状态订阅当成上面的配置订阅。
