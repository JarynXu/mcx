# MC 业务客户端申请停用多个功能别名：怎样确认每个别名的结果？

看服务器**单独寻址给请求客户端的停用响应**。例如甲的客户端请求停用 F 和 G，后来只收到一份提到 F 的组播状态通知。那份通知可以说明它列出的用户和别名状态，不能充当这次请求对 F 和 G 的逐项响应，也不能用 F 的状态判断 G。

## 离开区域可以触发请求，不等于服务器自己停用

在同一个 MC 系统内，业务服务器已经向功能别名管理服务器订阅别名信息，并保存了用户已启用的别名数据。用户可以让客户端停用别名，也可能是客户端检测到触发事件，例如终端离开该别名允许使用的区域。两种情况走的都是**客户端明确发出停用请求**。只知道终端离开区域，不证明它发了请求，也不证明服务器已停用。

请求带发起者的 MC 业务 ID 和待停用的一个或多个别名。收到请求的业务服务器若不负责控制这些别名，就把请求转给承担功能别名控制职责的业务服务器。控制侧根据用户的业务签约和保存的别名策略，检查甲有无权限停用，并检查甲本人此前是否已经启用所请求的别名；别人的启用状态不能替代甲的。确认停用获授权时，服务器更新的是**甲的启用状态**，不是清除别名或其他使用者的关联。原文没有为“查不到甲的启用记录”单列错误码。

依据：[TS 23.280 V16.7.0，Release 16，Stage 2，§10.13.5](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=199)，印刷页 198–199；[§10.13.2.5，表 10.13.2.5-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=195)，页 194。

## 看的是请求结果，还是给其他使用者的状态通知？

| 要判断的事 | 查什么 |
| --- | --- |
| 甲申请的 F 和 G 各是什么结果 | 停用响应。服务器给请求客户端单独寻址，可以经单播或组播发送。响应必带发起者的 MC 业务 ID、请求的别名列表及**列表中每一个别名**的停用结果。组播承载不等于按组寻址。 |
| 其他共享别名的用户被告知什么 | 功能别名状态通知。服务器通知共享同一别名的其他用户；通知可单独或按组寻址，可走单播或组播。通知带发起者的 MC 业务 ID、所列别名及各项的操作状态，不是请求方的结果清单。 |
| 其他服务器是否会获知状态 | 本程序还说明，系统内订阅了功能别名状态的其他服务器也获通知。这与给请求客户端的响应、给共享用户的通知是三件事。 |

如果手头只有 F 的通知，先核发起者和 F 的操作状态。没有 G 的结果，就保留未知；不能根据通知的传输方式、只见一项，或其他用户是否收到通知，推断两项都成功或都失败。本版这些条款给出信息项，不规定停用状态的枚举值、逐项失败码、SIP 字段或终端缓存更新算法。

依据：[§10.13.5 步骤 3–5 和注 2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=200)，印刷页 199；[§10.13.2.6–.7、表 10.13.2.6-1 和 10.13.2.7-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=195)，页 194。

这里是 MC 业务的 Stage 2 通用流程。要看特定的 MCPTT 手动申请和 SIP PUBLISH、NOTIFY 观察方法，查[客户端启停申请与状态](mcptt-functional-alias-client.md)。如果**没有收到客户端请求，实际触发来自拥有别名的 MCPTT 服务器或管理员**，查[所有者自动停用](owner-alias-auto-deactivation.md)，不要套用这里的逐项响应。
