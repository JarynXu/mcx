# 运营方管理 SIP 核心，终端用的 IMPI、IMPU 就由运营方提供吗？

不一定。对接资料如果只写「PLMN 运营方管理 SIP 核心」，还不能据此填写终端的 SIP 身份来源。3GPP TS 23.280 V16.7.0（Rel-16，Stage 2）给出了一个反例：在 **§9.2.2.1.6 的部署**中，公共陆地移动网（PLMN）运营方管理 SIP 核心；对该 MC 业务提供方所服务的终端，核心使用的 IMPI 和 IMPU **均由这家业务提供方的 SIP 数据库提供**。若站点确认采用此方案，应向业务提供方核实这两种身份的供应，而不因核心归运营方管理就改找运营方配号。[§9.2.2.1.6 首段及图 9.2.2.1.6-1，印刷页 52–53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=53)

**那运营方的核心靠什么认证？** 在上述部署中，访问信令控制面所需的认证根保存在业务提供方的 SIP 数据库，运营方拿不到这些根。SIP 核心得到的是完成该层认证所需的派生参数。应用层是另一回事：业务提供方可以要求应用层的全部身份和信令对 SIP 核心和 EPS（演进分组系统）隐藏；按业务提供方的要求，应用层的认证和授权机制（包括安全根）也可能需要对运营方隐藏且不可用。核心能做信令认证，不能据此认定运营方掌握认证根，或已取得应用层用户资料；也不能把可提出的应用层隐藏要求写成每一站的既成事实。[§9.2.2.1.6 图后各段，印刷页 53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=54)

## 知道业务服务器在哪一方网络，能定位哪个库？

能定位 **MC 业务用户数据库所属的网络**：业务用户库与 MC 业务服务器总在同一网络，要么都在运营方网络，要么都在业务提供方网络。若服务器在业务提供方网络，将它的业务用户库仅部署在运营方网络便不符合这项条件。这条同网要求没有指定哪一台主机，也没有给出 SIP 数据库或归属用户服务器（HSS）的位置。[§9.2.2.2 注 2，印刷页 53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=54)

读部署图时，先找业务用户库、SIP 库和 HSS 各自的边框，再看文字说的是哪一方网络。§9.2.2.2 给出四种摆法，不是 §9.2.2.1.6 的四个步骤，也不能按 SIP 核心的管理者直接选一幅。

|---|---|---|
| [-1，印刷页 54](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=55) | 业务用户库、SIP 库均与 HSS 合设 | 承载它们的 HSS 可在运营方或业务提供方网络。 |
| [-2，印刷页 54](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=55) | SIP 库与 HSS 合设，业务用户库另设 | 业务用户库可在任一方网络，HSS 可与之同网，也可在另一方网络。 |
| [-3，印刷页 55](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=56) | 业务用户库和 SIP 库合设，HSS 另设 | 两库可同在任一方网络。另设的 HSS 仍可与它们同网。也可在另一方网络。 |
| [-4，印刷页 55](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=56) | 三者分设 | 三者可分布在两方网络，也可同处一方网络；业务用户库仍须与业务服务器同网。 |

例如，业务用户库、SIP 库、HSS 都在运营方网络，既可能像图 -1 那样合设，也可能像图 -4 那样分设。即使明确采用图 -1，仍能在图中分别指出为业务服务器提供用户数据的业务用户库和为 SIP 核心提供数据的 SIP 库。**合设本身不说明共用一张逻辑表、一个进程或某台具体主机。** 原文把「业务提供方与运营方同一信任域」作为业务用户库可与 HSS 合设的例子；不能倒过来，仅凭合设认定两家同属一个信任域。[§9.2.2.2 首段及后文，印刷页 53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=54)；[图 -1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=55)、[图 -4](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=56)。

还有两个可选实现要靠部署资料确认：

- **如果把 SIP 库设在核心内部，AAA-1 还对外显露吗？** 不显露。仅因外部没有观察到 AAA-1，既不能断定没有 SIP 库，也不能断定库就在核心内部。[§9.2.2.2 注 1，印刷页 53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=54)
- **采用 UDC 架构，就一定用 UDR 承担业务用户库吗？** 不一定。采用用户数据融合（UDC）架构时，业务用户库可以是用户数据存储库（UDR），不是必须。若选用 UDR 承担业务用户库，MC 业务服务器和配置管理服务器被视为应用前端，经 Ud 访问库中数据。「业务服务器和业务用户库同网」本身不能证明用了 UDC 或 UDR。[§9.2.2.2 关于 UDR 的段落，印刷页 53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=54)

这三类工单要另查，不能用它们的回执代替站点的 SIP 身份供应方案：

- 已知两项已授权业务为同一用户配置同一个业务 ID 值，要辨认它代表哪项业务，查[跨业务用户身份映射](cross-service-user-mapping.md)（[TS 23.280 V16.7.0 §10.1.4.1，印刷页 68](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=69)）。
- 同机同时运行的 MCPTT 与其他 MC 业务客户端如何共享 SIP 注册，查[共享 SIP 注册与 MCPTT 授权](shared-sip-registration.md)。普通 SIP 注册成功不能据以认定 MCPTT 已获业务授权。[TS 24.379 V16.14.0 §7.1，印刷页 147–148](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=148)
- 要选出由 SIP 核心还是 MC 业务服务器单独经 Rx 控制承载的模型，查[承载控制部署](../bearers/bearer-control-deployment.md)。只知道谁管理 SIP 核心，选不出 Rx 模型；反过来，即使知道本部署由谁单独经 Rx 控制承载，也不能由此确定终端的 IMPI、IMPU 来源。[TS 23.280 V16.7.0 §§9.2.2.3.1–3，印刷页 56](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=57)；[§9.2.2.1.6，印刷页 52–53](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=53)
