# 已获 MCX 业务授权，取用户档和取组配置还要查哪两次授权？

**取用户档，配置管理服务器（CMS）查配置管理权限；取组配置，该组成员关系的宿主组管理服务器（GMS）查组管理权限。** 同一用户已经获准使用 MCPTT、MCVideo 或 MCData，不代表这两端已验证各自收到的令牌。以下按 Release 16 的 C-4、C-5，说明主系统取档和终端据档向宿主 GMS 取配置，不用于伙伴迁移或两台 GMS 之间交换配置。

## C-4：请求里的业务 ID 和令牌里的身份，各看什么？

在主系统，用户已在身份管理服务器（IdMS）完成认证，终端能安全访问 CMS。终端的配置管理客户端（CM 客户端）向 CMS 发 HTTP 用户档查询，并带本项业务的**配置管理范围访问令牌**。CMS 收到并验证令牌。有效时，它用**令牌中的对应业务身份**（MCPTT ID、MCVideo ID 或 MCData ID）从 MCX 用户库取档，再用 HTTP 把档发回。

Stage 2 的取档请求**另外要带 MC 业务 ID**。需要下载时，响应包含与该 ID 关联的全部用户档。这一字段没有取代 CMS 查令牌，也不补充令牌的权限。若请求写的是用户甲，令牌里的业务身份却指向乙，不能从这两处条文规定系统必须比对什么、选哪份档或回哪个 HTTP 错误码。CMS 发出档也不证明终端已收到、保存或选用了它。

依据：[TS 33.180 V16.13.0 §5.1.3.1 配置管理段，印 31](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=32)、[图 5.1.3.1-1 及 C-4，印 32](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=33)；[TS 23.280 V16.7.0 §10.1.4.3.1 前提及步骤 1–3，印 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=73)。

## C-5：收到这份用户档以后，下一次请求发给谁？

终端**收到同一用户、同一业务的相应用户档后**，组管理客户端（GM 客户端）从这份档取得组成员信息。它向承载该成员关系的**宿主 GMS**发 HTTP 组配置获取请求，出示**这项业务的组管理范围访问令牌**。GMS 验证有效才完成授权，向 GM 客户端发送该用户的组策略信息和组密钥信息；具体组钥的供应条件另见 TS 33.180 §5.7。拿到 MCPTT 档不能代替 MCVideo 档，只知道组号也不能代替从本档取得相应成员信息。要定位宿主 GMS，核对该组所用的 GMS 功能实体，不只看地址。

对照 TS 23.280 §10.1.5.2：终端已注册业务，GMS 已收到并保存组配置，GM 客户端需要适用于当前用户的配置。业务授权后，CM 客户端收到组清单时可以发起获取；收到 GMS 有新配置可取的通知后也可以获取。Stage 2 把**请求、GMS 提供数据、客户端保存**分开写。GMS 发出策略或组钥信息不是终端实收、已保存、已归属或已启用密钥的凭据。这个通知入口也不能证明每次都重做 C-5。

依据：[TS 33.180 V16.13.0 §5.1.3.1 组管理段，印 31](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=32)、[C-5，印 33](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=34)；[TS 23.280 V16.7.0 §10.1.5.2 引言，印 78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=79)、[前提、图 10.1.5.2-1 及步骤 1–3，印 79](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=80)、[§§7.4.2.2.3–.4 组管理功能，印 32](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=33)。

## 看授权记录时，先对到服务和接收方

C-3 是相应 MCX 业务服务器在 SIP 上核对业务授权。C-4 和 C-5 走各自的 HTTP 请求。附录 B 同时按业务（MCPTT、MCVideo、MCData）和用途（这里是业务、配置管理、组管理）区分权限范围。两笔 HTTP 要分别核对接收方有没有验证本次所用的相应范围，不能从范围类别数推令牌个数。该业务的 C-5 会用已经收到的那份档；这不等于所有业务都按一个统一时序办理。这里也不规定授权异常后的自动重试规则。[TS 33.180 V16.13.0 图 5.1.3.1-1 及 C-3/C-4，印 32](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=33)；[附录 B.4.2.2 表 B.4.2.2-1 的 scope，印 128](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=129)。

## 相邻问题

- 若查终端经 REGISTER 或 PUBLISH 向相应 MCX 业务服务器出示令牌、服务器何时绑定 IMPU 与该业务 ID，读[C-3 的 SIP 业务授权](mcx-sip-service-authorization.md)。只见初次注册成功不证明该服务已授权。
- 若查主系统取档响应应含几份，限该用户已由 IdMS 认证、终端可安全访问 CMS、实际办理主系统取档。本次确需下载时，再用[主系统的取档范围](user-profile-download.md)核对所请求业务 ID 的全部关联档；候选清单不是取档响应。
- 若查终端组管理客户端与该组 GMS 间的 Stage 2 获取或保存，先核对终端已注册业务、该 GMS 已收到并保存组配置、客户端需要当前用户适用的配置，且满足获取的一个入口：业务授权后 CM 客户端已收组清单，或收到有新组配置可取的 GMS 通知。读[组配置的获取、订阅与保存](../groups/client-group-configuration.md)；通知本身不证明已取或已存，也不是自动重走 C-5 的凭据。
- 若该用户已由 IdMS 认证、终端可安全访问 CMS 且已取得至少一份 MC 业务用户档，查已存在内容的两种更新：收到变更通知后取新值还要求 CMS 可访问该业务 ID 的关联档；客户端已被触发、要写回修改值则查写回。读[已有用户档的内容更新](user-profile-data-update.md)。不把内容更新当成这里 C-4 的用户档查询，也不当成选择活动档。
- 若查同一 MCX 业务服务器实际向终端分发 MuSiK 或更新 CSK/MuSiK，先核对终端已有本用户的 KMS 材料、已在该服务器注册并因而订阅其密钥下载通知，且 KMS 已为获准充当该业务服务器的身份配置材料。读[服务器何时有依据开始使用信令钥](../security/service-signalling-key-download.md)，另核是否成功提取及服务器实收本笔匹配应答。C-5 组钥不走这条；不判定其他程序能否由服务器初次下发 CSK。
