# 终端做身份认证、联系密钥管理服务，都要经过 MC 的 HTTP 代理吗？

不都要。先看终端里哪个客户端在跟谁交互，再看这笔交互的用途。这里讨论 3GPP TS 23.280 V16.7.0（Rel-16，Stage 2）的[在网功能模型（§7.3.1，印 27）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=28)。模型里的线表示两个功能之间的接口，不是某台终端的通信记录。

**身份认证：CSC-1 不用这个代理。** 终端里的身份管理客户端（IdM client）直接通过 HTTP 与身份管理服务器（IdM server）交互。这个接口供客户端认证公共服务核心，再由核心代表应用面内的应用认证用户。假如架构图在这两个功能之间画了一个框，要看框代表什么：画成 MC 的 HTTP 代理就不符合 CSC-1 的定义；画的是 IP 路由器，不能因“直接 HTTP”就把它划掉。“直接”既没有说链路无保护，也不能证明一次登录成功。[§7.4.3.3.2，印 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=38)；[§7.5.2.2，印 38](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=39)。

**密钥管理：CSC-8 要对照两段原文。** 一段讲接口有哪些连接方式，另一段讲送往客户端的安全相关信息该怎么传：

- [§7.4.3.3.2，印 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=38)：该段援引 TS 33.180，说明密钥管理服务器（KMS）与终端内密钥管理客户端之间，使用 HTTP 代理或直接 HTTP 接口。这里列出两种方式，没有要求部署两种、同时用两种，也没有指定默认方式。
- [§7.5.2.8，印 39](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=40)：CSC-8 供服务器向密钥管理客户端提供安全相关信息。**向该客户端传送和路由这类信息，必须使用 HTTP-1 和 HTTP-2 两个参考点。** 条文没有加上“仅在选了代理时”这个条件。

例如，设计单只标“接入 KMS”，不能按 CSC-1 的规则退回代理方案。如果设计单进一步写明“服务器直接给终端传安全相关信息”，就不能拿印 37 的直连选项单独签它合规；印 39 的具体要求必须一并核对。也不能倒过来删去印 37 的直连选项。本页不另定直连适用的业务或方向。图 7.3.1-3 在 CSC-8 旁写有 HTTP-1、HTTP-2；注 2 说明，为简洁起见，连接 HTTP 参考点的代理没有画出。图上没方框，不能当成本次直连的证据。[图 7.3.1-3 及注 2，印 30](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=31)。

## 终端到后台，TLS 会话止在哪里？

HTTP-1 是 HTTP 客户端与代理之间的参考点，HTTP-2 是代理与 HTTP 服务器之间的参考点；编号不是 HTTP 协议版本。在 HTTP-1 上，MC 终端的 HTTP 客户端与代理之间的 TLS 会话**止在代理**。这样，假如代理能到后台甲和乙，终端可用这一条会话与两个后台做 HTTP 交易。只知道终端与代理建了会话，不能断定终端与两个后台各自建了端到端 TLS，不能断定本次用了两个后台，也不能断定代理往后的链路是明文。参考点定义说 HTTP 可以采用 TLS 等保护，并未要求所有 HTTP 情形一律使用 TLS。[§7.4.3.3.2，印 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=38)；[§7.5.3.5，印 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=43)；[§7.5.3.6，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=44)。

## 两台代理在不同网络，能否向对方转交请求或响应？

若已识别出一个 HTTP-3 参考点，它的两端是不同网络中的 HTTP 代理，由代理终结。反过来，在设备清单上任取两台异网代理，不能认定它们之间就有一条 HTTP-3。**不同网络不等于不同信任域。** 一个信任域可以包括由不同提供方管理、约定共享敏感信息的 MC 功能。若两台代理分属甲网、乙网，但在同一信任域，单凭异网不触发跨信任域禁令，也不能证明两者已经转过一笔请求。若改为不同信任域，代理**不得**把请求或响应传给另一域的 HTTP 代理、HTTP 服务器或 HTTP 客户端。只知道网络归属而不知道信任域时，不能替该项检查下结论。[§5.1.2，印 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=19)；[§7.5.3.7，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=44)。

代理须与**位于 MC 业务提供方网络内的 HTTP 客户端和 HTTP 服务器**处于同一信任域。对本 MC 系统信任域外的 HTTP 实体，代理可以隐藏拓扑；这项能力不授权跨域转交。§7.5.3.7 的编辑注问的是：HTTP-3 用在分属不同信任域的服务器之间时，是否需要改动？这一点尚待研究。它没有给印 18 的转交禁令开例外。一个部署可有多个代理实例；“每个信任域一个”是例子，不是定额。[§7.4.3.3.2 及末注，印 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=38)；[§7.5.3.7 编辑注，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=44)。

若问题是三种 MC 用途能否填同一个 APN、认证前要不要另建 PDN，或传送公共 SIP-1、HTTP-1 信令的 EPS 承载该用哪种 QCI，查[附着与 APN 用途](../bearers/attachment-apn-roles.md)。若问的是 MCVideo 视频媒体专有 EPS 单播承载，应查 MCVideo 单播承载主题，不能套公共信令的 QCI。要找为用户服务的 SIP 注册器，查[注册器选择](registrar-selection.md)。跨系统分发文件时要分清 HTTP 代理与内容服务器，查[文件 URL 与正文的路径](../mcdata/intersystem-fd-url-content.md)。
