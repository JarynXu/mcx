# 用户没申请停用：服务器自动停用功能别名时通知谁？

MC 业务服务器向受影响的客户端发送停用通知，另向共享同一别名的其他用户发送状态通知。TS 23.280 V16.7.0 §10.13.9 描述的是 MC 系统内的自动停用，不是客户端请求停用后的应答。[图 10.13.9-1 与步骤 1–4，印刷页 203](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=204)

**触发前，服务器手里有什么？** MC 业务服务器已经从配置（功能别名）管理服务器取得相关信息，并保存了该用户已启用的相关别名数据。达到自动停用条件时，MC 系统可以发起停用；接入该 MC 系统且获授权的外部系统也可以发起。步骤 1 举的例子是定时器或用户当前位置，没有规定具体定时值或位置判定规则。[§10.13.9 首段及前提，印刷页 202](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=203) [图 10.13.9-1 与步骤 1–4，印刷页 203](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=204)

| 步骤 | MC 业务服务器做什么 |
| --- | --- |
| 2 | 向受影响的 MC 业务客户端发送功能别名停用通知。 |
| 3 | 保存所涉功能别名的状态（例如已停用）及对应的 MC 业务 ID。 |
| 4 | 向共享同一功能别名的所有其他 MC 业务用户通知状态。图中箭头指向这些用户的客户端，不指向全系统用户。 |

表中是图 10.13.9-1 和编号正文描述的动作。服务器发出通知，并不能证明客户端已收到、确认或改变本地状态。该节未定义 SIP 消息、重试或设备间的状态接替。[图 10.13.9-1 与步骤 1–4，印刷页 203](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=204)

**原文用词有出入。** §10.13.9 开头首句写的是 “can automatically activate”。标题和图 10.13.9-1 标为自动停用，四个编号步骤也在说明停用过程。上述流程按图和步骤解读，不把首句改作 “deactivate”，也不据首句增设自动启用步骤。[§10.13.9 首段及前提，印刷页 202](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=203) [图 10.13.9-1 与步骤 1–4，印刷页 203](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=204)

若终端发过请求，查[客户端主动停用及逐别名结果](functional-alias-client-deactivation.md)；若要判断触发条件能否用于启用或接管，查[服务端自动启用与共享上限](functional-alias-automatic-activation.md)；若查 MCPTT 规范中的 SIP 订阅和通知，查[MCPTT Stage 3 自动停用和 SIP 状态通知](owner-alias-auto-deactivation.md)。这些是另外的问题，不是本流程的后续步骤。
