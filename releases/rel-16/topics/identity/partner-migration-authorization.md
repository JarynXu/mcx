# 迁到伙伴系统：已通过用户认证，所选配置档的业务就获准了吗？

没有。伙伴系统认证了用户，客户端才具备申请业务授权所需的凭据。伙伴业务服务器先查能不能接纳来自主系统的这名用户；主系统业务服务器另查**这名用户能不能用所选配置档迁到这个伙伴系统**。要从客户端确认本次迁移及业务授权成功，还要看伙伴业务服务器发给它的响应结果。[3GPP TS 23.280 V16.7.0，Release 16，Stage 2，§10.6.3.3 前提及步骤 1–11，印刷页 116–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=117)

## 为什么同一份请求要写两个业务 ID？

两个 ID 指同一个迁移用户，分别供两地识别。用户想迁到目标伙伴系统，客户端已配置含有连接该伙伴所需参数的用户配置档，用户认证也已为客户端提供申请业务授权所需的凭据。这是申请的起点，不是申请的结果。客户端向伙伴业务服务器提出请求时，请求表列出的三项都是必填：

| 请求中的信息 | 指的是什么 |
| --- | --- |
| 伙伴系统提供的 MC 业务 ID | 伙伴的身份管理服务器在认证该用户时提供。 |
| 主系统中的 MC 业务 ID | 该用户在其主系统中的标识。伙伴业务服务器用它辨认用户的主系统。 |
| 所选用户配置档的索引 | 指向主系统提供、由用户选定用于向该伙伴请求迁移业务的那一份档，并非另一个用户 ID。 |

步骤 1 的注 1 另说明客户端还提供认证凭据；凭据的具体规定见其引用的 TS 33.180，此处不展开。[表 10.6.3.2.1-1 及两条表注、§10.6.3.3 前提，印刷页 116](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=117)；[步骤 1、注 1 及步骤 3，页 117](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=118)

## 谁查迁移许可，网关又负责什么？

**伙伴业务服务器先查来处：**它核实这名用户是否获准从其主系统迁入本伙伴系统。规范没有规定这项初审的具体准入标准。预先配置一份预计会申请的用户名单只是举例，不是所有伙伴系统都必须采用的做法。

**主系统业务服务器再查这次选择：**它核实的不是用户一般能否迁移，而是这名用户能否**按请求指明的配置档**迁到**请求所指的伙伴系统**。即使伙伴初审通过，也不能代替主系统对这次组合的判断。[§10.6.3.3 步骤 2、注 2 及步骤 6，印刷页 117](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=118)

在条款列出的网关路径中，伙伴业务服务器根据用户的主系统业务 ID 辨认主系统，把请求交给**伙伴网关**；伙伴网关用该 ID 找到主系统，转给**主系统网关**，后者据该 ID 找到**主系统业务服务器**。响应按相反方向从主系统业务服务器经两个网关返回伙伴业务服务器。如果**不使用拓扑隐藏**，请求和响应都在两地业务服务器之间传递，无需经过 MC 网关。改变的是跨系统的传送路径，不是两侧授权检查的分工；客户端仍与伙伴业务服务器交互。[§10.6.3.3 步骤 1、3–8，印刷页 117](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=118)；[步骤 9–11 及注 3，页 118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=119)

## 主系统已经登记迁往伙伴，客户端就知道成功了吗？

还不能这样判断。在所述成功流程中，主系统业务服务器先把用户标记为已迁移，并记录迁往哪个伙伴系统（步骤 7），再发响应（步骤 8）。伙伴业务服务器随后向客户端发响应，确认迁移及业务授权成功（步骤 11）。主系统里有迁移记录，不能证明客户端已经收到成功响应；仅仅缺少客户端收件证据，也不能判定授权失败。

响应表的三项必填信息是**原请求中的两个业务 ID** 和**结果**。两个 ID 标明答复对应哪位用户；结果可以是成功或失败。所选配置档索引是请求表的必填项，不是响应表列出的必填项。只有响应名称或两个 ID，不能断定结果为成功。编号步骤描述了成功经过，没有规定收到失败结果后如何回滚或何时重试。[表 10.6.3.2.2-1 及表注，印刷页 116](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=117)；[§10.6.3.3 步骤 7–8，页 117](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=118)；[步骤 9–11，页 118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=119)

## A 的用户能迁到 B，B 的用户也能迁到 A 吗？

先看两家 MC 业务提供方约定了哪个方向。两个 MC 系统要提供用户迁移，系统间需要提供 MC 业务互连；有互连不等于已开通双向迁移。双方可以约定单向，也可以约定双向，具体选择不是本规范替双方决定的。[§5.2.9.1，印刷页 22](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=23)

林的主系统是 A，周的主系统是 B。林已按自己的配置档从 A 成功迁到 B，这份结果只证明林的这笔业务。若协议只开 **A→B**，周要从 B 迁到 A，不在已约定的方向内；若尚未查明协议方向，不能据林的成功判周可迁，也不能判周被拒。若协议开通双向，周的方向符合协议，还要查 **A 能否接纳来自 B 的周，B 是否准许周按所选档迁往 A**，再看周自己的授权结果。原交易中经网关回传的响应仍是对林的答复，不是周的申请。林的通话媒体在迁移期间也可能送回 A，例如为留存日志；那不证明林已经回到 A 接受业务。周从 B 迁往 A 和林返回自己的主系统是两件事，本节不提供林的返家操作步骤。[§5.2.9.1，印刷页 22](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=23)；[§10.6.3.3 步骤 2、6，印 117](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=118)；[响应表，印 116](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=117)；[步骤 9–11，印 118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=119)。
