# 跨域密钥协商收到 KRR：谁生成了 KRR，还能继续吗？

以需要跨域交换密钥的在网私呼为例：即使发起端已经查到对端的 KMS URI，信令路径上的安全域策略仍可能拒绝这次使用的 URI。KMS 重定向响应（KRR）是沿原密钥消息的反方向返回的答复。它告诉原发起端哪些安全域可接受，不是让 SIP 请求改走另一个地址，也不发放证书。本文按 [TS 33.180 V16.13.0，Rel-16，§5.2.8.1.1，印刷页 47](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=48) 解释跨安全域的密钥交换，不指定某个呼叫流程如何承载 KRR。

**两个 URI 不同，表示两个安全域吗？** TS 33.180 让每个逻辑 KMS 对应一个安全域，由其 KMS URI 标识。确认两个不同的 URI 都是这个模型中的逻辑 KMS 标识，就能区分它们代表的域。只看到配置或日志里两个字段值不同，不能据此认定本次实际选用了哪个域，也不能认定哪一域是各自的归属安全域。[§5.2.8.1.2，印刷页 48](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=49)。

## 谁生成 KRR，为什么？

先把 KRR 与触发它的 **MIKEY 密钥消息** 对上，再判断是谁生成响应、为什么生成。“发起方”指发这份 MIKEY 的实体，可以是 MC 客户端或组管理服务器（GMS），不必是 SIP 主叫。MIKEY 原本要送达的实体是密钥接收方。[§5.2.8.1.1，印刷页 47](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=48)。

- **沿途节点不接受消息所用的域。** MCX 服务器或信令代理可以因所用的域不匹配、或发起侧或接收侧的域不被策略允许而生成 KRR。在适用的网络节点生成分支，原 MIKEY 在该节点被拦下。[§5.2.8.1.1，印刷页 47](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=48)；[§5.2.8.2.3，印刷页 49](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=50)；[§5.2.8.3 步骤 1a、2a，印刷页 52](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=53)。
- **密钥接收方收到消息，但不允许所用的域。** 终接客户端若判定发起方所用的安全域不被许可，可以发 KRR 告知允许的域。这时 MIKEY 已经送到该接收方，不能把终端判断当成中途未送达。[§5.2.8.3 步骤 3、3a，印刷页 52](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=53)。
- **密钥接收方给出偏好。** 收到来自该发起方的第一份 MIKEY 后，接收方可以按本地策略返回优先清单。若发起侧 URI 属于接收方的外部 KMS，发起方清单至少保留这个 URI；若接收侧 URI 属于接收方的 Home KMS 或已配置的迁移 KMS，接收方清单至少保留这个 URI。KRR 里仍有原值，不等于响应无效；仅看到 KRR 也不证明原值不受支持。[§5.2.8.2.2，印刷页 48–49](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=49)。

- **节点从收到的 MIKEY 生成 KRR：** 该网络节点必须丢弃这份 MIKEY，不再把它转给密钥接收方。须确认某网络节点是按这条程序从 MIKEY 生成 KRR，才能把丢弃规则落到该节点和该消息。[§5.2.8.2.3，印刷页 49](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=50)。
- **节点收到 KRR 后生成替代 KRR：** 新响应包含收到的那份 KRR。该节点不再单独转发原响应，向原 MIKEY 发起方转发新响应。限制哪份清单取决于该分支的节点角色和方向。替换响应的节点正在处理返回的 KRR，不一定刚拒绝了一份 MIKEY。[§5.2.8.2.4，印刷页 49–50](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=50)；[图 5.2.8.3-1 及步骤 1–4，印刷页 52–53](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=53)。

**看最后一跳，还是看谁生成了响应？** 发起端实收 KRR 只证明这份响应到了；即使知道直接发送者，也只定位到最后一跳。解码后，外层内容必须给出其声明的生成者；若这份 KRR 因收到旧 KRR 而生成，新响应须包含收到的旧 KRR，旧响应的内容另有自己的生成者。用这些内容区分响应的生成与替代，不把声明本身当作经过核验的身份，也不把最后一跳当作最初生成响应的人。KRR 签名并非必带；有签名也不等于已经验证。
[§5.2.8.2.1，印刷页 48](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=49)；[§5.2.8.2.4，印刷页 49–50](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=50)。

## 空清单能当成 ANY 吗？

不能。KRR 要带两份清单，一份给 MIKEY 发起方，一份给密钥接收方。两边分别判断。**`ANY`** 表示这份清单不限定某个 KMS，不撤销客户端自己的信任条件。**明确的空清单**则可由沿途过滤掉该侧所有选项产生；此时返回的仍是空清单，本次通信失败。**没有这份清单**不等于前两种。内容条款要求两份清单都存在；仅凭所引的内容与过滤条款，不能判断缺项后怎样解析或响应。日志没打印清单，也不能证明线上消息缺项。[§5.2.8.2.1，印刷页 48](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=49)；[§5.2.8.2.4，印刷页 49–50](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=50)。

发起方开始分发密钥且还不知道对端 KMS 时，选择程序以 `ANY/ANY` 为输入；收到前次尝试的 KRR 后，若按策略处理该响应，则用响应给出的两份清单。选不出可接受的配对，本次通信失败；选出配对后发一份新的 MIKEY。精确的选序不在本文范围。收到 KRR、选择新配对、再次发出密钥消息，都不等于对端验签通过或媒体已建立。[§5.2.8.2.5，印刷页 50–51](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=51)；[§5.2.8.3 步骤 4，印刷页 53](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=54)。

## 清单里有陌生 URI，证书向谁取？

**看归属 KMS（Home KMS）的策略，不去访问清单里写的外部 KMS。** 客户端只接受归属安全域许可、由 Home KMS 配置的外部安全域。KRR 不带来新的信任。策略禁用 KRR 时忽略它；若策略启用未知证书请求，且接收方清单列出了一个证书未知的外部 KMS，向 Home KMS 请求该证书；若另有等待归属 KMS 判定的策略，在收到判定前不对 KRR 采取行动。仅看到陌生 URI，无法判断策略要求请求证书还是等待，也不能认定证书已可用。这是本流程的证书来源，不是对其他迁移 KMS 程序的规定。[§5.2.8.3，印刷页 51、53](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=52)；[§5.2.8.5，印刷页 53](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=54)。

**收到 KRR 与验证 I_MESSAGE 是两件事。** KRR 的内容条款推荐签名，但不把签名列为必带项。客户端是否接受未签名或签名 KMS 未知的 KRR，仍取决于策略。验证收到的 MIKEY `I_MESSAGE` 时，若其中有 `KMSUri`，客户端核对它是否与对应配置相符，再按域从 Home KMS 提供的证书缓存取验证参数。没有匹配证书时，该条允许向 Home KMS 请求。这个允许请求的分支，不是前段“策略要求为 KRR 接收方清单请求证书”的分支。本文不为缺少 `KMSUri` 定义回退值，也不把对 I_MESSAGE 的检查当作 KRR 签名验证规则。[§5.2.7.3，印刷页 47](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=48)；[§5.2.8.2.1，印刷页 48](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=49)；[§5.2.8.3 注 1，印刷页 53](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=54)。

只想确认[私呼从哪份本端配置读取对端 KMS URI](../calls/private-peer-kms-uri.md)，查 TS 24.379 对应主题。若问[普通私呼或首接应答的 PCK 在哪份 SDP、怎样查认证结果](../calls/private-fta-pck-authentication.md)，查各自实际收到的消息；那两种 SDP 位置不能用来推定 KRR 的 SIP 方法或状态码。
