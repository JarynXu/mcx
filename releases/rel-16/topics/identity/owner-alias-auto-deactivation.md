# 用户没申请停用，谁能解除他的 MCPTT 功能别名？

“东区值班”由甲和乙同时使用。甲的关联到期时，**拥有该功能别名的 MCPTT 服务器可以只解除甲与“东区值班”的关联**，不必先收到甲发来的停用请求。自动停用有两种触发途径：MCPTT 管理员从外部触发，或者拥有别名的 MCPTT 功能因内部事件直接触发。关联到期是后一种的例子，不是唯一原因；标准不规定管理员通过什么接口或命令触发。[3GPP TS 24.379 V16.14.0，Release 16，Stage 3，§9A.2.2.3.6，印刷页 215](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=216)

**解除的是哪条记录？** 服务器按功能别名 ID 保存别名条目。每个别名条目里有一份用户列表，表内用 MCPTT ID 唯一标识用户记录，每条还保存能否接管的指示和到期时间。自动停用时，服务器先按别名 ID 找到“东区值班”，再从它的用户列表中移除 MCPTT ID 等于甲的记录。这个动作不移除乙的记录，不删除“东区值班”这个别名，也不移除甲在另一个别名下的记录。即使甲是最后一名使用者，该步骤移除的仍是用户记录，并未要求删除别名。[§9A.2.2.3.2，印刷页 211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=212)；[§9A.2.2.3.6，步骤 1–2，页 215](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=216)

**移除之后，谁会收到通知？** §9A.2.2.3.6 步骤 3 要求服务器针对同一个别名执行状态变更通知程序。这一步不等于已经向甲或乙发出通知。进入 §9A.2.2.3.5 后，服务器要按别名 ID 找到“东区值班”，再在它的用户列表内查找一条记录：记录的 MCPTT ID 必须等于标识本次订阅者的 ID（条文称为 `handled MCPTT ID`）。前面指定要解除的则是目标 ID（`target MCPTT ID`），两个 ID 用在不同步骤。[§9A.2.2.3.6，步骤 3，印刷页 215](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=216)；[§9A.2.2.3.5 引言及步骤 1–2，页 214](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=215)

例如，乙有按 §9A.2.2.3.4 建立且仍有效的相关订阅，别名下也仍有与乙的 ID 匹配的用户记录。服务器按该记录生成以别名为单位的 `application/pidf+xml` 消息体，其中的 `functionalAlias` 元素须带 `expires` 属性，然后为乙的订阅发送 SIP NOTIFY。这不是向所有使用者广播，发送记录也不能证明乙的终端已经收到。[§9A.2.2.3.4 末段、§9A.2.2.3.5 步骤 1–4，印刷页 214](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=215)

反过来，如果订阅者是甲，服务器刚移除的恰好就是与甲的 ID 匹配的记录。更一般地，**订阅仍有效不代表别名下还有匹配记录**。此时仍须调用通知程序，但这两条没有说明找不到记录时应如何选取条目、构造通知正文或处理本次发送。不能据此断言必定发给甲、禁止发送、免于执行通知程序，或应把记录补回去。[§9A.2.2.3.5 步骤 2–4，页 214](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=215)；[§9A.2.2.3.6 步骤 2–3，页 215](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=216)

不要把到期信息当成发布标识。`expires` 描述到期；`p-id-fa` 则用于关联一次发布。若是拥有别名的服务器在**处理 SIP PUBLISH** 时已识别出 `p-id-fa`，并由该程序调用通知程序，服务器须把识别到的值写进 NOTIFY 消息体的 `presence` 根元素下。仅因关联到期而调用通知程序，不满足这条复制规则。不能因此要求通知必带 `p-id-fa`，也不能单凭它缺失就断定这次一定是到期停用。[§9A.2.2.3.3，步骤 13–14，印刷页 213](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=214)；[§9A.2.2.3.5，步骤 3，页 214](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=215)

想知道用户怎样主动申请停用，见[客户端启停申请与状态观察](mcptt-functional-alias-client.md)；只想知道眼下谁在使用别名，见[按别名或用户查询当前使用情况](active-functional-alias-lookup.md)。两者都不是服务器自动解除关联的前置步骤。
