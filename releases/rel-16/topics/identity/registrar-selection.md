# finder 在运营方，服务用户的 SIP 注册器该去哪个库找？

两处部署的 registrar finder（负责查找服务注册器的功能）都在 PLMN 运营方域，答案却可以不同：注册器也在运营方域，就用运营方的 SIP 数据库信息；注册器在 MC 业务提供方域，则用业务提供方的 SIP 数据库信息。finder 要识别的是**服务该用户的注册器／应用服务选择功能实体**，不是业务服务器或终端的位置。[3GPP TS 23.280 V16.7.0，Rel-16 Stage 2，§7.4.3.1.3.3 a)，印刷页 35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=36)

| finder 在哪一方的域 | 注册器在哪一方的域 | 识别注册器用哪一方的 SIP 库信息 |
|---|---|---|
| MC 业务提供方 | MC 业务提供方 | 业务提供方的 SIP 库 |
| PLMN 运营方 | PLMN 运营方 | 运营方的 SIP 库 |
| PLMN 运营方 | MC 业务提供方 | 业务提供方的 SIP 库 |

这三行是 §7.4.3.1.3.3 a) 1–3 明列的场景。finder 还可以参考 PLMN 运营方的内部资料，例如网络拓扑和注册器可用性。在第一行，即使参考了这些资料，识别服务注册器的仍是业务提供方域内的 finder，不能把提供资料的运营方登记为选择者。在第三行，只有一张运营方的可用性表，不能替代业务提供方 SIP 库的信息。没拿到这份可选清单也不是故障。若只知道 finder 在运营方域，就缺了区分后两行的条件。相反方向（finder 在业务方域、注册器在运营方域）没有列在这里，不能靠表格对称性填答案，也不能据此判定禁止这种部署。[§7.4.3.1.3.3 a)，印刷页 35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=36)

**一处部署只有一个注册器，还需要 finder 吗？** 不需要。这个例子也不需要 SIP 库里**与寻找注册器有关的信息**。是否需要 finder 取决于部署；注 1 不禁止保留 finder，也没有规定一旦有两个注册器就必须增设 finder。[§7.4.3.1.3.3 注 1，印刷页 35](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=36)

省掉查找步骤不等于省掉注册或整个 SIP 库。**仍由注册器登记用户**，维护用户身份与 SIP 联系位置的绑定，并通知注册状态。这里的位置是用来联系用户的地址，不是经纬度。注册器还**可以**为 SIP 事务选择应用服务，可能使用运营方或业务提供方 SIP 库中的应用服务选择信息。finder 识别出注册器 R2，既不是注册成功的回执，也不是具体应用服务已选中的回执。[§7.4.3.1.3.4，印刷页 35–36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=36)；[§9.2.1.3 的联系地址绑定与应用服务选择，印刷页 49](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=50)

## 需要什么样的注册器，和当前由谁服务，是两个问题

分配时，**MC 业务提供方**针对用户提出要求，**SIP 库**据此向 **finder** 提供所需能力。比如，甲需要使用安全场所内的注册器。这一条不能填成“甲现在由 R2 服务”。终接业务则要知道当前由哪个注册器服务甲，SIP 库为终接提供这个信息。即使答复是 R2，也不能从这个名称还原分配时的全部要求。[§7.4.3.2.2 b) 和 c)，印刷页 36–37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=37)

## 跨网查库，能看到谁的哪些数据？

在一种部署中，finder 在运营方网络，注册器和 SIP 库都在业务提供方网络。此时 **AAA-1 跨网**。这是 SIP 核心与 SIP 库之间的参考点，核心通过它从库中取得信令面数据，使用 Cx 参考点；不是终端直连数据库的接口。[§7.5.3.8，印刷页 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=44)

访问权要按用户和数据分别核实：注册器或 finder 必须服务这位用户，同时对所供数据与库处在同一信任域。注册器选择条件与信令面用户身份可以属于不同的信任域。例如，若已确认 finder 服务甲、对甲的注册器选择资料与库同属一个信任域，不能仅因跨网否定它访问这项资料。反过来，仅凭这一条也不能允许读取甲的全部信令面身份数据，更不能因为另一位用户乙与 finder 同网，就许可该 finder 读乙的数据。[§7.4.3.2.1 正文及注，印刷页 36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=37)

## 管理整个核心，还是只管理其中一部分？

§9.2.2.1.5 讲共同管理：文中示例由运营方管理代理和 finder，业务提供方管理注册器。图 9.2.2.1.5-1 的 SIP 核心横跨双方管理范围；它不是实际服务器清单。采用 IMS 时，本地入／出代理、finder、注册器／应用服务选择功能分别对应 P-CSCF、I-CSCF、S-CSCF；这些功能名也不能用来数物理主机。另一类核心可不采用 IMS 内部架构，但仍须遵守对已暴露参考点的约束。[§9.2.2.1.5 的示例及图，印刷页 51–52](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=52)；[§§7.4.3.1.3.1–4，印刷页 34–36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=35)

若要核对终端的 IMPI、IMPU 来自谁，查[终端身份供应与 SIP 核心部署](identity-hosting-sip-core.md)。§9.2.2.1.6 是另一种部署：由运营方管理**整个** SIP 核心，对 MC 业务提供方所服务的终端，核心使用的这两种身份都由**该业务提供方的 SIP 数据库**提供，不是凭 finder 在哪一方得出的结论。[§9.2.2.1.6 首段，印刷页 52](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=53)

若要判断同一台终端同时运行的业务怎样共享 SIP 注册，或 MCPTT 是否已获准，查[共享 SIP 注册与 MCPTT 授权](shared-sip-registration.md)。这里对 finder 和注册器的分工不能替代具体业务的授权结果。

若同一工程还要认定迁移注册时核心到 Diameter 代理的参考点，见[两种 Cx 的端点和授权边界](migration-registration-reference-points.md)。

## 本地代理转发了 REGISTER，能确认 NAT 穿越或注册成功吗？

不能只看这一步。先把 SIP 核心里的三个功能分开：

| 这笔记录涉及的功能 | 这一步在做什么 |
| --- | --- |
| 本地入／出代理 | 充当 SIP 事务的入站和出站代理，可以路由和转发请求、响应，也能提供 NAT 穿越。支持穿越和这次穿越成功是两件事。 |
| registrar finder | 识别服务该用户的注册器／应用服务选择功能。是否需要 finder 取决于部署，单注册器部署可以不设。 |
| 注册器／应用服务选择功能 | 注册用户，维护用户身份与联系地址的关联，并提供注册状态通知。 |

在这一功能模型下，一条本地代理的 REGISTER 入向或转发记录只说明这一侧看到了或转发了请求；不证明 NAT 穿越已成功，不证明 finder 已选到注册器，也不证明注册器已经登记用户。核对注册结果，查负责注册的功能和这次用户的注册状态证据；核对实际网络可达性，则另查相关两侧记录。采用 IMS 的例子中，本地入／出代理、finder 和注册器分别对应 P-CSCF、I-CSCF 和 S-CSCF，这些是功能名称，不是设备台数。〔§§7.4.3.1.3.2–.4，印刷页 35–36〕

## 本地代理没解析 E.164，能说明配置有缺陷吗？

不能据此下结论。本地入／出代理是否做含 E.164 号码的发现及地址解析，取决于 **PLMN 运营方策略**。finder 的职责也列有发现及地址解析（包括 E.164），另有识别服务注册器的职责。不能因为日志里有号码解析，就把那一步登记为已选择服务注册器；也不能因入口代理没有解析记录，就认定 finder 缺失或注册失败。先查该笔事务由哪个功能负责以及本地策略要求，识别实际做过的步骤。单注册器部署可以不设 finder，这仍不等于省去注册。〔§7.4.3.1.3.2 末项、§7.4.3.1.3.3 a)、b) 与注 1，印刷页 35〕

依据：[3GPP TS 23.280 V16.7.0，Rel-16，Stage 2，SIP 核心三个功能实体（ETSI，印刷页 35–36）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=36)。本节不规定 NAT 穿越或号码解析的方法，也不能代替业务授权结果。

若已经知道服务注册器，却把 SIP 库的跨系统位置当成终端联系地址，或把漫游许可和应用过滤条件当成业务授权，读[SIP 用户库的路由、位置与授权边界](sip-database-routing-and-authorization.md)。
