# LMC 发给 LMS 的位置消息，何时带令牌？验不过怎么处理？

支持任务关键位置业务的 MC 终端，**LMC 每次向 LMS 发送位置消息，都要在该消息中带上位置管理业务范围的访问令牌**。位置信息报告和位置上报触发都是例子。这不是登录后出示一次令牌便可以不带；LMS 要验证随位置消息送达的访问令牌。依据是 Release 16 的安全规范 3GPP TS 33.180 V16.13.0。[§5.1.3.1 的 LMS 段，印刷页 32（PDF 第 33 页）](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=33)。

## 申请了位置范围，能证明令牌已经获准吗？

MCX Connect 的身份管理客户端向身份管理服务器（IdMS）的授权端点发起认证请求时，在 `scope` 中列出要申请访问的资源范围。位置管理业务的范围值是 `3gpp:mc:location_management_service`。**请求里写了这个值，只能证明申请了该范围。** 请求的范围获准时才会绑定到返回给客户端的访问令牌；发给 LMS 的位置消息还要带范围涵盖位置管理业务的访问令牌，由 LMS 验证。附录里的 HTTP GET 示例是发往 IdMS 的认证请求，不是 LMC 给 LMS 的位置消息，也不指定 LMS 要从哪个字段取令牌。[附录 B.4.2.2，表 B.4.2.2-1 的 scope 行及请求示例，印刷页 128（PDF 第 129 页）](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=129)；[§5.1.3.1 的 LMS 段，印刷页 32](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=33)。

## LMS 验证后，是处理、拒绝，还是保留？

- **验证成功：** LMS 处理这条消息。原文举例，若是位置信息报告，LMS 可以接受并存储它。不能把存储例子套到每种消息，也不能单凭请求发出、令牌验证成功或响应存在，就写成数据库已有新记录。
- **无法验证访问令牌：** LMS 可按本地策略处置收到的位置消息。原文举例，本地策略可能把保存位置报告作为应急措施。它既没有要求所有这类消息一律拒绝，也没有要求紧急时必须保存。即使确认报告按应急策略保存，也不能据此把令牌记为验证成功。

[§5.1.3.1 的 LMS 段，印刷页 32](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=33)。

这段只说明 **LMC → LMS** 的位置消息授权。没有指定这条接口使用 HTTP 或 SIP、报文字段、失败状态码或固定失败动作；也没有设定向 LMS 做一次初始注册的条件，不能把它当作 **LMS → LMC** 下发配置的授权规则。令牌通过验证，不证明某个目标已同意共享位置、订阅方已收到了消息，或实际位置已写入。

查[位置配置、注册触发与终端上报](event-reporting-configuration.md)时，先分清消息是哪一方向；查[一个 LMC 为另一用户发起上报](client-triggered-reporting.md)时，另看请求者权限、触发内容和目标同意。若只看到 SIP 注册成功，见[主系统的身份认证、SIP 注册和业务授权](../identity/home-system-authentication.md)，不能凭 SIP 注册判定 LMS 已经验过位置令牌。
