# 按组清单创建预配置组重组：少一份 200，CF 能先确认吗？

不能。**MCPTT 控制功能（CF）要等它通知的所有组成组侧非控制功能（NCF）的响应。** 全部是 SIP 200，才按这个分支确认创建。收齐后若有一份不是 2xx，CF 向发端参与功能回 480，还要给先前回过 200 的 NCF 发移除请求。这里是 **按组清单创建**，不是[按用户名单创建](user-regroup-response.md)，也不是组管理服务器办理的 Stage 2 通用重组。[TS 24.379 V16.14.0，Release 16，Stage 3，§16.2.3.1 步骤 4–7，印 501–502](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=502)

## 先对上同一次创建

例如，要用预配置组 **P** 把组成组 A、B 重组成临时组 **T**。发起客户端给服务自己的发端参与功能（O-PF）发 SIP MESSAGE；`regroup-action=create`，`mcptt-regroup-uri` 是 T，`preconfigured-group` 是 P，`groups-for-regroup` 列的是 A、B 的组标识。T 不是 P，也不是 A 或 B。[§16.2.1.1 步骤 3、7–8，印 495](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=496)

CF 若不能基于 P 处理，分发前即回 480 并停止；若判定拟用的 T 已被占用，回 403，Warning **文本码 165**，也不进入分发。走到分发步骤时，CF 逐组找服务该组成组的控制功能；后者在这次重组中充当 NCF。CF 发出的 MESSAGE 以该 NCF 的公共服务标识（PSI）为 Request-URI，复制入站的 MCPTT 业务正文、重组正文和 P-Asserted-Identity，以及来件实际带有的 Accept-Contact、Reject-Contact 字段。先沿这些事务找出本次 CF 发给了谁，再比它实际收到了谁的响应；不要按一张终端成员名单数应答。[§16.2.3.1 步骤 2–5，印 501](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=502)；[表 4.4.2-2 的 165 行，印 38](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=39)

## 全是 200、混有非 2xx、没收齐，怎样区分？

| CF 对本次分发实际观察到的结果 | 按 §16.2.3.1 判断 |
| --- | --- |
| CF 已实收 X 的 200，尚未收到 Y 的对应响应 | 尚未收齐。不能先回 200，也不能把缺失自动登记为非 2xx。即使目前已见一个 4xx，步骤 5 仍先写等齐；本条没有给出等待时长、超时值或超时如何归类。 |
| 收齐且每个结果都是 **200** | CF 回上游 200，再按所列步骤保存组成组列表、T 和 P。不是收齐终端通知回执，也不证明终端已参加组呼。 |
| 收齐且至少有一个实际结果**不是 2xx**，例如 Y 回 403 | CF 向 O-PF 回 480，然后只给创建时回过 **200** 的 NCF 各发移除请求。 |
| 收齐且全是 2xx，但至少有一个不是 200 | 两个分支条件都不满足。这个版本的本条未给后续结果，不能把 2xx 一律记作 200，也不能把它们记为非 2xx。这个例子只检验守卫，不表示正常 NCF 会回非 200 的 2xx。 |

如果只有 X 的发送日志，不能说 CF 已实收 X 的 200。反过来，CF 暂未收到某侧结果，不能说那侧一定没发。按用户名单创建时，另一条程序以任一被请求的终接参与功能（T-PF）的 200 为成功触发；该规则不适用此处。[§16.2.3.1 步骤 5–7，印 501–502](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=502)；[§16.3.3.1 步骤 6–7，印 511](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=512)

## 480 后，查给谁的移除 MESSAGE 和哪一段回执

例：X 管 A，正常收到创建后，先保存本次组清单、T、P 和重组标记，再回 200。X 回 200 在它按归属和服务关系生成各 T-PF 通知**之前**，并非终端收妥。Y 管 B；若按 NCF 步骤 2 认定本侧所管的组成组已重组，可从该拒绝看到 403、Warning 文本码 **148**，并停止该侧的后续创建。它与 CF 分发前发现 **T 已占用**的 403/165 不是一回事。[§16.2.4.1 步骤 2–7，印 504–505](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=505)；[表 4.4.2-2 的 148 行，印 37](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=38)

CF 收齐 X 的 200 和 Y 的 403 后，向 O-PF 回 480；给 X 另发一笔 SIP MESSAGE。这个例子中不向 Y 发补偿，也不直接向客户端或 T-PF 发。补偿请求的 Request-URI 是 **X 的 PSI**；`application/vnd.3gpp.mcptt-regroup+xml` 正文至少要有 `mcptt-regroup-uri=T`、`regroup-action=remove`，不要把 P 代入。第 7b 项原文写“在步骤 4 返回 200”；步骤 4 列分发，步骤 5 列接收。匹配的是这次分发实际回了 200 的 NCF。若没有这样的 NCF，本分支没有补偿收件对象。[§16.2.3.1 步骤 4–5、7，印 501–502](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=502)

**先查 X 是否把收到的 MESSAGE 归入移除程序。** §6.3.1.3 的接收分类还写明 S-CSCF 按初始过滤规则路由至 NCF、Request-URI 指向它的 PSI、重组正文中有 `preconfigured-group` 且 `regroup-action=remove`。第 7b 项的补偿构造列 T 和 remove，没列出复制或填入 P。不能凭这两项和一条收件日志就判定接收分类已匹配；也不能把发送条款没列 P 读成禁止带 P，或断言实现一定拒绝。[§6.3.1.3 的 NCF 移除 MESSAGE 分类，印 82](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=83)；[§16.2.3.1 第 7b 项，印 502](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=503)

**补偿已发不等于撤销已完成。** X 实际收到符合上述入口的移除请求后，若缺资源或有拥塞风险，可回 500 并结束本次处理。正常分支先回 200，再按 T 查该 NCF 所管组成组与相应 T-PF、逐 T-PF 的归属用户清单，并按该程序下发。该响应不证明旧 NCF 本地状态全部清除，更不证明下游都已收到或终端已恢复。创建失败条款也没有规定在回 480 前要等补偿结果。若要判断某个终端是否实际处理，见[终端收到预配置组重组通知](preconfigured-regroup-notification.md)。[§16.2.4.2 步骤 1–4，印 505–506](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=506)；[§16.2.3.1 第 7 项，印 502](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=503)

O-PF **实收其发出的创建 MESSAGE 的 480** 后，编号步骤写的是改选另一 CF、把新 MESSAGE 发往新 CF 的 PSI；同节注 2 又有是否重试属部署决定的字样。本页保留这处差异，不保证一定观察到第二笔请求，也不补重试次数、等待时间或先等旧侧撤完的规则。即使查到新 CF 实际收到新请求，也不能拿它证明旧 NCF 已撤销。O-PF 另有收到上游 2xx 后给客户端回 200 的规则，不替换旧 CF 的逐 NCF 全 200 条件。[§16.2.2.2 的 480 与 2xx 分支及注 2，印 498](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=499)

若 T 已建、后来才有用户归属到某个组成组，查[已有预配置重组的后续归属通知](preconfigured-regroup-late-affiliation.md)，不要把这件事计入本次创建应答。
