# MC 业务客户端订阅组动态数据：收到成功响应，就收到新数据了吗？

不能这样判断。甲的 MC 业务客户端向 MC 业务服务器订阅桥东组的动态数据。甲端收到的**订阅响应**给的是组 ID 和这次请求的成败。即使结果是成功，也不能把它登记为“甲端已收到桥东组的新数据”。携带数据的是服务器发往已订阅客户端的**通知请求**。两种消息方向相同，要看消息的用途和内容。[3GPP TS 23.280 V16.7.0（Rel-16，Stage 2），§10.1.5.6.1.2–3，印刷页 81–82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=82)。

**有权请求，为什么还要核查？** 订阅程序有两个前提：服务器已持有该组的动态数据；甲端有权请求该组的数据。甲端发出订阅请求后，服务器还要检查甲端是否有权**接收该组的数据**，然后答复请求成功或失败。两处说的是不同环节，不要求据此设计两套权限；只看到甲端有权请求，不能替服务器填“已核查并批准”。[§10.1.5.6.2，订阅前提及步骤 1–3，印刷页 82–83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=83)。

| 客户端与业务服务器之间的信息流 | 方向 | 该表列出的必填项 |
| --- | --- | --- |
| 订阅请求 | 甲端 → 服务器 | 要查的组 ID |
| 订阅响应 | 服务器 → 甲端 | 组 ID、请求结果（成功或失败） |
| 通知请求 | 服务器 → 已订阅的甲端 | 组 ID、该组的动态数据 |
| 通知响应（实际回复时） | 甲端 → 服务器 | 已收到动态数据的组 ID |

通知程序另有两个前提：甲端先前已订阅这个组，且服务器有**这个组**的新动态数据可供通知。若只有另一组有新数据，不能算作满足桥东组的这个前提。若日志只见服务器发出通知，可登记其发送，不能判定甲端收到了还是没收到。若再见甲端针对这次通知返回桥东组 ID，它确认的是甲端收到该组的数据；响应表不要求重传数据或附成败状态，也不能用它替同组的乙端确认收件。[§10.1.5.6.2，通知前提及步骤 1–2，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=84)；[§10.1.5.6.1.1–4 四表，印刷页 81–82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=82)。其中 §10.1.5.6.1.3 的引言称“响应”，但该小节标题、表题、数据行以及通知程序的步骤均把带数据的这一程指向客户端；客户端返回的响应见下一张表。

## 同一个业务 ID 下有两个 Contact URI，能认出两台终端吗？

不能只数地址。业务服务器所知、按请求提供的组动态数据，包含本组在相应 MC 业务下各业务 ID 的归属状态，以及用户通过哪些 **Contact URI** 归属该组。例如，视频业务的记录在同一个 MCVideo ID 下列出两个地址，说明这份数据列了该用户的两项归属联系地址，不能把它们数成两个用户或两台物理终端。表中另列**用来标识组的 Contact URI**，例如广播组别名，不能把那一行当成用户的归属地址。[§10.1.5.5.1 引言及表 10.1.5.5.1-1，印刷页 80](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=81)。

如果手上只有 **GMS 的已归属成员名单**，那张表按业务列成员 ID，不列这些归属联系地址。通知表要求通知请求带组 ID 和组动态数据，但没有规定每条通知都要列出所有归属联系地址。一次通知未列某个地址，不足以判定用户没有归属。[表 10.1.5.5.2-1，印刷页 81](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=82)；[表 10.1.5.6.1.3-1，印刷页 82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=83)。

**组播就一定是按组寻址吗？** 不一定。这里从服务器发给业务客户端的订阅响应**单独寻址**，可以用单播，也可以用组播。通知请求则可以单独寻址或按组寻址，也可以走单播或组播。因此记录里只有“组播”时，既不能据此认定这是通知而非订阅响应，也不能确定收件范围或哪台客户端实际收到。[§10.1.5.6.1.2–3 两表前的寻址说明，印刷页 81–82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=82)。

**甲收到通知，就一定要回吗？** §10.1.5.6.1.3 指向了 MBMS（多媒体广播多播业务）的应用层控制信令规则。这种信令可以传送组动态数据。例如，甲实际收到了服务器经 MBMS 按组寻址发送的这类通知，但既没有指示甲回复这条消息，也没有适用的回复配置，甲就**不得应答**。服务器没有看见回复，不能据此判甲没收到。如果有指示或配置，要看它针对哪条消息、规定了什么，不能反推每条通知都必须回复。只有“组播”两字则连是否按组寻址都不能确定，更不能断定甲不得回复。[§10.7.3.4.1，消息列表及末段，印刷页 126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=127)。若要进一步判断监听状态报告与具体控制消息收件的区别，见[经 MBMS 向组发送应用层控制消息](../bearers/mbms-application-control-signalling.md)。

**订阅方或要查的数据换了，入口也不同。** 四张表也列出组管理服务器（GMS）与业务服务器之间的方向；上文走的是业务客户端分支。若订阅方是 GMS，要跟踪组成员的隐式和显式归属，见[GMS 向定义该组的 MC 系统内的业务服务器订阅归属状态](gms-affiliation-subscription.md)，不要把那个程序的服务器位置和数据范围套给甲端。[§10.1.5.6.3，引言与订阅前提，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=84)。若要判读 MCPTT 的 SIP 订阅、200 应答、NOTIFY 或参与功能和控制功能怎样处理，见[MCPTT 组动态数据订阅（Stage 3）](group-dynamic-data.md)。要查的是组管理客户端有没有保存组配置，见[终端取得组配置](client-group-configuration.md)；要查同一 MC 系统内成员增删时，GMS 分别通知业务服务器和受影响成员什么，见[组成员名单变动](group-membership-notification.md)。
