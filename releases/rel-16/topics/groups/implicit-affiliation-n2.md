# MCPTT 请求触发隐式归属：同一用户有两台终端，N2 怎么数，哪一条记录会变？

车载台已经归属巡检组，手持台又发来一个需要隐式归属巡检组的请求。即便是同一个人，车载台的归属也不能直接登记在手持台名下。**参与 MCPTT 功能按用户合计不同的组来检查上限 N2，却按发来请求的客户端更新组记录。** 依据是 3GPP TS 24.379 V16.14.0（Release 16，Stage 3）[§§9.2.2.2.12–14，印刷页 183–185](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=184)。以下说的是需要这项处理的 SIP 请求，不是每个请求都会触发归属。

**先找准手持台的那份记录。** 参与功能用请求中 P-Asserted-Identity 的公共用户身份确定受服务的 MCPTT ID；注 1 说明，两种身份在业务授权时已绑定。该用户记录下有各客户端的记录：从请求的 MCPTT 信息体取 `mcptt-client-id` 找到本客户端，取 `mcptt-request-uri` 确定目标组。参与功能复制本客户端的组列表，再把其中各组记录复制到候选列表。同一用户的车载台有自己的列表，不复制进手持台的候选列表。[§9.2.2.2.12 第 1–7a 项，印刷页 184](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=185)

手持台原表中**没有目标组，或目标组记录已经到期**，才按第 7b 项为它新增一项：状态为 `affiliating`（正在归属），到期时刻为当前时刻加候选有效期。例如 10:00 处理、候选有效期 20 分钟，新项就到 10:20。若已有未过期的目标记录，第 7b 项不要求再新增一条，也没有据此续期的依据。即使候选列表稍后被采用，新项的初始状态也不是 `affiliated`（已经归属）。[§9.2.2.2.12 第 7b 项，印刷页 184](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=185)

**N2 是这位用户的上限。拿什么数与它比较？** 一边看本客户端的候选列表，一边看同一用户所有其他客户端的组列表。两边都只选未过期且状态为 `affiliating` 或 `affiliated` 的记录，再取其中不同组 ID 的个数。假设手持台有未过期的“调度”和新增的“巡检”，车载台有未过期的“巡检”和已过期的“救援”；前三条状态都符合条件。计入的是调度、巡检两个组。另一位用户哪怕也在同一设备上使用业务，其组也不参与这位用户的计算。[§9.2.2.2.12 第 8 项，印刷页 184–185](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=185)

若 N2 为 2，上例恰好到限，不触发超限缩减；参与功能用候选列表替换手持台保存的组列表。再看另一份记录：手持台原有“调度”、这次新增“巡检”，车载台只有“救援”，三组都未过期且状态符合条件。三个组超过 N2，参与功能须按服务商策略将候选组数减到两个。标准没有指定一律保留新目标或一律删除最老的组。若策略允许保留“巡检”，继续替换手持台的列表；若因 N2 不能加入“巡检”，丢弃候选列表，跳过本程序余步，手持台原表不被这次候选表替换。**跳过的是这项归属程序，条文没有因此为原 SIP 请求指定拒绝码。** 两种情况下都不能把第 11 项读成重写全用户所有客户端的列表。[§9.2.2.2.12 第 9–11 项及注 2，印刷页 185](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=186)

**在这个请求上，什么证据能结案？** 假设手持台这次确有一条新增的“巡检”记录。判读响应时既要认发来响应的是控制 MCPTT 功能，也要对得上触发隐式归属的那一个请求：

- **完成。** 参与功能收到控制功能对该请求的 SIP 2xx，就须把此次新增项改为 `affiliated`，并为该 MCPTT 用户执行 §9.2.2.2.5 的归属状态变更通知程序。2xx 记录证成了这两项义务；要声称状态确已改写或某订阅者已收到通知，还要分别看到对应的状态变更或收件证据。另一请求的成功响应不能结本案。[§9.2.2.2.13，印刷页 185](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=186)
- **取消。** 不必一定等到控制功能回错：参与功能自己判定原请求需要拒绝，或它收到控制功能对此请求的 SIP 4xx、5xx、6xx，都须移除此次新增项。删除范围同时受发送者的 MCPTT ID、请求中的客户端 ID、目标组 ID 限定。车载台原有的“巡检”不在其中；也不能据此删除手持台上其他组，或倒推整张列表恢复原样。若只见 1xx、3xx 或一条对不上请求的响应，这三节没有给出本次完成还是取消的结论。[§9.2.2.2.14，印刷页 185](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=186)

若记录从一端主动发布本端的组兴趣开始，查[显式自归属](explicit-affiliation-client.md)；若是请求另一用户确认其归属变更，查[协商式归属](negotiated-affiliation-client.md)。若要问主系统中谁有权改变他人归属，读 [Stage 2 的远程归属](remote-primary-group-affiliation.md)。这些问题的触发者、目标或证据都与本次请求中的新增项不同。
