# 按用户名单创建 MCPTT 预配置组重组：发起方收到 200，是所有人都收到了吗？

不是。**控制功能收到任一被它请求的终接参与功能回 200，就要向发端参与功能回 200。** 发端参与功能收到成功响应，再向发起客户端回 200。成功的是创建重组这项请求，不是逐人送达通知，更不是所有人已经入呼。〔3GPP TS 24.379 V16.14.0，Rel-16 Stage 3，[§16.3.3.1，印 511](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=512)；[§16.3.2.2，印 509](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=510)〕

## 两台终接参与功能，控制方只收到一份 200

假设要用预配置组 P 为甲、乙、丙建立临时组 T。发起客户端把创建请求（SIP MESSAGE）送到为发起人服务的参与功能，以它的公共服务标识（PSI）为目的地址。重组消息体另列 **T 的唯一 URI**（`mcptt-regroup-uri`）、**P 的组标识**（`preconfigured-group`）、创建动作和三人的 MCPTT ID（`users-for-regroup`）。T 标识本次重组，P 提供配置；T 的 URI 怎样生成由实现决定。[§16.3.1.1，印 507](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=508)

甲、乙由终接参与功能 X 服务，丙由 Y 服务。控制功能按服务关系拆分名单：给 X 发甲、乙，给 Y 发丙。X 在正常处理时**先向控制功能回 200**。它随后查自己保存的通知记录，只对名单中已知尚未通知过的客户端发送创建通知，不把 `users-for-regroup` 复制给客户端；它把相应用户视为已归属 T，并保存 T、P 和成员名单，直到重组移除。[§16.3.3.1，印 511](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=512)；[§16.3.2.4，印 509–510](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=510)

**控制功能已收到 X 的 200，还没收到 Y 的：**控制功能须向发端参与功能回 200，不用等 Y；它保存 T、P 和请求中的成员名单，包括丙。名单回答“这次重组有哪些人”，不回答“谁的客户端已收到通知”。发起客户端收到创建 MESSAGE 的 2xx，宜告知发起人创建成功。仅凭这个结果，连甲、乙是否已收到都不能断定，丙是否已收到也同样未知。[§16.3.3.1，印 511](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=512)；[§16.3.1.1，印 507](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=508)

**只在 X 的发送记录里看见 200：**这能证明 X 发出了响应，不能证明控制功能收到了，也不能由此认定控制功能已经保存成员名单。要判断控制功能是否该回 200，查它是否已收到 X 或 Y 对本次请求的 200。反过来，控制功能没收到 X 的响应也不能说明 X 没发：“没收齐”更不等于“一个也没收到”。[§16.3.3.1，印 511](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=512)

## 收到 403 或 480，先查哪一方？

| 本次创建请求的响应 | 谁在什么条件下给出 | 下一步 |
| --- | --- | --- |
| 403，Warning 文本含 **160** | 发端参与功能从公共用户身份确定发起人的 MCPTT ID，按此 ID 查用户配置档；档中没有设为 true 的 `allow-regroup`。 | 拒绝并停止，不再选择控制功能。查发起人的重组权限。〔[§16.3.2.2，印 508](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=509)〕 |
| 403，Warning 文本含 **165** | 控制功能判定请求提出的临时组 ID **T 已被占用**。 | 控制功能拒绝；发端参与功能按非 480 的 4xx 处理，向客户端回复并携带收到的 Warning。查 T，不是查 P 或发起人的权限。〔[§16.3.3.1，印 510](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=511)；[§16.3.2.2，印 509](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=510)〕 |
| 480，控制功能不能承办此次重组 | 控制功能在分发前回 480，停止处理。 | 发端参与功能必须改选**另一控制功能**，向新选功能的 PSI 重发创建 MESSAGE。〔[§16.3.3.1，印 510](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=511)；[§16.3.2.2，印 509](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=510)〕 |
| 480，控制功能分发后未收到任何终接 200 | 控制功能已向终接参与功能发出 MESSAGE，未收到其中任何一方的 200，向发端参与功能回 480。 | 同样由**发端参与功能**换控制功能；不是让发起人换 T。条款没有给出等候时长，截取的一段记录里还没看到 200，不足以断定已走这个分支。〔[§16.3.3.1，印 511](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=512)；[§16.3.2.2，印 509](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=510)〕 |

裸 403 不能区分无权与 ID 冲突；仅见控制功能回 480，也不能在上表两个原因中二选一。资源不足而无法处理或有拥塞风险时，发端参与功能、控制功能和终接参与功能各自都**可以**拒绝并回 500。发端参与功能若从控制功能收到非 480 的 4xx，或 5xx、6xx，要生成响应、带上收到的 Warning 并转给客户端，不走 480 的重选分支。控制功能的选择方法属于部署决定。[§16.3.2.2，印 508–509](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=509)；[§16.3.2.4，印 509](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=510)；[§16.3.3.1，印 510](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=511)

查原文时留意两处：印 511 第 4 项拆名单、第 5 项发送，但第 5 项及 5e 回指第 3 项，第 6、7 项把发送写作第 4 项，且第 5 项有两个 d。应按发送者、接收者和动作对照。印 507 的客户端成功句写 MESSAGE，失败提示句却写 INVITE；上表的失败处理依据是服务器条款，不据该句断定发起客户端怎样提示 MESSAGE 错误。

如果手上的是**某个客户端收到的创建或移除通知**，要查它如何认定归属、如何回执，见[接收方处理预配置组重组通知](preconfigured-regroup-notification.md)。

**同一系统的请求列了两个组 ID，还要看谁向谁请求。**

- 组管理客户端已取得组成组的配置，向其中一个组成组的组管理服务器（GMS）请求合并这些组，想查哪些组可以合并、GMS 要通知哪些对象，读[同系统临时重组的组成条件及通知](single-system-temporary-regroup.md)。这是业务流程（TS 23.280 V16.7.0 §10.2.4.1）。
- MCPTT 客户端向发端参与功能的 PSI 发创建 MESSAGE，正文列的是 `groups-for-regroup`，则是**按组成组**创建预配置组重组，见 [TS 24.379 V16.14.0 §16.2.1.1，印 495](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=496)。它不是上一项的 GMS 消息，也不是本页按用户名单创建的 MESSAGE；不能把本页“任一被请求的终接参与功能的 200 到达控制方就够”的规则套给它。

若这次 MESSAGE 用的是 `groups-for-regroup`，查[按组清单创建的全部应答与失败补偿](preconfigured-group-regroup-creation.md)。不能沿用本页任一 T-PF 回 200 即可的门槛。
