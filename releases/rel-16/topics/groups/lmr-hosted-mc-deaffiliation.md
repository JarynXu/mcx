# MC 用户怎样解除对 LMR 定义组的归属？IWF 已回应等于解除了吗？

**不等于。** 目标组定义在 LMR 系统，但本次请求来自一名 MC 用户，MC 系统处理个人解除。两侧组和用户的标识映射已配置在 IWF 内，先前已办理 §10.1.2.4 的归属。仍要检查这名用户现在是否归属所请求的组。依据为 3GPP TS 23.283 V16.8.0（Release 16，Stage 2）[§10.1.2.5，开头、前提、注和图 10.1.2.5-1，印刷页 20](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=21)。

| 阶段 | 该看什么 |
| --- | --- |
| MC 客户端发起（步骤 1） | 客户端向 MC 业务服务器提供**发起的 MC 业务 ID**和要解除归属的 **MC 业务组 ID**。 |
| MC 服务器检查（步骤 2） | 根据用户订阅和已存的组策略，核对该用户是否归属这些组，并查目标组是不是互通组。组的类别不代替用户当前归属或授权。 |
| 条件转给 IWF（步骤 3a、3b） | 对互通组，MC 业务服务器发 IWF 组解除归属请求，IWF 返回响应。跨两侧的信令标识和协议由 IWF 转换。本节没写 IWF 响应具体代表成功还是失败。 |
| MC 侧处理、回客户端（步骤 4、5） | 用户获准解除时，MC 业务服务器移除该用户对所请求组的归属状态。随后由该服务器向客户端返回 MC 业务组解除归属响应。图里“更新归属状态”的条件要看步骤 4 正文。 |

[步骤 1–3b，印刷页 20](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=21)；[步骤 4–5，印刷页 21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=22)。一条 IWF 响应不足以证明 MC 侧已移除状态，也不能判定授权通过。原文没有为未获准或 IWF 失败规定这里的处理细节、原因码或回滚，更没有要求同时解除其他用户的归属。非互通组不走步骤 3a；怎样处理其他类型的组不在本节范围。

要回查[原来怎样归属](lmr-hosted-mc-affiliation.md)，核对组宿主和 IWF 映射。若组实际定义在 **MCPTT**，和[反方向归属](mc-hosted-lmr-affiliation.md)区分。若正在核对[既有互通组呼中是否加入](../calls/lmr-interworking-group-late-entry.md)，不要用解除归属的回包代替一次呼叫的结果。此处也不定义 LMR 内部的解除方法或组呼释放。
