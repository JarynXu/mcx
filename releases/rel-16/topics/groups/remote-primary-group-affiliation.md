# 远程改变他人的组归属：什么时候要问目标用户？

甲请主业务服务器改变乙与组 G 的归属关系，例如让乙归属 G 或解除归属。**强制模式不需要乙批准；协商模式下，如果期望状态与现状不同，乙的客户端要征求乙同意。** 两种模式都要查权限。这里讨论的是单项 MC（任务关键）业务、由主系统定义的组，以及归属关系，不是替乙选中某个组。[3GPP TS 23.280 V16.7.0，Rel-16 Stage 2，§§10.8.5.1.1–2，印刷页 160–162](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=161)

**请求说明要改什么，不说明已经改好。** 两种模式下，甲的客户端都已预置目标用户及其获准归属或解除归属的组信息；主业务服务器可能已取得用户或组策略。强制模式还列有一个前提：组管理服务器（GMS）已向组定义所在系统的业务服务器订阅归属状态更新。协商模式并未列这项前提。甲可以针对一个或多个目标用户、一个或多个组提出变更。强制请求指明强制模式及所要求的关系变化；协商请求明确列出目标用户标识、组标识和期望归属状态。即使请求写明“让乙归属 G”，还不能把乙登记为已归属。[§10.8.5.1.1 前提、步骤 1，印刷页 160](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=161)；[§10.8.5.1.2 前提、步骤 1，印刷页 161–162](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=162)

**一份请求涉及多人，先按人读组。** 甲可以要求乙归属 G、解除对 H 的归属，同时只要求丙归属 G。丙的组表里没有 H，就不能把乙的解除请求也算到丙头上。请求有五项必填：甲的业务 ID、目标用户 ID 列表、每名目标各自的组 ID 列表、逐组所求的归属或解除状态，以及这份请求的类型（强制或协商）。[表 10.8.2.11-1，印刷页 149](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=150)

**给甲的答复逐组列结果，不是乙、丙各自的回执。** 服务器单独向甲的客户端寻址，可以用单播或多播。四项必填是甲的业务 ID、目标用户 ID 列表、组 ID 列表和每个所列组的变更结果。组表指要与目标改变归属关系的那些组；响应表没有像请求表那样注明“每名目标各一份”，也没有规定按姓名或列表下标配对。只看到 G 的结果，不能给 H 填成功。即使只有乙一人、G 一组，若乙原本就归属 G，服务器仍会给甲相应的接受答复，并没有新增归属。[§10.8.2.12 引言，印刷页 149](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=150)；[表 10.8.2.12-1，印刷页 150](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=151)；[强制模式步骤 8，印刷页 161](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=162)；[协商模式步骤 6，印刷页 162](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=163)

**强制模式：谁有权改，由谁保存？** 主业务服务器分别查甲能否发起这项变更、按用户签约乙能否具有所请求的归属关系，以及乙同时可归属的组数上限 N2。N2 不是甲在一张请求里能填几个组。服务器还按组策略核对乙是否获准归属或解除归属；本地没有缓存策略时，服务器向 GMS 订阅组策略，收到通知后在本地缓存。按流程核对并确认乙有资格后，服务器保存乙对相应组的请求状态，无需等乙点头。这次业务服务器向 GMS 索取**策略**，与前提中 GMS 向业务服务器订阅**状态**方向相反。[§10.8.5.1.1 步骤 2、3a/3b、4、5，印刷页 160–161](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=162)

若请求的状态与现状不同，主业务服务器向 GMS 更新乙的归属状态（步骤 6），也向乙的客户端发送带强制标记的变更请求（7a），让乙得知最新归属。乙端向服务器回应（7b），不是乙在审批。服务器还向甲端答复（8）；若期望状态原本就与现状一致，步骤 6、7a 的变化条件不成立，服务器自行生成相应的接受响应给甲。**在这些步骤适用时，7b 须在 7a 之后；6、7a、7b、8 除此之外可以换序或并行。** 因此，只看到甲端收到接受响应，不能反推乙端已经回应，甚至不能证明归属曾有变化。[§10.8.5.1.1 步骤 6–8 及其后注，印刷页 161](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=162)

**协商模式：有资格，不等于已同意。** 主业务服务器查甲能否发起，按用户签约和组策略查乙能否具有所请求的关系，并核对 N2。缺组策略时向 GMS 取得。若目标业务用户乙获准接受这类变更，主业务服务器就把请求发给乙的客户端。核的是乙这名用户的权限，收件的是客户端。设备合格或在线，不能代替用户授权；只有乙的资格记录，也不能当作这次请求已经发送或送达的凭据。是否把请求呈给**乙本人**是下一层判断：期望状态与现状不同时才问乙。不要把服务器发给客户端与客户端请人表态合并成一步。[§10.8.5.1.2 步骤 2–4，印刷页 162](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=163)

乙明确接受或拒绝，客户端都把相应响应送回主业务服务器；其中**接受**才触发服务器按甲所求启动后续归属或解归属程序。只有接受响应，不能证明后续程序已经完成。若乙在实现规定的时间内未回应通知，本次协商中止，既不是同意，也不是乙明确拒绝。若期望状态本就与现状相同，乙端不用征求乙批准；服务器生成相应的接受响应给甲，不代表乙亲自批准了变更。[§10.8.5.1.2 步骤 4–6、注 1，印刷页 162](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=163)

若要查 MCPTT 的[协商式归属客户端信令](negotiated-affiliation-client.md)、[远程改变所选组](remote-selected-group-client.md)，或[客户端解除自己的组归属](client-group-deaffiliation.md)，分别读对应主题。这三者不替代上面的主系统 Stage 2 过程。
