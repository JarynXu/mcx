# 组配置保存失败，说明组管理服务器查出了配置错误吗？

不能。组管理服务器（GMS）在保存前**可以**验证配置；验证不通过，或者保存操作本身失败，都会返回失败。只看到某个组的失败结果，不能断定服务器做过验证，更不能断定配置有错。要区分这两种原因，需要另有这笔请求的验证或保存记录。[3GPP TS 23.280 V16.7.0，Release 16，Stage 2，§10.1.5.1 步骤 3–5，印刷页 78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=79)

**先认发送方，再看字段。** 获授权用户的组管理客户端先收到组配置，再把它发给 GMS，请求保存。请求中，MC 业务组标识和该组的配置数据都必填。只有组标识的一条摘录，不足以还原完整请求；客户端发出了请求，也不证明服务器已经写入。[§10.1.5.1 步骤 1–2，印 78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=79)；[§10.1.2.1 表 10.1.2.1-1，印 61](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=62)

**有验证资料，不等于本次验过。** GMS 可能预先持有可用于在线验证组配置的数据，条文没有把“已有这些数据”列为必需条件，也没有要求每次保存前都验证。例如，记录写明 GMS 没有运行验证、但成功保存了组配置，这并不违反本节的验证规则。[§10.1.5.1 前提及步骤 3–5，印 78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=79)

**答复的是这一次服务器保存。** GMS 向发出请求的组管理客户端回送响应；表中两项必填内容是 MC 业务组标识和结果（成功或失败）。所以“G、成功”表示 GMS 报告 G 的配置保存成功，并不是发回一份配置给其他终端。它也不证明新组已创建、伙伴系统已收到配置，或有用户参加了呼叫。[§10.1.2.2 表 10.1.2.2-1，印 61](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=62)；[§10.1.5.1 步骤 4–5，印 78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=79)

要确认某个终端是否取回并保存了新配置，读[客户端取得组配置](client-group-configuration.md)；要判断组 ID 由谁分配，读[普通组的创建](normal-group-creation.md)；若关心主系统能否在伙伴没有请求时主动给它配置，读[主系统向伙伴提供组配置](primary-supplied-partner-group-configuration.md)。
