# 组里有哪些人，哪些人已归属？怎样主动查名单？

要查 G 组，不必先加入 G 组。MC 业务用户无论本人是不是组成员、是否已归属，都可以通过自己的组管理客户端发起查询。**可以问，不等于可以看到名单。** 组管理服务器（GMS）仍要检查发起用户有没有权限执行这次查询；已经是组成员也不能代替这项检查。

## 请求时选哪份名单？

假设甲、乙、丙都是 G 组成员，其中甲、丙已归属。问“G 组有哪些成员”时，选**成员名单**，本例的答案是甲、乙、丙。问“哪些成员已归属 G 组”时，选**已归属成员名单**，本例的答案是甲、丙。乙没有出现在第二份名单，并不表示他已被移出组。这两份名单都不告诉你谁正在参加某次组呼。

请求从发起用户的组管理客户端发给 GMS。请求里有三项必选信息：**发起用户的 MC 业务 ID、目标组的 MC 业务组 ID、查询类型**。第一个 ID 回答“谁在问”，不是要查的某个成员。查询类型表明想取哪一类名单；不要把省略类型解释成“默认查全部”或“两份一起返回”。

## GMS 返回什么？

授权检查通过后，GMS 按请求类型取出名单，回给**发起查询的组管理客户端**。响应的四项必选信息是发起用户的 MC 业务 ID、目标组 ID、查询类型和查询结果。前三项指明是谁、查哪个组、问哪类名单；结果是与类型相符的成员列表，不是一个表示操作成功或失败的开关。

如果不知道用户是否获准，不能仅凭他发过请求就断言他拿到了名单。这里引用的流程和信息表没有规定未获授权时的具体错误码、返回空列表或不发响应；不能把其中任何一种写成本流程的固定行为。上述必选项是 Stage 2 信息流表中的项目，不等于某种线上消息的字段编码。

## 收到组配置，为什么没有全体名册？

**组配置到手，不等于名册应当默认下发。** 表 A.4-1 注 1 规定，成员名单只在获授权的用户提出请求时提供。终端即使刚收到组配置通知并取到了配置，也不能因缺少成员名单就判定配置下发失败。要查是否取得名册，另找面向同一目标组、查询类型为成员名单的请求，以及组管理服务器（GMS）核对权限后给发起端的答复。[表 A.4-1 的成员名单行及注 1，印刷页 214–215](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=215)；[§10.2.5.2，图 10.2.5.2-1，印刷页 102](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=103)。

**完整名册不是只列主系统。** 表 A.4-1 注 8 把该组在主系统和伙伴 MC 系统中的成员都算进去。如果确认对照的是 GMS 针对该组返回的完整**成员名单**，也确认有配置在这组里的伙伴成员，只列主系统就少了成员。先别拿一段转发、筛选后的导出、已归属名单或成员变动通知去比较。它们不一定是那份完整成员名单；名册也不用于判断谁已归属或正在通话。原文没有给出跨系统同步、分页或聚合的具体算法。[表 A.4-1 注 8，印刷页 215](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=216)；[表 10.2.2.17-1，印刷页 91](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=92)；[§10.2.5.2，印刷页 102](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=103)。

## 两行授权用户名单有什么区别？

在网组的配置表 A.4-2 分开列出以下两项。这里读的是表中的配置对象栏，不是线上报文。附录 A.1 说，某栏标 Y，表示该行参数须配置给该栏的功能实体。[附录 A.1 的列义，印刷页 211](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=212)。

| 配置项 | 父行：UE / MC 业务服务器 / GMS | 该行下 MCPTT、MCVideo、MCData ID 子项 |
| --- | --- | --- |
| 可请求成员名单的授权用户列表 | Y / Y / Y | 仅 GMS 栏标 Y；另两栏为空。 |
| 可获取组信息的授权用户列表（表中此项引 §10.2.5） | 三栏均空 | 仅 GMS 栏标 Y；另两栏为空。 |

不能因为第一行的 UE 栏是 Y，就要求把逐业务的获授权用户 ID 都随组配置发给终端。也不能把空白当成原文明确写的 N，或把两行合成一个字段。表没有说明哪一项覆盖另一项、是否要同时校验、如何序列化；一次查询是否授权仍查 GMS 对本次请求的判定。[表 A.4-2 的两项授权用户列表和各自 ID 子行，印刷页 216](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=217)；[§10.2.5.2 第 2 项，印刷页 102](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=103)。

**别把查询当作更改。** 这是客户端主动询问，不改变成员资格，也不建立或解除归属。要了解成员被加入或移出时发给谁、通知里列哪些人，读[成员变动通知](group-membership-notification.md)；要持续观察组状态，读[组动态数据订阅](group-dynamic-data.md)。两者都不是本次查询的后续必经步骤。
