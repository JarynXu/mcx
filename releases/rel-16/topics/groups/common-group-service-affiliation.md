# 同一个组支持三项 MC 业务，用户选两项，可以只获准一项吗？

**可以，但得先区分“组里启用了什么”“终端能支持什么”和“本次准许了什么”。** 比如组 G 使用 MCPTT、MCVideo 和 MCData。用户只选 MCPTT 和 MCVideo；若终端发出合并的归属请求，业务在适当情况下可以只准许其中一项，例如只准许 MCPTT。这不表示终端已完成 MCPTT 归属，也不能仅据此判定有一条 SIP 请求没发出去。

本页只解释 [TS 22.280 V16.8.0 §§8.4.1–8.4.5，Release 16，Stage 1，印刷页 59–60](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60) 的业务需求。组配置、发起归属、服务决定准入和实际归属状态分别取证。

## 一次选两项，是一条请求还是两条？

两种实现都可以，不能从用户的一次操作推断线上请求的数量。一个组须能独立或组合使用多项 MC 业务。对获授权的用户，业务须提供机制，让人对组所用业务的任意子集做一次**逻辑组归属**，也能逐业务归属。§8.4.1 举例：可以有一份归属信息包含两项业务，也可以由终端在一次用户指令后按业务分送两份；原文还有其他可能。它不规定 SIP 怎么写，也不承诺多项业务一定同时成功、失败后一起回滚。[§8.4.1、§8.4.2 R-8.4.2-001、-002，印刷页 59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60)。

**有合并请求再判部分许可。** 如果是终端向同一个共用 MC 业务组发出的合并归属请求，业务可以在适当时只准许部分请求的业务。它不是任何请求的通用响应，也不规定何时应当驳回视频或如何标明结果。如果日志只写“组 G 已归属”，没有业务结果，不能据此认定两项都已准许；如果实际是两笔独立请求，就分别查各业务的结果。[§8.4.4 R-8.4.4-001，印刷页 60](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=61)。

**想退出视频，不必把语音也作为同一个解除目标。** 已获授权且在组 G 中确实归属多项业务的用户，须能逐业务单独解除归属。比如确认两项都已归属后，可以只解除 MCVideo；若记录仅显示此次准许 MCPTT，不能先假定还有一项已归属的视频要解除。该条给独立解除的能力，不给出当前会话是否结束的规则。[§8.4.2 R-8.4.2-005，印刷页 59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60)。

## 终端和业务哪边没公布能力？

| 已知条件 | 可以按哪条判断 |
| --- | --- |
| 判断终端可归属哪些业务 | 业务须提供机制，使用户在共用 MC 业务组里只能归属终端能够支持的业务。组启用了视频，不代表这个终端就能归属视频。 |
| 业务侧公布参加要求 | 业务须提供公布该组参加能力要求的机制，例如所需的编解码格式，用户可在尝试前核对。 |
| 用户正在归属，终端要报能力或限制 | 业务须提供让终端公布自身能力和限制的机制。MCVideo 终端可报支持的编解码格式和码率是条文例子，不是所有业务都必须上报这些字段。 |
| 用户已归属，但终端未提供能力和限制 | 业务必须假定该终端能处理相关的 MC 业务内容。这个假定是后续处理的条件，不证明终端实际能解码，也不能拿来替代准入或补出授权。 |

依据：[§8.4.3.1 R-8.4.3.1-001 至 -004，印刷页 59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60)。

**如果没公布的是业务一侧，规则不同。** 当业务没公布参加某组所需能力，§8.4.3.2 采用的假定是：终端具备该业务的能力就足以参加该组。条文举例：业务使用特定编解码格式，加入的终端支持该业务但不支持该格式，这个例子中由业务为这类终端提供转码。不要把例子改成任何编解码不匹配都必须转码，也不要用这条去解释终端未上报能力和限制的情况。[§8.4.3.2 R-8.4.3.2-001，印刷页 60](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=61)。

## “协调运行”会把规则和身份合成一份吗？

同一组使用的 MC 业务须能相互交互，以支持协调运行。对原本就打算协同的组合业务，还须能把一项业务的**类似地理限制**应用到与它协同的业务。不由此推定各项配置逐字相同、所有业务都协同，或系统已完成同步。[§8.4.2 R-8.4.2-003、-004，印刷页 59](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=60)。

在打算协同的组合中，一项业务须能访问并使用协同业务所用的用户识别信息通信。不要求身份字符串都相同，也不把一项业务的许可带给另一项业务。[§8.4.5 R-8.4.5-001，印刷页 60](https://www.etsi.org/deliver/etsi_ts/122200_122299/122280/16.08.00_60/ts_122280v160800p.pdf#page=61)。

定位问题时，分开查[组配置的业务启用清单](group-enabled-service-configuration.md)、[单业务显式归属](same-system-explicit-affiliation.md)和[解除归属](client-group-deaffiliation.md)；再按实际情况查 [MCData 的已配置子业务](../mcdata/affiliation-configured-subservices.md)、[MCVideo 的能力上报](../mcvideo/onnetwork-capability-sharing.md)或[跨业务身份映射](../identity/cross-service-user-mapping.md)。这些相邻主题各有版本和条件，不能用来补写本条不存在的统一流程。终端已归属后，一条周期位置消息适用于哪些业务或组，见[§8.4.6 的位置消息适用范围](../location/periodic-message-scope.md)。本页不讨论 §8.5 的业务优先规则。
