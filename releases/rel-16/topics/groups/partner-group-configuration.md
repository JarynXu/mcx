# 伙伴系统怎样首次取得组配置，又怎样获知后续更新？

G 组定义在主系统甲，部分组员在伙伴系统乙使用业务。乙的组管理服务器（GMS）还没有 G 的配置时，应先区分两件事：**拿到现在可用的配置**，以及**订阅甲以后的变化**。订阅不是取初始配置的捷径。这是跨系统 GMS 之间的 Stage 2 信息流，不是成员客户端订阅组动态数据。〔§§10.2.7.1、10.2.7.3–5，印刷页 104、106–108〕

## 乙第一次主动取：谁向谁要？

图 10.2.7.3-1 有六项前提：G 在甲定义；乙至少一名业务用户的用户配置中列有 G；乙至少一名在 G 名册中的用户已在乙的业务服务器获得 MC 业务授权；乙的 GMS 尚未存有 G 配置；乙已配置甲的 GMS 寻址信息；乙有权向甲请求组配置。图中假定可按组 ID 寻址 GMS，各 GMS 知道自己管理的组，系统间也已交换相应授权信息。用户获准使用业务与乙有权向甲取配置，是两项不同条件。〔§10.2.7.3 前提及注 1–2，页 106〕

乙的**业务服务器**先向乙的 GMS 要配置；跨系统发请求的是**乙的 GMS**，请求必带 G 的组 ID。甲的 GMS 向乙的 GMS 返回组 ID 和配置，两项都必带。这里的“配置”可以只是完整配置的一部分，由甲根据请求方身份和权限决定。初取响应中的组相关密钥材料是**条件必带**：若乙负责向由乙提供服务的 G 组成员供应组配置，就必须带。§10.2.7.3 正文概述为可携带，不能因此略去响应表的条件；图的注 3 也明确了乙 GMS 对这类成员的职责。〔表 10.2.2.26-1、10.2.2.27-1 及注，页 93；§10.2.7.3 注 3、步骤 1–3，页 106–107〕

收到后，乙的 GMS 按乙的策略和本地配置调整，保存调整后的配置，再通知乙的业务服务器。图中这次通知的接收方不是组员终端；它也不是乙向甲订阅的请求。此处是乙主动请求的情形，甲主动向乙提供现有配置另见 §10.2.7.2。〔图 10.2.7.3-1、步骤 4–6，页 107；§10.2.7.2，页 105〕

## 已有配置，怎样订阅？

G 仍在甲定义，至少一名 G 组成员在乙定义，而且乙的 GMS **已经从甲的 GMS 收到组配置**。前提只要求已经收到，不要求此前一定由乙主动索取。乙的 GMS 向甲的 GMS 发订阅请求，必带组 ID。甲在请求方获准时确认订阅，回应必带组 ID 和订阅成功或失败的结果。成功表示订阅成立，不是返回当前配置，更不是已经收到下一次更新；失败也不能算已订阅。〔§10.2.7.4 前提、图 10.2.7.4-1、步骤 1–2，页 107–108；表 10.2.2.28-1、10.2.2.29-1，页 93–94〕

## 订阅之后，什么变化会使甲发通知？

乙的 GMS 已向甲订阅 G；甲的 GMS 又**取得并保存了新组配置**，或**生成并保存了新组相关密钥材料**，或两者兼有，才符合图 10.2.7.5-1 的通知前提。不需要两种变化同时发生。〔§10.2.7.5 前提，页 108〕

通知请求从甲的 GMS 发给乙的 GMS。**区分触发原因和消息内容：**即使只有密钥材料变化，通知表仍把组 ID 和组配置列为必带，把组相关密钥材料列为可选。这不是初取响应的条件必带规则。乙向甲返回组 ID 及成功或失败结果。流程步骤 2 说乙报告接收结果；响应表把结果的范围写为乙对配置的接收、修改和保存。这是 GMS 间对本次通知的回应，不是成员逐人回执，也不能据此断定每台终端都已采用配置。〔表 10.2.2.30-1、10.2.2.31-1，页 94；图 10.2.7.5-1、步骤 1–2，页 108〕

若问题是同一系统内有人被加入或移出名册，见[组成员变动通知](group-membership-notification.md)；若是 MCPTT 客户端要看组的动态状态，见[组动态数据订阅](group-dynamic-data.md)。这两件事都不是上述 GMS 订阅的后续步骤。
