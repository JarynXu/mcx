# 伙伴系统怎样首次取得组配置，又怎样获知后续更新？

组 G 定义在主系统甲，伙伴系统乙也为部分组员提供业务。乙的组管理服务器（GMS）没有 G 的配置时，可以在满足下述条件后向甲索取。乙若要订阅以后的变更，前提却是**已经从甲收到该组配置**。初取、订阅和更新通知各有前提；一次订阅成功，不表示任何终端已经拿到新配置。〔§§10.2.7.3–5，印刷页 106–108〕

## 乙第一次主动取：谁向谁要？

这次初取有六项前提。看组和用户：G 在甲定义；乙至少一名业务用户的用户配置中列有 G；乙至少一名列在 G 名册中的用户已在乙的业务服务器获得 MC 业务授权。再看系统：乙的 GMS 还没有存储 G 的配置；乙已配置甲的 GMS 的寻址信息；乙有权向甲请求组配置。用户能用业务，不等于乙能跨系统取配置。若乙配置的是甲的代理地址，由甲内部路由选出实际提供配置的 GMS。〔§10.2.7.3 前提、注 1，页 106〕

乙的**业务服务器**先向乙的 GMS 要配置；跨系统请求由**乙的 GMS 发给甲的 GMS**，必带 G 的组 ID。甲向乙回应时，组 ID 一定要带。表 10.2.2.27-1 把组配置信息和失败原因都标为 O，但各有一条表注：**甲能满足请求时必须带组配置；不能满足时必须带失败原因。** 不能将 O 理解为甲可以任意省略当前分支所需的信息。这两条表注也没有规定按请求方身份或权限裁剪配置。〔表 10.2.2.26-1、10.2.2.27-1 及注 1、2，页 93；§10.2.7.3 步骤 1–3，页 107〕

在乙拿到配置的流程中，乙的 GMS 按乙的策略和本地配置调整它，保存调整后的版本，再通知乙的业务服务器。末步接收方不是终端。乙的 GMS 有责任向**由乙提供服务的 G 组成员**提供配置，但这项职责既不能证明这些终端已收到，也不能据此认定甲的初取响应必须附带密钥材料。反过来，§10.2.7.2 由甲的 GMS 主动向乙提供配置，不是乙先发起的索取。〔§10.2.7.3 注 2、步骤 3–6，页 106–107〕

## 已经收到配置，乙怎样订阅？

G 在甲定义，至少一名 G 组成员在乙定义，且乙的 GMS 已经从甲的 GMS 收到 G 的配置。这里不要求此前一定由乙主动索取。乙的 GMS 向甲的 GMS 发订阅请求，必带组 ID；甲给乙的响应必带组 ID 和结果，说明这次订阅请求成功还是失败。这个响应没有告诉乙下次会更新什么，也不是第一次取配置的响应。〔§10.2.7.4 前提及步骤 1–2，页 107–108；表 10.2.2.28-1、10.2.2.29-1，页 93–94〕

## 更新通知带什么，回执能证明什么？

发通知须同时满足两方面条件：乙的 GMS 已向甲订阅 G 的配置；甲的 GMS 已收到并保存新组配置、已生成并保存新密钥材料，或两者都已发生。不要求配置和密钥同时变更。甲的 GMS 给乙的 GMS 发通知，表 10.2.2.30-1 要求带组 ID 和组配置信息。即使只因密钥变化触发，这两项也不因此可省。§10.2.7.5 步骤 1 另说明，这条通知可以携带给组管理客户端的组相关密钥材料。这里的“可以”来自流程文字，不是上述表的一行。〔§10.2.7.5 前提及步骤 1，页 108；表 10.2.2.30-1，页 94〕

乙的 GMS 再向甲的 GMS 回复组 ID 和结果，二者都必带。**结果报告的是本次通知请求成功或失败**。这些 Stage 2 条款不规定 Stage 3 消息编码或密钥处理细节。保存是另外写出的动作：通知程序完成后，乙的 GMS 保存组配置，以及本次实际提供的密钥材料（如有）。因此，不能凭成功响应断定乙在回复前已经保存，更不能把它当成组员终端已经采用新配置的凭据。〔表 10.2.2.31-1，页 94；§10.2.7.5 步骤 2 及步骤后的末段，页 108〕

## 跨安全域排查：该看哪两端的记录？

**先看交换的配置，再看谁跟谁通信。** 甲、乙是分属不同安全域的 MC 系统，G 可参加互联组呼。换成另一个组时，要重新确认这个组能否参加；只知道两个系统互联还不够。甲的 GMS 主动把 G 的配置交给乙的 GMS，或乙的 GMS 向甲的 GMS 初取 G，都要看两侧 GMS 之间的**非订阅、非变更通知**信令。这个逻辑参考点是 **CSC-16**；它用 **HTTP-1、HTTP-2、HTTP-3** 传送和路由这类信令。甲主动提供不因此变成一次已订阅的更新通知。乙主动取时，乙的业务服务器先向本地 GMS 要配置，最后是乙的 GMS 通知本地业务服务器；这两段都不是 CSC-16。成员终端向 GMS 取配置也不是 CSC-16。〔§7.5.2.16，印 40；§10.2.7.2 步骤 1，印 105；§10.2.7.3 步骤 1–6，印 107〕

**乙订阅 G、甲通知 G 有更新，看的是另一类信令。** 业务上仍是乙的 GMS 向甲的 GMS 订阅，甲的 GMS 向已订的乙 GMS 通知。在参考点上，**GMS 与 MC 网关服务器之间**承载互联组配置的订阅与通知的是 **CSC-19**，用 **SIP-2、SIP-3**。**两个不同系统、不同安全域的 MC 网关服务器之间**承载这类信令的是 **CSC-21**，用 **SIP-3**。只在 CSC-16 的 HTTP 侧找更新，即使找不到，也不能据此说乙没订、甲漏发或乙没收到。要分别核对 G 的订阅结果、甲针对本次变化的通知，以及乙对同一次通知的回应。〔§§7.5.2.20、7.5.2.22，印 41；§§10.2.7.4–5，印 107–108〕

同一对跨域网关也能承载**为系统间迁移共享的用户配置**订阅与通知。在配置管理服务器与 MC 网关服务器之间，这一类是 **CSC-20**，同样用 **SIP-2、SIP-3**；在两侧网关之间仍是 **CSC-21 / SIP-3**。因此，一条只认出两端网关和 SIP-3 的记录，不能区分互联组配置和迁移用户配置，更不能据此指认某个组、某个订阅或某位组员收妥了更新。如果只查到某 MC 网关的对端是一台服务器，先核对它在这次交换中承担什么管理角色。普通 MC 业务服务器不等于 GMS 或配置管理服务器；只知道服务器名称，不能定为 CSC-19 或 CSC-20。这两个参考点不要求管理服务器与网关分属不同安全域。要认定具体业务，还要核对同一事务的对象及操作。§10.2.7 的程序图可以不画系统边缘的代理；参考点名称不是物理跳数、抓包先后或具体 HTTP/SIP 方法的清单。〔§§7.5.2.20–22，印 41；§10.2.7.1 末段，印 104–105〕

若问题是同一系统内有人被加入或移出名册，见[组成员变动通知](group-membership-notification.md)；若是 MCPTT 客户端要看组的动态状态，见[组动态数据订阅](group-dynamic-data.md)。这两件事都不是上述 GMS 订阅的后续步骤。
