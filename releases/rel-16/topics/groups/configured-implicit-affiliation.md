# 按配置档隐式归属：MCPTT 已授权，为什么没看到向组发归属请求？

手持台的用户配置档列着“巡检组”。服务授权成功后，既没看到手持台申请归属，也没看到服务器向巡检组发请求，能判失败吗？**不能。** 这条流程由服务该用户的参与 MCPTT 功能（PF）按配置档发起，不要求手持台先发显式归属请求。即使配置正确，PF 也可能按规定不发组请求。要分清原因，先看这台手持台原有的组记录，再看 PF 是否实际向组所有者发布；终端得知结果又是另一件事。以下限于 Release 16 同系统普通在网 MCPTT，依据 3GPP TS 24.379 V16.14.0（Stage 3）。

## 哪些配置组需要发请求？

先确认实际走的是[同时办理授权和设置](../identity/shared-sip-registration.md)，还是授权后[仅发布设置](../calls/settings-publication.md)。两支都在各自程序走到第 13 项，且该用户配置档的 `OnNetwork/ImplicitAffiliations` 中至少有一个含 MCPTT 组 ID 的 `entry` 时，才调用 §9.2.2.2.15。仅发布设置不重新办理授权。PF 须已成功办过业务授权；它用**那份授权请求**中的 MCPTT ID 和业务信息正文的 `mcptt-client-id` 找到该用户及其客户端。PF 尚未存有用户配置档才下载；若档中没有上述容器，或没有含组 ID 的条目，§9.2.2.2.15 第 4 项直接跳过余步。普通 REGISTER 或一份设置 PUBLISH 的 200，不能证明这一步走过。[§7.3.3 第 13 项，印刷页 157](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=158) [§7.3.4 第 13 项，印刷页 158](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=159) [§9.2.2.2.15 入口及第 1–4 项，印刷页 185–186](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=186)

PF 只复制**本客户端**的组列表做候选。逐个核对配置组：本端没有该组，或该组项已过期，才新增一项，初态为 `affiliating`（正在归属），到期时刻为当前时刻加候选有效期。**一个也没新增，就丢弃候选并停止**：不替换原表，也不因旧项仍显示 `affiliating` 就发请求。没抓到包本身不能证明 PF 命中了这个分支。[§9.2.2.2.15 第 5–8c 项，印刷页 186](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=187)

本次确有新增，才算用户上限 N2：把本端候选表与**同一用户其他客户端**的组记录合起来，只取未过期且状态为 `affiliating` 或 `affiliated` 的不同组 ID。例如，车载台已有巡检组，手持台原先没有，手持台仍要新增；两端的巡检组在 N2 中只算一个。超过 N2 才按服务商策略缩到 N2；条文没规定要保留哪个组。PF 用候选表替换的仍只是本客户端的列表。随后重看**每个配置组**：候选表内有该组的 `affiliating` 项，就按 §9.2.2.2.6 向其组所有者发布。第 11 项没有把这一步限定在“本次新增、尚未过期、还没写过 p-id”的项上。比如本端原有未过期的巡检组仍在归属中，另一配置组这次才新增；若巡检组仍在候选表且仍为 `affiliating`，即使已有归属 p-id，它也符合第 11 项。这不是一套并发或重试规则。[§9.2.2.2.15 第 9–11 项、注 1，印刷页 186–187](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=187)

## PF 发了什么？组所有者回 200 意味着什么？

这笔归属 PUBLISH 发往该组控制 MCPTT 功能的公共业务标识（CF PSI）。业务正文用 `mcptt-request-uri` 指明组、用 `mcptt-calling-user-id` 指明用户；`P-Asserted-Identity` 是发送服务器的 PSI，归属请求的 `Expires` 为 4294967295。这里区分的是两个功能的职责，不要求部署在两台机器上，也不保证外部采集点能看到这笔通信。PF 为此次发布生成新的全局唯一 `p-id`。第 9 项把它写入该用户各端中**该组、未过期、正在归属且尚无归属 p-id** 的项；第 10 项对每组 PIDF 正文中的客户端另设条件：须属于该用户，客户端 ID 等于受服务客户端 ID，该组项未过期且为 `affiliating` 或 `affiliated`。正文带本次 p-id；不能把本地写了编号的客户端都算进报文。若这笔 PUBLISH 的 Timer F 到期，或 PF 收到对它的 3xx、4xx、5xx、6xx，PF 须移除该用户各客户端下匹配该组的项，不是只撤手持台本次新增的那一项。只缺一次回包记录，不足以判定 Timer F 已到期。[§9.2.2.2.6，印刷页 177–178](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=178)

只有组所有者**实际收到**符合 §9.2.2.3.3 入口的 PUBLISH，才能按组侧规则判读：请求投给本组 CF PSI，业务正文带组和用户两个标识，`P-Asserted-Service` 标明 MCPTT，`Event` 含 `presence`，PIDF 正文描述该组。处理顺序决定了响应能证明什么：

- `Expires` 缺失，或为小于 4294967295 的非零值：回 **423**，`Min-Expires: 4294967295`，停止。组在组管理服务器中不存在，或该用户不是成员：回 **403**，停止。单看 403 分不出这两个原因。
- 通过上述检查，组所有者先发 **200 OK**，响应的 `Expires` 是所选期限；随后才核对 PIDF 的 `presence@entity` 是否等于该组 ID、`tuple@id` 是否等于该用户 ID。任一不符就停。身份相符且所选期限非零，才在该组下找到或建立用户项，按正文登记客户端名单和所选期限，再识别 p-id 并调用组状态通知程序。看到 200，不能据此断定名单已更新，更不能断定终端已收到通知。[§9.2.2.3.3，印刷页 188–190](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=189)

这里没有一笔“要求发送客户端隐式归属某个目标组”的原 SIP 请求可用来结案。那一支[以原请求的响应完成或取消](implicit-affiliation-n2.md)，不适用于本页的组侧 PUBLISH。

## 谁能证明手持台看到的结果？

**组所有者 → PF：按组报告。** 组所有者按 §9.2.2.3.5 为已按 §9.2.2.3.4 建立的订阅发送 NOTIFY。每组 PIDF 的归属项带 `expires`；若由 §9.2.2.3.3 调用且识别出 handled p-id，通知带该值。要确认 PF 本地的状态，另查 §9.2.2.2.7：PF 可为了解组侧结果发起状态查询或订阅，§9.2.2.2.15 并没有随发布自动建立这份订阅。若 PF 实收的有效组通知中，用户（`tuple@id`）、客户端（`affiliation@client`）匹配且带期限，而本地该用户、该端、该组有未过期的 `affiliating` 项，才按该分支改成 `affiliated`。若有效通知中缺少匹配，原为未过期 `affiliated` 或 `deaffiliating` 的项按第 2 项置为 `deaffiliated` 并到期；原为未过期 `affiliating` 的项还要求通知的 p-id 与该项已记的 p-id 一致，才按第 3 项这样处理。**没收到通知与收到通知、但正文缺项，是两件事。** [§9.2.2.3.5，印刷页 191](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=192) [§9.2.2.2.7，印刷页 179–181](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=180)

**PF → 手持台：按用户报告。** §9.2.2.2.15 注 2 指向客户端独立的状态查询或订阅。查本用户在本端的组时，手持台向自己的服务 PF 发 SUBSCRIBE；只取当前状态时 `Expires=0`，还要后续变化时用 4294967295，并用本客户端 ID 限定结果。PF 按这份订阅生成每用户 PIDF 通知，不列已过期或 `deaffiliated` 的项。要说“手持台已看到巡检组归属成功”，需看到**手持台实际收到**相应的有效 NOTIFY，且正文中本用户、本客户端的巡检组报告为 `affiliated`。§9.2.2.2.7 没有要求 PF 每收到一份组通知就立刻执行 §9.2.2.2.5，也不能把组通知的 p-id 直接当成终端通知的关联号。PF 更新本地记录、组所有者发出 NOTIFY、SUBSCRIBE 收到 200，都不是手持台收件；以上步骤也不证明手持台加入了组呼。两条订阅的构造与过滤可参看[归属状态观察](explicit-affiliation-client.md)，无需把那页的显式兴趣发布当作本流程的前提。[§9.2.2.2.15 注 2，印刷页 187](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=188) [§9.2.1.3，印刷页 169–170](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=170) [§§9.2.2.2.4–5，印刷页 176–177](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=177)
