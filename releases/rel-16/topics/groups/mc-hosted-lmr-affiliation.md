# 电台通过 IWF 呼叫 MCPTT 系统定义的组，必须逐人归属吗？

不一定。先确定目标组 G 定义在 MCPTT 系统，再看互通功能（IWF）**是否已经代表它所接的陆地移动无线电（LMR）用户归属 G**。能连接、配好了身份映射，甚至组员名单里已经有 IWF，都不能代替这个状态。这里讨论的是组归属；归属 G 不等于加入一通正在进行的组呼。依据是 3GPP TS 23.283 V16.8.0（Release 16）的 Stage 2 功能流程。[§10.1.2.1 a–f，印刷页 16](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=17)；[§10.1.2.1 g–h，印刷页 17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=18)。

## 看目标组，也看是哪台电台

| MCPTT 系统里已知的事实 | 来自电台甲的请求怎样判断？ |
| --- | --- |
| IWF 已代表其 LMR 用户归属 G，甲属于这台 IWF 所接的系统 | MCPTT 把甲视为已归属 G，不要求预先把甲单独列入 G 的名单。甲可基于这项归属请求建呼或话权；甲自己的请求仍用映射后的**甲的 MCPTT ID**。 |
| IWF 未归属 G，与该 IWF 关联的 LMR 系统中的甲向 G 发起呼叫 | 只有**甲映射后的 MCPTT ID 在 G 的组员名单内，而且甲本人已经归属 G**，该呼叫请求才可能被接受。只满足一项不够；两项都有也不等于呼叫已经建立。这里的条件针对呼叫请求，不能从中推出其他请求的判据。 |
| 只知道 IWF 在 G 的名单中、已获配置，或它已归属另一个组 H | 先查 IWF 对 **G** 的实际代表归属。若已归属，再核对甲与它的关联；若未归属，再查甲在 G 的成员资格和个人归属。不能用 H 的归属代替 G，也不能把未知当成未归属。 |

要走代表归属，G 的组员名单须有 IWF 的 MCPTT ID，MCPTT 通过配置识别这个 ID 有权代表与该 IWF 关联的 LMR 用户。这个配置说明的是 IWF 的权限，不是逐台电台的名单。IWF 用自己的 ID 归属 G，MCPTT 识别这是代表归属。名单里没有这个 IWF 的 ID，它就不能代表用户归属 G。MCPTT 根据甲映射后的 MCPTT ID 与该 IWF 属于同一系统来识别关联；另一系统电台乙不能仅凭这台 IWF 已归属 G 就取得同样待遇。[§10.1.2.1 a–d、e，印刷页 16](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=17)；[g–h，印刷页 17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=18)。

代表归属生效后，甲发起呼叫不会再触发 MCPTT 代甲做一次归属，也就不会因额外归属而向代表和甲重复发送释放消息。准许甲提出话权请求不等于已经授予话权，也不能证明媒体送达。

在配置 IWF 代表用户的方式下，请求用谁的 ID 取决于谁在行动：甲自己的请求带甲经转换的 MCPTT ID；IWF 自己代组内电台发请求时可用 **IWF 的 MCPTT ID**，例如请求加入聊天模式的组。身份规则不要求先证明 IWF 已归属，也不放宽上表中 IWF 尚未归属时对个人呼叫的两项要求。[§10.1.2.1 d(ii–iv)、e–f，印刷页 16](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=17)。

## 为什么首人归属和末人解除才上报？

LMR 系统可以逐人上报：每次有人归属，IWF 都向 MCPTT 转达该成员归属，并将身份转换为这名成员的 MCPTT ID。也可以合并上报。设 L 是 **LMR 系统内**与 MCPTT 的 G 对应的指定组。第一名 LMR 成员在无线系统内归属 **L** 时，IWF 向 MCPTT 代表组内电台报归属 **G**；最后一名成员在无线系统内解除对 **L** 的归属时，IWF 向 MCPTT 代表大家报解除。**只用合并方式时**，其间不再向 MCPTT 发组归属信令。触发上报的是 L 侧的归属人数从零变为一、从一变为零，不是甲先逐人归属 G、名单增删或某台电台进出一通呼叫。两种方式也可并用，由部分成员显式归属，IWF 代表其他成员。即使代表已归属，名单内的个人仍可通过 IWF 自行归属。[§10.1.2.1 开头、e(i)，印刷页 16](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=17)。

## MC 侧查什么，状态记在谁名下？

1. IWF 已连接 MC 系统且获准互通，持有互通组信息，并配置了两侧组标识和用户标识的映射。它负责身份转换和协议翻译，代表 LMR 系统把组归属请求发给 MC 业务服务器。[§10.1.2.2 前提 1–4、注 1、步骤 1，印刷页 17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=18)。
2. MC 业务服务器已有组策略缓存时直接使用；没有缓存才向组管理服务器（GMS）取策略。它按策略检查目标组是否未禁用，以及 IWF 所给 MCPTT ID 标识的用户是否获准归属该组。互通许可不等于对 G 的归属许可。[§10.1.2.2 步骤 2a、2b、3，印刷页 17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=18)。
3. MC 业务服务器按组策略和用户订阅，将 IWF 归属到目标组。要求逐人归属时，用 IWF 提供的、对应这名 LMR 用户的 **MC 业务 ID** 保存该人的归属状态；不要求逐人归属时，用 IWF 提供的 **MC 业务 ID** 保存组的归属状态。看到一条组状态，不代表服务器为每台电台各存了一条个人状态。[§10.1.2.2 步骤 4 起，印刷页 17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=18)；[步骤 4 续，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=19)。
4. MCPTT 服务器把组归属状态更新发给 GMS，GMS 存储并更新该状态。步骤 6 是 MC 业务服务器向 **IWF** 返回归属响应。条款没有写服务器需等 GMS 确认存储后才响应；此处的响应接收方也不是电台，不能用这一步证明电台收到了无线侧确认。[§10.1.2.2 步骤 5–6、注 2，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=19)。

这两节不给出电台在 LMR 侧如何归属、线上的协议方法和字段，也不讲由 **LMR 系统定义组**的反向流程。若两侧都是 MC 业务提供方，查[用户归属伙伴 MC 系统定义的组](partner-group-affiliation.md)，不要把两个 MC 系统的检查套到 IWF 上。
