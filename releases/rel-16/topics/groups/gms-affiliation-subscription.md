# 组管理服务器怎样跟踪一个组的归属状态？名单能认出哪台终端吗？

组管理服务器（GMS）可以向**定义该组的 MC 系统内的业务服务器**订阅组归属状态。业务服务器保存这份状态，订阅涵盖隐式和显式归属。GMS 表里列的是归属该组的成员在相应业务中的 **ID**，不是逐台终端的名单。

**订阅答复和变更通知怎样区分？** 以 G 组为例，GMS 先向上述业务服务器发订阅请求，业务服务器向 GMS 答复请求成功或失败。成功说明订阅请求被接受，并不证明 G 组的状态已经变化、GMS 已收到变化通知，或某名用户刚完成归属。失败答复也不能作为这次订阅成立的依据。[3GPP TS 23.280 V16.7.0（Release 16，Stage 2），§10.1.5.6.3，订阅程序的说明、前提及步骤 1–2，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=84)。

变更通知有两个前提：**GMS 已订阅 G 组的归属状态，且业务服务器上 G 组的归属状态已经更新**。这时业务服务器向订阅的 GMS 发通知，提供归属状态；GMS 再向这台业务服务器回通知响应。订阅答复和变更通知都是业务服务器发给 GMS 的，不能只凭方向辨认。另一组的状态变了，也不满足这次针对 G 组的通知条件。[§10.1.5.6.3，通知程序的两个前提，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=84)；[通知步骤 1–2，印刷页 84](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=85)。

**名单里的 ID 标识谁？** GMS 的归属状态表先标明 MC 业务组 ID，再按业务列已归属成员：MCPTT 项下是 MCPTT ID，MCVideo 项下是 MCVideo ID，MCData 项下是 MCData ID。组 ID 指明查的是哪个组；例如在 G 的 MCVideo 项下看到甲的 MCVideo ID，说明名单将甲列为该组的视频业务已归属成员，不能据此断言甲在 MCPTT 或 MCData 下也已归属。表内没有列出终端标识或归属时所用的联系地址（Contact URI）；不要把业务服务器的其他动态数据当成 GMS 这张表要求提供的项目。[§10.1.5.5.2，首段及表 10.1.5.5.2-1，印刷页 81](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=82)。

若甲用同一业务用户身份登录手持机和车载机，只看到甲的业务 ID，不能判定是哪一台归属，也不能判定两台都已归属。表后的编者注明确将**同一 MC 业务用户登录多台终端（UE）时，GMS 如何支持其归属状态**列为待研究（FFS）。这既不是说多终端登录被禁止，也不是说整项归属订阅都未定义。[§10.1.5.5.2，表后编者注，印刷页 81](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=82)。

如果是用户想通过组管理客户端向 GMS 查一次名单，见[主动查询组名单](group-list-query.md)；如果订阅方是 MCPTT 客户端，要查参与功能和控制功能怎样处理，见[客户端订阅组动态数据](group-dynamic-data.md)。这两种问题都不同于 GMS 向业务服务器订阅。

若要查本系统单项业务的显式归属如何触发，以及本次 GMS 更新和客户端逐组答复谁先发，读[本系统显式归属](same-system-explicit-affiliation.md)。只见一个组的动态数据不能替客户端确认其他组。
