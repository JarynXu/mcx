# 新建普通 MC 业务组：谁定组 ID，谁会得知建组？

管理员要把甲、乙编入一个新组，请求列的是两人的 **MC 业务用户 ID**，不是若干已有组的 ID。以下是同一 MC 系统内的在网建组：组管理客户端、组管理服务器（GMS）、MC 业务服务器和成员都在该系统内，发起者已知道拟纳入哪些用户。〔§10.2.1，页 86；§10.2.3 前提 1–2，页 94〕

## 请求必须先取一个组 ID 吗？

不必。用户 ID 列表是必选项，但可以是空列表。步骤 1 要求说明组要启用的业务；不要因此把专门的“MC 业务列表”字段一律判为必选：表中标为可选，注 2 要求建多业务组时必须带。建议组 ID 和组配置数据均可省略。〔表 10.2.2.1-1 及注，页 87；§10.2.3 步骤 1，页 95〕

| 请求中的建议组 ID | GMS 在步骤 2a 的处理 |
| --- | --- |
| 没有提供 | GMS 生成组 ID，不要求发起者补填。 |
| 已提供，且可接受 | 新组采用该 ID。 |
| 已提供，但不可接受 | GMS 可以修改建议值、另行生成组 ID，或拒绝建组请求。规范没有规定三者的尝试顺序。 |

若继续建组，GMS 在步骤 2b 保存组配置数据（需要时先创建），并检查组成员总数上限 Nc6。这是成员数检查，不是判定建议 ID 是否可用的条件。〔§10.2.3 步骤 2a–2b，页 95〕

## 业务服务器、成员和发起者各会知道什么？

图 10.2.3-1 从保存配置往下画了三步。它给出的是流程顺序，并没有要求 GMS 等全体终端签收后才返回结果。

**第 3 步，MC 业务服务器。** 普通建组时，GMS 可以按条件发建组通知，并非每建一组都必发。通知里必带新组 ID 和组内用户的业务 ID 列表；如配置了多项业务，发送对象是为该组配置的相应业务服务器。§10.2.3 没有给出普通建组触发该通知的具体判据。同一条款还写了 *user regroup*（按用户重编组）这一不同情形：此时 GMS 通知业务服务器临时组及其成员；仅当业务服务器做了相应配置，这些用户才可能自动归属。不能把这条特殊规则搬到普通建组。〔表 10.2.2.7-1 及表前注，页 88；§10.2.3 步骤 3，页 95〕

**第 4 步，新组成员。** 如果新组有成员，成员的组管理客户端会获知有了该组的新配置。成员列表为空，就没有这一步要通知的成员。知道新配置不证明该用户已归属，更不证明已加入某次组呼。发起者若也想参加，仍须列为成员并归属该组；发起建组本身不给他这些身份。〔图 10.2.3-1、步骤 4，页 95；§10.2.1 注 1，页 86〕

**第 5 步，发起者的组管理客户端。** GMS 返回操作结果：成功并采用建议 ID，成功并采用 GMS 提供的 ID，因建议 ID 不可接受而失败，或因其他原因失败。响应表把结果和组 ID 都列为必选，但结果为失败时，**组 ID 字段的值没有意义**，不能拿来寻址或证明组已创建。成功响应也不是成员签收记录。〔§10.2.3 步骤 5，页 96；表 10.2.2.2-1 及注，页 87〕

若要把几个**既有组**临时合并，见[同系统临时重组](single-system-temporary-regroup.md)；若只改已有组的名册，见[组成员变动通知](group-membership-notification.md)。
