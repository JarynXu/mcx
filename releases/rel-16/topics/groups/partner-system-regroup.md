# 跨系统临时重组：伙伴接受了请求，主系统就拿到了用户名单吗？

不一定。主系统想把自己的 A 组和伙伴系统的 B 组编成临时组 T。伙伴要回答的是“是否接受，涉及我管理的哪些**组**”。列出 B 的组 ID，不等于列出 B 中的人；主侧也不需要靠一份伙伴用户名单逐个通知 B 的成员。

## 两侧分别查什么？

这里的 A、B 配置了相同的 MC 业务；主侧已获授权用户的组管理客户端已经取到两组配置。它向管理 A 的组管理服务器（GMS1）请求重组，列出 A 和 B 的组 ID，指明是否广播重组，也可提出安全级别和优先级。GMS1 按组策略核实**发起人**是否有权操作，并查 **A 自身**是不是临时组。如果 A 已是临时组，就拒绝，不继续转发。否则，在授权检查通过后，GMS1 把属于伙伴服务器 GMS2 的组成组 ID 列表转给它。GMS2 查的是自己管理的 B：如果 B 已是临时组，同样拒绝。〔§10.2.4.2 前提及步骤 1–4，印刷页 98–99；表 10.2.2.12-1，页 89〕

A、B 都是普通组，并不保证可以重组。已经编入另一个临时组的组成组不能再用；系统策略**不允许**纳入处于紧急状态的组时，任一组成组处于紧急状态也会阻止重组。还须满足 §10.2.4.4 对系统策略和业务服务器控制角色的要求。该条区分“临时组可包含外系统的组”和“不可包含外系统的组，但组的成员分布在不同系统”，不能拿后一种情形来放行外系统的组成组。〔§10.2.4.4，页 101〕

## 伙伴回复的是组 ID，还是用户 ID？

步骤 5，GMS2 向 GMS1 回复。表 10.2.2.13-1 列了两项必选信息：伙伴侧接受或拒绝的**结果**，以及伙伴侧的**组成组 ID 列表**。表中没有必传的用户 ID 名单。即便结果是接受，这也只是伙伴对请求的答复，还不是主侧建好 T 或发起客户端收到结果的凭据。〔§10.2.4.2 步骤 5–6、17，页 99–100；表 10.2.2.13-1，页 90〕

用户信息共享的安全事项由双方服务提供商的协议约束。条款举的情形是伙伴不向主侧提供所管理组的用户信息。步骤 5 后的注另说，两家服务提供商有信任关系时，伙伴**可以在这一步**向主侧共享用户信息，但没有要求它一定共享，更没有规定必须交出完整名册。即使这一次共享过，后来 B 加人或减人，针对 T 怎样与主系统同步，仍不在本规范范围内；不能从 B 的变更推定主侧名册已经更新。〔§10.2.4.2 前提 1、步骤 5 及其后注，页 98–99〕

## 接受和拒绝之后能断言什么？

**接受且其余条件满足时**，步骤 6 由 GMS1 创建并保存 T 的信息，包括临时组 ID、组成组标识、离网信息、优先级、安全级别及广播属性。若发起人既未指定安全级别又未指定优先级，取组成组中较低的安全级别和较高的优先级。GMS1 随后通知 GMS2；GMS2 确认，并保存 T 与组成组的标识、优先级和安全级别。〔§10.2.4.2 步骤 6–8，页 99〕

### 同叫“通知”，要先看发给谁

步骤 7–8 是两台 GMS 之间的往返。此后，GMS2 联系伙伴侧业务服务器和 B 中已归属的成员，GMS1 联系主侧业务服务器和 A 中已归属的成员。已归属成员通过各自的组管理客户端向本侧 GMS 回执，不是向主侧交一份跨系统人员名册。下表中 M 为必选，O 为可选。

| 方向（成功流程的步骤） | 消息及字段 |
| --- | --- |
| GMS → 本侧 MC 业务服务器（9、13） | 表 10.2.2.8-1 的 **Group regroup notify**：组成组 ID 列表、T 的组 ID 均为 M；启用的 MC 业务列表、广播指示均为 O。该表没有优先级或安全级别。步骤 10、14 是业务服务器确认，不能把成员回执的字段套给它。 |
| GMS1 → GMS2（7），或本侧 GMS → 已归属成员的组管理客户端（11、15） | 表 10.2.2.14-1 的 **Group regroup notification**：组成组 ID 列表、T 的组 ID 均为 M；优先级、安全级别、广播指示均为 O。 |
| GMS2 → GMS1（8），或已归属成员的组管理客户端 → 本侧 GMS（12、16） | 表 10.2.2.15-1 的 **Group regroup notification response**：组成组 ID 列表、T 的组 ID、优先级、安全级别均为 M；广播指示为 O。 |

即使方向同为 GMS2 → GMS1，步骤 8 确认的是刚收到的**建组通知**，步骤 5 回答的却是是否接受**重组请求**。步骤 17 才是 GMS1 向发起客户端回复；步骤 18 是已归属成员各自请求临时组配置。〔§10.2.2.8 的方向与表 -1，页 88–89；表 10.2.2.13-1、10.2.2.14-1、10.2.2.15-1，页 90；§10.2.4.2 步骤 5、7–18，页 99–100〕

**违反重组规则时**，步骤 5 明写应给否定响应，并跳到**步骤 15**。该版步骤 15 的正文是 GMS1 通知主侧已归属成员，并非向发起客户端回复（那是步骤 17）。保留这个回指：不能把 15 改成 17，也不能把成功路径中步骤 6 的建组、两侧存储和临时组配置获取当作拒绝后的既成事实。该回指没有另给一套失败通知的内容，不能据它补写。〔§10.2.4.2 步骤 5、6、15–18，页 99–100〕

若 A、B 本就属于同一系统，见[同系统临时重组](single-system-temporary-regroup.md)；若 T 已存在、现在要将它拆除，见[临时组拆除](temporary-regroup-teardown.md)。这里解释 Stage 2 的组建过程，不据此指定协议编码或认定某次跨系统部署已经互通。
