# 跨系统临时重组：伙伴接受了请求，主系统就拿到了用户名单吗？

不一定。主系统想把自己的 A 组和伙伴系统的 B 组编成临时组 T。伙伴要回答的是“是否接受，涉及我管理的哪些**组**”。列出 B 的组 ID，不等于列出 B 中的人；主侧也不需要靠一份伙伴用户名单逐个通知 B 的成员。

## 两侧分别查什么？

这里的 A、B 配置了相同的 MC 业务；主侧已获授权用户的组管理客户端已经取到两组配置。它向管理 A 的组管理服务器（GMS1）请求重组，列出 A 和 B 的组 ID，指明是否广播重组，也可提出安全级别和优先级。GMS1 按组策略核实**发起人**是否有权操作，并查 **A 自身**是不是临时组。如果 A 已是临时组，就拒绝，不继续转发。否则，在授权检查通过后，GMS1 把属于伙伴服务器 GMS2 的组成组 ID 列表转给它。GMS2 查的是自己管理的 B：如果 B 已是临时组，同样拒绝。〔§10.2.4.2 前提及步骤 1–4，印刷页 98–99；表 10.2.2.12-1，页 89〕

A、B 都是普通组，并不保证可以重组。已经编入另一个临时组的组成组不能再用；系统策略**不允许**纳入处于紧急状态的组时，任一组成组处于紧急状态也会阻止重组。还须满足 §10.2.4.4 对系统策略和业务服务器控制角色的要求。该条区分“临时组可包含外系统的组”和“不可包含外系统的组，但组的成员分布在不同系统”，不能拿后一种情形来放行外系统的组成组。〔§10.2.4.4，页 101〕

## 临时组 T 可以由哪台 MC 业务服务器控制？

先问**哪个系统拥有组成组**，再看**成员由哪个系统服务**。比如 B 属于伙伴系统，哪怕 B 的成员目前都在主系统接受服务，B 仍是外系统组。反过来，A、B 都属于主系统，即使有人在伙伴系统接受服务，A、B 仍是本系统的组。只知道其中一人在伙伴系统接受服务，还不知道其余成员由谁服务，不能断定成员已分布在多个系统。若另有成员在主系统接受服务，才能据这两地的记录确认成员跨系统。下列规则判断的是某台 MC 业务服务器 S 能否承担 T 的控制角色，不是 GMS 怎么选举 S，也不是给某位成员分配话权。临时组、已经编入另一临时组的组，以及策略不准纳入的紧急状态组，在两种策略下都不能重组。这里共用的是组资格禁项，不是 §10.2.4.2 所举的 GMS 检查、拒绝步骤或消息。〔§10.2.4.4 第一组规则，印刷页 101〕

**策略允许纳入外系统组，组成组来自多个系统。** S 若已控制所有组成组，可以控制 T；若只控制其中一个，也满足“至少一个”的条件，不要求全部原控制服务器同属一个系统。若只是策略允许、本次所有组成组实际属于同一系统，不能用这一分支。条款还给了第三种可能，即使 S 原先一个组成组也不控制，也要同时核对两件事：

- S 与至少一个组成组满足原文的关系：S 是 “an MC service server homed by at least one of the MC service groups”。不要把这写反成“S 托管一个组”，也不能用某位成员已归属该组、S 与那位成员在同一系统来代替。
- 原文所说的 “the MC system of any involved MC service group” 允许把**整组重组所涉及的话权控制**交给 T 的控制服务器 S。只允许 S 处理一个组成组的话权，不等于允许它接手整套组。该条没有规定系统间如何投票或交换同意消息。

这两个条件合起来才是第三条；它们不是前两条的附加条件。三条中有一条适用即可，可以重合：控制全部当然也算控制了至少一个。S 未控制任何组成组时，只能用第三条证明它有资格。缺一项证据就还不能确认；若确认其中一项不成立，S 就不符合这条。〔§10.2.4.4 第二组规则，印刷页 101〕

**策略不允许纳入外系统组，组成组的成员分布在多个系统。** 先排除外系统组。对符合该策略的本系统组成组，若 S 已控制所有组成组，它可以控制 T。若 S 只控制其中一部分，则它必须至少控制一个，而且**所有组成组各自的控制服务器都须位于同一个 MC 系统**；是同一个系统，不必是同一台服务器。若 S 一个都不控制，或只控制部分且其余控制服务器分处不同系统，就不能按此分支让 S 控制 T。上一分支的 “homed by” 和话权控制移交不能在这里补救。成员是否已归属某组、成员在哪里接受服务，都不能代替对控制服务器所在系统的核对。〔§10.2.4.4 第三组规则，印刷页 101〕

符合某一条，只说明 S 满足相应的控制角色条件，不证明实际选定了 S 或已经创建了 T。伙伴 GMS 回复“接受”并列出组成组 ID，也不能指出哪台 MC 业务服务器担任 T 的控制角色。〔§10.2.2.13 表 -1，印刷页 90；§10.2.4.2 步骤 5–6，页 99；§10.2.4.4，页 101〕

## 伙伴回复的是组 ID，还是用户 ID？

步骤 5，GMS2 向 GMS1 回复。表 10.2.2.13-1 列了两项必选信息：伙伴侧接受或拒绝的**结果**，以及伙伴侧的**组成组 ID 列表**。表中没有必传的用户 ID 名单。即便结果是接受，这也只是伙伴对请求的答复，还不是主侧建好 T 或发起客户端收到结果的凭据。〔§10.2.4.2 步骤 5–6、17，页 99–100；表 10.2.2.13-1，页 90〕

用户信息共享的安全事项由双方服务提供商的协议约束。条款举的情形是伙伴不向主侧提供所管理组的用户信息。步骤 5 后的注另说，两家服务提供商有信任关系时，伙伴**可以在这一步**向主侧共享用户信息，但没有要求它一定共享，更没有规定必须交出完整名册。即使这一次共享过，后来 B 加人或减人，针对 T 怎样与主系统同步，仍不在本规范范围内；不能从 B 的变更推定主侧名册已经更新。〔§10.2.4.2 前提 1、步骤 5 及其后注，页 98–99〕

## 接受和拒绝之后能断言什么？

**接受且其余条件满足时**，步骤 6 由 GMS1 创建并保存 T 的信息，包括临时组 ID、组成组标识、离网信息、优先级、安全级别及广播属性。若发起人既未指定安全级别又未指定优先级，取组成组中较低的安全级别和较高的优先级。GMS1 随后通知 GMS2；GMS2 确认，并保存 T 与组成组的标识、优先级和安全级别。〔§10.2.4.2 步骤 6–8，页 99〕

### 同叫“通知”，要先看发给谁

步骤 7–8 是两台 GMS 之间的往返。此后，GMS2 联系伙伴侧业务服务器和 B 中已归属的成员，GMS1 联系主侧业务服务器和 A 中已归属的成员。已归属成员通过各自的组管理客户端向本侧 GMS 回执，不是向主侧交一份跨系统人员名册。下表中 M 为必选，O 为可选。

| 方向（成功流程的步骤） | 消息及字段 |
| --- | --- |
| GMS → 本侧 MC 业务服务器（9、13） | 表 10.2.2.8-1 的 **Group regroup notify**：组成组 ID 列表、T 的组 ID 均为 M；启用的 MC 业务列表、广播指示均为 O。该表没有优先级或安全级别。步骤 10、14 是业务服务器确认，不能把成员回执的字段套给它。 |
| GMS1 → GMS2（7），或本侧 GMS → 已归属成员的组管理客户端（11、15） | 表 10.2.2.14-1 的 **Group regroup notification**：组成组 ID 列表、T 的组 ID 均为 M；优先级、安全级别、广播指示均为 O。 |
| GMS2 → GMS1（8），或已归属成员的组管理客户端 → 本侧 GMS（12、16） | 表 10.2.2.15-1 的 **Group regroup notification response**：组成组 ID 列表、T 的组 ID、优先级、安全级别均为 M；广播指示为 O。 |

即使方向同为 GMS2 → GMS1，步骤 8 确认的是刚收到的**建组通知**，步骤 5 回答的却是是否接受**重组请求**。步骤 17 才是 GMS1 向发起客户端回复；步骤 18 是已归属成员各自请求临时组配置。〔§10.2.2.8 的方向与表 -1，页 88–89；表 10.2.2.13-1、10.2.2.14-1、10.2.2.15-1，页 90；§10.2.4.2 步骤 5、7–18，页 99–100〕

在 §10.2.4.2 的跨系统组建流程中，**违反重组规则时**，步骤 5 明写应给否定响应，并跳到**步骤 15**。该版步骤 15 的正文是 GMS1 通知主侧已归属成员，并非向发起客户端回复（那是步骤 17）。保留这个回指：不能把 15 改成 17，也不能把成功路径中步骤 6 的建组、两侧存储和临时组配置获取当作拒绝后的既成事实。该回指没有另给一套失败通知的内容，不能据它补写。若策略禁纳外系统组，组成组都是本系统组，成员分布在多个系统是这一分支的适用前提，不是拒绝理由。若一个组成组本身是临时组，这些组不能按该方案重组。若组成组通过了资格检查，已核实 S 一个组成组也不控制，其他服务器的控制关系还没查，能排除的是 S；其他服务器能否控制 T，要按它们各自的控制关系及本分支条件另判。§10.2.4.4 没有给这一分支指定哪台 GMS 发拒绝响应或随后转到哪一步，不能套用 §10.2.4.2 的步骤 5、15。〔§10.2.4.4 第三组及共同规则，印刷页 101；§10.2.4.2 步骤 5、6、15–18，印刷页 99–100〕

若组成组以及组管理客户端、组管理服务器、MC 业务服务器和组成员都属于同一 MC 系统，见[同系统临时重组](single-system-temporary-regroup.md)；若 T 已按 §10.2.4.2 建成、现在要将它拆除，见[临时组拆除](temporary-regroup-teardown.md)。前一转读条件见 §10.2.4.1 前提 1（印刷页 96）；后一转读条件见 §10.2.4.3 前提 4（印刷页 100）。仅知 T 存在而不知如何形成，不能把后一页的整套拆除流程当作已适用。这里解释 Stage 2 的组建过程，不据此指定协议编码或认定某次跨系统部署已经互通。
