# MCPTT 服务器删掉组文档缓存后，为什么在建呼前重新订阅？

Rel-16、Stage 3。本文只看在网组呼涉及的 MCPTT 服务器及其访问的组管理服务器（GMS）。重订阅、订阅获应答、服务器已有文档和呼叫通过是不同的事件。先确认日志对应哪台服务器、哪个组标识。

## 缓存被移除，与收到 INVITE 是两个入口

MCPTT 服务器可以缓存组文档，也可以订阅文档变化。服务器先前缓存的某一组的数据被移除时，服务器会为同一 MCPTT 组 ID 或临时组标识（TGI）重新订阅其组信息变化。这个动作可以早于携带该标识的 INVITE，不要求先有组呼。判断是否走到这个入口，要找本服务器对该标识的缓存移除记录及随后发出的订阅；只查不到缓存，不足以证明曾经有缓存又被移除。

如果服务器实际收到一份需要组文档的 INVITE，则按另一个入口检查：用 `application/vnd.3gpp.mcptt-info+xml` 中 `mcptt-request-uri` 的组标识查本服务器是否已订阅该文档。尚未订阅时，服务器须订阅该文档的 `xcap-diff` 事件包。这里的守卫是尚未订阅，不能用缓存状态替换。已经订阅也不能证明本机有文档。

依据：[TS 24.379 V16.14.0 §6.3.5.1，印 130，含注 2](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=131)；[§6.3.5.2(1)，印 131](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=132)。

## 已订阅或收到成功应答，怎样确认文档可用？

对同一份 INVITE，§6.3.5.2(4) 给出两个文档可用的入口：服务器实际收到来自 GMS、且含所需组文档的通知；或对应组文档已在本服务器的缓存中。先把组标识对齐。只有发出订阅、收到 SUBSCRIBE 的成功应答、订阅对话仍在，或看到一条不知内容的通知，都不能替代这两项证据，也不能证明缓存被补写。反过来，这份调用抓包中没见文档通知，不排除本机已经缓存了相符文档；这不是“允许使用任何陈旧版本”的规则。要确认缓存已变更，核对本机相应组条目的变更记录，这两条不规定缓存写入、刷新或淘汰算法。

文档可用后，**非控制功能（NCF）退出这一条组文档处理程序**。它不在这条程序里接着做控制功能（CF）的组类型和成员检查；不能把任何参与功能（PF）直接当成 NCF。CF 则先识别组文档对应的组类型；如果 INVITE 确是发给控制功能、且指向未重组的 MCPTT 组 ID，再走 §6.3.5.2(5) 的组级检查（如组停用、成员名单）。退出这条程序或已取得文档，都不能证明某一呼叫腿返回成功、整场已接受、成员已接到呼叫或有媒体。

对 INVITE 中实际发起的文档订阅，看到匹配的失败响应才进入相应失败分支；缺一份文档或抓包中没见通知，不等于收到订阅失败。普通按需聊天组的订阅应答与后续组级拒绝继续看[聊天组建呼](../calls/chat-establish-join.md)；预安排组呼的后续准入见[预安排组呼服务器准入](../calls/prearranged-server-admission-routing.md)。[终端收到组配置通知](client-group-configuration.md)是不同的流程，不是本服务器文档缓存的证据。

依据：[TS 24.379 V16.14.0 §6.3.5.2(2)–(5)，印 131–132](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=132)。本文不展开 TGI 的后续建呼处理、其他系统之间的路由或被引用规范中的订阅实现。
