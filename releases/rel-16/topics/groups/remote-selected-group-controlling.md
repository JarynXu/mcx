# MCPTT 远程换组：目标尚未归属，控制功能该拒绝还是转送？

甲请求把乙的所选组改为 G。控制 MCPTT 功能不会替乙换组。若乙尚未归属 G，关键在于乙**能否归属**：有资格就转送请求并要求先归属；无资格才因这一原因拒绝。以下限于在网 MCPTT，3GPP TS 24.379 V16.14.0（Release 16，Stage 3）§10.1.4.4。

## 先分清：这条 MESSAGE 是要换组，还是在报告结果？

两者在 SIP 层都是 MESSAGE **请求**。一种提出选组变更；另一种是返回业务结果的新 MESSAGE，不是给前一条 MESSAGE 的 SIP 状态响应。控制功能对这两种消息都先做以下处理：

- 若资源不足以处理，或存在拥塞风险，可以用 SIP 500 拒绝，也可以在这个 500 中附上 Retry-After；两者都不是必须。
- 若继续处理，而收到的 Accept-Contact 中没有值为 `urn:urn-7:3gpp-service.ims.icsi.mcptt` 的 `g.3gpp.icsi-ref` 标签，必须回 SIP 403 并停止。这条检查并未判断乙能否归属。

依据：§10.1.4.4 开头及步骤 1–2，印刷页 311 末至 312。

## 只有变更请求才查乙对 G 的归属

当业务正文的 `request-type` 为 `group-selection-change-request` 时，控制功能用收到的资源列表中的 MCPTT ID 识别乙，用 MCPTT 业务正文的 `mcptt-request-uri` 识别 G，按 §6.3.6 判断乙对 G 的归属。在前面的检查已通过时：

| 乙对 G 的情况 | 控制功能怎样处理这条变更请求 |
| --- | --- |
| 已归属 | 继续转送。步骤 3 不要求再查归属资格，步骤 8 不要求加上先归属指示。 |
| 未归属，但按 §9.2.2.3.8 判断有资格 | 继续转送，必须在出站业务正文的 `anyExt` 中加入 `affiliation-required=true`，要求目标客户端先归属。指示本身不使乙成为已归属用户。 |
| 未归属，且判定无资格 | 必须回 SIP 403，在 Warning 中写入 `120 user is not affiliated to this group`，不再转送。 |

同样是 403，缺服务标签与无归属资格是不同原因，不能只看状态码就认定乙无资格。若收到的是报告结果的 MESSAGE，上述资格检查和加指示的步骤不适用；仍按两类消息共有的规则处理。不能把“不要求加 true”读成“必须写 false”。

依据：§10.1.4.4 步骤 2、3(a)、8(a)，印刷页 312。

## 转送时，组、用户和下一跳写在哪里？

两类消息只要走到转送这一步，控制功能就生成新的 SIP MESSAGE。先复制收到的 MCPTT 业务正文，再明确设置两个元素：

| 入站信息 | 出站位置 |
| --- | --- |
| 业务正文 `mcptt-request-uri` 里的组标识 | 写进业务正文的 `mcptt-calling-group-id`。 |
| `application/resource-lists` 正文里本条消息的目标用户 MCPTT ID | 写进业务正文的 `mcptt-request-uri`。 |

所以，发往乙的变更请求，出站业务正文分别写 G 和乙；**SIP 请求行的 Request-URI** 却写服务本条消息目标用户的终接参与 MCPTT 功能的公共服务标识，不是 G 或乙的 MCPTT ID。返回业务结果时仍按这条 MESSAGE 的资源列表识别收件人，不能固定填乙。本版不规定控制功能如何找到终接参与功能的地址。

出站 Accept-Contact 中既要有 `g.3gpp.mcptt`，也要有带上述 MCPTT 服务值的 `g.3gpp.icsi-ref`；两项都配 `require` 和 `explicit`。P-Asserted-Service 使用同一服务值；P-Asserted-Identity 复制入站同名字段中呼叫用户的公共用户标识。控制功能按 TS 24.229 发送。这里不反推发起参与功能先前如何解释它收到的标识。

依据：§10.1.4.4 步骤 4–7、9–12 及步骤 9 后的注，印刷页 312–313。

## 控制功能回 200，能登记“乙已换组”吗？

不能。收到下游对出站 MESSAGE 的 SIP 2xx，控制功能必须**生成** SIP 200 (OK) 回给本次事务的发起参与 MCPTT 功能；收到 4xx、5xx 或 6xx 则把该错误响应转给同一上游。200 是这一跳对 MESSAGE 的事务响应，不是乙报告的换组结果。只有这个 200 而未见业务结果，既不能断言乙已选中 G，也不能断言换组失败。

依据：§10.1.4.4 步骤 12 后的两段，印刷页 313。若要判断乙是否真的换组，或查询甲能否发起变更，见[远程选组变更的两个客户端](remote-selected-group-client.md)。

[固定版本原文：3GPP TS 24.379 V16.14.0，§10.1.4.4](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=313)

要区分发起侧的 403/155、两端不同的绑定 404，或核对每一跳的 SIP 响应，读[远程换组的参与功能](remote-selected-group-participating.md)。
