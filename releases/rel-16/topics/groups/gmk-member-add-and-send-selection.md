# 新成员何时拿到 GMK？同组有两把已激活的 GMK，发媒体用哪把？

用户配置档已把甲加进一组，不能据此认定甲的终端拿到了组主密钥（GMK）。要查**何时提供组记录和 GMK**，看甲走哪种归属、是否满足组管理的条件。要查**发组媒体用哪把 GMK**，看这台发送端与该组关联的密钥哪些已激活。两个判断各有依据。[TS 33.180 V16.13.0，Release 16，§§5.7.1、5.7.3，印刷页 60–62](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=61)

## 新成员何时拿到组记录和 GMK？

配置管理服务器（CMS）通过用户已订阅的配置档更新通知成员资格变化，更新标出受影响的组 ID。这和组管理服务器（GMS）的**组配置更新订阅**不是一件事，只看到入组更新，不代表终端已经收到组记录或 GMK。[§5.7.3 开头，印刷页 61](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=62)

| 同样是加入新组或已有组 | 提供组记录和 GMK 前的条件 |
| --- | --- |
| 甲走**隐式归属** | 甲自动订阅来自 GMS 的组配置更新，仍须取得面向 GMS 的组管理服务授权。获授权后，GMS 向甲的终端发组管理记录和 GMK。 |
| 甲**须显式归属** | 甲先取得面向 GMS 的组管理服务授权，再向 GMS 订阅该组的更新。这份订阅还须通过验证。授权和订阅条件满足后，GMS 发组管理记录和 GMK。 |

只见显式分支的授权成功，仍不能认定订阅已验证；找不到验证记录，也不能断定验证没发生。**GMS 已发不等于终端实收。** 两支都允许用户在收到组更新和 GMK 后参加相应组通信。这不是已加入某次呼叫、已获话权或已用这把密钥发媒体的证明。这里的组管理授权也不是 [KMS 的身份密钥供应](../security/kms-provisioning.md)，或 MC 业务服务器的业务授权。[§5.7.3 印刷页 62 的前两段](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=63)

## 发组媒体时，按哪个时间选钥？

同一组 ID 可以关联多把已激活的 GMK。**MC 终端为该组加密媒体时，须用已激活的 GMK 中 Activation Time 最近的一把。** 例如甲已收到 B，B 的激活时间晚于正在使用的 A；若 B 的激活时间尚未到，不能因 B 刚收到就选它。若两把在发送时都已激活，按这个比较选 B。[§5.7.1 的多把已激活 GMK 段，印刷页 60](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=61)

**Activation Time** 指可开始用于发送的 UTC 时间。字段值为 `0` 时，取收到的 MIKEY `I_MESSAGE` **所带的时间戳**，不是终端收到消息的时刻。**Expiry Time** 指到时不得再使用该密钥的 UTC 时间；这个字段为 `0` 才表示不设到期。未到期不等于已激活。若最新的激活时间并列，或没有已激活的候选，本页所引条款没有给出补选规则。[附录 E.6.4、E.6.10，印刷页 168](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=169)

不要用到达顺序、GMK-ID 大小替代激活时间。这条选择规则只回答**发送端怎样加密组媒体**，不规定收端怎样选历史密钥、较早的钥何时删除，也不证明某个包已经用哪把钥加密。若要查 [GMS 标记撤销后能否再用](gmk-security-context-revocation.md)，或 [CMS 移出成员后何时删除 GMK](removed-member-gmk.md)，各用对应条件。若只查 [GMS 向业务服务器和成员发什么名单变动通知](group-membership-notification.md)，查 Stage 2 业务流程，别把那份通知当这里的 CMS 更新。
