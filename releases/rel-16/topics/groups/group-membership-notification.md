# 组成员名单变了，业务服务器和成员各收到什么？

这里的组管理服务器（GMS）和 MC 业务服务器服务于同一个 MC 系统。以甲、乙同时被加入同一组为例：MC 业务服务器需要知道这次加了谁；甲的组管理客户端需要知道自己被加入了哪个组。两种接收方收到的都是成员变动通知，但标准为它们列出的信息不同。

| GMS 通知谁 | 通知里的必选信息 | 加入甲、乙时的含义 |
| --- | --- | --- |
| MC 业务服务器 | 组 ID、受影响的业务用户 ID 列表、增删操作 | 哪个组增加了甲和乙。列表指本次变动涉及的用户，不是全组名册。 |
| 被加入或移出的用户的组管理客户端 | 组 ID、增删操作 | 甲获知自己被加入该组，乙也获知自己的变动。客户端表没有列出受影响用户 ID 列表。 |

两张表适用于加入和移出，所列各项的状态都是 M（必选）。客户端表没列用户名单，不是说该名单在这里属于可选项。〔§10.2.2.20，表 10.2.2.20-1、-2，印刷页 91–92；§10.2.6.1，图 10.2.6.1-1，印刷页 102–103〕

**收到通知后。** 在一般成员变动过程中，被加入者的组管理客户端向 GMS 请求相关组配置；移出成员时，终端可以删除本地保存的该组配置。移出成员并没有删除组本身。〔§10.2.6.1 步骤 3–4；§10.1.5.2，印刷页 78–79〕

若是 CMS 用户配置档显示新增成员，要核对 GMS 何时提供 GMK；或要核同一组有多把已激活密钥时发组媒体选哪把，读 [新增成员与 GMK 的发送选择](gmk-member-add-and-send-selection.md)。名单通知和组配置获取不能证明终端已收到密钥。

若要判断移出成员后终端是否须删除组主密钥，见[成员移出后的 GMK 处理](removed-member-gmk.md)。本地组配置清理不能证明密钥已删除。

**谁得到操作结果？** 管理员、调度员或其他获授权用户发起更新前，已了解当前名册和拟增删用户的身份。发起者的组管理客户端提交三项必选信息：组 ID、受影响用户的业务 ID 列表、增删操作。GMS 处理请求时可以检查成员总数上限 Nc6。〔表 10.2.2.18-1，印刷页 91；§10.2.6.2，印刷页 103–104〕

在图 10.2.6.2-1 所示的名单实际改变的流程中，GMS 先更新名单，再通知业务服务器和受影响的成员，最后向发起者的组管理客户端返回结果。这个响应有两项必选信息：组 ID、操作结果（成功或失败）。它不是成员通知。如果发起者收到失败结果，不能据此认定名单已改变，也不能认定 GMS 已发出变动通知，或业务服务器、成员已收到通知。〔表 10.2.2.19-1，印刷页 91；图 10.2.6.2-1，印刷页 104〕

**这能证明甲已经参加当前的组呼吗？** 不能。成员资格回答“甲是否在名册上”；组归属（affiliation）回答“甲是否对该组的某项业务建立了归属”。先有成员资格，才可能成为已归属成员；归属可由客户端显式表达，也可由业务服务器按配置和策略隐式建立。至于甲是否参加了一次具体的组呼，得看那次呼叫的参与情况。成员通知本身甚至不表明此时有组呼正在进行。〔§5.2.5 及注 1，印刷页 19–20；表 10.1.5.5.1-1，印刷页 80〕
