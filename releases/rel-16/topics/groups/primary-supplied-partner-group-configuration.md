# 伙伴没来索取，主系统也能把组配置发过去吗？

可以。组 G 定义在甲系统，至少一名 G 组成员定义在伙伴系统乙。若甲已配置乙的组管理服务器（GMS）的寻址信息，并获准向乙提供组配置，甲的 GMS 就可以主动把 G 的配置发给乙的 GMS。例如，管理员的操作可能触发这次提供；不要求乙先来索取或订阅。这里的组 ID 标识 G，不是组员身份。〔§10.2.7.2 引言、四项前提及步骤 1，印刷页 105；表 10.2.2.24-1，页 92〕

**哪一端发“请求”？** 这条请求叫“提供组信息请求”，由甲发给乙，必带组 ID 和该组的配置信息。甲寻址乙的 GMS 时可以用代理地址，由乙内部路由选出实际接收的 GMS。若是乙向甲询问“请给我 G 的配置”，方向就反了，应查[伙伴主动取得配置、订阅及接收变更通知](partner-group-configuration.md)。〔表 10.2.2.24-1，页 92；§10.2.7.2 注 1、步骤 1，页 105〕

**乙保存哪一份？** 乙的 GMS 根据乙的策略和本地配置信息调整收到的配置，再保存调整后的版本。乙还**可以**通知乙的 MC 业务服务器；这一步的接收方不是组员终端，也不是甲的 GMS。不能因为没有看到乙通知业务服务器，就断定乙没有保存。〔§10.2.7.2 步骤 2–4，页 105–106〕

**甲拿到乙的回执，能确认到哪里？** 乙的 GMS 给甲的 GMS 回送组 ID 和结果，两项都必带。表中的结果表示乙对这次配置的接收、修改和保存成功或失败；它不是逐步回执。流程步骤 5 描述的是成功情形：乙告诉甲配置已正确接收并存储。若结果为失败，不能反过来认定配置已存好，也不能凭一个失败结果断定具体哪一步出了问题。〔表 10.2.2.25-1，页 93；§10.2.7.2 步骤 2–5，页 105–106〕

乙的 GMS 负责向**由乙提供服务的 G 组成员**提供配置，这项职责不是已经交付的证明。即使系统间回执成功，也不能据此认定某个终端已收到或保存配置，更不能认定组员已加入一次组呼。若要判断某个终端是否已保存，应另查[终端如何获取和保存组配置](client-group-configuration.md)。〔§10.2.7.2 注 2 及步骤 5，页 105–106〕
