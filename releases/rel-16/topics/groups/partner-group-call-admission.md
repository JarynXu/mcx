# 组在甲、组员在乙：同一次跨系统组呼，谁决定请求能不能往下送？

排查这通呼叫，先看记录出自哪一段。**网关找到目标组的主业务服务器，是找到了转送地址，不是准许起呼。** 两侧都隐藏拓扑时，§10.14.2 说明请求经谁转给组主服务器，由谁检查来源。若组主已提供组配置、伙伴对其采用本地设置，§10.14.3 另讲伙伴在两个方向怎样逐通放行；这两幅本地配置图没有画网关。

## 伙伴按本地组配置放行：先看呼叫方向

组 G 的主系统是甲，客户端 C 正在乙接受 MC 业务。**C 起呼时，乙的业务服务器按本地组配置放行，才把请求送到甲；甲的组宿主还要独立检查来话来源。反过来，甲的组宿主把请求送到乙，乙的业务服务器仍要按本地组配置放行，才把请求送到 C。** 两个方向都由服务 C 的业务服务器执行乙的本地配置。乙的组管理服务器（GMS）保存过配置，不等于这通呼叫已经获准。[TS 23.280 V16.7.0，Rel-16 Stage 2，§10.14.3.1，印 207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=208)；[§10.14.3.2 步骤 1–4，印 208](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=209)；[§10.14.3.3 步骤 1–3，印 209](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=210)。

**先认清“伙伴”是谁的伙伴。** 甲、乙互联，甲已向乙提供 G 的组配置，乙对这份配置采用本地设置。C 已归属 G，由乙为它提供业务。乙是相对于 **G** 的伙伴系统，却可以是 **C 自己的主系统**，也可以是 C 成功迁入的系统；并不要求 C 一定迁移过。下文的“乙服务器”指为 C 服务、作为 G 的参与服务器的 MC 业务服务器，“甲宿主”指 G 在甲的宿主业务服务器。已归属是两种程序的前提，不是任一方向本次放行的结果。[§§10.14.3.1–2 前提与注，印 207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=208)；[§10.14.3.3 前提及注，印 208–209](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=209)。

## C 从乙呼叫 G：向甲转出，只过了第一道检查

C 向乙服务器发起组呼请求。乙服务器按 G 的本地配置核准**这次请求**；通过才转给甲宿主。甲宿主还要判断：对目标组 G，**主叫用户当前接受服务的系统**是不是允许的来话来源，**这名主叫用户**是不是允许的来话来源。只知道两系统已互联、或只知道乙是允许的系统，都不足以签认甲已准许这名用户来话。[§10.14.3.2 图 10.14.3.2-1、步骤 1–4，印 208](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=209)。

甲的检查通过后，甲宿主向乙服务器发组呼响应，乙服务器再向发起端 C 发响应。图中随后才建立话权控制或传输控制以及媒体路径。核对一通具体呼叫时，若最后一条记录是“乙已核准并向甲转发”，可记录乙已放行，不可代甲登记授权成功；若只看到甲给乙回了本流程步骤 5 的响应，也不要代 C 登记已收响应，更不要登记某个成员已经听见声音。[同节步骤 5–7，印 208](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=209)。

## 乙收到甲宿主的请求：到达乙，不等于到达 C

乙服务器收到甲宿主发来的组呼请求，按乙的本地组配置核准本次来话。**检查通过，乙才向 C 发送请求**；若已知没有通过，不能按这条成功路径继续转给 C。C 向乙服务器回组呼响应，乙服务器再向甲宿主回响应。最后才建立话权控制或传输控制以及媒体路径。这个方向没有再列一次“甲检查乙方主叫来源”的步骤；这里的 C 是被联系的组员，不是上一例中的主叫。[§10.14.3.3 图 10.14.3.3-1、步骤 1–6，印 209](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=210)。

例如，值班记录只写“乙收到甲的请求”，下一项应查**乙对该来话的授权结果**。没有这项记录不能断言乙已拒绝，也不能据此填“C 已响铃”。即使另有“乙向 C 发出请求”，也不能填“C 已回应”；再看到 C 的回应，才有 C 回应的证据，却仍不证明媒体路径已经建好或有人已听见。§10.14.3 的两幅图都省略拓扑隐藏，不说明现场有无网关。这里讲的是 MCPTT、MCVideo 业务程序共用的互联情形，这两幅图不给出 SIP 拒绝码、网关路由或媒体实测结果，也不用于判定私呼或 MCData 文件分发。[§10.14.1，印 205](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=206)；[§10.14.3.2 注 1，印 207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=208)；[§10.14.3.3 引言，印 208](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=209)。

## 两侧都隐藏拓扑：网关找谁，谁准许对 G 起呼？

沿用甲、乙，取一个能直接对照图 10.14.2.2-1 的例子：**C 在自己的主系统乙接受业务，目标组 G 的主系统是甲**。两系统互联，双方都用 MC 网关隐藏内部拓扑；C 已归属 G。目标是组，不是组内某个人。原文要求起呼端当前服务系统与 G 的主系统不同，允许起呼端由自己的主系统服务，也允许它成功迁入伙伴系统。图及步骤 2–4 称“服务系统”，步骤 5、12–13 的文字又称起呼端的“主系统”。本例乙兼有两种身份；若两者不同，不能照搬下面的每一跳，也不能据图断定必须经过或绕开发起用户自己的主系统。[§§10.14.2.1–2、前提及注 1–2，印 205](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=206)；[§10.14.2.2 图 10.14.2.2-1、步骤 1–7 及注 3–4，印 206](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=207)；[§10.14.2.2 步骤 8–15 及注 5，印 207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=208)。

| 请求在谁手里 | 这一侧查什么、做什么 |
| --- | --- |
| 为 C 服务的乙业务服务器 | C 发起对 G 的组呼。服务器认出目标在另一系统，选**乙网关**作下一跳，并把请求交给它（1–3）。 |
| 乙网关 | 识别出**甲是 G 的主系统**；按本侧通往甲网关的信令面配置，把请求转到甲网关（4–5，注 3）。这一步不是选择甲的内部服务器。 |
| 甲网关 | 用**目标 G 的组 ID** 和甲网关的配置，选出 G 在甲的主业务服务器（6，注 4），再把本次请求转给它（7）。同属甲的 G、H 可以配置给不同主服务器；不是用某个成员的用户 ID 替 G 选宿主。 |

配置表中有映射，只说明能怎样选择；本次查得 G 对应哪台服务器，是步骤 6 的结果。要记“甲网关已经向它转发本次请求”，还得有这次转送的证据。网关已转出，不等于主服务器已收到、已授权，更不是成员收到请求。[§10.14.2.2 图 10.14.2.2-1、步骤 1–7 及注 3–4，印 206](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=207)。

**主服务器核的是这次对 G 的来话来源。** 步骤 8 要核两项：**主叫用户当前接受服务的系统**是否可向 G 起呼，**这名主叫用户**是否可向 G 起呼。两项都要通过；不能凭选对宿主、网关已经转送、主叫已归属 G 或仅有系统许可，替用户填通过。若已确认步骤 8 失败，就不发生向图中客户端 2 发请求的步骤 9，也不发生它回响应的步骤 10。只是日志止于 7，还不能判已经失败。[§10.14.2.2 步骤 8–15 及注 5，印 207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=208)。

**目标端回应和主服务器往回发的响应，是两笔记录。** 授权通过时，图中主服务器向客户端 2 送请求（9），客户端 2 回主服务器（10）。按注 5，两步都在 8 之后、15 之前，9 必须先于 10，但 10 不必在 11 前完成。本例另一条响应链是：甲主服务器 → 甲网关 → 乙网关 → 为 C 服务的乙业务服务器 → C（11–14）。收到或发出其中一段响应，不代表其余各段已经完成。**呼叫响应成功**才进入步骤 15，建立控制与媒体路径（正文称话权控制，图中标为话权／传输控制）。图中一个目标端回应、甚至路径已建，都不是每位组员已获准、已回应或实际收到媒体的证据。本节不给出 SIP 报文字段、地址或失败码。[§10.14.2.2 图 10.14.2.2-1、步骤 1–7 及注 3–4，印 206](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=207)；[§10.14.2.2 步骤 8–15 及注 5，印 207](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=208)。

**如果记录里只有组配置回执：** 甲主动发配置、乙确认保存，查[主系统提供组配置](primary-supplied-partner-group-configuration.md)；乙主动获取或订阅变更，查[伙伴取得组配置](partner-group-configuration.md)。

**如果要追查此前那次归属操作，要看当时是谁申请、哪个系统定义了组。** 用户本人在自己的主系统，申请归属另一个系统定义的组，且无需拓扑隐藏，查[本人申请归属伙伴定义的组](partner-group-affiliation.md)。若是获授权的用户替别人变更归属，两人的客户端和主业务服务器同属一个主系统，组由它的伙伴定义，且请求为强制模式，才查这里的[远程变更伙伴组归属](remote-partner-group-affiliation.md)。

例如，两人都属甲，G 也由甲定义，其中一人曾替另一人协商改变对 G 的归属。这份记录要在组域索引查《远程改变他人的组归属：什么时候要问目标用户？》，该页区分主系统定义组的强制和协商模式。即使目标后来迁入乙，在乙接到 G 的来话，乙也只是为本次呼叫服务；这不会将先前的归属变更改判为“伙伴定义组的强制变更”。同样，归属操作的结果不是本次呼叫许可。

若问题已经具体到 MCPTT 普通按需预安排组的 SIP 邀请如何路由，查[预安排组呼服务器准入与路由](../calls/prearranged-server-admission-routing.md)；若要解释同一系统内 MCVideo 建呼成功是否代表所有必答成员确认，查[MCVideo 预安排组呼建立](../mcvideo/prearranged-group-call-setup.md)。
