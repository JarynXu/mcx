# MCPTT 与 IWF 预配置组重组：谁建立、谁拒绝、谁撤销？

**先对上本次事务。** 申请重组时，列出要合并的组成组、实际重组组 **D** 和提供配置的组 **P**。撤销已经形成的重组，目标是 **D**。若终端漏收更新后按 PTT，遭拒的是这次**建呼**，不是重组申请。形成重组发生在向 D 建呼之前，重组响应不能证明通话已建立。

本文只讲 3GPP TS 23.283 V16.8.0（Release 16，Stage 2）中 MCPTT 系统与连接 LMR 系统的互通功能（IWF）之间**按组清单**的预配置重组。相关组成组成员须事先得到所需配置。P 只提供配置，不是本次重组组；MCPTT 侧示例由获授权用户给出 D，IWF 拥有 D 时由 IWF 给出。若拟纳入的任一组成组已按 TS 23.280 或本版 §10.2.2 的组重组程序重组，本次申请须拒绝。§10.3.7.1 还引用 §10.2.2.5，不把动态 GMS 重组的创建流程套进来。[§10.3.7.1，印刷页 70](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=71)、[续，印刷页 71](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=72)。

## 跨 IWF 的消息怎样对上

| 消息 | 信息流表列出的必带项 |
| --- | --- |
| 重组请求 | 请求人的 MCPTT ID、D 的组 ID、P 的组 ID。组成组 ID 清单和用户 MCPTT ID 清单二选一，必须且只能带一个；本文用组成组清单。 |
| 重组响应 | 请求人的 MCPTT ID、D 的组 ID、本次重组的结果。 |
| 撤销请求／响应 | 撤销请求人的 MCPTT ID、D 的组 ID。响应还带本次**撤销**的结果。 |
| 重组拒绝 | D 的组 ID、拒绝原因。 |

这些是 MCPTT 服务器与 IWF 之间双向信息流的字段，不是终端报文格式。看到响应的消息名，不能把 Result 判成成功；申请的结果也不能替代撤销的结果。[表 10.3.2.14-1、10.3.2.15-1，印刷页 37](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=38)、[表 10.3.2.16-1 至 10.3.2.18-1，印刷页 38](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=39)。

## 建立重组：先看 D 由谁托管

**D 在 MCPTT 服务器，MCPTT 用户发起。** IWF 至少托管一个组成组，已预置 D 的身份和配置，并收到所需安全资料。MCPTT 侧组管理服务器（GMS）与 IWF 侧 GMS 分享相关配置和安全参数；MCPTT 系统不必知道由 IWF 服务的重组成员名单。前提还列出 IWF 对拟重组的组已有归属和／或拥有其中的组；MCPTT 服务器向 GMS 订阅组配置，GMS 向同系统的 MCPTT 服务器订阅组动态数据。两项订阅方向不同。[§10.3.7.2.1 前提，印刷页 71](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=72)。

获授权且在本系统接受 MCPTT 服务的用户**不必是所列组成组的成员，也不必已归属其中任一组**。服务器仍须检查发起权限，解析组成组标识，检查本侧所托管组成组中哪些成员已经归属，并找出清单中各组的伙伴宿主或 IWF。不知道 D 的配置时，可以向 GMS 取。服务器发跨 IWF 重组请求，IWF 回服务器，服务器再回发起客户端。注 3 只向已归属的组成组成员发重组请求，不能把这项限制当成发起人的资格。此例中，重组一旦形成就持续到显式撤销；IWF 的参与持续到它不再归属任何组成组。IWF 不再参与不等于 D 已撤销。[图 10.3.7.2.1-1、步骤 1–6、注 2–3 与末段，印刷页 72](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=73)。

**D 在 IWF，IWF 发起。** MCPTT 系统至少托管一个组成组。图示客户端是 MCPTT 系统定义的组成组 1 的已归属成员，预置 D 的身份和配置，且已收到所需安全资料。IWF 侧 GMS 把配置及安全参数给 MCPTT 侧 GMS，由后者按 TS 23.280 §10.2.7 向它所服务的用户分发；IWF 不必知道由 MCPTT 系统服务的重组成员名单。[§10.3.7.2.2 前提、图 10.3.7.2.2-1，印刷页 73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=74)。

收到 IWF 的申请后，MCPTT 服务器检查**自己托管的组**的状态，再找由它提供业务的**已归属成员**。成员所归属的组成组可以托管在任一侧。服务器向符合条件的客户端发重组请求，客户端通知用户。客户端可回重组响应；请求若用组播，客户端不回这份响应。随后看**服务器是否把该端归属到 D（步骤 6）**，以及**服务器是否另回 IWF（步骤 7）**。组播只省略客户端的回执，不省略这两个步骤。这个重组也持续到显式撤销；该客户端不再归属任何组成组时不再参与，关机或登出也可能使该端对 D 的归属停止。只观察到单个客户端离线、回执缺失或服务器回 IWF，不能据此判断 D 已撤销、某终端实际收到请求或所有端都已归属。[§10.3.7.2.2 步骤 1–7、注 2 与末段，印刷页 73–74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=74)、[步骤续，印刷页 74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=75)。

## 被拒的是重组申请：谁把原因回给谁

| 发起方 | 图示冲突及拒绝方向 |
| --- | --- |
| MCPTT 用户 | MCPTT 服务器核发起权限、解析并转申请；IWF 发现拟重组的组已参加另一重组时，向服务器发带理由的 IWF 重组拒绝。例中另一重组可在 IWF 内或 MCPTT 系统内。服务器再向发起客户端发带理由的拒绝。 |
| IWF | IWF 向 MCPTT 服务器发申请；服务器查自己托管的组，发现所列组已参加另一重组，向 IWF 直接回带理由的重组拒绝。这个失败示例没有向客户端发请求或等它答复的步骤。 |

[§10.3.7.4.1 开头和前提，印刷页 76](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=77)、[图 10.3.7.4.1-1、编号步骤及 §10.3.7.4.2 开头，印刷页 77](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=78)；[图 10.3.7.4.2-1 及编号步骤，印刷页 78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=79)。两节开头分别回指撤销的 §10.3.7.3.1、§10.3.7.3.2，但图和编号步骤处理的是**重组申请被拒**。保留原回指，不把这两图当成撤销失败规范。也不把已重组这一示例原因当成所有拒绝的原因，或从表里的理由字段推出 SIP 状态码、重试或回滚。

## 已形成的重组怎样撤销

- **原重组由 MCPTT 侧发起，IWF 已被重组到 D。** 客户端以 D 请求撤销，服务器检查该客户端的撤销权限，向 IWF 发撤销请求、收撤销响应，再回客户端。前提还列出 GMS 已向本系统 MCPTT 服务器订阅所指组动态数据。步骤 5 先写 IWF 发撤销响应，紧接着却用 group regroup response 称呼可被拒绝的响应。这里只保留图中的撤销往返和响应的撤销结果，不从这句异文补写独立拒绝路径，也不把任何回包都认作成功。[§10.3.7.3.1 前提，印刷页 74](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=75)、[图 10.3.7.3.1-1 与步骤 1–6，印刷页 75](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=76)。
- **原重组由 IWF 发起，客户端已被重组并在 MCPTT 系统接受服务。** IWF 用 D 发撤销请求；MCPTT 服务器转给客户端，客户端通知用户。步骤 4 是客户端给 MCPTT 服务器的可选回执。图中的虚线标作 Pre-configured regroup cancel response，正文写 pre-configured regroup remove response。两处都指向客户端给服务器的这一步，不据此认定两种写法是线上报文别名。收到组播撤销请求时不发这份回执。步骤 5 是服务器解除该客户端对 D 的归属；步骤 6 是服务器另向 IWF 发 IWF pre-configured regroup cancel response，不能拿来代替步骤 4。图 10.3.7.3.2-1 图题末尾写 MCPTT 系统，条款标题及步骤 1 写 IWF 发起；按明确的第 1 步识别方向。[§10.3.7.3.2 前提，印刷页 75](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=76)、[图 10.3.7.3.2-1 与步骤 1–6，印刷页 76](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/16.08.00_60/ts_123283v160800p.pdf#page=77)。

组播没有客户端回执，不等于撤销失败；看到一份响应，也不能代替对相应的解除归属和其他客户端实收的取证。两个流程都不说明如何拆除 D 内正在进行的呼叫、回收话权和媒体、或删除 P。成立例 §10.3.7.2.1 步骤 5 也把可能被拒绝的对象写作 group regroup response。重组申请被拒的图示另见 §10.3.7.4。

若实际是**漏收后按 PTT**，[按 A 或 D 的建呼拒绝](../calls/lmr-preconfigured-regroup-stale-ptt.md)要先核对 IWF 上的 D 是否仍生效。若由 **GMS 创建和保存临时组**，查[动态互通组重组](lmr-interworking-dynamic-regroup.md)。若查的是特定 SIP 消息，分别按 [Stage 3 的按组创建与补偿](preconfigured-group-regroup-creation.md)和 [Stage 3 的移除与响应](preconfigured-regroup-removal.md)的适用条件阅读，不把其中的 480 或 200 套回 IWF。已形成 D 后，实际建立符合条件的**非广播预安排互通组呼**才查[建呼](../calls/lmr-interworking-prearranged-group-setup.md)；由宿主结束**已经在呼的整场预安排互通组呼**才查[整场释放](../calls/lmr-interworking-group-release.md)。不在本页办理按用户清单的重组、广播呼叫或无线侧协议。
