# 本系统显式组归属：进区由谁发请求，GMS 先收到更新正常吗？

用户当前由目标组所在的 MC 系统提供业务，客户端一次申请归属 G、H 两组。**只看到 GMS 先收到 G 组的用户状态更新，不能判 H 组也归属成功，也不能判客户端已经收到答复。** TS 23.280 V16.7.0 为两条发送定义了不同的对象和内容，没有固定谁先发。这里看一项 MC 业务的 Stage 2 功能流程；不从这一章推定 SIP 方法、状态码或某项业务的全部前提。[§10.8.1、表 10.8.2.3-1，印 147](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=148)；[图 10.8.3.1-1、步骤 5 及注，印 151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=152)

## 没有手点，为什么仍是显式归属？

客户端须已获配允许归属的组资料或指向资料的指针。这套流程预设组管理服务器（GMS）已向定义该组的系统内的业务服务器订阅归属状态。业务服务器事先查过用户订阅和组策略、客户端事先申请过组配置更新，都是可能发生的准备，不是必经动作。客户端实际发起归属时，触发可以来自用户，也可以来自事件，例如终端进入允许的组工作区域。**入区触发客户端发出的归属请求仍属显式归属。** 只见位置变化，没有客户端触发并发起该流程的证据，不能据入区本身判定它已经请求归属或归属成功。本条也没有要求每次入区都发请求。[§10.8.3.1 前提 1–5，印 150–151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=151)

客户端向业务服务器申请归属一个或多个组。请求的必需内容是发起者的 MC 业务 ID 和一个或多个 MC 业务组 ID。组 ID 名单表达本次申请的对象，不是用户已有归属的组清单。要核对 MCPTT 中实际收到的区域 SIP 通知，则看[组地理区域通知](group-geographic-area-notification.md)：那条通知的 200 只确认收到了通知，不能替代这里的归属请求或结果。[表 10.8.2.1-1，印 147](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=148)；[§10.8.3.1 步骤 1，印 151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=152)

## 没看到服务器问 GMS 策略，能否判它漏掉授权？

不能先下这个结论。业务服务器先查本地是否已有组策略；**本地没有才向 GMS 请求取得策略。** 图 10.8.3.1-1 的 2a、2b 标的是订阅和通知，正文说请求和取得组策略；这不是本次客户端的归属答复，也不能由图给某个 SIP 请求定名。

无论策略来自已有缓存还是这次从 GMS 取得，业务服务器都要依据组策略和用户订阅，检查目标组是否启用、该客户端是否获准归属，以及用户可同时归属的组数上限 N2。N2 不等于本次请求列表的长度。用户获准时，保存该用户对请求所指组的归属状态。只见策略取得、没看到策略查询，或者只见 N2 尚有名额，都不能替本次作授权或保存的判断。本条未给出拒绝原因码、超限时挤掉哪个组或批量回滚算法。[图 10.8.3.1-1、步骤 2–4，印 151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=152)

## GMS 收到 G 的更新，客户端那条答复该核对什么？

- **5a 给发起客户端。** 业务服务器发的是发给该客户端的个别应答，承载可以是单播或多播。答复要有发起者 MC 业务 ID、所申请的组 ID 列表和列表中**每个组**的结果。要确认终端知道 G、H 各自怎样，核对它实收的这份答复，分别读 G 和 H 的结果。表的逐组结果不等于定义了批量操作的原子性。
- **5b 给已订阅的 GMS。** 查对应用户在对应组的动态状态。表 10.8.2.14-1 的必需字段是 **GMS 所订阅的一个组 ID、该用户的 MC 业务 ID、该组的归属或解除归属状态**。“归属或解除”是通用表的字段语义；本页的 5b 更新本次办理的归属，不把它当成解除程序。这是单个组的语义范围；表没有规定每个组必须用一份物理报文发送。若只见 G，不能把同一请求里的 H 当成已更新，也不能用它辨认究竟是哪台终端。

**5a 与 5b 可以任意先后，也可以并行。** GMS 先收到 G 的更新，不足以说客户端没获准，也不足以说客户端已收到确认。核对 5b 的组 ID、用户业务 ID 和状态，再按需要核对业务服务器的保存记录和 5a 的终端实收。保存、发出、收到了结果以及已经加入一场组呼，不是同一件事。[表 10.8.2.3-1，印 147](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=148)；[表 10.8.2.14-1，印 150](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=151)；[§10.8.3.1 步骤 4–5 及注，印 151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=152)

查 **GMS 的订阅是否成立、更新后名单能判到哪一层**，读[GMS 订阅组归属](gms-affiliation-subscription.md)。查**在网 MCPTT 用户对本客户端的组兴趣发布及状态确定**，读[显式组归属的协议过程](explicit-affiliation-client.md)。不要把这里的请求名单直接当作该协议的全量兴趣正文，也不要套用伙伴组的双系统审批。
