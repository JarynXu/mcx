# 归属、迁移和外部 KMS：客户端能连谁，证书从哪来？

**密钥管理客户端（KM 客户端）不连接外部 KMS。** 与伙伴安全域通信所需的外部 KMS 证书由归属 KMS 提供。知道外部 KMS 的 URI 或持有它的证书，不会改变连接规则。这里按 TS 33.180 V16.13.0（Release 16）的 KMS 角色规定判断，不按某次 HTTP 请求的路径判断。[§5.3.1.4，印刷页 55](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=56)

## 以哪个客户端为参照？

同一个 KM 客户端有且只有一个归属 KMS，可以有零个或多个迁移 KMS，也可以有零个或多个外部 KMS。这些角色以客户端为参照，不是服务器实例数量。MC 用户参与端到端通信安全需要归属 KMS 供应的密钥材料；设置或控制端到端通信的管理实体也需要供应密钥材料。这里的用户不限于终端，也可以是组管理服务器、MCX 服务器、信令代理或其他含 KM 客户端的实体。条文的注把这里的 MC KMS 与 TS 33.328 的 MIKEY-TICKET KMS 区分开。[§5.3.1.1，印刷页 53–54](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=54)

[图 5.3.1.1-1，印刷页 54](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=55)画的是外部 KMS 的证书带外送到归属 KMS，再由归属 KMS 向客户端提供。没有该证书，客户端不能与归属在该伙伴安全域的用户或组进行安全通信。证书是通信的前提，不是通信已经建立的证据。

## 归属 KMS 必须提供什么？

归属 KMS 是客户端信任的主安全域管理方，控制主域中客户端的媒体安全使用。客户端要取得归属在伙伴 MC 域的用户或组对应的 KMS 证书，也从自己的归属 KMS 取得。归属 KMS 须向 KM 客户端提供：

- 归属 KMS 自己的证书。
- 所供密钥材料的使用策略。
- 已认证用户身份的密钥材料。
- 允许使用的迁移 KMS 清单及各自地址。
- 允许使用的外部 KMS 清单及各自证书。

依据：[§5.3.1.2，印刷页 54](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=55)。

## 迁移 KMS 在什么条件下提供材料？

在用户是迁移 MC 域的获授权成员期间，迁移 KMS 控制其媒体安全。它可提供自己的证书；用户仍是该域成员时，它可提供已认证用户身份的密钥材料。迁移期间，归属 KMS 仍能提供归属证书和密钥材料，不因迁移而失去这个角色。

条文的注 2 说明一种可能：迁移 KMS 可以支持撤销由归属 KMS 签发的密钥材料，同时仍允许用迁移 KMS 供应的未受损材料通信。这个注没有规定撤销步骤，也不能用来判断某份材料已经被撤销。

依据：[§5.3.1.3 及注 1–2，印刷页 54–55](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=55)。

## 能向迁移 KMS 提供 KRR，为什么指定的上传仍只发归属 KMS？

§5.3.1.2 允许客户端向归属 KMS 提供收到的 KMS 重定向响应（KRR）；§5.3.1.3 也允许客户端向自己的迁移 KMS 提供 KRR。迁移这条许可没规定用哪条消息或哪种传输方式提供。[§5.3.1.2，印刷页 54](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=55)；[§5.3.1.3，印刷页 55](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=56)。

[§5.3.3 的 KRR upload](kms-provisioning.md)是一个指定请求，仍只能发给归属 KMS。不能用角色条文的许可给这个请求增加迁移目的地。若要查[谁生成 KRR、怎样选择可用的安全域](../identity/kms-redirect-response.md)，按跨域密钥交换的条款判断。收到或提供 KRR 本身不证明某个安全域已被接受。
