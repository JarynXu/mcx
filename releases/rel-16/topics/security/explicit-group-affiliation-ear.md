# 显式组归属及解除：业务服务器转交哪份 EAR？

**转交客户端原请求中的 EAR，不是用服务器自己的 EAR 代替。** EAR（Element for Authenticating Requests）是给接收方核对请求来源用的。这里限在网、同一 MC 系统的一项业务：所涉组定义在服务该客户端的系统内，客户端实际发起显式归属或解除，组管理服务器（GMS）已向该系统内的业务服务器订阅该组的归属状态。先核对实际办理的是哪一步，再查这一步的证据。

## 一笔事务，分别看三处

| 实际观察点 | 查哪份来源证据 |
| --- | --- |
| **客户端向业务服务器发原请求** | 归属或解除的第 1 步应附该客户端的 EAR。用户手动发起或事件触发客户端发出请求，都可以是显式流程；只有进区或出区记录不算请求。 |
| **业务服务器向已订阅的 GMS 发对应状态更新** | 业务服务器已收到本笔原请求里的客户端 EAR，办理这笔更新时应复制**同一份客户端 EAR**。归属是 5b；解除对应 4b。服务器可以另附一份用于认证自身的 EAR；它不是原客户端的 EAR。 |
| **GMS 实际收到本笔更新和对应客户端 EAR** | 收到的是核对本次变更授权所需的信息。服务器可以另附自己的 EAR，不必同时有两份。再查 GMS 的检查结果和对应用户在这一组的状态；不能从收件直接判授权通过或状态已写入。 |

TS 33.180 V16.13.0 §9.6.5.2.2 的开头说归属流程需要转交 EAR；描述第 1 步及复制动作时用的是 **should**，服务器另附自己的 EAR 用的是 **may**。最后一段把同一做法用于解除状态更新。没有证实原请求携带客户端 EAR，就不能认定后续复制了它。只看到服务器自己的 EAR，不能代证客户端来源。[§9.6.5.2.2 和图 9.6.5.2.2-1，印 111](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=112)；[续文和解除，印 112](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=113)。

## 客户端的答复不是 GMS 的状态更新

- **归属：** 客户端已获配该组资料或指针。业务服务器按组策略、用户订阅和同时可归属的组数上限 N2 检查，获准才保存相应归属状态。**5a 回发起客户端，5b 更新已订阅的 GMS。** 两步可以任一先做，也可并行。[TS 23.280 V16.7.0 §10.8.3.1 前提，印 150](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=151)、[步骤与并行注，印 151](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=152)。
- **解除：** 业务服务器已订阅组信息并保存所涉组资料。服务器按用户订阅和组策略确认该用户已经归属此组且获准解除，才移除所涉归属状态。**4a 回发起客户端，4b 更新已订阅的 GMS。** 两步也可以任一先做，或并行。伙伴系统、服务器主动解除和隐式归属不走本页入口。[TS 23.280 §10.8.4.2，印 155](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=156)、[步骤与并行注，印 156](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=157)。

查 5b 或 4b，按**GMS 所订阅的组 ID、用户在本项业务的 ID、该组的归属或解除状态**对齐。安全图中的 `MC service group ID(s)` 没有另定批处理或报文格式。比如只证实 GMS 收到用户甲对 G 组的更新及两份 EAR，不能替 H 组结案，也不能证明甲的客户端已收到 5a 或 4a。[TS 23.280 表 10.8.2.14-1，印 150](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=151)。

## 哪些记录不能代证本次处理？

业务服务器已**发出**更新，不等于 GMS **实收**；缺少收件记录也不能断定没有收到。接收方支持 EAR 处理时，§9.6.5.4 给出实收后的检查；不支持时，该节要求忽略 EAR。这不表示基础业务授权可以省略。对本次缺 EAR 或检查未通过的情形，这里不指定一律通过或拒绝、错误码及重试。通用 SIP EAR MIME 只标出这类正文，不确定两条业务信息流的 SIP 方法。普通 REGISTER 或 PUBLISH 的 200、业务授权令牌、MIKEY 和信令钥下载的 200，都不能代证这笔更新的来源认证或 GMS 的处理结果。[TS 33.180 §9.6.2.1，印 107](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=108)；[§9.6.5.2.1，印 111](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=112)；[§9.6.5.4，印 112](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=113)。

TS 33.180 图 5.1.3.1-1 的授权流程到 **C-5** 为止，没有 C-6。这里是另一条业务流程，不是收到 C-5 的配置就已归属。组资料或指针可静态或动态提供；本条不要求在每次显式归属前重做 C-5。[TS 33.180 图 5.1.3.1-1，印 32](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=33)、[C-5 与下一节，印 33](https://www.etsi.org/deliver/etsi_ts/133100_133199/133180/16.13.00_60/ts_133180v161300p.pdf#page=34)。

## 相邻问题

- 查在网同系统单项业务的客户端实际显式请求，业务服务器怎样核权、保存并回逐组结果，读[本系统显式组归属](../groups/same-system-explicit-affiliation.md)。
- 查在网同系统单项业务的客户端实际发起解除，业务服务器怎样核对原已归属、解除权限，分别答复和更新，读[客户端发起解除组归属的本系统分支](../groups/client-group-deaffiliation.md)。
- 查 GMS 向定义该组的系统内的业务服务器订阅状态，或实际收到针对该组的变化通知及回了什么，读[GMS 怎样跟踪组归属](../groups/gms-affiliation-subscription.md)。订阅成功和更新实收分开查；名单的业务 ID 不指明是哪台终端。
- 查主系统中已由 IdMS 认证的用户，终端能安全访问 CMS 并实际取同一业务的档，或终端实收该份档后由组管理客户端按其中成员信息向宿主 GMS 取配置，读[C-4、C-5 的范围和验证方](../identity/configuration-and-group-authorization.md)。既不是 5b/4b，也不规定额外的授权阶段。
