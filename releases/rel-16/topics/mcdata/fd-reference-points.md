# 在网 MCData 文件分发：FD-1 上发了链接，文件正文也发了吗？单播一定走 FD-2 吗？

**单凭链接不能认定正文已经发出；单凭“单播”也选不出 FD-1 还是 FD-2。** 例如，甲经 FD-1 发出了文件 X 的 URL，这条记录证明发出的是取件地址。它既不能证明 X 的正文已发，也不能证明正文一定没发：要判断这笔正文传送，得看有没有传文件数据的记录。

这里说的是 Release 16 **在网**文件分发（FD）的应用面架构。FD-1、FD-2、FD-3 都连接 **MCData 客户端的 FD 功能和 MCData 服务器的 FD 功能**。在网范围见 [TS 23.282 V16.8.0 §6.6.1 标题，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)；两端的功能见 [§§6.6.4.1.1–2 标题，印刷页 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34) 和 [§6.6.4.1.3 标题，印刷页 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35)。[在网模型图后的前三项，印刷页 30](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=31) 分别说明三个参考点的用途，不是一次分发的三个必经步骤，也不是接收端的签收记录。

**FD-1 上到底发了什么？** 它主要传建立文件分发会话的应用信令，也支持上下行单播事务。文件的大小和类型是元数据，URL 是文件地址，下载完成报告陈述的是下载结果，这些都不是文件正文。FD-1 还可以直接传小文件：看文件大小是否超过 **FD-1 自身的能力**，例如载荷或传输限制。不超过时可以用，不是必须用；刚好等于某项限制不算超过，但其他适用限制也须满足。本条没有给通用字节数，不能拿短数据业务（SDS）的配置上限来判文件。若 Y 的大小超出 FD-1 的能力，Y 的正文不符合这项许可。至于与 Y 有关的链接、建会信令或完成报告能否仍经 FD-1 发送，本条没有另作说明；仅凭 Y 超限也不知道实际发过什么、走的哪条路。若明确记录 FD-1 已单播发出 X 的小文件正文，可以确认这次发送，不代表对端已收齐。[§6.6.1 图后第 1 项：主次用途，印刷页 30](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=31)；[§6.6.4.1.1 首段及单播事务清单，印刷页 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)

**FD-1 上哪些信令必须用 SIP-1 和 SIP-2？** 在网客户端和服务器的 FD 功能之间，FD-1 **传送和路由 SIP 信令时**必须使用 SIP-1 和 SIP-2。这个要求针对 SIP 信令，不能据此把每一笔文件数据都标成 SIP。建会是 FD-1 的主要用途；具体到消息，条款说支持的消息还**可以包括**客户端向服务器提供的文件分发建会信令。这个方向不能写反，“可以包括”也不表示每笔事务都要发这条信令。即使看到它已发，也只能确认有建会信令发出，不能断定会话已经建立。见[§6.6.1 在网模型，印 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)、[§6.6.1 图后第 1–3 项，印 30](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=31)、[§6.6.4.1.1 标题、首段及末段，印 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)。

**只看到 conversation ID，能分清 FD-1 和 FD-2 吗？** 在网客户端与服务器的 FD 功能间，FD-1 和 FD-2 都支持用对话标识（conversation identifier）指明消息属于哪个消息串，也都支持 **MCData 用户和 MCData 应用的应用面身份**。FD-1 的清单说的是客户端经 MCData 服务器与其他客户端进行的上下行单播文件事务；FD-2 的清单说的是客户端与服务器之间的单播文件事务。仅凭这些标识，不能辨认这笔事务走的是 FD-1 还是 FD-2，也不能确认某端收齐文件；清单没有规定每份报文都必须携带全部标识。见[§6.6.1 在网模型，印 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)、[§6.6.4.1.1 标题、单播事务清单的引句及末两项，印 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)、[§6.6.4.1.2 标题、首段及功能清单末两项，印 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)。

| 要辨认的传送 | 路径和能下的结论 |
| --- | --- |
| **FD-2：单播文件数据** | 客户端的 FD 功能向服务器的 FD 功能发是上行；服务器的 FD 功能向客户端的 FD 功能发是下行。FD-2 支持两个方向。若只知道“两端单播了一份小文件”，没有标出实际路径，也没有排除 FD-1 的条件，不能断定走了 FD-2。[§§6.6.4.1.1–2：FD-1 的小文件条件与 FD-2 的单播用途，印刷页 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34) |
| **FD-3：下行组播文件数据** | 服务器的 FD 功能向客户端的 FD 功能发。客户端向服务器上行组播不符合这里的方向。仅知文件超出 FD-1 的能力，也推不出实际选了组播。[§6.6.4.1.1 的 FD-1 能力条件，印刷页 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)；[§6.6.4.1.3 的 FD-3 组播方向，印刷页 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35) |

**哪些底层参考点或接口承载文件？** 在网客户端与服务器的 FD 功能间，FD-2 的上下行单播文件事务使用 **SGi**，其定义指向 3GPP TS 23.002 [10]。服务器 FD 功能向客户端 FD 功能发下行组播文件数据时，FD-3 使用 **MB2-U**（3GPP TS 23.468 [8]）**或 xMB-U**（3GPP TS 26.348 [20]）。条文不要求同一次下行组播同时使用两者；只有一条 FD-3 发送记录，也不能定出用了哪一个。见[§6.6.1 在网模型，印 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)、[§6.6.1 图后第 1–3 项，印 30](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=31)、[§6.6.4.1.2 标题、首段及清单，印 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)、[§6.6.4.1.3 标题及正文，印 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35)。

FD-1、FD-2、FD-3 列在文件分发的**应用面**参考点之下。见 [§§6.6.4、6.6.4.1 两级标题和 FD-1、FD-2 的子标题，印 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)、[§6.6.4.1.3 FD-3 子标题，印 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35)。要查文件分发的**信令控制面**参考点，TS 23.282 V16.8.0 [§6.6.4.2 全段，印 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35) 指向 3GPP TS 23.280 [5] 的任务关键业务公共功能架构。本节给出查找定义的去处，并未在这里列出控制面参考点，因而不能把上述应用面两端直接当作控制面参考点的两端。上述规范号是本节的转引，不表示已经核过所引规范全文。

例如，服务器经 FD-3 组播发出了 X，随后有一份明确对应乙端和 X 的下载完成报告。前一条只证明服务器发出了文件数据，后一条才是乙端已报告 X 下载完成的依据，不能替丙端确认。报告经 FD-1 发送，也不表示文件正文走的是 FD-1。反过来，没看到丙端的完成报告，也不能据此判定它没收齐。[§6.6.1 图后文字第 1、3 项，印刷页 30](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=31)

若问**终端的媒体存储客户端向内容服务器上传或下载**，或**业务服务器为 MBMS 分发向内容服务器取此前上传的文件**，看[文件存储与消息存储的参考点](message-store-vs-file-storage.md)。若问在网组独立文件分发采用媒体面时谁答复接受、谁报告下载完成，看[组内逐人报告与汇总](group-media-plane-fd-reports.md)。若比较的是在网短数据载荷和为信令控制面 SDS 配置的最大载荷，看[短数据的三个参考点](sds-reference-points.md)。
