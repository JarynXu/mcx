# 在网 SDS：正文走哪个参考点，交付和已读回报该查哪一面？

**在网短数据的载荷恰好等于信令控制面 SDS 的配置载荷上限时，可以走信令面；仅凭大小不能认定已经走了这条路。** Release 16 的这项许可比较的是这笔 SDS 载荷和信令控制面 SDS 的最大载荷。如果配置记录还列出 SDS 业务允许的最大数据量，不要把它当成信令面的载荷上限。条款用的是“不超过”，并说此时“可以”使用 MCData-SDS-1。若只知道含信令开销的整条消息大小，不能拿它代替载荷比较；条款也没有给一个所有系统通用的字节数。[TS 23.282 V16.8.0 §6.5.4.1.1 第 2 段，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)

这与[同系统一对一独立 SDS 的两个传送示例](one-to-one-standalone-sds.md)不冲突：两个示例分别假定小于、大于上限，单凭它们不能给恰好相等的消息指定程序。这里的架构条款补上的是**等于信令面 SDS 载荷上限时允许什么**，不是为某条实际消息选出了路径。

**看到 MCData-SDS-1，要看这条记录做的是什么。** 在网模型中，服务器的 SDS 分发功能和客户端的 SDS 功能之间，SDS-1 主要承载为传输短数据而建立会话的应用信令，也可以在信令控制面上传或下发单播短数据。它还支持按情况请求或通知交付、已读。只有建会信令的记录，不能说明正文是从哪一面发的，也不能说明接收端拿到了正文。若另有一条“请求已读通知”，它说明有人请求回报，不等于接收人读过，更不等于已读通知已经返回。[§6.5.1 图后第 1 项，印刷页 27](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=28)；[§6.5.4.1.1 第 1–3 段，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)

**正文从媒体面发出，为什么在媒体面等不到已读回报？** 对终端（MCData UE）来说，决定去哪里找回报的是短数据服务的用法，不是刚才正文走的那条路。“处置请求”是请对方回报交付或已读；“处置通知”是针对那一笔消息给出的相应回报。用户可以只要求其中一种。例如，乙给甲发消息，乙端收到了甲端针对该笔的交付通知，可以记甲端报告已交付、乙端已收到这份报告；不能把它记成甲已读。

| 业务类型和终端发出记录时的媒体面状态 | 处置请求 | 处置通知 |
| --- | --- | --- |
| 独立 SDS（standalone）：一笔事务向一个方向传数据 | 查信令面 | 查信令面，即使正文经媒体面传送 |
| SDS 会话（session）：通过已建立的会话交换短数据，发出相应记录时媒体面可用 | 查媒体面 | 查媒体面 |
| SDS 会话：发通知时媒体面已不再可用 | 这项回退规定只适用于通知 | 改查信令面 |

表里列的是终端**应使用**的平面，不是这次已经发出或对方已经收到的证明。抓包中有一段时间没有媒体包，不等于媒体面已不再可用；可核对发通知时的媒体面状态，例如这次通信的媒体面是否已释放。即使确定通知该走信令面，也不能据此要求重发原处置请求或正文。[TS 23.282 V16.8.0 §5.9，印刷页 20](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=21)

同一 MCData 系统内，甲、乙均已注册接收 MCData 服务。比较两次一对一传送：

- **甲发一笔独立消息。** §7.4.2.3.2 步骤 2 的请求名称虽然含有 *standalone session data request*，它所属的仍是独立 SDS 程序。步骤 7 通过媒体面发正文。若甲要求已读回报，乙读后由乙端发起通知：查乙端的信令面，不必先证明媒体面释放。[独立消息的定义与前提，印刷页 57](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=58)；[步骤 2，印刷页 58](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=59)；[步骤 7、11–12，印刷页 59](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=60)
- **甲建了 SDS 会话，里面刚好只发一笔。** 会话允许交换至少一笔数据，不能凭“只发一笔”改判为独立 SDS。两端建立媒体面后，任一端均可发送。谁发送这一笔，谁就可以请求相应回报；接收端按该请求发起通知。若此时媒体面仍可用，应查媒体面。只有“要求已读”而没有匹配通知，不能给乙记已读；反过来，只在一个平面没找到通知，也不能给乙记未读。[§7.4.2 的单系统范围，印刷页 44](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=45)；[§7.4.2.4.2 引言、前提，印刷页 59](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=60)；[合述步骤 8、10 及步骤 12，印刷页 61](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=62)

若记录只有一条媒体面正文，却不知道它属于独立 SDS 还是 SDS 会话，先补看本笔所在的业务程序；若是会话，再核对发通知时的媒体面状态。正文走媒体面和消息名称里有 *session*，都不能单独替你选定回报的平面。

**在网 SDS 的载荷超过为信令控制面 SDS 配置的最大载荷时，不能仅看大小就填“组播”。** 架构区分了媒体面上两种传法。要给一次传送选对参考点，得知道是谁向谁发、是单播还是组播：

| 媒体面记录 | 对应的参考点 |
| --- | --- |
| 客户端向服务器上传单播短数据，或服务器向客户端下发单播短数据 | **MCData-SDS-2**，连接客户端的 SDS 功能和服务器的 SDS 分发功能。 |
| 服务器的 SDS 分发功能向客户端的 SDS 功能下发组播短数据 | **MCData-SDS-3**。这里没有客户端经 SDS-3 向服务器上行组播的方向。 |

例如，一条记录写明服务器已通过媒体面组播发出消息 X，可以把**这次下行发送**记在 SDS-3 下。要说乙端收到 X，还须有针对乙端和 X 的收件依据；服务器的发送记录既不能证明乙收到，也不能证明乙没收到。[§6.5.1 图后第 2、3 项，印刷页 27](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=28)；[§§6.5.4.1.1–3，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)

若要判定某接收端接受了**一笔独立消息还是组会话邀请**，看[同系统在网组 SDS 的两种媒体面程序](group-media-plane-sds-session.md)。若问题是客户端收到组到承载的映射或解除映射后要监听哪里，看[组 SDS 的 MBMS 映射与解除映射](group-sds-mbms-map-unmap.md)。参考点说明不能代替这些程序的具体步骤。
