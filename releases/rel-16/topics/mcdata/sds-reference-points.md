# 在网短数据：载荷等于为信令控制面 SDS 配置的最大载荷，能走信令面吗？建会信令能确定正文路径吗？

**在网短数据的载荷恰好等于信令控制面 SDS 的配置载荷上限时，可以走信令面；仅凭大小不能认定已经走了这条路。** Release 16 的这项许可比较的是这笔 SDS 载荷和信令控制面 SDS 的最大载荷。如果配置记录还列出 SDS 业务允许的最大数据量，不要把它当成信令面的载荷上限。条款用的是“不超过”，并说此时“可以”使用 MCData-SDS-1。若只知道含信令开销的整条消息大小，不能拿它代替载荷比较；条款也没有给一个所有系统通用的字节数。[TS 23.282 V16.8.0 §6.5.4.1.1 第 2 段，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)

这与[同系统一对一独立 SDS 的两个传送示例](one-to-one-standalone-sds.md)不冲突：两个示例分别假定小于、大于上限，单凭它们不能给恰好相等的消息指定程序。这里的架构条款补上的是**等于信令面 SDS 载荷上限时允许什么**，不是为某条实际消息选出了路径。

**看到 MCData-SDS-1，要看这条记录做的是什么。** 在网模型中，服务器的 SDS 分发功能和客户端的 SDS 功能之间，SDS-1 主要承载为传输短数据而建立会话的应用信令，也可以在信令控制面上传或下发单播短数据。它还支持按情况请求或通知交付、已读。只有建会信令的记录，不能说明正文是从哪一面发的，也不能说明接收端拿到了正文。若另有一条“请求已读通知”，它说明有人请求回报，不等于接收人读过，更不等于已读通知已经返回。[§6.5.1 图后第 1 项，印刷页 27](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=28)；[§6.5.4.1.1 第 1–3 段，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)

**在网 SDS 的载荷超过为信令控制面 SDS 配置的最大载荷时，不能仅看大小就填“组播”。** 架构区分了媒体面上两种传法。要给一次传送选对参考点，得知道是谁向谁发、是单播还是组播：

| 媒体面记录 | 对应的参考点 |
| --- | --- |
| 客户端向服务器上传单播短数据，或服务器向客户端下发单播短数据 | **MCData-SDS-2**，连接客户端的 SDS 功能和服务器的 SDS 分发功能。 |
| 服务器的 SDS 分发功能向客户端的 SDS 功能下发组播短数据 | **MCData-SDS-3**。这里没有客户端经 SDS-3 向服务器上行组播的方向。 |

例如，一条记录写明服务器已通过媒体面组播发出消息 X，可以把**这次下行发送**记在 SDS-3 下。要说乙端收到 X，还须有针对乙端和 X 的收件依据；服务器的发送记录既不能证明乙收到，也不能证明乙没收到。[§6.5.1 图后第 2、3 项，印刷页 27](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=28)；[§§6.5.4.1.1–3，印刷页 29](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=30)

若要判定某接收端接受了**一笔独立消息还是组会话邀请**，看[同系统在网组 SDS 的两种媒体面程序](group-media-plane-sds-session.md)。若问题是客户端收到组到承载的映射或解除映射后要监听哪里，看[组 SDS 的 MBMS 映射与解除映射](group-sds-mbms-map-unmap.md)。参考点说明不能代替这些程序的具体步骤。
