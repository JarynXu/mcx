# 另一位获授权的 MCData 参与者要求释放通信，谁有权同意延期？

发起通信的甲想继续传，参与同一次通信的乙有权要求释放。**如果乙要求先通知甲，甲可以通过 MCData 服务器向乙申请延期。决定是否同意的是乙，服务器负责转达。** 如果乙选择不先通知甲，流程就没有这个申请环节。

两条流程都以通信正在进行为前提。乙已注册 MCData 服务，并在跟踪哪些参与者正在接收此次通信，例如参考已送达或已读指示。参与通信、看到回执，都不等于有权释放。乙的客户端须向服务器指明要释放的是哪次通信、是否先通知甲；服务器核验请求人的身份和释放权限。[3GPP TS 23.282 V16.8.0，Release 16，Stage 2；§§7.7.2.5.1–2、7.7.2.6.1–2，流程前提及步骤 1–3，印刷页 131–133](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=132)。

**乙不要求预告。** 核实乙有权释放后，服务器按 §7.7.2.3 释放通信，再把释放结果回给提出请求的乙方客户端。“不预告”是指不先把释放意向告诉甲，不能据此认定服务器不查权限，或释放后不用回复乙。[§7.7.2.5.2 步骤 1–5，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=133)。

**乙要求先通知甲。** 核实权限后，服务器向甲的客户端发送释放意向，甲由自己的客户端得知乙想释放通信。乙可以在释放请求里询问还剩多少数据待传；服务器可以把这个问题带给甲，也可以在预告中写明释放原因。如果甲收到询问，就把剩余量报给服务器，服务器再转给乙。报告数据量只是答复询问，甲要争取继续传，还得另提延期申请。[§7.7.2.6.2 步骤 1–8，印刷页 133](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=134)。

- **只报剩余量，没申请。** 步骤 7 后的注针对服务器**收到补充信息响应后**的情形：服务器可以等候延期申请，等候时限由 MCData 管理员配置；若在时限内未收到申请，服务器按 §7.7.2.3 释放通信。不能把这段注读成每发一份预告都必须先等满一段固定时长。[§7.7.2.6.2 步骤 7 后的注，印刷页 133](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=134)。
- **甲提出延期申请。** 甲的客户端把申请发给服务器，服务器转给乙的客户端，由客户端告知乙。乙接受或拒绝后，决定同样经服务器传回甲的客户端。接受，通信继续；拒绝，按 §7.7.2.3 释放。给甲的**延期答复**与给乙的**释放响应**是两件事：后者由服务器在通信实际释放后发给乙，不能把甲收到延期答复的时刻当作释放完成。[§7.7.2.6.2 步骤 8–15，印刷页 133–134](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=135)。

判断相邻流程时，先看谁提出释放。[服务器自己预告释放](server-release-intent.md)时，延期由服务器裁决；[发送方主动停止媒体面传输](transmitter-initiated-media-release.md)则是发送方在要求结束通信。两者都不是这里乙提出释放、甲想继续传的情形。
