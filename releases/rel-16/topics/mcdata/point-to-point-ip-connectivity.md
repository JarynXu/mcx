# 在网 MCData 点到点 IP 互通：服务器放行后，能否认定对端已接受、数据已到达？

不能。**服务器放行**说明它已核对发起方和目标方的权限；**是否接受**由目标客户端答复。即使答复是“接受”，也不能把它当作某台主机收到 IP 数据的凭证。

**这套流程从哪里开始？** 在同一 MCData 系统内，发起方和目标方的客户端均支持 IP 互通，各连接一台已有 IP 地址、获准借该客户端建立连接的数据主机。本次连接不受时长或数据量配额阻止。服务器已订阅功能别名的激活及去激活变化，发起客户端已知道目标主机的 IP 地址对应哪个目标客户端。 数据主机本身不必懂 MCData。主机怎样获得授权、发起客户端怎样找出地址与目标客户端的对应关系，不是本规范在这里定义的步骤。服务器订阅了别名变化，也不表示每个请求都要用别名。以下依据 3GPP TS 23.282 V16.8.0（Rel-16，Stage 2）。[§7.14.2.2.1、§7.14.2.2.2 前提及注，印刷页 166–167](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)

**请求中的时限是提议，还不是结果。** 客户端 1 有数据要发，就向服务器请求与客户端 2 建立连接。请求表要求有发起用户和目标客户端的 MCData ID；可带发起用户的功能别名、应用优先级及建议时限。若没填应用优先级，预定义的默认应用优先级在**收到 IPcon 答复后**适用，不是在发请求时就按本条生效。建议时限可从 1 分钟到不限时。[表 7.14.2.1.1-1，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)；[§7.14.2.2.2 步骤 1–2，印刷页 167](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=168)

**谁作哪一个决定？** 服务器先检查两件事：客户端 1 的用户有没有权**发出这类请求**，客户端 2 有没有权**接收 IP 互通服务**。在放行的路径上，服务器才向客户端 2 发起请求。客户端 2 可以接受；若拒绝，它向服务器给出拒绝原因。服务器把客户端 2 的答复转给客户端 1，并不是替客户端 2 作决定。[§7.14.2.2.2 步骤 3–6，印刷页 167](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=168)

答复表要求有目标用户和请求用户的 MCData ID，以及**连接建立结果**。协商后的时限是可选项（1 分钟到不限时）：接受时，客户端 2 可以带上它，但不是非带不可。不能把请求里建议的时限当作双方已同意的时限，也不能单凭答复没写时限断定拒绝或不限时。[表 7.14.2.1.2-1，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)；[§7.14.2.2.2 步骤 5–6，印刷页 167](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=168)

**接受之后还差什么？** 在成功路径上，服务器还要实施发送控制、接收控制及必要策略。步骤 8 描述的是两个**客户端**已成功建立数据通信的媒体面，并交换 IP 数据。只见服务器发出请求，不能断言对端接受；只见接受答复，不能断言已经交换数据；即使引用步骤 8，也不是某台附接主机实际收到某个包的记录。[§7.14.2.2.2 步骤 7–8，印刷页 167–168](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=168)

要分清 IP 互通和短数据、文件分发等能力，见[MCData 服务能力与功能角色](service-capability-and-functional-roles.md)。
