# MCData 通过 MBMS 向组发文件：“已接受”以后，还能缺一部分吗？

能。“已接受”是接收端对分发请求的应答，可以发生在文件传送之前。多媒体广播多播业务（MBMS）传完后，有的客户端可能已经收全，有的只差几个片段，还有的接收质量太差，需要另行下载整个文件。要知道哪一步完成了，先看是谁向谁发了什么。

**先核对组和文件。** 甲要把文件发给选定组的多名用户。本例中，发起端和接收端的用户同属该组，都已注册接收 MCData 业务，也都已归属该组；文件已经上传到 MCData 内容服务器的媒体存储功能。MCData 服务器可以根据目标成员的密度和分布选择 MBMS，并非发给组就一定走 MBMS。[3GPP TS 23.282 V16.8.0，Rel-16，Stage 2，§§7.5.2.10.1–2，概述与前提 1–2，印刷页 103](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=104)。

**控制请求可以单播，文件仍由 MBMS 投递。** 服务器在 MBMS 会话属性中给出文件在媒体存储中的位置，并为投递前的通知、应答留出时间。它向选定的每个目标用户发出组文件分发请求：可走单播，也可走承载应用层控制信令的 MBMS 承载。接收客户端通知用户；随后，客户端在 MBMS 上接收文件本身。因此，只看到控制请求走单播，不能断定文件也走单播。[§7.5.2.10.2，步骤 5–7、10，印刷页 104](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=105)。

**强制下载时，谁回“已接受”？** 请求带强制下载指示时，接收客户端自动向 MCData 服务器回复接受，服务器把收到的应答转给甲的客户端。应答可在请求发出后、文件投递前给出；终端（UE）若处于空闲态，接收客户端可以略过这一步。因此，收到接受不证明文件已下载；缺一份应答也不能单凭此断定对方拒绝。[§7.5.2.10.2，步骤 6、8–10 及注 1–2，印刷页 104](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=105)。

| MBMS 投递结束时，接收端遇到什么情况？ | 接下来取什么、由谁取？ |
| --- | --- |
| 接收到的文件缺少部分片段 | 接收方的 MCData 客户端按 §7.5.2 所指的过程下载缺失部分。只缺片段不意味着要重下整个文件。 |
| MBMS 接收质量太差 | 接收方 MCData 客户端中的媒体存储客户端按 §7.5.2.3 下载文件本身，而不是只补一组缺片。注 3 没有给出数值门限，也没有规定必须先补片失败。 |

表中两个条号是原文给出的后续入口。步骤 11 后的编者注把“待研究”（FFS）限定在 **MCData-FD5 是否需要增强**，没有把补片、整文件下载或整个组分发程序都列为待定。[§7.5.2.10.2，步骤 10–11，印刷页 104；编者注和注 3，印刷页 105](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=105)。

**谁能报告“下载完成”？** 甲若要求完成报告，成功收到文件的接收客户端才发起下载完成报告。MCData 服务器可以保存报告，供获授权的 MCData 用户查询下载历史；也可以聚合各用户的报告。服务器向甲返回的是单份或聚合的完成报告。收到聚合报告不等于甲手里有每位成员的一份单独回执，更不等于用户打开或看过文件。若甲没要求报告，不能把没收到报告当作下载失败。[§7.5.2.10.2，步骤 12–14，印刷页 105](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=106)。

若问题是服务器如何核准强制或自愿下载，见[发送权限与下载决定](mandatory-consented-file-distribution.md)；若问题是哪些客户端负责报告承载暂停，见[MBMS 承载暂停上报](../bearers/mbms-suspension-reporting.md)。暂停报告不是某份文件的下载完成报告。
