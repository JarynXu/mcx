# MCData 并发发送：哪一路进入仲裁，收到链接算收到数据吗？

同时来了两笔 MCData 发送请求，一笔走信令控制面，另一笔走媒体面。**图 B.1-1 中，两笔都要核对发送权限；通过核验的媒体那笔进入传输控制仲裁，信令那笔不经过仲裁框。** 即使已经获准，也还要看服务器随后发的是正文还是取件链接。

这是 [3GPP TS 23.282 V16.8.0，Release 16，Stage 2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf) 的 MCData 应用层。第 5、6 章是正文。下面的图和队列例子出自**资料性附录 B**，用来理解职责，不是每个产品必须采用的调度流程。

## 先看正文：有发权，不等于本次可以开传

发送和接收控制都是 MCData 服务器的功能。正文 §5.1 说明 SDS 可以向选定个人或组自动发送，服务器仍可拒绝。该节对信令控制面 SDS 以外的数据类型描述了发送前的请求／授予办法。§6.3.1 从数据量说明：小量数据不需预先取得发送授予，何时能自动发要查具体程序；大文件这类大量数据要等传送请求获准。正文没有在这两处给出大小分界的统一数值。〔[§5.1，印刷页 16–17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=17)；[§6.3.1，印刷页 22–23](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=23)〕

拥塞时，MCData 业务可以拒绝发送请求、把请求排队，或暂不准自动发送。**实际拒绝后要通知用户；排队指示表示请求进入等待，不是拒绝，也不是获准发送。** 若同一组没有其他已归属成员，正文还要求通知提出传送的组员。“没有其他已归属成员”不是组名单为空。〔[§5.1，续页三项拥塞措施和末段，印刷页 17](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=18)〕

## 看例图：两支都核权，媒体一路经过仲裁

图 B.1-1 从终端选数据和收件人或组开始。**选择信令控制面、且载荷没有超出图示的信令面上限**，才走图中的信令分支；未选择信令面，或载荷超出这一上限，走媒体分支。

| 图中的网络侧条件 | 接下来读哪一框 |
| --- | --- |
| 任何一支未获发送授权 | 都走拒绝框，不进入后面的分发。 |
| 信令控制面的发权核验通过 | 不经过仲裁框，进存储转发判断。 |
| 媒体面的发权核验通过 | 先进入传输控制仲裁，再进存储转发判断。授权本身不是仲裁的结果。 |

B.1 说信令控制面请求宜及时处理。这不是固定时延，也不表示具体程序禁止排队。编者注把数据流相关问题和流程的准确性列为待研究。图只画出上述分支，不能凭一条大小记录、一个队列名或服务器名称确定某次消息真实走的路。〔[资料性 B.1，首段、编者注和图 B.1-1，印刷页 182](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=183)〕

## 进了仲裁，属于哪一类队列？

B.2 明写仲裁取决于实现。它举了一种按不同请求类型分队列、使用不同优先级的典型部署。**在这种模型中，同一个请求同一时刻不能同时放在多条队列里；队列种类和先后可由 MCData 管理员配置。** 例如一笔请求虽同时带有组、用户优先级和位置，也不能据这些属性在这个模型中登记成同时占三条队列。B.2 没有说明当多个属性重叠时怎样选队列，也没有要求所有部署都用这个模型。〔[资料性 B.2 首段，印刷页 182](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=183)〕

| 队列例子 | B.2 用来说明什么 |
| --- | --- |
| 主传输控制队列 | 从这里处理待传请求，例如紧急请求可能进入此队列，并以最高优先级处理。 |
| 通信类型队列 | 可按通信类型排序，例如组通信请求可排在一对多或私通信请求之前。 |
| 静态属性队列 | 可根据预配的组优先级或用户优先级分类。 |
| 动态属性队列 | 可考虑发送者位置、内容大小等本次请求属性。 |

这不是四个必经阶段。面对一笔普通组请求和一笔紧急私聊请求，不能把头两行拼成通用的先后次序。查实际配置和两笔请求的处理记录。〔[资料性 B.2 续页四项，印刷页 183](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=184)〕

## 授权和仲裁之后，服务器发的是链接还是数据？

信令分支通过授权、媒体分支经过仲裁后，图上的两路汇合。**采用存储转发，数据放在网络存储，向接收者发送对应的 URL；不采用存储转发，图中才继续选直接广播或单播正文。** 这里的广播是图中的分支，不足以指定具体承载。若乙实际收到了 URL，只能记乙收到了地址。要登记乙收到正文、完成下载或看过内容，分别查相应证据。〔[资料性 B.1 首段末与图 B.1-1，印刷页 182](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=183)；[§6.3.1 的存储说明，印刷页 23](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=24)〕

**若排查的是一笔在网自动 SDS，按 §7.6.2.2 查。** 该节说不需要请求／授予和接收端的显式操作，步骤 2 列有信令面和媒体面两类选择，步骤 4c 又允许服务器排队并给出指示。不能拿附录图消掉该程序的排队分支，也不能为自动 SDS 的媒体面实例另加一种规定的请求／授予接口。〔[§7.6.2.2.1，印刷页 116](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=117)；[§7.6.2.2.2 步骤 2、4c，印刷页 117](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=118)〕
