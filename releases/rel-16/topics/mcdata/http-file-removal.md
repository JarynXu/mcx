# MCData：上传方移除文件后，原来收到下载链接的人会知道吗？

上传方收到移除成功的答复，表示这次**服务器端文件移除**成功，不是给原收件人的通知。即使文件曾转存到伙伴系统，伙伴确认的也是其**内容服务器**上的文件已移除，不能据此断定收件人已经知道，或此前下载到终端的副本已被擦除。

**只涉及一个系统时。** 媒体存储客户端上的用户已注册 MCData 服务，且此前已成功上传这个文件；内容服务器能够核查该用户是否有权移除它。用户决定移除后，客户端用 HTTP 向内容服务器的媒体存储功能提交文件 URL，服务器按 URL 移除文件，并向这个客户端报告是否成功。知道链接不等于拥有移除权限；只看到请求也不能判定成功。[3GPP TS 23.282 V16.8.0，Release 16，Stage 2，§§7.5.2.8.1–2、图 7.5.2.8.2-1，印刷页 101–102](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=102)。

**已转存到伙伴系统时。** 互联示例的前提是用户已注册、文件此前上传到主内容服务器，且已成功转存到伙伴内容服务器。仅将链接发给另一系统的用户，还不能套用这个示例。客户端向主服务器提出移除（步骤 2）。主服务器根据先前的转送记录向伙伴发移除请求（步骤 4），请求中用的是**主服务器上原文件的 URL**。伙伴按该引用移除自己的文件，向主服务器确认成功（步骤 5、6）；主服务器再向发起客户端报告结果（步骤 7）。主服务器自己的移除（步骤 3）只要求在步骤 2 之后、步骤 6 之前，不要求一定先删本地再向伙伴发请求。伙伴的确认不能当作用户已收到最终答复；图中也没有给出伙伴失败或不响应时如何重试、回滚。[§7.5.2.8.3、图 7.5.2.8.3-1 及步骤 3 的说明，印刷页 102–103](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=103)。

**怎样读请求和答复？** 请求必带内容引用（文件 URL）；答复必带结果（成功或失败）。两张表中的用户 MCData ID、伙伴系统身份都标为 O，但不能因此把相关身份任意省略：按表注，客户端到服务器的请求和服务器给客户端的答复带移除用户的 MCData ID；服务器之间的请求和答复带伙伴系统身份。这是 Stage 2 信息流，并不指定 HTTP 方法名或状态码。[表 7.5.2.1.14-1、7.5.2.1.15-1 及各表注 1、2，印刷页 86](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=87)。

**为什么有通知表，却不能断言收件人会收到？** 表 7.5.2.1.18-1 描述 MCData 服务器发往 MCData 客户端的移除通知：上传者的 MCData ID 和已移除文件的 URL 必填，移除原因可选。表回答的是“这种通知携带什么”；单系统和跨系统程序末尾的编辑注都把“原 URL 收件人是否需要获知文件已不可下载，以及如何通知”留待研究（FFS）。因此既不能承诺会逐人通知，也不能说禁止通知。这里移除的是服务器上的文件，不规定远程删除收件人已下载的本地文件。[通知表，印刷页 86](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=87)；[单系统编辑注，页 102](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=103)；[跨系统编辑注，页 103](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=104)。

要判断接收端是否已经取到文件，见[私聊 HTTP 文件分发客户端](http-fd-client.md)；要判断分发信令是否被受理、转送，或服务端收到过期通知后怎样清理列表，见[私聊 HTTP 文件分发服务端](http-fd-server.md)。这些分发事件都不是本页的用户移除确认。
