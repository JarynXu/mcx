# 在网 MCData 一对一 HTTP 文件分发：哪份记录能把下载完成对应到某个文件？

甲在同一对话里先后给乙发了两份文件。甲看到两个取件地址，又收到乙的一份一对一 HTTP 文件分发（FD）响应。**这份响应不能说明乙下载了哪一份，甚至不能证明乙下载过文件。** 要判断“乙的客户端报告哪一笔已下完”，看在网下载完成报告：谁回报、回复哪一笔、确认了什么。不能只按对话或时间先后配对。

先确认是哪张表。[§7.5.2 和 §7.5.2.1 的标题（印刷页 81）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=82)把这三张表归入**在网**文件分发信息流。[表 7.5.2.1.5-1 和 7.5.2.1.6-1 的引言（印刷页 83）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)把请求和响应指向 §7.5.2.4.2；它位于[一对一 HTTP 文件分发程序（§7.5.2.4 标题、§7.5.2.4.2 标题与首段，印刷页 91）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=92)。不要把这两张表当成组 HTTP 请求和响应的字段清单。第三张是[在网下载完成报告表 7.5.2.1.7-1（印刷页 83）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)，标题和引言没有把它限定为 HTTP。

**请求：给谁发什么，希望对方做什么？** 在一对一 HTTP FD 请求中，两项必选的 MCData ID 分别标识发文件的甲和收文件的乙。另有三个必选项：Conversation Identifier 标识对话；Transaction Identifier 标识本笔 MCData 事务；Content reference 引用要取的内容，其说明包含内容 URL 和文件元数据。表中标为必选（M）的是整个内容引用，并未把每项元数据各列为必选。URL 指向内容，不表示乙已取回它。请求还可带 Reply Identifier，指向**本笔正在回复的原事务**；请求不带它，并不缺少必选项，但仍须有本笔的事务标识。[§7.5.2.1.5，表 7.5.2.1.5-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)

一对一 HTTP FD 请求中的两项可选（O）指示要分开读：Disposition indication 表达是否期望下载完成报告；Download indication 表达要求强制下载。甲可以要求乙下载而不要求回报，也可以期望回报却不指示强制下载。即使两项都明确提出，也只是要求，不是完成确认；没看到报告不能反推乙没下载。可选的发件用户功能别名和紧急指示也不改变这些标识的含义。[表 7.5.2.1.5-1，指示及身份行](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)

**响应：谁回答了谁？** 在网一对一 HTTP FD 响应表只有三项，均必选：发起 FD 请求的用户 ID、发送响应的用户 ID 和对话标识。它没有列本笔事务标识、原事务回复标识或下载完成确认。假设甲先发清单（事务 A），再发地图（事务 B），两笔都发给乙、对话都是 C。仅有“甲、乙、C”的响应可以认出两名用户和对话，却不足以选出 A 或 B，更不能凭它给其中一份标上“下载完成”。[§7.5.2.1.6，表 7.5.2.1.6-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)

**完成报告：乙确认的是哪一笔？** 在网下载完成报告表的六项都必选。前两项仍是发起 FD 请求的用户 ID、发送响应的用户 ID；再看对话标识、**报告本身的 Transaction Identifier**、**指回原事务的 Reply Identifier**，以及表示该客户端下载完文件的 **Disposition confirmation**。若乙的报告属于 C，自身事务为 R，回复 B，且有完成确认，能记的是“乙的客户端报告地图 B 已下载”。R 不是文件请求 B；清单 A 的状态仍未知。即使乙有另一台设备，也不能据此替另一端确认，更不能断言乙本人读过地图。只有回复标识缺少完成确认，或有确认却缺少回复标识，都不足以据这张表认定一份完整且对应到 B 的完成报告；节选缺项不等于设备真的没下载。[§7.5.2.1.7，表 7.5.2.1.7-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)

**转发者不一定是回报的用户。** 在网一对一 HTTP FD 请求、响应，以及在网 FD 下载完成报告，这三张表的引言都列出相应信息流的三种方向：MCData 客户端到服务器、服务器到另一客户端、服务器到伙伴 MCData 服务器。这是允许描述的不同传递段，不是每次必经三跳。即使是在两台服务器之间看到报告，两个 MCData ID 仍是用户身份，不是这两台服务器的标识；也不要把服务器已发送记作甲端已收到。§7.5.2.4.2 举的是单系统程序的例子，但请求和响应表的引言本身也列出了伙伴服务器这一段；不能因这个程序示例就删掉表里写明的方向。这三张表定义 Stage 2 信息的意义和必选性，不给出报文字节、HTTP 头名或交易状态码。[3GPP TS 23.282 V16.8.0，Release 16，§§7.5.2.1.5–7，三表及引言，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84)

要查同系统里**谁发起、保存或转送报告**，见[一对一 HTTP 分发程序](one-to-one-http-file-distribution.md)；若实际是**离网客户端直接互报**，见[离网一对一 FD](offnetwork-one-to-one-fd.md)，不要套用本页的回复标识名称。要查**信令或文件数据走哪条参考点**，见[FD-1、FD-2 和 FD-3](fd-reference-points.md)。
