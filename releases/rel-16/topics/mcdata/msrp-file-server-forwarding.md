# MCData 用 MSRP 分发文件：谁回复 200，文件往哪些客户端转发？

发起侧参与功能把一条文件 SEND 转给控制功能。**控制功能为这条 SEND 生成 MSRP 200（OK），发起侧参与功能收到后再把它转回发起客户端。** 这个 200 回答的是控制功能收到的请求，不是终接客户端的下载回执。仅知道日志里后来出现一个 200，却不能将它与这条 SEND 对应，就不能据此认定这条请求得到了谁的回复。若组内只有乙和丙已成功建立 MSRP 连接，控制功能须向乙、丙各转发这条 SEND；丁虽在组内，未成功建连，就不在这次转发的目标之中。[3GPP TS 24.582 V16.3.0，Release 16，Stage 3，§7.2.4.3，印刷页 31](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=32)；[§7.3.3 第 1、2 项，页 33](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=34)。

**发起侧参与功能：先看它到控制功能的那一段。** 收到发起客户端的 SEND 后，如果还没有到控制功能的 MSRP 连接，就须按 §7.2.4.2 建立；已有连接则须复用。然后将收到的 SEND 转发给控制功能。如果收到控制功能返回的 200，就把这个 200 转给发起客户端；如果收到的是错误响应，也把该错误响应转给发起客户端。这些是不同的接收事件，不要求先有 200 才能处理错误。[§7.2.4.3 第 1、2 项及其后两段，页 31](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=32)。

**控制功能：回复发起侧，按终接连接分别转发。** 收到发起侧参与功能的 SEND，控制功能须为此请求生成 200 并发回该参与功能。它还须向每个已成功建立 MSRP 连接的终接客户端转发 SEND：对每个目标，按该客户端 SDP 应答中的 MSRP URI 修改 `To-Path`，将 `From-Path` 改为控制功能自己的 MSRP URI。本条没有要求在 200 中列出目标。单凭这个状态码，不能确定哪些目标已建连、实际向谁转发，更不能认定文件已送达；要核对目标名单，须另看各目标的建连和转发记录。[§7.3.3 第 1、2 项及 2a、2b，页 33](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=34)。

**终接侧参与功能：另生成一个 200。** 收到控制功能发来的 SEND，终接侧参与功能须为此请求生成 200 给控制功能，并将收到的 SEND 转发给终接客户端。这个 200 不是终接客户端返回的。如果终接客户端后来返回错误，条款写明终接侧参与功能须把错误响应转给**发起客户端**；目的端明确，但该段没有逐跳列出中间路由。先看到终接侧参与功能的 200，后来又看到终接客户端报错，两项记录并不矛盾。[§7.2.5.3 第 1、2 项及其后错误段，页 32](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=33)。

以上只解释文件分发时这些功能实际收到指定消息后的职责。两个服务功能分别回应各自收到的 SEND；单凭这些响应，不能判断某个客户端已收齐重组、用户已读或全组已收。要核实乙是否下载完成，应查乙客户端向信令面给出的[下载完成指示](msrp-file-delivery.md)。若要查普通在网按需一对一会话短数据，见[会话 SDS 的服务端媒体程序](sds-session-media-server.md)；该页不适用于组 SDS，本页文件分发的条款也不能直接移用于短数据。
