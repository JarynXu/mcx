# MCData：发送方要求停止传输后，什么时候算这次通信已经释放？

发送方发出释放请求，只表示要结束当前通信。接收方的响应报告是否已释放；正常流程的完成状态是**所有参与方都已释放这次通信占用的媒体面资源**。这几个事件都不是文件或短消息的送达回执。[3GPP TS 23.282 V16.8.0，Release 16，Stage 2，§7.7.2.2.2.2、图 7.7.2.2.2.2-1，印刷页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=128)

**谁能提出停止？** 在网一对一或组通信进行期间，发送方可以随时向 MCData 服务器表示停止传输。图中双方用户都已注册 MCData 服务，通信已经建立，发送方的客户端 1 也是原发起端。条文列出三种业务：通过媒体面传送短数据（SDS）、SDS 会话、通过媒体面分发文件（FD）。这里传的是媒体面上的数据，结束通信的请求和响应则走控制面。该版将 MBMS 上的通信释放列为待研究，不能把图中的步骤直接套过去。[§7.7.2.2.1、§7.7.2.2.2.1，页 126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=127)；[§7.7.2.2.2.2 前提，页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=128)

**请求发给谁，谁向谁回报？** 以发送方甲向组内传文件为例：

1. 甲决定结束本次通信。甲的客户端向 MCData 服务器发释放请求；服务器把释放请求发给**这次通信的所有参与方**。这里看的是谁参与了这次通信，不是组通讯录里有谁。
2. 收到请求的客户端先告知各自用户，再向服务器发释放响应。服务器另向甲的客户端发释放响应。甲不会直接收到各接收方的回复。
3. 图示成功流程接下来列出：所有参与方都已释放**与本次通信关联的媒体面资源**，然后甲的客户端通知甲通信已释放。组员先前收到的通知与甲最后看到的通知是两个事件。只有一个组员的响应，不能证明其他参与方也已释放；这些步骤也不规定有人未回应时服务器该等多久或如何重试。[图 7.7.2.2.2.2-1，步骤 1–8，页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=128)

**响应里看什么？** 一对一请求和响应都用两个 MCData 用户 ID，分别标识上传方和本次释放所针对的用户；组通信改用上传方的 MCData 用户 ID 和目标 MCData 组 ID。这两项身份在各自表中均为必填。两类**响应**还必须注明释放结果（*Release confirmation*），值可表示已释放或未释放。只看到消息名不足以认定成功；即使某个接收方回报已释放，也不能据此认定文件传完、对方已读，或服务器已删除文件。[表 7.7.2.1.1-1，页 121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=122)；[表 7.7.2.1.2-1 至 7.7.2.1.4-1，页 122](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=123)

如果最先提出释放的是服务器，见[服务器预告与延期](server-release-intent.md)；如果上传方要移除内容服务器里的文件，见[HTTP 文件移除](http-file-removal.md)。两者都不是发送方结束本次媒体面通信的前置步骤。
