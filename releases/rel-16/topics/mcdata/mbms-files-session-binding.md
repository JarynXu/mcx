# MCData 通过 xMB 向组发文件：何时把目标文件的位置和 URI 写入 Files 会话？

**预建的会话在发这份文件前更新；为这份文件动态建立的会话在创建时就指定文件。** 这里的“指定”指 MCData 服务器给出**目标文件的位置和 URI**。客户端拿到的 SA file 是业务通告文件，不能拿它当作已收到目标文件的凭据。这是 3GPP TS 23.282 V16.8.0（Release 16，Stage 2）的 MBMS 用户业务文件分发流程；它可以用于任一 MC 业务组，不表示每次组分发都采用它。[§7.3.5.1，印刷页 40](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=41)。

**预建：先有能发文件的业务，后指定要发的文件。** 服务器先为预配置区域建好 MBMS 用户业务。例中参与用户已归属；在 xMB 分支，服务器经 xMB-C 创建该业务，再为它创建类型为 `Files` 的会话，采用 MBMS 下载投递方式。步骤 2 的响应给服务器承载标识 TMGI 和描述用户业务的 SA 文件。若此时只知道“会话已建，SA 已返回”，不能登记任务单 X 已被指定。服务器决定向组发 X 时，在步骤 7 **更新已有会话**，给出 X 的位置和 URI。向目标客户端发传输信令是步骤 8，客户端经 MBMS 接收 X 是步骤 9。只见服务器已向乙发信令，可以记“已向乙发送 X 的传输通知”；乙有没有收到这条通知、乙有没有收到 X 正文，仍是两个未确认的结果。[§7.3.5.3.1.1 与 .1.2 前提，印 41](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=42)；[图 7.3.5.3.1.2-1、步骤 1–2，印 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=43)；[步骤 7–9，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=44)。

**动态：为 X 建业务，创建会话时就带上 X。** 服务器何时决定创建用户业务由实现决定，目标组终端的位置只是一个可参考的因素。服务器先创建用户业务（步骤 1），再在创建 `Files` 会话时给出 X 的位置和 URI（步骤 2）。响应除 TMGI 和 SA 文件外，还有这次文件投递的调度参数。这里不需要照搬预建例的步骤 7 再指定一次 X，也不能据此禁止会话日后更新。服务器把用户业务与待收文件的信息一起通告；信息不等于正文。动态例的步骤 7 是传输信令，步骤 8 才是客户端接收 X。[§7.3.5.3.2，开头、注 1、图 7.3.5.3.2-1、步骤 1–2，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=44)；[步骤 2 续、4–8，印 44](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=45)。

**客户端收到 SA，知道了什么？** 从服务器到客户端的用户业务通告中，业务标识和 SA 文件必填；监听状态（Monitoring state）和单播状态（Unicast status）可选。SA 来自创建或更新会话的响应，提供 TMGI、MBMS 业务区标识列表、频率和投递参数。预建用户业务可以预先通告，也可以随分发信令通告；预建例的注 2 只说后续通告的步骤 4 可选，并没有把首次通告的必填字段改为可选。[§7.3.5.2.1，印 40](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=41)；[表 7.3.5.2.1-1 及注、§7.3.5.3.1.1，印 41](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=42)；[预建步骤 4、注 2，印 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=43)。

两例中的客户端都保存业务信息，用 TMGI 和其他信息开始监听承载。两例的步骤 6 描述的是：客户端已在或进入至少一个已通告 TMGI 的服务区，向服务器表示**自己能经 MBMS 收文件**。如果只看到“监听状态报告”这个消息名，没有内容、关联业务或区域记录，就不能确认该客户端表示能收文件，也不能从消息名倒推它在区。这里没有列出所有可能的报告触发条件。即便乙在上述区域内明确报告能收，服务器也只是可以选用该用户业务代替单播；这份报告既不证明这次已选 MBMS，也不证明乙或其他组员已收 X。查指定文件看会话的创建或更新记录，查通知看传输信令，查交付结果看相应客户端对同一文件的接收记录。[预建步骤 4–6，印 42](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=43)；[预建步骤 7–9，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=44)；[动态步骤 4–8，印 44](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=45)。

**不要把图中的 MB2 支路当成部署说明。** 预建、动态两条程序开头各有一条编者注：它们引用的 TS 26.346 所定义的 MBMS 用户业务无法经 MB2 支持，程序需要修订。图中保留的 MB2 操作不能据此验收为可部署，也不能用这条注否定本节所述的 xMB 分支。预建场景还明确，传文件的用户业务不传应用层控制信令；按通用程序可以用 MBMS 承载传这种控制消息。看到控制信令不能反推它走了传文件的用户业务，或断定现场必用另一条 MBMS 承载。[§7.3.5.3.1.1 末段、§7.3.5.3.1.2 编者注，印 41](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=42)；[§7.3.5.3.2 编者注，印 43](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=44)。这些条款不提供产品接口报文或实际部署证明。

若已确定本次组独立文件分发选择 **MBMS 下载投递正文**，见[采用 MBMS 下载的组文件：投递前应答、投递后补片和完成报告](mbms-group-file-delivery.md)（§7.5.2.10.2，印 103–105）。查应答不必等正文送达；控制请求即使走单播，也不能据此排除 MBMS。若原先经 MBMS 投递，结束后才用 HTTP 补下载，查补救仍从该 MBMS 程序开始。若本次从一开始就是在网 HTTP 组独立文件分发，收件端凭 URL 下载正文，则查“在网 HTTP 组文件分发”§7.5.2.6.2（印 97–98）；不能把 MBMS 程序里的空闲终端可省应答或投递后补片套过来。
