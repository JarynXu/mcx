# 在网 HTTP 组文件分发：请求里有文件链接，怎样判断哪位组员已经下载？

甲给同组的乙和丙发文件，只点选了这两人。甲端的记录里有文件 URL、会话标识和乙的“接受”应答。这三项分别说明**去哪儿取文件、请求属于哪个消息线程、乙端怎样答复请求**。没有一项说明乙已经收齐，更不能替丙作判断。要确认乙下载完成，应找乙端成功收件后的完成记录，或能明确归到乙的下载完成报告。〔§7.5.2.6.2，步骤 1–2、6–12，印刷页 97–98〕

**文件已经在哪里？** 这是在网、通过 HTTP 的组独立文件分发（FD）。示例从文件已上传到 MCData 内容服务器的媒体存储功能开始。甲和接收用户属于同一组，都已注册接收 MCData 服务，也已归属该组。客户端可选用已激活的功能别名；例中的 MCData 服务器已向本系统的功能别名控制服务器订阅激活和停用更新。上传完成是这次分发的起点，不是接收端下载完成。〔§7.5.2.6.1；§7.5.2.6.2 前提 1–4，印刷页 96〕

**服务器向谁发请求？** 甲先选一个预配置组，可以选整组，也可以在组里点选特定成员。甲的客户端把所选组 ID 或选定的目标收件人发给 MCData 服务器。请求的内容载荷是文件 URL；文件元数据可带可不带。会话标识用于标明消息线程。甲要求接收端强制下载时，请求带强制下载指示；甲还可另选下载完成报告。〔§7.5.2.6.2，步骤 1–2，印刷页 97〕

服务器检查甲是否获准发组独立 FD 请求，以及文件大小是否**低于**组配置的 FD 上限。文件大小恰好等于上限不满足该条件；有发送权不免除大小检查。若甲附了功能别名，还要查它是否可供甲使用、是否已为甲激活。若以组 ID 寻址，服务器依据组管理服务器的信息解析成员及其归属状态。它实施收发控制及必要的策略控制，再向确定的每个目标发请求。不能只凭组名册，或把甲点名的子集扩大到全组。〔§7.5.2.6.2，步骤 3–5，印刷页 98〕

这里有一个容易误读的分支：示例前提已写明用户归属该组；步骤 2a 另写的是**收到含紧急指示或迫近危险指示的请求，而且发起客户端尚未归属**时，服务器才在这一步让发起端隐式归属该组。不是普通请求一来就替它归属，也不是给所有接收人办理归属。〔§7.5.2.6.2 前提 1，印刷页 96；步骤 2a，印刷页 98〕

**应答和下载分别发生在哪一端？** 乙端先通知乙有分发请求，有元数据时一并告知。普通请求可接受、拒绝或忽略；若来件带强制下载指示，乙的客户端自动向服务器回复接受，不必等乙点选。服务器把接收端的分发应答转给甲；按步骤 8 的注，视传送条件，可在向目标发出请求后、实际下载前转回。随后由乙端的媒体存储客户端取文件：强制下载自动进行，非强制下载取决于用户后续操作。因此即便应答是“自动接受”，也不等于下载成功。〔§7.5.2.6.2，步骤 6–9 及步骤 8 后的注，印刷页 98〕

**谁记完成，谁能收到报告？** 成功收到文件的客户端记录本端下载完成，并通知本端用户。若甲要求完成报告，成功收件端还发起下载完成报告。服务器可保留报告供获授权用户查下载历史，也可将多份报告汇总（步骤 11）。无论是否汇总，服务器都将报告发给甲：汇总了就发汇总结果，不汇总就逐份发（步骤 12）。只把汇总结果存好而没有发送，不能算已执行步骤 12；看到服务器已发，也不等于已经证实甲收到了。甲没有要求报告时，缺少报告不能证明乙下载失败。一份只反映乙的报告，也不能把丙记为完成。〔§7.5.2.6.2，步骤 9–12，印刷页 98〕
