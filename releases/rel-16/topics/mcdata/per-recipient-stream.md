# MCData 数据流：自动接收要等乙同意吗？同一条流能只停给乙吗？

甲把数据流 X 发给乙和丙。**如果这次请求设为自动接收，MCData 服务不得等乙同意才让乙接收。** 乙端可以显示“正在接收”这样的提示；要看的是，不点“同意”会不会挡住接收。这个设置只回答是否需要接收用户同意，不替甲取得发送许可，也没有说明客户端做过哪些处理、乙收到多少内容。反过来，只见乙没点按钮，不能判定这次请求设了自动接收。[3GPP TS 23.282 V16.8.0，Rel-16 Stage 2，§5.5 自动接收条件，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=19)。

**能只停给乙。** 用户应当能对指定流施加开始（start）、停止（stop）或取消（cancel）控制，也能把控制限定到单个接收者。如果甲的记录只写“停止给乙的 X”，该操作没有要求同时停给丙；它也不是执行结果。要判乙是否已经停收，或丙此刻是否仍在接收，须分别核对乙、丙对 X 的实际记录。[§5.5 续页首段，印刷页 19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=20)。

**没人点停止，流为什么也会结束？** 用户显式停止或取消是一种终止原因；所传内容到达末尾是另一种。这两种都能结束流。已知 X 的内容已到末尾，不需要再找一条用户停止命令来解释终止。若只知道 X 已结束，原因仍未确定；也不能据此签认乙收齐了 X。[§5.5 末段，印刷页 19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=20)。

发送对象也要看清：服务须支持一对一和组数据流；用户既可向另一用户发流，也可只发流的 URL。即便乙收到 URL，也只说明链接到了。流的源头可以是 MCData 客户端或网络功能实体；源在网络侧时，内容仍可能由 MCData 用户提供。分发机制须支持单播和广播，条文没要求同一次传送两种都用，也没要求为每位接收者单建一条物理链路。[§5.5 前两段，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=19)。

停止后是否能从断点恢复？§5.5 的编辑注只说**暂停和恢复是否适用于一对一通信**仍待研究；不能把 stop 当成可恢复的暂停，也不能凭这条注解判定组通信支持或禁止暂停。本版同节还将**数据流应支持的最低比特率**列为待研究，没有给出可用于验收的数值。[一对一暂停与恢复，印刷页 19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=20)；[最低比特率，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=19)。

- 若乙报告“X 已停止”，这份报告本身不能确定是谁下了停止命令。查[数据流参考点：报告、控制与流数据各能证明什么](data-stream-reference-points.md)。
- 若问题是**在网 MCData 文件分发（FD）**中收件人能否推迟或拒绝下载，查[在网文件分发的强制下载与同意下载](mandatory-consented-file-distribution.md)。离网独立组 FD 要查离网组的程序。若只知道“向组发文件，要求强制下载”，先确认这次分发是在网还是离网。
- 若只知道乙已开始处理，想知道为什么不能据此签收全部内容，查[数据未收全即可开始处理的服务能力](service-capability-and-functional-roles.md)。
