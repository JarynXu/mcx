# 私聊HTTP文件分发客户端：上传、URL通知、下载决定与完成证据

## 适用条件
- 固定 TS24.282 V16.13.0（2026-02），普通在网直接MCData ID私聊、供用户使用的HTTP FD客户端职责；不含组、功能别名、应用定向文件、媒体面FD或服务器完整转送链。
- 发送、接收、用户决定和HTTP响应按各自实际事件适用；不把发送许可、上传成功、接收200或下载成功设为所有分支共同前提。供用户使用的FD信令不携Application ID或Extended application ID。
- 适用的XML验证/解密须依6.5.1.4在其他处理前执行，失败不得继续；发送保护、MIME封装按6.5.1.2–3及6.4。HTTP的TLS、代理和认证依赖24.482，文件保护依赖33.180，本页不证明这些外部实现已通过。

## 先判发送资格与下载需求，再上传取得文件URL

- 条件：用户请求向直接目标发送私聊standalone文件，进入10.2.1.1；或媒体存储客户端实际收到所发上传POST的HTTP响应。HTTP上传细节仅适用于进入10.2.4且前序大小检查未停止的分支。

先执行11.1：发送许可缺失或false、出站名单存在且含一个或多个 entry 且目标不匹配、超过max-data-size-fd-bytes或MaxData1To1均不能凭文件很小而绕过。通过后，不要求mandatory download才走HTTP 10.2.4，要求mandatory download则走媒体10.2.5，不按SDS控制面阈值选择。HTTP入口再检查文件大小不大于服务FD上限，超限停止；确定存储URI后请求上传。媒体存储客户端用HTTP POST上传，私聊信息含one-to-one-fd及主叫MCData ID；需要端到端安全时保护文件并加安全参数，不需要时按该分支携二进制及其长度。实际收到含Location文件URL的HTTP201才存该信息；这只证明存储位置反馈，不证明目标用户下载。

规范强度：发送检查、分派、上传及201信息保存shall；文件保护按其条件执行。
- 边界：10.2.4.1与10.2.2.1把MCDataContentServerURI的来源字面称为MCPTT user profile并指24.484[50]；本页不改称另一个配置文档，也不补未取得URI时的客户端发现报文。
- 边界：10.2.4.1列出请求上传后发URL信令；本页只在实际已有文件URL时解释下一构造步骤，不给未成功上传的重试、超时或URL缺失情形补流程。

## SIP MESSAGE携文件URL，不等同文件本体已送达

- 条件：客户端已进入HTTP FD发送分支，实际具有待分发文件URL，构造10.2.4.2.1普通直接ID私聊请求。

按6.2.4.1使用FD服务标识并把Request-URI设为服务PF公有服务身份；resource-lists+xml中携目标MCData ID，request-type为one-to-one-fd。6.2.2.2生成FD SIGNALLING PAYLOAD，包含消息/会话标识和FILEURL类型的Payload IE；回复另关联原消息。可携Metadata；要求完成更新时携相应FD disposition request。该MESSAGE发送的是文件引用与控制信息，不是以SIP成功证明文件内容已在目标端。

规范强度：请求构造与发送shall；Metadata及完成更新请求为may。
- 边界：6.2.2.2也定义有mandatory需求时的IE构造，但不能据此推翻10.2.1.1对发起端HTTP/媒体入口的选择。本页不把helper存在某字段解释为所有发起分支都可用。
- 边界：接收端按实际收到的Mandatory download IE判定，不从发起端的选择条件推定接收IE必然缺失。服务器如何按11.2作自动接收判断不在本页展开。

## 终端先回SIP200，再按实际信令决定自动或等待下载

- 条件：终端实际收到6.2.1.1分类的HTTP FD MESSAGE，FD Accept-Contact的g.3gpp.icsi-ref与P-Asserted-Service均匹配；资源拒绝不以前序成功为共同条件。信令分支仅在收到相应FD SIGNALLING PAYLOAD且通过10.2.1.2.1检查时适用。

资源不足可拒绝；若拒绝回480并停止。否则先生成并发送SIP200，再调用10.2.1.2。收到信令body后解码，不是FD SIGNALLING PAYLOAD、多于一个Payload IE或Payload类型不是FILEURL则退出该处理。Mandatory download IE为MANDATORY DOWNLOAD时进入自动分支：建立或关联消息上下文、告知用户将自动下载，若有Metadata则交给用户，随后发接受通知并尝试下载。若Mandatory download IE缺失，则通知用户、按有无Metadata展示相关信息，启动可配置TDU2（默认60秒）等待决定。接受、拒绝或延期时停表；运行期间用户延期则发延期通知，拒绝则发拒绝通知并退出，用户接受才发接受通知、关联消息并尝试下载。表到期本身无特定动作，到期后仍可接受或拒绝，延期则不采取动作。

规范强度：资源拒绝may；选择拒绝后的480/停止、正常200及条件分支动作shall；上下文本地保存may。
- 边界：接收200发生在信令解码和下载决定之前，不能证明用户接受、文件已下载或已读。上述初始检查不补零Payload或Mandatory download IE其他值的未明分支。
- 边界：本页限定用户消费文件；应用标识已知/未知的启动、丢弃与应用决定分支不在此展开。自动与等待决定是替代分支，不要求用户先接受才进入自动下载。

## HTTP200须含请求文件，完成通知还须符合请求条件

- 条件：媒体存储客户端被10.2.1.2.2或10.2.1.2.3实际调用尝试下载；或实际收到下载HTTP响应；或客户端达到该接收分支的接受、拒绝、延期或下载完成通知事件。各事件分别适用，完成不是拒绝/延期的前提。

下载使用以文件绝对URL为Request-URI的HTTP GET；实际收到包含所请求文件的HTTP200后，通知用户文件已成功下载。接受通知在尝试下载前，不能当作下载完成。自动分支或用户接受分支均仅在原FD信令要求完成更新且文件已成功下载后生成完成通知。12.2.1.1从原请求的mcdata-calling-user-id确定通知目标，通过服务PF发送另一个SIP MESSAGE；6.2.3.2把接受、拒绝、延期和完成编码为各自FD NOTIFICATION，完成还关联原Message ID。生成或发出通知不证明原发送者已经收到。

规范强度：GET、实际成功后的用户通知及满足条件的处置通知shall。
- 边界：HTTP200是下载事务的证据，SIP200是FD请求处理响应，HTTP201是上传存储位置反馈，三者不能互换。本页不定义下载失败重试或完整通知转送/聚合。
- 边界：只引用24.282中明确的TLS/代理/令牌依赖，不扩称完整传输或端到端密钥校验已实现；服务器收到403等情形不在本客户端主链中构造恢复算法。

## 使用边界
- 这是HTTP FD客户端业务主链，不建立服务器准入、配置schema、存储服务完整实现或通知送达闭环。
- 本页按固定Rel16原文整理，不借其他Release补缺；已有SDS规则不作为FD的替代算法。

服务器如何准入并转送同一请求，见[私聊 HTTP 文件分发服务器](http-fd-server.md)。
