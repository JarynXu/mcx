# 在网 MCData 媒体面文件分发：谁是目标、谁回了应答，能否据此确认收齐文件？

甲向救援组 G 发文件，服务器转回一条带有「甲、G、乙、对话 C、SDP answer」的响应。**甲是原请求者，G 是文件发往的组，乙是这条响应的用户。** 即使请求标了强制下载，这条响应也不能证明乙收齐文件，更不能替组里其他成员确认。要判读这样的记录，先分一对一和组，再分请求和响应。

这里的文件分发（FD）限于 **3GPP TS 23.282 V16.8.0，Rel-16 Stage 2**。[§7.5.2 和 §7.5.2.1，印刷页 81](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=82) 确定在网范围。四表引言分别回指[一对一媒体面程序 §7.5.2.5.2（§7.5.2.5 标题始于印刷页 94）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=95)和[组独立媒体面程序 §7.5.2.7.2，印刷页 99](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=100)。四表都描述客户端至服务器、服务器至另一客户端的信息流。表中的用户 ID 说明业务角色，不是转发服务器的身份。这里的 M、O 是该信息流的必选、可选，不是 HTTP 头或 SIP 报文的编码规则。

**同一对话有两笔事务，响应是哪一笔的？** 假设甲在 C 内给 G 发了两份不同的文件，本笔事务号分别为 T1、T2。请求中的 Conversation Identifier 是 C；Transaction Identifier 标识正在处理的这笔事务；可选的 Reply Identifier 另指本笔正在回复的原事务。例如，T2 带回复标识 T0，本笔仍是 T2，既不会变成 T0，也不必指向时间更近的 T1。这三种标识在两类请求里的含义相同。两张响应表都没有列本笔事务标识或回复标识。假如 T1 和 T2 选定的媒体参数也相同，只凭开头那条响应无法把乙配给其中一份文件。不能因响应少了请求里的事务号就判它缺必选项，也不能反推其他协议层禁止携带用于关联的信息。

**自动接受什么？谁期望什么？** 两类请求都可带 Download indication；它指示强制下载时，要求接收客户端**自动接受本次媒体面建立请求**。请求里有此指示，说明提出了这项要求；它本身不是客户端已执行的记录。另一可选项 Disposition indication 表达是否期望下载完成报告。两者可以分开：甲可以指示强制下载而不要求报告，也可以要求报告而未指示强制下载。请求里期望报告、乙答复选定媒体参数、乙的客户端报告对应文件已下载，是三种证据。前两者都不能替第三者。只缺报告时，也不能倒推出下载失败。核对一人还是多人实际收件，应找与该文件事务及相应接收端匹配的下载完成证据；要确认甲收到了报告，还需甲端收件或同等送达证据。例如，甲端收到一份能对应乙及原文件事务的完成报告，就能记「乙的客户端报告已下完，甲已收到这份报告」。[表 7.5.2.1.7-1，印刷页 83](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=84) 的完成确认针对客户端下载，不表示乙本人已打开或读过文件。

**组请求里的三个可选指示怎么组合？** [表 7.5.2.1.12-1 两条表注，印刷页 85](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=86) 约束信息项是否出现。注 1：紧急指示与迫近危险指示都可以不带，要带至多一个。注 2：只有带紧急指示，才可带告警指示；带紧急指示并不要求带告警指示。告警指示的值表达是否要发紧急告警，不是告警已发送的证明。因此「仅紧急」符合这两条注；「紧急＋迫近危险」、「仅告警」以及「迫近危险＋告警」都不符合。不要把组请求表的两条注搬到一对一请求表：后者列了可选紧急指示，没有列另两项或这两条注。两类请求还都可带发件用户的功能别名和所请求的应用优先级；别名不替代必选用户 ID，请求等级也不是已获准的等级。

**媒体面分发由谁自动应答，发件端何时开传？** 只知道这个问题，还不能选程序。先查这笔请求的目标：若是单个用户乙，查[一对一媒体面分发程序](one-to-one-media-plane-fd.md)（§7.5.2.5.2，步骤 7–9，印刷页 95–96）；若是组 G，查[组媒体面分发与报告](group-media-plane-fd-reports.md)（§7.5.2.7.2，步骤 7–9 及注 1，印刷页 100–101）。例如，组请求带强制下载指示时，收到它的各目标客户端自动回复接受。组程序的注 1 说明服务器转回应答的时点取决于继续传文件的条件，并未规定甲必须等全组应答才开传，也未规定收到第一份应答就一定开传。各成员的下载和报告汇总仍按组程序判断。

**HTTP 请求只有取件地址，能据此选表吗？** 不能。一对一 HTTP 请求和组独立 HTTP 请求都要求内容引用，其中包括取件 URL 和文件元数据。要区分两类请求，查目标身份：若收件目标是一名用户，查[一对一 HTTP 请求表 7.5.2.1.5-1 的字段说明](http-fd-download-report.md)；若为目标组 ID，查[组独立 HTTP 请求表 7.5.2.1.10-1，印刷页 84](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=85)。只剩地址、看不到目标时，两类皆有可能。不要从 HTTP 内容引用推导本页四张媒体面表都必带 URL。若问题与取件方式无关，只想把一份在网下载完成报告对应到原事务，则查[在网完成报告表 7.5.2.1.7-1 的字段说明](http-fd-download-report.md)；这张报告表不限于一对一 HTTP。
