# MCData：文件上传成功，能记成个人通信历史已入库、其他终端已同步吗？

不能。甲把文件传到**内容服务器**，说明的是一次文件传输。要把“甲的个人通信历史已入库”写进记录，得有这段历史已存入**甲的消息存储区**的依据；要写“甲的另一台终端已同步”，还得有涉及那台终端和相应对象的同步结果。文件名相同，不能把三件事合并。

[3GPP TS 23.282 V16.8.0（Release 16，Stage 2）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf) 用四个参考点说明参与的功能和用途。“参考点”在这里表示哪两个功能交互，不是某一条操作成功的记录。判断时先看另一端是谁，再看操作的对象。

| 要查的记录 | 两端及参考点 | 这条记录能说明什么 |
| --- | --- | --- |
| 甲上传文件，或乙从内容服务器下载文件 | 终端（UE）的媒体存储客户端 ↔ MCData 内容服务器的媒体存储功能；**MCData-FD-4**，用 HTTP | 上传、下载针对文件本身。只见甲端上传成功，可以记甲这次上传成功，不能替乙记下载成功。〔[§6.6.4.1.4，印刷页 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35)〕 |
| 业务服务器为甲建目录，或把一段通信历史存进甲的消息存储区 | MCData 业务服务器 ↔ MCData 消息存储；**MCData-8** | 建目录和存通信历史是两种管理操作。建成目录，并不证明某段历史已存入；即使确有该段历史入库的记录，也不能据此断定甲的终端已有本地副本。〔[§6.4.4.1.7，印刷页 26](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=27)〕 |
| 甲的一台终端管理已存信息，或将本地消息存储与网络消息存储同步 | 消息存储客户端 ↔ MCData 消息存储；**MCData-7** | 同步针对特定用户的消息存储。若记录明确甲的手持终端已将指定对象同步到本地，只能确认这台终端上的这些对象；不能推及同一用户的车载终端。〔[§§6.4.3.3–4，印刷页 25](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=26)；[§6.4.4.1.6，印刷页 26](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=27)〕 |
| 业务服务器为组播取文件 | MCData 业务服务器的文件分发（FD）功能 ↔ 内容服务器的媒体存储功能；**MCData-FD-5**，用 HTTP | 业务服务器取的是某个终端的媒体存储客户端先前上传的文件，目的是经多媒体广播多播业务（MBMS）分发。这个参考点还支持为传输控制检查文件大小等操作。大小检查和成功取回文件不是一回事；成功取回文件也不是组成员接收文件的凭据。〔[§6.6.4.1.5，印刷页 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35)〕 |

**同样是 HTTP 下载，看谁在取。** 若乙的媒体存储客户端从内容服务器下载文件，这是 FD-4；若业务服务器的 FD 功能从内容服务器取此前上传的文件以供 MBMS 分发，这是 FD-5。若记录只写“HTTP 取件完成”，既没有取件方，也没写用途，就不能替它选一个参考点。终端侧与内容服务器侧的媒体存储角色分别见 [§6.6.3.1.2，印刷页 32](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=33) 和 [§6.6.3.1.4，印刷页 33](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=34)。

在 FD-5 的上述取件场景里，待取文件先前确实已经上传；这不要求先给用户建消息目录或完成同步。四个参考点不是规定每次传文件都走的四个步骤，也不能用它们的数量推算要部署几台机器。这里只辨认功能和证据，不据此断言某个系统实际记录了哪些动作。

**若要判断具体程序：** 上传与下载如何处理紧急指示，见[HTTP 文件上传与下载](http-upload-download.md)；在网短数据存入谁的账户，见[双方通信的存档](sds-message-store-deposit.md)；收到同步通知后有哪些对象真正回到设备，见[消息存储同步](message-store-sync.md)；组员接受分发后是否收全文件，见[MBMS 组文件分发](mbms-group-file-delivery.md)。
