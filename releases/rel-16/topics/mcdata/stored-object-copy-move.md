# MCData 消息存储：把对象从 A 放到 B，原处还留不留？

假设一条消息已存在本人账户的文件夹 A，想把它放进同一账户的另一个文件夹 B。要保留 A 中的消息，选**复制**；要让它只留在 B，选**移动**。改变的是 MCData 消息存储里的对象位置，不是终端的本地文件夹。

| 操作 | 对目标 B 有什么要求？ | 消息存储报告本次操作成功后 |
| --- | --- | --- |
| 复制 | B 尚未存有这个对象；B 可以已有其他对象。 | A 和 B 都有该对象。 |
| 移动 | B 是同一账户中的另一个文件夹。移动条款没有照抄复制的“目标尚无该对象”条件，也没有规定遇到冲突就覆盖。 | 该对象只在 B，A 不再保留。 |

两种操作都只在用户账户采用文件夹层级时有意义。用户已在消息存储有账户，消息存储客户端与 MCData 消息存储之间已成功完成认证和授权；客户端知道已存对象的标识和目标文件夹的标识。复制的目标限制说的是**该对象**，不能改成按文件名判断，也不能据此指定冲突时的错误码。[3GPP TS 23.282 V16.8.0，Rel‑16 Stage 2，§7.13.3.9.1–2，印刷页 154–155](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=155)；[§7.13.3.10.1–2，印刷页 155–156](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=156)。

**怎样认出一次操作？** 客户端向消息存储发复制请求或移动请求。两张请求表都列三项必填：用户的 **MCData ID**、要操作的**已存对象标识**、**目标文件夹标识**。源端靠对象标识点名，不另填源文件夹 A 的标识；目标填 B 的标识，不填另一位用户的身份。消息存储执行相应操作，再向这个客户端回对应的响应。[表 7.13.3.1.15-1，印刷页 144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=145)；[表 7.13.3.1.17-1，印刷页 145](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=146)；[图 7.13.3.9.2-1，步骤 1–3，印刷页 155](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=156)；[图 7.13.3.10.2-1，步骤 1–3，印刷页 156](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=157)。

**响应说明了什么？** 复制和移动的响应表都只列用户的 MCData ID 和本次操作结果（成功或失败），两项均必填。不返回对象内容，也不列新对象标识。只看到请求不能断定位置已经改变；失败响应也不能按上表的成功结果推定 A、B 的状态。这两节没有说明复制品是否换号、失败如何回滚或其他终端何时刷新。[表 7.13.3.1.16-1、7.13.3.1.18-1，印刷页 145](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=146)。

若想把对象内容取回客户端，见[按标识取回或按条件搜索](stored-object-lookup.md)；若想让终端上的消息存储与服务端同步，见[同步通知、请求与响应](message-store-sync.md)。两者都不是文件夹内复制或移动的必经步骤；复制或移动成功也不等于终端已经收到对象。
