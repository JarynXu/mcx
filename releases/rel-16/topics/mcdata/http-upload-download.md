# MCData HTTP 文件上传与下载：两端分别凭什么设置紧急指示？

甲上传一张示意图，乙随后按文件分发（FD）请求里的链接下载同一张图。虽是同一个文件，甲、乙的媒体存储客户端设置紧急指示时，依据却不同：**上传看甲端已有的紧急状态；下载看乙收到的分发请求。** 这里说的是 Release 16 在网、用 HTTP 存取独立数据文件的两个程序，不是文件本身带有一种会自动传递的紧急属性。

**甲端上传。** 这个示例以甲已注册接收 MCData 服务、内容服务器有能力核查甲的上传权限为前提。“能核查”不是“已经授权”。甲选择文件、发起上传。若此前触发的 MCData 紧急告警已使甲的媒体存储客户端处于 MCData 紧急状态，该客户端就在这次请求中设置紧急指示。仅知道以前有过告警，并不能确定上传时仍处于该状态。〔§7.5.2.2.1、§7.5.2.2.2 前提 1–2，印刷页 89；步骤 1，印刷页 90〕

同一步还要核文件大小，由甲的媒体存储客户端按**准备发起的 FD 请求类型**选择上限。要发组文件，查该组的组配置；要一对一发，查业务配置。假设文件为 6 MB，两份配置的 FD 上限分别为 4 MB 和 8 MB：同一文件用于前者会超限，用于后者则在上限内。这些数值只是例子，通过大小检查也不等于上传成功。

上传步骤 2 说明文件送到哪里：客户端把文件送往内容服务器的媒体存储功能。步骤 3 说明谁负责处理并回复：**内容服务器**在存储前可应用发送控制策略，并向甲的媒体存储客户端返回上传响应，说明成功或失败，成功时附上文件 URL。步骤 3 没有指定由服务器内哪个功能执行策略或返回响应；不能拿步骤 2 的存储去向代填这两个动作的执行者。此时乙即使还没发下载请求，甲也能拿到 URL，不能据此把乙登记为已收件。〔§7.5.2.2.2，步骤 1–3，印刷页 90〕

**乙端下载。** 这个示例也以乙已注册接收 MCData 服务为前提。乙发起下载，其媒体存储客户端按收到的 MCData FD 请求或 MCData 组独立 FD 请求里的 URL，向内容服务器的媒体存储功能要文件。**若收到的那份分发请求已经设置紧急指示**，乙端就在自己的下载数据请求里设置紧急指示。这一步不要求先证明乙本地曾触发告警。反过来，若手头只有甲端上传时的指示、没有乙收到的分发请求，就不能据此判定乙的下载指示。两处条文都给出了满足条件时如何置位，均不能倒过来当作判定其他情况一定不置位的规则。〔§7.5.2.3.1、§7.5.2.3.2 前提 1、步骤 1–2，印刷页 90〕

在下载步骤 3 图示的返回文件情形中，**内容服务器的媒体存储功能**可应用接收控制策略，并向乙的媒体存储客户端返回含文件的下载响应。即便服务器已经发出响应，传送仍可能不完整。此时乙端可以发起部分下载请求，只取缺少的部分。条文没有要求每次中断都自动重试；即使看到乙已请求缺失部分，也不能据此断定文件已经补齐。〔§7.5.2.3.2，步骤 2 后的注、步骤 3，印刷页 90〕

## 在网 MCData 文件下载中断后，怎样判断补齐了？

**先看乙端有没有把原文件恢复出来。** MCData 文件分发服务须支持检测和恢复丢失的数据。接收端宜能发现并报告传输不完整、请求重传，指出并重取缺失部分，再把重传回来的部分与已有内容拼成原文件。这是对服务和接收端能力的两种不同要求，不是每次中断都会发生的经过。例如，乙端只记下“已收到补传片段”，还不能登记文件已补齐；若乙端另有对应这份文件的重建成功记录，就有了乙端完成修复的证据。[§5.4，丢失检测与恢复，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=19)；[§7.5.2.3.2，步骤 2 后的注，印刷页 90](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=91)。

**再看这一次请求和响应各说明什么。** 乙的媒体存储客户端向内容服务器请求下载时，必填的是乙的 MCData ID 和文件 URL，紧急指示可选；若乙收到的分发请求已置该指示，仍按上文在下载请求中置位。传输中断后，乙端可请求缺失部分。至于怎样发出修复请求、怎样在请求中指明缺了哪部分，本版留待研究，没有指定某个 HTTP 范围头。[§7.5.2.1.3，下载请求表及编者注，印刷页 82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=83)；[§7.5.2.3.2，步骤 2 及注，印刷页 90](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=91)。

这里核对的是**在网 MCData 下载数据响应（MCData download data response）**，Result 是业务结果；只有 HTTP 2xx，不能当作这份业务响应报告成功。[§§7.5.2、7.5.2.1，在网文件分发信息流，印刷页 81](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=82)。内容服务器发给乙的媒体存储客户端的这份响应须有请求用户的 MCData ID 和结果（成功或失败）。内容（Content）一栏虽标为可选，但表注要求**成功时必须带内容**。若完整响应明确报成功却没有内容，就不符合这条表注；若手头只是省略正文的日志摘要，则不能判断原响应缺了内容。若结果是失败，表注没有要求也没有禁止返回内容；失败且无内容不违反这条成功条件。服务器如何标明返回的是整份文件还是用于修复的补丁，也是本版未定的事。因此，“成功并带内容”能说明这一次请求的结果，不能单凭这条响应确认乙端已收到整件或重建成功。[§7.5.2.1.4，下载响应表、表注及编者注，印刷页 82](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=83)。

**要把重试次数或加密文件修复写进验收条件吗？** §5.4 把自动重试机制的要求和最大重试次数列为待研究，没规定一中断就重试或重试几次；使用端到端加密时，文件修复也待研究。后者既不保证加密文件能按上述办法修复，也不表示禁止产品提供修复。[§5.4，两条编者注，印刷页 18](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=19)。
