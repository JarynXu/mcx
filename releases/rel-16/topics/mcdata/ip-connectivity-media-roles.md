# 在网 MCData 点到点 IP 互通：从 200 OK 到应用收包，中间隔着哪些隧道？

发起客户端收到建立 IP 互通所用的 200 OK，稍后又记下「隧道已建立」。这两条记录不能合成「对端应用已经收包」：前一条给出建隧道所用的地址，后一条还得看隧道的**另一端是谁**。即便整条媒体路径就绪，也只是两端应用可以交换 IP 数据。以下按 3GPP TS 24.582 V16.3.0（Rel-16，Stage 3）判读在网一对一 IP 互通；[§4.1.4，印刷页 11](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=12) 给出这个范围。

**先找应用，再找隧道端点。** 媒体面的业务端点是收发 IP 数据的应用。应用可以就在装有 MCData 客户端的 UE（用户设备）上，也可以在外接的非 3GPP 主机上。只有后一种部署，§13.1.1 才要求 UE 为与外接主机通信提供第二个 IP 接口，且该接口的 IP 地址独立于 3GPP 系统。接口如何实现由实现方决定；缺少外接接口记录，不能据此否定 UE 内应用这一路径。[§13.1.1，印刷页 44](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=45)

**两端的建隧道起点不同。** 发起客户端收到 MCData 用户请求，**或**收到应用交来的一个 IP 包，即进入 §13.1.2 所指的发起信令程序；该程序的 200 OK 所带的 IP 地址用来建立 GRE（通用路由封装）隧道。触发信令的应用包，并不因此已送到对端。终接客户端则以 §13.1.3 所指的终接信令程序**成功**为开始建 GRE 隧道的触发条件。「程序成功」不是「隧道已建成」。两端客户端都是中继：从应用收到包就封装送入隧道，从隧道收到包就解封装，再交给应用。因此在同一会话内，终接侧应用向回发包时，也是终接客户端负责封装。两条所引信令程序分别是 TS 24.282 的 §20.2.1 和 §20.2.2；这里依据的是 TS 24.582 自身对触发和地址用途的说明，不展开那两条程序。[§13.1.2，印刷页 44](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=45)；[§13.1.3，印刷页 45](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=46)

**哪一段通了？** 沿发起端到终接端的方向，先把记录放回以下逻辑路径。相邻功能是隧道的两端；最外侧的应用与本侧客户端之间不是这里说的 GRE 隧道：

发起应用 ↔ 发起客户端 ↔ 发起侧参与功能 ↔ 控制功能 ↔ 终接侧参与功能 ↔ 终接客户端 ↔ 终接应用。

每一侧的**参与功能**都有两个隧道端点：一个面向本侧客户端，一个面向控制功能。本侧客户端来的隧道已经建立后，该参与功能才按 §13.2 建立通向控制功能的第二段，并在两段间中继 IP 流量。**控制功能**的两个端点则分别面向发起侧、终接侧的参与功能；它中继两边的 IP 流量，不直接把包交给终接应用。「两段」是从一个参与功能看的，不是说整个业务只有两段，也不表示两侧必须按某个全局先后次序建成。[§13.2、§13.3，印刷页 45](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=46)

例如，要确认「终接应用是否收到编号 47 的样本」，可把工单里的证据分开写。以下是记录判读示例，不是协议规定的日志或回执格式：

| 现有记录 | 能把结论写到哪里 |
| --- | --- |
| 发起侧参与功能确认与本侧客户端的隧道已建立；没有控制侧记录 | 这一段已建；规范要求参与功能接着建立到控制功能的隧道。第二段是否建成仍未知，不能因缺记录写成建立失败。 |
| 控制功能已把 47 转给终接侧参与功能；终接客户端的收发记录缺失 | 可确认控制功能对这份数据的转发，不能替终接客户端确认解封装，更不能替终接应用确认收包。 |
| 终接应用有与本次会话及样本 47 对应的接收记录 | 可以确认该应用收到了这个样本；这不替其他样本、反方向数据或整个会话作收件证明。 |

GRE 头的 **Key** 唯一标识**该包载荷所属的 IP 互通会话**。客户端如何设置会话标识，由实现决定。Key 是把记录归到某个会话的线索，不是单包收据、用户身份凭证或加密证明。同一会话内可以有不同的包；只凭相同的 Key，无法认定应用收到的就是样本 47。[§13.1.2、§13.1.3、§13.2，印刷页 44–45](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=45)

要区分**服务器准入**和**目标客户端对本次请求答复接受还是拒绝**，见 [Stage 2 点到点 IP 互通示例](point-to-point-ip-connectivity.md)。只见服务器放行，不能代替目标客户端答复；即便记录了目标客户端答复接受，也不能据此断定用户本人作过决定。该例预设两端各接一台已获准的主机，并非这里唯一允许的应用位置。若记录实际是文件分发产生的 **MSRP** 200，则看[文件分发的服务器转发](msrp-file-server-forwarding.md)，不要把它当作建立 IP 互通所用的 200。
