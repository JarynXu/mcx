# 在网组独立短数据：发往组、发给某位成员和收到该成员的报告，分别看哪条记录？

甲给调度组 G 发了两次交班通知。服务器的发送记录写着「甲、G、乙」，能给乙标上“已读”吗？**不能。这一条说的是数据发往乙，没说乙的客户端报告了什么。** 要在甲端登记一份回报，得知道是谁就哪笔原事务报告了什么，还要确认甲收到了这份报告。

这里的短数据服务（SDS）限于 **3GPP TS 23.282 V16.8.0，Rel-16 Stage 2，同一 MCData 系统内、在网、组独立 SDS 的信令控制面传送**。[§7.4.2 开头，印刷页 44](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=45) 限定系统范围。[§7.4.2.5.1–2，印刷页 61–62](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=62) 的例子假定载荷小于配置的控制面上限；用户属于同一组，已注册接收 MCData 服务并已归属该组。这里的 M（必选）和 O（可选）是信息流表的列值，不是 SIP 头或日志格式。

**同一对话里有两笔，怎样把回报记到正确的一笔？** 两张数据请求表都必列对话、本笔事务、载荷和载荷去向；回复标识（Reply Identifier）可选。设对话 C 中有 T1、T2 两笔，T2 是对更早的 T0 的回复：T2 的本笔事务仍是 T2，回复标识指 T0，不是时间更近的 T1。两张表的处置类型也都可选，用来表达期待交付回报、已读回报或两者；期待哪一种，并不表示已有那种结果。

通知表用的是**处置关联（Disposition association）**，它指向被报告的原事务。通知表列五项，全部 M：通知发给谁、由谁报告、对话标识、处置关联、处置结果。没有另列通知自身的事务号、请求中的回复标识或组 ID。要还原组，可回查对应原请求的目标组；不能说通知表本身给出了 G。表中没有某行，也不表示线上其他协议层禁止携带相关信息。

例如甲端收到「甲、乙、C、T1、已送达」，可以登记“甲收到乙关于 T1 的送达报告”。不能据此给 T2 登记，不能把“送达”改成“已读”，更不能给丙记任何结果。若处置结果为“已读”或“两者”，就按原值登记乙对 T1 的报告。协议报告不是对某人亲自阅读或理解内容的独立观察。只见请求或未见回报，既不能宣布送达，也不能判传送失败。[请求两表及通知表，印刷页 48–49](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=49)

**为什么是服务器发报告，报告人却是乙？** [§7.4.2.5.2 步骤 6–9，印刷页 63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=64)：若甲要求送达回报，由接收客户端发起送达报告；若要求已读回报，接收用户读后才由接收端发起已读报告。服务器可以存储报告，也可以汇总，然后向请求者发送逐份或汇总的通知。表 .9 描述的是最后一段，不是乙端向服务器发起的那一段；未汇总也不是客户端直连。一份汇总只能支持其中能匹配到的成员、原事务和结果，不用“汇总”二字替缺席成员签收。

**“发给组 G”“发往乙”和“交给应用”是三个问题。** 两张数据表的载荷去向（Payload Destination Type）都是 M，区分供 MCData 客户端还是应用使用。应用标识（Application identifier）是 O，两表注 3 都限定：仅在去向为应用时才可带；不是凡交应用都必带。因此，去向为应用且无应用标识，不能单据该行判缺项；去向为客户端却带了应用标识，不符合表注。用户身份既不代替载荷去向，也不代替应用标识。两表还可带原发件用户的功能别名及位置，均非本次收件人 ID。若材料只是经过筛选的日志，先查它保留哪些字段，再判断完整信息流是否缺项。[两表的载荷行及注 3，印刷页 48–49](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=49)

**紧急、迫近危险和告警能怎样组合？** 对这两张组请求表，注 1 允许紧急与迫近危险都省去；使用时至多一个。注 2 只允许在紧急指示出现时带告警指示，反过来并非必然。通常的表内判读是：“紧急＋告警”符合这两注；“紧急＋迫近危险”或“迫近危险＋告警”不符合。告警指示表达是否要发紧急告警，不是告警已经送达。程序还有条件：发起紧急通信时按规定带紧急指示；是否须设置告警指示取决于发起时是否配置发送告警。选项在一般表中标 O，不表示在满足特定程序条件时仍可随意省略。[请求两表注 1–2，印刷页 48–49](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=49)；[§7.4.2.5.2 步骤 2、4，印刷页 62–63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=63)。
