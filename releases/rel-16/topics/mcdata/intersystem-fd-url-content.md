# 跨系统分发文件：两个 MCData 业务服务器交换了 URL，文件本身走哪条路？

在**主系统与伙伴系统互联的在网文件分发**中，先问记录的两端是谁。两个 **MCData 业务服务器**可以分享文件的上传或下载地址；两个 **MCData 内容服务器**可以分享文件正文和元数据。前者告诉对方用哪个地址，后者才涉及两个存储端之间的内容。把同一个文件名或 URL 在两处对上，还不能把两次操作合成一次下载。[3GPP TS 23.282 V16.8.0，Release 16，Stage 2，§6.6.1a 图 6.6.1a-1 及图后说明，印 31](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=32)

**共享地址：看 MCData-3 和 MCData-9。** 沿图从主系统读到伙伴系统，是“主业务服务器的 FD 功能 ↔ 主 MC 网关 ↔ 伙伴 MC 网关 ↔ 伙伴业务服务器的 FD 功能”。两头各自系统内的一段标 **MCData-3**，中间两网关之间标 **MCData-9**。上传和下载是 URL 的用途，不是分段依据，不能按“上传走 -3、下载走 -9”分工。图上的连线是功能关系，不是三条消息的时序。若伙伴业务服务器确实收到了 X 的上传地址，可以登记它已收到地址；这不证明 X 已经上传、已存到伙伴内容服务器或已被某台终端下载。[§6.6.1a 图及 URL 说明，印 31](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=32)

**共享正文或元数据：看 MCData-FD-6。** 这个基于 HTTP 的参考点连接主、伙伴两个内容服务器。若伙伴内容服务器只记录了收到 X 的元数据（例如文件大小），只能确认收到了该项描述；它不能证实或否定 X 的正文另有传输。若记录明确证实伙伴内容服务器已完整收到 X 的正文，便可确认 X 到了伙伴内容服务器，仍不能替乙的终端登记“已下载”。条款说明可以共享哪些对象，不规定每个 URL 必触发一次 HTTP 请求，也不要求元数据和整个正文在同一次请求中传完。[§6.6.1a 图及 FD-6 说明，印 31](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=32)

同样一条“HTTP 取件”日志，换了端点就可能是另一件事：

| 已查明的两端与用途 | 查哪个参考点 |
| --- | --- |
| 主、伙伴内容服务器之间共享文件正文或元数据 | **MCData-FD-6** |
| 乙终端的媒体存储客户端向伙伴内容服务器的媒体存储功能下载文件 | **MCData-FD-4** |
| 业务服务器的 FD 功能向内容服务器的媒体存储功能取回终端先前上传的文件，供 MBMS 组播分发 | **MCData-FD-5** |

只有 HTTP 或某个代理的 IP，还不能选其中一行。先找操作两端的功能，再查对象、方向和接收结果。若两端是客户端与业务服务器的 **FD 功能**，应看[FD-1、FD-2、FD-3 的用法](fd-reference-points.md)；这里的 **MCData-3** 也不是下行组播的 **MCData-FD-3**。终端和业务服务器对存储的不同访问见[文件存储与消息存储](message-store-vs-file-storage.md)及[§§6.6.4.1.3–5，印 34](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=35)。

**为什么两条路径上都看得到代理？** 图中两个系统各有 HTTP 代理，位于信令面，用于在系统间隐藏拓扑和 IP 地址。图上它们在 FD-6 路径中，却不是共享文件的两个内容服务器。MC 网关在 MCData-3/-9 这条路径上，连接的是不同信任域。以主系统甲与伙伴系统乙互联为例：网关为**乙的一台或多台 MCData 业务服务器**做代理；甲无须为此把**甲自己的 MCData 业务服务器暴露到甲的信任域外**。被代理的是乙侧的业务服务器，不必向域外公开的是甲侧的业务服务器。这说明互联不以暴露甲侧服务器为前提，不能用来证明某套部署从未泄露地址。网关转送呼叫控制、传输控制信令及媒体；MCData 业务服务器也可承担网关角色。功能不同不等于必须分机器部署。图不能证明某产品由哪台主机终止 TLS、执行鉴权或缓存文件。[§6.6.1a，图及 HTTP 代理说明，印 31](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=32)；[§6.4.3.1.5，印 25](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=26)

**-3 和 -9 只许发地址吗？** 不只。按通用定义，MCData-3 是 MCData 服务器间的参考点，建会应用信令的传送与路由须用 SIP-2；两服务器由不同 SIP 核心服务时，还须用 SIP-3。MCData-3 也传媒体。MCData-9 连接互联系统的两个 MC 网关，建会应用信令的传送与路由须用 SIP-3；应用数据太大、无法在信令面传递时，-9 也承载这种数据。所以，不能只因互通文件图写了 URL，就把 -9 上的大应用数据判作违规；反过来，这项能力也不是文件 X 的正文经过 -9 的实证。这些建会规定没有指定某次 URL 交换采用哪种 SIP 方法或头域。[§6.4.4.1.3，印 25–26](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=26)；[§6.4.4.1.8，印 26](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=27)

**要验收“乙已下完 X”时，换到具体程序。** [跨系统一对一 HTTP 文件分发](cross-system-http-file-distribution.md)的示例从文件已上传到主系统、尚未在伙伴系统下载开始。伙伴内容服务器仅在本地没有该文件时才向主内容服务器取件；它可保留本地副本供后续请求使用。后续下载若命中仍可用的副本，没有本次跨系统取件并不反常。确认乙收到全件，查乙端与 X 对应的下载完成记录；若还要确认发件端知道结果，查发件端是否收到与乙和 X 相符的完成报告。程序只在初始请求要求报告时才发起报告，未见报告不能改判下载失败。链接加工、缓存和报告转送的步骤由该程序说明，不是每一次 FD-6 交换都要做。[§7.5.2.4.3，适用场景及前置条件，印 92](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=93)；[步骤 10–16 及注 4，印 94](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=95)
