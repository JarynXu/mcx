# 一对一文件分发途中升级紧急：对端回执能证明双方承载已调整吗？

不能。对端客户端确认的是**收到升级请求**。调整双方底层承载优先级是 MCData 服务器接下来的动作，服务器随后才向发起客户端发升级响应。双方继续原有的文件分发（FD），但这次通信已转为紧急一对一 FD；两条升级响应都不是文件下载完成报告。〔§7.5.2.11.2，步骤 5–8，印刷页 106〕

**哪些传送可以用这套流程？** 发起升级的用户须有相应授权；两名参与者属于同一 MCData 系统，一对一 FD 已按 §7.5.2.5 通过媒体面建立，并且仍在进行。条件缺一不可。不能用它解释[跨系统的一对一 HTTP 文件分发](cross-system-http-file-distribution.md)，也不能把[组 FD 升级](group-fd-emergency.md)的规则搬来。〔§7.5.2.11.1；§7.5.2.11.2 开头及前提 1–2，印刷页 105〕

**从发起到继续传送，谁做什么？** 设甲发起升级，乙是对端。
1. 甲的用户发起紧急事件。甲客户端设置自己的 MCData 紧急状态，向服务器请求升级这次一对一 FD。服务器把升级请求发给乙客户端，乙的用户获知这次通信正在转为紧急通信。〔§7.5.2.11.2，步骤 1–4，印刷页 106〕
2. 乙客户端向服务器回送升级响应，确认的是这次请求。服务器随后调整甲、乙双方的底层承载优先级，再给甲客户端发升级响应。因此，只看到乙发出的那条响应，还不能断定服务器已完成调整；乙的用户获知紧急情况也不等于其手动批准了升级。〔同条，步骤 4–7，印刷页 106〕
3. 甲、乙客户端继续这次通信，传送没有因为升级而重新开始。此时的业务是紧急一对一 FD，不是文件已经传完。〔同条，步骤 8，印刷页 106〕

**哪项状态在什么时候结束？** 甲客户端在步骤 1 设置的本地紧急状态，保留到**显式取消**。服务器在步骤 6 调整的是这次通信中**双方底层承载的优先级**，调整后的优先级保持到**此次通信结束**。因此，得知 FD 已结束，不能据此认定甲已显式取消本地状态；反过来，只知道甲本地已取消，也不能据此断定这次 FD 已结束。本条没有让乙在确认请求时也设置与甲相同的本地状态。〔同条，步骤 1、4–6、8，印刷页 106〕

来源：[3GPP TS 23.282 V16.8.0，Release 16，Stage 2（ETSI，2021-01），§§7.5.2.11.1–2，印刷页 105–106](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=106)。这里区分的是业务流程中的角色和动作，不据此指定承载优先级数值。
