# MCData 文件分发：选了“强制下载”，服务器还查什么？

**服务器仍要检查这次发送。** 在网文件分发（FD）把两个决定分开：发送者能否向选定的用户或组发送，由发送端检查权限，MCData 服务器再核准本次请求；收件人能否推迟或拒绝下载，则取决于发送者是否选择强制下载。强制指示不是发送许可，也不是下载完成回执。[3GPP TS 23.282 V16.8.0，Rel-16，Stage 2，§§7.6.2.3–4，印刷页 117–120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=118)。

| | 强制下载 | 由收件人同意下载 |
| --- | --- | --- |
| 开始前已配置什么？ | 用户有发送权限；管理员已设 FD 的最大数据大小，还设有用户单次请求的数据量上限和传送时长上限。 | 用户有发送权限；已设用户单次可传的数据量或时长上限，以及待投递数据的暂存期限。 |
| 发送端怎么做？ | 用户选文件和目标，并选强制下载。客户端核对用户的发送权限，计算请求总大小，选择分发过程，发出的请求**带**强制下载指示。 | 用户也选文件和目标，但不选强制下载。客户端核对权限，还明确检查数据未超过允许大小，再计算请求总大小，选择分发过程；请求**不带**强制下载指示。 |

两种模式的服务器都要核对用户是否获准发送、数据大小及单次传送时长是否符合限制。发送者可以使用功能别名；若请求里带了别名，服务器还核对该用户能否使用它、它是否已为该用户激活。客户端不必有别名；服务器也只是可以订阅别名状态更新。[强制：§7.6.2.3.2 的前提、图 7.6.2.3.2-1 步骤 1–3，页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=118)；[非强制：§7.6.2.4.2 的前提、图 7.6.2.4.2-1 步骤 1–3，页 119](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=120)。

## 发送端收到控制指示，能判断什么？

服务器可向发送端发出相应的控制指示。**没有向目标发送的权限**与**所选组没有已归属成员**是不同原因；后者不等于组里没有登记成员。单次请求的数据量超限，服务器拒绝该请求并指明大小超限。**时长超限的拒绝在本版两段流程中的适用范围不同**：强制下载步骤 4c 列了这项拒绝，未加业务类型限定；非强制步骤 4d 却明写仅适用于数据流传输（DS）。不能因为两边都检查时长，就断言非强制 FD 也按该项拒绝。

服务器也**可以**把当前请求放进队列，留待稍后传送。它发给发送端的排队指示只说明这笔请求已入队，不是拒绝，也不要求发送端重新提交。文件是否已经转给收件人，不能用入队来证明。控制指示表中的用户 MCData ID、会话标识、事务标识和指示类型均为必填；类型取相应原因之一，并非每次依次发送五种指示。[表 7.6.2.1.1-1，页 115](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=116)；[强制步骤 4–5，页 118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=119)；[非强制步骤 4–5，页 119–120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=121)。

## 文件发给谁？没人回应又说明什么？

服务器继续传送时，目标是选定的一名用户；若发给组，通常是该组**已归属的成员**，在无损通信（lossless communication）条件下才是该组的**全部成员**。若有可用的发起方功能别名，也随数据传递。强制模式下，接收客户端自动接收；非强制模式下，用户可接受、推迟（不响应）或拒绝（例如删除通知项）。非强制步骤 5 虽写客户端**可以**自动接收，但没有取消用户的选择。两种模式中的发送对象都不是成功下载者名单。[§7.6.2.3.1 及图 7.6.2.3.2-1 步骤 5，页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=119)；[§7.6.2.4.1 及图 7.6.2.4.2-1 步骤 5，页 119–120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=120)。

非强制分发时，收件人暂时不可达、网络拥塞或用户推迟下载，服务器**可以**暂存数据，并可通知收件人取回。周期通告定时器到期时，等待下载的接收端收到的清单列的是待取数据的引用，不是文件本身。**暂存数据本身过期**则是另一件事：服务器可以清理数据，也可以告知收件人该项已不可下载。不响应不能证明一定已暂存，收到清单也不能证明已下载。[§7.6.2.4.2 步骤 6a–b，页 120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=121)；[表 7.6.2.1.2-1，页 115](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=116)。

接收端主动[查询暂存的组数据](deferred-group-list.md)是另一个程序，§7.6.2.5.1 的“仍待研究”（FFS）指那项查询，不是给这两种发送模式下的结论。若要判读私聊 HTTP 文件分发中的 URL、终端应答和实际下载结果，见[HTTP 文件分发客户端](http-fd-client.md)。
