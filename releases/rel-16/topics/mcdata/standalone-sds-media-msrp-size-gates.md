# 在网独立短数据走媒体面：同一个 MSRP 403，该查哪个大小上限？

**先查谁生成了 403。** 一对一独立短数据（SDS）用媒体面发送时，发起参与功能查发送方的用户配置档，控制功能另查业务配置。两处超限都可见同一个 MSRP 403。客户端收到 O-PF 发来的 403，不代表它是 O-PF 生成的：O-PF 也会转送实际收到的 CF 错误。

这里查 TS 24.582 V16.3.0（Rel-16，Stage 3）的在网独立 SDS：一笔消息用 MSRP SEND 传送。O-PF 是发起侧参与功能，CF 是控制功能。按这笔 SEND 的实际收件和应答角色判断，不按节点名称或部署位置猜。不是建立后可持续交换数据的 SDS 会话，也不是 SIP 控制面请求。[§4.1.1，印刷页 10](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=11)；[§5.1.1，印刷页 11](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=12)。

## 谁实际收到 SEND，谁查哪一项？

| 实际收件和业务类型 | 必须通过的大小检查 | 不通过时 |
| --- | --- | --- |
| O-PF 收发起客户端的 SEND；一对一独立 SDS | SDS 消息大小不超过发起客户端所属用户配置档的上限。原文印作 `<MacData1To1>`。 | 向发起客户端回 MSRP 403，停止本程序，不走后续建立或复用 CF 连接和转送。 |
| CF 收 O-PF 的 SEND；一对一独立 SDS | SDS 消息大小不超过 MCData 业务配置的 `<max-data-size-sds-bytes>`。 | 向发送该 SDS 的 MCData 客户端回 MSRP 403，停止本程序，不走后续 200 或终接转送。 |
| CF 收 O-PF 的 SEND；组独立 SDS | 分别查组文档的 `<mcdata-max-data-in-single-request>` 和 `<mcdata-on-network-max-data-size-for-SDS>`，SDS 消息大小须同时不超过两项。 | 任一检查不通过，向发送该 SDS 的客户端回 MSRP 403 并停止。不能用上两行的一对一门槛代替。 |

**恰好等于上限，不触发该项的 403。** 第一行通过只说明这次 O-PF 检查通过，不能替 CF 的检查。同一条 SDS 可通过用户档的上限，却超过业务上限。O-PF 这一款的用户档检查只写了一对一独立 SDS，不给组独立 SDS 另加同一条规则。[§6.2.1.4.3 第 1–4 项，印刷页 21](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=22)；[§6.3.1.3 第 1–4 项，印刷页 24](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=25)。

**追这次 403，要区分本地产生与转送。** 若 O-PF 没过用户档检查，按本程序就不会把这笔 SEND 转给 CF；若 O-PF 实际收到 CF 的错误响应，则要转给发起客户端。CF 的拒绝条款写的是向发送 SDS 的客户端回复；O-PF 的转送条款以**实收 CF 错误**为条件。不从这两句补出每种部署的固定回程，也不把任何 CF 错误都认成业务配置超限。CF 的建连条款提到没有 O-PF 时可对客户端，但这里的 CF 消息处理条款字面从收到 O-PF 的 SEND 开始；不要自动改写那个收件条件。[§6.2.1.4.3 后两段，印刷页 21](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=22)；[§6.3.1.2.1 和 §6.3.1.3，印刷页 23–24](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=25)。

## 走到 200，能确认什么？

CF 通过适用的大小检查后，向 O-PF 生成并发送本跳 MSRP 200；随后按第 5 项，只向**已成功建立 MSRP 连接**的终接客户端转送。成功连接是转送对象的条件，不是 CF 发 200 的条件。若没有符合条件的终接连接，不能凭 200 把任何终端记成已收到。O-PF 实收 CF 的 200 时向发起客户端转送。若终接参与功能收到 CF 的 SEND，它也先回自己的 200 再向客户端转送。这些响应、终端实收和已读分别需要证据。[§6.3.1.3 第 4–5 项，印刷页 24–25](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=25)；[§6.2.1.4.3 后段与 §6.2.1.5.3 第 1–2 项，印刷页 21](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=22)。

## 看到相近的字段或状态码，先确认是不是同一个程序

- 服务器两款写的是 **SDS 消息大小**。它们没有规定怎样从整个 MSRP 报文或单个分块算出这个大小，也没有定义字段缺失时的默认值。选择信令面还是媒体面是另一问题。建连用的空 SEND 的 200 也不是后续发送这条 SDS 的应答。[§6.1.1.1–§6.1.1.2.1，印刷页 12–13](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=13)。
- 会话内客户端 §6.1.2.4 印作 `<MaxData1To1>`；与第 21 页 O-PF 条款的 `<MacData1To1>` 保留区分。这不能替换成同名配置或断定实现都认哪种拼写。会话内的服务器 SEND 处理没有重复这两个独立发送的 403 尺寸检查，不据此取消会话内客户端自己的逐条许可和上限。[§6.1.2.4，印刷页 18](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=19)；[§6.2.2.4.3，印刷页 22–23](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=23)；[§6.3.2.3，印刷页 26](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=27)。

若只查一对一独立 SDS 怎样选信令面或媒体面，且两端在同一 MCData 系统、都已注册接收 MCData 服务，要发的是一条面向人的单向消息，查[两条传送路径与接受证据（Stage 2）](one-to-one-standalone-sds.md)。若手里实际是普通在网、直接 MCData ID 寻址的一对一独立 SDS 的 **SIP 控制面**服务器拒绝，查[控制面服务器准入](sds-control-server.md)，不把其中 Warning 码带到 MSRP。若是普通在网、直接 MCData ID 寻址的按需一对一 **SDS 会话内**的 MSRP，且符合该页部署和收件条件，查[会话媒体服务器](sds-session-media-server.md)。以上入口都不替本次媒体面收件或终端交付提供证据。
