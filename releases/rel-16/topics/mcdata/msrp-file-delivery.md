# MCData 用 MSRP 发文件：发送端收到最后一个 200，谁已收齐？

**仅凭发送端的记录，不能确定哪个接收端已收齐。** 在分块传送中，发送端收到最后一个 MSRP 200（OK），应终止 SIP 会话。要确认乙的客户端下载完成，应看乙客户端向信令面给出的下载完成指示。两者观察的是不同端、不同事件。[3GPP TS 24.582 V16.3.0，Release 16，Stage 3，§7.1.2.1，印刷页 29](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=30)；[§7.1.3.2，印刷页 30](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=31)。

**首个 200：可以开始发送，不是已经送达。** 一对一和组文件分发都适用。用户或用户应用请求分发文件后，由发起客户端建立媒体面。没有获准发送数据的客户端**不宜**使用发起程序（should not），并非这里规定了绝对禁止。发送文件的一方未必是建立传输连接的主动端；接收方也可作主动端。在各自连接上，作为主动端的客户端须发一个空的 MSRP SEND，让被动端将连接绑定到 MSRP 会话。这个空请求不承载文件。发起客户端收到对第一条 MSRP SEND 的 **MSRP** 200 后才可以发送文件；这不是携带 SDP 应答、供它建立连接的 **SIP** 200。传文件的 SEND 才携带整个文件或其中一部分。[§§7.1.1、7.1.2.1，页 29](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=30)；[§7.1.3.1 建连第 2–4 项，页 30](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=31)。

**分块发送：每条 SEND 都要等其 200。** 发起客户端按需用后续 SEND 发送其余内容，须等到每条已发 SEND 对应的 200；收到最后一个 200 时，须按规定终止 **SIP 会话**。这是分块成功分支的收尾，不是接收端报告下载完成。若记录未说明是否分块，不能把这项收尾规则直接套到一次未分块的成功发送上。[§7.1.2.1 分块段第 1–3 项，页 29](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=30)。

**某条 SEND 得到非 200，怎么办？** 发起客户端须按规范引用的 MSRP 错误规则处理。若还有分块待发，应停止发送那些分块；它还须告知 MCData 用户本次文件未能分发，并按规定终止 SIP 会话。即使已无余块，后两项仍适用。这里没有给出 SIP 终止的具体信令步骤。[§7.1.2.1 非 200 段及第 1–3 项，页 30](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=31)。

**接收端：交给应用和通知信令面，各看什么条件？** 乙客户端发现 SEND 使用分块时，必须等余块全部到齐，重组成完整文件，再把内容交给应用；先到的一块不能作为整份文件交付。乙客户端还须解码文件的 MIME 正文，全部分块成功接收后，向信令面指示下载完成。假设是组分发，只看到乙的这条指示，可以记“乙客户端下载完成”，不能据此记“乙用户已读”或“全组已收齐”；对其他成员是未知，不是已确认失败。[§§7.1.3.1–2，页 30](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=31)。

若问题是收件人能否推迟或拒绝下载，见[在网文件分发的强制下载和同意下载](mandatory-consented-file-distribution.md)；通过 URL 下载文件，见[HTTP 文件分发客户端](http-fd-client.md)。两者都不能代替本次 MSRP 客户端的收发记录。
