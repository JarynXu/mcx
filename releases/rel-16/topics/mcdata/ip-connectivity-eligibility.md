# MCData IP 互通：有资格参加，就能建立连接吗？

不能只看配置里有没有这个人。**支持 IP 互通且获授权的客户端仍能屏蔽入站请求；服务器也可以限制数据量或使用时间。** 对于一次在网点到点请求，服务器放行、目标客户端接受、应用实际收到数据是三个不同的结果。

这里查 3GPP TS 23.282 V16.8.0（Rel-16，Stage 2）的 IP 互通能力，以及在网用户配置和点到点请求中相邻的条件。

## B 有权接收，还能拒接 A 吗？

能。B 的 MCData 客户端既支持 IP 互通又获授权时，可以按需屏蔽入站 IP 互通请求，也可以提供一份排除发起方的名单。名单用 **MCData ID** 标识被排除的发起方；有相应功能别名时，也用该别名。知道 B 有权接收，不能反推 B 没有屏蔽这次请求。要判断是否实际命中屏蔽，得查本次记录。这里没有规定名单与其他许可的判定顺序，也没有给屏蔽指定响应码。[§5.11，印刷页 21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=22)。

**配置档上的候选名单是另一回事。** 在网用户配置表 A.3-2 有一组 IP 互通参与数据。它列出可纳入会话的 MCData 用户；各用户项下列其 MCData ID、该 ID 安全域的 KMS URI、以及关联数据主机的 IP 信息列表。注 9 说 IP 信息可含地址、子网掩码、网关和 DNS 设置。这里的“可纳入”不是上一段的排除名单，也不是一次会话的实际准入结果。

表里写着“获授权参加 IP 互通会话”的那一行，下边还有子项。按 A.1，它只用来归组，本身不取值。标 Y 的参数须配置给对应列的实体；这四列是 MCData UE、MCData 服务器、配置管理服务器、MCData 用户数据库。四个 Y 不是“这个用户已获准接通”，也不证明这四处已收到了某个值。若问题是**某个组有没有启用 IP 互通**，查[A.4-1 组配置与归属](affiliation-configured-subservices.md)，不拿个人配置表的列值代替该组的实际配置。[A.1，印刷页 169](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=170)；[表 A.3-2 标题，印刷页 174](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=175)、[列头，印刷页 175](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=176)、[IP 互通行和子项，印刷页 177](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=178)、[注 9，印刷页 178](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=179)。

## 授权过了，还要查哪种额度？

服务器**可**支持两类限制：对授权客户端间的 IP 数据总量按发送、接收分别设限；对使用时间设限，例如限制总分钟数，或规定可交换数据的起止时段。条文没有要求所有部署都开启，也没规定收发额度相等。点到点建立示例从**配额不阻止本次建立**开始；若已知本次被额度阻止，不能套用示例的放行路径。[§5.11，印刷页 21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=22)；[§7.14.2.2.2 前提，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)。

例如，A 建议连 10 分钟，B 接受但没回协商时限。请求中的**建议时限**和响应中的**协商时限**都是可选字段，和服务器的时限策略不是同一项。不能从没填协商时限断定本次不限时，也不能拿 A 的提议当双方的约定。§5.11 没有规定额度怎么算或达到上限时回什么。[表 7.14.2.1.1-1 与 7.14.2.1.2-1，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)。

## 名单上的身份与主机地址，分别拿来判断什么？

- **别名不替代点到点请求的必填项。** §7.14.1 说，寻址时 MCData ID 和功能别名可各自使用，关联机制由服务器提供。具体到本版的**点到点请求表**，发起用户、目标客户端的 MCData ID 都是 M（必填）；发起用户的功能别名是 O（可选）。只有 B 的别名，不能据通用寻址段落删去这张表要求的目标 ID。[§7.14.1，印刷页 165](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=166)；[表 7.14.2.1.1-1，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)。
- **传输服务和主机的地址分别分配。** IP 互通传输服务管理自己需要的地址池；这个地址分配与附接数据主机自己的地址分配独立。点到点例子里，两台附接主机已经有自己的 IP 地址，也已获准使用所在客户端。用户配置有对应的主机 IP 信息，不等于这两个地址由同一处发放，不代表本次已经分到业务地址或建成媒体面。[§5.11，印刷页 21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=22)；[§7.14.2.2.2 前提及注，印刷页 167](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=168)。

## 查本次连接，用哪一页？

要按 §7.14.2.2.2 的在网点到点示例判断，先核对这些前提：两端客户端同属一个 MCData 系统且都支持 IP 互通，各接一台已有 IP 地址、获准用本侧客户端建立 IP 互通的数据主机；时长或数据量配额不阻止本次建立；MCData 服务器已向本 MC 系统内的 MCData 功能别名控制服务器订阅功能别名激活和停用两种更新；发起客户端已知目标主机 IP 地址与目标客户端的对应关系。 只订阅一种更新、只见其他目录的通知，或不知道订阅来源，都不能认定本例前提齐备。 这是本版点到点示例的前提，不是所有 IP 互通服务的准入规则。订阅存在不证明请求已获准，也不让请求中的发起方别名变成必填。 前提齐备后，再查[在网点到点 IP 互通](point-to-point-ip-connectivity.md)，分别核对发起用户的发送权限、目标客户端的接收权限和实际答复，再看后来是否建立媒体面。 [§7.14.2.2.1–2，范围和额度前提，印刷页 166](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=167)； [§7.14.2.2.2，主机、同系统、别名订阅和地址对应，印刷页 167](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=168)。

若实际查的是**在网一对一 IP 互通媒体面**中哪段通了、应用是否收到数据，读[媒体面与收包证据](ip-connectivity-media-roles.md)。那里也包括应用位于 UE 内的情况，不套本处 Stage 2 例子的附接主机或订阅条件。§5.11 支持一对一和组传输，但不能把这个点到点示例当作组建立流程。[§5.11，印刷页 21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=22)。

客户端申请 IP 互通传输服务时带关联的 QoS 要求和通信优先级。§5.11 的编辑注仍把四件事留待研究：获授权用户撤回 IP 互通连接、远程发起、按逐包优先级控制 QoS、IP 互通对互操作的影响。不能用这些注解判定某实现不支持，也不能从一般通信流程填入本版未定的 IP 互通步骤。[§5.11 编辑注，印刷页 21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=22)。
