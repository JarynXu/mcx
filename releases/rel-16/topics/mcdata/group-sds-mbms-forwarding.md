# 在网 MCData 组短数据：终接参与功能两次回了 MSRP 200，就组播了两份吗？

同组的甲、乙都在监听 MBMS 媒体子信道 S。日志显示，终接 MCData 参与功能先后对两份 MSRP SEND 回了 200 OK。这两份 SEND 属于同一条业务短消息。**两次应答不能算作两次组播；同一条业务短消息也不能算作只须组播一次。** 参与功能查的是：封装**当前这份 SEND** 的媒体包，是否已经在 **S** 上发过。两个 200 都不能证明甲、乙的终端收到了包，或用户读过内容。

**先认清应答的两端。** 已建立的在网 MCData 组 SDS 会话采用 MBMS 媒体面投递时，终接参与功能分别与控制 MCData 功能、终接 MCData 客户端建立 MSRP 会话。规范分别指向 §6.2.2.5.1 和 §6.2.2.5.2；不是说控制功能与客户端建立了一条直达会话。下文的正常 200 是参与功能自己针对收到的 SEND 发给控制功能的，不是替终端转交收件回执。[TS 24.582 V16.3.0，Rel-16，Stage 3，§6.5.3.1 及 §6.5.3.3 步骤 1，印刷页 28](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=29)

**重复通告映射，不等于重复传短数据。** 这里有个前提：已经建立的在网组 SDS 会话采用了 MBMS 媒体面投递。如果会话从头到尾只用单播、从未启用这项映射，就不能仅凭「组会话已结束」要求它也发 MBMS 解映射通告。[§6.5.1 的非规范性背景及注 3（印刷页 26–27）](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=28)区分了两种投递方式。

采用 MBMS 投递时，参与功能发出的 Map Group To Bearer 说明哪条 MBMS 承载（用 TMGI 标识）承载哪条媒体流、属于哪个 MCData 组。它在**通用** MBMS 子信道上按短间隔重复发送 Map，具体间隔由实现决定。会话结束时，参与功能生成对应的 Unmap Group To Bearer，也在通用子信道上发送。该款没有要求 Unmap 按 Map 的节奏重复，也没有规定 Unmap 只能发一次。看到多份相同 Map，只能据此辨认映射通告，不能证明有新承载、新短数据或终端已处理通告。[§6.5.3.2，印刷页 28](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=29)

**对每份 SEND，先看能否走组播，再检查这个子信道上是否已发。** 下面的 200 和去重规则有两个共同前提：终接参与功能判定这份 SEND 适合 MBMS 投递，且它发往正在监听相应媒体子信道的客户端。任一项不满足，注 1 把它归到单播 SEND 处理；不能从这个组播步骤推断单播如何应答，也不能把不监听等同于消息被丢弃。两项都满足时，参与功能先向控制功能回复 MSRP 200，然后检查封装该 SEND 的媒体包是否已在该子信道上传送：
- **该媒体包已在本子信道发过：** 丢弃本次收到的 SEND，不为它在这个子信道上再发一包。丢弃的是这份输入，不是否定先前那次发送，也不撤销这次 200。
- **该媒体包未在本子信道发过：** 构建承载该 SEND 的媒体包，并在已发 Map 的 TMGI 所标识的 MBMS 承载上传送。若只知道在另一个子信道上发过，还不能断定本子信道也发过；反过来，也不能把记录缺失当作确定未发。

回到甲、乙。假定参加组播的两个条件都满足，第一份 SEND 的对应包原先未在 S 上发过，而且已有记录证实它随后在 S 上发出。如何解释第二个 200？

| 关于第二份 SEND 还知道什么？ | 能怎样判断第二次处理？ |
| --- | --- |
| 只知道它与第一份属于同一条业务短消息，或文字相同 | 仍不能选分支。业务消息相同，不等于封装当前 SEND 的媒体包已在 S 发过。 |
| 独立记录确认：封装第二份 SEND 的媒体包，正是已经在 S 发过的那个 | 回复 200 后丢弃第二份 SEND。两次应答，只需第一次那一份新组播。 |
| 明确查到：封装第二份 SEND 的媒体包此前未在 S 发过 | 同样回复 200，但要为第二份构建并传送媒体包。该发送义务本身不等于日志已记录第二包实际发出。 |

为什么只对短消息内容不够？[§6.5.1 注 1（印刷页 27）](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=28)的非规范性说明明确，MBMS 投递也支持 MSRP 分块；不能假定每份 SEND 就是一整条业务短消息。§6.5.3.3 没有规定用哪些字节或标识来配对历史记录。只见另一子信道发过对应包，S 上的历史仍未知，结果也未知。即使在 S 上查到了实际发送记录，终端是否收到、用户是否读过，还需要相应一端的证据。[§6.5.3.3 首段、注 1 和步骤 1–4，印刷页 28](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=29)

**还有两件事不能从 200 反推。** 一是单播下行承载的状态：为节省空口资源，可释放单播 SDS 下行承载或降低其带宽；为快速切换单播与 MBMS，也可保持原样。二是终端错误的去向：**终接参与功能实际收到终接客户端的 MSRP 错误响应时，须向发起客户端方向转发该错误**。「向……方向」不等于发起客户端已收到；没看到错误也不等于送达。这里转发的终端错误，与前面参与功能发给控制功能的正常 200，来源、去向和触发条件都不同。[§6.5.3.3 注 2（印刷页 28）](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=29)；[同款末段（印刷页 29）](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=30)。

[§4.1.1 首句（印刷页 10）](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=11)把 SDS 媒体面控制限定于在网；本页只谈其中已建立的组 SDS 会话如何经 MBMS 分发。[§6.5.1（印刷页 26–27）](https://www.etsi.org/deliver/etsi_ts/124500_124599/124582/16.03.00_60/ts_124582v160300p.pdf#page=27) 给的是非规范性背景。有三个不同对象：**组 SDS 会话本身已经建立**；发起客户端和终接客户端已经成功完成 SDP 提议/应答协商；终接参与功能已经发出 MBMS 承载通告，终接客户端已经收到并处理。只看见重复 Map，不能分别证明这些事情都在这个现场发生。要判定**终端收到 Map 后怎样监听、收到 Unmap 后怎样处理**，见[终接客户端的映射与解映射](group-sds-mbms-map-unmap.md)；要判断**是否接受加入组会话**，见[组媒体面 SDS 会话](group-media-plane-sds-session.md)；**一对一**会话的服务器路径另见[私聊 SDS 会话媒体](sds-session-media-server.md)。
