# 同一 MCData 系统内一对一发文件：收到“接受”，文件就下完了吗？

甲把一份班次表发给乙。即使甲的客户端已经收到“接受”，这条响应回答的也是**乙端怎样处理文件分发（FD）请求**。乙端是否已经取回文件，要看乙端的下载完成记录，或这笔传送的下载完成报告。两者都不是乙本人已读文件的证明。

**先确认是哪一种分发。** 这里讨论同一 MCData 系统内普通在网、一对一、文件供人阅读的情形。甲、乙已注册接收 MCData 服务，班次表已上传至 MCData 内容服务器的媒体存储功能。客户端可以有已激活的功能别名，但不要求这次一定用别名。示例另把一件事列为前提：MCData 服务器已向本系统的 MCData 功能别名控制服务器订阅别名激活和去激活的更新。这不是“甲乙都已激活别名”。Stage 2 把 HTTP 程序列为适用于强制和非强制下载；它没有据此规定每个设备实际选哪一种传送方式。〔§7.5.2.4.1、§7.5.2.4.2 引言及前提 1–4，印刷页 91〕

**甲给服务器的是取件地址。** 甲选定乙，甲端向 MCData 服务器发 FD 请求。请求用文件 URL 引用已经上传的文件，可以带文件元数据；目标是甲选的这一个 MCData 用户。请求还含对话标识（conversation identifier），说明这笔消息属于哪个消息线程，不是下载凭证。甲要求乙端强制下载时，请求带强制下载指示。甲还可另行选择要求下载完成报告，请求可带相应指示。强制下载与要求回报是两项选择，不能由前一项推出后一项。〔§7.5.2.4.2 步骤 1–2，印刷页 91〕

**上传成功后，谁还要核什么？** 收到 FD 请求的是 MCData 服务器。它核查甲是否有权发送该请求、文件大小是否**低于业务配置中的 FD 上限**。若请求带功能别名，还要核实别名可用于甲，且已为甲激活。服务器应用发送和接收控制及必要的策略控制，再向乙发起 FD 请求。上传时甲的媒体存储客户端另有大小检查；“上传成功”不能代替这里的服务器检查。若文件大小恰等于上限，就不满足本步骤的“低于”；本条没给出这种情况下的具体错误响应，不要把两个环节的边界措辞改成一样。〔§7.5.2.4.2 步骤 3–5，印刷页 92；上传另见[HTTP 文件存取](http-upload-download.md)〕

**乙的两次通知说的是不同的事。** 第一次是乙的客户端通知乙有分发请求，如果带了元数据，一并提示。非强制时，乙可以接受、拒绝或忽略；“忽略”说的是用户没有答复通知，不能据此补出具体网络报文或超时结果。有 FD 响应时，乙端发给 MCData 服务器，服务器转给甲端。若请求带强制下载指示，乙端会自动发送接受响应，无须乙手动同意。此时乙的媒体存储客户端自动下载；非强制情形下，实际下载取决于乙随后采取的动作。**第二次是下载完成后，乙端记录完成并通知乙。** 自动答复与自动下载仍是两件事。〔§7.5.2.4.2 步骤 6–9，印刷页 92〕

**甲能看到什么？** 如果甲请求了完成报告，乙端在下载完成后发起报告。服务器可以保存这份报告，供获授权的 MCData 用户查询下载历史；服务器还会把报告发给甲端的用户。保存是可选的，发送不以保存为前提。只有保存记录，不能证明已经发给甲；即便有服务器发出的记录，也不等于已在甲端收到。反过来，如果甲没有要求报告，就不能因甲手里没有报告而断言乙没有下完。〔§7.5.2.4.2 步骤 9–11，印刷页 92〕
