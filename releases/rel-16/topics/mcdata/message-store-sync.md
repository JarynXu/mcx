# MCData 消息存储：收到同步通知，哪些对象已经回到终端？

仅凭通知，一个对象也不能确认已经回到终端。通知说明 MCData 消息存储收到了该用户需要同步的新对象。要知道这台终端这一次实际收到了哪些对象，要看它收到的**同步响应**；要知道对象是否已写入本地，还得看终端自身的记录。

这里讨论用户在一台设备上的本地消息存储如何与 MCData 消息存储同步。依据是 [3GPP TS 23.282 V16.8.0，Release 16，Stage 2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf)。这份规范分开描述通知与同步，不把“先收到通知”列为发起同步的前提。

**通知：消息存储告诉谁？** 用户须已在 MCData 消息存储有账户，且存储客户端与消息存储之间已成功完成认证和授权。消息存储收到该用户的新对象，决定通知时，向存储客户端发送通知。通知表只列一个必填项：接收通知的用户的 MCData ID，没有对象、对象 ID 或对象数量。消息存储怎样判定需要发通知，不在本版规范范围内。因此不能靠通知次数推算新增对象数，也不能把一次通知当作已发起下载的证据。[§7.13.3.17、图 7.13.3.17.2-1、步骤 1–2 及注，印刷页 162–163](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=163)；[表 7.13.3.1.31-1，页 148](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=149)。

**请求：这台设备要同步哪些对象？** 发起者是存储客户端。同步程序列出的前提是客户端与消息存储之间已成功完成认证和授权。请求必须有用户的 MCData ID 和同步类型（全量或部分）。筛选条件的状态栏虽为 O（可选），同表表注却要求：选**部分同步**时必须给出筛选条件，用来指定要同步哪类对象。全量请求不因这条表注而必须带筛选条件。若一份完整的部分同步请求缺少筛选条件，应指出它不符合表注，不能自行改按全量解释，也不能据此指定服务端会回哪种错误。[表 7.13.3.1.9-1 及表注，页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=144)；[§7.13.3.6.1–2、图 7.13.3.6.2-1、步骤 1，页 151–152](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=152)。

**响应：本次回了什么？** 消息存储按本次请求的范围，在响应里返回全部符合条件、需要同步的已存对象，不只是引用。用户的 MCData ID 和已存对象字段都必填；对象字段存在但为空，表示本次没有需要同步的对象。空字段不是字段缺失，不说明该账户从未存过对象，也不是其他设备已同步的证明。即使响应带回了对象，流程也只写到消息存储向客户端返回对象，没有本地写入完成或跨设备一致性的确认。[表 7.13.3.1.10-1，页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=144)；[§7.13.3.6.2、图 7.13.3.6.2-1、步骤 2，页 152](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=153)。

如果只是想打开某条历史消息，见[按 ID 取回或按条件搜索](stored-object-lookup.md)。若想列出哪些暂存组数据还可下载，见[查询组暂存数据引用](deferred-group-list.md)。这两项都不是同步的必经步骤。
