# 经 MBMS 向组发送控制消息：客户端何时不得应答，监听状态报告又说明什么？

假设服务器经多媒体广播多播业务（MBMS）向蓝组发了一条应用层控制消息。甲收到消息，但既未被指示要回复这条消息，也没有适用的回复配置。**甲不得应答。** 所以服务器没见到甲的应答，不能据此判定甲没收到消息。如果有适用的指示或配置，要按其所指的消息和条件判断；不能反推该客户端从此必须给每条组消息回执。这条规则针对**以组为收件对象**的应用层控制信令，不能直接套到发给单个客户端的消息上。[3GPP TS 23.280 V16.7.0，Release 16，Stage 2，§10.7.3.4.1 末段，印刷页 126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=127)。

**监听状态报告回答的是另一个问题：服务器能否用这条承载给甲发控制消息？** 服务器决定激活控制承载后，把承载信息发给客户端。甲从业务描述中取得标识这条承载的 TMGI（临时移动组标识），保存相关信息，再用 TMGI 和其他承载信息启动终端监听。这里的 TMGI 指明要监听哪条承载，并不是某条控制消息的回执。[§10.7.3.4.2 步骤 1–3，印刷页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=128)。

当甲进入或已经处于该 TMGI 所通告的服务区时，它向服务器报告：**自己能在这条承载上接收应用层控制消息**。它还可以附上自己在该承载上接收 MC 业务媒体时的质量级别；没有附级别，不等于报告说“不能接收”。服务器可以据此决定用这条承载发送应用控制消息。报告是步骤 4，服务器发送控制消息是步骤 5：只有甲的报告，既不能把服务器的选择记为已执行，也不能把后来发给蓝组的某条消息记为甲已收，更不能替其他组员确认送达。[§10.7.3.4.2 步骤 4–5，印刷页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=128)。

若关心的是“收到**另一条承载的通告**后，何时要确认该通告”，见[经控制承载通告、撤告另一条承载](mbms-bearer-announcement.md)。要判断媒体接收质量何时上报，见[MBMS 接收质量](mbms-reception-quality.md)；要解释单播 MCPTT 组呼中一条“进行中”的通知，见[MCPTT 组状态](../calls/mcptt-mbms-group-status.md)。[结构化条件与声明](mbms-application-control-signalling.json)。
