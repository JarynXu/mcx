# 谁管三个平面，谁经 Rx 控制承载：在网 MC 业务部署资料能说明哪一项？

甲站的分工表写明：应用服务层、SIP 核心和演进分组系统（EPS）由同一家机构管理。乙站的分工表则写明：MC 业务提供方独立管理 MC 业务，公共陆地移动网（PLMN）运营方管理 SIP 核心和 EPS。**这两张表足以分清管理职责，却都不足以判断哪一个功能经 Rx 参考点控制承载。** 在 3GPP TS 23.280 V16.7.0（Release 16，Stage 2）中，甲符合三个平面共同管理的示例，乙符合业务独立于 SIP 核心和 EPS 管理的示例。规范列有五种管理场景，这里只比较两种。见[§9.2.2.1.2 首段，印刷页 49](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=50)、[§9.2.2.1.3 首段，印刷页 50](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=51)和[§9.2.2.3.1，印刷页 56](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=57)。

资产登记还要另读。设乙站的某件无线接入网（RAN）设备登记在 MC 业务提供方名下。这与运营方管理 EPS 并不矛盾：标准举的例子正是，MC 业务提供方可以拥有 EPS 内部分 RAN 设备，而 EPS 仍由 PLMN 运营方管理。资产表可以回答这件设备归谁，不能替代平面分工表，更不能替代承载控制的部署说明。见[§9.2.2.1.1，印刷页 49](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=50)。

## 哪份资料能认出承载控制模型？

看适用于该部署的说明是否指明**由哪一个功能单独经 Rx 控制承载**。按[§§9.2.2.3.2–3，印刷页 56](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=57)：

- 若说明指定只有 **SIP 核心**承担这项控制，便是 §9.2.2.3.2 的模型。不能因为应用业务也有服务器，就把它算作第二个承载控制方。
- 若说明指定只有 **MC 业务服务器**承担这项控制，便是 §9.2.2.3.3 的模型。这项分工并不意味着 SIP 核心不存在，也不说明设备归业务提供方所有。

回到甲、乙两站：即使补来的部署说明为两站指定了**同一个**承载控制模型，也不与先前的两种管理场景矛盾。反过来，只读控制分工，也推不出三个平面由一家还是分开管理。§9.2.2.3.1 明说这两类场景没有直接对应关系；这不等于标准验证了所有组合在实网均可运行。见[§9.2.2.3.1，印刷页 56](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=57)。

**一条 Rx 申请记录有多大证明力？** 如果记录只说“MC 业务服务器已发出申请”，可以记下该次申请及发起方。没有说明其为本部署唯一控制方，就不能把这条记录写成整站的独占分工；没有这笔资源的分配结果，也不能写成“已经分配”。§9.2.2.3 给的是部署模型，并非单笔申请的完成记录。

若问题是某次普通在网会话究竟何时已分配单播资源，见[单播资源的建立与修改](unicast-resource-establishment-modification.md)；若材料明确说的是不经过 SIP 核心的在网 MCData 业务，见[非 SIP 的 MCData 资源管理](../mcdata/nonsip-resource-management.md)。这两页各有自己的适用程序，不能以其中一次申请替整站选模型。
