# MC 业务方管 SIP 核心，运营方管 EPS：哪些信息可以要求隐藏？

这一部署中，**MC 业务提供方管理应用服务层和 SIP 核心，PLMN 运营方管理 EPS（演进分组系统）**。MC 业务和 SIP 核心独立于运营方管理。图中的分工回答谁管理哪一层。它不能证明某项信息已经隐藏，或某一次认证已经完成。[3GPP TS 23.280 V16.7.0，Release 16，Stage 2，§9.2.2.1.4 首段及图 9.2.2.1.4-1，印刷页 51](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=52)

## 对 EPS 隐藏，不等于对 SIP 核心隐藏

| 要区分的边界 | 这一部署的规定 |
| --- | --- |
| **应用服务层 → EPS** | 业务提供方可要求对 EPS 隐藏应用服务层的全部身份和其他敏感信息。 |
| **应用服务层 → SIP 核心** | 业务提供方不必向 SIP 核心隐藏应用服务层的身份和信令。这不是要求把这些资料交给核心，也不能从中断定核心实际看到了什么。 |
| **SIP 核心与终端内的 SIP 客户端之间 → EPS** | 业务提供方还可要求对 EPS 隐藏这段交互中的身份和其他敏感信息。 |

[§9.2.2.1.4 图后首段，印刷页 51](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=52)。例如，分工表上只写“运营方管理 EPS”，不能据此认定 EPS 看到了应用层的身份，也不能认定这些身份已经被隐藏。要判断本部署的要求，查业务提供方对这两条 EPS 边界分别作了什么规定。

## 对运营方隐藏认证与授权机制，要看哪两层？

**应用服务层和 SIP 信令面都在范围内。** 本条说，这两层的全部认证、授权机制（包括安全根）可能需要对 PLMN 运营方隐藏，且对运营方不可用。它没有要求所有站点一律这样做，也没有规定如何实施。[§9.2.2.1.4 末段，印刷页 51](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=52)

这不是登录或承载建立过程。若要看谁经 Rx 控制承载，另查[管理场景与承载控制部署的区分](bearer-control-deployment.md)；不能凭 SIP 核心由业务提供方管理就选定承载控制方。
