# MCPTT 的 MBMS 通告写了 ROHC，怎样查谁压缩、终端应做什么？

**同样的 ROHC 通告，可能对应两条不同的压缩路径。** 参与 MCPTT 功能（PF）可以自己压缩包头，再经 MB2-U 交给广播多播业务中心（BM-SC）；也可以请 BM-SC 压缩。终端处理的是实际收到的包。下文只查 MCPTT 经 MBMS 的 ROHC 包头处理，不用这段规定判断单播或其他 MC 业务。[TS 24.380 V16.9.0，Release 16，Stage 3，§10.4.1，印刷页 210–211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=211)

## 同样的通告，发送侧要核对哪条路径？

PF 决定给某条 MBMS 承载做头部压缩，就须在这条承载的通告里声明使用 ROHC。**声明是两条路径的共同动作，不标识压缩方。** 另查同一承载的 PF 所选分支：

| 已知的分支 | PF 在该分支须做什么 |
| --- | --- |
| PF 自己压缩 | 对发往该承载的每个包，按 §10.4.2 第 3 项引用的 ROHC 规范压缩包头。使用单向模式，不做 ROHC 分段；自行压缩在经 MB2-U 交包之前。 |
| PF 请 BM-SC 压缩 | 在激活或修改该承载时，指明要用 `0x0101` 压缩包头的组播 IP 和端口列表。列表是 PF 的请求内容，不证明 BM-SC 已对某个包做了压缩。 |

只见通告，不能选其中一行；只见发送侧的包或承载动作，也不能认定终端已经收到。若要核对“承载已激活后”的 Setup ROHC 及其响应，读[公共 MBMS 的 Stage 2 流程](mbms-rohc-roles.md)。不拿那一步替换本条的“在激活或修改时”，也不靠两句推断实际消息时间。通告写法另由 TS 24.379 给出；委托路径引用 TS 29.468，本页不把分支要求当作这两份标准的字段或编码说明。[§10.4.1 的两种分工及 §10.4.2 第 1–3 项，印刷页 211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)

## 终端收到包后做什么？加密放在哪一步？

当这条承载的通告声明了 ROHC，MCPTT 终端须按 §10.4.3 引用的规范**解压实际收到的 ROHC 包，再将解压后的包交给媒体混合器**。只见通告或发送记录，不能确认终端已收、已解压或已交混合器；交到混合器也不等于用户已经听见。若要判某个子信道来包有没有对应的本地通话、怎样区分音频 SSRC，另查[终端的 MBMS 子信道收包规则](mcptt-mbms-map-unmap-timers.md)，不靠 ROHC 通告补那个关联。[§10.4.3，印刷页 211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)

**同一路媒体同时采用这两种处理时，发送侧先做媒体面加密，再做包头压缩；接收侧先解压包头，再做媒体面解密。** 这说的是各方向的先后，不说承载必须加密、不指定加解密实体，也不证明某次操作已执行。若问题是 FEC 编码，读[公共 MBMS ROHC 的 Stage 2 职责与 FEC 顺序](mbms-rohc-roles.md)：那里约束 FEC 与头部压缩的先后，不能与本页拼出 FEC 和加密之间的先后。[§10.4.1，印刷页 211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)

## 怎样读配置档、CID 和 MAX_CID？

- `0x0101` 用于压缩 RTP/UDP/IP 头。使用这个配置档的 MBMS 子信道各用不同的 CID（ROHC 上下文标识）。
- `0x0000` 用于发送未压缩包。使用这个配置档的 MBMS 子信道**可**共用一个 CID；不是必共用，也不是在压缩失败时自动切到这个配置档的规则。
- 建立带头部压缩的 MBMS 承载前，PF 先确定 `MAX_CID`。`MAX_CID > 15` 用大 CID 表示；否则用小 CID 表示。15 属于小 CID，16 属于大 CID。MCPTT 经 MBMS 的 ROHC 只用单向模式。

这版原文对 `0x0000` 的引用文字不一致：§10.4.1 写 `RFC 3075 [21]`；§2 的参考文献 [21] 列 `RFC 3095`，§10.4.2 第 3 项和 §10.4.3 也写 `RFC 3095 [21]`。保留这处差别，不据此修订引用或选择线上编码。[§10.4.1–.3，印刷页 211](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=212)；[§2 的 [21]，印刷页 17](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=18)。
