# 远端终端按业务组找网络中继：通告和征询分别由谁核对？

远端终端收到中继 R 的发现通告时，要回答的是“**我的这个组能否经 R 入网？**”R 用中继服务码表示允许哪些组。远端终端要把通告中的码与自己所属组的预配码对上，才能按该组选 R。即使匹配，也不能登记“已连上 R”或“已加入组呼”。这是 Rel-16 的网络中继发现，不是应用层入组。[TS 23.280 V16.7.0 §10.5.1，印 114](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=115)

## 同一份发现记录，不要用错码表

采用 ProSe（邻近服务）中继服务码时，**R 持有的是允许经它中继的组所对应的码，远端终端持有的是该用户所属组所对应的码**。原文给出两种做法，不要求先通告再征询。[§10.5.1，印 114](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=115)

| 发现方式 | 由谁作决定 | 哪一步还没有证据 |
|---|---|---|
| R 广播发现通告（Discovery Announcement），带允许组的码 | 远端终端查看**本用户目标组的预配码**是否出现在通告中。匹配，就能按这个组选 R。已知该组的码均不在通告中，便不能据此通告按这个组选 R；若没有该组的预配资料，就还不能判断。 | 看到 R 通告或看到匹配，都不是远端已建立连接的记录。 |
| 远端终端发发现征询（Discovery Solicitation），带本用户所属组的码 | **R** 查看征询中的码是否在**自己的许可码表**内，据此决定是否响应。命中表示满足按组响应条件；所带码均不在表内，则不满足。 | 只有远端发出的征询，不能替 R 判断匹配。许可表有此码也不证明 R 回了这一次；需要能与这次征询对应的响应记录。没看到响应也不能反推表中一定没有这个码。 |

## 同一个码为什么不能认定唯一的组？

MC 业务**必须支持让中继按组限制通信的能力**。ProSe 服务码是条文给出的一种实现，不是唯一允许的实现。规范建议业务提供配置手段，让管理员给中继设置获准组清单；每个获准组**宜**分配一个独特的关联码。码**可**由 MC 业务服务器或 DPF（直接预配功能）提供给中继，不要求从两处各取一份。[§10.5.1，印 114](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=115)；[§5.2.3，印 19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=20)；[§3.3，DPF，印 16](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=17)。

§5.2.3 的注允许移动网运营方将一个码映射到一个或多个组。若两个组共用一个码，通告有这个码并不能区分这两个组，更不能指认某个用户。发现所用的“用户所属组”是预配的前提；发现匹配本身不产生业务授权、组成员资格或组归属，也不证明用户参加了哪一场通话或收到了媒体。[§5.2.3 正文及注，印 19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=20)；[§10.5.1，印 114](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=115)。

## 在网终端的中继组列表缺失，要按哪张表判？

视频查 **TS 23.281 V16.4.0**，数据查 **TS 23.282 V16.8.0**。两份规范的在网 UE 配置表都编为 **A.2-2**，均在各自的**印刷页 170**：

| 核对的业务 | 在网 UE 配置中要核对的字段 |
|---|---|
| MCVideo | 中继服务标志（Relay service，Y/N）；可选的获准中继视频组列表。列表子项是 **MCVideo 组 ID** 与中继服务码。[TS 23.281 V16.4.0 表 A.2-2 及注](https://www.etsi.org/deliver/etsi_ts/123200_123299/123281/16.04.00_60/ts_123281v160400p.pdf#page=171) |
| MCData | 中继服务标志（Relay service，Y/N）；可选的获准中继数据组列表。列表子项是 **MCData 组 ID** 与中继服务码。[TS 23.282 V16.8.0 表 A.2-2 及注](https://www.etsi.org/deliver/etsi_ts/123200_123299/123282/16.08.00_60/ts_123282v160800p.pdf#page=171) |

两表中，**标志为 N，本业务列表及其子项都不需要；为 Y，也不能据此要求列表一定存在且非空**。可选的是列表。仅凭 Y 不知道允许哪个组；拿到一对组 ID 与码，也只是核实了本业务的配置。即使数据组和视频组同名，也不能用数据配置补视频证据，或拿配置单当作响应记录。

**发现之后该查什么？** 远端失去蜂窝覆盖、实际经 R 使用在网 MC 业务时，R 提供三层 IP 路由，远端用户的应用层信令与在网终端相同。[TS 23.280 §10.5.2，印 114](https://www.etsi.org/deliver/etsi_ts/123200_123299/123280/16.07.00_60/ts_123280v160700p.pdf#page=115)。若要验收换接入前已有的 MCPTT 会话，查[原通话的媒体是否都转到了新路径](anchored-session-transfer.md)：若采用 TS 23.280 资料性附录 B.1 的锚定会话示例，新路径已注册或只证实一路媒体，均不能替其余各路签字。若其他同组成员已经在一场离网视频组呼中，才查[后来者怎样加入那场既有组呼](../mcvideo/offnetwork-group-join.md)；若终端从建呼时就在场，应查[离网视频组呼首次建立](../mcvideo/offnetwork-group-call-establishment.md)。这两种直通组呼的参呼情况都不能用中继通告确认。
