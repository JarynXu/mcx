# 在网 MCPTT 组呼：MBMS 容量不够时，怎样把正在组播的通话改走单播？

一段新通话准备使用 MBMS（多媒体广播多播业务），不代表它已经占到了容量。参与 MCPTT 功能（PF）可以把**另一段正在走 MBMS 的通话**迁到单播，给新通话让位；也可以不挪旧通话，让新通话的信令走 MBMS、媒体走单播。前一种选择改变旧通话的传送方式，不要求先结束它所属的组呼。

**什么时候才检查容量？** 这里是普通同系统在网 MCPTT 组呼，PF 支持 MBMS 子信道控制。对准备上 MBMS 的这段新通话，PF 处在 Start-stop：组会话已经存在，还没有为这段通话运行 MBMS 子信道控制实例。PF 收到 Floor Request **或** Floor Taken，并决定用 MBMS 子信道传送这段通话时，才需要判断承载容量。容量不足时，上述两种处置都可选。条文没给出数值门限，也没指定应该选哪段旧通话、两段通话是否属于同一组。只看到话权消息，不能确认 PF 已经作了容量决定；即使确认它决定挪走旧通话，也不能登记新通话已经映射成功。[3GPP TS 24.380 V16.9.0，Release 16，Stage 3，§10.2.1，印刷页 204](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=205)；[§10.2.2.1–10.2.2.2，印刷页 205](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=206)。

**应用寻呼不是开单播的门槛。** 参与服务器决定迁移旧通话后，PF *可以*通过这段通话关联的 MBMS 子信道发 Application Paging。§4.1.3.6 给出一种走法：先寻呼，再发 Unmap Group To Bearer（解除组与承载的映射），此后通话继续走单播。具体迁移条款 §10.2.3.12 的注释也允许发寻呼与开始单播同时发生；这一条没有要求等客户端收到或确认寻呼，也没把 Unmap 列为开始单播的前提。寻呼带有 MCPTT Group ID，但用途有两种：迁移旧通话，或让新通话从单播开始。单见这个组 ID 和一份寻呼，分不出是哪一种，更不能断定 PF 正在为别的通话腾容量。[§4.1.3.6，印刷页 24](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=25)；[§10.2.3.12 及注，印刷页 209](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=210)；[§8.4.6、表 8.4.6-1，印刷页 187](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=188)。

**一台空闲终端收到寻呼，下一步是请求连接。** 客户端支持从 MBMS 接收话权控制消息和 RTP，且承载已经激活并已通告。若甲处于空闲模式，确实从 MBMS 子信道收到寻呼，甲就应发起服务请求，以进入 RRC Connected（无线连接态）。发起请求还不是已经连上；即使连上，也不能据此认定甲收到了这段通话的单播 RTP。若甲原已连接，§10.3.5 没有要求它为此再发一次服务请求。PF 的发送记录也不能替甲或其他终端证明收件。[§10.3.1，印刷页 209–210](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=210)；[§10.3.5，印刷页 210](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=211)。

**PF 为何释放实例，要看它收到哪条指示。** 两个分支释放的都是旧通话使用的那个 MBMS 子信道管理实例，不是整条承载。

| PF 实际收到的指示 | 此分支要求 PF 做什么 |
| --- | --- |
| 应用与信令面指示：这段通话的所有相关客户端现已监听单播 | 释放该段通话的实例。§10.2.3.10 只列这项动作，没有另列发 Unmap 或停定时器。 |
| 控制与信令面指示：组呼会话已释放 | 经 MBMS 子信道发送带 MCPTT Group ID 的 Unmap，停止 T15、T16、T17 中仍运行的定时器，释放该段通话的实例。§10.2.3.11 不要求先取得上一行的指示。 |

前一行的依据是 PF 收到“全部已监听单播”的指示，不是一台终端收到了寻呼或发起了服务请求。“已监听”也不证明每台终端收到了某个单播媒体包。反过来，看到一份 Unmap 不能推断组呼已结束：例如，T15 到期而应用指示仍有客户端监听 MBMS，PF 也要发带组 ID 的 Unmap。[§10.2.3.10–10.2.3.11，印刷页 209](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=210)；[§10.2.3.6 第 2 项，印刷页 208](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=209)。

终端甲从 MBMS 子信道实际收到 Unmap，只在本地查消息所指的组。若存在相应关联，甲的 MBMS 接口解除 TMGI（临时移动组标识）、音频子信道、话权控制子信道与该组会话中这段通话的关联。这项动作不等于停用整条承载，也不能用来断定 SIP 会话已结束、乙也解除了映射，或甲已经收到单播媒体。[§10.3.1、§10.3.4，印刷页 209–210](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=211)。
