# MCPTT 组播：Map 为什么反复发，Unmap 什么时候停止重发？

在网 MCPTT 组呼已使用 MBMS（多媒体广播多播业务）。同一段通话反复出现 Map Group To Bearer，不一定在新分配承载，也不一定是某台终端没收到。先查参与 MCPTT 功能（PF）中，**本段通话的子信道控制实例处在哪个状态，哪个定时器实际到期**。

## 通话仍活跃：T16 到期重发 Map

支持子信道控制的 PF 在 Start-stop 收到 Floor Request 或 Floor Taken，决定为已有组会话中的这段通话使用 MBMS 子信道，且承载容量足够时，按 §10.2.2.2 建立实例、发送首份 Map，启动 T15 和 T16，进入 `M: A conversation is active`。此后若在活跃状态实际发生 **T16 到期**，PF 须在**通用 MBMS 子信道**再发 Map，携带 TMGI（临时移动组标识）、MBMS Subchannel 和 MCPTT Group ID，并重启 T16、保持活跃状态。这个到期分支没要求等终端确认，也没有再次分配子信道的步骤；只有抓到重复的 Map，尚不能断定就是 T16 到期。

本版 §10.2.2.2 第 4 项把 T16 的括号名写成 Unmap；§10.2.3.1、§10.2.3.7 与定时器表却把 T16 用于 Map。按实际编号与到期动作对证，不按这处括号名对换 T16、T17。终端要另核 §10.3.1 的前提：该 MCPTT 客户端支持经 MBMS 收取话权控制消息和 RTP，且承载已激活并已通告。它**实际收到**通用子信道上的 Map 才按 §10.3.2 把 TMGI、音频和话权子信道与目标组关联。PF 已发送不能证明某台终端已收到、已建立关联或已收到媒体。

依据：[TS 24.380 V16.9.0，Rel-16 Stage 3，§§10.2.2.2、10.2.3.1，印刷页 205–206](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=206)；[§10.2.3.7，印刷页 208](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=209)；[§§10.3.1–.2，印刷页 209–210](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=210)；[表 11.1.4-2，印刷页 222](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=223)。

## T15 到期：有没有终端还在监听？

这里看的是**应用给 PF 的指示**，不是从发送次数猜还有几个听众。

| 事件 | PF 按该分支执行 |
| --- | --- |
| T15 到期，应用指示已没有客户端监听 MBMS 承载 | 释放这段通话的 MBMS 子信道管理实例，进入 Start-stop。该分支未列发送 Unmap。 |
| T15 到期，应用指示仍有客户端监听 MBMS 承载 | 经 MBMS 子信道发带 MCPTT Group ID 的 Unmap，启动 T17，把 C17 初始化为 1；仍处于活跃状态。 |
| T17 到期，尚未到 C17 的次数上限 | 重发带该组 ID 的 Unmap，重启 T17，C17 加 1。 |
| T17 到期，达到 §10.2.3.9 所述上限事件 | 该正文仍列一次带该组 ID 的 Unmap，随后释放此通话的子信道管理实例。 |

§10.2.3.8 第 2 项把 T17 的括号名写成 Map 重发，但该事件、发送的消息和定时器表都指向 Unmap。表 11.1.4-2 的 T15 到期栏只简写“发送 Unmap”，应对读 §10.2.3.6 的监听条件。表 11.2.4-2 又把 C17 到限简写为“不再重发”，而 §10.2.3.9 仍列发送后释放。不要仅凭表格或抓到的包数定一个唯一的最后一包算法。值班要查实际配置、计数和进入的分支；这三项定时器的默认值分别为 T15 **30 秒**、T16 **500 毫秒**、T17 **200 毫秒**，C17 的默认上限是 **3**，均可配置。默认上限不是固定的线上发包数。

依据：[§§10.2.3.6、10.2.3.8–.9，印刷页 208–209](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=209)；[表 11.1.4-2，印刷页 222](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=223)；[表 11.2.4-2，印刷页 225](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=226)。

**释放管理实例不等于释放组会话，也不等于停用整条 MBMS 承载。** 对符合 §10.3.1 前提的终端，查解绑需要它实际经 MBMS 子信道收到该组的 Unmap，且原来有相应关联；只凭 PF 停止重发不能签认解绑。若 PF 收到的是“所有终端改听单播”或“组呼已释放”的控制指示，读[迁单播与组呼释放的独立分支](mcptt-mbms-capacity-to-unicast.md)；若包其实是 MBMS 承载通告，其收件状态另读[承载通告与监听状态](mcptt-mbms-announcement-sdp.md)，不要用通告的状态报告给 Map 或 Unmap 补一份确认。[§§10.2.3.10–.11，印刷页 209](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=210)；[§§10.3.4、10.3.6，印刷页 210](https://www.etsi.org/deliver/etsi_ts/124300_124399/124380/16.09.00_60/ts_124380v160900p.pdf#page=211)。
