# MCPTT 承载通告：怎样读初始 SDP、解释 Map 和处理撤告？

<a id="initial-announcement-sdp"></a>
## 初始通告里有两个 m=application，哪一个给终端监听？

参与 MCPTT 功能（PF）向目标终端发送初始承载通告时，每条 SIP MESSAGE 宣告一条承载，用它的通用 MBMS 子信道（GPMS）发送应用层组播信令；同一条消息还可以宣告其他承载来传媒体和媒体控制。消息含一份 `application/sdp` 体，`Content-Disposition` 为 `render`。**先在承载通告项中找 `GPMS`，再按它给出的媒体行编号读同一份 SDP。** 承载 GPMS 的那一项必须写这个编号；它标识用于通用子信道的 `m=application` 行，不是端口号或 TMGI。不要选遇到的第一条应用媒体行。[§14.2.2.1，印刷页 464](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=465)；[§14.2.2.2 第 5 项，页 465–466](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=466)、[第 6(f) 项，页 467](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=468)。

| 初始通告 SDP 中的用途 | 地址、端口与属性 |
| --- | --- |
| 通用子信道 | 必须有一条供 GPMS 使用的 `m=application`，给出有效组播 IP 地址和有效端口。它承载组播信令，不直接给出本组的语音目的地。 |
| 音频和媒体控制共用子信道 | PF 宜提供一条或多条这种 `m=audio`。提供时，IPv4 的 `c=` 填 `0.0.0.0`；IPv6 填 `.invalid` 顶级域之下的域名，不是 `::`。媒体端口填 `9`，且有 `a=rtcp-mux` 和 `a=rtcp:9`。 |
| 只传音频 | PF 也宜提供一条或多条只传音频的 `m=audio`。地址占位和端口与上一行相同，但这一媒体段不含 `a=rtcp-mux` 或 `a=rtcp:`。两类音频行是分别给出的建议，不要求整份 SDP 二选一。 |
| 独立话权控制 | 只要通告包含只传音频的行，PF **就必须**给出一条或多条供话权控制的 `m=application`，同样使用 IPv4 或 IPv6 的地址占位和端口 `9`。独立话权子信道并非每次都用；不用时，话权消息走媒体子信道。 |

所以两条应用行可以各有用途：一条是由 `GPMS` 指定的组播信令端点，另一条可以是话权控制的占位描述。即便两种音频行同时出现，只传音频的那一行仍使独立话权行成为必需。仅截到 IPv6 音频段的 `.invalid` 域名和端口 9，连它是否与媒体控制复用都不能判定，要看同段的 RTCP 属性；也不能据此选出通用子信道。缺少承载 GPMS 的通告项、编号不指向合格应用行，或抓包不完整时，不用 IP、端口或排列顺序补选，也不据此指定终端的 SIP 错误码。[§14.2.2.2 第 5(b)–(e) 项、注 1–3，印刷页 465–466](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=466)。

**组媒体实际使用哪些参数，要看 `Map Group To Bearer`，不是把语音或话权发向占位地址的 9 端口。** 收到 Map 时，行编号要按承载这份 Map 的通用子信道所关联的 SDP 解释（见下文）。PF 的初始出包能说明它通告了什么，不能证明终端已进入服务区、开始监听、收到该组的 Map 或收到了语音。要确认语音收达，还要有终端的媒体接收记录。[§14.2.2.2 注 2、3，页 466](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=467)；[§14.3.2，页 470–471](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=471)。收到 Map 后，要判断第一个端口是话权还是语音，读[Map 的话权选择值和端口次序](mcptt-mbms-map-unmap-timers.md#map-subchannel-ports)；同页说明终端何时建立或解除关联。

## 两条通告共用 SDP，撤告一条会发生什么？

撤告按 TMGI（临时移动组标识）找通告。假设甲、乙两条通告现在都关联同一份本地 SDP。只撤告甲时，客户端丢弃甲的通告，断开甲与 SDP 的关联，停止监听甲对应的通用 MBMS 子信道。乙仍关联这份 SDP，就保留它。这不能判定乙当前是否在监听，尤其不能承诺甲、乙使用同一个通用子信道时乙会继续听到。只有这份 SDP 已经没有任何存储的通告关联，客户端才删除它。

这里处理的是在网 MCPTT 客户端实际收到的 SIP MESSAGE。P-Asserted-Service 须标明 MCPTT 的 ICSI（`urn:urn-7:3gpp-service.ims.icsi.mcptt`），消息还须带 `application/vnd.3gpp.mcptt-mbms-usage-info+xml`，其中至少有一项 `announcement`。客户端逐项判断，不把整个 MESSAGE 当成承载清单快照。

## 这项通告带服务区：按 TMGI 新建或替换

一项 `announcement` 带 `mbms-service-areas`，客户端用它的 TMGI 查已有通告。找到同值就替换旧通告；没有同值就存这项。客户端把该通告与收到的 SDP、GPMS 字段及从 P-Asserted-Identity 取得的参与功能 MBMS 公共业务标识关联。

例如参与功能只更新甲、没有在这份消息列出乙，客户端不能因此删掉乙的通告。对规范所述的更新，发送方沿用甲原来的 TMGI、GPMS 值和初始 SDP；服务区列表可以保留或更新。一般条款还说明收到新通告所带的 SDP 体替换原 SDP 体；这与删除未列出的通告不是一件事。本页不据此推断不同承载之间如何重建内部 SDP 引用。

若这项通告带有本款所述的 MIKEY-SAKKE 保护参数，须按本款处理；校验失败则拒绝并停止后续步骤。客户端继续处理有效通告时，就要检查发送监听状态报告的条件，不必等到进入服务区才检查。监听另有触发条件：进入该承载可用的 MBMS 服务区时，监听 SDP 中 `m=application` 指定的通用子信道。[收到 Map、入区、撤告或无线变差时，哪些情况须发监听报告？](mcptt-mbms-status-message-rejection.md#listening-report) 检查报告条件不是保证已报告，更不是收到业务媒体的证据。

依据：§14.2.2.1 及其注（印刷页 464），§14.2.2.3（页 467），§14.3.2 开头及含服务区项的步骤 1(a)–(h)（页 470–471）。

## Map 从哪条通用子信道收到，就到哪里找 SDP

终端把通告消息收到的 SDP 和安全密钥关联到**同一份通告消息所宣告的通用 MBMS 子信道**（GPMS）。后续实收 `Map Group To Bearer` 时，先找**实际收到这份 Map 的通用子信道**，再用与该子信道关联的 SDP 解释 Map 的内容，例如 `m=` 行编号。[3GPP TS 24.379 V16.14.0，Rel-16，§14.3.2 开头，印刷页 470](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=471)。

例如，终端在甲通用子信道上收到 Map，Map 把媒体或媒体控制映射到乙承载。要解释这份 Map 的行编号，查**甲通用子信道关联的 SDP**。乙的 TMGI 标识此次映射的承载，不决定这些编号按哪份 SDP 来读。即使乙的通告比甲更新，也不能单凭时间换用乙的 SDP。路由记录只保留了乙的 TMGI、没记录 Map 从哪条通用子信道进来时，先找回接收来源与当时的关联，不能替缺失记录选一份 SDP。[§14.3.2 开头，印刷页 470](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=471)。

**映射后的安全密钥也先看 Map 来路。** 若没有另行适用的密钥，也没有不使用加密的指示，被映射的乙承载上的 MBMS 子信道采用**承载这份 Map 的甲通用子信道当时有效的安全密钥**。有适用的另一密钥或明确的不加密指示时，不套用该默认规则。这里没有给出替代密钥的字段或选择算法。只看到乙的通告更新、一次映射或终端报告 listening，不证明已成功处理安全材料，也不证明终端已解开或收到业务媒体。[§14.2.2.2 第 6(a) 项后的注 5，印刷页 466](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=467)。

## 安全负载的发起者不符，即使签名正确也要拒绝

这一检查针对**带服务区的通告项**，而且该通告的 SDP 在**通用子信道**的 `m=application` 段确实带了 `a=key-mgmt`、`mikey` 标识和 MIKEY-SAKKE `I_MESSAGE`。不能在同一份 SDP 里任选一条应用媒体段，也不能把 SIP 头本身当作安全负载。[§14.2.2.2 第 5(d)–(e) 项，印刷页 465–466](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=466)；[§14.3.2(1f)，印刷页 471](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=472)。

1. 从 `I_MESSAGE` 的 `IDRi` 取发起者 URI，与**正在为该用户服务的参与 MCPTT 功能的 PSI** 比较。不同就拒绝这条 SIP MESSAGE，回 **488、Warning 文本编号 136**，终止后续步骤。另一个参与功能的签名即使正确，也不能替代这一身份检查。
2. 比较通过后，才把发起者 URI 转为 UID，用于验证签名。验证失败同样回 **488/136** 并停止。通过后按本条提取、解开封装的 MSCCK，并取出标识该密钥的 MSCCK-ID。MSCCK 用于保护通用 MBMS 子信道的控制消息，不等同于明确给某个组下发的 [MuSiK](../media/mbms-musik-download.md)、私呼 PCK 或语音 RTP 已解密的证据。

`P-Asserted-Identity` 中随通告存下的是参与功能的 **MBMS 公共服务标识**；取这个字段是另一步，不能替代 `IDRi` 与服务参与功能的身份比对。两种失败都停止后续的 MSCCK 处理、监听和报告条件检查；仅凭同一个 488/136 分不出是哪一步失败，也不能断言此前的通告存储或关联已回滚。规范的 Warning 文本拼写为 `MIKEY-SAKE`；协议名为 `MIKEY-SAKKE`。[§14.3.2(1c)–(h)，印刷页 471](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=472)。

## 这项通告不带服务区：按 TMGI 撤告

真正的撤告是**这一项仍在消息里，有对应 TMGI，但没有 `mbms-service-areas`**；不是整项没出现在这份消息里。客户端丢弃该 TMGI 已存的通告，去掉它与已存 SDP 的关联，停听对应的通用子信道，再检查监听状态报告条件。停听针对条款所指的子信道，不是另给乙发出撤告。删除 SDP 的判据是同一份 SDP 是否仍关联其他已存通告，不是本次 MESSAGE 有没有带 SDP。

如果 usage-info XML 体里的所有通告项都是撤告，参与功能须省略 GPMS 和整个 SDP 体。其中有新通告或更新，也可能与撤告放在同一份消息；不能用整条消息有无 SDP 代替逐项判断。撤告不等于网络停用承载，也不说明客户端已送达报告或业务媒体。

依据：§14.2.2.1（印刷页 464），§14.2.2.4 步骤 1–4（页 467–468），§14.3.2 撤告项的步骤 2(a)–(d)（页 471）。

固定原文：[TS 24.379 V16.14.0，Release 16，Stage 3](https://www.etsi.org/deliver/etsi_ts/124300_124399/124379/16.14.00_60/ts_124379v161400p.pdf#page=471)。若要查的是[通过已监听的承载向客户端通告另一条承载](mbms-bearer-announcement.md)，读 Stage 2 流程；要查[何时检测承载暂停和报告](mbms-suspension-reporting.md)，再查报告条件。

如果收件方不是终端而是 PF，且这笔 MBMS MESSAGE 返回 403，查[通告方向与上报者绑定](mcptt-mbms-status-message-rejection.md)。
