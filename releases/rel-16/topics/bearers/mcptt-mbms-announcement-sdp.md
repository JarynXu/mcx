# MCPTT 客户端收到 MBMS 承载撤告：什么时候才能删除共用的 SDP？

撤告按 TMGI（临时移动组标识）找通告。假设甲、乙两条通告现在都关联同一份本地 SDP。只撤告甲时，客户端丢弃甲的通告，断开甲与 SDP 的关联，停止监听甲对应的通用 MBMS 子信道。乙仍关联这份 SDP，就保留它。这不能判定乙当前是否在监听，尤其不能承诺甲、乙使用同一个通用子信道时乙会继续听到。只有这份 SDP 已经没有任何存储的通告关联，客户端才删除它。

这里处理的是在网 MCPTT 客户端实际收到的 SIP MESSAGE。P-Asserted-Service 须标明 MCPTT 的 ICSI（`urn:urn-7:3gpp-service.ims.icsi.mcptt`），消息还须带 `application/vnd.3gpp.mcptt-mbms-usage-info+xml`，其中至少有一项 `announcement`。客户端逐项判断，不把整个 MESSAGE 当成承载清单快照。

## 这项通告带服务区：按 TMGI 新建或替换

一项 `announcement` 带 `mbms-service-areas`，客户端用它的 TMGI 查已有通告。找到同值就替换旧通告；没有同值就存这项。客户端把该通告与收到的 SDP、GPMS 字段及从 P-Asserted-Identity 取得的参与功能 MBMS 公共业务标识关联。

例如参与功能只更新甲、没有在这份消息列出乙，客户端不能因此删掉乙的通告。对规范所述的更新，发送方沿用甲原来的 TMGI、GPMS 值和初始 SDP；服务区列表可以保留或更新。一般条款还说明收到新通告所带的 SDP 体替换原 SDP 体；这与删除未列出的通告不是一件事。本页不据此推断不同承载之间如何重建内部 SDP 引用。

若这项通告带有本款所述的 MIKEY-SAKKE 保护参数，须按本款处理；校验失败则拒绝并停止后续步骤。客户端继续处理有效通告时，就要检查发送监听状态报告的条件，不必等到进入服务区才检查。监听另有触发条件：进入该承载可用的 MBMS 服务区时，监听 SDP 中 `m=application` 指定的通用子信道。检查报告条件不是保证已报告，更不是收到业务媒体的证据。

依据：§14.2.2.1 及其注（印刷页 464），§14.2.2.3（页 467），§14.3.2 开头及含服务区项的步骤 1(a)–(h)（页 470–471）。

## 这项通告不带服务区：按 TMGI 撤告

真正的撤告是**这一项仍在消息里，有对应 TMGI，但没有 `mbms-service-areas`**；不是整项没出现在这份消息里。客户端丢弃该 TMGI 已存的通告，去掉它与已存 SDP 的关联，停听对应的通用子信道，再检查监听状态报告条件。停听针对条款所指的子信道，不是另给乙发出撤告。删除 SDP 的判据是同一份 SDP 是否仍关联其他已存通告，不是本次 MESSAGE 有没有带 SDP。

如果 usage-info XML 体里的所有通告项都是撤告，参与功能须省略 GPMS 和整个 SDP 体。其中有新通告或更新，也可能与撤告放在同一份消息；不能用整条消息有无 SDP 代替逐项判断。撤告不等于网络停用承载，也不说明客户端已送达报告或业务媒体。

依据：§14.2.2.1（印刷页 464），§14.2.2.4 步骤 1–4（页 467–468），§14.3.2 撤告项的步骤 2(a)–(d)（页 471）。
