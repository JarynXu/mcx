# 离网话权排队与移交：收到授予、用户接受和首包观察

收到排位信息、收到话权授予、用户接受和旧仲裁者收到媒体，是不同的事件。排队接收者收到 Granted 后仍可能等待用户操作；旧仲裁者则以匹配 SSRC 的 RTP 收包结束移交等待。下文按两端状态分别说明，不能把这些观察合并为全组已完成接手。

## 适用范围

- 仅 TS24.380 V19.1.0 §7 普通离网 MCPTT 组呼；§6.2 是在网参与者，不混入。
- 离网呼叫已成功建立，且所需授权、载体、身份及配置已满足；不覆盖 ProSe、系统发现、SSRC 认证、完整安全或编码实现。
- 普通呼叫不自动等同非抢占；排队主链须另满足已判非抢占。排除紧急、迫近危险、广播、system、私呼、dual floor、multi-talker、audio cut-in 和抢占后续。
- 每项结论须同时满足本页共同范围与该项主体、状态、事件及匹配条件；同一项内明示的替代分支分别判断，不要求各角色事件同时发生。收包按到达顺序；没有状态专门过程的消息或媒体丢弃且状态不变，格式错误亦忽略（§7.2.3.1，印刷页 132–133）。
- 不建立任意丢包/并发/隐藏节点下唯一持权或全员成功保证。时限默认值不是部署实值；TS24.483 配置取得及缺失处理不在本页覆盖范围。

这里的 current 和 candidate 分别指本端保存的当前与候选仲裁者 SSRC。Floor Granted 中的被授予者 SSRC 与消息发送者 SSRC 分开判断；离网临时仲裁者仍是一个 MCPTT 客户端。

## 阅读前先看字段差异

Queue Position Info 的初发步骤、接收守卫和编码语义对 User ID、Queued User ID 的用法有差异。下文保留各条实际写法，不能据此拼出无歧义的完整排队准入算法。具体对照见文末“条款差异与未闭合行为”。

## 有人发言时，如何进入队列

### 已有人发言时，普通请求也须先判断是否抢占

适用条件：

- 适用主体及状态：临时仲裁者，O: has permission。
- 收到普通 Floor Request，当前呼叫也为 normal；配置和比较输入已知有效。

按 §7.2.1.2，请求带 Floor Priority 时取请求值、发送者 UserPriority 和 NumLevelHierarchy 的最低值；缺失时使用允许的最小优先级。请求优先级高于当前发言者在获准时确定的有效优先级，会走抢占；当前发言者值相等或更高时才进入本页的非抢占排队/拒绝分支。

- 不将“普通”当作“不抢占”
- 不核配置获取、缺值处理或抢占后续。原文引用的配置项只据本版所述，不表示覆盖 TS24.483 配置过程。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §4.1.1.5；§7.2.1.2，印刷页 23、130、131。

### 排队开关与请求者能力共同决定是否排队

适用条件：

- 适用主体及状态：临时仲裁者，O: has permission。
- 收到按上述政策判为非抢占的 Floor Request。

QueueUsage=false，或 QueueUsage=true 但 F=0/未带 Floor Indicator 时，发 Deny cause #1，携收到的 User ID，Reject Phrase 为 MAY，仍持权。QueueUsage=true 且 F=1 时，未存过的请求须存储；队列未满发 Queue Position Info，队列满发 Deny cause #7，携收到的 User ID、可选原因文字，仍持权。Info 条文明列请求者 MCPTT ID 写入 User ID、请求者 SSRC 写入 queued SSRC，并携位置和优先级。

- 存储步骤列在满队列检查之前，不补回滚或丢弃策略。
- User ID 与 Queued User ID 存在下列源冲突，不能据此声称收发字段链已经闭合。
- 一名用户只可在队列出现一次；本页未核出完整排序、同优先级排序和去重键算法，不把 first 等同 FIFO。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.1；§7.2.3.5.4，印刷页 130、139、140。

### 收到排位信息才按匹配条件转入 queued

适用条件：

- 适用主体及状态：请求者，O: pending request。
- Queue Position Info 的 Queued User ID 等于本端 MCPTT ID。

服务端 SSRC 匹配 current 时，先更新排位，再可提示位置、停 T201、进入 queued。若没有 current，则先更新排位，再将服务端 SSRC 存为 current，然后可提示位置、停 T201、进入 queued。若匹配 candidate，则先更新排位，再把服务端 SSRC 存为 current 并清 candidate，然后可提示位置、停 T201、进入 queued。

- 三个分支按原文顺序判断，不把任意来源的 Info 当作排队确认。
- §7.1 要求排队时通知用户并由用户松开 PTT；§.6.3 的具体位置通知为 MAY，二者不合并成所有通知均可选。
- §.5.4 初发字段与此接收 guard 不一致，保留缺口。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.1；§7.2.3.6.3，印刷页 130、144、145。

## 授予之后，双方分别等什么

### 结束当前发言后，授予队首并携剩余队列

适用条件：

- 适用主体及状态：临时仲裁者，O: has permission。
- QueueUsage=true 且至少存有一个 Floor Request。以下触发互为替代：不再收到用户编码媒体；或 T207 到期。两分支的计时器停止动作不同，分别见正文。

不再收到编码媒体的分支先停运行中的 T206/T207；两分支都请求停止发送 RTP，向参与者发 Granted，User ID 和被授予者 SSRC 取队首并将其移出队列。剩余各项携 Queued User ID、queued SSRC、位置及优先级。把 current SSRC 更新为被授予者，启 T205、C205=1，进入 pending granted。

- §.5.6 标题是 PTT released，正文触发是 no more encoded media；不缩成任意 PTT 事件。
- T207 分支未另列停 T206/T207，不移植。
- 这是选择已有队首，未给完整建队排序算法；发 Granted 不证明接收方已接受或发首包。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.5.6；§7.2.3.5.10；§8.2.5，印刷页 141、142、143、176、177、178。

### 排队者收到 Granted 仍等待本地接受

适用条件：

- 适用主体及状态：排队请求者，O: queued。
- Granted 的 User ID 等于自身，且发送者 SSRC 匹配 current 或 candidate。

匹配 current：请求停止呈现 RTP，T233 未运行才启动，必须通知授予，仍 queued。匹配 candidate：同样停呈现、条件启 T233、通知，另将 current 设为自身 SSRC 并清 candidate，仍 queued。

- 重复 Granted 不重启已运行 T233。
- candidate 分支在用户接受之前设自身 current，按原文保留，不能擅改为发送者。
- 该条未列保存/更新 Granted 携带的全部剩余队列；不把队列传递目标当作已核完整接收状态算法。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.8.6，印刷页 153。

### 接受是用户事件，不是另发 Accept 报文

适用条件：

- 适用主体及状态：排队请求者，O: queued。
- 两个替代事件分别适用：用户要求发送媒体且 T233 正运行；或 T233 到期。用户要求发送媒体不是超时分支的前提。

用户事件下停运行中的 T204、停 T233、current=自身 SSRC、进入 has permission；此条不发 Accept。媒体编码事件随后按既有 §.5.2 启动未运行的 T206 并请求发 RTP。T233 到期则停运行中的 T204、启 T230、进 silence。

- 接受分支不能省略 T233 正运行条件。
- 超时条文未列发送 Release 或清 current/candidate，不补步骤。
- 本地许可与请求发送不等于对端收到媒体。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.8.7；§7.2.3.8.8；§7.2.3.5.2，印刷页 153、154、139。

### 旧仲裁者等待匹配媒体，不等待用户接受报文

适用条件：

- 适用主体及状态：旧仲裁者，O: pending granted。
- 收到 RTP 且包 SSRC 匹配已存 current（移交时已设为被授予者）。

请求呈现该 RTP；停运行中的 T205、T233；启 T203，进入 has no permission。

- 这是该客户端收到匹配 RTP 的观察，不是全部成员听到、语音解码成功或全局唯一仲裁证明。
- §7.1 将新客户端开始发媒体与仲裁角色接手联系起来；本地状态字段变化和远端媒体观察应分别描述。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.1；§7.2.3.7.1；§7.2.3.7.2，印刷页 129、148、149。

### 尚未排队的直接授予不等待 T233

适用条件：

- 适用主体及状态：请求者，O: pending request。
- Granted User ID=自身；按发送者匹配 current、无 current、或匹配 candidate 的原文顺序分支。

三分支均设置 current=自身、停 T201 和 T203、可通知授予、进入 has permission。current 匹配分支另请求停止呈现 RTP，且 T203 仅运行时停；无 current 和 candidate 分支直接列停 T203；candidate 分支另清 candidate。

- 不要把 queued 的用户接受窗口移到该状态；也不要把此处 MAY 通知改为 queued 分支的 SHALL。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.6.7，印刷页 146、147。

## 没有接手或有人取消时

### Granted 重试上限后按剩余队列分流

适用条件：

- 适用主体及状态：旧仲裁者，O: pending granted。
- T205 到期；按 C205 是否达到配置上限及是否仍有排队请求分别判断。

未到上限：重发 Granted，携各剩余排队者身份、SSRC、位置和优先级，重启 T205、C205 加一、留原状态。达到上限且队列仍有请求：C205 重置 1，启 T233，仍 pending granted。达到上限且无请求：C205 重置 1，启 T230，清 current，转 silence。

- 达到上限且无请求这条没有发送 Release；不要与 T233 空队列出口合并。
- 计数包含首发；由收到 Request 触发的额外重发另见下一条，不把计时器重试上限当作任意事件下的总发送次数保证。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.7.3；§7.2.3.7.4；§7.2.3.7.5，印刷页 149。

### 等待窗口结束才处理下一个队首

适用条件：

- 适用主体及状态：旧仲裁者，O: pending granted。
- T233 到期；分别判断剩余队列为空或仍有请求。

仍有请求则给下一队首发 Granted、移除该项，携剩余队列身份/SSRC/位置/优先级，current 设为新被授予者，启 T205、C205=1、留 pending granted。空队列则发携自身 User ID 的 Release，启 T230、清 current、转 silence。

- 旧仲裁者与排队接收者的 T233 启动点不同；不推同步窗口。
- 所列普通分支不自行补 normal Floor Indicator 或候选清除动作。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.7.6；§7.2.3.7.7，印刷页 149、150。

### 移交等待中，新请求不重新排队

适用条件：

- 适用主体及状态：旧仲裁者，O: pending granted。
- 分别处理收到 Floor Request，或本端用户要求发送媒体；后者无需先收到 Floor Request。

Request 的 SSRC 等于 current 时重发 Granted（携剩余队列），重启 T205、C205 加一；不等时发 cause #1 的 Deny，携请求的 User ID，可附 Reject Phrase；均仍 pending granted。本端用户要求发媒体时可通知拒绝，仍 pending granted。

- 此 Request 重发分支未列 C205<上限 guard；不能把 §.7.3 的 guard 直接移植。
- 不把此状态当作仍可自行恢复发言或新增排队的 has permission。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.7.8；§7.2.3.7.10，印刷页 150、151。

### 排队者取消和仲裁端移除是两个观察

适用条件：

- 本端取消：请求者处于 O: queued，收到用户取消指示。
- 远端移除：仲裁者实际收到 Floor Release，User ID 匹配队列项；若处于 O: has permission，另须 QueueUsage=true；若处于 O: pending granted，按该状态单独处理。取消发送与远端收到是不同事件，不合成同时成立的守卫。

请求者发携自身 User ID 的 Release，停运行中的 T204/T233，转 has no permission。仲裁端 has permission 且 QueueUsage=true 时移除匹配项并留原状态；pending granted 的匹配移除也留原状态。

- 本端发取消不证明仲裁端已经移除。
- 获授者在授予时已出队，不能从匹配移除条款推断取消会立即授予下一人。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §7.2.3.8.5；§7.2.3.5.3；§7.2.3.7.9，印刷页 153、139、150、151。

## 如何理解时间窗口

### 计时配置不等于固定接手期限

适用条件：

- 适用主体及状态：分别适用上述参与者及计时状态。
- 部署有有效 T205、C205、T233 配置；这里只核本版表列取值和关系。

T205 默认 80 ms，可配置且与 D2D sidelink period×2 有关；C205 默认上限 4，可配置，计数从 1 开始。T233 默认 3 s、最大 5 s，可配置；表建议 T205×C205+T233 小于 T203，强度为 should。

- 不据默认值承诺固定总耗时或所有丢包情形下接手成功。
- 表将发送/接收 Granted 列为 T233 启动原因，但旧仲裁者具体 §.7.4 在 C205 上限时启动，接收者 §.8.6 收 Granted 启动；保留概述/具体过程粒度差异，不统一提前启动。
- TS24.483 配置默认回退及缺值处理未核。

规范强度：SHALL；明确标出的 MAY/SHOULD 和证据边界除外。

依据：3GPP TS 24.380 V19.1.0 §11.1.2；§11.2.2；§7.2.3.7.4；§7.2.3.8.6，印刷页 240、241、249、149、153。

## 条款差异与未闭合行为

### 排位信息的身份字段不一致

初发 Info 将请求者身份置 User ID；接收 pending guard 读取 Queued User ID。编码语义规定 User ID 为发送者、Queued User ID 为排队者。查询响应 .5.8 区分两字段；queued 的 .8.3 candidate 分支却读 User ID，current 分支读 Queued User ID。

保留逐条字段，不静默改名；只发布限定动作，不声称完整一致的排队准入线。

依据：§7.2.3.5.4；§7.2.3.6.3；§7.2.3.5.8；§7.2.3.8.3；§8.2.12，印刷页 140、144、145、142、152、186、187。

### 传递队列不等于已核完整导入过程

概述说明移交队列，授予消息携完整剩余队列；所核 queued 接收/接受状态未另列完整队列导入、去重与排序步骤。

不声称携带即已完成所有接收状态更新，也不将此限定检查上升为整份规范绝无算法。

依据：§7.1；§7.2.3.5.6；§7.2.3.8.6；§7.2.3.8.8；§8.2.5，印刷页 130、141、153、154、176、177、178。

### 候选授予与清理动作须按原状态区分

candidate 授予分支在用户接受前已设自身 current；T233 超时条文未清 current；接受条文未列停 T203。

按正文保留；不自行补清理。T203 表的正常停止描述另有状态摘要，不擅定全部冲突计时优先级。

依据：§7.2.3.8.6；§7.2.3.8.7；§7.2.3.8.8，印刷页 153、154。

### T233 表格概述与具体启动事件

表列 Granted 收发启动原因，具体仲裁端启动位于重试上限；接收端在收到合格 Granted 时启动。

分别交代实际事件，不自造同步或统一入口。

依据：§7.2.3.5.6；§7.2.3.7.4；§7.2.3.8.6；§11.1.2，印刷页 141、149、153、241。

## 覆盖边界

- 仅覆盖列明的普通离网排队与移交事件，不是全部 O 状态机或完整可实现协议。
- 未覆盖 T204 排位查询重试、全部 Deny/Granted-to-other/RTP 分支及丢包后的完整重选。
- 未闭合队列排序、并列排序、满队列存储回滚和完整队列导入算法。
- 不补 SSRC 认证、安全、配置获取或与其他固定版本组合的互操作保证。
