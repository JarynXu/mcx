# LMC 怎样主动拉取自己的位置配置？

**LMC 向 LMS 发 GET，LMS 完成业务授权后返回适用的位置配置。** 这里读 TS 24.283 V19.3.0（Rel‑19 Stage 3）的 `ConfigurationRequest`。这是终端主动取配置，不是 LMS 推送，也不是替另一用户改配置。

## 调用方和地址

LMC 可在需要时向 LMS 发 **`GET {apiRoot}/lms-reporting/v1/configurations`**，不必等新推送或再注册一次。§4.2 要求先做 LMS 注册才能使用位置服务，IMS 注册不能替代；“随时请求”没有免去业务授权，也不是随时都能取到。查标准不用抓包；查某笔现场 GET，不要求同一段记录也抓到先前的注册 201。

用 LMS 的集合地址，`apiRoot` 按 §7.1.1 的引用取得。不是注册 201 的 `Location` 或 `locationConfigUri`、`locationRequestUri`。资源表没有为这笔 GET 定义查询参数、请求正文或在表中另列专用头；A.2 的 GET 也没有请求体或参数声明。不要在路径或 GET 正文里自行加目标 `mcServiceId`、注册 ID，或把这个集合读成配置列表。**表列 n/a 不等于免传 Authorization 或其他适用标准头。**[§§4.2、6.2.2.6、7.1.1、7.1.2.2 与 7.1.3.4，印刷页 12、20–21、32–33、38–39](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=22)；[A.2 `/configurations`，印刷页 77](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=78)。

## LMS 怎么认请求方？

- **业务身份：**LMC 按 §7.1.9 通过 TLS 发请求，带所有适用的 Bearer 访问令牌。LMS 确定认证发送者并按 §6.2.2.6.2 调用业务授权；返回适用于该 LMC service ID 的配置。令牌可涉及多个有效 MC service ID，条款没有给出多 ID 冲突、排序、合并或逐 ID 返回的方法。
- **实例身份：**§4.3.1 另要求 LMC 向 LMS 发请求时带 MCLOC client ID，用来区别同一用户的各个客户端。§7.1.3.4 和 A.2 的 GET 未给出这个 ID 的专用传输位置。保留两处约束，不自行指定一个查询参数、头名或 GET 正文，也不因本操作表未列而删去一般要求。实例 ID 不是令牌或业务授权。
- **网络身份：**这节定义的是 **LMC 角色**的 GET。调度台等设备可以承载 LMC；不能只因有网络节点的 PSI、断言头或业务服务器在通用准许名单上，就把此调用改成无 LMC 的网络请求，或用网络身份替掉本笔的 Bearer 条件。

[§§4.3.1–.2、5.3.1–.2、6.2.2.6.2、7.1.9，印刷页 12–14、21、60](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=14)；[§7.1.3.4、A.2，印刷页 38–39、77](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=39)。

## 200 证明取到了什么？

| 实际看到的证据 | 能判断什么 |
| --- | --- |
| LMS 对这笔 GET 发出 **200 和一份 `LocationConfiguration`** | 是业务授权通过分支的配置返回。这份配置适用该次 LMC service ID；只见 LMS 发出不等于 LMC 已收。 |
| 发起 LMC 实收对应 **200 和可读的配置体** | 能确认取得这份配置。只有 200 状态、代理结果或缺少正文的抓包不能说明配置内容；确证完整 200 无体不符合这里的成功响应。 |
| LMS 对同笔 GET 回 **401** | 正文的未获业务授权分支回 401。不从孤立状态码猜哪条令牌或身份规则失败，也不判已有注册被删除。 |

A.2 列有通用 403、404 等错误，流程没有为“无适用配置”指定这些码，也没有定义无体成功或回空配置作为兜底。307/308 按 §7.1.10 是指向**同一 LMS 的另一服务实例**的重定向，不是已取到配置。节标题和路径是配置；§7.1.3.4.1 的简介误写为报告集合，A.2 的 200 描述误写为位置报告已提交；方法、响应表和 schema 都给 GET 的 `LocationConfiguration`。不能据误写改成 `MCUELocation` 或调用报告发布。[§6.2.2.6.2 与表 7.1.3.4.3.1-3，印刷页 21、38](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=39)；[§7.1.10、A.2，印刷页 60、77](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=78)。

## 拉到配置以后，规则已经生效吗？

**没有这个证据。** GET 章节没有规定 LMC 收到后如何保存、设置触发或启动计时器，也没给配置版本、刷新上限或与并发推送的先后。返回的适用配置不一定刚改过；不能拿 GET 200 的时间当改动时刻。若另有应用或报告证据，再分别核对对应实例和配置。

共享类型的表要求紧急或非紧急触发条件至少一种，A.2 没有列 `required` 或编码此组合；可选历史字段在表中写 `locationHistory`、A.2 写 `historyReporting`。A.1 的附录优先限信息元素和方法的**编码**，未表达的程序和适用条件仍适用。不能把 A.2 未列必填当成空配置体已满足成功条件。不造字段别名。可选 `configScope` 的 FULL／UPDATE 分别描述替换和追加，但本 GET 没给缺省值，也没把推送的处理步骤移到取回响应后。[表 7.1.6.2.3-1、§7.1.6.3.3、A.1–A.2，印刷页 43、58–59、73、78、86](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=44)。

问 **LMS→LMC** 推送及其收件、处理规则，看[注册与配置回调](lms-registration-configuration.md)。问 **A 怎样请 LMS 改 B 的配置**，看[改另一用户的配置](lms-target-configuration-change.md)。本机拉取成功不证明上述任一事务发生或某次改动生效。
