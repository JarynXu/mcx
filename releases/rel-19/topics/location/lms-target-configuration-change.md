# LMS 改另一用户的位置配置：怎么知道改动到了哪一步？

**请求方收到应答，不等于目标终端收到配置。** 在 TS 24.283 V19.3.0（Rel‑19 Stage 3）里，请求方 A 向 LMS 发 `LocationInfoConfigRequest`。A 有权改 B 的配置且前序步骤成功后，LMS 才向 B 的 LMC 另发 `ConfigurationNotify`。查标准不需要抓包；判断现场进展，要分开核对这两笔 HTTP 事务。

## A 发什么，LMS 查什么

A → LMS：`POST {apiRoot}/lms-information/v1/configrequest`，JSON 正文为 `LocationConfiguration`。没有定义查询参数。过程正文称这笔 POST 建立与变更请求关联的资源。不用 `GET /lms-reporting/v1/configurations`（拉取自己的配置）、`/requests`（要位置），或 `/subscriptions`（订阅位置）代替这笔请求。

- **指定 B。** 这笔请求中的 `mcServiceId` 必须填目标用户 B，不填 A。通用数据类型把此字段列为可选，A.2 也未把它列为必填，还把它描述为请求者字段；这不取消本操作对目标的要求。正文要求：触发条件的子结构定义了 `triggerId` 时，复用已有且有效的值，否则生成唯一值。印刷表要求紧急或非紧急触发条件至少一种。
- **识别 A。** A 是 LMC 时，带适用的全部 Bearer 访问令牌；LMS 验证令牌，以令牌派生的 MC service IDs 识别 A。任一验不过，LMS 返回 401 并停止。A 是 MC 业务服务器、IWF 或另一 LMS 时，正文要求它发送 `X-3GPP-Asserted-Identity`，值为网络实体自己的公共服务标识，不是 B。A.3 的该操作仍列 `BearerAuth`；接下来的令牌、应答和重写细节则以「从 LMC 收到 POST」为入口。这里不把 LMC 的后续分支套给网络发起方，不因出现该头判定已通过身份检查，也不为网络发起方裁定两种材料是否必须同时发送。
- **授权 A 改 B。** 通过令牌验证只是识别与认证，不是获得改动权限。LMS 按本地策略，或查 **A 的位置用户配置文档**：同一规则的条件中有匹配 B 的 `identity`，动作把 `allow-change-location-configuration-of-users` 设为 `true`。按文档判定不满足时，后续忽略该目标。不能用 B 的位置分享许可代替 A 的配置变更许可，也不从 A.3 通用错误表给这个目标分支指定 403。

## 200、201、204 分别看哪笔事务

| 证据 | 本版能确认什么 |
| --- | --- |
| **LMS 对 A 的 POST 回匹配 200** | §6.3.2.7.2 步骤 4 在 LMC 的令牌验证通过后发 200；随后才识别 B、查 A 对 B 的变更权限。按这段程序，200 不证明目标通过权限检查、配置已改或通知已发。 |
| **LMS 对 A 的 POST 回匹配 201** | 表 7.2.3.5.3.1-3 描述资源更新成功，响应类型写 `LocationInfoConfigRequest`；A.3 把 201 描述为请求成功提交，正文引用 A.2 的 `LocationConfiguration`，没有列 `Location`。保留差别；不把 201 当成另一个必须到达的业务完成应答，不从这些文字判定实际部署已给 B 更新、下发或启用。 |
| **B 对 LMS 的配置 POST 回匹配 204** | 这是另一笔 POST 的收件确认。获准并完成前序步骤，LMS 更新目标配置，将用于通知的 `mcServiceId` 从 B 改为发起者 A，再考虑现有 LMS 策略，按 `ConfigurationNotify` 向 B 在 LMS 注册的 `locationConfigUri` 发配置。正文步骤 7、8 都提到同一身份替换；这不产生两次通知的依据。 |

确认末段实际到达，要看到 **B 的 LMC 对该次配置 POST 的匹配应答**，或同一 LMC 实收该配置的独立证据。只有 LMS 的发出记录不能确认到达；孤立的回调 204 也不能证明它由某次 A 的请求触发。请求方、目标用户、目标 LMC 和资源别串线。收件不证明目标保存了配置、启用了触发或已经发布报告；要查这些动作，需要对应的目标处理记录或实际报告；仅看到可复用的 `triggerId` 不能把报告归到这次改动。该过程没有给目标用户的多设备分发、未知回调或投递失败定义专用返回码或后续算法。

## 有没有「临时改一下，到点恢复」？

**这项 POST 没有定义配置到期、取消或自动恢复。** `FULL` 和 `UPDATE` 在配置通知中分别表示替换旧配置和追加；要移除配置项需 `FULL`。这里不为省略 `configScope` 指定默认值，也不把 `FULL` 当成到期恢复机制。注册和订阅的 `expTime` 各管各的资源；LMC 收配置后启动的最短**上报**间隔不是配置期限。

正文和表的可选 `locationHistory` 为真，是在目标收到适用配置后、报告无法成功送出时本地留存的规则；不填或为假不建立这项必存义务。A.3 引用的 A.2 schema 把字段写作 `historyReporting`。没有依据把两种拼法设为别名、同时发送，或把它当作配置有效期。[§§6.2.2.5.2、7.1.6.2.3、7.1.6.3.3 与表 7.2.6.3.3-1、A.2–A.3，印刷页 20、43、58–59、78、92–93](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=44)。

本版 §7.2.2.1 将 LMS_Information 的 OpenAPI 指到 A.4，实际定义在 A.3。A.1 仅在信息元素及方法**编码**不一致时给附录优先；规范中未写入 OpenAPI 的程序和适用条件仍有效。不能用 schema 省掉目标或业务检查，也不据此安排 200、201 双回或断言部署会接受两种成功码。[表 6.1-2、§7.2.2.1、A.1、A.3，印刷页 16、61、73、89](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=74)。

问本机注册或配置回调，查[注册与配置回调](lms-registration-configuration.md)。本机拉取则是[§6.2.2.6.2，印刷页 21](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=22)的 GET。若问题是单 MC 系统里**哪些触发可以覆盖、取消后恢复哪份配置**，查 [TS 23.280 V19.10.1 Stage 2 的触发覆盖](trigger-override.md)，不从该流程为此 HTTP 操作补到期或取消规则。要判断目标实际提交的位置，查[位置报告提交](lms-location-report-publish.md)。
