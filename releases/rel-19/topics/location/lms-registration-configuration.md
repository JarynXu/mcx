# LMS 注册与位置配置回调：201 和 204 各确认什么？

**注册成功不等于配置已下发。** 这里说的是 Rel‑19 **TS 24.283 V19.3.0 Stage 3** 的 LMS_Reporting。LMC 是终端侧的位置管理客户端，LMS 是位置管理服务器。

按[§4.2，印刷页 12](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=13)，LMC 要先向 LMS 注册才能使用该规范所述的 MCLoc 服务。查规范不要求先有抓包；判断一笔实际事务时按下列证据。

| 观察到的事务 | 能确认什么 |
| --- | --- |
| LMC 向 LMS 发 `POST {apiRoot}/lms-reporting/v1/registrations`，LMS 对这一笔注册回 `201 Created` 和 `Location` | LMS 创建了该 LMC 的注册资源。`Location` 给出**注册资源**的 URI，不是配置回调地址。 |
| LMS 向已注册 LMC 的 `locationConfigUri` 发另一笔 `POST`，正文是 `LocationConfiguration`；LMC 对这笔回调回 `204 No Content` | 这个 `204` 确认**收到这份配置**，不是注册成功码。只有 LMS 的已发送记录，尚不能确认终端收到；也不能判定送达失败。 |

分别见[§6.2.2.2.2，印刷页 17–18](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=18)、[§§7.1.1、7.1.3.2，印刷页 32、34–35](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=35)和[§7.1.5.2 的回调及响应表，印刷页 40–41](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=42)。

注册 201 应带 `Location`。注册 201 的说明要求带该头，§7.1.3.2.3.1 对应的小表却列 `n/a`；规范性附录 A.2 把它列为必需，编码按 A.1–A.2。只看到匹配 201、捕获里没有这个头，不能还原资源 URI，也不能断定实际消息漏发了头。若完整响应确实省略，不能称它是符合该要求的完整成功报文。[印刷页 35、73–74](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=74)。

### LMS 什么时候推？终端收到后做什么？

LMS **可以**在成功创建注册资源的分支发起配置通知，也可在 LMC 注册期间决定发新配置。条款没有要求每次注册都推、没给首次推送时限，也没规定两个 HTTP 事务在 LMC 的到达顺序。LMC **实际收到**配置才进入处理步骤：按配置范围保存，设置上报触发条件，启动最短上报间隔计时器。这个计时器不是推送时限。回调 `204` 只证明协议上的收件确认，不证明规则已执行、定时器已启动或已发位置报告。[§6.2.2.2.2，印刷页 18](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=19)；[§6.2.2.5.2，印刷页 20](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=21)。

对日志时要对上**角色、操作、同一事务**。LMS 在注册请求里取得 `locationConfigUri`；`locationRequestUri` 则用于索要报告。续期的 `204`、拉取配置的 `GET /configurations` 的 `200`、IMS SIP 注册的成功都不能当作配置回调收件。LMC 的独立实收记录也可确认收到。只分析回调时，不要求同一份日志也抓到之前的 `201`；应有证据表明这是发给已注册 LMC 的那笔配置通知。[§6.2.2.5–.6、§7.1.3.3.3.1 和 §7.1.5.1，印刷页 20–21、35–36、40](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=41)。

同一注册若只见 `401`，能确认请求被拒，不能仅凭状态码确认具体原因。已核实在注册的令牌校验步骤失败，才可用 §6.2.2.2.2 的停止分支解释所见结果。

## 重启或注销后，要换 MCLOC client ID 吗？

**不用因一次重启或失去业务授权给同一 LMC 实例换 ID。** LMC 首次使用时分配自己的 MCLOC client ID。§4.3.2 要求保留这个 ID：LMC 有 LMS 业务授权时、未获授权但所在 UE 开机时，以及 UE 关机和重新上电时。该条的注另写，UE 恢复出厂设置不保留旧 ID。它没有给卸载重装、换设备、迁移实例或恢复备份规定同样的行为，也不要求 LMS 因恢复出厂设置删除旧资源。[TS 24.283 V19.3.0 §4.3.2，印刷页 13](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=14)。

| 标识 | 用来确认什么 |
| --- | --- |
| **MCLOC client ID** | 区分 LMC 实例。同一用户可有多个 LMC；不把它们合并为一个实例。LMC 发给 LMS 的请求应带这个 ID；它不是用户或认证凭据。对比重启前后的实际 ID，先核同一 LMC 实例，不用同用户名、UE 标签或回调 URI 代替。 |
| **MC service IDs** | 来自用户认证的业务身份。没有一个专供 LMS 或 LMC 使用的 MC service ID。LMC 与 LMS 交互要给出当前可用的业务 ID；本次注册通过全部适用的 Bearer 令牌让 LMS 识别发起者。LMS 给新注册资源关联的是已获它授权的 MC service IDs，不由实例 ID 或一份令牌推断已获所有业务授权。 |
| **注册资源 URI** | LMS 对匹配注册 POST 回 `201 Location`，用来标识该次创建的资源。实例 ID 保留不等于资源仍在、旧 URI 可继续用或授权仍有效；要确认实际资源，另看[注册的到期、续期或注销](lms-registration-maintenance.md)。 |

`pei` 和 `supi` 在注册正文中是可选设备／订阅标识。LMS 可在经 Le 向位置服务网络索取位置时使用它们；它们不替代实例 ID、Bearer 业务身份或注册资源 URI。其他消费位置的网络实体（如 MC 业务服务器、IWF、另一 LMS）也要给本规范的 API 分配 MCLOC client ID；§5.3.1 也允许调度台等设备承载 LMC。开关机和出厂重置的句子写的是 UE；不从它们推导其他设备或网络实体的保存规则。[§§4.3.1–.2、5.3.1、6.2.2.2.2、表 7.1.6.2.2‑1，印刷页 12–14、17–18、43](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=13)。

**核 API 字段时，按该操作的数据类型读。** §3.1 把 MCLOC client ID 定义为识别具体实例的全局唯一 UUID URN；§4.3.2 将生成引用到 RFC 9562 §4.2。本版注册正文写 `mclocClientId`，表及 A.2 的 `LMCRegistration` 写必带的 `mclocClientID` 字符串。A.2 在 `MCUELocation` 中用 `mclocClientId`，引用 `MclocClientId` 的 `string` 和 `format: uuid`。A.1 的附录优先只限 API 信息元素和方法的编码。这不是一个同时兼容两种字段名的约定，也不能用报告的 schema 为注册补上固定前缀、强制 UUID 版本或服务端拒绝码。只需查规范，不用先有抓包；要验一次实际提交，则看该操作的真实字段和同一实例。[§3.1、§§4.3.2、7.1.6.2.2、.49、A.1–A.2，印刷页 11、13、43、56、73、77–78、86–87](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=12)。

## 初次登录和收到配置，怎样区分这两种上报触发？

**它们是 LMC 上报位置的两个可选事件，不是要求 LMS 下发配置的条件。** 这里看 TS 24.283 V19.3.0 的 `LocationConfiguration`。先核这台 LMC 当时适用的 `TriggeringCriteria`：紧急时读 `emergencyTriggeringCriteria`，非紧急时读 `triggeringCriteria`。其中的 `signallingEvent` 可分别配置以下子项；有配置还要看实际事件。[表 7.1.6.2.3-1、.4-1、.40-1，印刷页 43–44、54](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=55)。

| 生效配置中的子项 | 对哪件事起作用 |
| --- | --- |
| `initialLogOn` | 初次登录可触发上报。表和 A.2 没指定它对应 IMS SIP REGISTER、LMS 注册 POST 或 MC 业务授权，也没给重新登录或续期的等价条件。单看其中一笔成功不能认定这项事件发生。 |
| `locationConfigurationReceived` | LMC 收到位置配置可触发上报。只有 LMS 发出、LMC 取得注册 201，或配置只是保存在用户档，都不能证明它收到这份回调。配置回调的匹配 204 可确认收件，不证明刚收到的这份配置已生效，也不证明它自身新增的触发已经适用于本次收件。 |

**核对改动和 `triggerId`。** `ConfigurationNotify` 下发 `LocationConfiguration`；`triggerId` 放在触发子项上，不是整个配置共用一个触发 ID。子项已有且仍有效的 `triggerId` 要复用；没有或无效时为该子项分配新的唯一值。实收配置后 LMC 按 `configScope` 修改并保存配置、设置触发条件并启动最短上报间隔计时器。`UPDATE` 是向现有配置追加，正文没有规定省略某个旧子项就删掉它；要删除该项，用 `FULL` 提供替代配置。只有对同一 LMC 的实际应用证据才能确认删掉了旧项。已发送 `FULL`、只见其 204、缺少 `configScope` 或看到 ID 变化，都不能确认删除成功；也不据此定义空配置有效或老 ID 的回收。[§6.2.2.5.2，印刷页 20；表 7.1.6.2.43-1、.46-1，页 54–55；§7.1.6.3.3，页 58–59](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=21)。

要判断实际报了什么，核同一 LMC 的适用配置、事件和实际报告。报告中能和该配置子项对应的 `triggerId` 可用于追溯所报触发；相同 ID、没有 ID、配置收件或配置改动本身，都不能单独证明这是唯一触发、已发布、LMS 已接受或刚测到位置。印刷表把这两个子项的 `triggerId` 标为必需；A.2 定义该属性却未声明 `required`。报告过程列了触发 ID 数组，报告表又把整组标为可选。分别读这些定义，不把它们合成字段省略或输出条目数的通则。[§6.2.2.8.2、表 7.1.6.2.49-1，印刷页 22、56；A.1–A.2，页 73、83–84、86](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=23)。

查规范无需抓包。现场不要把配置收件、采用配置、匹配事件和发报告算成一步。原文没规定同一回调刚启用的收件触发应如何评估、一次性事件怎样保持到计时器到期、配置拒绝后怎样重试，或收到这份配置到发包的固定时限。查实际事件发布，另看[上报及最短间隔](lms-location-report-publish.md)；问 A 请求 LMS 改 B 的配置，另看[跨用户请求与目标回调](lms-target-configuration-change.md)。

## LMS 特性协商与空错误表

**这版没有可用来协商的 LMS 特性值。空的本地错误表不免除通用 HTTP 错误要求。** 这里读 TS 24.283 V19.3.0 的两套 Stage 3 API：`LMS_Reporting`（`lms-reporting/v1`）和 `LMS_Information`（`lms-information/v1`）。先分清接口、操作和 HTTP 方法。查规则不需要抓包。回调地址按操作判：例如 Reporting 向 LMC 索要报告，用注册中的 `locationRequestUri`；Information 发位置通知，用查询或订阅的 `locationNotificationUri`。不要求回调 URI 含这两个服务前缀。

| 看到什么 | 怎样判断 |
| --- | --- |
| **Supported Features 表是空的** | §7.1.8 和 §7.2.8 都指向 TS 29.500 §6.6 的扩展机制，但本版未定义这两套 API 的任何特性。表 7.1.8-1、7.2.8-1 没有特性号或名称；路径里的 `v1` 是 API 版本，不是特性号。A.2、A.3 的本地 API 声明没有定义这两套服务的特性协商字段。不从其他 API 或版本借编号，不自填 `0` 或空串，也不据此规定收到其他值时一律拒绝或忽略。没有特性协商值，不等于业务不支持某操作，也不免除认证。 |
| **Application errors 表是空的** | §7.1.7.2、§7.2.7.2 没有本服务另加的协议错误处理步骤，表 7.1.7.3-1、7.2.7.3-1 未列本服务另加的应用错误。§7.1.7.1、§7.2.7.1 仍要求按 TS 29.501 §4.8 支持通用错误响应。TS 29.500 表 5.2.7.2-1 中的通用协议／应用错误，只在表 5.2.7.1-1 将相应状态码列为**这个 HTTP 方法**的必选项时，才是此处要求支持的错误。不要把总表全部状态码移给每个方法，也不从本页另编完整码表、错误正文、超时或重试。 |

[§§7.1.1、7.1.7–.8，印刷页 32、59–60](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=60)；[§§7.2.1、7.2.7–.8，印刷页 60–61、71–72](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=72)。

**具体操作的错误分支照常适用。** `POST /registrations` 中任一访问令牌验不过，LMS 回 401 并停止处理这笔注册；`POST /subscriptions` 通过前序身份检查、确认入口三类目标数组均空时，LMS 回 403 加该分支的 `Warning`。只看孤立的状态码不能认定原因；创建订阅的两种 403 另读[位置订阅](lms-subscription-notification.md)。两张资源的 POST 成功表都另注通用必选错误也适用，A.2、A.3 的 POST 定义也列公共响应引用。不把成功表或空的应用错误表当成服务器只会回 201，也不把订阅的 `Warning` 套到所有 403。[§6.2.2.2.2、§6.3.2.3.2、表 7.1.3.2.3.1-3、表 7.2.3.3.3.1-3，印刷页 18、27–28、35、64](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=36)；[A.2/A.3，印刷页 73–74、90](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=91)。

**原文的名字不要当成第三套 API。** §7.1.7.1 两次写 `LMS_Registration`，外层 §7.1 和相邻小节写 `LMS_Reporting`，A.2 也列后者。保留写法差异；不只按这个词把通用规则缩到注册 POST，也不另造注册专用路径。A.1 的附录优先限信息元素与方法的编码；不能因此删掉其他小节的操作条件。若问某次[向 LMC 要位置报告](lms-location-report-request.md)是否收到、能否给出所要数据，另核实际回调和报告；没有可协商特性不回答这个问题。[§§7.1.7.1–.3、A.1–A.2，印刷页 59、73](https://www.etsi.org/deliver/etsi_ts/124200_124299/124283/19.03.00_60/ts_124283v190300p.pdf#page=74)。
