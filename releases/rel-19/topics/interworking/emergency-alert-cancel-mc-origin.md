# MC 用户取消互通紧急告警：发起端何时确认，服务器向 IWF 发几条？

**步骤 3 回给原告警取消的发起端 client 1；步骤 4 是 server 另向 IWF 发请求。NOTE 3 允许 3、4 任一先做。** 发 3 不要求先等 IWF 回 5 或成员 ACK。IWF 收到一条还是逐人的请求，看实际归属方式。查规范不需要抓包。[TS 23.283 V19.5.0 §10.6.5.2，图、步骤 1–8 和 NOTE 3，印刷页 144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。

## 先对上原告警和原取消请求

MC service client 1 此前成功发起过紧急告警，且**现在仍处紧急状态**。client 2 已归属于该 MC service 组。IWF 已掌握互通组信息，且配置了 MC 和 LMR 之间的组、用户身份映射；组可定义在 MC 或 LMR。server 可能已帮 LMR 用户做显式或隐式归属，原文没把执行这项操作写成必需。NOTE 1 的身份转换和协议翻译适用于经过 IWF 的跨 MC/LMR 信令，不是 MC 系统内部的客户端消息。[§10.6.5.2 前提和 NOTE 1，印刷页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=144)。

步骤 2 是 client 1 请求 server 向**自己先前发送告警的同一组**发取消。server 解析组 ID、判断成员归属并检查是否需要通知 IWF。这里有已归属成员的本属在 IWF，**本场景必须涉及 IWF**；仅知道组是互通组，或只知道图中的 client 2 已归属，不能代替这项判断。

NOTE 2 说的是原 **MC service 告警取消请求**还可带取消组进行中紧急状态的指示。带了也仍走告警取消。本节没有规定把该指示自动复制到 IWF 步骤 4，也没有规定仅凭指示或回执就认定组状态已清。若原请求是组紧急状态取消，按组定义另查对应流程。[步骤 1–2 和 NOTE 2，印刷页 144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。

## 把三条消息腿分开

| 步骤 | 看什么 |
| --- | --- |
| **2 → 3：原发起端** | client 1 发告警取消请求，server 回给原 client 1，确认这次原请求。步骤 3 还写明 client 1 重置自己的紧急状态。仅看到 server 发 3，不证明 client 1 实收或确实重置，更不证明组或其他客户端的状态已清。 |
| **4 → 5：IWF** | server 发 4，IWF 回 5 确认原请求。IWF 实际为该组的 LMR 用户代理归属则发一条；若 server 已收到 LMR 用户的逐人归属，则向 IWF 为每名已归属 LMR 用户各发一条。按实际归属，不按静态组名单、MC 人数或图的一根箭头算。混合或未知归属方式不从这里补规则。 |
| **6 → 7 → 8：已归属 MC 成员** | server 向已归属组成员的 MC service client 发 6，步骤 7 告知成员 client 1 的告警已被取消。图只画 client 2，正文称已归属成员，不能据图限定只发一人，也不从图补给发起者的额外成员消息。实际收到对应 6 的客户端回 8；组播呼叫场景不发这种成员确认。 |

NOTE 3 只放开 **步骤 3 和 4** 的相对顺序，不改配对。发起端确认不固定等 4 或 5；组播例外只省 **8**，不跳过发起端确认、IWF 确认或成员处理。[图 10.6.5.2-1、步骤 2–8、NOTE 3，印刷页 144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。

IWF 告警取消请求表 10.6.1.9-1 必带 **取消者 MCPTT ID** 和 **关联组 ID**。第二个 MCPTT ID 标 O，但表注要求取消他人告警时带被取消者 ID；不带时目标是取消者本人，这条取值规则不是授权。该表组级可选项用“组的进行中紧急告警”，具体流程 NOTE 2 用“组的进行中紧急状态”。保留用词差异，不据此添字段或从原请求自动推断 IWF 携带值。应答表 10.6.1.10-1 只列两个必带 ID，没有目标用户 ID、组级指示或 `Result`。两张表通用方向为双向，本页的 4/5 方向按图。[两张表，印刷页 119–120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=121)；[NOTE 2，印刷页 144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。

查现网分别配 **2/3、4/5、各端 6/8**。同组同取消者可能对应多个逐人 IWF 请求，两项 ID 不够判定某笔 5。实际匹配回发可佐证原请求到了发应答的一端；不能代替另一端实收。IWF 回 5 不证明每个 LMR 用户实收或本地清状态；实际有 8 也不代证所有成员通知。组播缺少 8 不等于未收到 6。信令不用媒体来代证，发起端本地状态、LMR 应用、组状态、成员显示和媒体另查。[步骤 2–8，印刷页 144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。

## 换主请求或发起侧，就换入口

- **LMR 用户发起告警取消：**查 [§10.6.5.1](emergency-alert-cancel-lmr-origin.md)。该支 IWF 发 1、server 回 2，NOTE 3 是 2 与成员请求 3 可任一先，不用本页的 3/4 和出向 IWF 分发规则。[印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)。
- **MCPTT 用户主要取消组紧急状态：**按组定义读 [MCPTT 定义组 §10.6.2.3.2](emergency-group-state-cancel-mcptt-origin.md) 或 [LMR 定义组 §10.6.2.3.4](emergency-group-state-cancel-mcptt-origin-lmr-defined.md)。例如后者发起端确认 7 在该支 IWF 应答 4 后，还看继续条件，不套本页告警的 3/4 可任一先。[印刷页 129–132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=133)。
- [原生 MCPTT 的告警取消](../emergency/standalone-alert-cancellation.md)另读 Stage 3。本页是互通 Stage 2，不给 SIP 编码、LMR 内部执行、拒绝码或重试。
