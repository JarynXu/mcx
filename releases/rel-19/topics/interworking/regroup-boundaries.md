# 跨 MC/LMR 重组：接纳、所有权与信息边界

适用：Rel19，TS23.283 V19.5.0，Stage2 MC/LMR 互通。仅下列结论已对照原文。

MC 发起的重组要求客户端已取得组成组配置，且 MC 与 IWF 各已定义至少一个 MC 服务组。本次用了哪些组，另看请求。GMS 检查用户授权和组策略；临时组输入会被拒绝，IWF 也可因组成组处于紧急状态、已参与重组，或不支持相关能力等条件拒绝，不能把请求发出当成接纳（§10.2.2.2，步骤1–4）。

这些跨系统流程不会由 IWF 或 MC GMS 向对侧分享各自管理组的用户信息（§10.2.2.2 步骤4；§10.2.2.3 注）。实际执行重组的 GMS 拥有产生的临时组（§10.2.2.4）。

## 重组的应答、成立通知和撤组通知分别证明什么？

**看这一笔应答的是哪件事。** 接纳重组、通知对方临时组信息、回应撤组通知，是三个不同的操作。这里查 **TS 23.283 V19.5.0，Rel‑19 Stage 2** 的 IWF‑1，端点是 **组管理服务器（GMS）和 IWF**。§10.2.1.2–.7 的六张表均列两个方向。只查一条已识别的消息，不用先找到对应回复；同方向、同组或同一个 Result 名字都不能决定消息类型。例如撤组通知 .2 和查组配置 .8 都可只列一个组 ID，含义不同。

| 要查什么 | 请求／通知 | 对应类型的应答表 |
| --- | --- | --- |
| **申请重组（.4/.5）** | .4 只列必带的组成组 ID 列表（MC service group ID list）。它不是新临时组的 ID，也不是用户列表。 | .5 列 M 的组成组 ID 列表和 Result（接纳或拒绝）。单个临时组 ID 在表中标 O，表注规定：**Result 表示重组成功时必须带，否则不得带**。不能只看 O 当任意省略，也不能只凭没抓到这个 ID 判断失败。 |
| **通知临时组（.6/.7）** | .6 同时列 M 的组成组 ID 列表和临时组 ID；Priority level、Security level 都是 O，描述的是临时组要求的级别。 | .7 也列这两个 M 的组字段，**Priority level、Security level 都为 M**；不列 Result。通知没带这两项，不能按表把应答的 M 也视为 O。这张表没给如何确定、补齐或沿用具体值的规则。 |
| **撤组通知（.2/.3）** | .2 只列 M 的被撤临时组 ID，不列组成组或成员名单。它是撤组通知，不是要某人退出呼叫的请求。 | .3 列 M 的临时组 ID 和 Result。这个 Result 指**通知的成功或失败**，不是说哪个组成组被删除、用户已退出或整通呼叫释放。 |

[接口、撤组通知与重组请求／应答，§10.2.1.1–.5，印刷页 23（PDF 第 24 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=24)；[临时组通知、应答和查组配置对照，§10.2.1.6–.8，印刷页 24（PDF 第 25 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=25)。

例如申请将 **A、B** 重组，匹配的 .5 报告成功并给临时组 **D**，说明这一笔应答的结果和临时组身份。它不是 .6 通知已到另一端，也不是成员已归属或已有媒体。MC 发起的 §10.2.2.2 示例分别写 **4：IWF 回应**和**5：GMS 创建并保存临时组信息**；不能从 .5 表注证明 GMS 已保存，也不用步骤顺序猜 ID 分配时点。该示例步骤 5 的级别规则另按其条件读，不能填成 .7 应答表的默认参数。[§10.2.2.2 步骤 4–5，印刷页 27–28（PDF 第 28–29 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=28)。

D 的 .3 若报告成功，只能读作对应撤组**通知**的结果。应答写了什么、该端是否发出、另一端是否收到，分别判断。要把多条消息归到同一次重组或撤组通知，再核实际类型、组、角色、端点和关联上下文；同一组 ID 不够。

§10.2.1.6 的 Security level 注指向 TS 23.280 的媒体及话权控制保护参数配置；不据此判断保护已启用或级别算法。§10.2.1.1 对其他参考点也只引 TS 23.280。问本流程的授权、检查和组所有权，读本页开头；若实际是[预配置重组](preconfigured-regroup.md)或[整通组呼释放](group-call-release.md)，读各自流程，不套这里的 Result。

## 重组应答之后谁保存临时组信息谁通知谁

先分发起侧。MC 发起（§10.2.2.2）由组管理客户端提出申请、MC 组管理服务器（GMS）转给 IWF；IWF 发起（§10.2.2.3）的原请求直接由 IWF 发给 MC GMS。两支都要求 MC 与 IWF 各已定义至少一个 MC 服务组。已定义不等于列入这笔请求；本次组成组另查。只有 MC 发起的这支列客户端已取回各组成组配置。单查某一步或一条已识别的消息，不需要两边的记录都齐。

| 要查的动作 | MC 发起，§10.2.2.2 | IWF 发起，§10.2.2.3 |
| --- | --- | --- |
| 原请求与应答 | 1 客户端→GMS，3 GMS→IWF；4 IWF→GMS 回应，可拒绝。11 GMS 回原授权用户的组管理客户端，是另一腿。 | 1 IWF→GMS，2 GMS 检查组能否并入临时组，3 GMS→IWF 回原请求。没有 .2 步骤 11 那条原发起客户端应答。 |
| 临时组与 IWF 通知 | 5 GMS 创建并保存临时组信息：临时组 ID、离网信息、各合并组的 MC service ID、优先级和安全级别。6 GMS 通知 IWF，7 IWF 回应该通知。 | 4 IWF→GMS 的临时组创建通知带组成组信息；7 GMS 回应这条通知。4 是通知，不是 GMS 创建并保存临时组信息，也不是 3 的再次发送。 |
| 通知 MC service server | 8 GMS→MC service server 通知创建并带组成组信息，9 该 server→GMS 确认。不要把 7 当 9。 | 5 GMS→MC service server 通知创建并带组成组信息，6 该 server→GMS 确认；该步写明 **MC service server 可拒绝**，例如本次重组的一个组成组此时已处于一项重组中。这不是 3 的处理结果，也不是 .2 步骤 4 的 IWF 拒绝。 |
| 通知成员 | 10 GMS 通知其所管组成组的 MC 服务组成员，可带较低安全级别指示。图是通知动作框，不表示成员实收。 | 8 也是 GMS 通知其所管组成组的 MC 服务组成员，可带较低安全级别指示。不是 7，也不证明对端名单或全员收件。 |

MC 侧步骤 5 的条件是授权用户未指定**安全级别和优先级**。两项都未指定时，GMS 必须设为组成组中较低的安全级别和较高的优先级。只缺一项时，这段没有给单项补值规则，也没说覆盖另一项已给的值。这里的条件不填作 [IWF 临时组通知应答表](#重组的应答成立通知和撤组通知分别证明什么) 的缺值规则；成员收到较低安全级别指示与实际启用保护也是两件事。

例如 D 的 IWF 通知已发并见匹配应答，可分别判断这条通知的发送与确认；若只见应答从对端发出，还不能说通知方收到。判断 GMS 是否创建并保存临时组信息、MC service server 是否实际确认、哪一位成员实收、原发起端是否收到自己的应答，要各查同一次操作相应端的证据。图按步骤画消息，不补「所有确认到齐」的屏障，也未写 .3 发生拒绝后第 7 步要报什么、是否还通知成员或如何回滚。IWF 的临时组 ID 用法仍按 .2 步骤 6 的注留在范围外；.3 的通知自身也不证明由哪个 GMS 实际执行重组或拥有新组。

## 两侧重组时什么信令不能转给 LMR

**MC 侧使用临时组的重组信令，所连 LMR 系统又不支持重组，IWF 必须阻止这种信令传到该 LMR。** §10.2.2.5 的引言说，为避免两侧重组同一批用户带来的路由问题，可采用下列规则。引言的“可”不把列项中的两个 “must” 改成可选。

- **拦的是重组信令，不是整组通信。** 例如 MC 侧用临时组 D 发送重组信令，LMR 能做普通组呼但不支持重组，仍要拦这类信令。LMR 支持重组时，不能反过来推出一定转发；支持情况未知也不能当成不支持。条文没说反向信令怎么拦，也没要求阻断原组呼叫、媒体或所有 IWF 流量。
- **组标识转换另有要求。** IWF 必须处理 MC 侧临时组标识与 LMR 侧所用的原有互通组标识之间的转换。这条没附前一项“不支持重组”的条件；不表示 LMR 新建临时组，也不指定一对一关系、字段或转换算法。§10.2.2.2 步骤 6 的注把 IWF 怎样使用临时组 ID 排除在范围外，不取消这里规定的转换责任。

只查规则，不需要两条现场请求。判断一次运行时，先确认 MC 侧实际用了这种信令、目标 LMR 对重组的支持情况，再分别查 IWF 是否向 LMR 发出、LMR 是否实际收到。只见 GMS 与 IWF 之间的重组申请或应答，不能确定 LMR 一侧发生了什么；不完整记录没抓到也不能证明已拦截。要判断本次转换，核对同次操作的 MC 临时组与 LMR 原有互通组，而不是仅看两个 ID 同名、不同名，或拿成员 ID 和配置来源组代替。

**不能用这节裁谁先赢。** 它没定义请求的先后、优先方、并发检测或回滚。§10.2.2.5 还写明 TS 23.280 [5] §10.2.4.4 的规则适用；这里仅定位引用，不代读其正文；[5] 未指定版本，按 §2 查同一 Release 的最新版。[§10.2.2.5，印刷页 29（PDF 第 30 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=30) · [§10.2.2.2 步骤 6 的注，印刷页 28（PDF 第 29 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=29) · [§2 [5]，印刷页 11（PDF 第 12 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=12)。

[MCPTT 预配置组重组](preconfigured-regroup.md)是独立流程，但 §10.3.7.1 明说 §10.2.2.5 的规则也适用。若此次请求中的任一 MCPTT 组成组已按 TS 23.280 或 §10.2.2 重组，必须拒绝这个预配置重组请求；能做标识转换不能跳过这项检查。查重组能否接纳，仍按所处流程查原因及应答，不把重组信令的拦截当成一次重组的拒绝结果。[§10.3.7.1 末段，印刷页 73（PDF 第 74 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=74)。
