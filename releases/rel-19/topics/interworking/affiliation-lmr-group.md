# LMR 定义组：显式与隐式归属通知

TS23.283 V19.5.0，Release 19，Stage 2。

组定义在 LMR，IWF 已配置 MC/LMR 组及用户身份映射。

## IWF 已连接且获与 MC 系统互通授权

客户端请求经 server 转 IWF；成功响应后 server 存状态并回复客户端。IWF 可因组 ID 未知或无 LMR 映射而拒绝。隐式归属仅执行跨侧请求、响应及存状态步骤，仍通知 IWF。 [§10.1.2.4](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 先前已执行 §10.1.2.4 归属

显式请求携发起 ID 与组列表；server 按订阅/策略检查归属及互通组，经 IWF 请求/响应后，仅在用户获取消授权时移除状态。隐式取消只执行跨侧请求/响应及有条件移除状态。 [§10.1.2.5](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 隐式归属和取消还要联系 IWF 吗？哪一步改本地状态？

**两种隐式流程都保留 server 与 IWF 的请求和应答。** 省略的是相应流程的客户端收发等步骤，不是省掉 IWF，也不是自动跳过取消资格。这里的 server 指 **MC service server**，适用 TS 23.283 V19.5.0 Rel‑19 Stage 2 的 **LMR 定义组**；不要用呼叫另一侧的归属过程代替。查规则或已辨明的一条消息不用等齐全链。

| 读哪一笔 | 客户端腿和本地检查 | IWF 腿、本地状态和隐式分支 |
| --- | --- | --- |
| **归属（.4）** | 前提是组定义在 LMR、IWF 与 MC 已连接且获准互通、IWF 已配置组和用户标识映射。显式时 **1** 客户端带组 ID 向 server 请求，**2** server 检查这些 ID 是否为 LMR 定义的互通组。图把这一步写作 Resolve group ID，不补具体解析算法。 | **3** server → IWF 请求；**4** IWF → server 的应答在所示成功流程报告归属成功；**5** server 保存本客户端在所请求组的归属状态；**6** server 另回客户端。NOTE 5 对隐式归属只列 **3、4、5**，不要求这套流程另有客户端的 **1/6**。 |
| **取消归属（.5）** | 明列前提是 IWF 已配置对应组和用户映射、之前执行过 .4 归属过程；之前执行过不替代现在是否仍归属的检查。显式 **1** 客户端须提供发起的 MC service ID 及要取消的组 ID；**2** server 按用户订阅和已存组策略查该用户是否已归属所请求组，并查是否是互通组。 | 互通组走 **3a** server → IWF 请求、**3b** IWF → server 应答。**4** 只在该用户获准取消这些组的归属时，server 才移除该用户对所请求组的状态；**5** 另向客户端回包。NOTE 2 对隐式取消只列 **3a、3b、4**；在这里保留 4 的授权条件，不补隐式授权的取得方法。 |

[§10.1.2.4 前提、图 10.1.2.4-1 及 NOTE 5，印刷页 20–21（PDF 第 21–22 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=21)；[§10.1.2.5 前提、图 10.1.2.5-1 及 NOTE 2，印刷页 22（PDF 第 23 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=23)。

**归属请求转给谁，不等于谁已获权。** .4 NOTE 2 说 IWF **可以**向 LMR 系统转请求，LMR 系统**可以**查客户端是否有权归属。IWF 已获准互通不代替这位用户的资格。NOTE 3 中，组 ID **对 IWF 未知**或**在 IWF 配置中没有对应的 LMR 组标识**，任一情况都可拒绝归属；不是必须拒绝，也不在看到一次拒绝时自动给出原因。LMR 内如何执行归属不在本节范围。[§10.1.2.4 NOTE 2–4，印刷页 21（PDF 第 22 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=22)。

**读取消应答，不要先填“成功”。** .5 第 3b 步只写 IWF 返回取消应答；它不像 .4 的第 4 步明确写报告归属成功。图 .5 把 2 标为授权检查，把 4 标为更新 MCPTT 组归属状态；具体检查及有条件移除仍按 MC service 的正文，不凭图框名称把适用范围缩成仅 MCPTT。已辨明一笔 3b 且有匹配的逐组结果，可读它报告的业务结果，不能用它代本地状态。不据图加一条隐式客户端请求、假定某个响应值，或把步骤 2 的检查当成步骤 4 已经获得授权。[§10.1.2.5 图和步骤 2–5，印刷页 22（PDF 第 23 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=23)。

要判断一次实际操作，按同一业务用户、请求组、操作和端点找证据：IWF 应答已发、server 实收、**本地保存或移除状态**、原生回包发出和客户端实收，分别核实。缺少客户端请求或应答的记录，不单独判为隐式或失败。只判断状态时核该客户端及相应组的实际状态，不要求先找齐消息。已辨明的 IWF 信息流若问字段和逐组结果，另读[归属请求与逐组结果](affiliation-results.md)；[离开正在进行的呼叫](deaffiliation-exit.md)、[MC 定义组的代理范围](affiliation-mc-group.md)有各自条件。这两段不规定 SIP、隐式触发来源、失败重试或相反定义侧的状态更新。
