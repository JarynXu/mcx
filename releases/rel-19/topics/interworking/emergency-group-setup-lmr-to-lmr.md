# LMR 发起、组也定义在 LMR：谁先发请求，谁回结果？

**第一跳 IWF‑1 建呼是 IWF → MCPTT server，按已归属的 MCPTT 成员逐人发。** server 回 IWF 的是各条请求的结果。这里没有「MCPTT server 先向 IWF 发一条原建呼、IWF 再回原请求」那一腿。发起者换成 MCPTT 才读那个分支；组仍定义在 LMR 时，两支都由 LMR 系统主控。

本文限 **TS 23.283 V19.5.0（Rel‑19 Stage 2）§10.6.2.2.3**：LMR 用户起呼，组定义在 LMR，该组有已归属的 MCPTT 客户端，IWF 与 MCPTT 已连通并获准，且已配置组及用户身份映射。图中举两名 MCPTT 侧成员，不规定数量为二，也不把静态成员名单当成归属。查条款不用抓包；判断现场先确认发起者、组定义处与实际信令。不能仅凭看到 IWF 或某个用户归属就定分支。[§7.4.1 与 §10.6.2.2.3、图 10.6.2.2.3‑1，印刷页 15、125–126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=126)。

## 每名已归属成员的一条链

| 步骤 | 谁给谁 |
| --- | --- |
| **1a／1b** | IWF 向 MCPTT server 为每名**已归属的 MCPTT 用户**各发一个 `IWF emergency group call request`，带紧急指示。不是逐 LMR 用户，也不是由一个 IWF 代表 MCPTT 成员只收一条。 |
| **2a／2b → 3a／3b** | MCPTT server 配置底层承载优先级并向相应 MCPTT 客户端发紧急组呼请求；每个客户端给 server 应答。 |
| **4a／4b** | MCPTT server 把各条 IWF 应答回给 IWF。图的 a 回 a、b 回 b；**4a 不是初始 LMR 主叫的单一汇总应答**。正文列步骤 3、4；图还画了 4a 在 3b 前，说明这个例子没有等另一名成员先答。不要从图定全组串行、并发调度或失败等待规则。 |

[§10.6.2.2.3 步骤 1–4、图 10.6.2.2.3‑1，印刷页 125–126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=126)。

**Result 要配到原请求上。** IWF 应答表的 `Result` 必带，也可表示拒绝；步骤 4 描述的是成功流程。请求和应答表的 `MCPTT ID` 都指**主叫**，不是被邀成员；同一个组 ID 加相同主叫 ID 也不足以把 4a 与 1b 配对。要查一条实际信令是否到达，找正确接收端的实收证据；对请求而言，该端实际发出的对应应答也可作证，但不证明原发送端已收到这个应答。证实一条信令不要求看见媒体。

紧急指示不是告警或话权授予。IWF 请求表的告警指示可选；隐式话权请求只在发起端确实请求话权时带。只见其中一项，不证明告警已送或者已授话权；本分支也没规定如何从 LMR 内部触发它们。步骤 5 才描述 LMR 用户经 IWF 与已归属 MCPTT 客户端已建立媒体。实际有没有 RTP 或端到端音频，要另核该次媒体证据。未听到音频、无法证实另一成员收件或尚未看到回包，也不能仅凭这些条款推定失败原因。[表 10.6.1.1‑1、10.6.1.2‑1 与 §10.6.2.2.3 步骤 4–5，印刷页 117–118、126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=118)。

## 容易串读的两处

- **原文概述与具体端点。** §10.6.2.1 在 LMR 定义组的概述里把逐成员请求目的写成 IWF；本支图与步骤 1 明写 **IWF → MCPTT server**。保留字面差别，不增加 IWF 自发自收、不补另一个 LMR 内部端点。
- **另一发起侧的步骤不能搬来。** [MCPTT 发起同类组的流程](emergency-group-setup-mcptt-to-lmr.md)有 server→IWF 的原请求及 IWF→server 的独立原应答（3／8）。这里不要求它们出现，也不套 §10.6.2.2.4 的 NOTE 5。若组定义在 MCPTT，则再换该版的对应分支。
