# LMR 普通组呼遇到已有迫近危险状态：为什么 IWF 收到不同类型的应答？

**IWF 先发普通组呼请求。MCPTT server 查到该组已经处于迫近危险状态，才走迫近危险的互通信息流。** server 给原 IWF 请求回的是迫近危险组呼应答；不要因为应答叫这个名字，就把原请求也读成迫近危险请求，或者把它配到另一笔逐人请求。

本页限 **TS 23.283 V19.5.0（Rel-19 Stage 2）§10.6.3.3**。LMR 用户实际发起普通组呼；互通组已由组管理服务器定义，MCPTT 客户端及经 IWF 代表的 LMR 用户已经归属，且该组在 MCPTT 内**已有**迫近危险状态。要求已有的是组状态，不是另有一通还在进行的电话。IWF 已接入并获准，掌握互通组信息，配置了组和用户身份映射。图中的两个 MCPTT 客户端均已归属，不用图示人数代替实际归属；单 server 图示合画用户本属和组托管两个角色，不要求同机。查规范不需要抓包。[§10.6.3.3 前提、NOTE 1–3，印刷页 135–136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=136)。

## 谁知道组处于迫近危险状态

1. **步骤 1：普通 IWF 请求。** IWF 在这条流程不跟踪该组的迫近危险状态，向 MCPTT server 发 `IWF group call request`，带目标 MCPTT 组 ID。正文在 LMR 主叫请求话权的条件下写两项：带隐式话权指示，位置若有要求才附带。该段没另给无话权请求时的位置流程。不要从这些字段推出 IWF 已知道组状态、一定有位置、已授话权或已获下游位置传播许可。普通请求的身份字段及预留 ID 见[普通 IWF 组呼请求表](group-call-request.md)。
2. **步骤 2：server 识别已有状态。** MCPTT server 判断该组当前在迫近危险状态。不是由普通请求设这项状态，也不从请求是否带位置判断状态；孤立、未配对的同名应答不能证明起呼前的组状态。

## 三组请求和应答怎么配

| 配对 | 实际端点及条件 |
| --- | --- |
| **3 → 4：MCPTT 成员** | server 转换请求，给全部已归属的 MCPTT 客户端发迫近危险组呼请求。实际收到该请求的客户端在 4 回 server；组播时不发这条 MCPTT 成员 ACK。不从无 4 推断没有通知，也不据此判断 4a 或 5 实际是否发生。 |
| **3a → 4a：逐 LMR 用户** | 有主叫之外的其他已归属 LMR 用户、且 server 收到这些用户的逐人归属时，另向 IWF 发逐人迫近危险组呼请求。IWF 向 server 回对应的 4a。原文末句写每名已归属 LMR 用户，不据此判主叫另收到一份；仅主叫归属、静态名单或只有 IWF 代理归属不满足此处的逐人条件。 |
| **1 → 5：原发起腿** | server 向 IWF 回原普通请求的 `IWF imminent peril group call response`。它不是 3a 的回包，也不证明 LMR 主叫终端已收。不要因为组播没有 4，就把 5 或 4a 当作成员 ACK。 |

图把 3a／4a 画为虚线，5 是独立的 server→IWF 应答，画在 4／4a 后。该节没有另给 5 的统一等待或提前条件，不规定 server 发 5 必等全员回包，也不承诺 5 总能提前。别搬用 §10.6.3.2 NOTE 7 对该支步骤 10 的 5 后／11 前，或 §10.6.3.4 NOTE 7 对取消应答的时序。§10.6.3.1 虽概述过单代理请求，不能靠它给本支的 3a 自动补一条 server→IWF 请求。[§10.6.3.1，印刷页 133](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=134)；[§10.6.3.3 图及步骤 3–5，印刷页 136](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=137)。

**辨明应答类型，再选消息表。** 4a 和 5 的迫近危险应答表 10.6.1.4-1 列主叫 MCPTT ID、组 ID、必带的 `Result`（可表示拒绝）。普通应答表 10.3.2.3-1 的 MCPTT ID 指目标组成员，还列 SDP answer；不能因为原请求是普通类型就用普通应答表替换步骤 5。两张表不能合成 SIP 编码模板。多条逐人腿同组同主叫也不等于同一事务。核实际信令要找同次呼叫、方向、端点及匹配事务；接收端实际发出的匹配回包能支持原请求已到该端，不能替代对端实收这条回包。确认信令不需要媒体证据。[普通应答表，印刷页 35–36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=37)；[迫近危险应答表，印刷页 118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=119)。

**步骤 6 才描述媒体建立。** LMR 用户经 IWF 与已归属的 MCPTT 客户端通信，定义该组的 MCPTT 系统主控。正文说该呼叫在 MCPTT 系统内因组已有迫近危险状态而获得调整后的承载优先级；NOTE 4 不规定 IWF 自身怎么处理优先级。实际音频、RTP、话权或 LMR 终端的收件另核；不从 4、4a、5 或承载优先级代替。也不补拒绝处理、LMR 内部调用或 SIP 编码。[§10.6.3.3 步骤 6、后续段及 NOTE 4，印刷页 136–137](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=137)。

若是 [MCPTT 用户主动发起迫近危险组呼](imminent-peril-group-call-mcptt-origin.md)，查该支的指定组、位置许可及建呼拒绝；若是[明确清除组状态](imminent-peril-group-state-cancel.md)，查取消流程。不要从这条 LMR 普通建呼推组状态已新设或取消，也不要用[晚加入](late-entry.md)或[组呼释放](group-call-release.md)替代它。
