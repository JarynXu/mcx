# MCPTT 用户取消 LMR 定义组的紧急状态：发起端确认等哪一笔？

**IWF 回给 MCPTT server 的步骤 4，确认的是 server 向 IWF 发的步骤 3。server 给发起端的步骤 7，确认的是 client 1 发的步骤 2。** NOTE 5 允许 7 在 4 后发，取决于继续呼叫的条件。不能只因 server 收到 2 就回 7，也不能把图里的承载调整和成员处理变成 7 每次必等的步骤。查规范不需要抓包。[TS 23.283 V19.5.0 §10.6.2.3.4 图、步骤和 NOTE 5，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=133)。

## 先分清组和原请求

MCPTT 用户发起，互通组定义在 **LMR**，所对应的 MCPTT 组仍处紧急状态，另一 MCPTT 客户端（图中的 client 2）已归属。IWF 已接入并获准互通，且在 IWF 已配置组和用户身份映射。NOTE 2 要获授权用户明确取消；挂断不自动清组状态。不能用 IWF 互通授权、映射或 client 2 的归属替代发起者权限。本节没要求发起者就是原紧急主叫或必须还在传媒体。[前提及 NOTE 1–2，印刷页 131–132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=132)。

**原请求类型是组紧急状态取消才查这里。** 若 MCPTT 用户原请求是取消紧急告警，即使还带清组状态指示，仍查 §10.6.5.2 NOTE 2；不能仅凭想清两个状态就确定请求类型。告警流程的应答时序、逐人规则及组播 ACK 不是本节的规则。[§10.6.5.2，图 10.6.5.2-1 和 NOTE 2–3，印刷页 143–144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。

## 两笔应答不能互换

| 步骤 | 看什么 |
| --- | --- |
| **2：client 1 → server** | 发起端请求取消组紧急状态，可另指定清发起者本人的告警。这一步不是第三方告警取消。 |
| **3、4：server ↔ IWF** | server 发 3，IWF 回 4 确认原 3。NOTE 3 不展开 IWF 怎样查授权、怎样执行取消；NOTE 4 说明 LMR 系统可以拒绝。本节没有规定拒绝怎么表示、是否仍回 4、是否回 7 或怎么重试。不从 4 单独认定 LMR 接受、状态已清或发起端已收到 7。 |
| **5：server 调整承载** | 调整底层承载优先级，此组紧急状态不再要求优先处理。不能推出其他原因的优先级一并取消、承载实际值、媒体停止或话权释放。 |
| **6：面向已归属 MCPTT 客户端** | server 按 TS 23.379 §10.6.2.6.1.3 处理，图标作通知。这里没单列成员 ACK 或组播例外，不能说成员必不应答或全员已收到。 |
| **7：server → client 1** | 回给发起端，确认原 2，不是把 4 原路发给 client 1。NOTE 5 明确 7 要在 4 后，还要符合继续呼叫的条件；只有 2 或 3，或只有不匹配的 4，都不能拿来代替这笔 4。图把 7 放在 5、6 后面，不等于每次都得完成 5、6 或等成员收件才发。NOTE 5 也不是遇到拒绝仍无条件回复的规则。 |

[§10.6.2.3.4 图 10.6.2.3.4-1、步骤 1–7 和 NOTE 3–5，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=133)。

IWF 请求表 10.6.1.11-1 和响应表 10.6.1.12-1 都列必带的 **取消者 MCPTT ID** 和 **组 ID**。请求表可带 `Alert indicator`，指取消者本人告警。步骤 3 没规定自动复制步骤 2 的告警指示，正文也没单列清本人告警的动作。应答表没列 `Result`、告警指示或被通知用户 ID，组 ID 描述重复写的 “in-progress” 不是额外字段。两张表描述双向消息；本支的方向按图中 3/4。[两张表，印刷页 120–121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=121)。

§10.6.2.1 对 LMR 定义组说按已归属的 MCPTT 组成员逐人发请求，字面把发送和接收两端都写成 IWF；本支步骤 3 的正文和图都是 **server → IWF**。保留两处写法。不把总则改成一个确定方向，也不从总则或图的一根箭头认定本支实际请求数。MCPTT 定义组和告警流程的代理、逐人分发规则不移到这里。[§10.6.2.1，印刷页 121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)；[§10.6.2.3.4 步骤 3–4，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=133)。

查现网按同次组态取消、取消者、组、事务、端点和方向分别配 **2/7** 与 **3/4**。IWF 实际发出的匹配 4 可佐证 3 到了 IWF，但不能证明 server 收到了 4；server 发出的匹配 7 也不证明 client 1 收到了 7。信令取证不需要媒体证据。实际 LMR 是否接受、组态和告警是否清除、承载是否已调整、成员是否收到或应用、媒体和话权分别查证。[步骤 2–7，印刷页 132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=133)。
