# LMR 发起互通 First-to-answer：IWF 何时能按新参数重来？

**IWF 收到的参数变了，而且它接受，才有本段所说的另发请求。** 由 IWF 用新参数回到步骤 1，原来的应答不算新尝试成功。原文说参数不可接受则呼叫失败，另写参数未变继续步骤 6。若参数未变而 IWF 明确不接受，本段没给这两句的优先次序；不能判定必进步骤 6，更不能判定媒体已建立。

这是 **TS 23.283 V19.5.0，Rel‑19 Stage 2，§10.15.3.2**。节标题和前提 1 写 **LMR 用户选了 first-to-answer**，图的第一箭头和步骤 1 是 **IWF → MCPTT server**；开场句和图题却写 MCPTT 用户发起。保留这处字面差异，按实际发起方、前提和箭头分流。另两个前提是 MCPTT 客户端已注册该业务、server 已向本 MC 系统的功能别名控制服务器订阅激活/去激活更新。实际是 MCPTT 用户起呼才读[相反方向的过程](first-to-answer-mcptt-origin.md)。[节标题、前提和图，印刷页 179（PDF 第 180 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=180)；[步骤 1，印刷页 180（PDF 第 181 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)。

## 从哪一腿发起，server 核的是谁？

| 步骤 | 这一腿做什么 |
| --- | --- |
| **1　IWF → MCPTT server** | IWF 发 first-to-answer 请求，带对应 LMR 主叫的 MCPTT ID、被叫目标、含一种或多种媒体的 SDP offer，并给加密算法/模式、是否请求话权及全/半双工选择。被叫可是一组候选 MCPTT ID，或一个功能别名。 |
| **2　MCPTT server 核权** | 核 **MCPTT 被叫能否获准接收**这类呼叫，不是核 MCPTT 主叫的发起权。若给 **LMR 主叫的别名**，另查它可用且已为该 LMR 主叫激活；这不是解析被叫别名。 |
| **3　server → MCPTT 被叫客户端** | 获准才传原参数，提供初始请求媒体类型或其子集。这里没列 .3.1 的位置隐私检查，不把那一步套到这一边，也不因本段没写就说位置字段必定不能有。 |

通用 IWF 请求表 .2.1-1 要求主叫 ID 和是否使用话权控制的指示。被叫 ID 或被叫别名至少有一种；ID 可成集合，有别名则为单个，未规定两类同时有的优先顺序。表里 SDP offer、隐式话权请求和位置一般可选，不免掉步骤 1 明写的原 offer。请求话权和是否使用话权控制也不是同一个选择。只见候选 A、B 或只见 A 实收，不证明 server 已向每个候选发出邀请。原文未给等待时限或超时分支，不能因缺步骤 5 推失败或取消。[表 10.15.2.1-1，印刷页 177（PDF 第 178 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=178)；[步骤 1–3，印刷页 180（PDF 第 181 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)。

## 谁回结果，什么时候可以重来？

**4 是被叫客户端回 server，5 才是 server 回 IWF。** 步骤 4 说明被叫支持一种请求媒体，并回成功或失败；失败可附替代参数。步骤 5 沿用步骤 4 给出的媒体类型，不一定是步骤 1 或 3 的原提议。通用 IWF 应答表 .2.2-1 列双方 MCPTT ID 和 SDP answer 必带、双方别名可选；未列 Result 行。它不能代替步骤 4 的结果或 IWF 对实际收件的判断。[表 10.15.2.2-1，印刷页 177（PDF 第 178 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=178)；[步骤 4–5，印刷页 180（PDF 第 181 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)。

| IWF 实收对应步骤 5 后，参数怎样 | 本段怎样继续 |
| --- | --- |
| **不可接受** | 本次呼叫失败。 |
| **有变化，而且可接受** | IWF **可以**按新参数另发请求，从步骤 1 重新开始。只见替代建议或 IWF 接受，不说明新请求已发；用新尝试自己的消息判断。 |
| **无变化** | 原文另列继续步骤 6；若同时明确不可接受，本段未规定哪句优先。没对上 IWF 的收件，或只见被叫步骤 4 成功，都不能认定这一步。无变化不证明结果成功或媒体已建。 |

步骤 5 开头叫 IWF first-to-answer call response，但讲变化与重来时用 IWF private call response / request。保留这种写法，不把它改成已定义的新报文名，也不把这笔 first-to-answer 切到普通私呼流程。这里不用 .3.1 的「向 MCPTT 主叫客户端回成功才继续」代替 IWF 的参数判断；原文没有交代结果与参数状态冲突时如何合并处理，也没给未变但不可接受时的优先规则。[步骤 5，印刷页 180（PDF 第 181 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)。

## 哪些证据才到媒体、话权或取消？

- **媒体。** 步骤 6 说 MCPTT 客户端与 IWF 已建立媒体面，两端才可传媒体。成功或无参数变化只看到了前面的分支；谁发包、对端是否实收、LMR 用户听没听到另查。
- **话权。** 若使用话权控制，步骤 6 原话把授予、竞争处理和撤销归给 `MCPTT system initiating the call`。本页实际主叫是 LMR；原文没把这个称谓映射到 IWF、LMR 主叫侧或 MCPTT 被叫端，不能凭图中位置认定某节点已经裁决或授予。
- **取消。** 通用表 .2.3/.2.4 的取消请求、取消应答在 server 与 IWF 之间；请求列双方 ID，应答只列被叫 ID（表题写 MCPTT first-to-answer call cancel response）。它不是含双方 ID 及 SDP answer 的普通应答，且 .3.2 的 1–6 步没列取消。不从失败、通用表或实际应答猜已清理候选、谁先接听、SIP CANCEL/BYE 或其顺序。
