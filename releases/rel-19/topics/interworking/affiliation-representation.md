# IWF 归属表示：逐用户与代理可以并存

TS23.283 V19.5.0，Release 19，Stage 2。

组定义在 MCPTT 系统，适用 TS23.283 §10.1.2.1。

## LMR 侧报告归属

可逐用户报告，也可在首成员归属时由 IWF 代理归属、末成员取消时代理取消，中间不另发归属信令；两种方式可以对不同成员同时使用。 [§10.1.2.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## IWF 配置为代理归属

组成员表须配置 IWF 的 MCPTT ID 并识别其代理能力；IWF 归属后，其关联 LMR 用户被视为归属，无需预列全部用户；不允许向未配置该 IWF ID 的组代理归属。 [§10.1.2.1 a–d, g](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 处理关联 LMR 用户请求

LMR 用户自身请求使用转换后的个人 MCPTT ID；另有 IWF 代表组内用户、以 IWF ID 发请求的情形，二者不得混同。代理归属后不因呼叫请求再生成重复归属。IWF 未归属时，该用户呼叫请求只有在个人 ID 列于组表且已归属时才可接纳。 [§10.1.2.1 d–f, h](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## IWF 已代表用户归属，个人还能用自己的 ID 吗？

这里读 §10.1.2.1 的**第二种方式**：IWF 已配置为代表该组的 LMR 用户归属。判断 d) 或 h) 是否适用时，按实际目标组查 **IWF 当前是否已归属**；有代理配置、已归属别的组或没有抓到归属消息，都不能替代这个状态。[§10.1.2.1 方式及 d) 的条件，印刷页 17（PDF 第 18 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=18)。

- **代理已归属这一个组。** MCPTT 系统允许由个人 MCPTT ID 代表的关联 LMR 用户针对该组发请求，带或不带功能别名均可；建呼和话权请求是原文的例子。系统不因这些用户发起呼叫再为其做一遍归属，也不发由重复归属带来的额外消息，例如在处理呼叫时经 IWF 给代理归属身份和实际发起操作的用户身份各发一份释放消息。这不取消其他适用的释放信令，也不证明建呼获准、话权已授或消息已到。
- **怎么认关联用户？怎么算上限？** 本条按用户的 MCPTT ID 与 IWF 同属一个系统来识别关联。没有规定从标识字符串哪一段来判同系统。MCPTT 系统对 IWF 的归属上限等采用专门规则，原文举 N2（每用户归属数量限制），没给数值、计数办法或豁免。别以同一组 ID、相同域名后缀或别名代替身份判断。
- **代理已归属，个人也可以归属。** 组成员表列有该 LMR 用户时，他可以经 IWF 用转换后的个人 MCPTT ID 为自己归属，即便 IWF 已经归属。能办理不表示已经办成。IWF 用自己的 ID 代表用户发请求又是另一种情况，不拿它当个人已归属的证据。
- **代理尚未归属这一个组。** 关联 LMR 用户若对该组发呼叫请求，只有其个人 MCPTT ID **在该组成员表里，并且已经归属该组**，请求才可能被接纳。两项是必要条件，不是接纳成功的保证，也不把它们搬到该用户尝试办理归属或所有话权请求。只知代理是否已归属还不够；只见某个用户 ID、静态名册或缺记录，不能补出实际归属和接纳结果。

[§10.1.2.1 d(ii)–(v)、e(i)、f)、h)，印刷页 18（PDF 第 19 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=19)。查规范不需要抓包。查现场时，d) 核 IWF 已归属同一目标组及用户与该 IWF 的关联，不要求用户另行归属。e(i) 查该用户在不在本组成员表、其个人 ID 如何对应，不以个人或 IWF 的当前归属为前提。h) 只看关联用户对本组的呼叫请求，核 IWF 对本组未归属，再分别查个人是否列名、是否已归属。确认实际建呼或获授话权，另查对应操作和结果。

## 首末成员事件什么时候需要代理信令？

**先看同一个互通组采用哪种报告方式。** §10.1.2.1 说的是定义在 MCPTT 系统的互通组。逐用户方式中，LMR 侧每次实际归属都经 IWF 向 MCPTT 报告，带该成员经转换的个人身份。代理方式中，LMR 侧指定组的首成员实际归属时，IWF 代表该组 LMR 用户发送归属；末成员实际取消时，发送代理取消。原文在代理方式下写不再发其他组归属信令，不能用这句话压掉同时采用逐用户方式的其他成员的归属信令。该节允许两种方式分给不同成员，没有规定混用时怎样划分、计数或处理并发。

例如 LMR 用户 B 取消归属时，已经确认同一个指定组还有 A 归属，就不能把 B 当作末成员。组名单上还有一个名叫 A 的用户，并不提供这个结论。只看见一条个人归属或取消，也不能据此认定代理不存在。只判断这是不是首末成员事件，查同一指定 LMR 组在事件前后的实际成员归属，不用先知道报告方式。要判断是否适用代理发送规则，再查本次采用的方式；要判断信令发出、MCPTT 系统收到或改变归属状态，再查各自的记录。未抓到一条消息不证明没有成员变化或没有发送。

[§10.1.2.1 两种方式与可混用，印刷页 17（PDF 第 18 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=18)。

## 配了代理 ID，系统就已把用户视为归属吗？

不一定。配置、办理归属、识别代理身份是三件事。按 §10.1.2.1 的第二种方式：

- **配置能力（a、g）。** MCPTT 组成员表配置的是该 IWF 自己的 MCPTT ID，系统通过配置认识到该 ID 能代表与该 IWF 关联的 LMR 用户。已知本组未配此 ID 时，不允许 IWF 按此方式归属；现场只见这一成员项不证明已配置代理能力或已识别本次归属，也不代权限检查。名单没抓全时，不能断言未配置。
- **办理与识别（b、c）。** IWF 用自己的 MCPTT ID 归属这一 MCPTT 组，MCPTT 系统把实际归属识别为 IWF 代该组 LMR 用户进行。配置可代理和已经识别本次归属不是同一个事实；也不能用经 IWF 中转的个人请求来判断。
- **何时视为归属（d(i)）。** IWF 实际已归属该组时，MCPTT 系统把与此 IWF 关联的 LMR 用户视为归属该组，无需把这些用户预先逐个列在该组成员表。不能用 IWF 已归属另一组、用户只是列名或状态未知替代本组条件；被视为归属也不是该用户已经发过或完成了自己的归属操作。

f) 另说 IWF 可以像普通组成员一样用自己的 MCPTT ID 代表该组 LMR 用户发送请求，原文以 chat 组的 group join 为例。这和用户用转换后的个人 MCPTT ID 自己请求不同。f) 在第二种方式下，但不属于 d) 的已归属分项；它不规定允许每种请求或本次动作获准。实际发送、对端接纳、入呼或授话权分别取证。

只查规则、名单是否配置或一条已识别的请求，不必先观察到完整过程。需要定位 MC 服务器实际验权、状态写入和应答时，读 [MC 定义组的归属流程](affiliation-mc-group.md)；只查已辨认消息的字段和每组结果，读[归属信息流](affiliation-results.md)。

[§10.1.2.1 a–c 与 d 的适用条件，印刷页 17（PDF 第 18 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=18)；[§10.1.2.1 d(i)、f、g，印刷页 18（PDF 第 19 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=19)。
