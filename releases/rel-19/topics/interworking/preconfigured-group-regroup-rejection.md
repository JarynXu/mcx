# 预配置组重组被拒绝：谁拒绝，原因回给谁？

适用版本：TS 23.283 V19.5.0，Rel‑19，Stage 2。

**先看本次要做什么。** 这里拒绝的是把几个组成组放入新重组组的**形成请求**。组成组名单包含例中的组 1；**D** 是本次拟形成的重组组，**P** 是提供配置的组。D、P 和名单各有用途；拿 P 当 D，或把组成组名单读成用户名单，都会选错条款。两段导言字面分别引用取消条款 §10.3.7.3.1／.3.2，但图题与实际步骤都在发起组重组并拒绝形成，不把取消动作读进来。

[§10.3.7.4.1/.2 导言、图 10.3.7.4.1‑1／10.3.7.4.2‑1，印刷页 78–80（PDF 第 79–81 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=79)。[P、D 与冲突总则](preconfigured-regroup.md)另见 §10.3.7.1。

## MCPTT 发起，IWF 拒绝

- **前提：**MCPTT 客户端获准发起；IWF 已预配 D 的组标识和配置，也已收到相关安全信息。MCPTT server 已向 GMS 订阅组配置；GMS 已从本系统 MCPTT server 订阅组动态数据。原文以 “and/or” 并列两种关系：IWF 已归属一个或多个拟重组组，和／或可托管其中一个或多个，不要求对每个组同时归属和托管。
- **1–4：**获授权用户指定组成组名单、D 与 P，客户端向 server 发请求（2）。server 查本次发起权限、解析名单中的组标识、核本系统托管的请求组中谁已归属、找托管其他请求组的伙伴系统或 IWF；未掌握配置时可向 GMS 获取（3）。NOTE 写明：发起用户不必是名单内任何组的成员或已归属成员。server 向 IWF 发重组请求（4）。
- **5/6：**IWF 向 server 发拒绝并指明原因（5）。图名有 IWF 前缀，正文省略，方向相同。例如一个或多个拟重组组已被其他流程重组，先前重组可在 IWF 内部或 MCPTT 系统。server 另向发起客户端发带原因的拒绝（6）。5 和 6 是两条消息；正文未规定两处如何映射原因值，不能拿 5 的发出或到达证明客户端已收到 6。

[§10.3.7.4.1 前提、步骤 1–6 与 NOTE，印刷页 78–79（PDF 第 79–80 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=79)。

## IWF 发起，MCPTT server 拒绝

- **前提：**MCPTT 客户端已归属 MCPTT 系统定义的组 1；D 的标识和配置预先配在该客户端，客户端已收到相关安全信息。这里的客户端不是步骤 1 的发起者。
- **1–3：**IWF 向 MCPTT server 发请求，仍指定组成组名单（含组 1）、D 与 P（1）。server 查自己托管的 MCPTT 组状态，并确定本次拟重组组中有一个或多个已被另一流程重组（2）。正文称伙伴 MCPTT server 向 IWF 发带原因的拒绝（3），图的 MCPTT server 就在这条回执的发出侧，没有另画一次回复给客户端。
- 只见其他系统有组已重组，不能替本支的步骤 2；只见 server 发出拒绝，不能判 IWF 已收到。两图都省略介于系统间的 gateway MC servers，逻辑方向不表示网络直连。

[§10.3.7.4.2 前提、图与步骤 1–3，印刷页 79–80（PDF 第 80–81 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=80)。

## 两个方向都可以发拒绝，按哪张表？

| 已识别的 IWF-1 消息 | 核哪些字段 |
| --- | --- |
| server→IWF 的 .4.1 步骤 4，或 IWF→server 的 .4.2 步骤 1 **重组请求** | 表 **10.3.2.14‑1**：请求者 MCPTT ID、D 的组 ID、P 的组 ID 各必选。两个列表各标 O，注要求有且只有一个。这里选组成组 MCPTT group ID list，不是用户 MCPTT ID list。 |
| IWF→server 的 .4.1 步骤 5，或 server→IWF 的 .4.2 步骤 3 **重组拒绝** | 表 **10.3.2.18‑1**：D 的 MCPTT group ID 与 Reject reason 均必选。组 ID 在这张表里标明的是 D；不借它指认哪个组成组冲突。表没有单列冲突组、P、请求者或 Result，不给拒绝码。 |

单查一条已辨明类型与方向的消息，可只读自己的表。只见日志没显示原因，不等于拒绝漏了必选项。要把请求与拒绝配成同一次，另核同次和对应端点，单凭 D 不够。带 Result 的形成应答（表 10.3.2.15‑1）和取消应答（表 10.3.2.17‑1）不是本拒绝表。也不要把 IWF 拒绝表套给 .4.1 步骤 6 的客户端腿。

观察到匹配拒绝，能说明这次请求被报为拒绝及其所报原因。不由原因字段推出哪个组成组实际冲突、旧重组已取消或仍在运行，也不证明 D 已形成、回滚、终端已知悉或某种 SIP 状态码。如果要判断已重组的某个组成组何时一定挡住这次请求，读[前一页的 §10.3.7.1](preconfigured-regroup.md#某个待重组组已按-ts23280-或-1022-重组)。若实际拒绝的是在 A 上 **建立组呼**，读[漏收重组通知后按下 PTT](preconfigured-regroup.md#漏收重组通知后按下-ptt)；若输入是用户而不是组名单，读[预配置用户重组成形](preconfigured-user-regroup-formation.md)。
