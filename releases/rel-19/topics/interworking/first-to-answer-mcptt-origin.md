# MCPTT 发起互通 First-to-answer：怎样看应答、重试与媒体建立？

**IWF 支持一种媒体，不等于这次呼叫已经接通。** TS 23.283 V19.5.0 §10.15.3.1 分三步看：IWF 先回应 MCPTT server（步骤 4），server 再回发起客户端（5）；结果成功，客户端才往与 IWF 建立媒体面的步骤 6 走。

这里只读 **Rel‑19 Stage 2，MCPTT 用户发起，经 IWF 到 LMR 用户**。前提是主叫选了 first-to-answer、客户端已注册 MCPTT 服务、server 已向本 MC 系统的功能别名控制服务器订阅激活/去激活更新。就算本次用直接 ID，前提也没有变。查规范不需要抓包；判某次通信须先对上主叫、尝试与消息方向。[§10.15.1，印刷页 176（PDF 第 177 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=177)；[§10.15.3.1 前提与图 10.15.3.1-1，印刷页 178（PDF 第 179 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=179)。

**先分发起方。** 若实际是 LMR 用户发起、第一笔 IWF 请求由 **IWF → MCPTT server**，去核 §10.15.3.2，不是本页 server→IWF 的步骤 3。相邻段的开场和图注写成 MCPTT 发起，但前提 1 写 LMR，图上第 1 箭头与步骤 1 都是 IWF→server。按实际角色和方向分流，不拿开场或图注换掉方向。[§10.15.3.2 开场、前提与图，印刷页 179（PDF 第 180 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=180)；[相邻分支步骤 1，印刷页 180（PDF 第 181 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)。

## 谁发请求，哪些参数能转给 IWF？

| 步骤 | 这一步查什么 |
| --- | --- |
| **1　主叫 MCPTT client → server** | 提交主叫 MCPTT ID 和被叫目标，可用一组潜在 LMR 被叫的 MCPTT ID，或一个功能别名。原请求给出带至少一种媒体的 SDP offer，以及加密算法和模式、是否请求话权、希望全双工还是半双工（是否建立话权控制）。 |
| **2　server 核权** | 查主叫是否获准发起 first-to-answer；若带的是**主叫**别名，再查能否使用和是否已为主叫激活。不把这项检查当作被叫别名已经解析。 |
| **3　server → IWF** | 授权通过才向 IWF 发请求。转交原参数，提供原请求提出的媒体类型或子集。主叫位置是否转给 IWF 另看隐私检查，不因已获准呼叫而自动发位置。IWF 怎样再转到 LMR 不在本规范范围。 |

表 10.15.2.1-1 描述 server 与 IWF 间通用请求：主叫 MCPTT ID 与是否使用话权控制必带，主叫别名可选。被叫 ID 和被叫别名至少有一种；有 ID 时可是一组，有别名时须为单个。候选 ID 的集合不等于一个组标识。表内 SDP offer、隐式话权请求和主叫位置一般可选，这不改变步骤 1 明写的原 offer，也不把「是否使用话权控制」当作「已经请求或取得话权」。这里不规定同时给出两类目标时的优先顺序。[表 10.15.2.1-1 及表注，印刷页 177（PDF 第 178 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=178)；[步骤 1–3，印刷页 178–179（PDF 第 179–180 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=179)。

## 失败带替代参数，能沿用这笔呼叫吗？

**不能把旧失败当成成功。** 步骤 4 的 IWF 应答说明支持所请求的一种媒体，仍分别有成功与失败；失败可附替代参数。步骤 5 由 server 向发起客户端转回结果。通用 IWF 应答表 10.15.2.2-1 把主叫和被叫 MCPTT ID、SDP answer 列为必带，双方功能别名可选；表未列 Result 一行，而流程按实际结果走。SDP answer、被叫 ID 或表示支持某一媒体，都不替代这次的成功结果。[表 10.15.2.2-1，印刷页 177（PDF 第 178 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=178)；[步骤 4–5，印刷页 179（PDF 第 180 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=180)。

- **成功**：发起客户端继续步骤 6。看到 server 转出的应答，还不等于客户端收到了，也不等于媒体已建立。
- **失败，替代参数可接受**：客户端可用这些参数另发请求。用户可能获知参数变化，例如改为无话权控制，也可以结束而不继续。要确认重试是否发生，看新请求和自己的应答。
- **替代参数不可接受**：此呼叫失败。没有替代参数也不能从这段推出会自动重试。

步骤 6 中，只有 MCPTT 客户端与 IWF 已建立媒体面，才可确认这里所说的两端可传媒体。若使用话权控制，发起侧 **MCPTT 系统** 负责授予、竞争处理和撤销。还需分别查谁实际获权、谁发了包、谁收到了；不从媒体就绪推 LMR 用户已经听到，也不从应答中有被叫 ID 推哪一名候选实际先接听。[步骤 5–6，印刷页 179（PDF 第 180 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=180)。

## 通用表里的取消，不等于这条过程发了取消

§10.15.2.3/.4 的请求与应答是通用信息腿；取消请求列主叫与被叫 ID，取消应答表只列被叫 ID（该表标题写 MCPTT first-to-answer call cancel response）。§10.15.3.1 的图和步骤 1–6 未列取消步骤。不能从定义反推出本次已取消其他候选，更不能补 SIP CANCEL、BYE、ACK、状态码或先后顺序。[取消表，印刷页 177–178（PDF 第 178–179 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=178)。

若未涉及 IWF，而要查 MCPTT 原生的应答选择与 SIP 分支清理，读 [Stage 3 first-to-answer](../calls/first-to-answer-selection.md)；若不是 first-to-answer，另查[互通自动私呼](private-automatic.md)或[互通手动私呼](private-manual.md)。
