# LMR 用户取消 LMR 定义组的紧急状态：IWF 回执要等什么？

**步骤 1 是 IWF 向 MCPTT server 发组紧急状态取消请求；步骤 4 是 server 回 IWF，确认原步骤 1。** NOTE 3 说 4 可在 1 后发，取决于继续呼叫的条件，不是固定等承载调整和成员处理完成。查规范不需要抓包。[TS 23.283 V19.5.0 §10.6.2.3.3，图 10.6.2.3.3-1、步骤 1–4、NOTE 3，印刷页 131](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=132)。

## 先判发起侧、组定义和原请求

LMR 用户发起，互通组定义在 **LMR**，所对应的 MCPTT 组仍处紧急状态，已有 MCPTT 客户端归属。IWF 已接入并获准互通，在 IWF 已配置组和用户的身份映射。NOTE 2 区分挂断和取消：紧急组呼结束不自动清组状态，需获授权用户明确取消。IWF 获准互通、身份映射和成员归属都不能替代用户的取消权限。正文没有列出谁在哪一步验权，也没有单列本地如何清除组状态。不补授权算法或 LMR 内部流程。没有媒体，不等于组紧急状态已经消失。[§10.6.2.3.3 开头、NOTE 1–2 和前提，印刷页 130–131](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=131)。

**原请求类型是组紧急状态取消，才看本页。** 若发的是紧急告警取消请求，即使 §10.6.5.1 NOTE 2 允许附带清除组状态的指示，仍查告警取消流程。不能只看两项取消目标，就断定用了组状态取消的请求和确认。[§10.6.5.1，图 10.6.5.1-1、NOTE 2，印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)。

## 步骤 4 确认原请求，不替承载和成员取证

| 步骤 | 看什么 |
| --- | --- |
| **1：IWF → server** | IWF 为发起的 LMR 用户发组紧急状态取消请求。图从 IWF 起，不显示 LMR 用户发给 IWF 的内部信令。 |
| **2：server 调整承载** | MCPTT server 调整底层承载优先级。本组的紧急状态不再要求优先处理，不代表其他原因的优先级一并取消；不由此断定媒体停止或话权释放。 |
| **3：面向已归属 MCPTT 客户端** | MCPTT server 按 TS 23.379 §10.6.2.6.1.3 处理，图标作通知成员。本节没有单列成员 ACK 或组播例外，不能说成员必不回 ACK，也不能说所有成员已收到。 |
| **4：server → IWF** | server 回发原请求的 IWF，不是另发一次取消请求，不是确认成员步骤，也不是给发起 LMR 用户的直接应答。NOTE 3 以原步骤 1 为先，保留继续呼叫的条件；图把 4 排在 2、3 后，不能据此增加必等 2 或 3 的规则，也不能说收到 1 就无条件回 4。 |

[§10.6.2.3.3 图、步骤和 NOTE 3，印刷页 131](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=132)。

表 10.6.1.11-1、10.6.1.12-1 各列两个必带项：**取消者 MCPTT ID**、**组 ID**。请求总表允许可选的 `Alert indicator`，指取消者本人的告警。本支步骤没有指定是否携带该项，也没有规定清告警动作，不能由字段可选推本支禁用、必带或已清告警。应答表不列 `Result`、告警指示或被通知用户 ID，组 ID 说明重复的 “in-progress” 不是新增字段。[两张表，印刷页 120–121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=121)。

§10.6.2.1 对 LMR 定义组说按已归属的 MCPTT 组成员发送逐人请求，字面却把发送端和目的端都写成 IWF。§10.6.2.3.3 的正文和图均明确步骤 1 是 **IWF → MCPTT server**，步骤 4 反向确认。不要把总则改写成一个确定的目标或由图只画一箭头推只有一笔；具体是否逐人、某条应答配哪笔实际请求，单凭这处文字和图还不能定。[§10.6.2.1 总则，印刷页 121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)；[§10.6.2.3.3，印刷页 131](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=132)。

判断现网信令，按同次组态取消、取消者、组、端点、方向和事务配对。server 实收 1，或 server 实际发出的匹配 4，可佐证请求到了 server；要说 IWF 收到了 4，另核 IWF 的实收。确认一跳信令不需要媒体证据。LMR 侧确认、组态或告警已清、承载是否已调整、成员是否收件或应用，及媒体是否停止，各自另取证。[步骤 1–4，印刷页 131](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=132)。
