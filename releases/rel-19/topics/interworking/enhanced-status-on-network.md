# 在网增强状态互通：谁请求分享，哪一侧查 IWF 归属？

**谁实际请求分享，决定读哪一支；不用先找到接收者的 IWF。** 只有要确认某个接收者属于 IWF 后方的情形，才查它所在 IWF 对同一目标组的实际归属。 这里限 TS 23.283 V19.5.0、Rel‑19 Stage 2 §10.16：在网增强状态分享给 MCData 组。IWF 是互通功能，在这两支作为对等 MCData server。它们不把 IWF 当作终端。

| 谁请求 | client 与 IWF 怎样分 |
| --- | --- |
| **MCData 用户请求（§10.16.3.1）** | 使用接收侧 client 2…n 的用户中，可有一名或多名 LMR 用户位于**已归属这个 MCData 组**的某个 IWF 后。IWF 作为对等 MCData server；不是说每次分享都必有 LMR 接收者。 |
| **IWF 代表 LMR 用户请求（§10.16.3.2）** | client 1 位于某个 IWF 后。接收 client 2…n 中，一个或多个也可以位于**已归属这个 MCData 组**的 IWF 后。IWF 对其他 MCData servers 作为对等 server；代发端不等于 client 1，也不要求所有接收者都是 LMR 用户或处在同一个 IWF 后。 |

[MCData 发起分支，印刷页 180（PDF 第 181 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)；[IWF 代 LMR 发起分支，印刷页 181（PDF 第 182 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=182)。

**只对上接收方的条件。** 假设 IWF 甲代表 LMR 用户向组 G 请求分享；一名接收者位于 IWF 乙后。乙已归属 G，才符合本段说的这种接收方条件。只知乙属于别的组，或乙出现在 G 的配置里，不能代替实际归属。原文这句不修饰位于发起侧的 client 1；不能用来要求甲也得归属 G，也不能据此断言甲免归属。两个 IWF 是否是同一实例，由实际部署和事件证据判断，条文不指定。[§10.1.2 归属入口，印刷页 17（PDF 第 18 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=18)；[互通组归属另查](affiliation-mc-group.md)，不把其他组呼的归属步骤照搬到增强状态。

**配置或服务器角色不说明收到了什么。** §10.16.1 把向接收用户提供增强状态的高层流程指向 TS 23.282 [6] §7.9；§10.16.2 把组配置里的预设值指向 §7.9.2；两方向都引用 §7.9.3 的在网过程。本版 §2 对 [6] 没写修订号，按非指定 3GPP 引用查同一 Release 的最新版本；这里没有核被引条文正文、预设值清单或载荷格式。预设值存在不表示配置已送达，也不表示某次已分享。“给所有接收的 MCData 用户”也不意味着已送达每个组成员。[§10.16.1–.3，印刷页 180–181（PDF 第 181–182 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=181)；[§2，[6] 和非指定引用，印刷页 11（PDF 第 12 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=12)。

实际交付另查对应接收端的证据。网关已归属、由对等 server 角色参与或发起请求，都不证明终端已收到、显示或已读。不从普通 [IWF SDS 的回执](sds-addressing.md)补 SIP／MSRP、处置码、超时或重试，也不把[离网普通 SDS](../mcdata/offnetwork-sds-initial-context.md)套到这一在网分支。
