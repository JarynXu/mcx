# MCPTT 发起、组也定义在 MCPTT：何时发 IWF 请求，回包能证明什么？

**MCPTT server 先检查主叫能否在该互通组发起紧急呼叫，再把紧急建呼请求发给 IWF。** 已有一条 IWF 归属代表全组 LMR 用户时发一条；收到 LMR 用户的逐人归属时，按已归属的 LMR 用户逐人发。IWF 的匹配应答和 MCPTT server 给主叫的应答是两笔信令，实际媒体另核。

本文限 **TS 23.283 V19.5.0（Rel-19 Stage 2）§10.6.2.2.2**。主叫是 MCPTT 用户，互通组也在 MCPTT 系统定义；图中另一名 MCPTT 客户端已归属该组。IWF 已接入并获准与 MCPTT 互通，且配置了组和用户身份映射。查规范不需要抓包；判断现场不能用主叫所属、IWF 出现或身份映射代替实际组定义和归属。图用一个 MCPTT server 表示主叫本属服务器和组托管服务器两个角色，不据此断定部署在同一台服务器。[§7.4.1、§10.6.2.2.2 前提和 NOTE 1，印刷页 15、123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=124)。

## 客户端配置和服务器授权是两关

| 位置 | 看什么 |
| --- | --- |
| **发起端配置** | 主叫客户端已配有指定的 MCPTT 紧急组。NOTE 3 允许另一种配置：在所选组上执行紧急行为。所选组不必同时是指定紧急组，也不能把没有紧急配置的普通选组当成这个替代条件。 |
| **步骤 1、2** | 用户发起后，客户端设置自己的紧急状态，保留到明确取消。发给 server 的紧急组呼请求带紧急指示，可附告警指示或隐式话权请求；这些字段不证明告警已送达或话权已授予。 |
| **步骤 3、4** | 主叫客户端此前未归属时，由 server 隐式归属；已归属不重复做步骤 3。server 仍核主叫用户对**该互通组**的紧急起呼授权；授权通过才解析成员及实际归属。客户端配置、已有归属或 IWF 互通授权均不替代这项主叫授权。 |
| **步骤 5、6** | server 配置组参与者底层承载优先级，记录该组的进行中紧急状态和起呼用户。组紧急状态持续至取消；这期间后续呼叫享有调整后的承载优先级。客户端紧急状态、组状态、承载优先级和话权许可不是一个结果。 |

[§10.6.2.2.2 前提 5、NOTE 3、步骤 1–6 和 NOTE 4，印刷页 123–124](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=124)；[图 10.6.2.2.2-1 与步骤 1–7，印刷页 124](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=125)。

## 分清 IWF 应答、主叫应答和媒体

| 步骤 | 端点与作用 |
| --- | --- |
| **7 → 8** | MCPTT server 向 IWF 发 `IWF emergency group call request`。IWF 若以一条归属代表组内 LMR 用户，发一条；server 若收到逐人归属，按每名**已归属的 LMR 用户**发一条，不按静态成员或 MCPTT 人数计数。IWF 给 server 的步骤 8 回应该腿。步骤 8 正文写成功路径；表 10.6.1.2-1 的 `Result` 必带，也可表示拒绝。请求及应答表的 `MCPTT ID` 是主叫，不是被邀成员；同组同主叫不能单独配对逐人请求。 |
| **9、10** | 步骤 9 是 server 向每名已归属 MCPTT 成员的客户端发邀请。步骤 10 是 server 给**发起端**的 MCPTT 建呼应答，不是 IWF 的步骤 8，也不是任一被邀终端已应答的证据。 |
| **11** | 成功流程在这里才描述 LMR 用户经 IWF 和已归属的 MCPTT 客户端建立媒体；主控是定义该组的 **MCPTT 系统**。实际 RTP 或音频要查该次媒体证据；匹配的步骤 8 或 10、优先级已配置，都不能代替它。 |

图画出一次 7／8、再画 9／10。**数量看步骤 7 的归属条件，时序看 NOTE 6 和 NOTE 8**：7–8 可在 5 和 10 之间发生；10 可在 8 后发生，并随继续呼叫的条件最迟在 9 之后。不能把图中的 9 固定为 10 每次都得等的门槛，也不能把步骤 9 的发邀请读作全员必须返回成功。两条注未定义逐人应答的聚合、缺答等待时限或失败处置。[§10.6.2.1、印刷页 121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)；[§10.6.2.2.2 步骤 7–11、NOTE 5–8，印刷页 124–125](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=125)；[表 10.6.1.1-1、10.6.1.2-1，印刷页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=118)。

要判断实际信令是否到达，看相应接收端对同一组、主叫和该笔事务的收件。实际回出的匹配应答也能支持原请求已到该端，不能证明原发送端收到了这个应答。**核实指定一跳的信令不需要媒体证据**。IWF 请求表把紧急指示列为必带、告警指示列为可选；隐式话权项只在发起客户端请求话权时才带。步骤 8 报告建呼结果，不证明 LMR 内部如何叫人、叫了谁或每人是否收件。NOTE 5、NOTE 7 分别把 LMR 内部叫人、IWF 对优先级的处理列在范围外；本页不给出 SIP 字段、拒绝原因或完整失败流程。[表 10.6.1.1-1 和 10.6.1.2-1，印刷页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=118)；[§10.6.2.2.2，印刷页 125](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=126)。
