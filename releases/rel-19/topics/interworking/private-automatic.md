# 互通自动私呼：哪一笔应答之后能走到媒体建立？

**先看谁发起。** MCPTT 主叫时，IWF 向 MCPTT server 回应，server 再向主叫客户端回应；LMR 主叫时，MCPTT 被叫客户端先回 server，server 再向 IWF 回应。两支都把 **MCPTT 客户端和 IWF 之间成功建立媒体面**列为步骤 7。原请求、别名解析、支持一种媒体类型、报文发出和真实媒体到达，是不同证据。

这里读 [TS 23.283 V19.5.0，Rel‑19，Stage 2，IWF‑1 §10.4.1.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=90) 的自动开始私呼。IWF 与 server 相连的一腿是 IWF‑1；图中的 server 与客户端是另一腿。两支都要求主叫已选自动模式、MCPTT 客户端已注册 MCPTT 服务、server 已订阅 MC 系统功能别名的激活/去激活更新。别名可选；LMR 主叫分支还要求 LMR 已向 MCPTT 用户发起私呼。查规范不需要抓包；判断某次通信，核实际主叫、所选模式及响应与哪笔请求匹配。没有振铃记录不说明它是自动模式。[通用请求表 10.4.1.2-1，印刷页 90](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=91)把请求的开始模式列为可选；本节步骤 1 随请求带所选的自动模式，不从通用表推未带该项时的默认模式。

## 两支的应答和重试

| 实际主叫 | 步骤 5（负责回报能力的端 → server） | 步骤 6（server → 发起侧） |
| --- | --- | --- |
| **MCPTT 客户端 → LMR** | IWF 回 `IWF private call response`，报告结果以及对请求媒体的支持；失败可附替代参数。 | 向 MCPTT 客户端转交 `MCPTT private call response`。看本次应答的 Result。若失败而替代参数可接受，**客户端可另发请求**，也可结束；参数不可接受则呼叫失败。 |
| **LMR → MCPTT 客户端** | 被叫客户端回 `MCPTT private call response`，报告结果以及对请求媒体的支持；失败可附替代参数。 | 向 IWF 发 `IWF private call response`；正文写使用步骤 4 发出的媒体类型。参数不接受则失败；**有变化且 IWF 接受**时，IWF 可用新参数从步骤 1 另发 IWF 请求；无变化是正文继续本次流程的条件，不是独立成功证据。 |

[§10.4.2.1 与图 10.4.2.1-1，印刷页 92–93](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=93)；[§10.4.2.2 与图 10.4.2.2-1，印刷页 94–95](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=95)。两支步骤 6 的正文分别在成功、参数不变时写回到“步骤 6”；图和各自正文都把新状态“媒体面已建立”列在步骤 7。保留该回指，不据此编出再发一次响应的循环或把收到步骤 6 当作媒体已到。替代参数的段落回指步骤 3，但不能给直接 ID 场景补出一次别名解析，也不能把附带的替代参数拿来延续已失败的那笔请求。

IWF‑1 的[表 10.4.1.3-1，印刷页 91](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=92)将 `Result` 与 `SDP answer` 标为必有信息，将 `Acceptance confirmation` 标为可选。流程中报告支持一种媒体类型、SDP 选择、参数不变和可选接受确认，都不替代本次响应的成功结果。自动流程不列手动分支的“振铃、等被叫实际接受、再发后续响应”。不要从这张 Stage 2 表推 SIP 成功/失败码、ACK、早期媒体或某状态码必带的 SIP 正文。

## 怎样对上这一笔请求

- **MCPTT 主叫才走出向一支。** server 核 MCPTT 主叫的私呼及自动发起权限；使用主叫别名则核其可用及激活，被叫用别名则另核解析及双方许可。授权后步骤 4 是 **server→IWF**，转送原来提出的媒体类型或其子集。请求含位置时，按该段的隐私检查决定是否转给 IWF。发了请求不等于 IWF 已接受。
- **LMR 已发起才走入向一支。** IWF 的步骤 1 请求到 server，server 核 MCPTT 被叫已获授权且能够接收、并有自动接收权限；LMR 主叫可以使用已激活且归属 MCPTT 系统的功能别名（前提 4），并非必带。主叫可选用别名，与被叫以别名寻址分开；只有后者才另按步骤 2 解析被叫并核许可。不要把 MCPTT 主叫分支的 GSM‑R 最终解析注套到这里。授权后步骤 4 是 **server→MCPTT 被叫客户端**，同样不凭转送确定所选媒体的结果。LMR 用户与 IWF 之间的调用以及 LMR 替代地址映射不在本节范围。
- **别名解析或参数重试会换请求。** 步骤 3a 返回已解析的 MCPTT ID，不是建立成功；收到了相应解析响应才放弃原请求、由原发起端（MCPTT 客户端或 IWF）对解析目标发新请求。LMR 主叫一支的图把步骤 3b 标为 IWF private call request，正文用了 MCPTT private call request；发起者是 IWF，不能用命名差异换成客户端发出的消息。参数改变后另发也是新的尝试，不能用旧失败或旧成功应答替代它。LMR 归属别名（如 GSM‑R）的最终解析见 .2.1 注 1，不能假定所有这类别名都在 MC 侧最终解析。

## 什么时候可以说媒体能走？

- **查规则：**步骤 7 中，MCPTT 客户端已成功建立至 IWF 的媒体面，才有本节所列的两端可传媒体；不是发完请求就传，也没有额外的手动接听步骤。
- **查实况：**用对应请求的步骤 5/6 结果和实际媒体建立情况判断。步骤 5 的成功不证明步骤 6 已送达；步骤 6 的成功也不证明媒体面已建立、某个首包已发送、更不证明对端收到或 LMR 用户听到。重试必须查新尝试。
- **用了话权控制：**两支步骤 7 分别把授予、竞争处理、撤销交给发起侧系统（MCPTT 或 LMR）。媒体面可用不等于某端已获话权；这些分支也允许不启用话权。一般主控分配另看[话权主控](floor-control-owner.md)，不把本例当作全局配置规则。

问[手动私呼](private-manual.md)才查振铃与被叫实际接受后的步骤 9–11；[已建私呼释放](private-release.md)适用于通话已在进行，不能当成建立阶段参数拒绝或重试的后续；[加密](private-encryption.md)另查密钥与保护范围。依据：[手动差别 §§10.4.3.1–.2，印刷页 97、99](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=98)，[释放前提 §10.4.4.1，印刷页 99](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=100)。不套离网私呼、MCVideo 或 TS 23.379 的底层行为。
