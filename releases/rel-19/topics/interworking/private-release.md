# 互通私呼释放：发起方与确认次序

ETSI正式发布的TS23.283 V19.5.0，Release19，Stage2。

适用前提：MC用户已注册且正与经IWF接入的LMR用户私呼；可为自动或手动模式，有或无话权控制。

## MC客户端发起释放

客户端向服务器请求结束，服务器转IWF；收到IWF确认后，服务器再确认客户端请求。客户端和IWF释放媒体资源；若有话权控制，也释放相关资源，客户端不得再请求话权或发送媒体。 [§10.4.4.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 服务器因结束条件决定终止

最大通话时长或无收发超时是示例条件，并非本页给定的固定时长。服务器向MC客户端和IWF发结束请求，双方确认并释放媒体及适用的话权资源，用户获得结束通知。 [§10.4.4.2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## LMR用户或系统发起释放

IWF请求服务器，服务器转MC客户端；收到客户端确认后再确认IWF。双方释放媒体及适用的话权资源。附加应用数据可选，客户端如何反应不在该规范范围。 [§10.4.4.3](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 哪条结束应答可以触发另一条

**按谁发起这次释放分路，不按最初谁起呼。** 三支都讨论 MCPTT 用户已注册、正与经 IWF 接入的 LMR 用户通话。原呼叫可手动或自动建立，可以有或没有话权控制。只查规范或一条已认出的消息，无需先有完整来回记录。

| 这次谁先要求结束 | 结束请求走哪条腿 | 应答与结束通知 |
| --- | --- | --- |
| **MCPTT 客户端，§10.4.4.1** | 2 客户端经 SIP 核心向 server 发原生结束请求，视释放原因可带附加应用数据。3 server 向 IWF 发对应请求，按原请求指定的 MCPTT 客户端 ID 寻址。 | 4 IWF→server 应答。server **收到这笔匹配应答后**才生成给原客户端的确认（5，图为 server→客户端）。正文步骤 5 把 IWF 来的确认称为 MCPTT 私呼结束请求确认；4 和图称 IWF call end response，是同一笔输入，不再补一条原生应答。LMR 用户也会被通知，方式不在范围内。 |
| **MCPTT server，§10.4.4.2** | 步骤 1 是 server 本身决定结束。管理员配置的最长通话时长到期、无收发超时只是例子。2a 发原生结束请求给客户端（经 SIP 核心）；2b 正文写按与 LMR 用户关联的 MCPTT 客户端身份发送，图中是 server→IWF。2b 不是再次向本地客户端发 2a。 | 本地 MCPTT 用户获终止通知（3）；注说 LMR 用户也被通知，方式不在范围内。图中有两个同编号 **4**：原生客户端和 IWF 各回 server，分别确认各自被请求的腿。没有把一个回包说成两端都确认，也没从图的排布规定两条同时到达、谁先回或等齐才开始清理。 |
| **LMR 用户或 LMR 系统，§10.4.4.3** | 引言包括两者；步骤 1 写 LMR 系统欲结束，图在 IWF 泳道画开始动作。2 IWF→server 可视原因带附加应用数据，步骤 2 首句与附加数据句用两个请求名称，仍是这一腿。3 server 把原生结束请求发给原 IWF 请求指定的 MCPTT 客户端。 | 4 是 MCPTT 用户的结束通知。原生请求确有附加数据时，客户端可按内容响应，具体反应不在范围内；只看到步骤 2 的数据，不证明 3 带原值或已经显示。5 客户端→server 确认。server **收到这笔匹配确认后**才生成给 IWF 的应答（6，图为 server→IWF）。 |

例如，看到 server→IWF 的结束请求，可能是 .1 的转发，也可能是 .2 的主动结束。要判完整分支，看本次原请求或 server 本身的决定；要判一端是否已确认，分别看对应操作、角色、端点、发送与实收。标准给出 .1 的 4→5 与 .3 的 5→6 的收件依赖；现场只见外腿应答发出，不代内腿的实收记录或对端的最终收件。一个通知动作也不代用户实际看到通知。

**最后释放的是这通私呼的资源。** 三支分别在 6、5、7 写 MCPTT 客户端和 IWF 释放用于这通呼叫的全部媒体面资源。建立时启用了话权控制，还释放话权资源；该条件句也写客户端不能再请求话权或发送媒体。没有话权控制仍要释放媒体资源，不能反过来当成释放后仍可发媒体。图中资源框跨 server 泳道，不据此增加 server 的清理要求；确认、提示、资源真正释放和媒体实际停止都要各自取证。这里的整通结束与 [单次话权交还或撤销](floor-control-owner.md) 不同。
