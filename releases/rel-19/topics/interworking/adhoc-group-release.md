# 互通 ad hoc 组呼如何释放：谁发请求，组何时消失？

**按这一次从哪侧发起释放分流，不按当初谁建呼。** 固定 TS 23.283 V19.5.0、Rel‑19 Stage 2，只看已建 IWF 互通 ad hoc 组呼的整次释放。普通组按定义侧释放另查[§10.3.3.8](group-call-release.md)；[单个用户退出](../calls/group-participant-leave.md)也不是本页流程。

## MC 系统开始释放：2a 发请求，2b 回 server

§10.17.3.3 的 Step 1 有两个入口：MCPTT server 因释放条件满足而发起，或获授权用户发起。前者回指 TS 23.379 §10.19.3.1.2，后者回指 §10.19.3.1.2a。原文两条前提都写 IWF 已配置两系统的组和用户 ID 映射，是重复的文字，不是第二个条件。经过 IWF 的跨系统信令由 IWF 转换身份和协议。映射不能证明本次释放条件或用户权限成立；获授权用户也不等于只能是原主叫。[§10.17.3.3 前提，印刷页 187（PDF 第 188 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=188)。

MCPTT server 向 IWF 发 2a 释放请求，IWF 向 server 回 2b 释放应答。发送、对应端实际收到及各端资源清理分别取证。正文的 Step 3 说的是成功终态：呼叫已终止，client 1、client 2 与 LMR 用户已释放该呼叫的话权控制和媒体面资源，**临时组不再存在，不能用同一个组再起呼**。图只把它们画成释放过程。看见 2b 甚至 server 确实收到了 2b，也还不能判达到 Step 3。同一个组不能再用，不等于规定后续永远禁止使用相同字面 ID，或必须删除全部记录。[图 10.17.3.3-1、Steps 1–3，印刷页 188（PDF 第 189 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=189)。

## LMR 系统开始释放：2 向 server，7 才回 IWF

§10.17.3.4 始于 LMR 侧的释放条件；NOTE 1 不定义那些条件。发送请求的 LMR 用户须符合 TS 23.379 §10.19.3.1.2a 的授权，IWF 须已有两系统组、用户 ID 映射。图把获授权用户放在 IWF 一侧，不把网关认成授权对象。Step 2 从 IWF 向 server 请求释放，Step 3 是 server 对本次请求验权并生成释放。[§10.17.3.4 前提，印刷页 188（PDF 第 189 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=189)。

server 向示例 client 2／3 发 4a／4b；两个客户端分别提示用户（5a／5b）并各回 server（图标号是 **6b、6c**）。Step 7 从 server 返回 IWF；Step 8 是 IWF 一侧的通知动作，不能证明哪个 LMR 用户实收。图示的 7 在两条响应后，不据图判必须等齐、无需等任何响应或全体终端都已清理。Step 9 的横条只画关联话权与媒体资源的释放，**本段不说明临时组是否消失、保留或可复用**，不能套用 .3.3 的 Step 3。仅看见发 7、IWF 收 7 或一端完成释放，不能判整组已释放。[图 10.17.3.4-1 与引用，印刷页 189（PDF 第 190 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=190)。
