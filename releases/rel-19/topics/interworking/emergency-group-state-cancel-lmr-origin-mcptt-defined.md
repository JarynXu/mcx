# LMR 用户取消 MCPTT 定义组的紧急状态：谁验权，谁回 IWF？

**IWF 向 MCPTT server 发请求（1），server 验发起者的本组取消权限（2）。server 清组状态（3）后可回 IWF（6），不必等图中后列的承载调整或成员处理。** 这里问的是 MCPTT 定义互通组仍在进行中的紧急状态，不是结束通话。查规范不用抓包。[TS 23.283 V19.5.0 §10.6.2.3.1 图及步骤 1，印刷页 128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=129)；[步骤 2–6、NOTE 4，印刷页 129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=130)。

## 先认准组和请求

LMR 用户明确请求取消组的紧急状态。该互通组定义在 MCPTT，仍处紧急状态，已有 MCPTT 客户端归属；IWF 已接入并获准互通，且在 IWF 配置了组和用户身份的映射。IWF 获准互通、映射匹配，均不能代替 server 查这名用户是否有权取消本组状态。本节没有要求此人先前发起原紧急组呼，也未列优先承载支持或持续媒体为前提。挂断不能清组紧急状态。图中一台 MCPTT server 代表用户本属与组托管角色，不规定它们同机。[前提、NOTE 1–3，印刷页 128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=129)。

## 把回执和取消结果分开

| 步骤 | 看什么 |
| --- | --- |
| **1：IWF → server** | IWF 为发起取消的 LMR 用户发组紧急状态取消请求。可另指定清发起者本人的告警；只取消告警、不改组状态不走本支。 |
| **2、3：server 本地** | server 验发起者的取消权限。成功流程在 3 清组紧急状态；只有同一请求另指定才一并清发起者本人的紧急告警。不从这一步推出自动清告警、取消他人的告警或 LMR 内部完成。 |
| **4：调整本地承载** | server 调整底层承载优先级；这次组状态不再要求紧急优先。不规定撤掉其他原因的优先级、实际承载值、媒体停止或继续，或话权释放。 |
| **5：面向已归属 MCPTT 客户端** | server 按 TS 23.379 §10.6.2.6.1.3 处理，图画的是通知成员。本节没有单列成员 ACK 或组播例外，不据此宣称成员永不应答。 |
| **6：server → IWF** | 回答原步骤 1，不是再向 IWF 发一条取消请求，也不是给起始 LMR 用户的直接回执。NOTE 4 明说 6 可在 3 后发出，没加“视继续呼叫的条件”的措辞。图把 6 放在 4、5 后面，不能据此定成必等 4、5 或成员收件。这个注释不是拒绝处理或超时规则。 |

[图 10.6.2.3.1-1 与步骤 1，印刷页 128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=129)；[步骤 2–6、NOTE 4，印刷页 129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=130)。

表 10.6.1.11-1 和表 10.6.1.12-1 各列两个必带项：取消者的 **MCPTT ID**、被取消紧急状态的 **组 ID**。只有请求表列可选 `Alert indicator`，含义是是否同时取消发起者本人的告警；不是目标 LMR 用户 ID。应答表不列 `Result`、告警指示或被通知用户 ID。应答表的组 ID 描述重复写了 “in-progress”，不是额外字段。两张表描述双向信息流，本场景的请求和应答仍按图中的 **1/6** 配对。总则 §10.6.2.1 描述发往 IWF 的请求粒度，不在这个 **IWF 发出请求** 的场景补反向请求、逐人扇出或第二个确认。[两张表，印刷页 120–121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=121)；[§10.6.2.1，印刷页 121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)。

判断现网信令时，按同次取消的组、取消者、端点、方向和事务配对。server 实收 1 的证据或 server 实际发出的匹配 6，支持请求到了 server；要说 IWF 收到了 6，另核 IWF 端收件。信令判断不用媒体证据。组状态、是否清告警、承载是否已调整、成员是否收到或应用、LMR 端结果和媒体是否停止，分别查证，不由 IWF 回执一并推出。[步骤 1–6，印刷页 128–129](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=129)。

## 换了发起侧、组定义或所取消的对象，就换入口

- **MCPTT 用户发起、组仍定义在 MCPTT：**读 [§10.6.2.3.2](emergency-group-state-cancel-mcptt-origin.md)。该支的 IWF 6/7 是 **server 发请求、IWF 回**，不是本页的方向；发起端另收 9，NOTE 5 是步骤 4 后并看继续条件。[印刷页 129–130](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=130)。
- **LMR 用户发起、组定义在 LMR：**§10.6.2.3.3 的 1/4 仍是 IWF 与 server 的请求/应答，但该图和步骤没有列本页的 server 验权、清状态这两步；NOTE 3 说 4 可在 1 后，取决于继续呼叫的条件。未列验权不能当作无需授权。**MCPTT 用户发起、组定义在 LMR：**§10.6.2.3.4 又不同，3/4 是 server 向 IWF 请求、IWF 应答，7 回 MCPTT 发起端，NOTE 5 以 4 为边界并保留继续条件。两支仅用于选入口，不据此判断其完整取消、授权或拒绝流程。[印刷页 131–132](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=132)。
- **LMR 用户主要请求取消紧急告警：**查 §10.6.5.1。它的告警取消请求可另请求清组紧急状态（NOTE 2），仍不能按本页的组状态取消消息或时序读。不要把其中成员 ACK、组播例外或他人告警字段补到本页。若取消的是[迫近危险状态](imminent-peril-group-state-cancel.md)、只问[组呼整体释放](group-call-release.md)，或要查[紧急建呼](emergency-group-setup-lmr-to-mcptt.md)，分别进入相应主题。这里不定义 SIP、LMR 内部回执、失败码或重试。[§10.6.5.1，印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)；[§10.6.3.4，印刷页 137–139](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=138)。
