# IWF 功能别名：激活、停用和逐项结果

**MC service server 处理激活或停用；回给请求者的是逐别名结果，发给其他共享者的是另一条通知。** 同一请求可以带多个别名。只收到回复，不能判整组别名都成功；收到“可接管”，也不表示已经接管。

适用：TS 23.283 V19.5.0 Rel‑19 Stage 2 §§10.14.3.3–.4，系统提供功能别名，发起者是归属 IWF 的用户。MC service ID 在 MC 系统代表该 LMR 用户，不是 IWF 节点身份。§10.14.1 说明功能别名对支持 TS 22.179 的系统是可选特性。查规范无需抓包。[§3.1，印刷页 12](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=13)；[§10.14.1，印刷页 170](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=171)。

## 两种请求，检查的条件不同

- **激活（§10.14.3.3）：** IWF 已取得该用户可激活的别名配置，可以是静态或动态配置。MC service server 已取用户订阅与别名策略。步骤 2 的图框写按策略和订阅核权，正文步骤 2 写检查与已激活别名的冲突，步骤 3 以请求者获授权为存状态的条件。拿到配置不代替 server 核权；存状态不等于逐项获准。按多人共享分支，允许共享且人数未达上限时，MC 业务必须为该用户激活并通知其他共享者；已达上限或不允许共享时，原文在该分支写拒绝并以步骤 4 通知 IWF。这不是禁止激活空闲的非共享别名。步骤 3 另写，别名已被其他人使用时，获授权的 IWF 归属用户收到接管选项。不要用共享拒绝替所有别名判接管资格，也不要把选项当作完成接管。[§10.14.3.3 前提，印刷页 173](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=174)；[图 10.14.3.3-1、步骤 1–5，印刷页 174](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=175)。
- **停用（§10.14.3.4）：** MC service server 已向功能别名管理服务器订阅别名信息，并保存了 IWF 归属用户已激活的别名数据。步骤 2 按用户订阅和已存别名策略，检查**该用户是否有权停用**和**该用户是否已激活所请求的别名**。别人的激活不能替代后者。步骤 3 的字面只重申获授权后更新这名用户的激活状态，没有单列已获授权但未激活时如何处理或返回。不把停用一名用户理解成撤销所有共享者。[§10.14.3.4 前提，印刷页 174](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=175)；[图 10.14.3.4-1、步骤 1–5，印刷页 175](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=176)。

## 别名列表是请求范围，状态才是逐项结果

两图的步骤 1 都是 **IWF → MC service server**。表 10.14.2.3-1 和 10.14.2.5-1 都要求请求者 `MC service ID`、含至少一个别名的 `Functional alias list`，两项均必选（M）。这不是[查询功能别名](functional-alias-query.md)的可选目标字段。

| 步骤 4 应答 | 表列的必选信息（M） |
| --- | --- |
| 激活 | 原请求者 `MC service ID`、拟激活的别名列表、每个别名的激活结果：`activated`、`rejected` 或 `can be taken over`。 |
| 停用 | 原请求者 `MC service ID`、拟停用的别名列表、每个别名的停用结果。停用表没有列状态枚举，不照搬激活的三个值。 |

应答列的是**原来想变更的别名**，不是只列成功的别名。判断 A 请求的两项是否成功，要匹配本次操作、原请求者、相应别名和各自结果；只看到列表出现或应答已发，都不能替代逐项结果。图上步骤 4 是 **server → IWF**；激活信息流写到 IWF，停用信息流写给归属 IWF 的用户，两处过程正文都说给原发起用户。服务器发出、IWF 实收和请求者看到结果分开取证，不从图里补一条终端确认。[表 10.14.2.3-1 至 10.14.2.5-1、§10.14.2.6 引言，印刷页 171](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=172)；[表 10.14.2.6-1，印刷页 172](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=173)。

## 共享者通知不是原请求的应答

步骤 5 是服务器通知**共享相同别名的其他对象**，不是向所有用户广播。激活正文写其他 MC service 用户和/或共享别名的 IWF；停用正文写其他 MC service 用户和/或归属 IWF 的共享用户。两图都只画一个 IWF 端点。IWF 通知表的必选三项是发起变更者的 `MC service ID`、至少一个别名的列表、逐别名 `Operational status`；ID 不是通知接收者。通知和步骤 4 可能走同一方向，仍是两种消息。拿到其中一条，不能证明另一条已到，更不能证明其他持有者都收到、被停用或已交出别名。[表 10.14.2.7-1，印刷页 172](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=173)；[§10.14.3.3–.4 步骤 5，印刷页 174–175](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=175)。

本页只解释激活与停用。实际发起接管按 [§10.14.3.5，印刷页 175–176](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=176)另查；一般共享与接管要求看 [Stage 1](../identity/functional-alias.md)，原生 MCData 变更看[本业务对应过程](../mcdata/functional-alias-change-request.md)。这里未定义线上协议、错误码、缺失应答原因、超时重试或多个别名的事务原子性。[结构化条件](functional-alias-activation-deactivation.json)。
