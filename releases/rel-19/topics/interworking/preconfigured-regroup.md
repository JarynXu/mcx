# 预配置重组：配置来源组不是重组本身

TS23.283 V19.5.0，Release 19，Stage 2。

TS23.283 §10.3.7.1 的 MCPTT 预配置重组，非完整形成协议。

## 准备重组

相关成员须提前取得配置；提供配置的预配置组不是实际重组组，可服务多个组/用户重组。实际重组 ID 由授权用户，或拥有该重组的 IWF，在重组时提供。 [§10.3.7.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 根据配置选择广播或非广播重组

广播型仅授权用户或拥有重组的 IWF 发、其余成员收；非广播型允许成员收发，但不表示免除话权规则。 [§10.3.7.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 某个待重组组已按 TS23.280 或 §10.2.2 重组

本节预配置重组请求必须拒绝；本过程仅服务 MCPTT，并独立于 §10.2.2 的组重组。 [§10.3.7.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 边界

只核验所列互通条款；TS23.280/23.379 引用的配置字段、隐私策略及基础过程未独立核验，不能据此形成完整实现。

如果输入是用户名单、要查实际新组怎样在 MCPTT 或 IWF 侧形成，另读[预配置用户重组成形](preconfigured-user-regroup-formation.md)（§10.3.8），不把下面的组成组规则替入。

## 漏收重组通知后按下 PTT

以下两条是 TS 23.283 V19.5.0 的 Stage 2 互通流程。A、B、C 是构成组，D 是由 IWF 管理的实际重组组。查规则不需要抓包。判断一次拒绝时，要对上重组状态、实际目标组、终端漏掉的通知，以及 IWF 的应答原因。

### 重组还在进行，终端呼叫构成组 A

终端已归属 A，A 与 B、C 正在重组，终端漏收了建立重组的请求。A、B、C 可由 IWF 或 MCPTT 系统管理。终端请求在 **A** 建立组呼，MCPTT server 转给 IWF。IWF 拒绝，原因是 A 正在参与重组；server 向终端转交拒绝。IWF 另发带实际重组组 ID **D** 的重组请求，经 server 转给终端。补发不是把 A 的呼叫自动改发到 D。

终端告知用户 A 的呼叫失败和重组情况，并向 server 发重组确认。server 再把确认转给 IWF，IWF 将该终端归属到 D。注 1 允许步骤 5 先于步骤 4，也说步骤 7 可在步骤 4 后发生；不能仅凭图上的编号断定整个流程的固定收发顺序。终端发确认、IWF 实收确认、IWF 已执行归属是不同证据。

D 已有呼叫时，可按晚加入程序加入；D 此时确无呼叫时，用户可重试组呼。查[互通组呼晚加入](late-entry.md)时，要核对 D 上的实际进行中呼叫、参与侧归属成功、双方已知组配置、IWF 的组与用户标识映射，以及所选晚加入分支的组定义和用户侧前提。D 由 IWF 管理不替代这些条件；接到补发或回了确认也不证明晚加入、话权或媒体成功。[§10.3.7.5.1，印刷页 80–81，图 10.3.7.5.1-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=81)。

### 重组已经取消，终端仍呼叫 D

终端是以前参与重组的 A 的成员，漏收了重组取消请求。终端仍请求在 **D** 建立组呼，server 转给 IWF。IWF 拒绝，原因是重组已不活跃；server 把拒绝转给终端。D 仍在终端的配置档中，或终端仍是 D 的成员，都不表示重组仍活跃。本分支的前提是 A 的成员身份，不要求补证当前归属 A。

补发取消请求（IWF→server→终端，步骤 5、6）与取消确认（终端→server→IWF，步骤 8、9）是可选步骤。步骤 6 若发送，注 3 建议单播；这不是必须补发。步骤 7 是终端告知用户呼叫失败、重组已取消，不在注 2 的可选列表内。单独看见取消应答，不能证明 IWF 已收到转发，也不能证明再次执行拆除、退归属或删配置。[§10.3.7.6.1，印刷页 82–83，图 10.3.7.6.1-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=83)。

两条流程的步骤 3 都叫 IWF 组呼应答，拒绝原因不同。通用表 10.3.2.3-1 列出目标成员 MCPTT ID、组 ID 和 SDP answer，没有为这两种拒绝定义失败字段、SIP 状态码或 SDP 映射。不要用消息名或表中的 SDP answer 推断呼叫已建立。[开始形成组重组时的冲突拒绝](preconfigured-group-regroup-rejection.md)、主动撤销、重组中有新成员归属，各有独立入口，不套这里的 PTT 恢复步骤。[§10.3.2.3，印刷页 35–36](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=36)。

## 构成组刚归属，怎样加入正在进行的预配置重组？

A 是这次归属的构成组，D 是已经开始的实际重组组，P 提供 D 的配置；**P 不是 D**。这两个流程的对象先前是 A 的成员但尚未归属 A；本次按各支所列角色实际归属 A 后，再处理 D。只在 A 的成员表里、已经配置 D、发出归属请求或此前就已归属 A，都不能证明有这次新归属。查规范不需要抓包；判断现场是否走到某一步，按实际事务分别核对 A 归属、重组消息和 D 归属。用户归属在哪一侧、A 由哪边定义，都不能替代对 D 所有者的判断，也不要把上节陈旧 PTT 的 IWF 管理 D 前提带到这里。

### 新归属的是 MCPTT 客户端（§10.3.7.7.1）

客户端是 A 的成员，原先未归属 A；A 参与正在进行的重组。客户端已预配 D 的 MCPTT 组 ID 和组配置，也已收到用于该重组的安全信息。步骤 1 的新归属发生在 A：本节称它为 MCPTT 组，步骤 1 引用的 [§10.1.2.4，印刷页 20–21](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=21)明确是 MC 侧经 IWF 归属 **LMR 系统定义的组**。不能因名称或客户端类型改读成 MC 定义的组。该基础流程也有隐式归属，不把显式的客户端请求和应答当成唯一证据。

A 归属后，IWF 向 MCPTT server 发重组请求（步骤 2）。server 向客户端发预配置重组请求（步骤 3），客户端告知用户（步骤 4）。

- **步骤 5，客户端 → server：**客户端可以发重组确认；若步骤 3 的请求用组播发，客户端不对该组播请求发此确认。单播也不是必须回。图 10.3.7.7.1-1 将箭头 5 标成 `IWF pre-configured regroup response`，与图中箭头 6 同名；正文在步骤 5 只称 `pre-configured regroup response`，发件人是客户端，不能按图名把它当成 IWF 发的消息。
- **步骤 6，server → IWF：**正文另列 server 发 IWF 重组应答、IWF 将 MCPTT 客户端归属到 D，没有把它写成等待客户端步骤 5 确认才执行。组播没有客户端确认不等于没有步骤 6。客户端发确认、server 发应答、IWF 实收应答、IWF 已执行 D 归属，是不同证据。

[§10.3.7.7.1，印刷页 83–84，图 10.3.7.7.1-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=84)。

### 新归属的用户在 IWF 侧（§10.3.7.7.2）

这里的前提是 LMR 用户是 A 的成员，原先未归属 A；IWF 已预配 D 的组 ID、配置并收到安全信息。步骤 1 的行动方是 IWF，它归属 A。引用的 [§10.1.2.2，印刷页 18–19](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=19)是 IWF 代 LMR 侧归属 **MC 系统定义的组**；基础条文的逐用户和按 IWF 汇总两种记录不能靠本节标题选定，更不能据此补出 D 的逐用户记录。

MCPTT server 查出两个用途不同的 ID：实际重组 D 的 MCPTT 组 ID，以及配置来源 P 的 MCPTT 组 ID（步骤 2）。server 向 IWF 发重组请求（步骤 3），IWF 向 server 回应（步骤 4）。这两条箭头和上一分支的 server/IWF 方向相反，不存在要沿用的客户端步骤 5 确认。

步骤 5 的正文写 **MCPTT server 把 IWF 归属到 D**，图 10.3.7.7.2-1 的 server 操作框却写 `Affiliate user to the regroup group`。两处都把动作放在 server；被归属对象的写法不同。不能从图名认定已写入某个 LMR 用户的独立 D 归属，也不能只看 IWF 回了重组应答，就认定 server 已收或已做步骤 5。

[§10.3.7.7.2，印刷页 84，图 10.3.7.7.2-1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=85)；[§10.3.7.1，印刷页 72–73，D 与 P 的用途](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=73)。

### 加入重组和加入一次呼叫，分别核对

重组在进行不等于 D 正在通话。本节只描述向已有 D 补归属，不是新建重组、发起呼叫或加入呼叫的程序，也不证明获话权或收到媒体。要判断是否进入一场**已经在进行**的 IWF 互通组呼，看该通话的组和参与侧实际归属是否匹配，再按组定义、参与侧、配置及标识映射查[互通组呼晚加入](late-entry.md)；不要把对 A 的归属或一笔重组应答当作已加入 D 的呼叫证据。[§§10.3.3.7.1–.3，印刷页 48–50](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=49)。这里是 Stage 2 信息流，不据名称填 SIP/Stage 3 状态码、超时或重试。

## 广播结束后谁发起取消重组

**先形成临时重组 D，再在重组上做广播，最后单独发起取消 D。** D 由 MCPTT server 托管时，第三步由 MCPTT 客户端发起；D 由 IWF 托管时，由 IWF 发起。不能按某个构成组、发送者或收听者的本属来选。查规范不需要抓包。这里读 TS 23.283 V19.5.0 §10.3.4.6：两支把重组用于这次广播的持续期间，不是所有预配置重组的通用结束规则。临时组也可以是非广播型，不能说一次普通通话结束就撤销 D。

| D 由谁托管？ | 要核的前提 | 三步由谁发起或执行？ |
| --- | --- | --- |
| **MCPTT server（§10.3.4.6.2）** | MCPTT 客户端已注册、有发起预配置重组的许可；获权用户至少是一个本次构成组的成员。示例另要求客户端已归属组 1。客户端和 IWF 已预配 D 的组 ID 与配置、已获所需安全信息；客户端知道 IWF 和拟重组用户的 UE 都已预配的合适配置来源。IWF 已归属组 1、2、3 中至少一组，还须是至少一个构成组的托管侧。这两项分别核。 | 获权用户经客户端发起形成，组 1、2、3 组成组 4；MCPTT 用户经客户端做广播；**MCPTT client 发起取消**。不是图里出现的 MCPTT server 代替终端发起第三步。 |
| **IWF（§10.3.4.6.3）** | 两个 MCPTT 客户端均已注册，都已预配 D 的组 ID、配置并取得所需安全信息；客户端 1 已归属组 1，客户端 2 已归属组 2；MCPTT server 至少托管一个构成组。不能因为 server 有构成组就把 D 判为 server 托管。 | 概述写 IWF 用户可发起这类广播，图文三步的行动方是 **IWF**：发起形成，把组 1、2 组成组 3；做广播；发起取消。不把左列的用户许可和两项 IWF 归属／托管条件照搬到本支，也不据此说本支免验权。 |

[§10.3.4.6.1–.2、图 10.3.4.6.2-1，印刷页 61–62](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=62)；[§10.3.4.6.3、图 10.3.4.6.3-1，印刷页 62–63](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=63)。

**配置来源 P 不是本次重组 D。** §10.3.4.6.1 写在 “pre-configured group” 上广播；§10.3.7.1 明确提供配置的组不是实际重组。上述组 4、组 3 是各图组成的 D；不因概述的写法把 P 当作广播或取消的实际目的，也不从本节推报文字段或线路上的组 ID。两图把形成与取消都回指 §10.3.7.1，广播回指整个 §10.3.4；它们画的是三个子流程框，不是三条消息，也没给每段逐跳应答。MCPTT 托管图还明确省略收听端；IWF 托管图画了两个端，也不能凭画面推回执。[§10.3.7.1，印刷页 72–73](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=73)。

**广播结束、发起取消、撤销生效是三件事。** 收到本次广播的结束应答，不证明已经发起取消，更不证明 D 已撤销、成员都退归属或配置已删。要查执行，用同一次 D 的实际形成、广播结果和取消证据分别判断；问形成或撤销的具体流程，可先查同版 [§10.3.7.2／§10.3.7.3，印刷页 73–78](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=74)，再选适用分支。本节没给失败时是否取消、自动拆除、固定时限或 SIP 映射。问非此重组场景的[互通组广播建呼](group-broadcast-setup.md)或[广播释放回包](group-broadcast-release.md)，按两页各自前提读。不因 §10.3.4 的回指，把其中 MCPTT 用户起呼的图拼成 IWF 用户起呼的细节。
