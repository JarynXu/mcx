# LMR 用户取消互通紧急告警：两种回执怎样区分？

**步骤 2 是 MC service server 对 IWF 告警取消请求 1 的确认。步骤 5 是收到成员侧请求 3 的 MC service client 回给 server 的确认；组播呼叫场景不发这笔成员确认。** NOTE 3 允许步骤 2 和 3 任一先发，不能用图中顺序要求先回 IWF 或先发成员请求。查规范不需要抓包。[TS 23.283 V19.5.0 §10.6.5.1 图及步骤，印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)。

## 原请求是告警取消

LMR 用户先前已经通过 IWF 成功发起紧急告警，现在明确请求取消该告警。IWF 已掌握互通组信息，且配置了 MC 和 LMR 之间的组、用户身份映射。组可以定义在 MC，也可以定义在 LMR；图中的两个 MC service client 已归属。server 可能已经为 LMR 用户做显式或隐式归属，原文没把执行这一步写成必需。NOTE 1 的身份转换和协议翻译适用于 **经过 IWF、跨 MC 和 LMR 系统的信令**，不是所有 MC 系统内成员消息。此处不补具体 LMR 侧报文。[§10.6.5.1 前提、NOTE 1，印刷页 142](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)。

步骤 1 指向 **IWF 先前代表同一 LMR 用户成功送出告警请求的 MC service 组**。正文写发往组，图中该箭头落在 MC service server：前者是所针对的组，后者是图上的交互端点，不能据正文改成 IWF 直接向各 MC service client 发请求。原请求还可附带取消组进行中紧急状态的指示（NOTE 2），但**主请求仍是告警取消**，不能按另一类组状态取消消息或时序读，也不能只凭指示已发送就认定组状态已经清除。[§10.6.5.1 图、步骤 1、NOTE 2，印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=144)。

## 两条消息腿各配各的请求

| 步骤 | 看什么 |
| --- | --- |
| **1 → 2：IWF ↔ server** | IWF 发 1；MC service server 回 2 确认原告警取消。不回给 LMR 终端，也不是第 5 步的成员 ACK。 |
| **3 → 4：server 到成员** | server 向组中已归属成员的 MC service client 发独立的告警取消请求 3；步骤 4 是告知这些 MC service 用户 LMR 用户的告警取消。图画了两个客户端，不是固定两笔或全员已收。 |
| **5：接收客户端 → server** | 收到对应 3 的 MC service client 回 5，确认本笔成员请求。组播呼叫场景不发步骤 5 的确认，不是取消步骤 2 或绕过步骤 3、4。 |
| **NOTE 3：2 与 3 不固定先后** | server 可以先回 IWF 也可以先发成员请求。不能因为 2 已出现就断言成员已经收件；也不能把收到成员确认当作发 2 的必等条件。不是说两个动作可脱离原请求或未接收的客户端也要回 5。 |

[§10.6.5.1 步骤 1–5 和 NOTE 3，印刷页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=144)。

IWF 告警取消**请求表 10.6.1.9-1**列必带的 **取消者 MCPTT ID** 和 **关联组 ID**。第二个 `MCPTT ID` 这一行标 `O`，但表注要求取消他人告警时必须带该人 ID；不带时所指的是取消者自己的告警。它是总表的目标规则，不给本页所述情形增加第三方授权。总表另列可选的组级取消项，名称和说明用“组的进行中紧急告警”，具体流程 NOTE 2 用“组的进行中紧急状态”。保留两处用词，不据此添加第二个组字段、定义实际清除动作，或换用组状态取消表里的 `Alert indicator`。[§10.6.1.9 表 10.6.1.9-1，印刷页 119–120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=121)；[§10.6.5.1 NOTE 2，印刷页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=144)。

**应答表 10.6.1.10-1**只列必带的取消者 ID 和关联组 ID，不列目标用户 ID、组级取消项或 `Result`。两张总表定义双向信息流，本页按图中的 **1 IWF → server、2 server → IWF** 配对。多个候选请求共用取消者/组 ID 时，仍须按原事件、事务、方向和端点配对，不能靠两个 ID 判定具体是哪笔确认。[§10.6.1.9–.10，印刷页 119–120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=120)。

检查现网时，server 发出的匹配 2 可佐证 1 到了 server，不能证明 IWF 实收 2。接收端发出的匹配 5 可佐证该端收到了 3，不能证明 server 实收 5，更不代其他成员的收件或用户界面通知。组播下缺少 5 不等于成员没收到。确认单跳信令不需要媒体证据；LMR 侧实收、告警是否清除、组状态是否清除、成员实际显示和媒体状态各查各的证据。[步骤 1–5，印刷页 143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=144)。

## 发起侧或原请求类型变了，就换入口

- **LMR 用户以取消组紧急状态为主**，即使同时问本人告警，也按组定义分别查 [§10.6.2.3.1 MCPTT 定义组](emergency-group-state-cancel-lmr-origin-mcptt-defined.md) 或 [§10.6.2.3.3 LMR 定义组](emergency-group-state-cancel-lmr-origin-lmr-defined.md)。不要把组状态取消的 IWF 应答时序或字段带进本页，也不从二者的总则推本页 IWF 或成员请求的固定笔数。[§10.6.2.3.1、.3，印刷页 128–129、130–131](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=129)。
- **MC 用户发起告警取消**，改查 §10.6.5.2。那一支的发起端 3、IWF 4/5 和 NOTE 3 的 3/4 可任一先，不是本页的 2/3；它另列发起端仍处紧急状态和代理/逐人发往 IWF 的条件，不能套入 LMR 发起流程。[§10.6.5.2，印刷页 143–144](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=145)。
- [原生 MCPTT 的告警取消](../emergency/standalone-alert-cancellation.md)另有 Stage 3 入口。本节只整理互通信息流，不定义 SIP 编码、LMR 内部处理、拒绝码或重试。[§10.6.5.1 开头与 NOTE 1，印刷页 142](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)。
