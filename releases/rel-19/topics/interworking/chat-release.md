# 互通 chat 释放：会话结束不取消归属

TS23.283 V19.5.0，Release 19，Stage 2。

进行中的互通 chat 组呼包含 MCPTT 客户端与 IWF。

## 组定义在 LMR 系统；LMR 发起释放

IWF 按呼叫中每个 MCPTT 用户发送释放请求；server 转发，MCPTT 用户获通知。客户端应答可选；客户端与 IWF 释放本通话的话权和媒体面资源。成功释放本身不改变客户端归属状态。 [§10.3.5.4](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 MCPTT 系统；MCPTT server 决定释放

IWF 代理全组加入时 server 向 IWF 发一条；逐用户加入时按每名已加入 LMR 用户发一条。IWF 须响应所收释放请求，MCPTT 客户端确认可选；成功释放不改变客户端归属状态。 [§10.3.5.5](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 客户端没有回包，能认定整通 chat 没结束吗？

不能只凭缺客户端应答判断。§10.3.5.4/.5 描述**释放同一通正在进行的互通 chat，针对该通呼叫的所有参与者**。两支都把原生 MCPTT 客户端的释放应答列为可选，但 IWF 腿上的消息用途不同。

| 实际适用场景 | 请求发给谁 | 应答各走哪一条腿 |
| --- | --- | --- |
| **LMR 定义组，由 LMR 释放（.4）**。这通呼叫已有 MCPTT 客户端与 IWF 参与。 | **1** IWF→server，按**呼叫中的每名 MCPTT 用户**各发一条 IWF 释放请求。**2** server 把请求转给该组的 MCPTT 用户，正文引用 TS 23.379；不从这句扩大到静态名单全部人员。**3** 用户获通知，图在客户端画提示。 | **4** 收到步骤 2 请求的客户端**可**向 server 回本次原生应答；**5** server 将该应答转为 IWF 应答发回 IWF。5 是转发，不是客户端没回时由 server 自动代答，也不是必须等齐全员的规定。 |
| **MCPTT 定义组，由 MCPTT server 决定释放（.5）**。图示同一在途呼叫有客户端 1、2 与 IWF。 | **2** server→IWF 请求释放。如果 IWF 已代表该组**全部 LMR 用户加入**，发一条；如果 server 实际收到逐用户 join，对每名已加入的 LMR 用户各发一条。**3** server 另向进行中呼叫的每名 MCPTT 参与者发原生请求，**4** 通知用户。 | **5** IWF→server 确认实际收到的步骤 2 请求；**6** 收到各自释放请求的 MCPTT 客户端**可**向 server 回原生应答。两类回包不互相替代。图画出两客户端作例，不规定客户端数量、全员等待或应答到达顺序。 |

**别把归属、参加呼叫和释放原因混在一起。** .5 写服务器在满足至少一个释放条件时作决定，例子有 hang time 到期、最后或倒数第二个参与者离开、发起者离开、已归属的 MCPTT 组员数低于允许下限。不能把已归属人数换成正在通话人数；正好等于下限不是“低于”。这些不是固定时长、人数或完整条件表，看见某个例示事件也不证明服务器已决定释放。步骤 2 的数量另按实际代理加入或逐人 join；只见一条请求，可能是代理，也可能只对应一名已加入用户或记录不全。归属状态或成员名单不证明采用了哪一种 join，本段也没写两类记录并见时如何合并。

**何时可说已结束？** 已辨明的单条请求或应答可以单独读。要把两条关联到一次操作，查本次同一通 chat、组、目标用户和实际端点。各腿的发出、实收、用户提示和资源状态分别查。正文 .4 **6** 写客户端与 IWF 释放该通话的话权和媒体面资源；.5 **7** 写客户端 1、2 与 IWF 释放。图框跨过 server 泳道，不因此补一个 server 清理动作或证明任一端已清理。成功释放本身不改变客户端的组归属；要查是否仍归属，看实际状态和另外发生的归属变更。
