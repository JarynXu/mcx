# 互通组呼释放：主控侧与请求粒度

适用版本：TS23.283 V19.5.0，Release 19，Stage 2。

组配置双方已知、IWF 身份映射已配置，组呼正在进行且包含 IWF 与 MCPTT 客户端。

## 组主控服务释放呼叫

该流程释放所有参与者的组呼，不是单用户退出。MCPTT 侧释放条件引用 TS23.379；LMR 侧释放条件不在本规范范围。 [§10.3.3.8.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 MCPTT 系统；MCPTT server 发起释放

MCPTT server 向 IWF 发送释放请求：IWF 代表 LMR 用户统一归属时只发一个；收到逐用户归属时，按每名已归属 LMR 用户各发一个。向 IWF 和 MCPTT 用户发送的先后不限。 [§10.3.3.8.2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 LMR 系统；LMR 发起释放

IWF 按呼叫中每个 MCPTT 用户发释放请求，server 转发；客户端响应后 server 向 IWF 确认，最终释放相关话权和媒体资源。 [§10.3.3.8.3](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 一条释放应答，能证明哪些端已释放？

先分**组定义在哪一侧**和**哪侧实际发起这次释放**。§10.3.3.8 是组主控释放一通已经在进行的互通组呼，面向当时的所有参与者，不是把所有静态组成员移出组。判现场适用性时，核双方已知组信息、IWF 已配置组与用户标识映射，以及同一通正在进行、包含 IWF 和 MCPTT 客户端的呼叫。查规范或读单条已辨明的消息，不必先收齐报文或资源状态。[§10.3.3.8.1–.3，印刷页 51–53（PDF 第 52–54 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=52)。

### MCPTT 定义组，MCPTT server 发起

server 先确定这通呼叫的参与者（步骤 2），其中至少一名 LMR 用户由 IWF 代表。接着有两个发送动作：发给 **IWF** 的 IWF 释放请求是 **3**，按上面的代表／逐人归属选粒度。两种方式都可能只发一条：逐人归属且只有一名已归属 LMR 用户时也是一条。发给 **MCPTT 用户** 的原生释放请求是 **4**。NOTE 4 只说 **3 和 4 可以任一顺序发生**。不能用它推各端的实际收件顺序，也不能把 5 排在它回应的 3 之前。

**5 是 IWF → server**，用 IWF 释放应答确认 IWF 收到的步骤 3 请求。图把 4 画成原生释放过程框，不画逐个 MCPTT 客户端的原生应答；这不等于原生过程不需要应答。只看到 5 发出，不能说 server 实收，更不能替步骤 4 的终端取证。NOTE 3 不规定怎样把释放请求转给 LMR 系统。[图 10.3.3.8.2-1、步骤 2–6、NOTE 3–4，印刷页 51–52（PDF 第 52–53 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=52)。

### LMR 定义组，LMR 系统发起

**1：IWF → server**，每名呼叫中的 MCPTT 用户各一条 IWF 释放请求；**2：server → 相应 MCPTT 用户**，是原生腿。**3 是客户端 → server 的原生释放应答；4 是 server → IWF 的 IWF 释放应答**，后者确认的是 server 在 1 收到的 IWF 请求。看到一条应答不等于另一条已发或已收。图中 4a 画在另一客户端的 3b 之前；不把正文的步骤编号读成“先收齐全体客户端应答”，也不把图中 a／b 两支定为人数或运行时顺序。步骤 2 的 TS 23.379 [7] 是原生过程指针，LMR 侧为何释放不在本节范围。[图 10.3.3.8.3-1、步骤 1–5，印刷页 52–53（PDF 第 53–54 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=54)。

### 确认请求，和资源已经释放，怎么取证？

两支分别在 **.2 步骤 6、.3 步骤 5** 写明客户端 1、客户端 2 和 IWF 已成功释放这通呼叫对应的话权控制和媒体面资源。两图的框横跨 server，但正文在这一步只点名这三个端点，不以框的宽度增加端点。实际关联请求与应答，要查同次呼叫与释放尝试、当事角色、接口两端和对应消息；同组 ID 不能替代配对。核资源终态再查所问端点的话权控制、媒体面资源是否释放。不以应答或无媒体代替资源状态，也不由呼叫结束推出组归属已取消、组已删除或 IWF 后方终端已清理。[.2 步骤 6，印刷页 52（PDF 第 53 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=53)；[.3 步骤 5，印刷页 53（PDF 第 54 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=54)。

只问已识别消息的用户 ID、组 ID 或释放原因，查 [IWF 组呼操作字段](group-call-operation-elements.md)；实际是互通组广播，查[广播释放](group-broadcast-release.md)。这里只核 Stage 2 过程，不按这些步骤补 SIP 状态码、定时器、失败处理或 LMR 内部实现。
