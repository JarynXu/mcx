# 互通预安排组呼：哪一端发起，哪条应答才对应？

**先看组由 MCPTT 还是 LMR 定义，再看原主叫在哪一侧。** 两个问题分别决定谁管这通呼叫、哪些请求回给原发起端。同一次呼叫可能在 IWF 与 MCPTT server 之间有两笔方向相反的请求，不能用其中一笔成员应答代替原请求的应答。

适用：**TS 23.283 V19.5.0，Rel‑19 Stage 2，预安排互通组呼建呼**。§10.3.3.1 还明确将这些过程用于非广播的预配置组重组呼叫、预配置用户重组呼叫和组重组呼叫。这里查它们的建呼，不查重组本身。四支的共同前提是：server 与 IWF 已知组信息，图示 MCPTT 客户端已注册且用户已认证并获准使用服务，组用户已归属，IWF 已配置两侧组和用户标识映射。两个 LMR 起呼分支还明列 LMR 用户起呼。**成员名单、先前配置或已获服务授权，不单独证明归属、某次建呼或特定组起呼权限。** §10.3.3.2 步骤 3 另查主叫能否在所选组起呼，不把该显式步骤放到其他分支。四支均引用 TS 23.379 的原生过程，本页不展开它。[§10.3.3.1，印刷页 40（PDF 第 41 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=41)。

## 同一组的请求和应答字段分别指谁？

IWF‑1 的 [Group call request .2](group-call-request.md) 与 Group call response .3 都可走 IWF↔MCPTT server。**请求的 M MCPTT ID 是主叫；应答的 M MCPTT ID 是目标 MCPTT 组成员。** 两表均有 M 组 ID，分别是起呼所在互通组、请求呼叫的组。请求 M 的 SDP offer 在表中写“MCPTT server 的媒体参数”，不能因这一腿由 IWF 发出就把字面换成 IWF 参数；应答 M 的 SDP answer 是选定媒体参数。普通应答表不列独立 Result。组广播建呼应答的 ID 写主叫，join 应答则写原请求者，各看自己的表。[§10.3.2.1–.3，表 10.3.2.2‑1/.3‑1，印刷页 35–36（PDF 第 36–37 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=36)。

请求里的功能别名和位置属于主叫。预留主叫 ID 的条件看原请求主题，不拿来填应答的目标成员。.3 步骤 1 和 .5 步骤 1 另写：LMR 主叫请求话权时，IWF 请求带隐式话权指示；带该指示时**可**附位置。这是两个步骤的条件，不把位置写成必带，也不把请求话权当作已获话权。

例如 .4 的组 G，同一次建呼里 server 先向 IWF 发 3，随后 IWF 向 server 发面向某已归属用户的 4；哪一条回应哪一条，不能靠同一组 G 或相同的 SDP 猜。只查某条已辨认的消息不必等对向；要关联实况才核类型、原／成员腿、同次呼叫与相应端点。**已发、对端实收、原主叫实收和实际媒体是不同证据。** 本节的成功建呼后媒体描述不表示每个用户立即获话权或已播放语音。四支写了同样的编解码条件：若指定 E2EE，两侧用同一 codec；未指定时两侧可用不同 codec，此时需 IWF 转码。不能用这条条件代实际加密、编解码或媒体证据。
