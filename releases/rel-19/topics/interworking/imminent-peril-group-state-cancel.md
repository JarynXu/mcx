# 互通组的迫近危险状态怎么取消？谁的应答算数？

**通话结束不取消组的迫近危险状态。** 在 TS 23.283 V19.5.0（Rel-19 Stage 2）§10.6.3.4 的流程中，MCPTT server 核取消权限后清组状态，再调整底层承载优先级。给发起端的确认不必等 IWF 或 MCPTT 成员回包。它也不证明通话、告警或话权随之结束。

## 先确认取消的是哪一种状态

互通组已经由组管理服务器定义。图中两名 MCPTT 客户端及经 IWF 代表的 LMR 用户已经归属。IWF 已接入并获准，掌握互通组信息，且配置了组和用户身份映射。**该组当前在 MCPTT 系统中处于迫近危险状态，并支持优先承载。** 图中的 client 1 曾发起迫近危险组呼，现由其用户请求取消；步骤 3 仍由 server 核实该用户的取消授权。曾发起不等于有取消许可；这条图示前提也不能倒推所有其他获授权者都不允许取消。

这里的“进行中”说的是**组状态**。NOTE 1 说呼叫结束后该状态不会自动取消；是否还有通话或 RTP，并非这条流程另列的前提。若通话已结束但组状态仍在，仍须逐项核其它前提，不由一次挂断得出“已取消”或“现在必能取消”。NOTE 2 的单 server 是用户本属和组托管服务器的示意，不规定同机；NOTE 4 说明 IWF 做身份和协议转换，未给 LMR 内部执行细节。查规范不需要抓包。[§10.6.3.4 前提与 NOTE 1–4，印刷页 137](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=138)。

## 三笔信令分别看

| 对应步骤 | 看谁发给谁 |
| --- | --- |
| **2 → 11：发起端请求和确认** | client 1 向 MCPTT server 发送取消请求。server 在 3 验权；成功流程在 4 清组状态，在 5 调整底层承载优先级，这个迫近危险状态不再要求优先处理。11 是 server 给 client 1 的确认，回应 2。规范没规定这里的拒绝码或回滚，也没说所有其他原因的承载优先级都被清除。 |
| **6 → 7：互通请求和 IWF 应答** | server 向 IWF 发取消请求。IWF 代表全组 LMR 用户作一条归属时只发一条；服务器实际收到逐人归属时，为每名已归属 LMR 用户向 IWF 各发一条。7 是 IWF 回 server。**IWF 即使不支持迫近危险组呼也会应答**（NOTE 5）；不能把应答当作支持组呼或 LMR 终端都已取消。 |
| **8 → 10：MCPTT 成员通知及其应答** | server 向 MCPTT 组成员发请求（8），步骤 9 是成员获通知；图示 client 2 用 10 回 server 以确认 8。组播时不发这条成员 ACK。没有 10 不等于没通知，也不能据此判断 7 或 11 是否发生。 |

图按 6、7、8、10、11 画。**按 NOTE 6，6 和 8 都在步骤 5 之后，先后不限。按 NOTE 7，11 在 5 之后即可发生。** 不能把图里的 7 或 10 变成发起端确认的前提，也不补全员一致、超时或重试规则。[图 10.6.3.4-1、步骤 1–10 和 NOTE 5–6，印刷页 138](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=139)；[步骤 11、NOTE 7，印刷页 139](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=140)。

## 收到应答能证明什么

表 10.6.1.5-1 和表 10.6.1.6-1 都列必带的 **MCPTT ID（取消者）**、**MCPTT 组 ID**。它们不列 `Result`、被通知的 LMR 用户 ID 或告警取消指示。多条逐人请求可能同组同取消者；不能靠这两个字段确定某个 7 对应哪条 6。要判断实际信令到达，看是否为同次取消的相应事务、端点、方向和实收事件。接收端实际发出的匹配应答可佐证原请求到了这一端，不能证明另一端收到该应答。**确认某跳信令不用媒体证据**；本次媒体是否继续、停止或已顺利转换需另外取证。[表 10.6.1.5-1、10.6.1.6-1，印刷页 118–119](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=119)。

这里只谈 MCPTT server 的组状态和承载动作。IWF 自身的优先级处理不在范围内，7 不保证 LMR 侧已应用；11 也不证明全组收到或听到任何提示。§10.6.3.2 的**建呼**可因 IWF 不支持而拒绝，不能搬到这里的应答规则。§10.6.1.11 的**紧急组状态取消**和 §10.6.5 的**紧急告警取消**各有信息流，不把其告警字段或动作拼到本支。[§10.6.3.2 NOTE 5，印刷页 135](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=136)；[表 10.6.1.11-1，印刷页 120](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=121)；[§10.6.5，印刷页 142–143](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=143)。

NOTE 3 复用 TS 23.379 的信息流，本页不映射 SIP 消息、状态码或 IE 编码。要查原生 MCPTT 客户端/PF/CF 在已有按需预安排组呼上的协议处理，转读 [TS 24.379 V19.4.0 的迫近危险请求与反馈](../emergency/group-imminent-request-feedback.md)。若问的是[整体组呼释放](group-call-release.md)、[晚加入](late-entry.md)或[话权覆盖](floor-override.md)，走各自入口。
