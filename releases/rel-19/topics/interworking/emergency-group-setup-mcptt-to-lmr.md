# MCPTT 发起、组定义在 LMR：IWF 两向请求怎么对？

**在 LMR 定义的互通组上，IWF 既响应原建呼请求，也向 MCPTT server 为已归属成员另发建呼请求。** 两笔都叫紧急组呼，但方向和对应应答相反。组的主控是 **LMR 系统**，不因主叫在 MCPTT 或 MCPTT server 接入终端而改变。

这里限 **TS 23.283 V19.5.0（Rel‑19 Stage 2）§10.6.2.2.4**。先确认主叫是 MCPTT 用户、互通组定义在 LMR。此场景还要求有已归属的 MCPTT 客户端（图中的 client 2），IWF 已接入并获准与 MCPTT 互通，且已配置组和用户身份映射。主叫所属、容易看到哪一跳、用户的归属与组定义所在系统不能互相代替。只查规范不用抓包；读一笔现场建呼才核实际组、成员、请求及对应结果。[§7.4.1、§10.6.2.2.4 与图 10.6.2.2.4-1，印刷页 15、126–128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=127)。

## 对上两组请求与应答

| 链路 | 对哪笔请求 |
| --- | --- |
| **原互通建呼：步骤 3 → 8** | MCPTT client 1 先向 MCPTT server 发紧急组呼请求（步骤 2）。server 配置底层承载优先级后向 IWF 发 **IWF emergency group call request**（3）。IWF 回给 server 的 **IWF emergency group call response**（8）对应这笔 3，图示成功路径用它通告建呼结果；不是逐成员邀请的应答。server 在步骤 9 另向发起端返回 MCPTT 应答。 |
| **逐已归属 MCPTT 成员：步骤 4 → 7** | IWF 向 MCPTT server 为每名**已归属的 MCPTT 组成员**各发一个请求（4），图中举 client 2。server 配置底层承载优先级并向相应客户端发请求（5），客户端给 server 回应（6）；server 给 IWF 的结果（7）对应步骤 4。不是只发给一个 IWF 代表，不按配置名单、LMR 用户或尚未归属的成员逐人发。 |

**原请求应答不必等逐成员链全回完。** NOTE 5 把步骤 8 放在步骤 3 之后，最迟在步骤 7 之后。图中顺次画到 8，不等于每次都要等 7 才发；注没有给等待时限、缺答重试或全员成功的收敛条件。两笔都见到同一个组 ID，不能据此关联应答。表 10.6.1.2-1 的 `Result` 必带，也可表示拒绝；不能把刚看到任一 Response 当成功。表中的 `MCPTT ID` 是主叫标识，不拿它当步骤 4 的成员目的地址。

[§10.6.2.2.4 步骤 1–9 和 NOTE 2–5，印刷页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=128)；[表 10.6.1.1-1、10.6.1.2-1，印刷页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=118)。

紧急指示与告警、话权分开。步骤 2 带紧急指示，可以附紧急告警指示或隐式话权请求。IWF 请求表把紧急指示列为必带；其 NOTE 仅在发起客户端确实请求话权时才带隐式请求。请求中的指示不证明告警已发或话权已授。步骤 10 才描述经 IWF 的 LMR 用户与已归属 MCPTT 客户端建立媒体；要断言现场媒体可用，不能用步骤 7、8 或 9 替代媒体证据。不从承载优先级配置推话权或 RTP 已通。[§10.6.2.2.4 步骤 2、3、5、10 与表 10.6.1.1-1，印刷页 117、127–128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=128)。

## 换了组定义所在系统，就换分支

同样是 MCPTT 用户发起，若组**定义在 MCPTT**，应读 §10.6.2.2.2。该支有额外的发起端配置前提：设备配有指定的紧急组，或配置为在所选组上作紧急处理。那里的步骤 7 是 **MCPTT server → IWF**：IWF 代表 LMR 用户统一归属时发一个；服务器收到 LMR 用户逐人归属时，按每名已归属的 **LMR 用户**发。这里的控制系统是定义组的 MCPTT 系统。不要把这个方向、人数、主控或额外配置前提搬到 LMR 定义支，也不由 LMR 支没有重述这些条件推出免授权。主叫若是 **LMR 用户**，另选同版起呼分支，不把本文步骤 3 当作其起点。[§10.6.2.2.2、图 10.6.2.2.2-1 及相邻分支，印刷页 121、123–126](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=124)。

**原文端点差异：**§10.6.2.1 在 LMR 定义组的概述里把逐成员请求的目的写作 **IWF**。本场景图和步骤 4–7 明写 **IWF → MCPTT server** 再向客户端、回程到 IWF。区分概述的字面和这条已核分支，不据误写补一条 IWF 发给自己的链路。[§10.6.2.1，印刷页 121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)；[图及步骤 4–7，印刷页 127](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=128)。

只核这条 Stage 2 建呼，不给出 LMR 内部叫人、IWF 优先级实现、SIP 编码或完整失败状态机。普通[组呼请求字段](group-call-request.md)、进行中[话权覆盖](floor-override.md)与[组呼释放](group-call-release.md)是不同入口；本篇不讲紧急状态撤销。
