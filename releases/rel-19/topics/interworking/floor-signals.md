# 互通话权消息：状态、队列与单播控制

ETSI正式发布的TS23.283 V19.5.0，Release19，Stage2。此处解释信息流，不是协议状态机。

## 解释授予、空闲或占用通知

granted表示相应请求获准可传媒体，并含允许发送时长；idle表示无人获授话权；taken表示另一用户获授。收到taken不等于自己获准发送。 [§10.5.2.3, 10.5.2.8, 10.5.2.10](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 普通话权请求、授予、拒绝：字段能说明什么？

先认信息流，再读身份和字段。**请求优先级、准许发送的时长、拒绝原因**是三件事。TS 23.283 V19.5.0 的三张表均列 IWF↔MCPTT floor control server 两个方向；方向不决定消息类型或最终裁决者。查规则或一条已识别的消息，不必先找到完整往返。

| 信息流 | MCPTT ID、别名指谁？ | 各自带什么？ |
| --- | --- | --- |
| **.2 IWF floor request** | MCPTT ID（M）是**请求者**，Functional alias（O）是其别名。 | Floor priority（M）是本次**请求的优先级**，不是已生效的优先级或仲裁结果。Location（O）是请求者的位置，不是另一名发言者或接收者的位置。这张表不列要求确认的指示。 |
| **.3 IWF floor granted** | MCPTT ID（M）是**获授话权者**，Functional alias（O）是其别名。 | Duration（M）是该方**获准发送的时长**。消息表示话权请求已获准、可传媒体，不等于已发、已收或一直占到时长结束。这张表不规定单位、时钟起点、到期处理或整通呼叫时限。 |
| **.4 IWF floor rejected** | MCPTT ID（M）是**被拒方**，Functional alias（O）是其别名。 | Rejection cause（O）说明拒绝原因。不带原因，已识别的消息仍报告拒绝；不能补默认原因。普通拒绝不是排队取消、队列位置报告、撤销已有话权或结束呼叫。 |

三表的 **Source identifier（O）** 都用来识别通信，例如媒体复用中的流。表明写只有媒体复用时才出现：已知消息符合该表且字段存在，说明有复用；有复用并不使它必带，缺项仍可能复用。实况只见某个值，不证明整笔合规、实际复用或两条消息匹配。**MCPTT ID 与对应别名**可代表 LMR 用户、IWF 或 MCPTT 用户，按互通方式和实际源、目的解释。不能从物理发送端直接得出请求者、获授者或被拒者。

**授予和拒绝可带 Acknowledgement required（O）。** 已知发送的消息，可以读它是否写明要求确认；判断接收端是否遇到这个条件，看接收端**实际收到这一条**，且该指示明确要求确认，再读 §10.5.2.12。仅出现字段、值未见或明确不要求，都不能当作肯定要求。通用确认的 MCPTT ID 指**确认发送者**，不把它当成获授者或被拒者的同义字段。确认另行取证，也不是收到语音、接受裁决或已清除排队项。

例如，同一通信里，A 发了带优先级的 .2，另一条 .3 的 ID 是 B。可以单读 B 的获授及允许时长，不能把 B 的授予写给 A；即使身份碰巧相同，也要有对应请求、通信和端点证据才可配对。发出 Grant、对端实收、实际发送媒体、对端收音分别看。操作要问实际由哪侧裁决，再查[话权主控](floor-control-owner.md)；不从一条通知逆推哪个节点最终作了决定。

[角色和请求／授予两表，§10.5.2.1–.3，印刷页 103（PDF 第 104 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=104)；[拒绝表，§10.5.2.4，印刷页 104（PDF 第 105 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=105)；[通用确认 §10.5.2.12，印刷页 106（PDF 第 107 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=107)。

## 空闲、交还、他人获授和撤销：下一步能做什么？

**空闲不等于你有话权；交还或撤销也不等于整通呼叫结束。** 这里查 TS 23.283 V19.5.0 §§10.5.2.8–.11 的四条信息流，均列 IWF↔MCPTT floor control server 两向。已知是哪条，就可以独立读它，不必先看到它前后的控制消息。

| 信息流 | 表里的身份和状态 | 不能代替什么 |
| --- | --- | --- |
| **.8 IWF floor idle** | 通告这次通信的话权**没有授予任何一方**。表仅列可选的 Source identifier 和 Acknowledgement required，**没有 MCPTT ID 或功能别名**。 | 不是某用户交还的证明；也不是接收者已获授、队列已空或你的读数时刻仍空闲。 |
| **.9 IWF floor release** | 通告媒体传输完成、话权已释放。MCPTT ID（M）与别名（O）指**交还话权的一方**；还有 Source identifier（O）。表不列 Acknowledgement required。 | 不从这个 ID 判网元、主动原因或下一位获授者；不是整通释放，也不能以这份通告证明对端已听完或所有媒体都已停。 |
| **.10 IWF floor taken** | 通告话权给了**另一名 MCPTT 用户**；MCPTT ID（M）、别名（O）及 Location（O）都指**获授方**。Permission to request the floor（O）则问**接收方可不可以申请**话权。 | 允许提出申请，不等于自己已获授或可发送媒体；不带该项时，本表没有给默认允许或禁止。获授方的位置不是接收者位置，也不是 .2 的请求者位置。 |
| **.11 IWF floor revoked** | 通告从**当前持有者**撤销话权。MCPTT ID（M）指被撤销方，别名（O）也属该方。 | 不是新的申请被拒，也不指下一位获授者；不从通知判断撤销原因、旧媒体已经停止或新话者已经开始。 |

**识别通信和是否要求确认。** 四表的 Source identifier 都是 O，只在媒体复用时才出现，用来识别通信；它不是用户或事务 ID。只有在明确符合表的前提下，带该项才可推出媒体复用；已复用仍不必有它。真实日志里的一个字段值不能代整条核验。带 MCPTT ID 的各表按自身角色读，再结合互通方式及本条实际源、目的判它是 LMR 用户、IWF 还是 MCPTT 用户。

只有 .8/.10/.11 在这四条中列 Acknowledgement required（O）。要判断**接收端**是否遇到确认条件，核该端实际收到**同一条**控制消息且指示明确要求，再读[通用确认](#排队取消的三类消息和确认)中的 §10.5.2.12。Release 表没列该指标，不给它添自动确认，也不妨碍独立核其他控制消息。独立 ACK 的身份是确认发送者；不能从 ACK 的 ID 反推谁交还、谁被撤销、谁已获授或谁的媒体已停。

例如依次只见 A 的 **.9**、另一个通信的 **.8**、B 的 **.10**。三条分别报告 A 交还、那条通信无人获授、B 获授；不拼成 A 的这一通已结束，不能因接收 .10 的端点收到提示就说它也取得话权。要把几条控制消息关联到本次操作，核同一通信、当事角色、对应端点及可配对的控制事件，不要求先找到媒体。要判断某端实际发出或收到媒体，再查该端对应的媒体证据。单查消息类型不用先拼出整条流程。

[§10.5.2.1 身份角色，印刷页 103（PDF 第 104 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=104)；[§10.5.2.8–.10 的三张表，印刷页 105（PDF 第 106 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=106)；[§10.5.2.11 的撤销表和 §10.5.2.12，印刷页 106（PDF 第 107 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=107)。

## 区分取消请求、释放与撤销

request cancel针对队列中的话权请求；release表示媒体传输完成并释放话权；revoked撤销当前持有者的话权。它们都不能直接当作全呼叫释放。 [§10.5.2.5, 10.5.2.9, 10.5.2.11](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

### 排队取消的三类消息和确认

**取消谁的排队请求，看取消请求里的目标列表；不要看应答、通知或确认里的 `MCPTT ID` 猜目标。** TS 23.283 V19.5.0 的这三种消息和通用话权确认均可走 **IWF → MCPTT floor control server** 或反向。谁发消息和字段里的身份是什么角色，分开看。身份在互通中可代表 LMR 用户、IWF 或 MCPTT 用户；取决于互通方式及消息源、目的。查规范无需抓包。[§§10.5.1、10.5.2.1，印刷页 103](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=104)。

| 信息流 | 用来做什么 | 表里要看哪些字段 |
| --- | --- | --- |
| **IWF floor request cancel**（.5） | 请求取消队列中的话权请求。 | `MCPTT ID`（M）是取消请求者；`List of MCPTT IDs`（M）另列被要求取消的目标。别名（O）描述请求者。表没有要求确认的字段。 |
| **IWF floor request cancel response**（.6） | 回应原取消请求。 | `MCPTT ID`（M）是**原取消请求发起者**，不是当前应答发送人；别名（O）也属请求者。`Acknowledgement required`（O）说明是否要求话权参与者确认。没有目标列表、逐目标结果或取消成功/失败字段。 |
| **IWF floor request cancel notify**（.7） | 通知话权请求由管理员或话权控制服务器取消。 | `MCPTT ID`（M）和别名（O）按表字面是**管理员**的；不因消息由控制服务器发送，就把它解释为服务器 ID 或被取消者。可带 `Acknowledgement required`（O）；没有被取消者列表或原取消请求的应答结果。 |

三个表都把 `Source identifier` 列为可选，用于识别通信，只有媒体复用时才出现；复用也不会把 O 变成必选。这不是取消事务 ID。[§§10.5.2.5–.7；表 10.5.2.5-1、10.5.2.6-1，印刷页 104](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=105)；[表 10.5.2.7-1，印刷页 105](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=106)。

**需要通用确认，要看收到的那条控制消息是否明确要求。** .6/.7 的可选确认指示只有在表明“要求”时才是依据，不能仅凭字段出现、消息名称或发送方已发就判要确认。.5 的表没有该字段，但取消业务应答 .6 仍是另一条信息流。§10.5.2.12 写双向的 IWF floor acknowledgement；NOTE 说话权控制服务器可在每条带有要求确认指示的信息流后发送。通用确认不限于取消场景，也不因 NOTE 就改为只能由服务器发。确认表只有**确认发送者**的 `MCPTT ID`（M）和其别名（O），没有 `Source identifier`、被取消者列表或结果。[§10.5.2.12、NOTE 和表 10.5.2.12-1，印刷页 106](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=107)。

例如，A 请求从队列取消 B、C 的请求，匹配的 .6 仍识别 A。只见 .6 或通用确认，不能判 B、C 都已移出队列；.7 报告管理员或服务器取消，也不靠管理员 ID 确定移除的是谁。查现场要对上这次通信、操作、对象、方向和实际收件；发送、收到应答/通知、队列条目实际移除分别取证。普通话权申请的 `rejected`（.4）可带拒绝原因，但不能拿来给取消应答补结果。查询队列位置、交还或撤销当前话权、整通呼叫释放也不是这三种消息。这里不规定失败状态、无确认处理、排队算法或 Stage 3 编码。[§10.5.2.4，印刷页 104](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=105)。

## MCPTT服务器和客户端支持话权请求排队

须支持查询队列位置的信息流；queue position info说明请求已排队及其位置，不是话权授予。 [§10.5.2.13–14](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

### 查谁的位置？哪条消息要求确认？

§10.5.2.13 和 .14 都列 **IWF↔MCPTT floor control server** 两向。**支持话权请求排队的 MCPTT server 和 MCPTT client** 须支持 .13 查询流。不是要求所有设备都支持队列或在每通呼叫启用队列。

| 消息 | 该表表达什么 |
| --- | --- |
| **.13 IWF queue position request** | 查询话权请求在队列中的位置。**MCPTT ID（M）** 指所查询的那一方，**Functional alias（O）** 也属该方。表没列位置值或要求确认的字段。 |
| **.14 IWF queue position info** | 向申请话权的 UE 报告该请求已排队及所在位置。**MCPTT ID（M）** 指所报告位置的那一方，**Functional alias（O）** 也属该方。**Queue position info（M）** 是已排队请求的位置；**Acknowledgement required（O）** 只说明是否要求话权参与者确认。 |

两个 ID 都按表里的对象角色读。谁发送、谁在物理链路接收，不能代替所查询或报告的一方。ID 和别名可代表 LMR 用户、IWF 或 MCPTT 用户，要结合互通方式及实际源、目的。.14 提到申请话权的 UE 是位置通告的对象，不把它当成导语所列 IWF 和服务器之间的网络端点。

两表 **Source identifier（O）** 都识别通信，例如区分媒体复用中的流。只有媒体复用才可带：假定消息符合该表，带此项就可知复用；有复用不等于此项必带，缺项不排除复用。真实日志只见它的值，不证明该笔合规或实际复用。它不代被查询者身份，也不是配对请求和通告的事务 ID。

**该端实际收到这条 .14，且其指示明确要求确认，才按 .12 的确认条件读。** 只见发送端发出，可以读取它有没有写“要求确认”，不能说收方已触发确认。字段只出现、值不清或明确不要求，也不能当成明确要求。.13 的表没有这项，也不能借其他消息的指示补给本笔。通用确认不是报告位置值，也不是实际授予话权。

查任一已识别消息的字段或意义，不用先拿到一问一答。举例：查询的 ID 是 A，随后看到同一通信的 .14 报告 B 在位置 2，不能把 B 的位置写到 A。即使同为 A，也要核对是不是本次查询的报告，不能只靠身份、Source identifier 或先后顺序配对。这两条没规定每次查询必有同步回答，也没给位置编号、等待时间或排队规则。看见 .14，能说它报告了排队及位置；要说某端已收到，看该端记录。报告不证明读者查询时状态仍相同、实际何时入队或退队，更不是授予话权。

[§10.5.2.13/.14 及两表，印刷页 106–107（PDF 第 107–108 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=107)；[表 10.5.2.14‑1，印刷页 107（PDF 第 108 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=108)；[§10.5.2.1 身份角色，印刷页 103（PDF 第 104 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=104)；[§10.5.2.12 通用确认，印刷页 106（PDF 第 107 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=107)。

## 停止或恢复指定通信对指定客户端的单播媒体

stop表示该单播媒体不需再发给指定客户端；resume由话权控制服务器请求恢复向该客户端发送。作用域不是停止整个组呼或撤销所有参与者话权。 [§10.5.2.15–16](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

### 怎么辨方向、客户端和实际媒体？

| 请求 | 读什么 |
| --- | --- |
| **stop，§10.5.2.15** | 导语列 IWF↔MCPTT floor control server 两向。它表示指定通信的单播流**不需要再向 MCPTT ID 指明的客户端发送**，不是接收者应停播的确认，也不是要求整通停止。 |
| **resume，§10.5.2.16** | 导语同样列两向，同一句又说**由话权控制服务器用来请求发送**指定通信的单播流给该客户端。保留两处表述：不改成只有 server→IWF 一向，也不据双向名单就认任意发件人都有该角色。判现网先核实际源、目的和话权控制角色。 |

两表中 **MCPTT ID（M）** 写的是请求者身份，导语用同一个 ID 指明媒体所发往的客户端；没有独立的目标客户端 ID。**Functional alias（O）** 是请求者的别名。按互通方式和实际消息源、目的，ID 与别名可代表 LMR 用户、IWF 或 MCPTT 用户。不能仅按箭头方向，就把该 ID 当成网元自己、现有话权持有者或另一名客户端。

**Source identifier（O）识别通信**，例如复用媒体中这条要停发或恢复的流。表写只有媒体复用时才可出现：已知符合该表的消息带此字段，说明有复用；有复用仍不要求带它，缺字段不排除复用。真实日志只见这个值，不能代替对本次媒体复用、字段角色或整条消息合规的核实。它不是额外的客户端 ID，也不是 stop/resume 配对的事务 ID。

控制消息送出、对端收到、同一通信向该客户端实际发媒体、客户端实际收到媒体，是四件事。只问客户端有没有收到这一流，看它的媒体收件即可，不必先凑齐控制来回。要把媒体变化归给本次控制，还需核对同一通信、客户端及对应事件。只见 stop 不能证明停发，只见 resume 不能证明恢复；本节也没有要求先见匹配 stop 才能解释一条 resume。一段抓包未见媒体，不一定是真没发或没到；即使客户端未收到流，也不表示发过 stop。某端恢复接收不代表其他端也恢复。表没列结果或要求确认的字段，不能因此补一个成功应答，也不能把通用话权确认当媒体已停／恢复。整通释放、话权授予或撤销按各自的消息查。
