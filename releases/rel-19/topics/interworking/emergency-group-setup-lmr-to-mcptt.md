# LMR 发起、组定义在 MCPTT：原请求和逐人请求怎么区分？
**原建呼由 IWF 发给 MCPTT server（步骤 1），server 用步骤 9 回 IWF。** 若有主叫之外的已归属 LMR 用户，且 server 收到了这些用户的逐人归属，另有反向腿：server 向 IWF 逐人发请求（7），IWF 回 server（8）。这两组请求和应答不能交叉配对。

本页限 **TS 23.283 V19.5.0（Rel-19 Stage 2）§10.6.2.2.1**。实际主叫在 LMR，互通组定义在 MCPTT，MCPTT 侧有已归属客户端（图示 client 1 和 2）。IWF 已接入并获准与 MCPTT 互通，且已配置组和用户身份映射。主叫所在系统不决定组定义；图用一个 MCPTT server 表示用户本属与组托管两个服务器角色，不要求同机。查规范不需要抓包；判断现场才核实际发起端、组定义和对应事务。[§7.4.1、§10.6.2.2.1 前提与 NOTE 1，印刷页 15、121](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)。

## LMR 主叫身份怎么进入 MCPTT

1. **步骤 1：原请求。** IWF 向 MCPTT server 发 `IWF emergency group call request`，带所呼 MCPTT 组 ID 和紧急指示。告警指示可选，隐式话权只在发起端确实请求话权时带。原文不展开 LMR 内部如何触发；请求中有指示不证明告警送达或获准发言。
2. **步骤 2、3：先区分归属，再看授权。** LMR 主叫尚未归属时，server 隐式归属该 LMR 用户映射的 **MCPTT ID**。若 IWF 配置为代表全组 LMR 成员一次归属，则由 server 归属 **IWF**，不归属单个业务身份。代理分支原文称执行方为 `MC service server`，图只画 MCPTT server；不据此补另一个接口或服务器。步骤 3 仍检查 **LMR 主叫的 MCPTT ID** 是否获准在该组发起紧急呼叫，授权通过才解析组成员和实际归属。IWF 接入授权、映射或代理归属都不替代主叫授权。
3. **步骤 4–6：承载、组状态和 MCPTT 侧邀请。** server 配置 MCPTT 参与者底层承载的优先级，记录进行中组紧急状态；该状态持续至取消，期间后续呼叫取得调整后的承载优先级。步骤 6 向已归属 MCPTT 成员的客户端发紧急组呼请求；它只说明发送邀请，不等于这些客户端已收件或回包。

## 哪条应答是给谁的

| 配对 | 判别 |
| --- | --- |
| **1 → 9：原建呼** | 步骤 9 是 MCPTT server → IWF，回应已经收到的步骤 1。正文描述成功建呼通告；这条应答不是逐人请求 7 的应答，也不证明 LMR 主叫终端已收到结果。 |
| **7 → 8：其他 LMR 用户的可选腿** | 步骤 7 的触发条件是有**主叫之外的已归属 LMR 用户**，且 server 收到了**来自这些用户的逐人归属**。server 向 IWF 发逐人请求，IWF 在 8 回 server。已知其他用户各有逐人归属，就按这些成员查对应 7/8。末句写每名已归属 LMR 用户，不据此判主叫另收到一份；仅有主叫的归属、静态组员或 IWF 代理归属不足以触发 7/8。 |

图把 7、8 画成虚线，9 画成独立实线。**NOTE 5** 允许 9 在 5 之后发出；最迟随继续呼叫的条件在 8 之后。不能用图定每次 9 都等 8、全员回复或失败后的等待算法。§10.6.2.1 对 MCPTT 定义组概述了一次代理归属下发一条请求的情形；本支的步骤 7 明列其他 LMR 用户逐人归属作为条件。不能从这个概述给本支自动补一个 server→IWF 的代理建呼请求，也不借同组定义、MCPTT 发起的 .2.2 规则补它。[§10.6.2.1、§10.6.2.2.1 步骤 7–9 和 NOTE 5，印刷页 121–123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=122)；[原图，印刷页 122](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=123)；[正文 NOTE 5，印刷页 123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=124)。

IWF 应答表把 `Result` 列为必带，也允许拒绝；只见响应名不等于成功。请求和应答表的 `MCPTT ID` 都是**主叫**，不是被邀 LMR 用户；同组、同主叫不足以把某个 8 配到某条 7。判断实际收件要对准同次呼叫、同笔事务、端点和方向。接收端实际发出的匹配应答也能支持原请求到达；它不证明对端已收到应答。证实这条信令不需要媒体证据。[表 10.6.1.1-1、10.6.1.2-1，印刷页 117–118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=118)。

**步骤 10 才描述成功流程的媒体建立。** LMR 用户经 IWF 与已归属 MCPTT 客户端通话，主控是定义这组的 **MCPTT 系统**。实际 RTP 或音频另取证，不能从步骤 8、9 成功、server 记录组紧急状态或承载优先级推出来。NOTE 3、4 不规定 IWF 内部优先级动作或 LMR 系统如何叫人。这里也不规定 SIP 编码、拒绝处置、[在会话权覆盖](floor-override.md)、[整体释放](group-call-release.md)或紧急状态取消。[§10.6.2.2.1 步骤 4、5、9、10 和 NOTE 3–4，印刷页 122–123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=123)。

组仍在 MCPTT 但主叫换成 MCPTT，查[客户端配置及另一条 7/8](emergency-group-setup-mcptt-to-mcptt.md)。若组实际由 LMR 定义，则分[LMR 主叫](emergency-group-setup-lmr-to-lmr.md)与[MCPTT 主叫](emergency-group-setup-mcptt-to-lmr.md)；不要按同名 IWF 消息猜分支。[§§10.6.2.2.2–.4，印刷页 123–128](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=124)。
