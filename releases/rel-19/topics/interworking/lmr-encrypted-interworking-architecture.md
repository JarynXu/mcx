# LMR 加密互通：密钥归谁控制，媒体怎么走

适用：TS 23.283 V19.5.0，Rel‑19，Stage 2。

**密钥管理方案要支持什么，和媒体实际怎么传，是两个问题。** §5.1 约束加密互通的密钥机制；§5.2 说明某些互通会话需要继续传 LMR 格式媒体，不要求所有呼叫都让 IWF 解密。

## 加密互通要提供哪些密钥能力

| §5.1 的场景 | 原文要求的机制 |
| --- | --- |
| **私呼（a）** | MCPTT 侧一方与 LMR 侧一方之间，需要安全共享这一私呼会话的 LMR E2EE 流量密钥。此项的“安全”列明真实性、完整性和机密性。 |
| **MC 业务组或一组业务组（b）** | 向组成员安全传递与该业务组或这些组相关的 LMR E2EE 密钥或密钥集，用于跨系统互通组呼加密。 |
| **临时 MC 业务组（c）** | 向 **MC 系统内的临时组成员**安全共享与该临时组相关的 LMR E2EE 密钥，用于跨系统互通组呼。不把已知的组成组成员或所有 LMR 成员都当成这项的收件对象。 |

（b）按关联的业务组或组集和成员读，不额外排除临时组；（c）另给临时组的明确对象。业务组呼所用的密钥与下文用户的密钥加密密钥是不同角色。条款没有指派某个 KMS 或固定网元发出，也不证明某一人已收到、已装入或正在用这些密钥。

**方案要保留组织独占两类密钥的控制权和访问权的能力（d）。** 密钥管理方案不得排除这样一种能力：IWF 可以让一个或多个组织各自只由自己控制、访问本组织媒体流量所用的 LMR E2EE 流量密钥，以及用户的 UKEK 或 KEK。只能独占控制、但必须让别方访问，仍未保留这里的两项能力。条款不要求每个部署都启用独占，也不证明网关或运营方已获得访问权。

**IWF 的处理能力（e）另算。** 密钥管理方案须支持 IWF 对零个或多个组的媒体流量做解密／再加密。零个在这个范围内：没有任何组实际走这一处理，不能单凭这一点判方案违反（e）；也不能以零个为由省掉方案要支持的能力。多组能力并不表示每组都要处理或本次媒体已处理。

**部署方希望在与 LMR 用户互通时使用 LMR E2EE，才按（f）看这两种机制。** 一是给 MC 业务客户端安全配置该用户的 UKEK 或 KEK，二是传递 LMR 的 OTAR 或 OTAK 消息内容。§3.2 把 UKEK、OTAR 列为 P25 术语，把 KEK、OTAK 列为 TETRA 术语。这些是用户密钥加密密钥及相关 LMR 消息的名称，不代私呼或组呼的流量密钥。只看见某个安全消息内容在传，不证明用户密钥已装入或更新。

## 需要传 LMR 格式媒体时走哪里

**IWF‑1 是 IWF 到 MCPTT server 的参考点，不是客户端直连 IWF。** 某次互通需要在 IWF 与能识别该 LMR 格式的 MCPTT 客户端（LMR-aware）之间传媒体时，§5.2 要求 IWF‑1 承载 LMR 格式媒体。经过 IWF‑1 的媒体再按 TS 23.379 [7] 指向的方法，在 MCPTT 系统内路由至或来自这种客户端。只查规则不要求已知某次实际传送；问现场时，再分别确认要求的媒体格式、客户端能力、实际路由和相应接收。

原文举的例子是使用端到端加密、因而 IWF 不能解这份媒体。这是保留 LMR 格式的一个场景，不是唯一条件，也不能据此认定任何 E2EE 场景中的 IWF 都不能解媒体。MCPTT 系统与 IWF **可以选择**用 3GPP 机制加密这份 LMR 格式媒体。被加密的对象仍是 LMR 格式媒体；这项保护不证明内部 LMR E2EE 已用、支持解密或格式已转换。原文没定义 LMR 格式媒体的内容、实际编码或如何叠加保护。看到有加密、通话建立或媒体从某一端发出，都不能代对端实际收到或能处理。
