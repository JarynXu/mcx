# 互通组呼晚加入：归属成功与话权状态

适用版本：TS23.283 V19.5.0，Release 19，Stage 2。

正在进行互通组呼；双方已知组配置，IWF 已配置组及用户身份映射；参与侧成功完成组归属。

## 参与侧成功完成组归属

触发正在进行的互通组呼晚加入；适用于包括紧急、迫近危险和广播在内的组呼类型。 [§10.3.3.7.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 MCPTT 系统；LMR 用户加入

首名 LMR 用户适用两种 IWF 归属方式；后续用户仅在 IWF 逐个透传成员归属时触发此流程。MCPTT server 向 IWF 发组呼请求，IWF 响应后加入，并接收已占用或空闲话权状态。 [§10.3.3.7.2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 LMR 系统；MCPTT 用户加入

流程适用于首名及后续 MCPTT 用户。IWF 向 MCPTT server 发组呼请求，后者为新用户建立呼叫并响应；IWF 提供话权状态，经 server 转交新用户。 [§10.3.3.7.3](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

LMR 定义组的晚加入在 §10.3.3.7.3 step 4 还有媒体条件：指定 E2EE 时两侧须同 codec；未指定时可不同，不同 codec 需 IWF 转码。[加密转码专门流程](encrypted-transcoding.md)不能作为忽略此分支条件的通用许可。

话权已占用/空闲通知描述当前状态，不表示向新加入用户授予话权。成功归属是晚加入的触发条件，不是所有呼叫建立步骤已完成的证明。

## 一条晚加入应答能证明谁已经加入

**先按组定义侧区分两条流程。** 查某一步的含义不用现网记录。判断一次现场是否适用晚加入，才要对上实际已有组呼、组定义及配置、IWF 映射和参与侧成功归属。组成员资格、归属过程的发出，或一条名为 group call response 的应答，都不能单独证明这些前提或新端已加入。

### MCPTT 定义的组：server 叫 IWF，IWF 回应

1. IWF 向 MCPTT server 触发组归属（步骤 1）；发起晚加入的是 **server**（2），它随后向 IWF 发组呼请求（3）。前两步是过程和动作，不是额外的两条组呼请求。
2. IWF 向 server 回 IWF group call response，确认该请求（4）。步骤 5 才描述 IWF **及 LMR 用户**成功加入已有呼叫。图中步骤 5 的框只写 IWF，不能因此删掉正文的 LMR 用户，也不按图框认定所有 LMR 用户已加入。
3. 已经在通话中的 MCPTT 客户端 1、2 上的用户**可以**收到该 LMR 用户加入的通知（5），不是必通知，亦不是步骤 6 那条给 IWF 的话权状态。看见步骤 4 发出或 server 实收，不代表加入已完成或既有用户已获通知。NOTE 2 不规定 IWF 如何把**组呼请求**送到 LMR 系统，不能用图补 LMR 终端动作。

这张图是首名 LMR 用户加入的例子。首名可用两种 IWF 归属方式；之后同一组的 LMR 用户，仅在 IWF **逐个传递成员归属**时触发本支。不拿代表归属、成员名单或其它组的逐人记录代这次的实际归属。[§10.3.3.7.2 前提、图 10.3.3.7.2-1、步骤 1–6 及 NOTE 2，印刷页 48–49（PDF 第 49–50 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=49)。

### LMR 定义的组：IWF 叫 server，server 为新客户端建立

1. MCPTT 用户（客户端 1）先归属组（步骤 1）；IWF 向 MCPTT server 发 IWF 组呼请求（2）。server 为这个新归属用户触发建立呼叫的过程（3），回指 TS 23.379 [7]。3 是本地面向新用户的过程，不是 IWF 请求或回包。
2. server 向 IWF 回 IWF group call response（4），原文描述它确认呼叫建立成功。步骤 5 另说新客户端加入**已经进行的**组呼。确认了建立结果，也不能把发出、IWF 实收、这位客户端加入或收到媒体并为一个事件。本页上面的 codec 条件仍按步骤 4 读。
3. 原文说也适用于其后归属**同一组**的 MCPTT 用户。首名示例的前提是这通组呼当时只有 LMR 用户；不能据此排除已有 MCPTT 用户参加时的后续晚加入，也不复制上一支对 LMR 用户逐人归属的条件。NOTE 2 不规定 IWF 怎样把**归属**送到 LMR 系统，或 LMR 系统如何处理晚加入。

[§10.3.3.7.3 导言与前提，印刷页 49–50（PDF 第 50–51 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=50) · [图 10.3.3.7.3-1、步骤 1–7 与 NOTE 2，印刷页 50（PDF 第 51 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=51)。

### 谁收到这条话权状态

- **MCPTT 定义组（.2 步骤 6）：**server 向 IWF 发 IWF Floor Taken（话权已授给其他用户）或 IWF Floor Idle（没有任何一方获授话权）。本步只指定 IWF 为接收方，不能据此认定 LMR 终端实收，也不代步骤 5 给既有客户端的可选通知。
- **LMR 定义组（.3 步骤 6、7）：**IWF 先向 server 发 IWF Floor Taken 或 Idle（6）；server 再向**新归属的客户端 1 用户**发 Floor Taken 或 Idle（7，TS 23.379 [7] 指针）。这是两个发送动作，不是同一个 IWF 报文直接到终端。IWF 发送、server 实收、server 发送、客户端实收各用对应证据，不把它们和 .2 的已有客户端通知混用。

话权未知不能按 Idle 处理；两种状态都不是给新用户的话权授予。实际发生加入、获话权或收到媒体，各有证据。[.2 步骤 6，印刷页 49（PDF 第 50 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=50) · [.3 步骤 6–7，印刷页 50（PDF 第 51 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=51)。
