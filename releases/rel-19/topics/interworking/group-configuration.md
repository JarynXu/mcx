# 互通组配置：向谁获取

适用：Rel19，TS 23.283 V19.5.0。先确定组定义在哪一侧，再判断本侧是否缺配置。

| 请求方向 | 全部前提 | 请求及返回 |
|---|---|---|
| IWF → MC | 组定义在 MC；至少一位 LMR 用户是成员；IWF 未存配置 | 请求该组 primary MC 系统的 GMS；GMS 返回配置（§10.2.3.3，p30–31） |
| MC → IWF | 组定义在 IWF；至少一位 MC 用户是成员；MC 的 GMS 未存配置；MC 已配置 IWF 组管理寻址 | MC 请求 IWF 组管理功能；IWF 返回配置（§10.2.3.5，p32） |

## 查组配置的应答带配置还是带失败原因？

**看请求能否满足，不看 Result 是不是“成功位”。** TS 23.283 V19.5.0 的这两张表用于 Stage 2 的 IWF‑1 组管理。组管理服务器（GMS）和 IWF 都可发起查询。

| 信息流 | 字段 |
| --- | --- |
| **查组信息 .8** | 只列必带的 MC service group ID，指被查的 MC 服务组。不列用户、发起者、成员列表或服务选择。 |
| **查组信息应答 .9** | 也必带组 ID。MC service group provisioning information 在表中标 O，但**请求能满足时必须带**（NOTE 1）。信息取自 GMS；若由 IWF 提供，则取自 IWF。Result 也标 O，**不能满足时必须带**（NOTE 2），表示未能提供配置信息的原因，不是一个独立的成功标志。 |

两条注各给一个条件下的必带项。它们没有写另一项必须缺席，也没有给缺项、两项同见时的接收方处理规则。若已知请求能满足且完整应答确实缺组配置，则不满足 NOTE 1；若已知不能满足且完整应答缺 Result，则不满足 NOTE 2。抓包没看到一项，不能据此补出成功、失败或字段值。只抓到一条已辨认的应答也能读字段；要把它认作某次查询的回包，再核实际消息类型、目标组、两端和相关上下文。同组 ID 不是唯一配对键。[§§10.2.1.8–.9 两张表及表注，印刷页 24（PDF 第 25 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=25)。

**查谁，按本页开头的拉取条件选流程。** §§10.2.3.3/.5 不靠图注里的 partner 或 primary MC 字面判端点：

- **IWF 缺 MC 定义组的配置（.3）**：满足相应前提后，IWF 请求该组的 primary MC 系统的 GMS。图 10.2.3.3‑1 的步骤 1、2 确实标查组信息的请求／应答，方向先 IWF→GMS、再 GMS→IWF。
- **MC 的 GMS 缺 IWF 定义组的配置（.5）**：满足相应前提后，正文步骤 1 是 MC 向 IWF 的组管理功能索取，步骤 2 是 IWF 提供所请求的配置。图 10.2.3.5‑1 保留这个方向，但两个箭头写的是 **IWF group Information provision request／response**。不要把图字面改成 .8/.9，也不要只看 provision 就认定是 .10/.11 主动提供或把那两表的字段补进来；要读某一笔的字段，先辨认该笔实际的消息类型。

[§10.2.3.3 前提、步骤及图，印刷页 30–31（PDF 第 31–32 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=31)；[§10.2.3.5 前提、步骤及图，印刷页 32（PDF 第 33 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=33)。

查回的配置、对端实收、实际保存和再提供给成员是不同的事。.11 的主动提供应答将 Result 定义为报告接收、修改和保存的成功或失败；不借这个定义解释 .9。已知相同组 ID 也不够辨认操作：例如[撤组通知 .2](regroup-boundaries.md#重组的应答成立通知和撤组通知分别证明什么) 同样只列一个组 ID。查持续更新或拟用服务选择器，先分清是否为[组配置订阅与通知](configuration-updates.md)。[§§10.2.1.10–.12，印刷页 25（PDF 第 26 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=26)。

## 主动提供不等于被请求获取

组定义在 MC、至少有一位 LMR 成员，且 MC 已配置 IWF 组管理寻址并获准提供配置时，MC 的 GMS 可主动向 IWF 提供配置。IWF 响应确认正确接收并存储（§10.2.3.2，p30）。

组定义在 IWF 且至少有一位 MC 服务用户为成员时，IWF 可向 MC 的 GMS 提供配置，由 GMS 响应确认正确接收并存储（§10.2.3.4，p31）。这些前提没有额外要求接收方必须先缺少配置；不能照搬上面的拉取前提。

### 主动提供的应答确认了什么？

IWF‑1 的 **.10 请求带配置，.11 应答报处理结果**。两类信息流都可走 GMS→IWF 或反向；同一笔操作里，提供方发 .10，接收方回 .11。

| 信息流 | 必带字段 |
| --- | --- |
| **提供配置 .10** | MC service group ID 标明这次提供的是哪个组；MCPTT group configuration information 是该组配置。配置取自 GMS；若组定义在 IWF，则取自 IWF。不要把 .9 查组应答的条件必带项套到 .10。 |
| **提供配置的应答 .11** | 同一组的 MC service group ID，以及 Result。Result 报告组配置的**接收、修改和保存**成功或失败；表没有逐阶段结果，也没写要回一份配置。它不是 .9 的失败原因，也不是 .13 的订阅结果。 |

[§§10.2.1.10–.11 导语及两表，印刷页 24–25（PDF 第 25–26 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=25)。

上面的两个主动提供分支里，**.2 图与正文都是 GMS→IWF 提供，.4 图的箭头与正文都是 IWF→GMS 提供**；两边的应答都走相反方向。.4 的图注却仍写 MC 向 IWF 提供，不能按图注反转 .4。再看[反向拉取 .5](#查组配置的应答带配置还是带失败原因)：图 .5‑1 的箭头也写 provision，但正文是 MC 向 IWF **索取**。不能只看一个箭头名、方向或组 ID，就把 .4 的主动提供和 .5 的拉取合成同一流程。§10.2.3.2 的寻址可以是 IWF 的代理地址；地址本身不证明实际发出、授权或接收。[§§10.2.3.2/.4 正文及两图，印刷页 30–31（PDF 第 31–32 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=31)。

例如 GMS 发 .10，IWF 记录生成了同一次的成功 .11。可以说 IWF **报告**接收、修改和保存成功；仅凭这两条，还不能说 GMS 已实收应答，也不能确认 IWF 的当前生效状态、后续分发或其他成员收到更新。只有要关联实际请求与应答时，才按实际类型、组、端点和上下文配对；单查任一已辨认消息的字段不要求先找齐两条。

MC 系统的 GMS 还负责向由该 MC 系统提供服务的组成员提供组配置（§10.2.3.5 注）。

获取配置不是订阅确认；持续更新见[订阅与通知](configuration-updates.md)（§10.2.3.6–9）。总则 §10.2.3.1 另引用 TS23.280 §10.2.7，本页不补写该依赖。上述是 Stage 2 信息流，不给出 HTTP/SIP 编码、认证或失败重试规则。
