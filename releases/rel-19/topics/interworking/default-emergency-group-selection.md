# 互通紧急事件：选哪个组，要不要另发告警？

按 TS 23.283 V19.5.0，先分**谁决定用哪个组**、**是否还发告警**和**实际目标组是否有告警配置**。知道其中一项，不等于其余两项也已确定。

## MCPTT 看用户 profile，IWF 一侧另作判断

- **MCPTT 用户：**用户 profile 决定紧急事件是在用户**当前所选组**发起，还是在**配置的默认紧急组**发起。仅知道已配默认组，不代表本次选择了它；若默认组和当前所选组碰巧同为 D，仅凭报文中的组 ID D 也认不出 profile 走了哪支。此段没规定 profile 缺项或默认组没配时自动回退。
- **LMR 经 IWF 互通：**IWF 与它连接的 LMR 系统决定**在哪个组发起紧急事件**，也决定**是否还发告警**。不能从选中一个组就推出一定发告警，不能把 MCPTT 用户 profile 的选择逻辑当成 LMR/IWF 必用的算法。这里没写网关与 LMR 怎么分工、判定先后或精确发送时间。

[§10.6.2.5，印刷页 133（PDF 第 134 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=134)。

## IWF 能决定，不代表能越过 MC 的紧急参数

从 MCPTT 系统看，IWF **代表已映射到 MCPTT 的用户**执行的紧急行为，须符合 TS 23.379；实现也须遵守组呼或私呼的紧急相关参数。§2 对 [7] 没指定版本：指向同一 Release 的该规范最新版本，不据这里补 TS 23.379 的字段或判断顺序。

例子是**要在某个 MC service 组上发紧急告警**：这个实际目标组必须在 MC service 组管理系统里配置为可发紧急告警。若 D1 是本次目标、只有 D2 配了告警，不能用 D2 的配置代 D1，也不能据此说会自动改发 D2。即使 D1 已配，仍不能说这次决定了要发、发警者获准、告警已发或已经送达。这个配置条件针对在组上**发告警**，不等于没这项配置就不能发起紧急组呼或私呼。

原文列了两种执行办法：**正确配置 LMR 与 MCPTT 两侧**，或**由 IWF 在运行时执行**。它没要求两种都用；只配一侧不等于已满足前一种办法。用运行时办法也不是绕过目标组配置或省略其他条件。

[§10.6.2.5，印刷页 133（PDF 第 134 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=134)；[§2 非特指引用及 [7]，印刷页 11（PDF 第 12 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=12)。

## 已有一笔实际告警，换到对应消息流程

[LMR 发起告警](emergency-alert-init-lmr-origin.md)和[MC 发起告警](emergency-alert-init-mc-origin.md)各自的 Step 3 都要核对**本次发警的 MC service 用户 ID 对所指组的告警权限**；不能用组配置、IWF 互通许可或映射代替。面向已归属 MC 客户端的那笔消息另有组 ID：前者 Step 5、后者 Step 7 都按组配置取用户所选 MC service 组或专用紧急组。看到那笔成员消息的组 ID，不能倒推本次事件最初的选组方式、profile 结果或 IWF/LMR 的决定。要查是否实际发出、接收、组态和分段优先，也各取其证据，不从这里的组配置串过去。
