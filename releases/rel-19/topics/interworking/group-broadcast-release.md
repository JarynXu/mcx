# 互通组广播结束：哪一笔释放应答才回到发起端？

**接收端确认释放，不等于发起端已经收到结果。** 发起者结束传输后，客户端请求结束本次组广播。广播组定义在 MCPTT，服务器最后回发起端的是步骤 **6**；定义在 LMR，IWF 回服务器的 **7a** 触发步骤 **8**，后者才回发起端。两支的步骤号不能互换。

适用 **TS 23.283 V19.5.0，Rel‑19 Stage 2，§10.3.4.4–.5**。两图都从一个**正在进行的层级组广播**开始，发起客户端、接收客户端与 IWF 均参与；实际事件是发起者结束传输。按广播组的定义侧选分支，不按发起者、接收者或某个子组的归属。两图不要求重验建呼图中的原有非紧急子组呼叫；只见无声、话权结束、一个人退出或某个释放包，还不能确认这是本次组广播的结束。查规则不需要抓包。

| 广播组定义侧 | 请求与接收端确认 | 哪一笔回发起端？ |
| --- | --- | --- |
| **MCPTT（§10.3.4.4）** | 发起客户端向广播组的 MCPTT server 发 **2**。server 分别向接收端发 **3a**、向 IWF 发 **3b**，各自以 **5a**、**5b** 回 server。IWF 实际代表该组的 LMR 用户归属时，IWF 请求、应答各一条；server 实际收到逐人归属时，每名**已归属** LMR 用户各一条请求及对应应答。不从一个箭头、静态名单或不完整日志估算数量。 | **6：server → 发起客户端**，告知呼叫已结束；不拿 5a/5b 代替。图把 6 放在两类接收腿应答后，正文未规定全部逐人应答齐备的门槛，也未规定何时可提前回。 |
| **LMR（§10.3.4.5）** | 发起客户端向 MCPTT server 发 **2**，server → IWF 发 **3**。IWF 再向服务接收客户端的 server 反向发 **4**，server 转给接收客户端（图 **4a**）。接收客户端获结束提示（5）并回该 server（**6**），server 向 IWF 回 **7**，确认接收腿。 | **7a：IWF → server** 回原请求 3。IWF 得知接收端已确认后才回 7a，这条应答触发 **8：server → 发起客户端**。7 回反向的接收请求，不是 7a；本分支没有把接收端 6 列为可选，不套建呼的可选步。图只画一个 server 角色，正文用服务接收端来定位步骤 4；不据此规定两客户端共用一台服务器，也不强定是两个实例。 |

## 看字段和回包，分别能确定什么？

- **释放字段和建呼字段不同。** IWF‑1 的释放请求和应答均列必带 MCPTT ID、MCPTT group ID。请求表写的是组员，应答表写的是目标组员；组 ID 指本次要释放广播呼叫的组，不是独立事务标识。别把建呼表的主叫 ID、SDP 或其他流程的 Result 搬进来。释放请求表的预留 ID 只适用于请求来自 LMR 侧且 LMR 未提供主叫身份，不能从广播组定义在 LMR 或一个 IWF 发送方向判断这一条件。
- **原文有三处写法差异。** §10.3.2.7 标题和表是 release response，表前导语却写 release request。§10.3.4.4 步骤 3、5 的逐人句省略 release，操作和图仍是释放。该节步骤 4 正文写接收客户端和 IWF 各自通知用户，图只画客户端提示；两节的 NOTE 都未规定怎样通知 LMR 用户。不把这些字面差异当成另一条消息、可选回执或实际下游已通知的证据。
- **先对上这次、这条腿。** 同组、同成员 ID 不能替代实际操作、事务和端点方向。匹配的 5a、5b 或 7 能说明对应收件方已作该腿的释放确认，不等于另一腿或发起端已收到结果。只见 7a 发出，仍不能确认 server 已收到、更不能确认 8 已到。发起端实际收到匹配的 6（MCPTT 定义）或 8（LMR 定义），能确认该端取得结束结果；这不证明终端全员实收、LMR 侧已通知、RTP 停止或所有资源已清除。核信令收件不要求先有媒体证据。
