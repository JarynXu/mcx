# 互通 chat 初建：授权、位置与按需媒体

TS23.283 V19.5.0，Release 19，Stage 2。

TS23.283 §10.3.5.1–3 的初建路径；与已在进行中呼叫的新成员加入分开。

## 组定义在 LMR，server 与 IWF 已知组配置，IWF 身份映射已配置；MCPTT 用户发起 join

server 将 join 转往 IWF，IWF 接纳并选择媒体参数；server 转回响应。请求发言/发送媒体且媒体面尚未建立时，server 建立媒体面。 [§10.3.5.2](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 LMR，server 与 IWF 已知组配置，IWF 身份映射已配置；MCPTT 用户发起 join，且 join 携主叫位置

server 核对请求用户的位置隐私策略，判断能否向其他 MCPTT 用户及 IWF 提供位置，依结果决定转给 IWF 的请求是否携位置，不能仅因原请求有位置就无条件转发。 [§10.3.5.2 steps 2–3](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 MCPTT，IWF 已知配置且身份映射已配置，MCPTT 用户已加入/归属；LMR 用户发起 join

IWF 向 server 请求 join；server 核验 MCPTT ID 的归属授权，未归属时生成隐式归属，接纳并选媒体参数。IWF 请求发言/发送媒体且媒体未建时，server 才建立媒体面。 [§10.3.5.3](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

Join 接纳不是话权授予；也不能把 MC→LMR 的位置隐私处理步骤擅自补到另一方向。

## 旧通话结束后，同组再呼还用话权信令吗？

**后续同组呼叫期间，只要该组仍有至少一位用户已归属，就继续用带话权控制的媒体面信令。** 这是 §10.3.5.2 步骤 7 和 §10.3.5.3 步骤 5 的第二句。它不要求留下的是原主叫、此前占话权的人或某个固定系统的用户。组内仍有人归属，也不表示会自动起呼、上次的媒体连接仍在，或现有用户已获话权。

两步的第一句是：**本通呼叫期间，各自的话权参与方继续使用话权控制。** .2 是 MCPTT 客户端和 IWF 所关联的话权参与方；.3 是 MCPTT 客户端 1、客户端 2 和 IWF 所关联的话权参与方。图末画出媒体面话权信令；不能只看图，就把“至少一位用户仍归属”读成当前话权归谁、谁已发出信令或媒体已经到达。[§10.3.5.2 步骤 7，印刷页 64（PDF 第 65 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=65)；[§10.3.5.3 步骤 5，印刷页 65（PDF 第 66 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=66)。

例如组 G 上一次成功释放，原主叫 A 已取消归属，但 B 仍实际归属 G。若随后又有 G 的呼叫，B 就可满足这条后续信令条件；若只知道 B 在组名单、以前归属过或别组仍有归属，证据就不够。若确认 G 已无用户归属，**这两句不说明接下来怎么办**，不能补成自动拆除或永久停用话权。释放另有条件；.4 步骤 6 和 .5 步骤 7 说明成功释放该通 chat 呼叫及相应话权和媒体资源，不改变客户端的组归属状态。它不证明释放以后一定还剩一人，或同一媒体连接会沿用。[§10.3.5.4 步骤 6 与 .5 步骤 7，印刷页 66–67（PDF 第 67–68 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=67)。

### 初建时的媒体和位置另查各自条件

- **媒体建立与 join 应答分开。** .2 的 4 是 IWF 向 server 返回接纳及 IWF 选定参数，5 才是 server 回原 MCPTT 客户端；6 写该客户端请求发送、媒体尚未建立时，由 server 建立媒体。.3 的 3 是 server 回 IWF、带 server 选定参数，4 写 IWF 请求发送、媒体尚未建立时，由 server 建立媒体。各条的发送、对端实收、实际获话权和媒体发送分别核对。已建立的媒体不因此要再建一次；这里也不为其他过程添加同样的启动条件。
- **不要把两条位置规则合并。** .2 步骤 1 写请求发送时带隐式话权指示和按需的加入者位置；步骤 2 先看原请求是否带位置，实际带了才按本步查隐私策略，3 按结果决定转给 IWF 的请求是否带位置。图里的隐私框没有改成无条件检查。.3 步骤 1 先写 IWF 的请求**可含发送方的位置**，另写请求发送时带隐式话权指示和按需的加入者位置。不能把首句的可选位置全部改写成只准随隐式指示发送，也不从 .2 补出反向的隐私步骤。.3 步骤 2 查的是 MCPTT ID 的组归属授权，隐式归属的条件是该 ID 尚未归属，不是话权授予。

[§10.3.5.2 步骤 1–6，印刷页 64（PDF 第 65 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=65)；[§10.3.5.3 步骤 1–4，印刷页 65（PDF 第 66 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=66)。实际是**加入已经在进行的呼叫或回覆盖**，另读[进行中呼叫加入](chat-entry.md)；实际要结束本通呼叫，读[chat 释放](chat-release.md)。这两条后续信令规则不给原生消息次序、承载重用、失败处理或 LMR 内部规则。
