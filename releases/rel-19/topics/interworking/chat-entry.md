# 互通 chat 加入与回到覆盖区

TS23.283 V19.5.0，Release 19，Stage 2。

TS23.283 §10.3.5 的 chat 组呼；不能直接套用预安排组呼触发条件。

## 组归属 LMR，呼叫正在进行；MCPTT 客户端已注册，用户已认证且获服务授权；客户端尚未加入，用户表示要加入

客户端携组 ID 发 join，经 server 到 IWF；IWF 接纳响应返回后建立媒体。只有请求发言时才携隐式话权请求。 [§10.3.5.8](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组定义在 MCPTT 系统，MCPTT 用户已加入且呼叫进行中；IWF 尚未加入

IWF 以 LMR 成员对应 ID 或代理用预配置 ID 发 join；server 对尚未归属者生成隐式归属，并验证 IWF 归属授权，接纳后建立媒体。 有发送请求才携隐式话权请求；携该请求时，位置信息仍为可选。 [§10.3.5.9](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

## 组归属 LMR；客户端在进行中 chat 呼叫期间离开无线覆盖，随后回到覆盖

客户端或 server 检测恢复后重建客户端与 IWF 媒体面；有人占话权时 IWF 经 server 转交 floor taken。检测机制不在规范范围。 [§10.3.5.10](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf)

隐式话权请求是请求，floor taken 是现有占用状态，二者都不等于新加入者已获授话权。回覆盖流程也未要求重新创建组。

## 新加入和回覆盖，谁回包、谁重建媒体？

先分**谁还没有进入组呼，还是原来就在呼叫中**。§10.3.5.8–.10 是正在进行的 chat 组呼，不是初建或预安排晚加入。查规范或一条已辨明的消息，不要求先找到全链。

| 场景 | Join 与媒体 | 通知与话权 |
| --- | --- | --- |
| **LMR 定义组，MCPTT 客户端尚未加入（.8）**。客户端已注册，用户已认证、获准用业务且表示要加入。 | **1** 客户端→MCPTT server，**2** server→IWF；**3** IWF→server 报告接纳该 join，**4** server→客户端转发应答。**5** IWF 与这名客户端建立媒体面。 | **6** IWF 可通知自己的用户有 MCPTT 用户加入。已有话权持有者，**7a** 才由 IWF→server 发送当前发言者的 IWF Floor Taken；MCPTT 端收到该类消息，**7b** 再向该客户端转告。**8** 通话期间继续使用话权控制。 |
| **MCPTT 定义组，IWF 尚未加入（.9）**。用户 1、2 先前已加入该组，其客户端已在同一通呼叫中。 | **1** IWF→server 发 join。**2** 按 IWF 本次使用的 MCPTT ID 处理：若 IWF 或 LMR 用户尚未归属目标组，server 生成隐式归属；同时还检查 **IWF** 是否获准归属。**3** server→IWF 回接纳；**4** MCPTT server 建立 server 与 IWF 间的媒体面。 | **5** 可以通知原来就在呼叫中的用户 1、2：IWF 已加入。**6** server→IWF 发当前发言者的 Floor Taken；此处没重复 .8／.10 的“有人持有才发”句，也未规定无人时发什么。**7** 两客户端与 IWF 相关的话权参与者继续使用话权控制。 |
| **LMR 所属组，客户端在进行中的 chat 通话时离开无线覆盖，后来返回同一通话（.10）**。 | **1** 客户端或 server 可检测已经回覆盖，检测方法未定义。**2** 用媒体面控制信令重建客户端与 IWF 间的媒体面；本节没有列再次发 join 或新建呼叫的步骤。 | 有人持有话权时，**3a** IWF→server 发 IWF Floor Taken，**3b** server→返回覆盖的客户端转告。**4** 继续使用话权控制，不是重新授予返回者话权。 |

[§10.3.5.8 前提、步骤及图 10.3.5.8‑1，印刷页 68–69（PDF 第 69–70 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=69)；[§10.3.5.9 前提、步骤及图 10.3.5.9‑1，印刷页 69–70（PDF 第 70–71 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=70)；[§10.3.5.10 前提、步骤及图 10.3.5.10‑1，印刷页 70（PDF 第 71 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=71)。

**不要用一个应答证明下游动作。** .8 步骤 3 是 IWF 回 server，步骤 4 才回 MCPTT 客户端；只见 3 发出，不证明 server 已收或客户端已收 4。.9 仍未加入的是**本次呼叫**，不等于尚未归属该组；图 2 把隐式归属和授权检查画在一个框里，正文只给隐式归属加条件，不能凭看见 join 或缺逐人记录判授权已过。图的媒体框或通知框不证明某端真收，话权通知也不证明新加入者获授、发了媒体或有人听到。只核一种结果，取该端对应证据；要把消息或状态归到同一次，才核这通 chat、组、角色、操作和两端的对应关系。

要查 IWF join 请求的 ID、必带与可选字段或 .9 步骤 1 的隐式话权和位置条件，见 [IWF 消息字段](group-call-operation-elements.md#怎样读代理身份话权和实际结果)。预安排组呼晚加入、chat 初建及归属流程分别查对应主题，不从这些信令推 SIP 编码、回覆盖检测算法或无发言者时的替代消息。
