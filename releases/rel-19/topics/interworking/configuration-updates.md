# 互通组配置：订阅与通知

适用：Rel19，TS23.283 V19.5.0，Stage 2。

| 订阅方 → 提供方 | 全部前提 |
|---|---|
| IWF → 组的 primary MC GMS | 组定义在 MC；至少一位成员定义在 LMR；IWF 已从该 GMS 收到组信息（§10.2.3.6，p32–33） |
| MC GMS → IWF | 组定义在 LMR；至少一位成员定义在 MC；GMS 已从 IWF 收到组信息（§10.2.3.8，p33–34） |

双方的订阅响应都指明成功或失败；收到组信息不能代替订阅成功。

订阅之后，MC GMS 收到并存储新配置时通知 IWF；反方向是 IWF 有新组信息时通知已订阅的 MC GMS。通知接收方返回成功或失败（§10.2.3.7/9，p33–34）。

## 订阅请求发给谁，成功应答说明什么？

**按该组的主系统定方向，不按发送者的名字定。** 这里是 TS 23.283 V19.5.0 的 IWF‑1 组管理，不是终端侧订阅。

| 同一 MC 服务组的主系统 | .12 订阅请求 | .13 订阅应答 |
| --- | --- | --- |
| MC 系统 | IWF → MC 的 GMS | MC 的 GMS → IWF |
| IWF | MC 的 GMS → IWF | IWF → MC 的 GMS |

.12 必带 MC service group ID。可选的 **MC services requested** 指这次要订阅哪些服务的组配置；带它时可从 **MCPTT、MCData** 中列一种或多种。表没有说省略表示订阅全部、默认 MCPTT 或取消；这两个值也不是对其他消息或能力的全局限制。.13 必带组 ID 和 **Result**，后者报告该次订阅请求成功或失败。表不列配置本身、服务选择器的回显或各服务的结果。[§§10.2.1.12–.13，印刷页 25（PDF 第 26 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=26)。

表定的是两种方向；按实际过程选支还要核上面的组定义侧、成员条件和**先前从哪一端收到本组信息**。例如 .6 要 IWF 已从该组 primary MC 的 GMS 收到组信息；.8 要 MC 的 GMS 已从 IWF 收到，并保留正文的「组定义在 LMR」。不能把表中的「IWF 是主系统」直接换成「刚收到组信息」或把 LMR 与 IWF 互作同义词。[§§10.2.3.6/.8 正文及图，印刷页 32–34（PDF 第 33–35 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=33)。

只看到一条确认为 .13 的消息，也能读它报告的成败。要说它是这次 .12 的回包、或请求方已经收到，再分别核配对和到达。**订阅成功不等于已发生变更通知、已收到新配置或已应用配置**；后续通知看本页开头的 .7/.9。已有配置也不能代替这一笔订阅成功。

## 组配置变更通知带什么，应答成功说明什么？

**.14 可以带组信息引用、组相关密钥材料，或两者都带；两个都不带不满足表注。** 这是 TS 23.283 V19.5.0 的 IWF‑1 组管理通知。它与主动提供配置本身、订阅应答是三种不同的信息流。

| 同一 MC 服务组的主系统 | .14 通知请求 | .15 通知应答 |
| --- | --- | --- |
| MC 系统 | MC 的 GMS → IWF | IWF → MC 的 GMS |
| IWF | IWF → MC 的 GMS | MC 的 GMS → IWF |

- **.14 请求**必带 MC service group ID，指被通知的组。MC service group information reference 指向已保存的该组相关信息；Group related key material 是该组使用的密钥材料。这两项各标 O，NOTE 要求**至少一项**。任带一项满足这条存在条件；两项都带也不违反它。已确认完整的 .14 中只有组 ID，不满足这条 NOTE；截断日志只看见组 ID，不能判定两项实际缺席。表没写引用的取用方法、缺项处理、密钥授权或何时启用。
- **.15 应答**必带组 ID 和 Result。Result 报告**这次通知请求**成功或失败；不是 .11 主动提供的接收、修改和保存结果，也不是 .13 的订阅成败。只查一条已辨认的应答，不必先找到 .14；要把它归给某次通知，再核消息类型、组、两端和上下文。同组 ID 加 Result 不能区分这三种应答。

[§§10.2.1.14–.15 导语及两表，印刷页 25–26（PDF 第 26–27 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=26)。

**发生什么才走通知流程？** 图 .7‑1 与正文是 primary MC 的 GMS→IWF：IWF 已订阅这组的信息，且该 GMS 已**收到并保存**本组新配置。图 .9‑1 与正文是 IWF→MC 的 GMS：GMS 已向 IWF 订阅这组，且 IWF 有新组信息；此处没有另写 IWF 必须先收到并保存配置。两支都由接收方回通知结果。.9 步骤 2 正文的消息名多一个 notify（IWF notify group information notify response），图与 .15 表用 IWF group information notify response；三处都只描述一次应答，不另造一个消息或通用 ACK。[§§10.2.3.7/.9 前提、步骤和两图，印刷页 33–34（PDF 第 34–35 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=34)。

例如在 MC 为主的组 G，GMS 发 .14，只带组 ID 和引用。该通知可满足表注，不代表 IWF 已取到引用内容。若 GMS 随后实收对应的成功 .15，可确认它收到了 IWF 报告的通知结果；仍不能确认 IWF 实际获取、保存或启用了配置，也不能确认组员收到更新。通知前提、请求发出、对端实收、应答实收和各节点应用情形分别判断。若要查主动提供配置本身，读[主动提供及其应答](group-configuration.md#主动提供的应答确认了什么)；[订阅方向和结果](#订阅请求发给谁成功应答说明什么)留在本页上一节。
