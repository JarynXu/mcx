# 互通组配置：订阅与通知

适用：Rel19，TS23.283 V19.5.0，Stage 2。

| 订阅方 → 提供方 | 全部前提 |
|---|---|
| IWF → 组的 primary MC GMS | 组定义在 MC；至少一位成员定义在 LMR；IWF 已从该 GMS 收到组信息（§10.2.3.6，p32–33） |
| MC GMS → IWF | 组定义在 LMR；至少一位成员定义在 MC；GMS 已从 IWF 收到组信息（§10.2.3.8，p33–34） |

双方的订阅响应都指明成功或失败；收到组信息不能代替订阅成功。

订阅之后，MC GMS 收到并存储新配置时通知 IWF；反方向是 IWF 有新组信息时通知已订阅的 MC GMS。通知接收方返回成功或失败（§10.2.3.7/9，p33–34）。

## 订阅请求发给谁，成功应答说明什么？

**按该组的主系统定方向，不按发送者的名字定。** 这里是 TS 23.283 V19.5.0 的 IWF‑1 组管理，不是终端侧订阅。

| 同一 MC 服务组的主系统 | .12 订阅请求 | .13 订阅应答 |
| --- | --- | --- |
| MC 系统 | IWF → MC 的 GMS | MC 的 GMS → IWF |
| IWF | MC 的 GMS → IWF | IWF → MC 的 GMS |

.12 必带 MC service group ID。可选的 **MC services requested** 指这次要订阅哪些服务的组配置；带它时可从 **MCPTT、MCData** 中列一种或多种。表没有说省略表示订阅全部、默认 MCPTT 或取消；这两个值也不是对其他消息或能力的全局限制。.13 必带组 ID 和 **Result**，后者报告该次订阅请求成功或失败。表不列配置本身、服务选择器的回显或各服务的结果。[§§10.2.1.12–.13，印刷页 25（PDF 第 26 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=26)。

表定的是两种方向；按实际过程选支还要核上面的组定义侧、成员条件和**先前从哪一端收到本组信息**。例如 .6 要 IWF 已从该组 primary MC 的 GMS 收到组信息；.8 要 MC 的 GMS 已从 IWF 收到，并保留正文的「组定义在 LMR」。不能把表中的「IWF 是主系统」直接换成「刚收到组信息」或把 LMR 与 IWF 互作同义词。[§§10.2.3.6/.8 正文及图，印刷页 32–34（PDF 第 33–35 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=33)。

只看到一条确认为 .13 的消息，也能读它报告的成败。要说它是这次 .12 的回包、或请求方已经收到，再分别核配对和到达。**订阅成功不等于已发生变更通知、已收到新配置或已应用配置**；后续通知看本页开头的 .7/.9。已有配置也不能代替这一笔订阅成功。

保留条款的“组定义在 LMR”措辞，不与[拉取流程](group-configuration.md)中的“IWF”擅自合并。定时器、重订阅、可靠投递及编码未覆盖。[来源](../../sources.json) · [结构化条件](configuration-updates.json)
