# IWF 紧急与迫近危险组呼：指示、身份和应答

**两类组呼应答都只列主叫、组和 Result。** 三个字段一样，不能据此判断应答是哪一类，也不能把主叫当成这条请求要通知的成员。本页读 TS 23.283 V19.5.0、Rel‑19 Stage 2 的 [IWF‑1 信息流](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=16)。四张表的导语均列 IWF↔MCPTT server 两个方向；先认实际消息类型、角色和接口，不按方向或相同字段配对。查一张表或一条已辨认消息，不用先找到来回、取得媒体或证明建呼成功。

## 请求里哪些项区分类别

| 已辨认的请求 | 字段和适用条件 |
| --- | --- |
| **IWF emergency group call request**（表 10.6.1.1‑1） | **Emergency indicator 是 M**，指本次紧急建呼。Alert indicator 是 O，可指示要发紧急告警；指示不是独立告警请求，也不是告警已经发出或到达。 |
| **IWF imminent peril group call request**（表 10.6.1.3‑1） | **Imminent peril indicator 是 M**，指本次迫近危险建呼。表未列 Alert indicator，不能从这里推出其他流程不许发告警。 |

两表的 MCPTT ID 都是**主叫**，与本次要呼叫的 MCPTT 组 ID 一样列 M。Functional alias 属于主叫，列 O。Location 也列 O，原文是“如可用”。有位置不让它变成 M，也不证明已经测量或获准传播。两表都未列 SDP offer；普通建呼表的 offer 和 LMR 未给主叫时的预留 ID 表注，不能填作这两表自己的规则。

### 两张表的隐式话权注释不同

两表的 Implicit floor request 都列 O。**紧急请求**的 NOTE 只要求发起客户端请求话权，才可带；不附加迫近危险表的方向文字。**迫近危险请求**的 NOTE 则同时写这条信息流为“从客户端到服务器”以及发起者请求话权。保留该表双向的 IWF↔server 导语和这条 NOTE，不把 IWF→server 自动认成客户端→服务器，也不把 MCPTT 客户端发给 server 的字段自动复制到 IWF 腿。

按表合规且带该项时，才能据相应 NOTE 得出必要条件；满足条件不等于必须带，缺项不证明没有申请。若实际已辨认紧急请求、确认该项出现且发起客户端没有请求话权，已足以判断这项不符合 NOTE，不用等整笔报文齐备。迫近危险也按各条件判断：已确认发起者未请求时，不必等方向明确才判这一项不符；没有证据时不补未知角色或方向。只有断某项真实缺失或整笔合规，才核报文完整性。带申请指示不等于已授话权。

[§10.6.1.1 表与 §10.6.1.2 导语，印刷页 117（PDF 第 118 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=118)；[§10.6.1.2 表、.3 与 .4，印刷页 118（PDF 第 119 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=119)；[§10.6.3.2 步骤 2 与 7，印刷页 134–135（PDF 第 135–136 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=135)。

## 应答里的 Result 没有换成媒体结果

紧急应答（表 10.6.1.2‑1）和迫近危险应答（表 10.6.1.4‑1）都是 **主叫 MCPTT ID、MCPTT group ID、Result 各 M**。各自 Result 的描述写相应请求可以被拒绝；没有列完整的结果值、SDP answer 或成员结果列表。应答出现在日志里，或只知道其中一个 ID，不等于成功、拒绝、实际收件或媒体已建立。已辨明应答且知道 Result 的实际含义，可直接记录该条报告了什么，例如拒绝。要把这个结果归给某笔请求才核两条是否匹配；主叫端是否实收、全组是否获准另取证。

相比之下，[普通 IWF 组呼](group-call-request.md)的 §10.3.2.2 请求列 SDP offer（M）；普通 §10.3.2.3 应答的 MCPTT ID 指**目标 MCPTT 组成员**，列 SDP answer（M）而没有 Result 行。不合成一个公共模板。也不能仅由原请求类型给应答定类：在 [§10.6.3.3 的既有迫近危险组场景](imminent-peril-group-call-lmr-origin.md)，原来的 Step 1 是 IWF 普通请求，Step 5 回该请求的是迫近危险应答。单查表不要求两条都出现；要将应答归给一笔真实请求，再核同次、端点及匹配证据。判断实际收件、建呼、媒体、话权和组状态，要各取对应证据。

[普通组呼对照表，§10.3.2.2/.3，印刷页 35–36（PDF 第 36–37 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=36)；[§10.6.3.3 步骤 1、2、5 与图，印刷页 136（PDF 第 137 页）](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=137)。

只读四张表，不展开原生客户端信令、SIP 编码、失败重试或其他参考点。实际是独立紧急告警时，按[MC 用户发起](emergency-alert-init-mc-origin.md)或[LMR 用户发起](emergency-alert-init-lmr-origin.md)分流；[取消迫近危险组状态](imminent-peril-group-state-cancel.md)也另查，不套建呼表。具体互通过程按主叫和组定义侧分流。
