# MCPTT 发起迫近危险互通组呼：IWF 可以拒绝吗？位置能给谁？

**建呼时，IWF 不支持迫近危险组呼可以拒绝。** 这和[取消该组的迫近危险状态](imminent-peril-group-state-cancel.md)不同，取消时 IWF 即使不支持这类建呼也要应答。建呼里的 IWF 应答也不是给主叫的应答。位置可选，MCPTT server 按主叫的隐私策略判断能否把位置给其他通话中的 MCPTT 用户及 IWF。

## 进入这条流程要满足什么

本页限 **TS 23.283 V19.5.0（Rel-19 Stage 2）§10.6.3.2**：MCPTT 用户起呼，主叫客户端已配有**指定用于迫近危险通信**的组，且这个互通组定义在 MCPTT。图中另一 MCPTT 客户端已归属，至少一名 LMR 用户也已归属；IWF 接入并获准互通，已配组和用户身份映射。不能用静态名单或 IWF 仅已接入代替实际归属。相邻[紧急组呼的所选组紧急行为](emergency-group-setup-mcptt-to-mcptt.md)是 §10.6.2.2.2 给出的替代条件，不搬到这里。图只画一个 MCPTT server，代表用户本属和组托管两个角色，不规定同机。查规范不需要抓包。[§10.6.3.2 前提和 NOTE 1–3，印刷页 133–134](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=134)；[紧急组呼 §10.6.2.2.2 NOTE 3，印刷页 123](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=124)。

| 步骤 | 判断 |
| --- | --- |
| **2、3** | client 1 向 server 发迫近危险建呼请求，带迫近危险指示；可附隐式话权请求及主叫位置。未归属的主叫客户端在 3 被隐式归属。请求里的迫近危险指示不能证明 server 已记组状态；也不要求组原先已处于该状态。 |
| **4** | server 核主叫获准在**这个互通组**发起迫近危险呼叫，许可通过才解析成员与实际归属。另查主叫的定位隐私策略，判断能否把其位置给其他通话中的 MCPTT 用户及 IWF。位置字段、起呼许可和归属都不代替位置传播许可。没附位置、没许可位置传播，不由此推出整通拒绝；有许可也不能说已发送、已收件或定位已更新。 |
| **5、6** | server 配置组参与者的底层承载优先级并记录组的迫近危险状态及发起用户。状态和发起用户的记录保留到状态取消；期间后续呼叫取得调整后的承载优先级。不从承载优先级推话权或媒体已通。 |

[图 10.6.3.2-1、步骤 1–2，印刷页 134](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=135)；[步骤 3–6 与 NOTE 4，印刷页 135](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=136)。步骤 4 引用 TS 23.379 Annex A.3 的发言时位置传播策略；这里核的是 server 作出位置许可判断，不规定隐私策略字段或 LMR 下游分发。

## 对上 IWF、成员和主叫的信令

- **7 → 8：互通腿。** MCPTT server 向 IWF 发迫近危险组呼请求。IWF 已代表全组 LMR 用户作一条归属时只发一条；server 收到逐人归属时，为每名实际已归属的 **LMR 用户**各发一条，IWF 向 server 回对应的 8。表 10.6.1.4-1 的 `Result` 必带；正文的成功路径不排除拒绝，NOTE 5 允许不支持时拒绝，不规定不支持一定拒绝、唯一失败原因或全组失败后的处置。请求/应答表的 `MCPTT ID` 指主叫，不是被邀终端；同组同主叫不足以配对不同成员腿。
- **9：MCPTT 成员腿。** server 向每名已归属的 MCPTT 组成员的客户端发请求，带迫近危险指示。正文还描述成员获通知，并按 TS 23.379 确认；图将它们合为邀请框。server 已发不证明这一成员已收、已确认或全组一致，不能借 .3.3 或取消分支的组播确认规则补这里的协议细节。
- **10 → 11：主叫应答在前，媒体另看。** 10 是 server 向发起用户回步骤 2 的成功路径应答，不是 IWF 的 8。NOTE 7 把 10 放在 **5 后、11 前**，取决于继续呼叫的条件；不能把图中 7–9 的排列固定成每次必等 8 或 9，也不能把这条注当作 IWF 拒绝后照样成功的依据。11 才描述经 IWF 的 LMR 用户和已归属 MCPTT 客户端建立媒体，由定义该组的 **MCPTT 系统**主控。实际 RTP 或音频另需同次媒体证据。

**一个字段的原文边界：**表 10.6.1.3-1 把请求描述为 IWF 和 MCPTT server 双向信息流，却在隐式话权项下注写“客户端到服务器”且发起者请求话权。步骤 2 是 client→server，可按其条件带隐式话权请求；正文没有说明把这项复制到向 IWF 发的步骤 7。保留表的方向差异，不凭步骤 2 或表注断定 IWF 两向消息该怎么编码，也不把请求中的隐式指示当授予话权。表中的位置、主叫功能别名均可选，主叫 MCPTT ID、MCPTT 组 ID 和迫近危险指示必带。[表 10.6.1.3-1、10.6.1.4-1，印刷页 118](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=119)；[图与步骤 2，印刷页 134](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=135)；[步骤 7–11、NOTE 5–7，印刷页 135](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=136)。

核实际到达时，找同次呼叫、组、主叫、事务及对应端点方向的接收证据。接收端确实发出的匹配回包也能佐证原请求到达，但不证明原发送端已经收到这个回包。**信令取证无需媒体；信令也不能代替媒体。** LMR 不原生支持迫近危险，[§10.6.3.1](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=134)说 IWF 可向 LMR 传播为普通或紧急组呼，没指定选哪类，也不写 LMR 内部叫人或 IWF 优先级动作。不要从可传播推实际选择、收件或互通成功。

若是 LMR 用户发起普通组呼且该组**已经**在 MCPTT 的迫近危险状态，查 §10.6.3.3 的另一条第一跳，不套这里的 MCPTT 客户端触发。整体[释放](group-call-release.md)、[晚加入](late-entry.md)、[话权覆盖](floor-override.md)和[原生 MCPTT 的迫近危险请求与反馈](../emergency/group-imminent-request-feedback.md)各有入口。本文不映射 SIP 编码、拒绝状态码、完整失败流程或 LMR 内部机制。[§§10.6.3.3–.4，印刷页 135–138](https://www.etsi.org/deliver/etsi_ts/123200_123299/123283/19.05.00_60/ts_123283v190500p.pdf#page=136)。
